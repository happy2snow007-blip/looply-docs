## 七、问题清单

### P1

#### P1-01 推荐横滑映射不符合统一动作表达，无法唯一落为稳定字段

- **位置**：事件工作簿`新增与修改`第47行“动作”；公共规则3.4。
- **类型**：准确性／完整性。
- **场景与影响**：公共规则规定动作列必须按`interaction_name：action → element_id → target_id`读取。第47行PC段把“PC点击previous／next”放在action位置；Mobile段写成“Mobile左滑／右滑且列表实际移动 → next／previous → recommendation_rail → placement_id”，比统一协议多一层。开发可猜测PC action应为`previous/next`、Mobile左滑／右滑应映射`next/previous`，但无法按表内协议唯一判断哪些文本是触发条件、action和element_id；测试也无法直接形成四个稳定Payload断言。
- **最小处理建议**：拆成明确的PC与Mobile映射，或在同一行分别完整写出：PC的`recommendation_rail + previous/next + recommendation_previous/recommendation_next + placement_id`，Mobile的`recommendation_rail + next/previous + recommendation_rail + placement_id`；“手势结束且实际移动”只放触发条件／说明，不占action字段。
- **产品决策**：不需要新取舍，当前文字已经给出左滑对应`next`、右滑对应`previous`，只需机械闭合格式。

#### P1-02 `share_channel`没有稳定值、来源与未知值处理

- **位置**：事件工作簿`新增与修改`第21行“参数／说明”；公共规则第五、六章和新增公共字段表均无定义。
- **类型**：完整性／准确性。
- **场景与影响**：用户选择具体分享渠道时，材料只要求增加`share_channel`，但未说明取UI稳定ID、平台名、系统分享目标还是展示文案，也没有值域、大小写、未知渠道或无法取得时的处理。PC和Mobile可以分别发送`Facebook`、`facebook`或应用包名，开发均未违反现有文字，却会拆分同一分析维度；测试无法写唯一断言。
- **最小处理建议**：在一个唯一位置定义`share_channel`的业务来源、稳定允许值或标准化规则，以及无法识别时省略还是使用封闭值；事件行只引用。`copy_link`已经是独立action，不应再作为渠道值重复记录。
- **产品决策**：需要产品确认稳定业务值域或明确引用的现有权威枚举；不能交给开发自行选择。

### P2

#### P2-01 `method`枚举与OAuth生命周期在三个位置完整定义，并指定实现机制

- **位置**：事件工作簿`新增与修改`第7、8行“说明”；公共规则第六章`method`。
- **类型**：重复／冗余／产品技术边界。
- **场景与影响**：四值枚举、OAuth跳转前暂存、回调成功发送、清理及缺失处理在`sign_up`、`login`和第六章各维护一次。当前答案一致，但任一处单改会漂移；“暂存／清理”还规定了实现步骤，而产品只需约束成功事件携带实际选择且不得复用陈旧值。
- **最小处理建议**：第六章作为唯一枚举与业务结果位置，改写为“成功事件携带用户本次实际选择的method；无法取得时省略，不伪造或沿用上次值”；两个事件行只保留字段名并引用第六章，具体跨跳转保存方式由技术方案决定。

#### P2-02 点击ID的值域、生产和缺失规则存在三套权威位置

- **位置**：新增公共字段表第24–25行；公共规则5.4第3、6–9条；公共规则第六章`click_id_type`。
- **类型**：重复／冗余／唯一权威位置。
- **场景与影响**：字段表完整列出六个类型、生产方、来源和缺失；5.4再次列出六值、生产、成对、优先级和缺失；第六章又重复六值。5.4第3条同时声明字段生产、来源和缺失以字段表为唯一依据，与后续条目实际重复定义不一致。当前值相同，但以后增加渠道时至少有三处可漂移。
- **最小处理建议**：只保留一个完整值域。建议5.4维护跨字段白名单、成对和优先级；字段表的值域列引用5.4并只保留字段级生产／来源／缺失；第六章`click_id_type`改为引用5.4，不再复制六值。或者反向以字段表为权威，但必须保证其余位置只引用。

#### P2-03 新增跨事件规则在事件行和公共规则重复完整维护

- **位置**：事件工作簿`新增与修改`第15、16、18行“说明”；公共规则3.2、5.2第6条、5.5。
- **类型**：重复／冗余。
- **场景与影响**：`exposure_id`生成／点击沿用／缺失处理、推荐请求只使用`placement.request_id`且不新增顶层字段、同一搜索页Query参数变化沿用`page_instance_id`并不发`page_view`，均在具体事件行和公共规则各完整定义。事件参数列已经列出需要携带的字段，说明列再次维护跨事件规则没有独立信息；后续改一处会造成双发、关联失败或页面访问计数漂移。
- **最小处理建议**：公共规则3.2、5.2、5.5保留跨事件定义；事件表参数列保留`exposure_id`、`placement.request_id`和搜索上下文字段，说明列改为只引用对应章节，不复制生成、沿用、缺失和禁用规则。

#### P2-04 历史v1.7非依赖和三份基线声明重复维护

- **位置**：事件工作簿`新增与修改`第3行；新增公共字段表第29行；公共规则首部及第一章。
- **类型**：重复／冗余。
- **场景与影响**：开发只读三份v1.5、不读取历史v1.7的边界在三份材料至少四处完整说明。删除两个工作簿中的重复正文不会改变实施或验收；未来版本号或基线组成变化时容易只更新部分位置。
- **最小处理建议**：公共规则第一章作为唯一基线和阅读顺序权威；工作簿只保留“开发基线与历史材料边界见公共规则第一章”的引用。历史来源可留在独立变更日志，不在每份正式正文重复解释。
