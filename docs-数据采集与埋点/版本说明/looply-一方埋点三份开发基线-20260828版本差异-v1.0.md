# Looply 一方埋点三份开发基线 2026-08-28 版本差异

> 版本：v1.0  
> 日期：2026-08-28  
> 用途：开发先看本文了解本轮变化，再按当前三份开发基线实施  
> 对比范围：2026-08-26开发基线 → 2026-08-28开发基线

## 一、差异总览

| 文档 | 旧版本 | 当前版本 | 本轮结论 |
|---|---|---|---|
| 详细埋点需求定稿 | v1.2 | v1.3 | 12个当前无生产入口点位转入“停止项”；6个售后点位补齐多商品及物流复制契约 |
| 公共基础字段需求定稿 | v1.1 | v1.1（不变） | 没有新增、删除或改名公共字段；`order_item_ids`为售后事件专属字段 |
| 一方埋点公共实施规则 | v1.7 | v1.8 | 增加售后多商品、防重复、物流复制与不适用点位处理规则 |

当前开发基线阅读顺序为：本文 → 详细埋点需求定稿v1.3 → 公共基础字段需求定稿v1.1 → 一方埋点公共实施规则v1.8。

本轮只调整Looply一方埋点，不修改GA4事件、参数或报表口径，也不要求产品新增当前不存在的页面或控件。

## 四、6个售后点位的契约变化

| 点位 | 旧问题 | 当前契约 |
|---|---|---|
| `pt-0192`物流复制 | d4弹窗可取得`shipment_id`，d3页面内复制只有物流单号 | d3、d4都发送同一事件；`target_id=shipment_id`；增加`copy_source=d3_inline/d4_modal`；d3数据链路需提供`shipment_id`，不得用物流单号冒充 |
| `pt-0196`原因弹窗打开 | 多商品时只有单个`order_item_id`字段 | 一次操作一条事件；`target_id=order_id`；`order_item_ids`传本次申请涉及的订单商品行数组 |
| `pt-0197`原因弹窗关闭 | 同上 | 同上 |
| `pt-0199`新增凭证 | 同上 | 同上 |
| `pt-0200`移除凭证 | 同上 | 同上 |
| `pt-0202`提交退货申请 | 多商品无法用单个`order_item_id`表达 | 一次提交一条事件；`target_id=order_id`；`order_item_ids`传数组；继续使用`result_state/failure_type`表达成功、请求失败和校验失败 |

“多商品退货”仅指同一订单内一次申请涉及多个订单商品行，不支持一次操作跨多个订单。单商品也传单元素数组；数组去重并按稳定顺序排列，不得按商品行拆成多条事件放大操作次数。

## 五、开发实施动作

1. 在事件Schema／机器契约中，为`pt-0196/0197/0199/0200/0202`增加事件专属`order_item_ids: string[]`，并支持单元素与多元素数组。
2. 保持上述五个点位的`target_id=order_id`；接收、存储和消费层不得再把它解释为单个`order_item_id`。
3. 为`pt-0192`增加`copy_source`封闭枚举，并保证d3页面内复制链路可以取得真实`shipment_id`。
4. 对数组进行去重和稳定排序；同一次UI操作只生成一个`event_id`，不得按订单商品行批量生成多条同义事件。
5. 将12个无生产入口点位标记为`disabled/not_applicable`或等价状态，并从覆盖率分母和必测Active清单中排除。
6. 保留12个点位的历史记录和ID，不删除、不复用，不新增当前不存在的产品控件来“满足埋点”。

## 六、测试验收重点

- d3页面内复制和d4物流弹窗复制均能发送`pt-0192`，`copy_source`正确，且`target_id`为真实`shipment_id`。
- 单商品退货的五个操作均发送单元素`order_item_ids`；多商品退货发送完整、去重、稳定排序的数组。
- 多商品提交只产生一条`pt-0202`；成功、请求失败、校验失败的结果字段仍正确。
- 不同订单不得合并进同一个`order_item_ids`数组。
- 12个不适用点位在生产路径不可触发，且不进入Active覆盖率分母；原ID仍被保留。

## 七、明确未变化

- 公共基础字段表继续使用v1.1；本轮没有新增公共字段。
- GA4采集、GA4参数和GA4报表均不在本轮修改范围。
- 订单、支付、成交、退款等权威业务事实边界不变。
- 除上述12个不适用点位和6个售后点位外，其他点位的事件语义、触发时机和字段口径不变。
