## 四、模拟评审问题

### P0：阻塞最终开发或视觉基线

#### 1. [设计 / 开发] PC 最终 UI 基线互相冲突

- **位置**：PRD 2.1.2、2.1.3、2.1.9、7.1、7.2；PC 视觉稿 v0.2 第 12–16 行；交互原型 v0.1 第 52–67 行。
- **具体场景**：开发进入 PC 页面实现时，PRD给出线性顺序，PC v0.2 给出 Hero + 左信息 / 右表单 + Contact Strip，交互原型则给出左表单 / 右信息。Footer v0.3 把 Contact Us 放在 Support，PC v0.2 又放在 About。开发无法判断哪份制品是唯一基线。
- **建议方向**：先确认 PC v0.2 是否为正式基线；若是，同步修正 PRD、交互原型和 Footer 区域，PRD 2.1.9 直接引用该文件。

#### 2. [设计 / 测试] Mobile 与非默认状态没有正式 UI

- **位置**：PRD 2.1.9、7.1；Checklist 四、六。
- **具体场景**：设计和测试验收字段错误、验证中、成功、失败、离开确认及 Mobile 页面时，只能看到 PRD 文字和演示原型，无法确认最终字号、错误位置、Loading、弹窗和长文案换行。
- **建议方向**：补齐 Mobile 默认态和 PC / Mobile 关键状态 UI，或明确本次交付只评审业务逻辑、不进行视觉验收。

#### 3. [开发 / 设计] Google reCAPTCHA 的产品版本和跨端体验未闭合

- **位置**：PRD 2.1.7、三、7.3。
- **具体场景**：PRD 同时覆盖 PC Web、Mobile Web 和 App，却只写 `Invisible reCAPTCHA` 和“风险需要时展示挑战”。Google 官方资料区分 Web 的 Invisible reCAPTCHA、其他版本及 Mobile SDK；当前文案也未说明是否隐藏 badge。开发和测试无法为 Native App 与 Web 写出同一套可判定验收标准。
- **建议方向**：由产品、技术和安全共同确认 Web 与 Native App 的具体产品形态；PRD 只保留用户可见的统一结果，并明确 badge 是否隐藏。若隐藏，保留当前 Google 声明。
- **处理结论（2026-07-30）**：已确认当前版本不接入 hCaptcha、Google reCAPTCHA 或其他 CAPTCHA；相关声明、验证步骤、状态、异常、埋点和外部依赖已从当前 PRD、Checklist 与原型中删除。

#### 4. [开发 / 测试 / 隐私] 表单个人信息的保存边界未定义

- **位置**：PRD 1.2、2.1.6、三“邮件服务”“隐私与数据处理”；Checklist 3.2。
- **具体场景**：用户提交姓名、邮箱和留言后，PRD 只规定发送至 `service@looply.com`，没有说明 Looply 是否另建 Contact Us 记录、邮件系统保存多久、谁可访问，以及删除依据。开发无法确定数据承载范围，测试也无法判断“未建立历史记录”是否包含后台记录。
- **建议方向**：确认本期是否仅进行服务端转发、不建立独立业务记录；邮件及必要日志的保存、访问和删除按最终 Privacy Policy / 内部数据规则引用，不在 PRD 中虚构期限。
- **处理结论（2026-07-30）**：已确认本期不建立独立 Contact Us 业务记录或用户侧咨询历史；邮件为唯一业务记录；必要技术日志不记录 Full Name、Email 或 Message 原文。邮件的访问、保存和删除按 Looply Privacy Policy 及客服邮箱管理规则执行。

### P1：规则不完整，影响实现与测试质量

#### 5. [开发 / 测试] 登录用户默认态与自动带入规则冲突

- **位置**：PRD 2.1.1、2.1.4、2.1.5。
- **具体场景**：登录用户打开页面时，2.1.4 要求姓名和邮箱自动带入，但默认态写“空表单”。测试无法判断登录态默认用例的预期。
- **建议方向**：把默认态拆成游客默认态和登录用户默认态，或改成“展示用户状态对应的初始表单”。
- **处理结论（2026-07-30）**：已将默认态改为按登录状态展示初始值：游客三个字段为空；登录用户自动带入 Full Name 和 Email，Message 为空。

#### 6. [测试 / 开发] 校验规则无法从当前原型完整验收

- **位置**：PRD 2.1.4、2.1.5；交互原型 v0.1 第 66、71 行。
- **具体场景**：用户输入超过长度、从 Email 失焦或留空 Email 时，PRD 与原型给出不同结果；真实点击 Send 还会跳过验证中状态。
- **建议方向**：以 PRD 的已确认校验规则为权威，补充“基础邮箱格式”的可测试口径，并同步原型的失焦、最大长度、空邮箱文案和验证中流程。

#### 7. [开发 / 设计] 账户信息读取和局部加载异常缺少可执行规则

- **位置**：PRD 2.1.1、2.1.8、三“用户账户信息”“公共页面框架”。
- **具体场景**：登录用户打开页面后立即输入姓名，而账户姓名稍后返回时，PRD 未说明是否覆盖用户已输入内容；“公共页面错误规则”“表单局部失败 Retry”也没有对应规范或文案引用。
- **建议方向**：明确账户初始值的读取完成时点及不覆盖已编辑值的原则；公共错误规则必须引用实际存在的公共规范，否则删除不可发生的局部加载状态或在本 PRD 内定义可见结果。

#### 8. [测试 / 客服] 提交结果未知后重试的重复咨询规则缺失

- **位置**：PRD 2.1.5、2.1.6、2.1.8。
- **具体场景**：邮件服务实际已受理，但页面因网络超时显示失败；用户点击 Send 重试后，客服可能收到两封相同邮件。当前只禁止验证中 / 提交中重复点击，未说明结果未知后的业务预期。
- **建议方向**：确认同一次用户提交在重试场景下是否要求避免产生重复咨询，并把用户可见结果和客服侧预期写清；具体实现方式由技术决定。

#### 9. [数据 / 测试] 埋点枚举无法覆盖直接访问和多字段同时错误

- **位置**：PRD 五。
- **具体场景**：用户通过收藏链接或外部链接直接进入 Contact Us 时，`entry_source` 只有 `footer`、`me`；三个字段同时错误时，`invalid_field` 是记录一条、三条还是数组没有定义。
- **建议方向**：增加 `direct` / `unknown` 等已确认入口口径，并明确多字段错误的事件记录方式。

#### 10. [开发] 跨文档依赖仍引用旧版本

- **位置**：Footer PRD v0.3 第 62 行；Contact Us PRD 1.5、2.1.9。
- **具体场景**：Footer 开发清单仍引用 Contact Us PRD v0.1，而当前评审版本为 v0.2；Contact Us PRD 又只把 `/pages/contact` 写成 UI 参考，没有明确最终目标页采用 Footer v0.3 的 `/contact-us`。
- **建议方向**：形成评审基线后同步 Footer 的依赖版本，并区分“线上内容参考地址”与“Looply 新站正式路由”。
