# Looply 数据分析需求对采集方案影响评估

> 版本：v0.2  
> 日期：2026-08-19  
> 评估对象：《Looply 数据分析报表 PRD v0.2》《Looply 报表指标与数据来源对照表 v0.2》  
> 对照基线：《Looply 数据采集与埋点产品需求 v1.7》  
> 门禁：本评估用于核对报表与采集方案一致性，不代表运行环境已经接入。

## 一、评估方法

### 1.1 结论分类

每个评估项只使用以下一种结论：

1. 当前采集已满足；
2. 只需分析侧计算，不改采集；
3. 需要补充现有事件的业务信息；
4. 需要新增统一事件；
5. 直接读取业务表，不新增埋点；
6. 需要产品进一步确认。

“当前采集已满足”表示当前产品采集方案已经覆盖所需事件、公共上下文或字段，不表示运行环境已经实现或报表已经有数据。

### 1.2 总体结论

- 新版五模块报表没有发现必须新增统一事件的确定性需求。
- 当前17个客户端统一事件、5类权威业务事实和一方公共上下文可以覆盖页面、搜索、推荐、商品意向、Checkout、成交和归因所需事实。
- 订单、支付、售后、退款和广告花费应读取权威业务表／平台数据，不为报表重复新增埋点。
- 主要增量集中在三个方向：补齐稳定字典／事件业务信息、完成分析侧计算、收口曝光与结果状态等产品规则。
- 采集方案覆盖与运行接入必须分开验收；本评估不把 Active 契约、Planned 事件或目标字段写成已上线。

## 三、按结论汇总

### 3.1 当前采集已满足

当前采集产品方案已经覆盖：

- 页面、身份、一方 Session 和原始来源触点；
- 搜索提交、结果终态、商品选择、商详、收藏、加购和 Checkout；
- 推荐请求、模块、曝光、点击和原始来源；
- 订单成交回指原始 Session；
- 站内外归因所需的用户行为和来源上下文；
- GA4 自动用户、Session、互动、页面、设备和地域数据；
- 搜推策略／实验作为专项遥测的边界。

这些结论不代表环境已经生效。Snowplow Active 契约、期望白名单和产品目标仍需按环境做全链路运行验收。

### 3.2 只需分析侧计算，不改采集

主要包括：比例、人均值、日／周／月趋势、新客 Cohort、来源映射、行为联合去重、站外／站内归因、成本和 ROAS。分析结果需保留规则版本，不覆盖原始事实。

### 3.3 需要补充现有事件的业务信息

本轮确定需要补充的是 `page_view` 的稳定页面类型、页面 ID、页面版本字典与实际页面映射。字段方向已存在，不新增事件。

搜索触发方式和推荐模块字典也存在补齐需求，但由于其中仍有产品定义分叉，先归入“需要产品进一步确认”，确认后再判断是否只补字典。

### 3.4 需要新增统一事件

当前确定项为：**无**。

若后续决定页面／模块直达加载结果无法由现有事实表达，才重新评估是否需要新增结果事实；本轮未确认前不得先加事件。

### 3.5 直接读取业务表，不新增埋点

包括订单、订单商品、支付成功、成交金额、售后、退款、广告花费及商品级优惠分摊。页面操作与业务状态分开，不用 UI 事件冒充权威结果。

### 3.6 需要产品进一步确认

| # | 待确认项 | 会影响什么 | 未确认时处理 |
|---|---|---|---|
| 1 | 无结果后的首个有效动作全集、并列顺序和观察截止 | 无结果去向下钻和 Search 诊断 | 不冻结动作分布，不新增事件 |
| 2 | “猜你想搜”的枚举归属 | 搜索触发方式表和 `search` 业务信息 | 保留展示项，暂不修改字典 |
| 3 | 页面／模块直达加载结果的表达方式 | 空态、失败率、模块稳定性和页面状态验收 | `page_view`继续只表示到达；内容结果不宣称已闭合 |
| 4 | 无曝光点击是否可参与站内订单归因 | 搜索／推荐来源的归因订单和金额 | 点击保留为质量异常；归因资格暂不冻结 |
| 5 | 无前序来源的商详成交是“直接商详”还是“站内来源未知” | 站内归因来源类型、未知占比和下钻解释 | 暂按“站内来源未知”展示，不修改采集枚举 |

## 四、使用边界

- 搜索上下文规则已经写入《数据采集与埋点产品需求 v1.7》，本评估不再保留旧采集文档门禁。
- 第3.6节尚未确认的项目只影响对应报表派生规则；确认前不得写成已实现能力。
- 采集方案覆盖不等于运行接入，正式报表仍需用真实事件和权威业务表验收。
