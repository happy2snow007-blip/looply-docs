## 一、概述

### 1.1 背景与目标

**背景**

looply 是面向海外市场的二手奢侈品电商平台。红布林（国内二奢平台）是 looply 的核心货源方，通过 API 向 looply 推送在售商品数据。此前 looply 依托 Shopify 建站，商品上架依赖「Excel 导出 → 人工导入 → 调 Shopify API 创建并发布」的半自动链路，受 Shopify 的 API 限流与批量写入约束，必须人工分批操作。

looply 自建商品系统后，上述外部约束消失，红布林对接链路需要重构为**全自动流水线**。

**目标**

1. 红布林推送的商品数据 100% 落库留底，不丢不失败
2. 选品定价、翻译、标品对齐、主数据映射、实体创建、上架校验**全流程自动化**，人工只处理异常
3. 红布林侧的状态变化（售出/下架/重新上架）与信息变化（折扣价/图片/品类）自动同步到 looply 商品系统
4. 折扣价变更引发的挂牌价重算，由系统算出建议价 B，运营分波勾选执行（把价格改到 B）；不设"采纳/维持/自定义"的逐行决策层（对齐 v3.1.2 的 3.4 改价规则，见 §2.8）

**与现有业务系统（Shopify 版 v3.1.2）的关系**：本模块是对 v3.1.2 中「3.1 商品上架 / 3.5 商品清理 / 4.1 选品定价 / 4.2 商品翻译」四个模块的重构与合并，详见附录 7.2。

### 1.2 不做什么（边界）

| 不做的事 | 原因 / 归属 |
|---|---|
| **订单履约链路** | 已拆分为独立模块「红布林订单对接」，含下单、支付、国内发货、集货仓、报关、国际物流、取消退回 |
| **批量打标 / 营销选品** | 筛选条件全部是商品系统标准字段，无红布林特有字段，对象不限红布林来源 → **归商品系统**，已记入商品模块待优化清单第 7 条 |
| **主动促销调价（大促 / 清仓）** | 与红布林折扣价无关，属商品系统渠道商品价格运营能力。本模块⑥只处理"折扣价变更倒逼的挂牌价重算"，运营不能在此凭空发起促销降价 |
| **人工确认上架** | 原为 Shopify 限流产物，自建系统已取消（见 §2.5.4） |
| **标品（SPU / 标品SKU）人工维护页** | 数据量大，人工逐款建标品不可行，改为系统自动创建 + 回填映射表 |
| **渠道库存分配** | 不在 V1 范围 |
| **商品详情页渲染规则** | 归商详模块，本模块只负责把英文数据写进 product / listing |
| **未上架商品的查看入口** | 去商品系统「渠道商品」列表查看，本模块不再提供上架页 |

### 1.3 用户角色

| 角色 | 职责 | 涉及页面 |
|---|---|---|
| **商品运营** | 处理加工异常、映射异常、上架校验异常；维护主数据映射 / 翻译术语库 / TRR 参考价 / 定价规则；对价格变更商品分波勾选并批量执行 | 全部 6 个页面 |
| **系统（自动任务）** | 接收推送、选品定价、翻译、标品对齐、映射、创建实体、校验上架、状态同步、算建议价 | 无界面 |

> V1.0 不做角色权限细分，所有商品运营人员权限一致，故 §六 权限与角色矩阵省略。

### 1.4 核心场景

1. **新商品自动上架**：红布林推送 → 留底 → 自动定价+翻译 → 款型对齐标品 → 属性映射 → 自动建 product/库存/listing → 自动校验 → 上架销售。全程无人工。
2. **异常修复**：加工异常（术语未命中）/ 映射异常（新颜色值）/ 上架校验异常（中文残留、url_slug 冲突）→ 运营在「红布林商品库」集中筛出并修正 → 系统自动重跑。
3. **商品售出/下架**：红布林推送下架信号 → 系统内部判断售出/普通下架/重新上架 → 清零或恢复库存、联动 listing 与 product_status。
4. **折扣价变更调价**：红布林折扣价变 → 系统按定价公式算出建议价 B → 进「商品调价处理」→ 运营按波次筛选并勾选本波 ready 商品 → 执行本波（把价格改到 B，走价格写入 4 规则）→ 回读验证；不勾选即"维持原价"。
5. **规则源维护**：运营在主数据映射 / 翻译术语库 / TRR 参考价三页补充或修订规则，系统按 §2.1.4 自动重跑受阻商品并重算存量（含已上架），**全程无人工确认**；`url_slug` 一经生成永不变更。

### 1.5 后台菜单地图与页面流转

**菜单归属**：本模块页面最终并入**商品系统**后台，聚合在其下的「**红布林货源**」分组中（对接层命名空间），与商品系统自有菜单区隔。菜单结构：

```
商品系统（后台）
└── 红布林货源                          ← 本模块，对接层命名空间
    ├── 红布林商品库（默认首页 · 快照层视图）
    ├── 商品调价处理                    ← 折扣价变更触发的挂牌价重算作业台
    └── 对接规则                        ← 加工/映射/定价所需的规则源
        ├── 主数据映射（10 个 Tab）
        ├── 翻译术语库（18 个 Tab = 15 类术语对照 + 3 类拼接规则）
        ├── TRR 参考价
        └── 定价规则                    ← 新增（v1.1）：②选品定价所用公式与顺序的运营可编辑规则源（§2.12）
```

> **为什么用「红布林货源」命名空间**：依据 §1.2 的跨模块归属判据——依赖红布林特有数据的能力（快照层视图、折扣价调价、对接规则源）留在对接层。未来接入第二个货源时，可平行新增「XX 货源」分组，红布林特有能力不散落到商品系统各处。
> **TRR 参考价的归属**：TRR 是三方市场参考数据，V1.0 因仅服务红布林定价公式而暂放本分组；它有上移至商品系统「商品定价」域的合理性（自营/其他货源定价也可能用），列入后续评估。

**页面流转**（跳转关系不受菜单结构影响）：

```
红布林商品库（默认首页）
  ├─ 筛「加工异常」→ 行内「去修正」弹窗 → 补英文/术语 → 回到列表
  ├─ 筛「映射异常」→ 行内「去映射」→ 主数据映射页
  └─ 行内「详情」→ 红布林原始信息弹窗（只读）

对接规则
  ├─ 主数据映射 → 行内「新增映射 / 编辑（影响范围预览）/ 删除」弹窗 / 批量导入
  ├─ 翻译术语库
  ├─ TRR 参考价 → 「导入」（按品牌全量覆盖）
  └─ 定价规则 → 行内「新增 / 编辑 / 调序 / 删除」+ 操作记录

商品调价处理
  └─ 「规则说明」弹窗
```

> 本模块共 6 个作业/规则页面，聚合在「红布林货源」分组下（含一层「对接规则」子分组）。②③④⑤ 四个环节为系统自动流程，**无独立页面**，其运行结果体现在「红布林商品库」的状态字段上。

### 1.6 术语说明

| 术语 | 含义 |
|---|---|
| **快照层** | 红布林推送数据的全量留底层，以红布林商品ID 为主键，保存中文原始值，后推覆盖 |
| **款型ID** | 红布林**款型库**的款型标识（红布林侧已有的标品主数据，一个款型 = 一个具体规格的标准品），与 looply 标品SKU **1:1 对应**，是标品层的对齐键。★**不是品牌系列（series）**——系列是 SPU 级的营销归类（如 Speedy、Classic Flap），款型是 SKU 级的具体规格；一个系列下有多个款型 |
| **标品SKU（standard_sku）** | 商品系统标品层实体，多件实物商品可共用同一标品SKU |
| **SPU** | 标准产品单元，品牌/系列/类目外键挂在此层 |
| **product（实物商品）** | 一物一码实体，只挂 `standard_sku_id` 一个主数据外键，品牌/系列/类目经 `standard_sku → spu` 继承 |
| **listing（渠道商品）** | 渠道销售实体，承载挂牌价、货币、上架状态、`url_slug` |
| **信息准备进度** | 快照层的加工进度状态（本模块特有），见 §2.1.1 |
| **product_status** | 商品系统的标准商品状态（共 7 态），本模块只写入其中 4 态 |
| **主数据映射** | **英文标准值** → 商品系统标准记录 ID，产物是 **ID**（落外键）。输入来自②翻译产出，**不是中文原始值** |
| **翻译术语库** | 中文值 → **英文标准值** + 拼接规则。产物既用于拼商品名，也作为③映射的查表 key；**业务上承担归一职责**（多个中文写法收敛到同一英文标准值） |
| **TRR 参考价** | 三方市场参考均价（The RealReal），按品牌+系列+尺码+成色四维、**按标准名匹配**，不挂自建实体 ID |
| **A / B / C** | A=折扣价/汇率（USD 成本基数，**汇率可配置**，V1 默认 6.86，见 §2.4）；B=挂牌价（定价公式输出，ceil 到整数 USD）；C=TRR 均价（USD）。**A、B、C 全部为 USD 维度，任何比较均在 USD 下进行**（v1.1 修量纲，见 §2.4 与附录 7.4） |
| **汇率（CNY→USD）** | 折扣价 CNY 换算 USD 成本基数 A 的除数。**可配置、不硬编码、不接实时汇率**；V1 默认 6.86。每次定价计算保存实际使用的汇率值与版本号，保证历史可复现（每商品保留最新 + 上一次成本版本） |
| **CostPrice（成本）** | 商品成本，权威归 **sourcing 域**（本模块加工/价格上下文），**不再向 inventory.unitCost 双写**（v1.1，OQ-004，见 §2.5.3）。**保留整数、小数位向上取整**（v1.2 调整，如算得 100.1 → 定价 101） |
| **定价错误** | 取整后 **A > B**（成本高于挂牌价）时的状态：阻断成本/价格写入与自动上架，不截断成本伪造利润（v1.1，OQ-018，见 §2.4） |

### 1.7 多语言支持

**A. 静态 UI 文案 — 不做国际化**

本模块是**国内商品运营团队使用的中文后台**，界面文案固定中文，不接入前端语言包，不做 i18n。

> 若后续有海外运营人员使用，再单独提需求接入语言包。

**B. 动态业务内容 — 本模块是英文内容的生产者**

本模块的产出物（product / listing 的英文字段）直接面向 C 端多语言展示，产出规则：

| 产出字段 | 来源 | 说明 |
|---|---|---|
| `product.title`（英文商品名） | 翻译术语库拼接生成（§2.10） | 中文原始值 → 术语库取英文 → 按拼接规则组装 |
| `product_inspection` 成色/瑕疵/配件描述 | 翻译术语库 | 同上 |
| `listing.url_slug` | `slugify(Brand+' '+ProductName)+'-'+ItemID` | 见 §2.5.4 及风险 R4 |
| 品牌 / 系列 / 类目 / 属性英文名 | **不由本模块产出** | 来自商品系统标准记录，本模块只落 ID |

**关键约束**：本模块写入 product / listing 的英文字段**必须无中文残留**，这是上架校验的阻断项（§2.5.4）。

**C. 翻译职责的三层归属（v1.1 明确 · OQ-008）**

已核实商品模块：looply 的正式多语言翻译由**独立的翻译模块**承载（`translation` 表，`resource_type='product'`，**该模块已上线**，见多语言模块 PRD v3.1）。据此明确本模块与翻译的三层边界，避免 sourcing 域自建平行翻译体系：

| 层 | 职责 | 归属 | 产物 |
|---|---|---|---|
| **第一层 · 产英文源文的工具** | `plm_glossary`（翻译术语库）把中文原值转成**英文标准值 / 英文源文**，并按拼接规则组装英文 Product Name | **本模块（sourcing 域）** | 英文标准值（供③映射查表）+ 英文源文本 |
| **第二层 · 英文源文入库** | 英文源文直接写入 **Product 字段**（title / description / condition_desc / appearance_desc / extra_desc / accessories_desc 等） | 商品系统 Product | product 英文源文 |
| **第三层 · 多语言翻译** | 英文之外语种的译文生产、译文生命周期、Key 注册与清理 | **翻译模块**（`translation` 表，已上线） | 各语种译文 |

**关键界定**：
- `plm_glossary` 只是"中文→英文标准值"的**生产工具**，**不是**平行的翻译卡；本模块**不自建**面向多语言的翻译记录。
- **本模块只产英文源文**；product.title 等自由文本的**译文生产与多语言 Key 注册归翻译模块**，按翻译模块规范执行，本模块不自建平行体系。
- **Fallback 规则**引用多语言模块 PRD v3.1 §4.6：有译文返回译文 → 有过期译文返回旧译文 → 无记录返回英文源文本。故本模块产出的英文源文即 C 端的兜底展示内容。

## 二、需求详细描述

### 2.1 公共机制：状态模型

> 本模块**不单独出 ER 图**，也**不在 PRD 定义数据实体与字段**（v1.2 调整）——实体字段、表结构、索引、约束由**技术环节设计并保证**。本节只定义业务状态模型与规则源变更的重算规则。

#### 2.1.1 信息准备进度（本模块特有状态）

| 枚举值 | 含义 | 触发时机 | 后续 |
|---|---|---|---|
| `to_process` 待加工 | 已留底未加工 | ① 同步留底完成 | 系统自动触发② |
| `processing` 加工中 | 正在选品定价/翻译 | ② 开始 | — |
| `process_err` 加工异常 | 翻译中文残留 / 术语未命中 | ② 失败 | 运营补术语 → 自动重跑 |
| `priced` 已定价 | 定价选中 + 翻译完成 | ② 成功 | 系统自动触发③ |
| `map_err` 映射异常 | 属性值未命中标准记录 | ③ 步骤二失败 | 定时重试 / 运营补映射 |
| `list_err` 上架校验异常 | 上架校验（商品域共享校验 + 红布林来源校验）未通过 | ③ 步骤四不通过 | listing 停留未上架、product_status 待销售，修复后自动重校验（§2.5.4） |
| `listed` 已上架 | 创建 + 校验 + 上架全部完成 | ③ 步骤四通过 | 终态 |
| `excluded` 已排除 | 未通过选品 | ② 排除检查或未选中 | 终态，不翻译不映射不建标品 |

> **v1.6 已删除**「已创建待上架」态——创建后立即自动校验上架，不再有"已创建但未上架"的常态停留。校验不通过属**异常**，进入 `list_err`「上架校验异常」态并停留在创建环节。

#### 2.1.2 商品状态（product_status，商品系统标准枚举）

商品系统定义 **7 态**：待核验 / 核验中 / **待销售** / **销售中** / **已售出** / 已停售 / **已失效**。

本模块只写入其中 **4 态**：

| 枚举值 | 本模块写入时机 | 可逆性 |
|---|---|---|
| **待销售** | ③ 创建 product 时初始值（等待上架校验）；**④ 普通下架后回到此态**（v1.1 · 1B 变更） | **可逆**：重新上架时**需重走上架校验**（§2.5.4），通过后转「销售中」 |
| 销售中 | ③ 校验通过自动上架；④ 重新上架（重走校验通过后） | — |
| 已售出 | ④ 售出场景 | 终态 |
| **已失效** | 仅用于**真正的永久失效 / 删除**（如商品被红布林删除且不再恢复、运营永久下线）；⑤ 实体归属变更重建时的**旧 product**（§2.7） | **终态、不可逆**（v1.1 · 1B：不再作为普通下架态） |

> **v1.1 · 1B 核心变更**：普通下架后 product 回到**「待销售(pending_sale)」**而非「已失效」——下架是**可逆**操作，重新上架需重走上架校验才能回到「销售中」。「已失效」收窄为**真正永久失效/删除的终态**。下架/售出/失效/重新上架 → Product/Listing/inventory 的逐态映射见 §2.6。

> **不能因本链路用不上就删除其余 3 态**——product_status 是商品系统标准枚举，红布林只是写入来源之一，未来自营/其他入驻商家会用到待核验/核验中/已停售。

#### 2.1.3 统一异常处理机制（机制型）

**功能描述**：三类异常（加工异常 / 映射异常 / 上架校验异常）全部汇入「红布林商品库」页集中处理，不设独立异常页。

**处理流程**

| 异常类型 | 入口 | 处理方式 | 修复后 |
|---|---|---|---|
| 加工异常 | 顶部「加工异常」KPI 快捷筛选 | 行内「去修正」弹窗，补齐英文/术语 | 系统自动重跑② |
| 映射异常 | 顶部「映射异常」KPI 快捷筛选 | 行内「去映射」跳转主数据映射页补 ID | **系统定时自动重试**（映射库更新后自愈），无需人工触发 |
| 上架校验异常 | 顶部「上架校验异常」KPI 快捷筛选 / 列表筛选 | 行内「去修正」→ 携 Product/Listing/渠道/来源记录/返回地址**跳渠道商品编辑页**，定位失败字段并回显红布林错误原因（v1.1 · OQ-006）；非商品字段（渠道停用等）跳渠道管理页 | 保存后重跑（共享 + 来源）校验，通过则恢复自动上架，失败更新原 list_err、不建重复渠道商品 |

**规则说明**
- 映射异常优先靠系统定时重试自愈，只有长期未解决的全新值才需运营补映射
- 修复动作不改变已有 product 数据，只推动流程继续

**异常处理**：三类异常各自保持对应异常态（`process_err` / `map_err` / `list_err`）直到修正事件到达——由运营或规则源修正后触发新的处理轮次。技术层面的重试、退避与告警策略由**技术环节**设计并保证，PRD 不约束实现方式。

#### 2.1.4 规则源变更处理机制（机制型）★

**功能描述**：翻译术语库 / 主数据映射发生变更时，系统按规则自动重算受影响商品，**全程无人工确认环节**。运营只负责维护规则源本身，重算范围与执行由系统按下述规则判定。

> **前置铁律 —— `url_slug` 一经生成永不变更**
>
> `listing.url_slug`（§2.5.4）是对外契约：C 端收藏链接、外链、SEO 索引都依赖它。因此 **product / listing 创建时生成一次，此后任何规则源变更、重新翻译、重新映射都不改动它**。
>
> 这条铁律是"重算可以全自动"的前提：内部字段（title / 属性外键 / 检验描述）重算不产生外部影响，无需人工判断；若 slug 可变则每次重算都要评估 SEO 影响，就必然需要人工确认。
>
> **适用边界**：本条约束**同一个 product 的字段重算**。§2.7 的品牌/系列/类目变更走 **product 重建**（换了一个 product），新 product 生成新 slug，不在本条约束范围内。

**变更类型与处理**

| 类型 | 触发 | 系统处理 |
|---|---|---|
| **补齐** `pending → active` | 新增映射 / 新增术语 | 自动重跑异常态商品（同 §2.1.3），无其他影响 |
| **修订** `active → 改值` | 编辑已生效的术语 / 映射 | 按下表「重算范围规则」自动重算，异步批量执行 |
| **删除** | 删除术语 / 映射 | 已创建 product 的商品**不回滚**；未创建的回到对应异常态 |

**重算范围规则（修订场景）**

| 商品当前状态 | 是否重算 | 重算内容 |
|---|---|---|
| 未创建 product（`to_process` / `process_err` / `map_err` / `priced`） | **是** | 重跑②③全流程 |
| 已创建未上架（`list_err`） | **是** | 重算 title / 属性外键 / 检验描述，重新执行上架校验（§2.5.4） |
| 已上架（`listed`，product_status = 销售中） | **是** | 重算 title / `product_inspection` 描述 / 属性外键；**`url_slug` 不变** |
| 已排除（`excluded`） | 否 | 终态，未进入加工 |
| 已售出 / 已失效（product_status） | **否** | 终态，历史数据保真，不因规则源变更而改写 |

**术语英文变更 → 映射 key 自动联动（★ 串联架构的必需配套）**

串联下英文标准值即映射 key（§2.9），若只改术语不动映射表，会同时产生「新值查不到」与「旧值成孤儿行」两个后果，表现为新商品批量进映射异常且与运营操作无可见关联。故：

| 情况 | 系统动作 |
|---|---|
| 新英文值在映射表**不存在** | 自动将该行 `source_value_en` 就地改为新值，`target_id` 不变——映射关系延续，不产生失配、不产生孤儿行 |
| 新英文值在映射表**已存在另一行** | 合并到已有行（映射表保留多对一结构，见 §2.9），原行标记失效不再参与查表 |
| 变更的是**自由文本字段**（商品名称 / 瑕疵描述 / 其它） | 不涉及映射，仅触发重算 |

**删除的影响面提示**

删除前需展示影响统计，并明确区分两类对象——**已创建 product 的商品不会回到异常态**（英文与 ID 已固化在 product / SPU 上，删规则不产生回滚）：

- 影响 N 件**未创建 product** 的商品 → 将回到「加工异常」/「映射异常」
- 影响 M 件**已创建 product** 的商品 → 数据不变，仅阻止后续新商品使用该规则

**规则说明**
- 重算**异步批量执行**，不阻塞规则源页面的保存操作
- 重算失败复用 §2.1.3 的失败计数与阈值机制（超 3 次标记需人工深度介入）
- 重算不改变 `product_status`，也不触发重新上架/下架
- 一次规则源变更可能影响大量商品，重算任务需支持断点续跑（技术方案保证）

**异常处理**：重算过程中商品被红布林推送变更（④/⑤）→ 以红布林推送为准，重算结果丢弃后重新排队。

### 2.4 ② 系统自动加工（机制型）

**功能描述**：对「待加工」商品自动执行选品定价 + 翻译，全程无人工向导。原「商品翻译」「选品定价」独立菜单已取消。

**触发条件**：①留底完成后系统自动触发。

**处理流程**

顺序：**先选品定价 → 选中的再翻译**（未选中不翻译，省资源）。

**阶段一 · 自动选品定价**

1. 读折扣价：`A = 折扣价 / 汇率`（CNY→USD 成本基数）。**汇率可配置**（V1 默认 6.86，不硬编码、不接实时汇率），每次计算保存实际使用的汇率值与版本号（历史可复现）。
2. 读 TRR：`C = 均价`（**按品牌/系列标准名匹配，不经自建实体 ID**）
3. 排除检查：补色养护 / 改色 / 边油重做 / 折扣价无效 → 「已排除」
4. 分流定价（完整公式表见**附录 7.4**，顺序命中即停 + 兜底）：

```
B146 = ceil(1.46A + 207)    B128 = ceil(1.28A + 181)    B122 = ceil(1.22A + 172)

· 包袋 Top(有C)：公式3(B146≤70%C) → 公式1(B146≤80%C) → 公式2(B128≤90%C)
                → 公式4(B128≤C) → 公式5(B122≤1.10C) → 公式7兜底(B122, B>1.10C 仍选中)
· 包袋 非Top / 无C / 宝格丽：公式6 = ceil(1.28A + 181)
· 非包袋（非排除大类）：固定 B146

低价修正：公式 2/4/5/7 及 6，B≤500 改用 B146 并保持选中
         Speedy 例外：B≤500 仍不选中
```

> **★ v1.1 · R4 删除"超 TRR → 不选中"**：依据 04-1，`B>1.10C` = **公式7兜底 = 仍选中**（只是标记为高于市场参考价）。原"不选中(否)"**只有 4 种情形**：① 价格无效；② 养护/改色/边油重做；③ 非目标包袋（且非固定公式大类）；④ Speedy 低价例外（B≤500）。**不再有"超 TRR 比例 → 不选中"分支。**

5. 选中 → 计算 **CostPrice（USD）** + 挂牌价 B + 所用公式，暂存快照（成本权威落 sourcing 域，见 §2.5.3）：
   - **CostPrice = A = 折扣价 / 汇率**（USD），**保留整数、小数位向上取整**（v1.2 调整，如算得 100.1 → 定价 101）。
   - **★ v1.1 · OQ-018 修量纲**：成本与挂牌价的一切比较**统一在 USD 维度**——**删除**旧 PRD「折扣价(CNY) ≤ B(USD) 保留原值，否则取折扣价/6.86」的**跨量纲直接比较**（该比较把 CNY 原值与 USD 成本混用，是真实 bug）。
   - **★ v1.1 · OQ-018 成本 > 挂牌价 = 定价错误**：取整后若 **A > B**（成本高于挂牌价），判为**定价错误**——**阻断成本/价格写入与自动上架**，商品进入定价错误异常，**不把真实成本截断成 B 伪造利润**。若业务确要自动改成 B，需再次显式确认（本期不做）。

**阶段二 · 自动翻译**（仅对选中商品）

1. 各字段中文 → 英文，取自**翻译术语库**（品牌/系列/类目/颜色/材质/尺码/五金/设计元素）
2. 按术语库的**拼接规则**（Category Suffix / Wallet 范围 / 类目拼接顺序）组装英文 Product Name

**规则说明**

**TRR 匹配颗粒度**：品牌 + 系列 + 尺码 + 成色 四维，按标准名匹配。示例：

> 折扣价 ¥7,546，标准化后 Louis Vuitton / Neverfull / MM / A
> → Top 系列表命中 `LV+Neverfull` → 走 Top 路径
> → 均价表 `LV+Neverfull+MM+A` → C = $2,200
> → A = 7546/汇率(6.86) ≈ 1100，B146 = ceil(1.46×1100+207) = 1813
> → 1813 ≤ 70%×2200(=1540)？否 → ≤80%×2200(=1760)？否 → B128 = ceil(1.28×1100+181) = 1589
> → 1589 ≤ 90%×2200(=1980)？是 → **命中公式2，B=1589**（A=1100 < B=1589，非定价错误，选中）

**降级规则**：尺码命名不同靠尺码术语归一；四维组合在 TRR 无数据 → 无 C 值，包袋走公式6；无系列 → 公式6 或标「否」。

**为什么定价不依赖主数据映射**：TRR 是三方参考数据，天然按品牌/系列名字组织，用标准名匹配即可。若强行让 TRR 挂自建实体 ID，等于要为每次 TRR 更新维护一层"三方值→自建 ID"的对应，成本高且脆弱。映射产出的实体 ID 只在③建 SPU / 落属性外键时才用。

**加工结果**

| 结果 | 信息准备进度 | 后续 |
|---|---|---|
| 定价选中 + 翻译成功 | 已定价 | 自动触发③ |
| **定价错误（A>B）** | 加工异常（定价错误子类） | 阻断成本/价格写入与自动上架；运营修正折扣价/规则后由变更事件触发新处理轮次（§2.1.3） |
| 翻译中文残留 / 术语未命中 | 加工异常 | 运营补术语 → 自动重跑 |
| 未选中 | 已排除 | 终态，不翻译、不映射、不建标品 |

**异常处理**：加工异常（含定价错误）汇入「红布林商品库」集中修正（§2.1.3）。

**技术说明**：
- **定价规则（公式与顺序）不再写死代码**（v1.1 · 决策4/R7）：以**「定价规则」运营页**（§2.12）维护，②加工流水线按当前生效的规则执行。
- 空尺码回填 TRR 匹配尺码、名称清洗等细节由后端处理。

### 2.5 ③ 标品对齐 + 创建实体 + 自动上架（机制型）★

**功能描述**：对「已定价」商品，按款型ID 对齐标品SKU → 属性主数据映射 → 自动创建全套实体 → 自动校验并上架。全程系统自动，**无人工确认上架环节**。

**触发条件**：②产出「已定价」后自动触发。「已排除」商品不进入本段。

#### 2.5.1 步骤一 · 标品对齐（款型ID → 标品SKU）

| 情况 | 系统动作 |
|---|---|
| **命中**（N:1） | 复用已有 `standard_sku_id`；同款型的多件实物商品共用同一标品SKU，直接继承 SPU 的品牌/系列/类目及 SPU 级属性 |
| **未命中**（新款型） | 先映射品牌/系列/类目 → **系统自动创建 SPU + 标品SKU**（无人工）→ **立即回填**款型ID↔标品SKU 映射表 |

> ★ **款型ID 是什么**：红布林**款型库**里的款型标识——红布林侧已维护的标品主数据，一个款型代表一个具体规格的标准品。它**不是品牌系列**：系列（series）是 SPU 级营销归类，一个系列下有多个款型；款型是 SKU 级具体规格，因此与 looply 标品SKU 天然同粒度、1:1 对应。

**规则说明**
- 款型ID 与标品SKU **1:1**；product → standard_sku 为 **N:1**
- **为什么标品自动创建、不做人工维护页**：红布林推送数据量大，人工逐款建标品不可行；款型ID 是红布林侧已有的稳定标识，足以作为标品层唯一键，自动建 + 回填映射表即可自愈
- **效果**：映射工作量从"每件商品"降到"每个新款型"，同款型第二件起零映射成本

> ★ **必须区分**：本段保留的「映射异常 → 定时重试 / 运营补映射」指**属性值归一**（步骤二）。**标品SKU 的创建是全自动的、没有人工兜底环节**。

#### 2.5.2 步骤二 · 主数据映射（按三层架构分流）

| 红布林字段 | 归一到 | 落在哪一层 |
|---|---|---|
| **款型ID** | 标品SKU | **标品层**（步骤一完成） |
| 品牌 / 系列 / 类目 | brand_id / series_id / category_id | **SPU**（建 SPU 时落外键，product 经 standard_sku→spu 继承） |
| 颜色 / 材质 / 尺码 | attribute_option_id / size_value_id | 按 `attribute_scope_config.value_level` 决定落 **SPU / SKU / ITEM**；`value_level=ITEM` 时属性值写入 **`product_attribute_value`** |
| 成色 / 瑕疵 / 配件 / 序列号 / 年份 | 标准选项 ID 或文本 | **product / product_inspection**（一物一码，不进标品层） |

**规则说明**
- 商品系统标准值为**英文**，映射即归一到英文标准记录，product 落英文不落中文
- **映射输入是②产出的英文标准值**，不是中文原始值（串联，非并联）
- **多对一**：结构上保留（多个英文标准值 → 同一标准记录），业务上归一优先在术语库完成
- **一致性告警**：`source_value_en` ≠ 目标记录 `name_en` 时告警不阻断
- **ITEM 级属性值的落库表**：`value_level=ITEM` 的属性值统一写入 `product_attribute_value`（product 一物一码维度）；SPU / SKU 级属性值分别落 SPU、标品SKU 的属性表
- 全部命中 → 进入步骤三；有失败 → 「映射异常」，系统定时自动重试，长期未解决的由运营补映射

#### 2.5.3 步骤三 · 自动创建实体

| 实体 | 内容 |
|---|---|
| **product** | `standard_sku_id`（★唯一的主数据外键）+ seller_id + title + serial_number，product_status 初始「待销售」，关联红布林商品ID |
| **product_image** | 产品图 + 瑕疵图，保持源顺序 |
| **product_inspection** | 成色 / 瑕疵 / 配件（一物一码字段） |
| **inventory_item** | qty=1 + 库存流水 INBOUND；**仅管数量与预占/锁定，不落成本**（v1.1 · OQ-004） |
| **listing** | 渠道 + 市场 + 挂牌价 + currency + url_slug |

> ★ **product 不落 brand / series / category 外键**——这些在 SPU 上，经 `standard_sku → spu` 继承（依据 ER v2.6）。

> ★ **v1.1 · OQ-004 成本权威单一化到 sourcing 域**：**去掉 `listing.CostPrice` 与 `inventory.unitCost` 的双写与三项回读**。CostPrice 及 last_cost、来源价、汇率值/版本、命中规则版本统一存 **sourcing 侧**（本模块加工/价格上下文）；`inventory` 仅管数量与预占/锁定。任何环节（③创建、⑤重建、⑥调价）需要成本时，**经 sourcing 接口/投影读取**，不再从 listing/inventory 回读成本。

#### 2.5.4 步骤四 · 自动校验 + 自动上架 ★

listing 创建后系统**立即校验**。**v1.1 · OQ-002**：校验由「5 项」改写为**「商品域共享校验 + 红布林来源校验」两段组合**，二者汇总为**一个统一的、可定位的错误集合**——每个失败项返回 **稳定错误码 / 问题字段 / 修正入口 / 是否可自动重试** 四要素，供「红布林商品库」list_err 修正入口精确回显与跳转。

**第一段 · 商品域共享校验**（商品系统对所有来源上架统一要求，本模块复用、不自定义）：

| 校验项 | 规则 | 稳定错误码 | 修正入口 | 可自动重试 |
|---|---|---|---|---|
| 必填项齐全 | 建 listing 必需字段完整 | `LIST_REQUIRED_MISSING` | 渠道商品编辑页 | 补齐后是 |
| 挂牌价有效 | 存在且为有效正值；且非定价错误（A≤B） | `LIST_PRICE_INVALID` | 渠道商品编辑页 / 修正折扣价 | 修正后是 |
| 图片顺序 | 商品/成色图在前、瑕疵图在后，保持源顺序 | `LIST_IMAGE_ORDER` | 渠道商品编辑页 | 补图后是 |
| url_slug 唯一 | `listing.url_slug` 是 **UK（唯一键）**，冲突阻断（唯一性由商品域保证） | `LIST_SLUG_CONFLICT` | 改名解冲突 | 改名后是 |

**第二段 · 红布林来源校验**（本模块产英文特有卡口）：

| 校验项 | 规则 | 稳定错误码 | 修正入口 | 可自动重试 |
|---|---|---|---|---|
| 中文残留 | 任何面向 C 端的英文字段出现中文字符即阻断 | `LIST_CN_RESIDUE` | 去修正弹窗 / 补术语 | 修正后是 |

> **v1.1 · OQ-003 slug 本期不作新增卡口**：本期**不动 slug**，不新增唯一约束/碰撞修复/301——slug 的唯一性仍由商品域既有能力保证（上表 `LIST_SLUG_CONFLICT` 复用商品域校验，非本模块新增卡口）。slug 的**通用治理由商品域 / SEO 独立立项**。

| 校验结果 | listing | product_status | 信息准备进度 | 后续 |
|---|---|---|---|---|
| **通过** | **Active（卖场可售）** | **销售中** | **已上架** + 回写 product_id | 无人工动作 |
| **不通过** | 未上架 | 待销售 | **上架校验异常**（`list_err`） | 进「红布林商品库」统一异常处理，修复后自动重新校验上架 |

> ★ **为什么取消人工确认上架**：原④的"人工确认 + 分批上架"是 **Shopify 上架数量/限流约束**的产物——Shopify 有 API 写入速率与批量限制，必须靠人工分批节流。对接自建系统后不存在这些限制，人工确认只剩重复劳动。
>
> **随原④一并删除（Shopify 驱动项）**：7 维写后审计 / 可修复项自动补写 / 3lane 分批限流 / Draft→Active 两步流转
> **保留并前移为本段自动卡口（与渠道无关）**：上两表的「商品域共享校验 + 红布林来源校验」组合（v1.1 · OQ-002）
> **注意**：⑥价格变更的"分波分批"是为降低 C 端浏览冲击，**与 Shopify 限流无关**，保留不动

**关键规则**

- **url_slug 生成**：`slugify(Brand+' '+ProductName)+'-'+ItemID`，创建时生成，UK 唯一。**同一 product 存续期内永不变更**——规则源变更（§2.1.4）不改动它。⑤实体归属变更（§2.7）触发 **product 重建**，新 product 生成新 slug，属换了一个 product，不违反本条
  > ⚠️ 该公式沿用旧 Shopify 实现，`ItemID` 是红布林商品ID，**对非红布林来源商品不适用**。已记入商品模块待优化清单第 8 条，待商品系统定义通用生成规则后本模块改为引用，见风险 R4
- **属性集由「属性作用域配置」（`attribute_scope_config`）决定**，非 Shopify 的 Template / Metafields：
  - 按 `category_id` + `scope_type` 配置，支持 **CATEGORY / CATEGORY_BRAND / CATEGORY_SERIES 三级作用域**
  - `is_required` 控制必填，`sort_order` 控制展示排序，`value_level` 决定值落 SPU/SKU/ITEM
  - 属性定义与可选值来自 `attribute_def` / `attribute_option`
  - Shopify 的 `template_suffix` 是前台主题渲染模板，**自建系统无对应对象**，商详页渲染归商详模块
- **一物一码**：inventory_item qty=1

> **映射与翻译的职责边界（★核心，串联关系）**
> - 链路：**中文原始值 ──②术语库──→ 英文标准值 ──③映射表──→ 标准记录 ID**
> - **翻译术语库**回答"这个中文值的英文标准值是什么" → 产**英文标准值**（既拼商品名，又作③的查表 key）
> - **主数据映射**回答"这个英文标准值是我库里的哪条记录" → 产 **ID**（建 SPU / 落属性外键）
> - **翻译是映射的上游，不是并列关系**。同一个英文值贯穿 title 与查表，来源单一
> - 与 Shopify 版 v3.1.2 一致：老系统即为 `4.3 术语库 → 4.2 翻译 → 3.1 用英文 L3 路由 template / taxonomy GID`，查 ID 的 key 一直是翻译后的英文值
> - **定价不受影响**：②查 TRR 仍按标准名匹配，不依赖③映射

**异常处理**：见 §2.1.3。

**技术说明**：渠道库存分配不在 V1 范围。已上架商品的信息修正走⑤。

### 2.6 ④ 红布林状态同步（机制型）

**功能描述**：接收红布林下架推送信号，内部判断场景并分流处理库存、listing、product_status。

**触发条件**：红布林推送商品下架信号（红布林商品ID + 状态）。

> **核心**：红布林侧「售出」与「下架」是**同一个下架推送信号**，红布林不区分。looply 收到后内部判断场景再分流。

**处理流程**

1. 覆盖快照（该红布林商品ID 最新状态）
2. 按红布林商品ID 查 product
3. 未建 product 或无 listing → 仅覆盖快照，结束
4. 已建 product → 内部判断场景并分流：

| 场景 | 库存（inventory） | listing | product_status | 订单保护 |
|---|---|---|---|---|
| **售出** | 清零 qty=0 + 流水 SOLD -1 | 下架不删除 | **已售出**（终态） | **有活跃订单不直接清零，转异常** |
| **普通下架** | 清零 qty=0 | 下架**不删除** | **待销售（可逆）** ★v1.1·1B | — |
| **重新上架** | 恢复可售 qty=1 + 流水 INBOUND | **需先重走上架校验**（§2.5.4），通过后恢复 Active | 校验通过 → **销售中** ★v1.1·1B | — |

5. 回查验证，不通过标记异常人工介入

**★ v1.1 · 1B 逐态映射表（下架/售出/失效/重新上架 → Product / Listing / inventory）**

| 触发事件 | product_status | listing 状态 | inventory | 可逆性 | 说明 |
|---|---|---|---|---|---|
| **普通下架** | 销售中/待销售 → **待销售** | Active → 下架（不删除） | qty → 0 | **可逆** | 下架是可逆操作；product 保留、listing 保留、库存清零 |
| **重新上架** | 待销售 → **销售中**（需先过 §2.5.4 上架校验） | 下架 → Active | qty → 1（INBOUND） | — | 重新上架**必须重走上架校验**，通过才回销售中；校验不通过停在待销售+list_err |
| **售出** | 销售中 → **已售出**（终态） | Active → 下架（不删除） | qty → 0（SOLD -1） | 不可逆 | 有活跃订单不直接清零，转异常保护 |
| **真正永久失效/删除** | → **已失效**（终态） | 下架（不删除） | qty → 0 | 不可逆 | 仅用于商品被红布林删除且不恢复、运营永久下线等；**普通下架不再写此态** |

> **★ v1.1 · 1B 关键变更**：普通下架后 product_status 回**「待销售」而非「已失效」**——下架**可逆**，重新上架**需重走上架校验**才能回到「销售中」。「已失效」收窄为**真正永久失效/删除的终态**。

**规则说明**
- 售出、普通下架、永久失效**都清零库存**——一物一码（qty=1），下架即置 0，**无"保留数量"概念**
- 三者区别**在 product_status**：售出→已售出（终态）、普通下架→**待销售（可逆）**、永久失效→已失效（终态）
- listing 一律**下架但不删除**，便于重新上架时恢复
- **重新上架不是简单恢复 Active**：需重走 §2.5.4 上架校验（商品域共享校验 + 红布林来源校验），通过才转销售中
- 对比现有系统 3.5 清理：手动 Excel 对账 → API 自动同步 + 定期对账安全网

**异常处理**

| 场景 | 处理 |
|---|---|
| 售出但有活跃订单 | 不清零库存，转异常人工介入（防止已售商品的在途订单失去库存依据） |
| 回查验证不通过 | 标记异常，人工介入 |
| 商品未建 product | 仅覆盖快照，不报错 |

### 2.7 ⑤ 商品信息变更（机制型）

**功能描述**：接收红布林信息变更通知，覆盖快照并按变更类型联动 product / listing。

**触发条件**：红布林通知信息变更（红布林商品ID + 变更字段 + 新值），或内部修正。

**处理流程**

1. 先覆盖快照（写入新的中文原始值）
2. 按红布林商品ID 查 product
3. 未建 product → 仅覆盖快照，后续加工用最新值
4. 已建 product → 按变更类型分流：

| 变更类型 | 处理 | 人工介入 |
|---|---|---|
| **折扣价变更** | 按定价公式算**建议价 B** + 更新 sourcing 侧成本 → **生成价格变更待办**进入⑥ | 无（执行在⑥） |
| **图片变更** | 下载新图 → 更新 listing 图片，保持源顺序 | 无 |
| **身份字段变更（品牌 / 系列 / 类目）** | **下架旧 + 重建新 product**（见下方「实体归属变更 → product 重建」） | 无（全自动） |
| **其余属性变更（颜色 / 材质 / 尺码 / 成色 / 瑕疵 / 配件 / 标题 等）** | **原地重算更新**，不重建 product：重新翻译/映射受影响字段，重算 title / product_inspection / 属性外键，`url_slug` 不变 | 无（全自动） |

**★ v1.1 · 3A 身份字段 vs 原地重算（基础版）**

| 变更字段 | 处理 | 原因 |
|---|---|---|
| **品牌 / 系列 / 类目**（3 个身份字段） | **下架旧 product + 重建新 product** | 决定标品SKU 归属、定价路由、属性作用域（`attribute_scope_config` 按 `category_id`），换了标品归属而非改字段 |
| **其余全部属性**（颜色/材质/尺码/成色/瑕疵描述/配件/标题…） | **原地重算更新**，不重建 | 不改变标品归属与作用域，重算内部字段即可 |

> **v1.1 · 3A 范围界定（本期只做基础版）**：本期实现 ①身份字段（品牌/系列/类目）变更 → 下架重建；②其余属性 → 原地重算 两条基础规则，全自动无人工确认。**完整的字段级「原地更新 / 下架重建 / 不处理」矩阵 + 影响预览 + 运营确认标注**，随规则变更专项能力**留至规则变更专项新 PRD（V2）**，本期不做影响预览与人工确认闸门。

5. 回查验证，不通过标记异常

> ★ **本段职责到"生成价格变更待办"为止**。运营的逐行决策、分波分批勾选、价格写入、回读验证**全部在⑥**，两段不重叠。

**规则说明**

**折扣价变更不区分是否已上架**：未上架的和已上架在售的一起进⑥。

**★ 实体归属变更 → product 重建（全自动）**

品牌 / 系列 / 类目**挂在 SPU 上**（§2.5.2），product 只挂 `standard_sku_id` 并经 `standard_sku → spu` 继承。因此这三项中**任意一项变更**，等价于该实物商品需要**重新对齐到另一个标品SKU**（必要时新建 SPU + 标品SKU）——不是改几个字段，而是换了一个标品归属。故走 **product 重建**，不做就地更新。

**为什么不能就地改**：
1. 依赖品牌/系列/类目拼接的 Name / Tags，及按 `attribute_scope_config` 取值的属性集连锁失准
2. 主数据 ID 失联（改英文文本不改映射 ID）
3. `standard_sku_id` 仍指向旧标品，product 与 SPU 的归属关系错位
4. 英文 product 与中文快照回溯断裂

**重建流程**（全自动，无人工确认）

| 环节 | 处理 |
|---|---|
| 标品对齐 | 按新品牌/系列/类目重新翻译取英文标准值 → 重新映射取 ID → 查款型ID↔标品SKU；未命中则新建 SPU + 标品SKU（复用 §2.5.1） |
| **新 product** | 新建，挂新 `standard_sku_id`，继承 serial_number / 成色 / 瑕疵 / 配件等一物一码字段 |
| **旧 product** | `product_status = 已失效`，**不删除**（保留追溯链）；快照层 `product_id` 回写指向新 product |
| 库存 | 旧 `inventory_item` 清零 + 流水；新 product 建 `inventory_item(qty=1)` + 流水 INBOUND |
| listing | 旧 listing **下架不删除**；新 listing 新建，走 §2.5.4 自动校验并上架 |
| **url_slug** | 新 listing **生成新 slug**（品牌/名称已变）；旧 slug 随旧 listing 保留不复用 |
| ITEM 级属性值 | **不迁移**——新类目/品牌的 `attribute_scope_config` 作用域不同，按新作用域重新映射落值 |

> ★ **与 §2.5.4「url_slug 永不变更」的边界**：该铁律约束的是**同一个 product 的字段重算**（规则源变更 §2.1.4）。本段是**换了一个 product**，新 product 生成新 slug 属预期行为，不违反铁律。

> ★ **只变类目也重建**：`attribute_scope_config` 按 `category_id` 配置作用域，类目一变属性集整套变，就地改必然连锁失准。故品牌/系列/类目**一视同仁都走重建**。

**已售出 / 已失效商品不重建**

| 商品状态 | 处理 |
|---|---|
| 销售中 / 待销售 | 按上表自动重建 |
| **已售出** | **不重建**，转异常人工介入——product 已被订单引用，且已售商品的品牌被改说明当初卖错，属业务事故，不由系统自动处理 |
| **已失效** | **不重建**，转异常人工介入 |

**异常处理**：回查验证不通过 → 标记异常，人工介入；已售出/已失效商品收到实体归属变更 → 转异常人工介入。

### 2.8 ⑥ 商品调价处理（页面型）★

**功能描述**：承接⑤折扣价变更生成的价格变更待办，运营**按波次筛选并勾选本波 ready 商品，批量执行**——把价格改到**系统建议价 B**（走价格写入 4 规则）。**不设"采纳/维持/自定义"逐行决策层**（v1.1 · R1/R2，完全对齐 v3.1.2 的 3.4 改价规则）。

> **用词口径（以原型 v20 为准）**：**页面**名为「商品调价处理」，页面内的**单条记录**称「价格变更待办」（对应表 `plm_price_change_todo`、页面 KPI「待办总数」，表名与记录名不变）。流程图 V13.1 中的"价格变更待办"即指此记录。

> **★ v1.1 · R1 比对基准**：改价比对 = **系统建议价 B vs 当前 Looply 挂牌价（price）**。其中 **B = 公式(新折扣价)**；**折扣价（成本）是定价输入，不是比对对象**，成本涨跌只作**背景信息**展示（对齐 03-4：`target(=B)` vs `price`）。
>
> **★ v1.1 · R2 调价处理层完全对齐 3.4**：**取消「采纳 / 维持 / 自定义」决策层与「自定义价」**（原始 3.4 无此决策层）。运营流程 = **分波筛选 → 勾选本波 ready 商品 → 执行本波**（把价格改到系统建议价 B）。**「维持原价」= 不勾选执行**（不是一种记录状态或按钮）。原型 v20 已去掉「调整决定」列、批量决定按钮与 PriceDecisionModal。
>
> **第一性原理**：红布林折扣价是 looply 的**定价输入**（挂牌价 B = f(折扣价)）。折扣价变 → 定价输入变 → 系统按公式算出新的建议价 B。涨/降是【系统建议价 B vs 当前挂牌价 price】的**比较结果**（既成事实），运营决定的只是**这一波要不要执行、执行哪些**，通过勾选控制节奏。

**前置条件**：⑤已生成价格变更待办。**本页输入唯一来自⑤**，运营不能在此凭空发起一次促销降价。

**页面布局**：单页列表。KPI 区 → 筛选区 → 表格（可勾选）→ 批量操作区 → 底部说明块。右上角「规则说明」弹窗。

**页面元素**

| 区域 | 元素 |
|---|---|
| KPI（5 项） | 待办总数 / 可改价(ready) / 无需改价(no_change) / 差价不足$30(invalid_discount) / 本批已勾选 |
| 筛选 | 涨跌方向（涨价 / 降价，**比较结果**）、预览分类（可改价 / 无需改价 / 差价不足$30 / 未匹配无效）、上架状态（已上架 / 未上架）、关键词搜索（红布林商品ID / 渠道商品ID / 名称） |
| 表格列 | 红布林商品ID、**渠道商品ID**、商品名、品牌、上架状态、当前挂牌价、建议价 B、**TRR 比对（信息展示）**、成本变化（背景）、预览分类 |
| 批量操作 | 「执行本批调价」（把勾选行价格改到建议价 B） |

> 本页**无「调整决定」列、无逐行决策**（v1.1 · R2）：运营看到的是系统算好的建议价 B 与预览分类，只需勾选并执行。

> **为什么要有渠道商品ID 列**：改价实际写入的对象是 **listing（渠道商品）**，红布林商品ID 仅为待办来源标识。运营需要看到真正被改价的对象。

> **★ v1.1 · R3 TRR 比对仅信息展示**：TRR 比对列**只展示** B 相对 C 的位置 / 命中公式档（**公式7 = 高于市场参考价的提示**）。**不设"超 TRR → 需人工"硬卡口、不禁用、不阻断**——所有 `ready` 行都正常可勾选执行。依据 04-1：`B>1.10C → 公式7兜底 → 仍选中`。

**页面状态变体**

| 状态 | 说明 |
|---|---|
| 默认态 | 全部待处理待办 |
| 分类筛选态 | 按预览分类（可改价 / 无需改价 / 差价不足$30 / 未匹配无效）筛出 |
| 本波已勾选态 | 已勾选待执行的行 |
| 空态 | 无待处理待办 |

**操作流程**

**步骤一 · 分波筛选并勾选本波 ready 商品**：运营按涨跌方向/品牌/上架状态等筛选，**勾选**本波要执行的 `ready`（可改价）商品。`no_change` / `invalid_discount` / `unmatched` 行**不可勾选执行**。

> 分波目的是**降低对 C 端用户浏览网站的影响**（避免大量商品价格同时跳动）。**与 Shopify 限流无关**，③取消分批限流不影响这里。「维持原价」即**本波不勾选该行**。

**步骤二 · 执行本波**：点「执行本批调价」→ 系统把勾选行价格改到**系统建议价 B**，剩下的下一波再执行。

**步骤三 · 价格写入规则**（B=系统建议价/目标价，price=当前价，compare_at=划线价，保留 3.4）

| 条件 | 新 price | 新 compare-at |
|---|---|---|
| B == compare_at | B | 清空 |
| B > price（**涨价**） | B | 原 compare-at > B 保留，否则清空 |
| B < price（**降价**） | B | max(原 price, 原 compare-at) |
| B == price | 不变 | 不变（成本变仍执行以刷新 sourcing 侧成本版本） |

- **★ v1.1 · R5 差价不足 $30 = 硬性不执行**（维持原始 3.4）：降价时若「**新划线价 − 目标价 B < $30**」→ 动作 `invalid_discount`，**系统不执行**（硬跳过），归入「差价不足$30」分类，**不可勾选执行**。注：$30 比的是"划线价 − 目标价"（显示折扣），非单纯降幅。**本期不改为可执行的筛选项**（用户核实后确认保留硬跳过）。

**步骤四 · 回读验证**：写入 listing 价格后回读验证 **price / compare-at 一致**才标记完成；成本刷新落 sourcing 侧（不回读 inventory.unitCost，v1.1 · OQ-004）。

**预览分类（取代旧"采纳/维持/自定义决定表"）**

| 分类 | 含义 | 可否执行 |
|---|---|---|
| `ready` 可改价 | B 与当前价不同且规则允许 | **可勾选执行** |
| `no_change` 无需改价 | price/compare-at 均无需变化 | 不可执行（无动作） |
| `invalid_discount` 差价不足$30 | 降价时新划线价−B < $30，硬跳过 | **不可执行**（R5） |
| `unmatched` 未匹配无效 | 未找到 listing / 行无效 | 不可执行 |

**校验规则**

| 字段 | 规则 | 时机 |
|---|---|---|
| 勾选执行 | 至少勾选一行；只能勾选 `ready` 行 | 点「执行本批调价」时 |

> **v1.1 · R2 删除**：旧「自定义价必须为正数」「自定义价超 TRR 二次确认」两条校验随「自定义价」一并取消。

**交互说明**
- 无逐行决策，先筛选勾选再执行；不勾选即本波维持原价
- 执行失败的待办留在列表，不消失

**异常处理**

| 场景 | 处理 |
|---|---|
| 回读验证不一致 | 标记失败、记录原因，**留在列表**等下一波 |
| 执行时 listing 已被其他流程改价 | 以执行前重新读取的实时价格为准再应用规则（避免用过期预览值误改） |
| 商品已下架/已售出 | 跳过并标记，不改价 |

**UI 关联**：原型 v20 →「商品调价处理」页（`PriceTodoInner`，内部 key `price-todo` 不变）

### 2.9 主数据映射（页面型）

**功能描述**：维护**英文标准值** → 商品系统标准记录 ID 的映射关系。产物是 **ID**，用于建 SPU 和落属性外键。

**校验规则**

| 字段 | 规则 | 时机 |
|---|---|---|
| 标准值 | 必选，须为商品系统已有的启用状态记录 | 保存时 |
| 英文标准值 | 同一字段类型下不可重复 | 保存时 / 导入时 |

**交互说明**
- **多对一（结构保留，业务不推荐）**：结构上允许多个英文标准值映射到同一记录，作为术语库归一未做净时的兜底。正常情况归一已在术语库完成（「路易威登」「路易·威登」→ `Louis Vuitton`），本页只需一行 `Louis Vuitton` → B001

| 中文原值 | 同一分组内不可重复 | 保存时 |
| 两者 | 均不可为空 | 保存时 |

**交互说明**
- 「Category Suffix」「Wallet 范围」「名称拼接规则」三个 Tab 是**拼接规则**而非单纯术语对照，决定英文 Product Name 的组装方式
- 术语库是主数据映射的**上游**（串联，非正交）：术语库产英文标准值，该值既拼进 title，又作为③映射表的查表 key
- **结构化字段的英文必须填商品系统标准记录的 `name_en`**（品牌/系列/类目/颜色/材质/尺码/成色/配件/包型/设计元素）。填错不阻断保存，但会在主数据映射页触发一致性告警
- **归一在本库完成**：同一实体的多种中文写法应译为同一英文标准值（「路易威登」「路易·威登」→ `Louis Vuitton`），这样③映射表保持近 1:1

**异常处理**：删除被引用的术语 → 提示影响范围，按 §2.1.4 区分展示未创建 / 已创建两类对象（已创建的不回滚）。

**UI 关联**：原型 v20 →「翻译术语库」页（`GlossaryPage`）

### 2.11 TRR 参考价（页面型）

**功能描述**：维护 The RealReal 市场参考均价，供②定价时取 C 值（均价表）与公式路由判断（Top 系列表）。

**数据来源（V1.0 口径）★**

TRR 数据由**爬虫从 The RealReal 抓取**，但**爬虫不直连写库**，链路为：

```
爬虫抓取 → 产出 Excel → 运营在本页导入 → 入库生效
```

> **为什么不让爬虫直连写库**：爬虫依赖三方站点结构，稳定性不可控；一旦抓错会**直接污染定价链路**（C 值错 → B 算错 → 商品以错误价格上架），且因为算得出结果而无人察觉。走导入至少保留一道人工确认与一份导入历史，出问题可定位可回滚。爬虫本身的调度与实现不在本模块范围。

**页面布局**：KPI 区 → 操作区（新增 / 导入 / 导出当前表）→ Top 系列表 + 均价表（双 Tab）→ 导入历史。

**页面元素**

| 区域 | 元素 |
|---|---|
| 操作区 | 新增记录 / **导入** / 导出当前表 |
| Top 系列表 | 品牌、系列、**是否 Top**、更新时间、操作 |
| 均价表 | 品牌、系列、尺码、成色、均价（USD）、**样本数**、**数据日期**、更新时间、操作 |
| 导入历史 | **批次版本**、导入时间、**导入人**、**品牌范围**、新增数、更新数、**删除数**、无效数、解析器版本、下载原文件、**暂停参与定价** |

**导入策略：按品牌全量覆盖 ★**

| 项 | 规则 |
|---|---|
| 覆盖范围 | 导入文件**声明品牌范围**，该品牌下的旧行**全部删除后重建** |
| 为什么不是整表覆盖 | 整表覆盖会误删其他品牌数据；TRR 数据通常按品牌分批抓取更新 |
| 为什么不是按 key upsert | upsert 下文件中不存在的旧行会**残留**，四维匹配时可能命中过期行导致 C 值错误——这是定价出错且不易察觉的主要来源 |
| 文件内校验 | 同一文件内四维组合重复 → 该行标记无效，不入库并在导入结果中列出 |
| 导入结果 | 展示 新增 / 更新 / 删除（被覆盖的旧行）/ 无效行 四项计数 |
| 导入前 | **校验 + 预览品牌范围与新旧数量**（导入文件涉及哪些品牌、每品牌旧记录数 → 新记录数）；确认后**原子提交** |

**★ v1.1 · OQ-010 批次审计与错误恢复**

| 能力 | 规则 |
|---|---|
| **批次版本号 + 审计** | 每次导入生成一个批次，保存 **原始文件 / 导入人 / 导入时间 / 品牌集合 / 解析器版本 / 结果摘要（新增·更新·删除·无效计数）** |
| **全量替换语义（复述）** | 识别文件品牌集合 → 每个出现品牌的旧有效记录**全部失效**、仅留本次文件该品牌数据 → **未出现品牌完全保留** → **不做品牌+系列细粒度差量** |
| **错误批次处理** | 发现某批次数据有误，可**暂停该批次参与新定价/重算**；**上传正确文件对同品牌再次全量替换**做**前向修正**（新批次覆盖旧批次） |
| **不做一键回滚** | **不提供"一键回滚"按钮**——纠错靠前向修正（重传正确文件），不做逆向回退 |
| **错误可回查** | 错误定价可**回查其命中的 TRR 批次**（定价记录关联所用 TRR 批次版本），定位问题数据来源 |

**规则说明**
- 颗粒度：**品牌 + 系列 + 尺码 + 成色** 四维
- **按标准名匹配，不挂自建实体 ID**——TRR 是三方参考数据，天然按名字组织
- Top 系列决定②走 Top 定价路径还是公式6
- **样本数 / 数据日期**为爬虫抓取时带入的元数据，供运营判断数据可信度与新鲜度；**V1.0 不参与定价逻辑**（定价降级规则维持 §2.4 现状不变）

**校验规则**

| 字段 | 规则 | 时机 |
|---|---|---|
| 均价 | 必须为正数 | 保存时 / **导入时** |
| 四维组合 | 不可重复 | 保存时 / **导入时（文件内查重）** |
| 品牌范围 | 导入文件必须声明品牌，且品牌须为已知标准名 | 导入时 |

**异常处理**：四维组合无数据 → 无 C 值，②包袋走公式6（非报错场景）。导入文件品牌未声明或含多品牌 → 阻断导入并提示。

**UI 关联**：原型 v20 →「TRR 参考价」页（`TrrPage`）

### 2.12 定价规则（页面型）★ v1.1 新增

**功能描述**：运营后台「定价规则」页——维护②选品定价所用的**公式与命中顺序**（附录 7.4 的规则集）。**v1.1 · R7 简化版**：仅"可读 + 可编辑 + 操作记录"，**不做审批/发布流程**。

> **★ v1.1 · R7 决策4 降级说明**：原决策4 计划做完整可编辑规则引擎（草稿 → 语法/量纲/重叠校验 → 影响预览 → 审批 → 发布不可变版本 → 暂停/恢复）。经核实，本期**降级**为：定价规则页仅 **可读 + 可编辑（增改 / 调序 / 新增 / 删除）+ 操作记录**，**去掉 影响预览 / 提交审批 / 发布版本 / Steps 发布流程**。理由：同一波人操作、变更直接生效、留操作记录即可。**完整的审批发布治理留至 V2。**

**前置条件**：定价规则集已初始化（附录 7.4）。

**页面布局**：单页列表。规则列表（按命中顺序排列）→ 行内编辑/调序/删除 → 新增规则 → 操作记录区。

**页面元素**

| 区域 | 元素 |
|---|---|
| 规则列表 | 规则ID、适用条件、B 表达式、命中顺序、低价修正、启用状态、更新时间、操作 |
| 操作 | 新增 / 编辑（改条件·改公式）/ 调序（上移下移）/ 删除 |
| 操作记录 | 操作人 / 时间 / 操作类型 / 前值→后值 |

**变更生效**

同一波人操作、**变更直接生效**（无审批 / 发布版本闸门）；每次变更留操作记录。规则的存储与分发方式由**技术环节**设计。

> **规则用受控条件/公式模板**（沿用附录 7.4 的 B146/B128/B122 与区间边界结构），**禁止任意自由表达式**，避免运营写出不可解析或量纲错误的规则。

**校验规则**

| 字段 | 规则 | 时机 |
|---|---|---|
| B 表达式 | 须为受控公式模板（系数 + 常数项），不接受自由表达式 | 保存时 |
| 命中顺序 | 顺序号唯一、连续 | 保存/调序时 |

**异常处理**：删除/停用某规则后，②按剩余规则集执行；历史已定价商品不回溯（成本/价格已固化，重算仅对未定价与规则源变更触发的商品，见 §2.1.4）。

**UI 关联**：原型 v20 →「定价规则」页（`PricingRulePage`）

### 7.4 定价公式表（OQ-017 固化 · 权威规则集）★ v1.1 新增

> 本表把②选品定价（§2.4）所用的公式 1~7 + 公式6 + 非包袋固定公式**逐条固化**，作为「定价规则」页（§2.12）的初始规则集与开发依据。原文见 `v3.1.2-product-modules-docs/rules/04-1-pricing.md`。**顺序命中即停 + 兜底**；区间边界一律**上界 ≤**。

**基数公式**

```text
A = 折扣价 / 汇率            汇率可配置，V1 默认 6.86（不硬编码、不接实时汇率）
B146 = ceil(1.46·A + 207)
B128 = ceil(1.28·A + 181)
B122 = ceil(1.22·A + 172)
```

**命中总路径**（自上而下，命中即停）

```
1. 价格无效（折扣价空/非数字/≤0） ────────────────→ 不选中（否）
2. 养护/改色/边油重做 ──────────────────────────→ 不选中（否，显示真实原因）
3. 非包袋且非排除大类 ─────────────────────────→ 非包袋固定公式（PRICE-NB）
4. 非目标包袋 ────────────────────────────────→ 不选中（否）
5. 宝格丽 / 非 Top / 无系列 / 无均价C ──────────→ 公式6（PRICE-F6）
6. Top + 有 C ────────────────────────────────→ 公式 3/1/2/4/5/7 顺序命中
   ★ 取整后 A > B（成本高于挂牌价）→ 定价错误，阻断写入与自动上架（v1.1 · OQ-018）
```

**公式明细表**（Top + C 分支，顺序命中即停）

| 规则ID | 公式名 | 适用条件（顺序命中，上界 ≤） | B 表达式 | 区间边界 | 低价修正（B≤500） | 命中说明 |
|---|---|---|---|---|---|---|
| `PRICE-F3` | 公式3 | `B146 ≤ 70%C` | B = B146 | B146 ∈ (—, 0.70C] | 不适用（本就用 B146） | 最深折扣档 |
| `PRICE-F1` | 公式1 | 上未命中且 `B146 ≤ 80%C` | B = B146 | B146 ∈ (0.70C, 0.80C] | 不适用（本就用 B146） | — |
| `PRICE-F2` | 公式2 | 上未命中且 `B128 ≤ 90%C` | B = B128 | B128 ∈ (—, 0.90C] | **B≤500 → 改用 B146** 并保持选中 | — |
| `PRICE-F4` | 公式4 | 上未命中且 `B128 ≤ C` | B = B128 | B128 ∈ (0.90C, C] | **B≤500 → 改用 B146** 并保持选中 | — |
| `PRICE-F5` | 公式5 | 上未命中且 `B122 ≤ 1.10C` | B = B122 | B122 ∈ (—, 1.10C] | **B≤500 → 改用 B146** 并保持选中 | — |
| `PRICE-F7` | 公式7（兜底） | 上均未命中（`B122 > 1.10C`） | B = B122 | B122 ∈ (1.10C, —) | **B≤500 → 改用 B146** 并保持选中 | **高于市场参考价提示**；★ v1.1 · R4：**仍选中**，不因超 C 而不选中 |
| `PRICE-F6` | 公式6 | 宝格丽 / 非 Top / 无系列 / 无均价C 的**包袋** | B = ceil(1.28·A + 181) | 无 C，不参与 C 比较 | **B≤500 → 改用 B146** | 无 C 的包袋走公式6，≠默认不选中 |
| `PRICE-NB` | 非包袋固定 | 非包袋且非排除大类 | B = B146（固定） | — | 不适用（本就用 B146） | 固定公式 |

**低价修正与例外**

- **低价修正**：公式 2 / 4 / 5 / 7 及 6，当 `B ≤ 500` → 改用 B146 并**保持选中**。
- **Speedy 低价例外**：Speedy 系列在 `B ≤ 500` 时**不选中（否）**（唯一的低价"不选中"例外）。

**不选中（否）的全部情形**（v1.1 · R4 收敛为 4 类，删除"超 TRR 不选中"）

1. 价格无效（折扣价空/非数字/≤0）
2. 养护 / 改色 / 边油重做
3. 非目标包袋（且非固定公式大类）
4. Speedy 低价例外（B≤500）

**示例（命中路径演示）**

| 输入 | 标准化 | C | A | 计算 | 命中 | 输出 B | 选中 |
|---|---|---|---|---|---|---|---|
| 折扣价 ¥7,546 | LV / Neverfull / MM / A（Top） | $2,200 | 7546/6.86 ≈ 1100 | B146=1813（>80%C=1760）→ B128=ceil(1.28·1100+181)=1589 ≤ 90%C=1980 | `PRICE-F2` 公式2 | **1589** | 是（A=1100 < B=1589） |
| 折扣价 ¥3,430（Top，深折） | 某 Top 包 | $2,000 | 500 | B146=ceil(1.46·500+207)=937；937 ≤ 70%C=1400 | `PRICE-F3` 公式3 | 937 | 是 |
| 折扣价 ¥13,720（Top，超C） | 某 Top 包 | $1,000 | 2000 | B122=ceil(1.22·2000+172)=2612；2612 > 1.10C=1100 | `PRICE-F7` 公式7兜底 | 2612 | **是**（高于市场参考价提示，R4 仍选中） |

> **量纲与舍入口径（v1.1 · OQ-018）**：A、B、C 全部 USD；B = ceil 到整数 USD；CostPrice = A **保留整数、小数位向上取整**（v1.2，如 100.1 → 101）；成本与挂牌价比较统一 USD；取整后 A>B → 定价错误阻断（见 §2.4）。
