## 一、概述

### 1.1 背景与目标

**背景**

looply 是面向海外市场的二手奢侈品电商平台。红布林（国内二奢平台）是 looply 的核心货源方，通过 API 向 looply 推送在售商品数据。此前 looply 依托 Shopify 建站，商品上架依赖「Excel 导出 → 人工导入 → 调 Shopify API 创建并发布」的半自动链路，受 Shopify 的 API 限流与批量写入约束，必须人工分批操作。

looply 自建商品系统后，上述外部约束消失，红布林对接链路需要重构为**全自动流水线**。

**目标**

1. 红布林推送的商品数据 100% 落库留底，不丢不失败
2. 选品定价、翻译、标品对齐、主数据映射、实体创建、上架校验**全流程自动化**，人工只处理异常
3. 红布林侧的状态变化（售出/下架/重新上架）与信息变化（折扣价/图片/品类）自动同步到 looply 商品系统
4. 折扣价变更引发的挂牌价重算，由系统给建议、运营做决策

**与现有业务系统（Shopify 版 v3.1.2）的关系**：本模块是对 v3.1.2 中「3.1 商品上架 / 3.5 商品清理 / 4.1 选品定价 / 4.2 商品翻译」四个模块的重构与合并，详见附录 7.2。

### 1.2 不做什么（边界）

| 不做的事 | 原因 / 归属 |
|---|---|
| **订单履约链路** | 已拆分为独立模块「红布林订单对接」，含下单、支付、国内发货、集货仓、报关、国际物流、取消退回 |
| **批量打标 / 营销选品** | 筛选条件全部是商品系统标准字段，无红布林特有字段，对象不限红布林来源 → **归商品系统**，已记入商品模块待优化清单第 7 条 |
| **主动促销调价（大促 / 清仓）** | 与红布林折扣价无关，属商品系统渠道商品价格运营能力。本模块⑥只处理"折扣价变更倒逼的挂牌价重算"，运营不能在此凭空发起促销降价 |
| **人工确认上架** | 原为 Shopify 限流产物，自建系统已取消（见 §2.5.4） |
| **标品（SPU / 标品SKU）人工维护页** | 数据量大，人工逐款建标品不可行，改为系统自动创建 + 回填映射表 |
| **渠道库存分配** | 不在 V1 范围 |
| **商品详情页渲染规则** | 归商详模块，本模块只负责把英文数据写进 product / listing |
| **未上架商品的查看入口** | 去商品系统「渠道商品」列表查看，本模块不再提供上架页 |

### 1.3 用户角色

| 角色 | 职责 | 涉及页面 |
|---|---|---|
| **商品运营** | 处理加工异常、映射异常、上架校验异常；维护主数据映射 / 翻译术语库 / TRR 参考价；对价格变更逐行决策并分批执行 | 全部 5 个页面 |
| **系统（自动任务）** | 接收推送、选品定价、翻译、标品对齐、映射、创建实体、校验上架、状态同步、算建议价 | 无界面 |

> V1.0 不做角色权限细分，所有商品运营人员权限一致，故 §六 权限与角色矩阵省略。

### 1.4 核心场景

1. **新商品自动上架**：红布林推送 → 留底 → 自动定价+翻译 → 款型对齐标品 → 属性映射 → 自动建 product/库存/listing → 自动校验 → 上架销售。全程无人工。
2. **异常修复**：加工异常（术语未命中）/ 映射异常（新颜色值）/ 上架校验异常（中文残留、url_slug 冲突）→ 运营在「红布林商品库」集中筛出并修正 → 系统自动重跑。
3. **商品售出/下架**：红布林推送下架信号 → 系统内部判断售出/普通下架/重新上架 → 清零或恢复库存、联动 listing 与 product_status。
4. **折扣价变更调价**：红布林折扣价变 → 系统算建议价 → 进「价格变更商品列表」→ 运营逐行决定采纳/维持/自定义 → 分波分批执行 → 回读验证。
5. **规则源维护**：运营在主数据映射 / 翻译术语库 / TRR 参考价三页补充规则，系统自动重跑受阻商品。

### 1.5 全局页面流转

```
红布林商品库（默认首页）
  ├─ 筛「加工异常」→ 行内「去修正」弹窗 → 补英文/术语 → 回到列表
  ├─ 筛「映射异常」→ 行内「去映射」→ 主数据映射页
  └─ 行内「详情」→ 红布林原始信息弹窗（只读）

数据维护
  ├─ 主数据映射（10 个 Tab）→ 行内「申请新增标准值」弹窗
  ├─ 翻译术语库（18 个 Tab = 15 类术语对照 + 3 类拼接规则）
  └─ TRR 参考价

价格变更商品列表
  └─ 「规则说明」弹窗
```

> 本模块共 5 个一级/二级页面，无多层级跳转。②③④⑤ 四个环节为系统自动流程，**无独立页面**，其运行结果体现在「红布林商品库」的状态字段上。

### 1.6 术语说明

| 术语 | 含义 |
|---|---|
| **快照层** | 红布林推送数据的全量留底层，以红布林商品ID 为主键，保存中文原始值，后推覆盖 |
| **款型ID** | 红布林对接**新增字段**，与商品系统标品SKU **1:1 对应**，是标品层的对齐键 |
| **标品SKU（standard_sku）** | 商品系统标品层实体，多件实物商品可共用同一标品SKU |
| **SPU** | 标准产品单元，品牌/系列/类目外键挂在此层 |
| **product（实物商品）** | 一物一码实体，只挂 `standard_sku_id` 一个主数据外键，品牌/系列/类目经 `standard_sku → spu` 继承 |
| **listing（渠道商品）** | 渠道销售实体，承载挂牌价、货币、上架状态、`url_slug` |
| **信息准备进度** | 快照层的加工进度状态（本模块特有），见 §2.1.2 |
| **product_status** | 商品系统的标准商品状态（共 7 态），本模块只写入其中 4 态 |
| **主数据映射** | 红布林原始值 → 商品系统标准记录 ID，产物是 **ID**（落外键） |
| **翻译术语库** | 中文值 → 英文文本 + 拼接规则，产物是**英文文本**（拼商品名） |
| **TRR 参考价** | 三方市场参考均价（The RealReal），按品牌+系列+尺码+成色四维、**按标准名匹配**，不挂自建实体 ID |
| **A / B / C** | A=折扣价/6.86（USD 成本基数）；B=挂牌价（定价公式输出）；C=TRR 均价 |

### 1.7 多语言支持

**A. 静态 UI 文案 — 不做国际化**

本模块是**国内商品运营团队使用的中文后台**，界面文案固定中文，不接入前端语言包，不做 i18n。

> 若后续有海外运营人员使用，再单独提需求接入语言包。

**B. 动态业务内容 — 本模块是英文内容的生产者**

本模块的产出物（product / listing 的英文字段）直接面向 C 端多语言展示，产出规则：

| 产出字段 | 来源 | 说明 |
|---|---|---|
| `product.title`（英文商品名） | 翻译术语库拼接生成（§2.10） | 中文原始值 → 术语库取英文 → 按拼接规则组装 |
| `product_inspection` 成色/瑕疵/配件描述 | 翻译术语库 | 同上 |
| `listing.url_slug` | `slugify(Brand+' '+ProductName)+'-'+ItemID` | 见 §2.5.4 及风险 R4 |
| 品牌 / 系列 / 类目 / 属性英文名 | **不由本模块产出** | 来自商品系统标准记录，本模块只落 ID |

**关键约束**：本模块写入 product / listing 的英文字段**必须无中文残留**，这是上架校验的阻断项（§2.5.4）。

**C. 其他语种的 Fallback**

本模块只产出**英文**。英文之外的语种由**翻译模块**负责：商品系统的品牌/系列/类目/属性标准记录已接入翻译服务，product.title 等本模块产出的自由文本是否需要注册翻译 Key，**由商品模块的多语言方案统一决定**，本模块按其规范接入。Fallback 规则引用多语言 PRD §4.6：有译文返回译文 → 有过期译文返回旧译文 → 无记录返回英文源文本。

#### 2.1.2 信息准备进度（本模块特有状态）

| 枚举值 | 含义 | 触发时机 | 后续 |
|---|---|---|---|
| `to_process` 待加工 | 已留底未加工 | ① 同步留底完成 | 系统自动触发② |
| `processing` 加工中 | 正在选品定价/翻译 | ② 开始 | — |
| `process_err` 加工异常 | 翻译中文残留 / 术语未命中 | ② 失败 | 运营补术语 → 自动重跑 |
| `priced` 已定价 | 定价选中 + 翻译完成 | ② 成功 | 系统自动触发③ |
| `map_err` 映射异常 | 属性值未命中标准记录 | ③ 步骤二失败 | 定时重试 / 运营补映射 |
| `list_err` 上架校验异常 | 5 项上架校验未通过 | ③ 步骤四不通过 | listing 停留未上架、product_status 待销售，修复后自动重校验 |
| `listed` 已上架 | 创建 + 校验 + 上架全部完成 | ③ 步骤四通过 | 终态 |
| `excluded` 已排除 | 未通过选品 | ② 排除检查或未选中 | 终态，不翻译不映射不建标品 |

> **v1.6 已删除**「已创建待上架」态——创建后立即自动校验上架，不再有"已创建但未上架"的常态停留。校验不通过属**异常**，进入 `list_err`「上架校验异常」态并停留在创建环节。

#### 2.1.3 商品状态（product_status，商品系统标准枚举）

商品系统定义 **7 态**：待核验 / 核验中 / **待销售** / **销售中** / **已售出** / 已停售 / **已失效**。

本模块只写入其中 **4 态**：

| 枚举值 | 本模块写入时机 |
|---|---|
| 待销售 | ③ 创建 product 时初始值；**仅在上架校验不通过时停留**（异常态） |
| 销售中 | ③ 校验通过自动上架；④ 重新上架 |
| 已售出 | ④ 售出场景 |
| 已失效 | ④ 普通下架场景 |

> **不能因本链路用不上就删除其余 3 态**——product_status 是商品系统标准枚举，红布林只是写入来源之一，未来自营/其他入驻商家会用到待核验/核验中/已停售。

#### 2.1.4 统一异常处理机制（机制型）

**功能描述**：三类异常（加工异常 / 映射异常 / 上架校验异常）全部汇入「红布林商品库」页集中处理，不设独立异常页。

**处理流程**

| 异常类型 | 入口 | 处理方式 | 修复后 |
|---|---|---|---|
| 加工异常 | 顶部「加工异常」KPI 快捷筛选 | 行内「去修正」弹窗，补齐英文/术语 | 系统自动重跑② |
| 映射异常 | 顶部「映射异常」KPI 快捷筛选 | 行内「去映射」跳转主数据映射页补 ID | **系统定时自动重试**（映射库更新后自愈），无需人工触发 |
| 上架校验异常 | 列表筛选 | 按阻断原因修正（补英文、改名解 slug 冲突、补图） | 系统自动重新校验并上架 |

**规则说明**
- 映射异常优先靠系统定时重试自愈，只有长期未解决的全新值才需运营补映射
- 修复动作不改变已有 product 数据，只推动流程继续

**异常处理**：修复后重跑仍失败 → 保持异常态并累计失败次数，超阈值（建议 3 次）后标记为需人工深度介入。

### 2.2 红布林商品库（页面型）

**功能描述**：红布林快照层的唯一视图，展示全量推送商品及其两维状态，同时承担三类异常的集中处理入口。本模块默认首页。

**前置条件**：红布林已推送数据。

**页面布局**：单页列表。顶部 KPI 区（8 项）→ 筛选区 → 表格 → 底部状态说明块。右上角「架构说明」按钮弹出三层架构与创建规则说明。

**页面元素**

| 区域 | 元素 |
|---|---|

### 2.3 ① 商品同步留底（机制型）

**功能描述**：接收红布林 Webhook 推送，全量落库到快照层，不做任何加工。

**触发条件**：红布林通过 Webhook 推送商品数据。

**处理流程**
1. 接收数据（品类/品牌/系列/**款型ID**/成色/折扣价/图片URL，中文）
2. 存入快照层，以红布林商品ID 为主键
3. 完整保留中文原始数据（折扣价 CNY、养护/改色/边油重做标记等）
4. 信息准备进度置「待加工」
5. 自动触发②

**规则说明**
- **快照层是全量主体**：红布林推送 100% 落库，不丢不失败，即使数据不完整也先留底
- 后推覆盖：同一红布林商品ID 再次推送时覆盖快照最新值
- 此阶段**无 product**，product 在③创建

**异常处理**：推送接收的幂等、重试、异常恢复由技术方案保证，PRD 不约束实现方式。

**技术说明**：无。

### 2.4 ② 系统自动加工（机制型）

**功能描述**：对「待加工」商品自动执行选品定价 + 翻译，全程无人工向导。原「商品翻译」「选品定价」独立菜单已取消。

**触发条件**：①留底完成后系统自动触发。

**处理流程**

顺序：**先选品定价 → 选中的再翻译**（未选中不翻译，省资源）。

**阶段一 · 自动选品定价**

1. 读折扣价：`A = 折扣价 / 6.86`（CNY→USD）
2. 读 TRR：`C = 均价`（**按品牌/系列标准名匹配，不经自建实体 ID**）
3. 排除检查：补色养护 / 改色 / 边油重做 / 折扣价无效 → 「已排除」
4. 分流定价：

```
B146 = ceil(1.46A + 207)    B128 = ceil(1.28A + 181)    B122 = ceil(1.22A + 172)

· 包袋 Top(有C)：3(B146≤70%C) → 1(≤80%C) → 2(B128≤90%C) → 4(≤C) → 5(B122≤1.10C) → 7兜底
· 包袋 非Top / 无C / 宝格丽：公式6 = ceil(1.28A + 181)
· 非包袋（非排除大类）：固定 B146
· 超 TRR 比例（如 B>1.10C）/ 未命中：不选中 → 已排除（记录原因）

低价修正：公式 2/4/5/7 及 6，B≤500 改用 B146 并保持选中
         Speedy 例外：B≤500 仍不选中
```

5. 选中 → 计算 Cost（折扣价≤B 保留原值，>B 则取 折扣价/6.86）+ 挂牌价 + 所用公式，暂存快照

**阶段二 · 自动翻译**（仅对选中商品）

1. 各字段中文 → 英文，取自**翻译术语库**（品牌/系列/类目/颜色/材质/尺码/五金/设计元素）
2. 按术语库的**拼接规则**（Category Suffix / Wallet 范围 / 类目拼接顺序）组装英文 Product Name

**规则说明**

**TRR 匹配颗粒度**：品牌 + 系列 + 尺码 + 成色 四维，按标准名匹配。示例：

> 折扣价 ¥7,546，标准化后 Louis Vuitton / Neverfull / MM / A
> → Top 系列表命中 `LV+Neverfull` → 走 Top 路径
> → 均价表 `LV+Neverfull+MM+A` → C = $2,200
> → A = 7546/6.86 ≈ 1100，B146 = ceil(1.46×1100+207) = 1813
> → 1813 ≤ 70%×2200(=1540)？否 → ≤80%×2200(=1760)？否 → 用 B128 继续判断…

**降级规则**：尺码命名不同靠尺码术语归一；四维组合在 TRR 无数据 → 无 C 值，包袋走公式6；无系列 → 公式6 或标「否」。

**为什么定价不依赖主数据映射**：TRR 是三方参考数据，天然按品牌/系列名字组织，用标准名匹配即可。若强行让 TRR 挂自建实体 ID，等于要为每次 TRR 更新维护一层"三方值→自建 ID"的对应，成本高且脆弱。映射产出的实体 ID 只在③建 SPU / 落属性外键时才用。

**加工结果**

| 结果 | 信息准备进度 | 后续 |
|---|---|---|
| 定价选中 + 翻译成功 | 已定价 | 自动触发③ |
| 翻译中文残留 / 术语未命中 | 加工异常 | 运营补术语 → 自动重跑 |
| 未选中 | 已排除 | 终态，不翻译、不映射、不建标品 |

**异常处理**：加工异常汇入「红布林商品库」集中修正（§2.1.4）。

**技术说明**：选品/定价/翻译规则全部写死代码，后端流水线实现。空尺码回填 TRR 匹配尺码、名称清洗等细节由后端处理。

### 2.5 ③ 标品对齐 + 创建实体 + 自动上架（机制型）★

**功能描述**：对「已定价」商品，按款型ID 对齐标品SKU → 属性主数据映射 → 自动创建全套实体 → 自动校验并上架。全程系统自动，**无人工确认上架环节**。

**触发条件**：②产出「已定价」后自动触发。「已排除」商品不进入本段。

#### 2.5.1 步骤一 · 标品对齐（款型ID → 标品SKU）

| 情况 | 系统动作 |
|---|---|
| **命中**（N:1） | 复用已有 `standard_sku_id`；同款型的多件实物商品共用同一标品SKU，直接继承 SPU 的品牌/系列/类目及 SPU 级属性 |
| **未命中**（新款型） | 先映射品牌/系列/类目 → **系统自动创建 SPU + 标品SKU**（无人工）→ **立即回填**款型ID↔标品SKU 映射表 |

**规则说明**
- 款型ID 与标品SKU **1:1**；product → standard_sku 为 **N:1**
- **为什么标品自动创建、不做人工维护页**：红布林推送数据量大，人工逐款建标品不可行；款型ID 是红布林侧已有的稳定标识，足以作为标品层唯一键，自动建 + 回填映射表即可自愈
- **效果**：映射工作量从"每件商品"降到"每个新款型"，同款型第二件起零映射成本

> ★ **必须区分**：本段保留的「映射异常 → 定时重试 / 运营补映射」指**属性值归一**（步骤二）。**标品SKU 的创建是全自动的、没有人工兜底环节**。

#### 2.5.2 步骤二 · 主数据映射（按三层架构分流）

| 红布林字段 | 归一到 | 落在哪一层 |
|---|---|---|
| **款型ID** | 标品SKU | **标品层**（步骤一完成） |
| 品牌 / 系列 / 类目 | brand_id / series_id / category_id | **SPU**（建 SPU 时落外键，product 经 standard_sku→spu 继承） |
| 颜色 / 材质 / 尺码 | attribute_option_id / size_value_id | 按 `attribute_scope_config.value_level` 决定落 **SPU / SKU / ITEM**；`value_level=ITEM` 时属性值写入 **`product_attribute_value`** |
| 成色 / 瑕疵 / 配件 / 序列号 / 年份 | 标准选项 ID 或文本 | **product / product_inspection**（一物一码，不进标品层） |

**规则说明**
- 商品系统标准值为**英文**，映射即归一到英文标准记录，product 落英文不落中文
- **多对一**：多个红布林原始值可归一到同一标准记录
- **ITEM 级属性值的落库表**：`value_level=ITEM` 的属性值统一写入 `product_attribute_value`（product 一物一码维度）；SPU / SKU 级属性值分别落 SPU、标品SKU 的属性表
- 全部命中 → 进入步骤三；有失败 → 「映射异常」，系统定时自动重试，长期未解决的由运营补映射

#### 2.5.3 步骤三 · 自动创建实体

| 实体 | 内容 |
|---|---|
| **product** | `standard_sku_id`（★唯一的主数据外键）+ seller_id + title + serial_number，product_status 初始「待销售」，关联红布林商品ID |
| **product_image** | 产品图 + 瑕疵图，保持源顺序 |
| **product_inspection** | 成色 / 瑕疵 / 配件（一物一码字段） |
| **inventory_item** | qty=1 + 库存流水 INBOUND |
| **listing** | 渠道 + 市场 + 挂牌价 + currency + CostPrice + url_slug |

> ★ **product 不落 brand / series / category 外键**——这些在 SPU 上，经 `standard_sku → spu` 继承（依据 ER v2.6）。

#### 2.5.4 步骤四 · 自动校验 + 自动上架 ★

listing 创建后系统**立即校验**，5 项卡口：

| 校验项 | 规则 |
|---|---|
| 中文残留 | 任何面向 C 端的英文字段出现中文字符即阻断 |
| url_slug 冲突 | `listing.url_slug` 是 **UK（唯一键）**，冲突必须阻断 |
| 必填项齐全 | 建 listing 必需字段完整 |
| 图片顺序 | 商品/成色图在前、瑕疵图在后，保持源顺序 |
| 挂牌价有效 | 存在且为有效正值 |

| 校验结果 | listing | product_status | 信息准备进度 | 后续 |
|---|---|---|---|---|
| **通过** | **Active（卖场可售）** | **销售中** | **已上架** + 回写 product_id | 无人工动作 |
| **不通过** | 未上架 | 待销售 | **上架校验异常**（`list_err`） | 进「红布林商品库」统一异常处理，修复后自动重新校验上架 |

> ★ **为什么取消人工确认上架**：原④的"人工确认 + 分批上架"是 **Shopify 上架数量/限流约束**的产物——Shopify 有 API 写入速率与批量限制，必须靠人工分批节流。对接自建系统后不存在这些限制，人工确认只剩重复劳动。
>
> **随原④一并删除（Shopify 驱动项）**：7 维写后审计 / 可修复项自动补写 / 3lane 分批限流 / Draft→Active 两步流转
> **保留并前移为本段自动卡口（与渠道无关）**：上表 5 项
> **注意**：⑥价格变更的"分波分批"是为降低 C 端浏览冲击，**与 Shopify 限流无关**，保留不动

**关键规则**

- **url_slug 生成**：`slugify(Brand+' '+ProductName)+'-'+ItemID`，创建时生成，UK 唯一
  > ⚠️ 该公式沿用旧 Shopify 实现，`ItemID` 是红布林商品ID，**对非红布林来源商品不适用**。已记入商品模块待优化清单第 8 条，待商品系统定义通用生成规则后本模块改为引用，见风险 R4
- **属性集由「属性作用域配置」（`attribute_scope_config`）决定**，非 Shopify 的 Template / Metafields：
  - 按 `category_id` + `scope_type` 配置，支持 **CATEGORY / CATEGORY_BRAND / CATEGORY_SERIES 三级作用域**
  - `is_required` 控制必填，`sort_order` 控制展示排序，`value_level` 决定值落 SPU/SKU/ITEM
  - 属性定义与可选值来自 `attribute_def` / `attribute_option`
  - Shopify 的 `template_suffix` 是前台主题渲染模板，**自建系统无对应对象**，商详页渲染归商详模块
- **一物一码**：inventory_item qty=1

> **映射与翻译的职责边界（★核心，正交关系）**
> - **主数据映射**回答"红布林这个值是我库里的哪条实体记录" → 产 **ID**（建 SPU / 落属性外键）
> - **翻译术语库**回答"这个中文值的英文文本是什么" → 产**英文文本**（②加工时拼商品名）
> - 品牌/系列/类目**两处都要处理**：②翻译取英文名、③映射取 ID，**英文名从术语库取，不从映射取**
> - 一句话：**映射产 ID（落外键），翻译产英文文本（拼名），两个正交模块**

**异常处理**：见 §2.1.4。

**技术说明**：渠道库存分配不在 V1 范围。已上架商品的信息修正走⑤。

### 2.6 ④ 红布林状态同步（机制型）

**功能描述**：接收红布林下架推送信号，内部判断场景并分流处理库存、listing、product_status。

**触发条件**：红布林推送商品下架信号（红布林商品ID + 状态）。

> **核心**：红布林侧「售出」与「下架」是**同一个下架推送信号**，红布林不区分。looply 收到后内部判断场景再分流。

**处理流程**

1. 覆盖快照（该红布林商品ID 最新状态）
2. 按红布林商品ID 查 product
3. 未建 product 或无 listing → 仅覆盖快照，结束
4. 已建 product → 内部判断场景并分流：

| 场景 | 库存 | listing | product_status | 订单保护 |
|---|---|---|---|---|
| **售出** | 清零 qty=0 + 流水 SOLD -1 | 下架 | 已售出 | **有活跃订单不直接清零，转异常** |
| **普通下架** | 清零 qty=0 | 下架**不删除** | 已失效 | — |
| **重新上架** | 恢复可售 | 恢复 Active | 销售中 | — |

5. 回查验证，不通过标记异常人工介入

**规则说明**
- 售出与普通下架**都清零库存**——一物一码（qty=1），下架即置 0，**无"保留数量"概念**
- 两者区别**仅在 product_status**（已售出 / 已失效）
- listing 下架但不删除，便于重新上架时恢复
- 对比现有系统 3.5 清理：手动 Excel 对账 → API 自动同步 + 定期对账安全网

**异常处理**

| 场景 | 处理 |
|---|---|
| 售出但有活跃订单 | 不清零库存，转异常人工介入（防止已售商品的在途订单失去库存依据） |
| 回查验证不通过 | 标记异常，人工介入 |
| 商品未建 product | 仅覆盖快照，不报错 |

### 2.7 ⑤ 商品信息变更（机制型）

**功能描述**：接收红布林信息变更通知，覆盖快照并按变更类型联动 product / listing。

**触发条件**：红布林通知信息变更（红布林商品ID + 变更字段 + 新值），或内部修正。

**处理流程**

1. 先覆盖快照（写入新的中文原始值）
2. 按红布林商品ID 查 product
3. 未建 product → 仅覆盖快照，后续加工用最新值
4. 已建 product → 按变更类型分流：

| 变更类型 | 处理 | 人工介入 |
|---|---|---|
| **折扣价变更** | 按定价公式算**建议价** + 更新 CostPrice → **生成价格变更待办**进入⑥ | 无（决策在⑥） |
| **图片变更** | 下载新图 → 更新 listing 图片，保持源顺序 | 无 |
| **品类/品牌/系列变更** | 重新翻译（英文文本）+ 重新映射（ID）→ 更新 product | **需人工确认** |

5. 回查验证，不通过标记异常

> ★ **本段职责到"生成价格变更待办"为止**。运营的逐行决策、分波分批勾选、价格写入、回读验证**全部在⑥**，两段不重叠。

**规则说明**

**折扣价变更不区分是否已上架**：未上架的和已上架在售的一起进⑥。

**为什么类目/品牌变更要走"重新翻译→映射→更新"而非直接改**：直接改会导致
1. 依赖品牌/系列/类目拼接的 Name / url_slug / Tags 及按属性作用域配置取值的属性集连锁失准
2. 主数据 ID 失联（改英文文本不改映射 ID）
3. 英文 product 与中文快照回溯断裂

正确做法是整体重算更新（术语库重取英文名、映射重取 ID），保证连锁字段一致、ID 正确、可回溯。

> 补充：品牌/系列/类目挂在 SPU 上，若变更导致款型归属改变，等价于该实物商品需要重新对齐到另一个标品SKU（必要时新建 SPU + 标品SKU），故必须整体重算而非就地改字段。

**异常处理**：回查验证不通过 → 标记异常，人工介入。

### 2.8 ⑥ 价格变更商品列表（页面型）★

**功能描述**：承接⑤折扣价变更生成的价格变更待办，运营逐行决策后分波分批执行价格写入。

> **用词口径（以原型 v15 为准）**：**页面**名为「价格变更商品列表」，页面内的**单条记录**称「价格变更待办」（对应表 `plm_price_change_todo`、页面 KPI「待办总数」）。流程图 V12.1 与业务操作说明书 v1.6 中的"价格变更待办"即指此记录。

> **第一性原理**：红布林折扣价是 looply 的**定价输入**（挂牌价 B = f(折扣价)）。折扣价变 → 定价输入变 → 挂牌价理论上应重算。但**"要不要跟着调售价"是商业决策**（成本降了可维持原价多赚、也可降价冲量；成本涨了要权衡利润与 TRR 市场价），**系统不能自动改售价**。系统能做的是"算出建议价 + 展示差异"，让运营决定。
>
> ★★ **核心业务口径**：**不存在"运营主动选涨价还是降价"**。涨/降是【系统建议价 vs 当前挂牌价】的**比较结果**，是系统算出来的既成事实；运营决定的是**"采纳 / 维持 / 自定义"**。旧 Shopify 系统 3.4 那套"运营设定目标售价 B → 涨价/降价分支"的主动改价模型**不适用**于本模块。

**前置条件**：⑤已生成价格变更待办。**本页输入唯一来自⑤**，运营不能在此凭空发起一次促销降价。

**页面布局**：单页列表。KPI 区 → 筛选区 → 表格（可勾选）→ 批量操作区 → 底部说明块。右上角「规则说明」弹窗。

**页面元素**

| 区域 | 元素 |
|---|---|
| KPI（5 项） | 待办总数 / 成本降(建议降价) / 成本涨(建议涨价) / 超TRR上限(需人工) / 本批已勾选 |
| 筛选 | 价格变动方向（成本涨·涨价 / 成本降·降价）、TRR 比对（正常 / 超上限需人工）、上架状态（已上架 / 未上架）、关键词搜索（红布林商品ID / 渠道商品ID / 名称） |
| 表格列 | 红布林商品ID、**渠道商品ID**、商品名、品牌、上架状态、当前挂牌价、建议价、TRR 比对、成本变化、调整决定 |
| 批量操作 | 「执行本批调价」 |

> 本页**无独立「操作」列**：运营的采纳/维持/自定义决策在「调整决定」列内直接完成。

> **为什么要有渠道商品ID 列**：改价实际写入的对象是 **listing（渠道商品）**，红布林商品ID 仅为待办来源标识。运营需要看到真正被改价的对象。

**页面状态变体**

| 状态 | 说明 |
|---|---|
| 默认态 | 全部待处理待办 |
| 超 TRR 标记态 | 建议价超 TRR 比例（如 B>1.10C）的行高亮，提示需人工判断 |
| 已决定未执行态 | 行已选择决定但未勾选执行 |
| 空态 | 无待处理待办 |

**操作流程**

**步骤一 · 运营逐行决定**

| 决定 | 目标价 B | 说明 |
|---|---|---|
| **采纳建议价** | B = 系统建议价 | 主路径 |
| **自定义价** | B = 运营手工输入价 | 用于超 TRR 等需人工判断的场景 |
| **维持原价** | — | 不改售价，关闭待办；Cost 有变仍更新 unitCost |

**步骤二 · 分波分批执行**：运营**手动勾选**本波要执行的商品 → 点「执行本批调价」，剩下的下一波再调。

> 目的是**降低对 C 端用户浏览网站的影响**（避免大量商品价格同时跳动）。**与 Shopify 限流无关**，③取消分批限流不影响这里。

**步骤三 · 价格写入规则**（B=目标价，price=当前价，compare_at=划线价）

| 条件 | 新 price | 新 compare-at |
|---|---|---|
| B == compare_at | B | 清空 |
| B > price（**涨价**） | B | 原 compare-at > B 保留，否则清空 |
| B < price（**降价**） | B | max(原 price, 原 compare-at) |
| B == price | 不变 | 不变（Cost 变仍可执行，仅更新 unitCost） |

- 降价时若「新划线价 − 目标价 < $30」→ **自动跳过**（避免频繁微调）

**步骤四 · 回读验证**：写入 listing 价格 + 库存 unitCost 后，回读验证 **price / compare-at / unitCost 三项一致**才标记完成。

**校验规则**

| 字段 | 规则 | 时机 |
|---|---|---|
| 自定义价 | 必须为正数 | 输入时 |
| 自定义价 | 超 TRR 比例时二次确认 | 提交时 |
| 勾选执行 | 至少勾选一行 | 点「执行本批调价」时 |

**交互说明**
- 决定与执行分离：先逐行做决定，再勾选执行，允许"决定了但本波不执行"
- 执行失败的待办留在列表，不消失

**异常处理**

| 场景 | 处理 |
|---|---|
| 回读验证三项不一致 | 标记失败、记录原因，**留在列表**等下一波 |
| 执行时 listing 已被其他流程改价 | 以执行前重新读取的实时价格为准再应用规则（避免用过期预览值误改） |
| 商品已下架/已售出 | 跳过并标记，不改价 |

**UI 关联**：原型 v15 →「价格变更商品列表」页（`PriceTodoInner`）

### 2.9 主数据映射（页面型）

**功能描述**：维护红布林原始值 → 商品系统标准记录 ID 的映射关系。产物是 **ID**，用于建 SPU 和落属性外键。

**前置条件**：商品系统已有标准主数据记录。

**页面布局**：KPI 区 → 说明块 → 10 个 Tab → 各 Tab 内筛选区 + 表格。

**页面元素**

| 区域 | 元素 |
|---|---|
| KPI | 覆盖映射字段数 / 已归一原始值 / 未匹配（映射异常） / 待申请新增标准值 |
| Tab（10 个） | 品牌、系列、类目、颜色、材质、尺码、成色、配件、包型、设计元素 |
| 表格列 | 红布林原始值、自建标准值、**实体ID / 属性选项ID**、状态、更新时间、操作 |
| 操作 | 编辑 / 删除 / 申请新增标准值 |

**映射字段类型枚举**

| 枚举值 | 归一目标 | 落库层级 |
|---|---|---|
| `brand` 品牌 | brand_id | SPU |
| `series` 系列 | series_id | SPU |
| `category` 类目 | category_id | SPU |
| `color` 颜色 | attribute_option_id | 按 value_level |
| `material` 材质 | attribute_option_id | 按 value_level |
| `size` 尺码 | size_value_id | 按 value_level |
| `condition` 成色 | attribute_option_id | ITEM |
| `accessory` 配件 | attribute_option_id | ITEM |
| `bagtype` 包型 | attribute_option_id | 按 value_level |
| `design` 设计元素 | attribute_option_id | 按 value_level |

**状态枚举**

| 枚举值 | 含义 |
|---|---|
| `active` 已激活 | 已映射到标准记录 ID |
| `pending` 待补充 | 未匹配到标准记录，需补映射或申请新增标准值 |

**操作流程**

主流程：运营切换 Tab → 筛选「待补充」→ 行内编辑选择标准值 → 保存 → 状态转「已激活」→ 系统定时重试自动重跑受阻商品。

分支流程：标准库无对应值 → 行内「申请新增标准值」→ 补录后再映射。

**校验规则**

| 字段 | 规则 | 时机 |
|---|---|---|
| 标准值 | 必选，须为商品系统已有的启用状态记录 | 保存时 |
| 原始值 | 同一字段类型下不可重复 | 保存时 |

**交互说明**
- **多对一**：多个原始值可映射到同一标准记录（「路易威登」「路易·威登」→ Louis Vuitton / B001）
- 品牌/系列/类目映射现在主要服务于「款型未命中时自动创建 SPU」场景，命中款型的商品直接继承 SPU，不重复走这三项映射
- 本页**不管标品**：标品SKU 的创建是全自动的，本页只处理属性值归一

**异常处理**：删除已被引用的映射 → 提示影响范围并二次确认（删除后相关商品会重新进入映射异常）。

**UI 关联**：原型 v15 →「主数据映射」页（`FieldMappingPage`）

**页面元素**

| 区域 | 元素 |

**校验规则**

| 字段 | 规则 | 时机 |

| 中文原值 | 同一分组内不可重复 | 保存时 |

**交互说明**

**异常处理**：删除被引用的术语 → 提示影响范围，删除后相关商品重新进入加工异常。

**UI 关联**：原型 v15 →「翻译术语库」页（`GlossaryPage`）

## 三、依赖与风险

### 3.1 上下游系统依赖

| 依赖方 | 依赖内容 | **本模块的关键要求** |
|---|---|---|
| **红布林（外部）** | Webhook 推送商品数据、状态变更、信息变更 | ① 必须提供**款型ID**字段（本次对接新增，标品对齐的唯一依据，缺失则③无法执行）；② 推送需保证幂等与可重试；③ 售出与下架为同一信号，looply 侧自行分流 |
| **商品系统** | SPU / 标品SKU / product / listing 的创建与更新能力；品牌/系列/类目/属性标准记录 | ① 需提供**标品SKU 的程序化创建接口**（本模块自动建标品，非人工）；② `listing.url_slug` 的**唯一性约束必须由商品系统保证**，本模块依赖其冲突检测；③ 属性作用域配置需覆盖二奢品类，否则③映射无处落值 |
| **库存模块** | inventory_item 创建、库存清零、流水记录、unitCost 更新 | ① 需支持 qty=1 的一物一码模型；② **售出清零前需能查询是否存在活跃订单**（订单保护依赖此能力）；③ unitCost 更新需与价格写入在同一事务边界内可回读验证 |
| **订单模块** | 活跃订单查询 | 供④售出场景的订单保护判断使用 |
| **翻译模块** | 品牌/系列/类目/属性标准记录的多语言译文 | 本模块只产出英文，英文之外语种由翻译模块负责；本模块产出的 product.title 是否注册翻译 Key 由商品模块统一决定 |

### 3.2 风险

| 编号 | 风险 | 影响 | 应对 |
|---|---|---|---|
| **R1** | **款型ID 语义未最终确认** | 若同一款型ID 下实际存在不同颜色/尺码，则 1:1 假设不成立，标品层会冲突，需返工重构 | 对接联调阶段抽样验证款型ID 与颜色/尺码的实际分布；一旦发现一对多，需改为「款型ID → SPU + 销售属性 → 标品SKU」两级定位 |
| **R2** | **标品SKU 自动创建污染标品库** | 同款商品因命名/属性差异被建成多个标品SKU，后续清洗成本高 | 定期做标品去重治理；`plm_style_sku_mapping.created_by` 标记 AUTO 便于识别自动创建的记录 |
| **R3** | **本模块 ER 图缺失** | 快照层、映射表等实体只在本 PRD 定义，未经 ER 图评审，可能与商品域已有设计冲突 | 开发前补出红布林对接 ER 图，以本 PRD §2.1 为输入 |
| **R4** | **url_slug 生成规则依赖红布林商品ID** | `slugify(...)+'-'+ItemID` 对非红布林来源商品不适用，多来源并存时 slug 规则碎片化 | 已记入商品模块待优化清单第 8 条，待商品系统定义通用规则后本模块改为引用 |
| **R5** | **属性作用域配置覆盖不足** | 二奢特有属性（包型、五金颜色、内衬颜色、设计元素等）若商品系统未配置作用域，③映射无处落值 | 开发前与商品模块核对属性作用域配置清单 |
| **R6** | **TRR 数据时效性** | TRR 是三方参考数据，更新不及时会导致定价偏离市场 | 建立 TRR 定期更新机制；②对超 TRR 比例的商品已有排除/标记逻辑兜底 |
