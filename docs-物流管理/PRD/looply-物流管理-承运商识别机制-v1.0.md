## 一、业务背景

### 1.1 问题描述
在物流追踪场景中，运营人员需要手动输入运单号并选择承运商。由于：
- 美国主流承运商众多（USPS、FedEx、UPS、DHL等）
- 运单号格式各异，人工识别易出错
- 手动选择效率低，影响订单处理速度

需要实现**自动识别承运商**功能，提升运营效率。

### 1.2 解决方案
通过集成第三方物流追踪平台（如 AfterShip、17Track），利用其运单号识别能力：
1. 自动识别运单号对应的承运商
2. 映射到 Looply 内部承运商管理体系
3. 提供手动修正和兜底机制

## 二、核心机制设计

### 2.1 数据流转路径

```
┌─────────────┐      ┌──────────────┐      ┌─────────────────┐      ┌──────────────┐
│ 运单号输入   │ ───> │ AfterShip API │ ───> │ 承运商映射表     │ ───> │ 显示本地化   │
│ (用户操作)  │      │ (识别承运商)  │      │ (平台→内部)     │      │ 承运商名称   │
└─────────────┘      └──────────────┘      └─────────────────┘      └──────────────┘
                            │
                            │ 识别失败
                            ↓
                     ┌──────────────┐
                     │ 手动选择列表  │
                     │ (承运商管理)  │
                     └──────────────┘
```

### 2.2 识别流程详解

#### 步骤1：运单号输入
- 用户在"添加物流信息"或"编辑物流信息"界面输入运单号
- 系统触发防抖（300ms），避免频繁调用API

#### 步骤2：调用第三方识别API
```javascript
// 伪代码示例
async function detectCarrier(trackingNumber) {
  const response = await aftership.detectCarrier({
    tracking_number: trackingNumber
  });
  
  // 返回格式：
  // {
  //   total: 2,
  //   couriers: [
  //     { slug: 'usps', name: 'USPS' },
  //     { slug: 'fedex', name: 'FedEx' }
  //   ]
  // }
  
  return response;
}
```

#### 步骤3：映射到内部承运商
- 查询 `carrier_platform_mapping` 表
- 根据 `platform_carrier_code` 匹配 `looply_carrier_id`
- 获取承运商的本地化名称和配置

#### 步骤4：结果处理
**情况A：唯一匹配**
- 自动填充承运商字段
- 显示"✓ (自动识别)"标识
- 允许用户手动修改

**情况B：多个匹配**
- 按优先级排序（priority字段）
- 默认选择第一个
- 提示"可能的承运商：USPS、FedEx"

**情况C：识别失败**
- 显示下拉选择框
- 提示"无法自动识别，请手动选择"
- 记录识别失败日志

## 三、数据库设计

### 3.1 新增映射表

#### carrier_platform_mapping（承运商平台映射表）

| 字段名 | 类型 | 说明 | 索引 |
|--------|------|------|------|
| id | bigint | 主键 | PK |
| platform_type | varchar(50) | 平台类型（aftership/17track） | INDEX |
| platform_carrier_code | varchar(100) | 平台承运商代码（如 usps） | INDEX |
| looply_carrier_id | bigint | 关联 carriers 表 | FK |
| priority | int | 优先级（多平台时的选择顺序） | - |
| is_active | tinyint | 是否启用 | - |
| created_at | timestamp | 创建时间 | - |
| updated_at | timestamp | 更新时间 | - |

**索引设计**：
- 唯一索引：`uk_platform_code` (platform_type, platform_carrier_code)
- 普通索引：`idx_carrier_id` (looply_carrier_id)

**初始数据示例**：
```sql
INSERT INTO carrier_platform_mapping VALUES
(1, 'aftership', 'usps', 1, 1, 1, NOW(), NOW()),
(2, 'aftership', 'fedex', 2, 1, 1, NOW(), NOW()),
(3, 'aftership', 'ups', 3, 1, 1, NOW(), NOW()),
(4, 'aftership', 'dhl-usa', 4, 1, 1, NOW(), NOW()),
(5, '17track', 'usps', 1, 2, 1, NOW(), NOW());
```

#### tracking_number_patterns（运单号识别规则表）

| 字段名 | 类型 | 说明 | 索引 |
|--------|------|------|------|
| id | bigint | 主键 | PK |
| carrier_id | bigint | 关联 carriers 表 | FK |
| pattern_regex | varchar(500) | 正则表达式 | - |
| pattern_description | varchar(200) | 规则描述 | - |
| confidence_score | decimal(3,2) | 置信度（0.00-1.00） | - |
| is_active | tinyint | 是否启用 | - |
| created_at | timestamp | 创建时间 | - |
| updated_at | timestamp | 更新时间 | - |

**用途**：
- 作为第三方API的补充识别规则
- 支持自定义承运商的识别
- 用于识别结果的二次验证

**示例数据**：
```sql
INSERT INTO tracking_number_patterns VALUES
(1, 1, '^(94|93|92|94|95)[0-9]{20}$', 'USPS 22位数字', 0.95, 1, NOW(), NOW()),
(2, 2, '^[0-9]{12}$', 'FedEx 12位数字', 0.90, 1, NOW(), NOW()),
(3, 3, '^1Z[A-Z0-9]{16}$', 'UPS 1Z开头18位', 0.98, 1, NOW(), NOW());
```

### 3.2 关联关系更新

#### shipments 表增加字段

| 新增字段 | 类型 | 说明 |
|---------|------|------|
| carrier_detection_source | varchar(50) | 识别来源（aftership/17track/manual/pattern） |
| carrier_detection_confidence | decimal(3,2) | 识别置信度 |
| carrier_detection_at | timestamp | 识别时间 |

## 四、接口设计

### 4.1 承运商识别接口

**接口路径**：`POST /api/admin/logistics/detect-carrier`

**请求参数**：
```json
{
  "tracking_number": "9400111899562537866192"
}
```

**响应格式**：
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "detected": true,
    "carriers": [
      {
        "carrier_id": 1,
        "carrier_name": "USPS",
        "carrier_code": "usps",
        "confidence": 0.95,
        "source": "aftership"
      }
    ],
    "selected_carrier_id": 1
  }
}
```

**识别失败响应**：
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "detected": false,
    "carriers": [],
    "available_carriers": [
      {"carrier_id": 1, "carrier_name": "USPS"},
      {"carrier_id": 2, "carrier_name": "FedEx"}
    ]
  }
}
```

### 4.2 承运商映射管理接口

**查询映射列表**：`GET /api/admin/logistics/carrier-mappings`

**响应格式**：
```json
{
  "code": 0,
  "data": {
    "items": [
      {
        "id": 1,
        "platform_type": "aftership",
        "platform_carrier_code": "usps",
        "carrier_id": 1,
        "carrier_name": "USPS",
        "priority": 1,
        "is_active": true
      }
    ]
  }
}
```

**新增/编辑映射**：`POST /api/admin/logistics/carrier-mappings`

```json
{
  "platform_type": "aftership",
  "platform_carrier_code": "usps",
  "carrier_id": 1,
  "priority": 1,
  "is_active": true
}
```

## 五、前端交互设计

### 5.1 承运商字段状态机

```
                    输入运单号
                        │
                        ▼
              ┌─────────────────┐
              │   识别中 (loading)│
              └────────┬────────┘
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
   ┌────────────┐ ┌──────────┐ ┌──────────┐
   │ 唯一匹配   │ │ 多个匹配  │ │ 识别失败  │
   │ 自动填充   │ │ 下拉选择  │ │ 手动选择  │
   └────────────┘ └──────────┘ └──────────┘
          │            │            │
          └────────────┼────────────┘
                       ▼
              ┌─────────────────┐
              │  用户确认/修改   │
              └─────────────────┘
```

### 5.2 各状态UI表现

**状态1：初始态**
- 承运商字段显示 placeholder："自动识别（或手动选择）"
- 运单号未输入时，承运商字段不可交互

**状态2：识别中**
- 显示 loading spinner
- 字段置灰不可编辑
- 超时时间：5秒，超时后降级为手动选择

**状态3：识别成功（唯一匹配）**
- 自动填充承运商名称
- 右侧显示绿色 ✓ 标识 + "(自动识别)"文案
- 提供"手动更改"链接按钮

**状态4：识别成功（多个匹配）**
- 转为下拉选择框
- 默认选中优先级最高的承运商
- 下方提示："检测到多个可能的承运商，请确认"

**状态5：识别失败**
- 转为下拉选择框，显示所有启用的承运商
- 下方提示："无法自动识别，请手动选择承运商"
- 承运商为必填项，未选择时阻止提交

### 5.3 交互细节

**防抖处理**：
- 运单号输入后 300ms 触发识别
- 输入过程中不发起请求

**错误处理**：
- API 超时（5s）：降级为手动选择
- API 异常：降级为手动选择，toast 提示"识别服务暂不可用"
- 网络错误：提示"网络异常，请稍后重试"

**用户修正**：
- 自动识别后用户手动修改，detection_source 记录为 "manual_override"
- 修正行为记入日志，用于后续优化识别规则

## 七、与承运商管理的关联关系

### 7.1 数据关联全景

```
┌─────────────────────────────────────────────────────────────────┐
│                     物流配置 > 承运商管理                          │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ carriers 表                                                │  │
│  │ - id, name, code, type, status                            │  │
│  │ - 维护 Looply 内部承运商基础信息                             │  │
│  └──────────────────────────┬────────────────────────────────┘  │
│                              │                                    │
│                              │ 1:N                                │
│                              ▼                                    │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ carrier_platform_mapping 表                                │  │
│  │ - 建立第三方平台代码 → Looply承运商的映射                    │  │
│  │ - 一个Looply承运商可对应多个平台代码                         │  │
│  └──────────────────────────┬────────────────────────────────┘  │
│                              │                                    │
└──────────────────────────────┼────────────────────────────────────┘
                               │
                               │ 被引用
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│                     物流追踪 > 运单追踪                           │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 录入运单号时：                                              │  │
│  │ 1. 调用 AfterShip API → 返回 slug (如 "usps")             │  │
│  │ 2. 查 carrier_platform_mapping → 找到 carrier_id = 1      │  │
│  │ 3. 查 carriers 表 → 获取名称 "USPS"                       │  │
│  │ 4. 前端显示 "USPS ✓ (自动识别)"                            │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

### 7.2 关键约束

1. **承运商管理是数据源头**：所有承运商必须先在"承运商管理"中创建，才能被映射
2. **映射关系是桥梁**：第三方平台的代码通过映射表关联到内部承运商
3. **删除保护**：承运商管理中删除承运商时，需检查是否存在映射关系和关联运单
4. **状态联动**：承运商停用时，对应的映射关系自动失效，不再参与自动识别

## 八、异常场景处理

| 场景 | 处理方式 |
|------|---------|
| AfterShip API 不可用 | 降级为本地正则规则识别，再失败则手动选择 |
| 识别出的承运商未在映射表中 | 提示"未配置该承运商映射"，引导管理员配置 |
| 承运商已停用 | 不显示在自动识别结果中，不显示在手动选择列表中 |
| 运单号格式异常 | 前端校验提示"运单号格式不正确" |
| 同一运单号重复录入 | 提示"该运单号已存在"，显示关联订单信息 |

## 九、后续优化方向

1. **识别准确率统计**：记录自动识别 vs 手动修正的比例，持续优化
2. **学习机制**：用户手动修正后，将运单号格式规则反馈到本地规则库
3. **多平台冗余**：支持配置多个追踪平台，主平台失败时自动切换备用平台
4. **批量识别**：支持批量导入运单号时的批量识别能力
