## 一、概述

### 1.1 背景与目标

收藏与浏览历史是 Looply 二手奢侈品平台的两项**买家高频核心能力**，从个人中心模块拆分独立成篇。拆分理由：二者是**有数据沉淀的平台级服务**（落库 + 跨页消费），区别于个人中心其余的聚合导航功能，独立成 PRD 便于明确数据边界与排期。

- **收藏 Wishlist**：用户主动声明"对这件孤品感兴趣"的持久化关系，是"先收藏、蹲降价、再下手"的核心转化路径。
- **浏览历史 Recently Viewed**：隐式记录用户看过的商品，帮助用户找回，降低重复检索成本。

**核心定位——能力与露出分离**：本模块负责"存 + 算 + 供"，不垄断展示。收藏/浏览的数据能力以中立服务形式开放，个人中心页、商详页等都是消费方。

### 1.2 核心设计锚点：一物一码

Looply 是一物一码（one-of-one）二手奢侈品平台，**每件商品库存唯一，卖掉即永久消失**。这决定了收藏与浏览历史的根本特性：

- 收藏/浏览锚定的对象是**渠道商品 listing**（用户前台可见、可下单的单件在售商品），不是 SPU/SKU。
- **失效是常态、高频**：被收藏/浏览的商品随时可能"已售出""已下架"，必须显著标识、避免误导下单，并提供"找相似"补救。
- 收藏时记录**价格快照** `price_at_save`、首次浏览时记录 `price_at_first_view`，作为各自降价判断的基准。

### 1.3 不做什么（边界）

| 不做项 | 说明 |
|---|---|
| 收藏分组 / 文件夹 | 二期；本期 ER 不预留 folder_id |
| 收藏排序（降价优先/价格） | 二期；本期仅默认时间倒序 |
| 批量管理（多选取消） | 二期；本期仅单条取消 |
| 社交化收藏（公开/分享） | 二期 |
| 关注品牌 / 卖家 | 二期 |
| 收藏变更事件输出 | 二期；本期只存数据不发事件 |
| 商详页"X 人收藏了此商品" | 二期；listing 维度反向聚合计数 |
| 浏览历史时间分组（Today/Earlier） | 不做；纯时间倒序（见 4.3） |
| 主动降价推送提醒 | 事件源在商品/促销模块，本模块不产生对外事件 |

### 1.4 用户角色

| 角色 | 说明 |
|---|---|
| 登录用户 | 以 `user_id` 为主体，收藏/浏览数据账户级持久化、跨设备同步 |
| 未登录访客 | 以设备级 `anonymous_id` 为主体记录，登录后复制关联到账户、跨设备同步（见第四章） |

### 1.5 核心场景

1. 用户浏览商品 → 点♡收藏 → 进 Wishlist 蹲降价 → 降价高亮 → 下单。
2. 用户看过多件商品 → 进 Recently Viewed 找回某件 → 跳商详。
3. 收藏/浏览的商品已售出 → 列表显示失效态 → 点"找相似"看同类在售。
4. 未登录访客收藏/浏览 → 注册登录 → 设备级记录复制关联到账户，跨设备可见。
5. 用户在商详页底部"最近浏览"横条 → 点击继续逛（消费方场景，见第五章）。

### 1.7 术语说明

| 术语 | 含义 |
|---|---|
| listing（渠道商品） | 用户前台可见、可下单的单件在售商品，收藏/浏览的锚定对象 |
| product（实物商品） | 一物一码的实物层，listing 的上游，本模块不直接锚定 |
| price_at_save | 收藏时记录的价格快照，降价判断基准 |
| price_at_first_view | 首次浏览时记录的价格快照，浏览历史降价判断基准（再次浏览不更新） |
| anonymous_id | 设备级匿名标识，未登录记录的主体 |
| 失效态 | 商品已售出 / 已下架，不可购买的状态 |
| 降价高亮 | 打开收藏列表时实时比对现价与快照价，现价更低则标识 |

### 1.8 多语言 / 多国家策略

本模块文案需支持 i18n（多市场方向）。价格按商品系统返回的币种展示。收藏/浏览数据本身不含地域属性，无多国合规差异；隐私相关（浏览记录、未登录记录）的合规告知见第四章隐私控制与第六章。

### 2.1 收藏 Wishlist

#### 2.1.1 模块概述

收藏让用户把感兴趣的孤品加入个人清单，支持登录与未登录。核心价值是"蹲降价"——收藏时记录价格快照，后续打开列表实时比对现价，降价则高亮。一物一码下，被收藏商品随时可能售出/下架，列表需处理失效态。

#### 2.1.2 收藏操作（机制型）

**功能描述**：在商品卡片或详情页点♡完成收藏/取消，是无独立页面的轻交互。

**触发条件**：用户点击商品卡片、商品详情页上的♡图标。

**处理流程**：
- **添加收藏**：♡空心 → 点击 → 写入 `user×listing`（或 `anonymous_id×listing`）收藏关系 + 记录当前价格快照 `price_at_save` → ♡变实心。采用乐观更新（先变 UI，再确认服务端）。
- **取消收藏**：♡实心 → 点击 → 软删除（`is_active=false` + 时间戳）→ ♡变空心。
- **未登录收藏**：以设备级 `anonymous_id` 为主体写入，不拦截、不强制登录。

**规则说明**：
| 规则 | 内容 |
|---|---|
| 收藏主体 | 登录用 `user_id`，未登录用 `anonymous_id`，二选一 |
| 价格快照 | 收藏成功即记录当时 listing 价格，后续不随商品改价变动 |
| 重复收藏 | (主体, listing_id) 唯一约束，同件不重复收藏 |
| 软删除 | 取消收藏不物理删除，置 `is_active=false`，保留追溯与合并幂等 |
| 收藏上限 | 不限上限 |

**异常处理**：
- 网络异常：乐观更新后服务端失败 → ♡回滚原状态 + 轻提示"操作失败，请重试"。
- 商品已失效仍点收藏：允许收藏（失效商品也可收藏，列表显示失效态）；但已售出/已下架的♡按钮在列表中置灰不可点。
- 并发：同一商品快速重复点击 → 以最终状态为准，幂等处理。

**UI 关联**：♡按钮属商品卡片/详情页组件（商品模块）。本模块负责收藏关系的写入与状态回显。

#### 2.1.3 收藏状态回显（机制型 / 对外能力）

**功能描述**：向商品卡片、详情页提供♡的收藏状态查询，使各页面正确显示实心/空心。

**触发条件**：商品卡片、详情页渲染时查询当前主体对某 listing（或一批 listing）的收藏状态。

**处理流程**：按主体 + listing_id（单个或批量）查询是否存在有效收藏（`is_active=true`），返回布尔状态供前端渲染♡。

**规则说明**：未登录态按 `anonymous_id` 查询；登录态按 `user_id`。状态回显是只读能力，供全站商品展示位复用。

#### 2.1.4 收藏列表页（页面型）

**功能描述**：展示当前用户的全部收藏，默认展示全部商品，支持"All / In Stock Only / Price Drop"三态筛选（各带数量角标），处理四种商品状态，提供失效项"找相似"。

**前置条件**：用户进入 Wishlist 页（APP：Tabbar♡ Favorites 聚合页收藏板块 "See All"（聚合页见移动端专属独立 PRD）/ 我的页入口 / 导航栏♡入口；PC：Navbar♡ 抽屉为主）。无收藏时显示空态（见 2.1.6）。
> PC 端 Navbar♡ 点击打开的是收藏抽屉（2.1.5），抽屉本身即带筛选的完整滚动列表；本收藏列表页是 APP 端的整页形态与 PC 端的全屏形态。

**页面布局（PC / APP 差异）**：
| 区域 | APP 端 | PC 端 |
|---|---|---|
| 顶部 | 返回 + 标题"Wishlist" | 全局 Navbar + 标题"Wishlist" |
| 筛选 | "All / In Stock Only / Price Drop" 切换 pill（默认 All，各带数量角标） | 同左，pill 横排 |
| 列表 | **瀑布流（masonry）多列卡片** | 4 列商品卡网格 |
| 翻页/加载 | **上滑无限滚动，每页最大 40 个商品** + 到底结束提示 | **"View More"按钮点击加载（每批 40 件，4×10）** + 到底结束提示 |
| 底部 | — | 全局 Footer |

**页面元素**：
| 元素 | 说明 |
|---|---|
| 标题 | "Wishlist" |
| 筛选 pill | "All"（默认/激活态紫底）、"In Stock Only"（仅在售）、"Price Drop"（仅已降价）；**每个 pill 后带数量角标**，展示该筛选态下的商品条数（如 All 487 · In Stock Only 56 · Price Drop 274），角标随数据实时刷新 |
| 商品卡片 | 复用 ProductCard：图 / 品牌 / 名称 / 价格；**不展示认证徽章**（前台收藏/浏览卡片精简，认证信息在商详页呈现）；失效态变体见 2.3 |
| 排序 | 默认按收藏时间倒序（本期不提供其他排序） |
| 翻页/加载 | PC "View More"点击加载（40/批，4×10）；APP 上滑无限滚动（40/页）。均到底显示结束提示。统一定义见 2.3.7 |

**页面状态变体**：
| 状态 | 说明 | 设计稿 |
|---|---|---|
| 默认（有收藏） | 卡片列表，按收藏时间倒序（失效项不下沉，原位显 Sold Out） | APP: 收藏-Favorites；PC: PC-收藏列表 |
| 真空态 | 无任何收藏 | APP: Wishlist-空态；PC: PC-收藏空态 |
| 筛选态-In Stock Only | 只显在售（隐藏失效项） | （同默认页，In Stock Only 激活） |
| 筛选态-Price Drop | 只显现价低于快照价的在售项 | （同默认页，Price Drop 激活） |
| 筛选空态 | 有收藏但当前筛选态角标为 0 | 保留筛选栏 + 列表区占位（见 2.1.6a） |
| 加载态 | 列表加载中骨架/loading | 待开发实现 |

**操作流程**：
- 主流程：进入页 → 加载收藏列表（实时附带商品状态与现价）→ 按收藏时间倒序排列（失效项不下沉，原位显 Sold Out）→ 点卡片进商详。
- 分支-筛选（三态，默认 All）：点"All" → 显示全部（含失效，按收藏时间倒序、失效不下沉）；点"In Stock Only" → 只显在售（隐藏失效项）；点"Price Drop" → 只显现价低于收藏快照价的在售项。三态互斥单选，pill 数量角标随之刷新。
- 分支-筛选无结果：切到 In Stock Only / Price Drop 后该态角标为 0 时，列表区显示筛选空态（见 2.1.6a），保留筛选栏，不落到真空态。

> **筛选口径说明**：三态**互斥单选**（非可叠加多选），任一时刻仅一态激活。**Price Drop 已内置"在售"过滤**——降价需比对有效现价，失效项（售出/下架）无有效现价，故 Price Drop 结果天然不含失效项。因此三态结果集为包含关系：**Price Drop ⊆ In Stock Only ⊆ All**（All 含失效项，In Stock Only 去失效，Price Drop 再在在售内取降价）。用户选 Price Drop 时无需再叠加 In Stock。由此角标恒满足单调性 **All ≥ In Stock Only ≥ Price Drop**，任何时刻违反即为数据/计数异常。

- 分支-取消收藏：在卡片上取消收藏 → 该项即时从列表移除（软删除）。
- 分支-失效项找相似：失效卡片点"Find Similar" → 跳同品牌/品类/价位的在售商品（依赖推荐/搜索）。
- 分支-分页/加载（**分端差异**，详见 2.3.7）：
  - **PC 端**：**"View More"点击加载**。列表底部居中"View More"按钮，点击追加下一批 **40 件（4 列 × 10 行）**，接续在当前列表尾部（不回到顶部、不整页刷新）；到底且无更多数据时按钮替换为**结束提示**"You've reached the end"。
  - **APP 端**：上滑无限滚动（infinite scroll），**每页最大 40 个商品**、上滑续接；滚动到底且无更多数据时显示**结束提示**"You've reached the end"（见 2.3.7）。

**校验规则**：
| 字段/动作 | 规则 | 时机 |
|---|---|---|
| 列表数据 | 每项渲染时实时取商品系统状态与现价 | 列表加载 |
| 计数 | active/sold 按 listing 实时状态分组 count | 列表加载 |

**交互说明**：
- 降价高亮：打开列表时实时比对 `price_at_save` 与现价，现价更低即在卡片标降价（原价划线 + 降幅）。任意幅度降价即标，非后台监控。
- 排序：按收藏时间倒序，失效项（已售出/已下架）不下沉，停在原位显 Sold Out（想只看在售用 In Stock Only 筛选）。分页/加载下若下沉，失效项会被推到后续批次导致首屏找不回，故不采用。

**异常处理**：
- 商品系统状态接口超时/不可用：降级展示（按上次已知状态或标"状态加载中"），不阻塞列表。
- 收藏的 listing 已被删除：显示为失效态 + 找相似。
- 空数据：显示空态。

**UI 关联**：
- APP 端：`收藏-Favorites`（含四态：在售 / 降价 / 已售出 / 已下架，后两者前台统一展示为 Sold Out）
- PC 端：`PC-收藏列表`（4 列网格，含降价态、失效态 Sold Out）

#### 2.1.5 PC 收藏抽屉（Wishlist Drawer，页面型 / PC 专属）

**功能描述**：PC 端点击全局 Navbar 右上角♡图标，从右侧滑出收藏抽屉（Drawer），在抽屉内提供**带三态筛选的完整收藏列表 + 抽屉内滚动自动加载 + 直接下单**，无需离开当前页即可完成浏览、筛选、蹲降价与购买。

> **v1.2 定位调整**：抽屉不再是"取最近若干条的轻预览"，而是**收藏能力在 PC 端的主要承载形态**——三态筛选、滚动加载全在抽屉内完成，**取消"View All"跳转到独立列表页**。设计稿中抽屉顶部已带 All / In Stock Only / Price Drop 三态筛选与滚动加载，本节据此定稿。

**为什么 PC 端用抽屉承载完整列表**：PC 端♡入口高频、用户常在浏览过程中顺手查看并管理收藏，右侧抽屉无需离开当前页、即开即用、随手可关，符合电商 mini-wishlist 通行模式（Fashionphile 等二奢平台）；把筛选与滚动加载收进抽屉，用户不必被抛到另一个整页，浏览-筛选-下单一气呵成。APP 端屏幕窄不适合抽屉，仍走整页瀑布流列表（2.1.4），此为分端差异。

**前置条件**：PC 端任意页面，点击 Navbar 右上角♡图标。无收藏时抽屉内显空态。

**功能描述**：用户无任何收藏时的引导页（真空态，区别于有收藏但筛选无结果的 2.1.6a）。

**页面元素**（对齐设计稿）：inbox（收纳盒）线框图标（黑色描边，无底色圆形）+ 主文案"Your wishlist is empty"（加粗）+ 副文案"Save pieces you love and we'll alert you when prices drop"（灰色，两行居中，呼应降价提醒价值，无句尾句号）+ 按钮"Explore Items →"（描边幽灵按钮 / ghost，含右箭头，非填充主按钮）。整块垂直居中于内容卡片。

**操作流程**：点"Explore Items" → 跳 **Shop All 页面**（全部商品集合 collection，带默认排序）。

> 跳转目标说明：二奢一物一码下没有标准商品流，Shop All（全部商品 collection）即用户淘货主场，最能接住空态用户"想逛但还没找到目标"的意图，优于跳首页（需二次导航、浪费意图）。本期统一跳 Shop All，无新依赖。**二期优化方向**：若推荐能力就绪，收藏空态可升级为跳"为你推荐 / Trending"策展页，转化更高。

**UI 关联**：APP 端 `Wishlist-空态`；PC 端 `PC-收藏空态`。

> **与筛选空态的区别**：本节是"一条收藏都没有"的真空态，占满整页、无筛选栏、CTA 跳 Shop All。当用户有收藏、只是当前筛选态无结果时，走 2.1.6a 筛选空态（保留筛选栏、CTA 切回 All），二者不可混用。

#### 2.1.6a 收藏筛选空态（状态变体）

**功能描述**：用户有收藏，但切到 "In Stock Only" 或 "Price Drop" 后该筛选态下无结果时的列表区空态（如全部收藏均已失效 → In Stock Only 为 0；或无任何降价 → Price Drop 为 0）。区别于 2.1.6 真空态。

**触发条件**：当前筛选态数量角标为 0（`In Stock Only 0` 或 `Price Drop 0`）。"All" 因含失效项，有收藏即不为 0，不触发本态（All 为 0 时即真空态 2.1.6）。

**页面元素**：
- **保留筛选栏**：三态 pill 与数量角标照常显示（当前态角标为 0），用户可随时切回其他态。
- **仅列表区为空**：显示轻量占位（inbox 线框图标，视觉弱于真空态）+ 主文案（随筛选态区分）：
  - In Stock Only 空：`No in-stock items` + 副文案 `All your saved items are currently unavailable`
  - Price Drop 空：`No price drops yet` + 副文案 `We'll notify you when a saved item drops in price`（呼应降价提醒价值）
- **CTA**：文字按钮 `View all saved items`（切回 All 态），**不跳 Shop All**——用户已有收藏，意图是看自己的清单而非重新逛。

**操作流程**：点 `View all saved items` → 筛选态切回 All、列表区恢复展示全部收藏（按收藏时间倒序，失效项原位）、角标刷新。

**适用范围**：收藏列表页（2.1.4）与 PC 收藏抽屉（2.1.5）共用同一套筛选空态；抽屉内占位块垂直居中于抽屉列表区，同样保留抽屉顶部筛选栏。

### 2.2 浏览历史 Recently Viewed

#### 2.2.1 模块概述

隐式记录用户进入过的商品详情页，帮助找回。纯时间倒序展示，支持登录与未登录，受容量与隐私约束。

#### 2.2.2 浏览记录写入（机制型）

**功能描述**：用户进入商品详情页即在服务端记录一次浏览，无独立页面。

**触发条件**：用户进入任一商品详情页。

**处理流程**：
- 进详情页 → 服务端记录一次浏览：主体（`user_id` 或 `anonymous_id`）× listing_id × `viewed_at`，**首次浏览同时记录价格快照 `price_at_first_view`**（作为"相对第一次浏览价"的降价判断基准）。
- **去重**：同一 listing 重复浏览不新增记录，只更新 `viewed_at` 为最近时间（列表中只保留最近一次，不堆叠重复项）；**`price_at_first_view` 保持首次不变，再次浏览不刷新快照**（区别于每次更新的 `viewed_at`）。
- **容量**：本期**不限制**条数与留存时长（容量淘汰策略留待二期按数据量与性能评估后引入）。

**规则说明**：
| 规则 | 内容 |
|---|---|
| 记录主体 | 登录 `user_id`，未登录 `anonymous_id` |
| 去重 | (主体, listing_id) 唯一，再次浏览更新时间戳 |
| 价格快照 | 首次浏览记录 `price_at_first_view`，后续再浏览不更新，作降价基准 |
| 容量 | **本期不限制**（二期再评估上限/留存期） |
| 隐式记录 | 无需用户操作，进详情页即记录 |

**异常处理**：写入失败不阻塞用户浏览（异步、容错）。

#### 2.2.3 浏览历史列表查询（机制型 / 对外能力）

**功能描述**：按主体查询浏览记录，返回时实时附带每件商品的最新状态与价格，供前端直接渲染失效态。

**处理流程**：按主体（`user_id` 或 `anonymous_id`）查询 → 时间倒序 → 分页 → 每项实时关联商品系统状态/价格。

**规则说明**：读写接口中立开放，供 C 端各页调用（列表页、商详页横条、首页卡条等），展示形态不约束（见第五章消费方）。

#### 2.2.4 浏览历史列表页（页面型）

**功能描述**：展示当前用户的浏览记录，纯时间倒序，默认展示全部，支持"All / In Stock Only / Price Drop"三态筛选（各带数量角标）与降价高亮（相对首次浏览价），支持单条删除与全量清除，失效项处理同收藏。

**前置条件**：进入 Recently Viewed 页（APP：Tabbar♡ Favorites 聚合页浏览历史板块 "See All"（聚合页见独立 PRD）/ 我的页 / 导航入口）。无记录显示空态（见 2.2.5）。

**页面布局（PC / APP 差异）**：
| 区域 | APP 端 | PC 端 |
|---|---|---|
| 顶部 | 返回 + 标题"Recently Viewed" + "Clear All" | 全局 Navbar + 标题 + "Clear All" |
| 筛选 | "All / In Stock Only / Price Drop" 切换 pill（默认 All，各带数量角标） | 同左，pill 横排 |
| 列表 | **瀑布流（masonry）多列卡片**（每卡带单条删除 X） | 4 列商品卡网格 |
| 翻页/加载 | **上滑无限滚动，每页最大 40 个商品** + 到底结束提示 | **"View More"按钮点击加载（每批 40 件，4×10）** + 到底结束提示 |
| 底部 | — | 全局 Footer |

**页面元素**：
| 元素 | 说明 |
|---|---|
| 标题 | "Recently Viewed" |
| 筛选 pill | "All"（默认/激活态紫底）、"In Stock Only"（仅在售）、"Price Drop"（仅相对首次浏览价已降价）；**每个 pill 带数量角标**，随数据实时刷新 |
| Clear All | 右上角，trash 图标 + 文字，触发全量清除 |
| 商品卡片 | 复用 ProductCard，失效态变体见 2.3 |
| 单条删除 | 每条记录的 X 按钮（APP 端卡片内） |
| 排序 | **纯时间倒序，不分组** |

**页面状态变体**：
| 状态 | 说明 | 设计稿 |
|---|---|---|
| 默认（有记录） | 纯倒序卡片列表（含降价高亮） | APP: 浏览历史-History；PC: PC-浏览历史 |
| 筛选态-In Stock Only | 只显在售（隐藏失效项） | （同默认页，In Stock Only 激活） |
| 筛选态-Price Drop | 只显现价低于首次浏览价的在售项 | （同默认页，Price Drop 激活） |
| 真空态 | 无记录 | APP: History-空态；PC: PC-历史空态 |
| 筛选空态 | 有记录但当前筛选态角标为 0 | 保留筛选栏 + 列表区占位（见 2.2.5a） |
| 加载态 | 加载中 | 待开发实现 |

**操作流程**：
- 主流程：进入页 → 纯时间倒序加载（实时附带状态/价格）→ 打开时实时比对 `price_at_first_view` 与现价，现价更低即在卡片标降价高亮 → 点卡片进商详。
- 分支-筛选（三态，默认 All）：点"All" → 显示全部；点"In Stock Only" → 只显在售；点"Price Drop" → 只显现价低于首次浏览价的在售项。三态互斥单选；筛选不改变纯时间倒序，pill 数量角标随之刷新。
- 分支-筛选无结果：切到 In Stock Only / Price Drop 后该态角标为 0 时，列表区显示筛选空态（见 2.2.5a），保留筛选栏，不落到真空态。

> **筛选口径说明**：三态**互斥单选**（非可叠加多选），任一时刻仅一态激活，筛选不改变纯时间倒序。**Price Drop 已内置"在售"过滤**——降价需比对有效现价（相对 `price_at_first_view`），失效项（售出/下架）无有效现价，故 Price Drop 结果天然不含失效项。因此三态结果集为包含关系：**Price Drop ⊆ In Stock Only ⊆ All**。用户选 Price Drop 时无需再叠加 In Stock。由此角标恒满足单调性 **All ≥ In Stock Only ≥ Price Drop**，任何时刻违反即为数据/计数异常。

- 分支-单条删除：点某条 X → **物理删除**该条 → 即时从列表移除。
- 分支-全量清除：点"Clear All" → 二次确认 → **物理删除**全部记录 → 显示空态。
- 分支-失效项找相似：失效卡点"Find Similar" → 跳相似在售品。

> **删除语义：浏览历史用物删，区别于收藏的软删**：浏览历史的单条删除与 Clear All 均为**物理删除**，与收藏"取消=软删（`is_active=false`）"不同。原因有二：①**可重新累积**——浏览历史的写入去重同样靠分域唯一约束（`UNIQUE(user_id/anonymous_id, listing_id)`），若清除用软删、约束又覆盖软删行，则"清除过的商品再次浏览也写不回来"，这对"最近看过"是反直觉的；物删后该 listing 无残留行，用户再看即正常重新记录。②**隐私更干净**——浏览历史是行为记录，Clear All 是 CCPA/CPRA 下的隐私清除主手段，物删对用户与 DSAR 交代都更彻底（软删只是标记、数据仍在）。收藏不受影响：收藏取消仍须软删以支撑防复活（见 2.1.2 / 4.3）。
- 分支-分页/加载（**分端差异**，详见 2.3.7）：PC 端"View More"点击加载，每批 40 件（4×10），接续在列表尾部；APP 端上滑无限滚动，每页最大 40 个商品；两端到底均显示结束提示"You've reached the end"。

**交互说明 —— 为什么纯时间倒序、不做日期分组**：
浏览历史采用纯时间倒序平铺，不做 Today / Earlier 等日期分组。依据：电商"最近看过"是**找回最近行为**的场景，用途是"快速找回刚看的"，纯倒序最直接；行业（Amazon Browsing History）即如此。日期分组适用于浏览器式海量历史的"按天回溯"场景，价值低且增加复杂度；本期采用分页加载承载列表长度，不靠容量上限约束。

**校验规则**：
| 动作 | 规则 | 时机 |
|---|---|---|
| 列表数据 | 每项实时取商品状态/价格 | 列表加载 |
| Clear All | 需二次确认（前端）防误删 | 点击时 |

**异常处理**：
- 商品状态接口异常：降级展示，不阻塞。
- 已删除/失效的 listing：显示失效态 + 找相似。
- 空数据：空态。

**UI 关联**：
- APP 端：`浏览历史-History`（纯倒序，含失效态 Sold Out + Find Similar、Clear All、单条 X）
- PC 端：`PC-浏览历史`（4 列网格，纯倒序，含失效态 Sold Out + Find Similar）

#### 2.2.5 浏览历史真空态（页面型 / 状态变体）

**功能描述**：无浏览记录时的引导页（真空态，区别于有记录但筛选无结果的 2.2.5a）。

**页面元素**（对齐设计稿）：inbox（收纳盒）线框图标（黑色描边，无底色圆形，与收藏空态同款图标）+ 主文案"No browsing history yet"（加粗）+ 副文案"Items you view will appear here so you can find them again"（灰色，两行居中，无句尾句号）+ 按钮"Explore Items →"（描边幽灵按钮 / ghost，含右箭头，与收藏空态样式一致）。整块垂直居中于内容卡片。

**操作流程**：点"Explore Items" → 跳 **Shop All 页面**（全部商品集合 collection，带默认排序），与收藏空态一致。浏览空态多为新用户，Shop All 提供商品发现主入口，让用户先逛起来。

**UI 关联**：APP 端 `History-空态`；PC 端 `PC-历史空态`。

> **与筛选空态的区别**：本节是"无任何浏览记录"的真空态，占满整页、无筛选栏、CTA 跳 Shop All。当用户有记录、只是当前筛选态无结果时，走 2.2.5a 筛选空态。

#### 2.2.5a 浏览历史筛选空态（状态变体）

**功能描述**：用户有浏览记录，但切到 "In Stock Only" 或 "Price Drop" 后该筛选态下无结果时的列表区空态（如浏览过的商品均已失效 → In Stock Only 为 0；或无一件相对首次浏览价降价 → Price Drop 为 0）。区别于 2.2.5 真空态。

**触发条件**：当前筛选态数量角标为 0（`In Stock Only 0` 或 `Price Drop 0`）。"All" 有记录即不为 0（含失效项），All 为 0 时即真空态 2.2.5。

**页面元素**：
- **保留筛选栏**：三态 pill 与数量角标照常显示（当前态角标为 0）。
- **仅列表区为空**：inbox 线框图标（视觉弱于真空态）+ 主文案（随筛选态区分）：
  - In Stock Only 空：`No in-stock items` + 副文案 `The items you viewed are no longer available`
  - Price Drop 空：`No price drops yet` + 副文案 `None of the items you viewed have dropped in price`
- **CTA**：文字按钮 `View all history`（切回 All 态），**不跳 Shop All**。

**操作流程**：点 `View all history` → 筛选态切回 All、列表区恢复全部记录（纯时间倒序）、角标刷新。

**说明**：浏览历史筛选空态不影响 Clear All / 单条删除入口（这些作用于全量记录，与当前筛选态无关）。

#### 2.2.6 隐私控制

**功能描述**：浏览历史涉及行为记录，需符合 CCPA/CPRA 等隐私要求。

**规则说明**：
| 控制项 | 本期 | 说明 |
|---|---|---|
| 清除浏览历史 | ✅ | 全量清除 + 单条删除，本模块直接负责，本期合规主手段 |
| 隐私告知 | ✅ | 隐私政策中说明记录行为、未登录记录复制关联到账户、用户域与匿名域分别删除 |
| 配合全局 DSAR | ✅ | 全局 DSAR 触发时删除本模块数据；DSAR 入口与导出归用户中心，非本模块 |

### 2.3 公共组件：商品卡片与失效态

#### 2.3.1 组件概述

收藏列表与浏览历史共用同一商品卡片组件（ProductCard），并共用一套失效态规则。提取为公共组件，两个列表页引用。

#### 2.3.2 商品卡片字段

| 字段 | 说明 |
|---|---|
| 商品图 | listing 主图 |
| 品牌 | 大写品牌名（如 CHANEL） |
| 名称 | 商品名称 |
| 价格 | 现价；降价时附原价划线 + 降幅 |
| Buy Now 按钮 | **仅在售卡展示**（紫色主按钮 + 闪电图标）；失效卡不展示，改为 Find Similar。详见 2.3.6 |

> 认证：前台收藏/浏览卡片**不展示认证徽章**，卡片保持精简。认证（Authenticated）信息在商品详情页呈现，不在列表卡片重复。

#### 2.3.3 失效态变体（枚举完整定义）

一物一码下失效是常态，卡片需完整定义状态。**前台买家侧不区分"已售出"与"已下架"**——买家只关心"能否购买"，两者统一展示为 **Sold Out**（行业通行做法，售出/下架的区分仅用于后台运营）：

| 状态枚举 | 含义 | 进入条件 | 卡片表现 |
|---|---|---|---|
| 在售（active） | 商品可购买 | listing_status=在售 且 有库存 | 正常图 + 价格；♡可点 |
| 已降价（active+discount） | 在售且现价低于快照价 | 在售 且 现价 < 快照价（收藏用 price_at_save，浏览历史用 price_at_first_view） | 正常展示 + 原价划线 + 降幅（绿色↓）|
| 失效（sold / off_shelf） | 商品已售出或已下架，不可购买 | listing_status=已售出 或 已下架/不可用 | **保留商品图 + 半透明灰蒙层 + 蒙层居中白字"Sold Out"** + 品牌/名称置灰 + "Find Similar" + ♡置灰不可点 |

> 说明①：后台 listing_status 仍区分 sold 与 off_shelf，但前台两者**渲染完全一致**（均为 Sold Out 蒙层），buyer 无需感知区别。
> 说明②：降价高亮是"在售"的子表现，不是独立状态；判定为实时比对（收藏比对 price_at_save，浏览历史比对 price_at_first_view，见 2.1.4 交互说明），任意幅度降价即标。
> 说明③：失效态**保留原商品图**，仅叠加半透明灰蒙层 + 文案，不用纯灰色块（保留商品识别度）。

#### 2.3.4 失效项排序与找相似

- **失效项排序（不下沉）**：收藏列表与浏览历史均按时间倒序（收藏时间 / 浏览时间），失效项（Sold Out）停在原位、不排到在售之后。原因：列表靠分页/滚动加载，若把失效项下沉会被推到后续批次，商品多时用户在首屏找不回自己收藏/看过但已售罄的项；想只看在售，用 In Stock Only 筛选即可。
- **找相似**：失效卡片提供"Find Similar"入口，跳同品牌/品类/价位的在售商品，依赖推荐/搜索能力。

#### 2.3.5 UI 关联

收藏列表四态见 APP `收藏-Favorites` / PC `PC-收藏列表`；浏览历史失效态见 APP `浏览历史-History` / PC `PC-浏览历史`。

#### 2.3.6 立即购买（Buy Now）

**功能描述**：在售商品卡片提供"Buy Now"立即购买按钮，让高购买意向的收藏/浏览用户无需跳转商详、无需经过购物车，**点击直接进入结算流程**，缩短转化路径。

**为什么用 Buy Now 而非加入购物车**：
- **孤品防抢**：一物一码下每件库存唯一、随时被他人买走。Buy Now 直接进结算锁定该件，比"加购后仍在购物袋里等待、可能被人买走"更稳，且绕开了"加购是否锁库存"的中间态难题。
- **二奢单件决策**：客单价高、多为单件购买，购物车"凑单一起结"的场景弱；收藏页用户已蹲守已久，看到合适即下手，Buy Now 一步到位最贴合心智。
- **意图明确**：收藏/浏览的在售卡面向"现在就想要"的高意向人群，即时购买路径转化更直接（TheRealReal、Fashionphile 等一物一码二奢平台通行做法）。

**展示规则**：
| 卡片状态 | 按钮 |
|---|---|
| 在售 / 已降价 | 展示"Buy Now"（紫色主按钮 + 闪电图标） |
| 失效（Sold Out） | **不展示**，位置改为"Find Similar"（已售/下架不可购买） |

**适用范围**：收藏列表页 + 浏览历史页的在售卡均展示（两页一致）。

**交互**：点击"Buy Now" → **跳转结算页（Checkout）**，不经过购物车 → 进入该 listing 的下单结算流程。

**一物一码关键依赖（库存锁定，对接交易模块）**：
- Buy Now 进入结算时需锁定该 listing，防止结算过程中被他人买走。锁定机制（锁定时长、超时释放、并发抢购处理）归属**交易/结算模块**定义，本模块负责"触发 Buy Now 跳转结算"，锁定逻辑由结算流程对接。
- 相比加入购物车，Buy Now 的锁定边界更清晰（点击即进结算即锁定），无"长期挂在购物袋里"的库存歧义。

**异常处理**：
- 点击 Buy Now 时商品已失效：拦截跳转 → 提示"商品已售出"+ 卡片刷新为失效态。
- 进入结算后库存锁定失败（已被抢）：由结算流程提示"商品已售出"并中止，引导"找相似"。
- 接口异常：提示"操作失败，请重试"，按钮状态回滚。

**UI 关联**：在售卡见 APP `收藏-Favorites` / `浏览历史-History`、PC `PC-收藏列表` / `PC-浏览历史` 的在售卡变体（紫色 Buy Now 按钮）。

#### 2.3.7 分页与加载策略（分端差异）

**功能描述**：收藏列表、浏览历史、PC 收藏抽屉共用同一套分批加载能力，按场景采用不同交互。三处均不限数据量，靠分批加载保性能。**v1.2 起统一为"点击/滚动加载"模型，PC 列表页取消经典页码翻页。**

**为什么统一改点击/滚动加载**：v1.1 曾在 PC 端用经典页码翻页。设计稿定稿后，PC 列表页采用 **"View More"点击加载**、PC 抽屉与 APP 均采用**滚动自动加载**。三者的共性是"个人清单式的连续浏览"，用户心智是"往下看更多"而非"跳到第 N 页"；点击/滚动加载让浏览位置连续、不打断，且都保留了明确的"到底"信号（"You've reached the end"），规避了纯无限滚动"够不到 Footer / 不知是否到底"的经典问题。PC 列表页用**点击式 View More**（而非纯滚动）正是为保住 Footer 可达性——用户主动点才继续加载，不会被无限滚动一直往下拽。

| 维度 | PC 列表页（2.1.4） | PC 收藏抽屉（2.1.5） | APP 列表页（2.1.4 / 2.2.4） |
|---|---|---|---|
| 交互 | **"View More"按钮点击加载** | **抽屉内滚动自动加载**（infinite scroll） | **瀑布流上滑无限滚动**（infinite scroll） |
| 布局 | 4 列网格 | 2 列网格 | 瀑布流 masonry 多列 |
| 每批数量 | **40 件（4 列 × 10 行）** | 每批按需（如 40 件），滚动续接 | **每页最大 40 个商品**，上滑续接 |
| 控件 | 底部居中"View More"按钮 | 无按钮；触底自动加载，加载时显 loading | 无按钮；触底自动加载，加载时显 loading |
| 续接后 | 追加在列表尾部（不回顶、不整页刷新） | 追加在抽屉列表尾部 | 追加在当前列表尾部 |
| 到底表现 | "View More"替换为**结束提示**"You've reached the end" | 底部**显示结束提示**"You've reached the end" | 底部**显示结束提示**"You've reached the end" |

**每批数量取值依据**：
- PC：数量取**网格列数的整数倍**（4 列 → 40 = 4×10），与 APP 每批 40 对齐，保证每批填充后最后一行不残缺。
- APP：瀑布流**每页最大 40 个商品**，一次续接量更大以减少上滑打断频次；瀑布流不要求整行对齐，故不取列数整数倍。
- 收藏/浏览是**个人清单**，规模远小于全站品类页，上述批量足以填满首屏又不过长；区别于二奢品类页常用的 48~60/页。

**结束提示（三处一致，到底无更多数据）**：
- 加载到最后一批、无更多数据时，底部显示一行居中弱化文案"You've reached the end"（i18n），明确告知"已看完全部"，避免误判为加载失败或网络问题。
- 结束提示是静态文案行，不可点击；PC 列表页由"View More"按钮**原位替换**为该提示。
- 筛选切换（All / In Stock Only / Price Drop）或数据变化导致列表重载时，加载状态与结束提示随之重置刷新。
- 空态不显示结束提示（真空态见 2.1.6 / 2.2.5，筛选空态见 2.1.6a / 2.2.5a，均有独立占位，不叠加"You've reached the end"）。

**与筛选/排序的关系**：
- 三态筛选切换时，加载基于筛选后的结果集重置（PC 列表回到首批 + 重置 View More，抽屉与 APP 重置滚动），pill 数量角标同步刷新。
- 排序按时间倒序（收藏时间 / 浏览时间）在分批前完成，失效项不下沉、原位参与倒序，加载顺序即倒序顺序。

**异常处理**：
- 加载某批失败：PC 列表页保留已加载内容、"View More"改为"加载失败，点击重试"；抽屉/APP 底部显示重试入口，均不顶掉已加载内容。
- 重复触发保护：滚动加载在上一批返回前不重复请求下一批（防抖 / 加载中锁）。

**UI 关联**：PC "View More"按钮见 `PC-收藏列表` / `PC-浏览历史` 底部；PC 抽屉滚动加载见 `PC-收藏抽屉`；APP 瀑布流结束提示见 `收藏-Favorites` / `浏览历史-History` 列表底部。

## 四、跨模块横切：未登录记录与登录关联

### 4.1 模块概述

收藏与浏览历史均支持未登录设备级记录，登录后**关联展示**到账户、并支持跨设备同步。核心模型是**双行分离 + 复制上移**：匿名记录与用户记录是物理分离的两行，登录时把匿名记录**复制**一份到用户名下（不删匿名原件），使得：

- **登录态**：按 `user_id` 读写用户记录，跨设备可见。
- **登出态**：按 `anonymous_id` 读写匿名记录，登出后匿名数据原样保留、仍可见。
- 两个域物理隔离，互不污染（登录态取消不影响匿名记录，反之亦然）。

> 设计取舍说明：本模型同时满足「①跨设备可见」与「②登出后匿名数据仍可见」。代价是「③共享设备隔离」存在残留——同一台设备上，下一个登出态用户按设备 `anonymous_id` 读取时，会看到上一个用户留下的匿名记录。鉴于二奢 App 以个人独占设备为主、且匿名数据本属设备本地资产，本期接受该残留。若未来上线公共/共享设备场景，可加「登出轮换 anonymous_id」开关治理（见 4.4）。

### 4.2 双行分离模型（机制型）

**规则说明**：
- favorite / browsing_history 每行主体二选一：`user_id` 与 `anonymous_id` 必须且只能一个非空（保留 XOR CHECK 约束）。
  - 匿名行：`anonymous_id` 非空、`user_id` 为空。
  - 用户行：`user_id` 非空、`anonymous_id` 为空。
- 同一个商品可同时存在一条匿名行和一条用户行（复制上移产生），二者物理独立。
- **分域唯一约束**（替代原单一 `(主体, listing_id)`）：
  - `UNIQUE(user_id, listing_id) WHERE user_id IS NOT NULL`（用户域防重）
  - `UNIQUE(anonymous_id, listing_id) WHERE anonymous_id IS NOT NULL`（匿名域防重）
  - 唯一约束**覆盖软删行**（含 `is_active=false`），是防"取消后复活"的关键（见 4.3）。
- `anonymous_id` 生成/存储方案（cookie/localStorage/指纹）与有效期待确认（见依赖与风险），影响未登录记录留存与关联成功率。

### 4.3 登录后复制上移（机制型）

**触发条件**：用户**首次获得登录态**那一刻——**登录 / 注册成功 / 第三方授权登录**，任一拿到 `user_id` 即触发。
> 注册尤其不可遗漏：注册流程须在建账户、拿到 `user_id` 的同时，带上当前设备 `anonymous_id` 执行复制，否则"先收藏再注册"的用户匿名数据关联不过来。

**处理流程**：
1. 取当前设备 `anonymous_id` 名下的匿名记录（`is_active=true`）。
2. **复制**到登录 `user_id` 名下（不删匿名原件）：
   ```sql
   INSERT INTO favorite (user_id, listing_id, price_at_save, created_at)
   SELECT '<user_id>', listing_id, price_at_save, created_at
   FROM favorite WHERE anonymous_id = '<本设备anon>' AND is_active = true
   ON CONFLICT (user_id, listing_id) DO NOTHING;   -- 防复活关键
   ```
3. **防复活**：`ON CONFLICT (user_id, listing_id) DO NOTHING` + 唯一约束覆盖软删行 ⇒ 用户域已存在该 listing（哪怕已 `is_active=false` 被取消过）则不再复制。否则会出现"登录态取消 → 再登录又复制 → 商品复活"的 bug。
4. 撞同一 listing 的快照/时间取舍（仅当用户域**尚无**该 listing、首次复制时适用）：
   - 收藏：保留**较早**的 `price_at_save`（锚定价更低基准更易触发降价提醒；不取最低价，避免压低基准反而难触发）。
   - 浏览：取**较晚**的 `viewed_at`（最近一次）；`price_at_first_view` 取**较早**的（真正的首次浏览价，基准更低更易触发降价提醒，与收藏 `price_at_save` 取较早对称）。
5. 匿名原件**保留不动**（登出态仍可读）。
6. **写合并日志**：每次触发复制上移，写一条 `anonymous_merge_log` 记录——`anonymous_id`、`user_id`、触发时机（登录 / 注册 / 第三方授权）、合并的收藏条数 `favorite_merged_count`、浏览记录条数 `history_merged_count`、`merged_at` 时间戳（详见 4.4）。

### 4.4 合并日志（anonymous_merge_log，机制型）

**功能描述**：登录后复制上移是"匿名数据认领进账户"的关键动作，涉及数据归属变化，需**可追溯**。为此每次合并落一条日志，记录"何时、把哪个匿名设备的哪些数据、合并到了哪个账户"。

**为什么要记合并日志**：
- **审计与追溯**：数据从匿名域进入用户域是归属变更，隐私合规（CCPA/CPRA、DSAR 争议）需能回答"这个账户下的收藏是何时从哪个设备认领来的"。
- **幂等排查**：复制用 `ON CONFLICT DO NOTHING` 幂等，但线上若出现"数据没关联过来 / 疑似重复复活"的问题，日志是定位依据（能看到某次合并实际搬了几条、是否重复触发）。
- **数据分析**：量化"先匿名收藏再注册"的转化路径价值（多少新用户带着匿名收藏进来、平均带入几条），支撑登录引导策略。

**记录内容**：
| 字段 | 说明 |
|---|---|
| merge_id | 合并日志 ID（PK） |
| anonymous_id | 被合并的设备匿名 ID（来源） |
| user_id | 合并目标账户 ID |
| trigger_type | 触发时机：login / register / oauth |
| favorite_merged_count | 本次实际复制的收藏条数（`ON CONFLICT` 跳过的不计入） |
| history_merged_count | 本次实际复制的浏览记录条数 |
| merged_at | 合并发生时间戳 |

> **为什么日志不记被搬商品的 ID 列表**：日志是**事件流水**，回答"何时发生一次合并、搬了多少量"；"具体哪些商品"已落在 `favorite` / `browsing_history` 的真实行里，查账户名下记录即可，无需在日志里再存一份。存 ID 数组会带来**数据冗余**（同一归属信息两处存易不一致）、**单行膨胀**（一次带入几百条则日志行变大数组，撑大 append-only 表）、**职责错位**（日志该轻该只增，商品清单该在业务表查）。审计 / 幂等 / 转化三个用途，条数已够。

**商品级溯源（行级，非日志）**：若需精确到"某一件收藏 / 浏览记录是从哪台匿名设备、哪次合并搬来的"，溯源信息**跟随业务行**、不塞进日志。为此在 `favorite` / `browsing_history` 各加两列：

| 字段 | 说明 |
|---|---|
| merged_from_anonymous_id | 该行由哪台匿名设备复制上移而来（来源匿名 ID）；原生登录态直接创建的行为 **NULL**（可空） |
| merged_at | 该行的复制上移时间；原生创建的行为 **NULL**（可空） |

- 两列在**复制上移写入用户行时**一并写入（`merged_from_anonymous_id` = 当次来源 anon，`merged_at` = 复制时刻）。
- 原生登录态下直接产生的收藏 / 浏览记录，两列均为 NULL —— 靠"是否为 NULL"即可区分"认领来的"与"账户内原生的"。
- 溯源信息随行走，天然一物一码、不与日志重复。**与日志分工**：日志答"这个账户被合并过几次、每次几条"；行级溯源答"这一件具体从哪来"。
- DSAR 删除 `user_id` 时，这两列随用户行一并删除（不单独留存）。

**规则说明**：
- 日志在**每次触发复制上移时**写入（登录 / 注册 / 授权任一），与复制在**同一请求 / 同一事务**内完成，保证日志与实际搬运一致。
- `_merged_count` 记录**实际新增**的条数（被唯一约束 / `ON CONFLICT` 跳过的重复项不计），可用于判断"本次是否真的搬了数据"（0 表示该 anon 无新数据或已全部认领过）。
- 日志**只增不改**（append-only），不参与业务读写路径，仅供审计 / 排查 / 分析。
- 同一 `(anonymous_id, user_id)` 可能多次合并（用户在同设备多次登入登出后再登录），每次各记一条，靠 `merged_at` 区分。

**异常处理**：合并主流程（复制）成功但日志写入失败时，不阻断用户登录；日志写入按"尽力而为 + 告警"处理（合并本身幂等，可事后补记或从复制结果反推）。

**读写口径**：
| 状态 | 读取 | 写入 | 取消/删除 |
|---|---|---|---|
| 登录态 | `WHERE user_id=?`（跨设备一致） | 只写用户行（`anonymous_id=NULL`） | 按 `user_id + listing_id` 删除该行 |
| 登出态 | `WHERE anonymous_id=?`（本设备） | 只写匿名行（`user_id=NULL`） | 按 `anonymous_id + listing_id` 删除该行 |

> 上表"取消/删除"的**删除方式因模块而异**：**收藏 = 软删**（`is_active=false`，唯一约束覆盖软删行以防复活，见 4.3）；**浏览历史 = 物删**（单条删除 / Clear All 物理删除，以支持清除后可重新累积、且隐私清除更彻底，见 2.2.4）。读写主体口径（登录按 `user_id`、登出按 `anonymous_id`）两模块一致。

**规则说明 —— 不建持久映射表**：
- 复制是登录瞬间对当前匿名记录的一次性快照搬运，**不建 `anonymous_id↔user_id` 持久映射**，不在读取时 JOIN 映射。登录后读取纯按 `user_id`，与 anon 解耦。
- **跨设备铁律**：匿名数据要跨设备可见，前提是**在数据所在设备登录过一次**（才会被复制进用户域）。在某设备纯匿名、从未登录产生的数据，换设备登录看不到——任何方案均如此，产品上靠引导登录解决（见 4.4）。

**异常处理**：
- 复制须幂等：`ON CONFLICT DO NOTHING` 天然幂等，重跑不产生重复或复活。
- 取拿 `anonymous_id` 与复制须在同一请求内完成，防 anon 丢失导致认领失败。

### 4.5 边界与说明

- **DSAR 删除**：删除 `user_id` 时删用户域记录；匿名域记录因物理分离**不被连带删除**（除非按设备 `anonymous_id` 单独清理）。边界清晰，需在隐私合规说明中写明用户域与匿名域分别删除。合并日志 `anonymous_merge_log` 含 `user_id` 与 `anonymous_id` 关联关系，DSAR 删除 `user_id` 时该用户相关日志一并处理（删除或匿名化，按全局 DSAR 策略）。
- **共享设备残留**：见 4.1 取舍说明。本期不轮换 `anonymous_id`，接受同设备登出态残留。预留"登出轮换 anonymous_id"作为未来公共设备场景的可选治理手段。
- **跨设备纯匿名数据**：不可跨设备找回（无设备指纹方案），通过登录引导管理用户预期。
