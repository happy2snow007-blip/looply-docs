## 一、概述

### 1.1 背景与目标

looply 是面向美国市场的二手奢侈品 B2C 电商平台，**商品实物存放在国内合作方红布林的仓库中**。looply 自身不持有库存，用户下单后需要在红布林侧建立对应订单、锁定商品，由红布林发货至上海集货仓，再经报关出口、国际物流送达境外用户。

本模块解决的问题：**把 looply 的交易链路与红布林的履约链路对接起来**，包括正向的建单/驱动支付/发货与签收回执，以及逆向的退款与联动取消。

目标：

1. 用户下单即在红布林侧锁定商品，避免一物一码商品被其他渠道售出
2. looply 侧订单状态与红布林履约进度保持可追溯的对应关系
3. 逆向场景（退款/取消）由**一次运营操作**完成 looply 与红布林两侧的处理，不需要人工分别操作两个系统

### 1.2 不做什么（明确边界）

| 不做 | 说明 |
|---|---|
| 上海仓收货验货、报关的系统化 | 由拾二线下全权处理，looply 系统只做状态记录与运营录入 |
| 买家主动申请退款入口 | 本期无 C 端申请入口，退款均由运营在后台发起 |
| 红布林侧库存的管理 | 库存由红布林系统管理，looply 只做锁定/释放的联动 |
| 异常处理系统化 | 缺货已在下单阶段拦截；验货不通过等异常走线下人工 |
| 用户签收段 | 国际物流末端配送与用户签收由 looply 订单模块负责，与红布林无关 |
| 国际物流商选型 | 不在本模块范围 |
| 红布林接口的技术定义 | 接口字段、幂等、鉴权属技术方案，不在 PRD 内 |

### 1.3 用户角色

| 角色 | 在本模块中的职责 |
|---|---|
| **looply 运营** | 录入国际物流单号、登记线下履约节点、发起退款与联动取消、处理线下退回登记 |
| **拾二（线下）** | 上海仓收货验货、报关出关、交付国际物流。不使用 looply 系统 |
| **红布林（外部系统）** | 库存管理、订单处理、国内拣货发货、国内签收确认与回调、退回处理 |
| **终端买家** | 在 looply 下单与支付。本模块内买家无直接操作入口 |

### 1.4 核心场景

| # | 场景 | 简述 |
|---|---|---|
| S1 | 正向履约 | 用户下单 → 红布林建单锁库存 → 支付 → 驱动红布林发货 → 国内物流 → 签收上海仓 → 验货报关 → 录入国际物流单号 → 订单转已发货 |
| S2 | 下单缺货 | 红布林库存不可用 → 建单失败 → 不生成待付款订单 |
| S3 | 支付未成功 | 支付超时 或 支付单最终失败 → looply 订单先转取消 → 由订单取消驱动系统自动取消红布林订单 + 释放库存 + 关单（不允许支付失败直接调红布林取消） |
| S4 | 支付后取消 | 红布林未发货 → 退某件即取消对应那张红布林订单、整单退取消全部 N 张 + looply 退款 |
| S5 | 发货后退回 | 红布林已发货 → 不联动接口，仅 looply 退款 + 线下协调退回并登记 |
| S6 | 出关后退货 | 订单已发国际物流 → 转 looply 售后退货流程，与红布林无关 |

### 1.5 全局页面流转

本模块**无独立菜单入口**，功能挂载在订单模块既有页面上：

```
订单管理 → 订单列表
    │
    ├─ 行操作「发起退款」 ─────→ 发起退款弹窗（含红布林联动）
    │
    └─ 行操作「详情」 ─→ 订单详情页
                            ├─ 板块「国内红布林履约信息」（只读展示）
                            └─ 顶部操作「发起退款」 ─→ 发起退款弹窗（含红布林联动）
```

> 列表页与详情页的「发起退款」为**同一套逻辑与同一个弹窗内容**，仅入口位置不同。

### 1.6 术语说明

| 术语 | 含义 |
|---|---|
| **红布林订单** | looply 在红布林系统中创建的订单。曾用名「采购单」，已统一为「红布林订单」 |
| **履约阶段** | 由红布林订单状态推导出的 4 个逆向处理阶段，决定取消/退款时与红布林的联动方式 |
| **联动** | looply 的一次运营操作，同时触发 looply 侧处理与红布林侧接口调用 |
| **上海集货仓** | 跨境中转节点，红布林发货的收货地址，由拾二线下运营 |
| **拾二** | 负责上海仓收货验货、报关、交付国际物流的线下合作方 |
| **一物一码** | 二手商品的库存模型，每件商品唯一、库存量恒为 1、不可替换 |

## 二、需求详细描述

### 2.1 全局约定

#### 2.1.1 红布林订单与 looply 订单的对应关系

- looply 父订单与红布林订单 **1 : N**
- **一单一件**：一个 looply 父订单包含 N 件商品时，在红布林侧**逐件创建 N 张**红布林订单，**每张仅 1 件**
- N 张红布林订单**均挂在父订单层**（不挂子订单）；库存锁定同样挂父订单层
- 逆向按件操作时，**取消对应的那张红布林订单**即可，无需依赖部分退能力（见 §2.7.3）

> ⚠️ **前置依赖**：一单一件下一个 looply 父订单会在红布林侧产生 N 张红布林订单。本方案成立的前提是**红布林能把这 N 张订单合并成一个国内包裹发出**（否则跨境物流成本上升、发货/签收回调变 N 次）。**该合并发货能力尚未与红布林技术确认**，详见 §3。

#### 2.1.2 looply 订单状态口径

本模块**不新增** looply 订单状态，沿用订单支付模块定义。本模块相关的关键口径：

| 状态 | 本模块相关口径 |
|---|---|
| `pending_payment` 待付款 | 已在红布林侧建单并锁定商品 |
| `paid` 已支付 | 从支付成功一直持续到**报关出关前**，期间包含红布林发货、国内签收、上海验货等节点，**状态均不变** |
| `shipped` 已发货 | 仅在**报关出关后运营录入国际物流单号**时触发 |
| `closed` 已关闭 | 待付款阶段未支付而取消/超时 |
| `processing` 处理中 | looply **有**该状态，沿用订单支付模块定义（卡风控异步支付场景）。本模块不新增其含义，对红布林侧的建单/驱动/取消动作无特殊分支 |
| `cancelled` / `refunded` | 支付后取消 / 退款完成，沿用订单支付模块口径 |

**关键约定**：红布林侧的任何履约进展（发货、国内签收）**都不改变 looply 订单状态**，仅作为履约节点记录。

> `processing` 状态口径以订单支付模块最新需求为准，本模块直接沿用，不单独定义。

#### 2.1.3 红布林订单状态枚举

| 枚举值 | 含义 | 触发时机 | 对应 looply 动作 |
|---|---|---|---|
| 待支付 | 已建单锁库存，未驱动支付 | looply 下单建单成功 | 记录红布林订单号 |
| 已支付 | 已驱动支付，红布林安排发货 | looply 支付成功后驱动 | 无（等待发货回调） |
| 已发货 | 红布林完成拣货打包并发出 | 红布林侧操作 | 记录国内物流信息，**不改订单状态** |
| 已取消 | 该张红布林订单被取消 | looply 取消/超时驱动，或退款时取消对应那张 | 释放该件库存 + 关单/退款 |

> 国内签收为红布林侧的**回调事件**，不改变红布林订单状态枚举。

#### 2.1.4 履约阶段枚举（系统自动判定）

履约阶段由系统根据红布林订单状态与 looply 订单状态自动推导，**运营不可人工选择或修改**。

| 阶段 | 判定条件 | 红布林联动方式 | looply 处理 |
|---|---|---|---|
| ① 支付前（待付款） | looply 订单未支付 | 系统自动 · 调红布林取消订单 | 释放库存 + 关单（未支付，无退款） |
| ② 支付后 · 红布林发货前 | 已支付，红布林订单未发货 | 系统自动 · 取消对应的那张/那几张红布林订单 | 退对应商品金额 + 释放对应商品库存 |
| ③ 红布林发货后 · looply 发国际物流前 | 红布林已发货 ~ 报关出关/发国际物流前 | **不联动接口**，需线下协调退回 | 仅 looply 侧退款 + 线下协调退回 |
| ④ looply 发国际物流后 | looply 订单已 `shipped` | 与红布林无关 | 转 looply 售后退货流程 |

#### 2.1.5 联动方式枚举

| 枚举值 | 含义 | 适用阶段 |
|---|---|---|
| 系统自动 · 接口 | 系统调用红布林接口完成联动，运营无需操作红布林 | ①② |
| 不联动接口 · 线下协调 | 系统不调接口，红布林侧退回由运营线下协调后在后台登记 | ③ |
| 与红布林无关 | 该阶段的逆向处理不涉及红布林 | ④ |

#### 2.1.6 幂等与补偿约定（全局）

本模块所有与红布林的交互均为跨系统调用，统一遵循：

| 场景 | 约定 |
|---|---|
| looply → 红布林（逐张建单 / 逐张驱动支付 / 逐张取消） | 必须**幂等**，重复调用不产生重复业务结果 |
| 红布林 → looply（发货回调 / 签收回调） | 必须**幂等**，重复回调不重复记录节点 |
| 回调丢失 | 支持**主动查询**红布林订单状态补齐节点，不依赖回调可靠性 |
| 调用失败 | 支持重试；重试仍失败的**挂起人工处理**，不静默失败 |

各功能章节不再重复描述，统一引用本节。

#### 2.1.7 红布林侧信息变更的处理

红布林侧订单信息（商品、金额、收货信息）在建单后发生变更时：

| 变更类型 | looply 处理 |
|---|---|
| 红布林侧**取消订单**（非 looply 发起） | 视为异常，挂起人工处理；需运营核实后决定 looply 侧订单如何处理 |
| 红布林侧**商品/金额变更** | 本期**不支持**。红布林订单一经创建，明细不可变更 |
| 红布林侧**物流信息更新** | 通过发货回调写入，以最后一次回调为准 |

> ⚠ 遗留：红布林侧主动取消订单的场景（如红布林发现商品有问题）本期未做系统化处理，走人工。若该场景高频，需在 V1.1 补充自动化处理。

#### 2.1.8 金额与币种口径

- looply 侧金额为**美元**（用户实付口径）
- 红布林侧金额为**人民币**（国内采购口径）
- 两侧金额在后台**分别展示，不做实时换算展示**

> ⚠ 遗留：两侧金额的汇率/换算口径（用于成本核算与对账）尚未定义，本期后台仅做展示，不参与计算。

### 2.2 红布林订单建单（流程型）

#### 功能描述

用户在 looply 提交订单时，系统同步在红布林侧**逐件创建 N 张红布林订单**（每张 1 件）并锁定商品，占住一物一码商品，防止被其他渠道售出。N 张红布林订单均挂在该 looply **父订单**层。

> ⚠️ **前置依赖**：一单一件下父订单会产生 N 张红布林订单。本方案成立的前提是**红布林能将这 N 张订单合并成一个国内包裹发出**；否则会产生 N 个国内包裹、跨境物流成本上升、发货/签收回调变 N 次。**该合并发货能力尚未与红布林技术确认**，是本期方案的地基性前置条件，详见 §3。

#### 前置条件

- 用户已在 looply 完成下单提交
- 订单内商品均为红布林供货商品

#### 操作流程

**主流程**

1. looply 创建父订单，状态 = `pending_payment` 待付款
2. 系统按父订单内商品**逐件**调用红布林建单能力，每件建 1 张红布林订单，传入：商品标识、收货信息、looply 父订单号
3. 红布林逐张校验库存可用性
4. 库存可用 → 红布林锁定库存 + 创建红布林订单（状态 = 待支付）
5. 红布林逐张返回红布林订单号
6. looply 记录 N 个红布林订单号（均关联父订单），并锁定 looply 侧对应库存占用
7. N 张全部建单成功后，订单进入待付款状态，向用户展示支付页

**分支流程：缺货**

- 步骤 3 某件校验不通过（商品已被售出/不可用）→ 建单失败 → **不生成待付款订单** → 向用户提示该商品已不可购买

> ⚠️ **遗留待确认（建单原子性）**：N 张红布林订单需保证「全建成功才放行」——若其中某张建单失败（缺货或系统异常），本期处理口径为**整单失败并回滚已建成功的那几张（逐张取消）**。但「某件缺货是否必须导致整个父订单失败、能否降级为仅去除缺货件」尚无明确业务结论，暂按整单失败实现，待确认。

#### 收货信息规则

当前方案下，红布林订单的收货信息统一走 looply 的**上海集货仓**、采购主体为 looply；但**收货人 / 收货电话 / 收货地址随商品类目路由到不同的集货点**——这正是"一单一件"的业务根因：同一 looply 父订单含不同类目商品时，因收货信息不同必须拆成多张红布林订单。买家账号（采购主体）本身是同一个。

**已实证的两类类目路由**（红布林侧真实订单数据）：

| 字段 | 非腕表类（箱包/配饰等） | 腕表类 |
|---|---|---|
| 买家 ID | 1576127975 | 1576127975（**同一采购账号**） |
| 买家手机号 | 13122811862 | 13122811862（同） |
| 收货人 | 12scales | 拾贰刻度-腕表收 |
| 收货电话 | 15802146223 | 13671788203 |
| 收货地址 | 上海市闵行区浦江镇恒南路 1328 号派拉蒙中心 1 号楼 308A 室 | 上海市静安区南汇路 38 号一楼 |

> **场景说明**：以上两套为红布林侧真实订单实证。可见**采购账号相同（1576127975），但收货人/电话/地址按类目路由不同**（腕表走静安腕表集货点、非腕表走闵行集货仓）——因此同一父订单含不同类目商品时天然拆分为多张红布林订单，佐证一单一件方案。
> ✅ 当前定论：本期按**集货模式 + 类目路由**实现，以上两类类目路由即为定论。集货模式以外的场景（如直发终端买家）本期不考虑、不阻塞；后续若出现新场景，另行提出并评估路由分支。

#### 校验规则

| 字段 | 规则 | 校验时机 |
|---|---|---|
| 商品库存 | 库存必须可用（一物一码，库存量=1） | 建单时由红布林校验 |
| looply 父订单号 | 必传，用于将 N 张红布林订单关联到父订单 | 每张建单请求发出前 |
| 收货信息 | 必传，本期固定为上海集货仓 | 每张建单请求发出前 |

#### 异常处理

| 异常 | 处理 |
|---|---|
| 红布林缺货 | 建单失败，不生成待付款订单，提示用户商品不可购买 |
| 红布林系统无响应 / 超时 | 建单失败，不生成待付款订单，提示用户稍后重试。**不允许生成无红布林订单号的 looply 待付款订单** |
| 某张建单成功但回执丢失 | 需依赖幂等机制避免重复建单（技术方案负责），业务上以红布林订单号为准 |
| N 张中部分建单成功、部分失败 | 整单建单失败处理，已建成功的那几张需**逐张回滚取消**（见"遗留待确认·建单原子性"） |

#### UI 关联

无买家侧界面变化。后台侧结果展示见 §2.6。

### 2.3 驱动红布林发货（流程型）

#### 功能描述

用户支付成功后，系统驱动红布林订单转为「已支付」，红布林据此安排真实发货。**支付成功前红布林不会发货。**

#### 前置条件

- looply 父订单已建单成功，其下 N 张红布林订单状态均 = 待支付
- 用户完成支付，looply 父订单状态转 `paid`

#### 操作流程

1. looply 父订单状态更新为 `paid` 已支付
2. 系统**逐张**驱动该父订单下的 N 张红布林订单转为「已支付」
3. 红布林逐张标记订单已支付，安排拣货发货
4. looply 父订单保持 `paid`，**不因红布林接单/发货而变化**

> 红布林无需回传预计发货时间。

#### 异常处理

| 异常 | 处理 |
|---|---|
| 驱动支付调用失败 | 需重试机制保证最终一致；重试仍失败则挂起人工处理，避免用户已付款但红布林不发货 |
| 重复驱动 | 依赖幂等机制，不产生重复发货 |

### 2.4 待付款自动取消（机制型）

#### 功能描述

待付款订单在支付未成功时，系统**自动**取消红布林订单并释放商品，不需要人工在后台操作。

#### 触发条件

| # | 触发源 | 说明 |
|---|---|---|
| 1 | **支付超时** | 超过 looply 支付有效期仍未支付。有效期口径**以订单支付模块最新规则为准**（⚠️ 非"下单+1 自然日"，最新时长待向订单支付模块核实），本模块不单独定义 |
| 2 | **支付单最终失败** | 支付单经处理后最终状态为失败 |

> 除上述两类系统自动触发外，用户/运营也可主动取消待付款订单。**三种情况下红布林侧的取消动作均由系统自动完成**，运营不需要去红布林侧操作。

#### 处理流程

> **取消触发约束（硬性）**：红布林订单的取消，**必须以 looply 订单先变为取消状态为前置**，由"looply 订单已取消"这一状态变更驱动。**不允许出现支付单状态失败就直接去调红布林取消**的上下游交互——支付失败/超时只是让 looply 订单转为取消，再由订单取消联动红布林取消。

1. 系统识别触发条件成立（支付超时 / 支付单最终失败）
2. **looply 父订单先转为取消状态**（`closed`）
3. 由订单取消状态变更驱动，系统自动**逐张**调用红布林取消订单能力，取消该父订单下全部 N 张红布林订单
4. 红布林逐张取消订单 + 释放商品库存
5. looply 释放本侧全部对应库存占用，未支付无退款

#### 规则说明

- looply 支付有效期口径与订单支付模块保持一致，本模块不单独定义（最新时长待核实，非 1 自然日）
- 红布林侧超时自动取消时长 = **120 小时**，该时长由**红布林侧控制**，looply 侧知晓即可、不做同步控制

> ✅ 已确认：红布林侧超时自动取消 = 120H（红布林控制）。looply 支付超时时长以订单支付模块最新规则为准（待核实）。两者由各自系统独立控制，looply 侧只需知晓红布林的 120H 口径，用于评估"looply 仍待付款但红布林已释放库存"的时间窗风险。

#### 异常处理

| 异常 | 处理 |
|---|---|
| 取消调用失败 | 需重试；重试仍失败挂人工，避免红布林侧库存被长期占用 |
| 红布林已发货后才收到取消 | 按阶段③处理（见 §2.7），不走自动取消 |

### 2.5 红布林发货与国内签收回执（机制型）

#### 功能描述

红布林发货、国内物流签收两个节点通过回调告知 looply，looply 记录履约节点，**不改变订单状态**。

#### 触发条件与处理

| 回执 | 触发时点 | looply 处理 | 订单状态 |
|---|---|---|---|
| **发货通知** | 红布林完成拣货打包并发出 | 记录国内物流单号、承运商 | 不变（仍 `paid`） |
| **国内签收通知** | **国内物流签收**（非上海仓验收完成） | 记录国内签收时间 | 不变（仍 `paid`） |

> **签收回执的触发时点已明确为「国内物流签收」**，与「上海仓验货完成」之间相差一个验货环节，两者不可混用。验货为拾二线下动作，不在系统内。

#### 规则说明

- 用户端在此阶段展示为「商品准备中」，**不显示已发货**
- looply 订单首次显示「已发货」的节点是**报关出关后运营录入国际物流单号**（见 §2.6.2）

#### 异常处理

| 异常 | 处理 |
|---|---|
| 回调丢失 | 需支持主动查询红布林订单状态补齐节点（技术方案负责） |
| 重复回调 | 幂等处理，不重复记录节点 |
| 回调顺序颠倒（先收到签收后收到发货） | 以红布林订单状态为准，按节点时间落库，不因顺序异常阻塞 |

### 2.6 国内红布林履约信息展示（页面型）

- 订单为红布林供货订单，已建单成功

每张红布林订单卡片自上而下分三部分：**卡片头**（订单号 + 状态）、**卡片体**（买家与收货信息，两列）、**商品行**（该单唯一 1 件商品）。

### 2.7 发起退款（含红布林联动）（页面型）

#### 功能描述

运营发起退款时，系统**一次操作**完成 looply 侧退款与红布林侧联动处理，运营不需要再单独取消红布林订单。

**入口合并说明**：原「发起退款」与「取消订单 · 联动红布林」两个操作已合并为单一入口「发起退款」。订单列表页与订单详情页使用同一套逻辑与同一弹窗内容。

**两入口一致性**：两个入口打开的是**同一份发起退款弹窗**，弹窗顶部订单信息区字段统一为两项——**订单号 / 买家**；每件商品对应的**红布林订单号与履约阶段随商品在退款商品表内逐行展示**（不再放在弹窗头部）。分阶段说明块、退款商品表、表单项（退款金额 / 退款原因 / 备注）在两个入口完全一致，不存在因入口不同而产生的字段或文案差异。每件的履约阶段均由系统按其对应红布林订单当前状态自动判定，不可人工更改。

#### 前置条件

- 订单为红布林供货订单
- 本期**无买家主动申请入口**，仅运营可发起

#### 页面布局

弹窗形式，自上而下：

1. 订单信息区：订单号、买家
2. 分阶段说明块（方案 A）：按**已勾选商品所跨履约阶段汇总**提示，只提示需运营关注/额外动作的部分——系统自动联动的件（支付前、支付后未发货）合并为一条提示（如「N 件由系统自动联动红布林取消并退款，无需额外操作」）、已发货件（需线下协调退回）单独提示、已发国际物流件（转售后）单独提示；未勾选商品时展示引导文案
3. 选择退款商品（表格 + 多选）：列含商品名称、**红布林订单（订单号，下方换行显示该件履约阶段标签）**、成色等级、单价
4. 表单区：退款原因、退款金额、备注

#### 页面元素

| 元素 | 说明 |
|---|---|
| 红布林订单 / 履约阶段 | 在退款商品表内**逐行随商品展示**：订单号 + 该件履约阶段标签；系统按该件对应红布林订单状态自动判定，不可人工更改 |
| 分阶段说明块 | 按已勾选商品所跨阶段汇总（方案 A，见页面布局）；系统自动件合并提示，已发货件、已发国际物流件单独提示 |
| 选择退款商品 | 可多选，默认全选待处理商品 |
| 退款原因 | 下拉必选：运营发起 / 缺货 / 商品问题 / 其他 |
| 退款金额 | 数字输入，默认带出所选商品实付金额合计 |
| 备注 | 多行文本，记录处理与联动结果（含阶段③线下退回的协调结果） |
| 确认按钮 | 文案随阶段变化，未选商品时禁用 |

#### 操作流程

**主流程**

1. 运营在订单列表或订单详情点击「发起退款」
2. 弹窗按件展示各商品对应红布林订单的履约阶段（见 §2.1.4，系统自动判定，运营不可更改）
3. 运营勾选需退款的商品；说明块按已勾选商品所跨阶段汇总提示需运营关注的部分（方案 A）
4. 运营填写退款原因、退款金额与备注
5. 提交后，系统**按每件对应的履约阶段分别执行**：

| 阶段 | 系统执行 |
|---|---|
| ① 支付前 | 取消对应的红布林订单（退某件取消对应那张、整单退取消全部 N 张）→ 释放库存 → 关单（无退款） |
| ② 支付后·未发货 | 取消对应的那张/那几张红布林订单 → looply 退对应金额 → 释放对应商品库存 |
| ③ 已发货·未发国际物流 | **不调接口** → looply 退款 → 红布林退回由运营线下协调，协调结果记入备注 |
| ④ 已发国际物流 | 不涉及红布林 → 转 looply 售后退货流程 |

#### 2.7.3 按件退款规则（取消对应红布林订单）

一单一件下，每张红布林订单只含 1 件，逆向按件处理即**取消对应的那张红布林订单**，不依赖红布林部分退能力。

| 勾选情况 | 红布林联动 | 库存处理 |
|---|---|---|
| **勾选部分商品** | 逐张取消所选商品各自对应的红布林订单 | 仅释放所选商品的库存 |
| **勾选全部商品** | 取消该父订单下全部 N 张红布林订单 | 释放整单商品库存 |

> 该规则是「一单一件、looply 父订单与红布林订单 1:N」的直接结果：每件独立一张订单，退某件即整单取消对应那张，无需红布林提供部分退能力。

#### 2.7.4 退款金额规则

- 退款金额基于**商品实付金额**（已扣除优惠分摊），非商品原价
- 默认带出所勾选商品的实付金额合计，运营可调整
- 阶段①（未支付）无退款
- **运费系统不处理**：阶段③线下退回产生的运费损失不在本模块内计算，退款按**全额**处理，后台退款字段**不拆分**「应退金额 / 扣减运费」，也不做运费扣减逻辑

#### 校验规则

| 字段 | 规则 | 校验时机 |
|---|---|---|
| 退款商品 | 至少勾选 1 件，否则确认按钮禁用 | 实时 |
| 退款金额 | 必填，大于 0，不超过所选商品实付金额合计 | 提交时 |
| 退款原因 | 必选 | 提交时 |

#### 异常处理

| 异常 | 处理 |
|---|---|
| 红布林联动接口调用失败 | looply 退款**不应先于**红布林联动结果确认；调用失败时提示运营并挂起，避免退款已出但商品仍在发货途中 |
| 红布林侧已发货但 looply 未收到回调 | 阶段判定可能滞后，需支持主动查询红布林订单状态后再判定 |
| 重复提交 | 幂等处理，不产生重复退款 |
| 退款失败 | 沿用订单支付模块口径：退款成功后才置 `cancelled`，退款失败挂人工、订单保持 `paid` |

#### UI 关联

- **PC 端（运营后台）**：后台原型 v2 · 订单列表页「发起退款」弹窗、订单详情页「发起退款」弹窗
- **APP 端**：不涉及

## 三、依赖与风险

### 3.1 上下游系统依赖

| 依赖方 | 依赖内容 | **本模块的关键要求** |
|---|---|---|
| **订单支付模块** | 订单状态机（含 `processing`）、支付有效期、退款能力、父子订单结构 | ①需提供支付有效期到期与支付单最终失败的**事件通知**，供本模块触发自动取消；②退款需支持**按商品逐件退款**（每件对应一张红布林订单的取消）；③本模块沿用其 `processing` 状态定义，无需另建 |
| **红布林系统** | 逐张建单锁库存、逐张驱动支付、**逐张取消订单**、**N 张合并发货**、发货回调、国内签收回调、订单状态查询、**商品明细与价格数据** | ①建单需**同步返回**库存校验结果，不可异步；②逐张建单/取消需**幂等**；③需支持**主动查询**订单状态，用于回调丢失时补偿；④库存锁定时长需与 looply 支付有效期对齐；⑤需返回**商品明细数据**（商品来源、品牌/类目、最低销售价、折扣价、订单支付价）；⑥⚠️ **前置依赖**：需支持将同一父订单下的 N 张红布林订单**合并为一个国内包裹发出**——此能力尚未与红布林技术确认，是一单一件方案成立的地基 |
| **库存模块** | looply 侧库存占用与释放 | 需提供**预占能力**，一物一码商品在下单到红布林建单成功之间不可被其他渠道占用 |
| **拾二（线下）** | 上海仓收货验货、报关出关、交付国际物流 | 报关出关后需及时告知运营录入国际物流单号，否则订单长期停留在 `paid` |

### 3.2 外部服务依赖

| 服务 | 说明 |
|---|---|
| 红布林开放接口 | 需完成对接联调、鉴权配置、IP 白名单等前置准备（技术侧负责） |

### 3.3 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| ⚠️ **合并发货前置依赖未确认（最高优先级）** | 一单一件下父订单产生 N 张红布林订单。**若红布林不支持将 N 张合并成一个国内包裹发出**，则产生 N 个国内包裹、跨境物流成本上升、发货/签收回调变 N 次，一单一件方案不成立 | **开发启动前必须与红布林技术确认合并发货能力**；若不支持，需重新评估一单一件是否成立（或退回其他下单方式） |
| **N 张建单原子性** | N 张中某张建单失败时，已建成功的那几张需回滚取消，否则出现库存被占但订单未成立；且"某件缺货是否必须整单失败"尚无业务结论 | 按"全建成功才放行、失败逐张回滚"实现；缺货处理口径待确认（见 §2.2） |
| **取消订单接口未在技术文档列出（阻塞项）** | 逆向按件取消依赖红布林"取消订单"接口，该接口在现有红布林技术文档中尚未列出 | 开发启动前需红布林技术侧确认并提供取消订单接口 |
| **一物一码超卖** | 下单到红布林建单成功之间存在时间窗，商品可能被其他渠道售出 | 建单失败即不生成待付款订单；库存模块提供预占 |
| **回调丢失导致节点缺失** | 运营看不到真实履约进度，或阶段判定错误导致逆向处理走错分支 | 支持主动查询红布林订单状态补偿 |
| **退款与联动不一致** | 退款已出但红布林仍在发货，产生货损 | 联动结果确认后再执行退款；失败挂人工 |
| **阶段③线下协调不可控** | 红布林已发货后退回依赖人工，成功率与时效均无保障 | 定位为「尽力而为」，PRD 不承诺退回成功 |
