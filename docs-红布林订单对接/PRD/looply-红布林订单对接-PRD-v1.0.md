## 一、概述

### 1.1 背景与目标

looply 是面向美国市场的二手奢侈品 B2C 电商平台，**商品实物存放在国内合作方红布林的仓库中**。looply 自身不持有库存，用户下单后需要在红布林侧建立对应订单、锁定商品，由红布林发货至上海集货仓，再经报关出口、国际物流送达境外用户。

本模块解决的问题：**把 looply 的交易链路与红布林的履约链路对接起来**，包括正向的建单/驱动支付/发货与签收回执，以及逆向的退款与联动取消。

目标：

1. 用户下单即在红布林侧锁定商品，避免一物一码商品被其他渠道售出
2. looply 侧订单状态与红布林履约进度保持可追溯的对应关系
3. 逆向场景（退款/取消）由**一次运营操作**完成 looply 与红布林两侧的处理，不需要人工分别操作两个系统

### 1.2 不做什么（明确边界）

| 不做 | 说明 |
|---|---|
| 上海仓收货验货、报关的系统化 | 由拾二线下全权处理，looply 系统只做状态记录与运营录入 |
| 买家主动申请退款入口 | 本期无 C 端申请入口，退款均由运营在后台发起 |
| 红布林侧库存的管理 | 库存由红布林系统管理，looply 只做锁定/释放的联动 |
| 异常处理系统化 | 缺货已在下单阶段拦截；验货不通过等异常走线下人工 |
| 用户签收段 | 国际物流末端配送与用户签收由 looply 订单模块负责，与红布林无关 |
| 国际物流商选型 | 不在本模块范围 |
| 红布林接口的技术定义 | 接口字段、幂等、鉴权属技术方案，不在 PRD 内 |

### 1.3 用户角色

| 角色 | 在本模块中的职责 |
|---|---|
| **looply 运营** | 录入国际物流单号、登记线下履约节点、发起退款与联动取消、处理线下退回登记 |
| **拾二（线下）** | 上海仓收货验货、报关出关、交付国际物流。不使用 looply 系统 |
| **红布林（外部系统）** | 库存管理、订单处理、国内拣货发货、国内签收确认与回调、退回处理 |
| **终端买家** | 在 looply 下单与支付。本模块内买家无直接操作入口 |

### 1.4 核心场景

| # | 场景 | 简述 |
|---|---|---|
| S1 | 正向履约 | 用户下单 → 红布林建单锁库存 → 支付 → 驱动红布林发货 → 国内物流 → 签收上海仓 → 验货报关 → 录入国际物流单号 → 订单转已发货 |
| S2 | 下单缺货 | 红布林库存不可用 → 建单失败 → 不生成待付款订单 |
| S3 | 支付未成功 | 支付超时 或 支付单最终失败 → 系统自动取消红布林订单 + 释放库存 + 关单 |
| S4 | 支付后取消 | 红布林未发货 → 系统自动调红布林取消/部分退 + looply 退款 |
| S5 | 发货后退回 | 红布林已发货 → 不联动接口，仅 looply 退款 + 线下协调退回并登记 |
| S6 | 出关后退货 | 订单已发国际物流 → 转 looply 售后退货流程，与红布林无关 |

### 1.5 全局页面流转

本模块**无独立菜单入口**，功能挂载在订单模块既有页面上：

```
订单管理 → 订单列表
    │
    ├─ 行操作「发起退款」 ─────→ 发起退款弹窗（含红布林联动）
    │
    └─ 行操作「详情」 ─→ 订单详情页
                            ├─ 板块「国内红布林履约信息」（只读展示）
                            └─ 顶部操作「发起退款」 ─→ 发起退款弹窗（含红布林联动）
```

> 列表页与详情页的「发起退款」为**同一套逻辑与同一个弹窗内容**，仅入口位置不同。

### 1.6 术语说明

| 术语 | 含义 |
|---|---|
| **红布林订单** | looply 在红布林系统中创建的订单。曾用名「采购单」，已统一为「红布林订单」 |
| **履约阶段** | 由红布林订单状态推导出的 4 个逆向处理阶段，决定取消/退款时与红布林的联动方式 |
| **联动** | looply 的一次运营操作，同时触发 looply 侧处理与红布林侧接口调用 |
| **上海集货仓** | 跨境中转节点，红布林发货的收货地址，由拾二线下运营 |
| **拾二** | 负责上海仓收货验货、报关、交付国际物流的线下合作方 |
| **TR** | Take Rate，红布林侧的抽成比例 |
| **一物一码** | 二手商品的库存模型，每件商品唯一、库存量恒为 1、不可替换 |

## 二、需求详细描述

### 2.1 全局约定

#### 2.1.1 红布林订单与 looply 订单的对应关系

- looply 订单与红布林订单 **1 : 1**
- **一单多件**：一个 looply 订单包含多件商品时，在红布林侧创建**一张**订单，多件商品作为该订单的明细，**不按件拆单**
- 逆向按件操作时，通过红布林的**部分退**能力实现（见 §2.7.3）

> 【TBD-2】上述"looply 订单"指父订单还是子订单尚未确定。订单支付 V1.2 为「下单只建父订单，支付到账后按商家拆子订单」。需明确：①红布林订单关联父订单还是子订单；②下单时尚未拆子单，库存锁定挂在哪一层。**确认前，开发不应据此设计数据关联。**

#### 2.1.2 looply 订单状态口径

本模块**不新增** looply 订单状态，沿用订单支付模块定义。本模块相关的关键口径：

| 状态 | 本模块相关口径 |
|---|---|
| `pending_payment` 待付款 | 已在红布林侧建单并锁定商品 |
| `paid` 已支付 | 从支付成功一直持续到**报关出关前**，期间包含红布林发货、国内签收、上海验货等节点，**状态均不变** |
| `shipped` 已发货 | 仅在**报关出关后运营录入国际物流单号**时触发 |
| `closed` 已关闭 | 待付款阶段未支付而取消/超时 |
| `cancelled` / `refunded` | 支付后取消 / 退款完成，沿用订单支付模块口径 |

**关键约定**：红布林侧的任何履约进展（发货、国内签收）**都不改变 looply 订单状态**，仅作为履约节点记录。

> 【TBD-1】`processing` 状态存废未定。本模块方案主张 looply 无 `processing`，但订单支付 V1.2 已为卡风控异步支付上线 `processing` 态与「订单已提交页」并交付开发。两侧结论冲突，需对齐后统一。**本 PRD 暂不定义该状态的本模块口径。**

#### 2.1.3 红布林订单状态枚举

| 枚举值 | 含义 | 触发时机 | 对应 looply 动作 |
|---|---|---|---|
| 待支付 | 已建单锁库存，未驱动支付 | looply 下单建单成功 | 记录红布林订单号 |
| 已支付 | 已驱动支付，红布林安排发货 | looply 支付成功后驱动 | 无（等待发货回调） |
| 已发货 | 红布林完成拣货打包并发出 | 红布林侧操作 | 记录国内物流信息，**不改订单状态** |
| 已取消 | 订单被取消 | looply 取消/超时驱动，或部分退全额 | 释放库存 + 关单/退款 |

> 国内签收为红布林侧的**回调事件**，不改变红布林订单状态枚举。

#### 2.1.4 履约阶段枚举（系统自动判定）

履约阶段由系统根据红布林订单状态与 looply 订单状态自动推导，**运营不可人工选择或修改**。

| 阶段 | 判定条件 | 红布林联动方式 | looply 处理 |
|---|---|---|---|
| ① 支付前（待付款） | looply 订单未支付 | 系统自动 · 调红布林取消订单 | 释放库存 + 关单（未支付，无退款） |
| ② 支付后 · 红布林发货前 | 已支付，红布林订单未发货 | 系统自动 · 调红布林取消/部分退 | 全额或部分退款 + 释放对应商品库存 |
| ③ 红布林发货后 · 发国际物流前 | 红布林已发货 ~ 报关出关/发国际物流前 | **不联动接口**，需线下协调退回 | 仅 looply 侧退款 + 登记线下退回 |
| ④ looply 发国际物流后 | looply 订单已 `shipped` | 与红布林无关 | 转 looply 售后退货流程 |

#### 2.1.5 联动方式枚举

| 枚举值 | 含义 | 适用阶段 |
|---|---|---|
| 系统自动 · 接口 | 系统调用红布林接口完成联动，运营无需操作红布林 | ①② |
| 不联动接口 · 线下协调 | 系统不调接口，红布林侧退回由运营线下协调后在后台登记 | ③ |
| 与红布林无关 | 该阶段的逆向处理不涉及红布林 | ④ |

#### 2.1.6 幂等与补偿约定（全局）

本模块所有与红布林的交互均为跨系统调用，统一遵循：

| 场景 | 约定 |
|---|---|
| looply → 红布林（建单 / 驱动支付 / 取消 / 部分退） | 必须**幂等**，重复调用不产生重复业务结果 |
| 红布林 → looply（发货回调 / 签收回调） | 必须**幂等**，重复回调不重复记录节点 |
| 回调丢失 | 支持**主动查询**红布林订单状态补齐节点，不依赖回调可靠性 |
| 调用失败 | 支持重试；重试仍失败的**挂起人工处理**，不静默失败 |

各功能章节不再重复描述，统一引用本节。

#### 2.1.7 红布林侧信息变更的处理

红布林侧订单信息（商品、金额、收货信息）在建单后发生变更时：

| 变更类型 | looply 处理 |
|---|---|
| 红布林侧**取消订单**（非 looply 发起） | 视为异常，挂起人工处理；需运营核实后决定 looply 侧订单如何处理 |
| 红布林侧**商品/金额变更** | 本期**不支持**。红布林订单一经创建，明细不可变更 |
| 红布林侧**物流信息更新** | 通过发货回调写入，以最后一次回调为准 |

> ⚠ 遗留：红布林侧主动取消订单的场景（如红布林发现商品有问题）本期未做系统化处理，走人工。若该场景高频，需在 V1.1 补充自动化处理。

#### 2.1.8 金额与币种口径

- looply 侧金额为**美元**（用户实付口径）
- 红布林侧金额为**人民币**（国内采购口径）
- 两侧金额在后台**分别展示，不做实时换算展示**

> ⚠ 遗留：两侧金额的汇率/换算口径（用于成本核算与对账）尚未定义，本期后台仅做展示，不参与计算。

### 2.2 红布林订单建单（流程型）

#### 功能描述

用户在 looply 提交订单时，系统同步在红布林侧创建订单并锁定商品，占住一物一码商品，防止被其他渠道售出。

#### 前置条件

- 用户已在 looply 完成下单提交
- 订单内商品均为红布林供货商品

#### 操作流程

**主流程**

1. looply 创建订单，状态 = `pending_payment` 待付款
2. 系统调用红布林建单能力，传入：商品标识、收货信息、looply 订单号
3. 红布林校验库存可用性
4. 库存可用 → 红布林锁定库存 + 创建红布林订单（状态 = 待支付）
5. 红布林返回红布林订单号
6. looply 记录红布林订单号，并锁定 looply 侧库存占用
7. 建单完成，订单进入待支付状态，向用户展示支付页

**分支流程：缺货**

- 步骤 3 校验不通过（商品已被售出/不可用）→ 建单失败 → **不生成待付款订单** → 向用户提示该商品已不可购买

#### 收货信息规则

当前方案下，红布林订单的收货信息为**上海集货仓**，采购主体为 looply：

| 字段 | 取值 |
|---|---|
| 收货人 | 上海集货仓收货人（拾二） |
| 收货电话 | 上海集货仓联系电话 |
| 收货地址 | 上海集货仓地址 |
| 买家 ID / 买家手机号 | looply 侧采购账号（非终端消费者） |

> **场景说明**：该规则已有实证——红布林侧真实订单显示收货人为拾二、收货地址为上海闵行集货仓、买家 ID 为 looply 采购账号。
> ⚠ 若后续出现集货模式以外的场景（如直发终端买家），本节规则需按场景路由，届时需重新评估流程分支。本期按**集货模式单场景**实现。

#### 校验规则

| 字段 | 规则 | 校验时机 |
|---|---|---|
| 商品库存 | 库存必须可用（一物一码，库存量=1） | 建单时由红布林校验 |
| looply 订单号 | 必传，用于两侧订单关联 | 建单请求发出前 |
| 收货信息 | 必传，本期固定为上海集货仓 | 建单请求发出前 |

#### 异常处理

| 异常 | 处理 |
|---|---|
| 红布林缺货 | 建单失败，不生成待付款订单，提示用户商品不可购买 |
| 红布林系统无响应 / 超时 | 建单失败，不生成待付款订单，提示用户稍后重试。**不允许生成无红布林订单号的 looply 待付款订单** |
| 建单成功但回执丢失 | 需依赖幂等机制避免重复建单（技术方案负责），业务上以红布林订单号为准 |
| 部分商品建单成功、部分失败 | 整单建单失败处理，已建部分需回滚取消 |

#### UI 关联

无买家侧界面变化。后台侧结果展示见 §2.6。

### 2.3 驱动红布林发货（流程型）

#### 功能描述

用户支付成功后，系统驱动红布林订单转为「已支付」，红布林据此安排真实发货。**支付成功前红布林不会发货。**

#### 前置条件

- looply 订单已建单成功，红布林订单状态 = 待支付
- 用户完成支付，looply 订单状态转 `paid`

#### 操作流程

1. looply 订单状态更新为 `paid` 已支付
2. 系统驱动红布林订单转为「已支付」
3. 红布林标记订单已支付，安排拣货发货
4. looply 订单保持 `paid`，**不因红布林接单/发货而变化**

> 红布林无需回传预计发货时间。

#### 异常处理

| 异常 | 处理 |
|---|---|
| 驱动支付调用失败 | 需重试机制保证最终一致；重试仍失败则挂起人工处理，避免用户已付款但红布林不发货 |
| 重复驱动 | 依赖幂等机制，不产生重复发货 |

### 2.4 待付款自动取消（机制型）

#### 功能描述

待付款订单在支付未成功时，系统**自动**取消红布林订单并释放商品，不需要人工在后台操作。

#### 触发条件

| # | 触发源 | 说明 |
|---|---|---|
| 1 | **支付超时** | 超过支付有效期仍未支付。有效期 = 下单 + 1 自然日（沿用订单支付 V1.2 的 `payment_deadline`） |
| 2 | **支付单最终失败** | 支付单经处理后最终状态为失败 |

> 除上述两类系统自动触发外，用户/运营也可主动取消待付款订单。**三种情况下红布林侧的取消动作均由系统自动完成**，运营不需要去红布林侧操作。

#### 处理流程

1. 系统识别触发条件成立
2. 系统自动调用红布林取消订单能力
3. 红布林取消订单 + 释放商品库存
4. looply 释放本侧库存占用
5. looply 订单关闭（状态 = `closed`），未支付无退款

#### 规则说明

- 支付有效期口径与订单支付模块保持一致，本模块不单独定义
- 红布林侧的库存锁定时长需与 looply 支付有效期对齐

> ⚠ 遗留：红布林侧库存锁定时长是否与 looply 的 1 自然日一致尚未确认。若红布林侧更短，会出现 looply 仍待付款但红布林已释放库存的情况，需要红布林技术侧确认。

#### 异常处理

| 异常 | 处理 |
|---|---|
| 取消调用失败 | 需重试；重试仍失败挂人工，避免红布林侧库存被长期占用 |
| 红布林已发货后才收到取消 | 按阶段③处理（见 §2.7），不走自动取消 |

---

### 2.5 红布林发货与国内签收回执（机制型）

#### 功能描述

红布林发货、国内物流签收两个节点通过回调告知 looply，looply 记录履约节点，**不改变订单状态**。

#### 触发条件与处理

| 回执 | 触发时点 | looply 处理 | 订单状态 |
|---|---|---|---|
| **发货通知** | 红布林完成拣货打包并发出 | 记录国内物流单号、承运商 | 不变（仍 `paid`） |
| **国内签收通知** | **国内物流签收**（非上海仓验收完成） | 记录国内签收时间 | 不变（仍 `paid`） |

> **签收回执的触发时点已明确为「国内物流签收」**，与「上海仓验货完成」之间相差一个验货环节，两者不可混用。验货为拾二线下动作，不在系统内。

#### 规则说明

- 用户端在此阶段展示为「商品准备中」，**不显示已发货**
- looply 订单首次显示「已发货」的节点是**报关出关后运营录入国际物流单号**（见 §2.6.2）

#### 异常处理

| 异常 | 处理 |
|---|---|
| 回调丢失 | 需支持主动查询红布林订单状态补齐节点（技术方案负责） |
| 重复回调 | 幂等处理，不重复记录节点 |
| 回调顺序颠倒（先收到签收后收到发货） | 以红布林订单状态为准，按节点时间落库，不因顺序异常阻塞 |

### 2.7 发起退款（含红布林联动）（页面型）

#### 功能描述

运营发起退款时，系统**一次操作**完成 looply 侧退款与红布林侧联动处理，运营不需要再单独取消红布林订单。

**入口合并说明**：原「发起退款」与「取消订单 · 联动红布林」两个操作已合并为单一入口「发起退款」。订单列表页与订单详情页使用同一套逻辑与同一弹窗内容。

**两入口一致性**：两个入口打开的是**同一份发起退款弹窗**，弹窗顶部订单信息区字段统一为四项——**订单号 / 买家 / 红布林订单 / 当前履约阶段**，联动说明块、退款商品表、表单项（退款金额 / 退款原因 / 备注，阶段③追加退回物流单号）在两个入口完全一致，不存在因入口不同而产生的字段或文案差异。履约阶段均由系统按订单当前状态自动判定。

#### 前置条件

- 订单为红布林供货订单
- 本期**无买家主动申请入口**，仅运营可发起

#### 页面布局

弹窗形式，自上而下：

1. 订单信息区：订单号、买家、红布林订单、当前履约阶段
2. 联动说明块：红布林联动方式、looply 处理动作
3. 阶段动作提示
4. 选择退款商品（表格 + 多选）
5. 表单区：退款金额、退款原因、备注（阶段③追加「退回物流单号」）

#### 页面元素

| 元素 | 说明 |
|---|---|
| 当前履约阶段 | 系统自动判定结果 + 说明「系统自动判定，不可人工更改」 |
| 红布林联动方式 | 取自 §2.1.5 枚举 |
| looply 处理 | 该阶段的 looply 侧处理动作 |
| 选择退款商品 | 可多选，默认全选待处理商品 |
| 退款金额 | 数字输入，默认带出所选商品实付金额合计 |
| 退款原因 | 下拉必选：运营发起 / 缺货 / 商品问题 / 其他 |
| 退回物流单号 | **仅阶段③展示**，用于登记线下协调的退回物流 |
| 备注 | 多行文本，记录处理与联动结果 |
| 确认按钮 | 文案随阶段变化，未选商品时禁用 |

#### 操作流程

**主流程**

1. 运营在订单列表或订单详情点击「发起退款」
2. 系统自动判定当前履约阶段（见 §2.1.4），运营不可更改
3. 弹窗展示该阶段的联动方式与处理动作
4. 运营勾选需退款的商品、填写退款金额与原因
5. 提交后，系统按阶段执行：

| 阶段 | 系统执行 |
|---|---|
| ① 支付前 | 调红布林取消订单 → 释放库存 → 关单（无退款） |
| ② 支付后·未发货 | 调红布林取消/部分退 → looply 退款 → 释放对应商品库存 |
| ③ 已发货·未发国际物流 | **不调接口** → looply 退款 → 登记退回物流单号，红布林退回由运营线下协调 |
| ④ 已发国际物流 | 不涉及红布林 → 转 looply 售后退货流程 |

#### 2.7.3 部分退规则

| 勾选情况 | 红布林联动 | 库存处理 |
|---|---|---|
| **勾选部分商品** | 调红布林**部分退**能力 | 仅释放所选商品的库存 |
| **勾选全部商品** | 走**整单取消** | 释放整单商品库存 |

> 该规则是「一单多件、looply 订单与红布林订单 1:1」得以成立的前提：红布林支持部分退，因此 looply 按件逆向时无需按件拆单。

#### 2.7.4 退款金额规则

- 退款金额基于**商品实付金额**（已扣除优惠分摊），非商品原价
- 默认带出所勾选商品的实付金额合计，运营可调整
- 阶段①（未支付）无退款

> 【TBD-3】阶段③线下退回产生的**运费损失由谁承担**尚未确定（平台 / 用户 / 按责任划分）。这将决定：①退款是否全额；②后台退款字段是否需要拆分为「应退金额 / 扣减运费」。**确认前，阶段③的退款金额按全额计算，扣减逻辑未实现。**

#### 校验规则

| 字段 | 规则 | 校验时机 |
|---|---|---|
| 退款商品 | 至少勾选 1 件，否则确认按钮禁用 | 实时 |
| 退款金额 | 必填，大于 0，不超过所选商品实付金额合计 | 提交时 |
| 退款原因 | 必选 | 提交时 |
| 退回物流单号 | 阶段③选填 | 提交时 |

#### 异常处理

| 异常 | 处理 |
|---|---|
| 红布林联动接口调用失败 | looply 退款**不应先于**红布林联动结果确认；调用失败时提示运营并挂起，避免退款已出但商品仍在发货途中 |
| 红布林侧已发货但 looply 未收到回调 | 阶段判定可能滞后，需支持主动查询红布林订单状态后再判定 |
| 重复提交 | 幂等处理，不产生重复退款 |
| 退款失败 | 沿用订单支付模块口径：退款成功后才置 `cancelled`，退款失败挂人工、订单保持 `paid` |

#### UI 关联

- **PC 端（运营后台）**：后台原型 v1 · 订单列表页「发起退款」弹窗、订单详情页「发起退款」弹窗
- **APP 端**：不涉及

## 三、依赖与风险

### 3.1 上下游系统依赖

| 依赖方 | 依赖内容 | **本模块的关键要求** |
|---|---|---|
| **订单支付模块** | 订单状态机、支付有效期、退款能力、父子订单结构 | ①需提供支付有效期到期与支付单最终失败的**事件通知**，供本模块触发自动取消；②退款需支持**按商品部分退款**；③`processing` 状态口径需与本模块对齐（TBD-1） |
| **红布林系统** | 建单锁库存、驱动支付、取消订单、**部分退**、发货回调、国内签收回调、订单状态查询、**商品明细与价格数据** | ①建单需**同步返回**库存校验结果，不可异步；②取消与部分退需**幂等**；③需支持**主动查询**订单状态，用于回调丢失时补偿；④库存锁定时长需与 looply 支付有效期对齐；⑤需返回**商品明细数据**（商品来源、品牌/类目、最低销售价、折扣价、订单支付价、TR），供后台展示与后续成本核算 |
| **库存模块** | looply 侧库存占用与释放 | 需提供**预占能力**，一物一码商品在下单到红布林建单成功之间不可被其他渠道占用 |
| **拾二（线下）** | 上海仓收货验货、报关出关、交付国际物流 | 报关出关后需及时告知运营录入国际物流单号，否则订单长期停留在 `paid` |

### 3.2 外部服务依赖

| 服务 | 说明 |
|---|---|
| 红布林开放接口 | 需完成对接联调、鉴权配置、IP 白名单等前置准备（技术侧负责） |

### 3.3 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| **一物一码超卖** | 下单到红布林建单成功之间存在时间窗，商品可能被其他渠道售出 | 建单失败即不生成待付款订单；库存模块提供预占 |
| **回调丢失导致节点缺失** | 运营看不到真实履约进度，或阶段判定错误导致逆向处理走错分支 | 支持主动查询红布林订单状态补偿 |
| **退款与联动不一致** | 退款已出但红布林仍在发货，产生货损 | 联动结果确认后再执行退款；失败挂人工 |
| **阶段③线下协调不可控** | 红布林已发货后退回依赖人工，成功率与时效均无保障 | 定位为「尽力而为」，PRD 不承诺退回成功 |
| **TBD 项未按时确认** | 状态机、数据关联、退款金额三处无法开发 | 见文首 TBD 表，需在开发启动前确认 |
