## 一、概述

### 1.1 背景与目标

「用户订阅管理」不是一个消息推送列表，而是一套**同意（Consent）与触达（Reach）的治理底座**，回答一个法律与体验上都关键的问题：Looply 在什么前提下、通过什么渠道、可以向用户发送什么类型的消息？

核心分界线（来自美国 CAN-SPAM）：

- **事务性消息**（订单、支付、物流、鉴定、账户安全）：服务于已发生的交易，**无需同意、不可退订、强制送达**。
- **商业/营销消息**（上新、降价、活动、newsletter）：受"订阅同意"开关管控，**必须随时可退订**。

本期目标：建立 **Email 营销订阅状态**的存储、读写、退订与同意审计能力，并对外提供查询接口，作为下游 EDM/促销/召回模块发送前的判断依据。

### 1.2 不做什么（明确边界）

本期**仅管理 Email 营销订阅状态 + 审计 + 对外查询**，以下明确不做：

| 不做项 | 归属 |
|------|------|
| 消息是否发送的判断（发送闸门） | ➡️ 移交 EDM/促销/召回模块（调用本模块查询接口） |
| Email 内消息类型细分（降价/促销/EDM…） | ➡️ 由对应业务模块定义 |
| Push 渠道（权限引导、OS 状态、App 内开关） | ⏸️ 二期 |
| 站内信 / 通知中心 | ⏸️ 二期 |
| SMS 渠道（逻辑） | ⏸️ 二期（结构预留 TCPA） |
| 订阅源引擎（保存搜索 / 心愿单降价 / 品牌关注 / 关注卖家） | ⏸️ 二期 |
| 系统自动退订（硬退信 bounce / 垃圾投诉 complaint） | ⏸️ 二期（归 EDM 抑制列表） |
| 邮件模板与发件 | ➡️ EDM / 基础设施（本模块只提供退订能力与状态） |

### 1.3 用户角色

| 角色 | 说明 | 在本模块的行为 |
|------|------|------|
| 访客（未注册） | 未注册的浏览者 | 通过页脚订阅框 / 弹窗留邮箱订阅；可凭邮件链接退订 |
| 注册买家 | 已注册账户的用户 | 偏好中心查看 / 开关 Email 营销订阅；可凭邮件链接退订 |
| 运营 | 平台运营人员 | 后台查询订阅分布、按邮箱调取同意凭证（只读，不代改） |
| 合规 | 法务/合规团队 | 调取指定用户同意凭证用于举证 |
| 系统 / 下游模块 | 注册模块、EDM 模块 | 注册关联认领；EDM 发送前查询订阅状态 |

### 1.4 核心场景

1. **未注册访客订阅**：访客在页脚订阅框 / 弹窗留邮箱 → 以 email 为主体创建订阅记录（user_id 空）+ 落同意凭证。
2. **访客订阅后注册**：同邮箱注册 → 系统回填 user_id 到已有订阅记录（不改状态、不新增凭证）。
3. **注册买家管理订阅**：偏好中心开 / 关 Email 营销总开关，事务邮件 Required 不可关。
4. **用户退订**：点邮件底部退订链接 → 免登录落地页 → 一步退订 + 落退订凭证，仍收事务邮件。
5. **运营 / 合规审计**：后台按邮箱查订阅状态与凭证时间线（何时、何入口、何 IP/设备）。

### 1.5 全局页面流转

```
[C 端]
全站页脚 ──(页脚订阅框)──► 订阅成功态
浏览页面 ──(订阅弹窗)──► 订阅成功态
偏好中心(登录后) ──(开/关营销开关)──► 状态即时更新
营销邮件底部 ──(退订链接)──► 退订落地页(确认态) ──► 退订成功态

[后台]
订阅管理后台 ──(点行: 查看/调取凭证)──► 用户详情 Drawer(含同意凭证时间线)
```

### 1.6 术语说明

| 术语 | 定义 |
|------|------|
| 事务性消息 | 服务于已发生交易的消息，无需同意、不可退订 |
| 营销/商业消息 | 推广性质消息，受订阅同意管控、可退订 |
| 同意凭证 | 带时间戳、来源、IP/设备的同意/退订审计记录，用于合规举证 |
| 偏好中心 | 用户管理营销订阅开关的入口（账户设置内） |
| 订阅入口（source） | 订阅记录"从哪订上的"入口：页脚订阅框 / 订阅弹窗 / 偏好中心 |
| 触发来源（凭证 source） | 每条同意变更的触发点（含退订来源） |
| 关联认领 | 注册时把已有订阅记录的 user_id 从空回填为新账户 |
| 免登录退订 | 凭邮件内签名 token 识别用户，无需登录即可退订 |

### 1.7 多语言 / 多国家策略

本期面向美国单一市场，合规以 CAN-SPAM 为准。C 端文案为英文，后台为中文运营界面。多语言 i18n 结构本期不展开；未来扩展其他市场时，订阅文案与合规规则（如 GDPR 的预勾选禁止、双重 opt-in 要求）需按区域适配，订阅状态模型本身与语言无关，不受影响。

## 二、需求详细描述

### 公共说明：消息分类与同意模型

本模块的所有逻辑建立在"消息分类"之上。每条系统发出的消息都带一个**类目标签**，类目决定它是否受同意管控。

| 类目 | 是否受同意管控 | 是否可退订 | 典型消息 |
|------|:---:|:---:|------|
| 事务通知 Transactional | 否（强制送达） | 否 | 订单确认、支付、发货/物流、鉴定结果、退换货、账户安全 |
| 个性化提醒 Personalized Alert | 是 | 是 | 保存搜索命中、心愿单降价/售罄、关注品牌上新（**二期**） |
| 群发营销 Mass Marketing | 是 | 是 | Newsletter、大促/降价场、节日活动、召回挽回 |

**本期同意粒度**：仅一个 **Email 营销订阅总开关**。已订阅 = 允许发送一切 Email 营销（个性化提醒 + 群发营销）；已退订 = 仅收事务邮件。Email 内的类型细分（降价/促销/EDM）由 EDM 模块未来定义，本期不做。

**边界判定原则**：当一条消息"既像事务又像营销"时（如"您收藏的商品降价了"），**一律从严归为营销类**，受同意管控。

#### 订阅状态枚举（贯穿全模块）

| 枚举值 | UI 展示（C 端/后台） | 含义 | 进入条件 | 退出条件 |
|------|------|------|------|------|
| `subscribed` | Subscribed / 已订阅 | 允许发送 Email 营销 | 用户经任一入口订阅成功 | 用户退订 |
| `unsubscribed` | Unsubscribed / 已退订 | 仅收事务邮件 | 用户退订；或邮箱从未订阅（无记录视作未订阅） | 用户重新订阅 |

> 默认态：opt-in 模式，无记录的邮箱视作未订阅，不预置"未订阅"行（见模块 D）。

### 模块 A：C 端订阅入口（页脚订阅框 / 订阅弹窗）

> 类型：页面型（嵌入式组件）。UI 实现归 C 端产品，本模块提供订阅写入能力与凭证记录。

#### A.1 功能描述

未注册访客与登录用户均可通过两个常驻入口留下邮箱完成订阅：**页脚订阅框**（全站页脚常驻）与**订阅弹窗**（Shopify 式营销弹窗）。订阅以 email 为主体，未注册时 user_id 留空。

#### A.2 前置条件

- 无需登录。任何访客都可订阅。
- 已登录用户也可通过这两个入口订阅（系统自动带上 user_id）。

#### A.3 页面布局（PC / Mobile）

**页脚订阅框**：
- PC：深色横幅（#1A1A1A），左侧主副文案，右侧邮箱输入框 + Subscribe 按钮横向排列。
- Mobile：深色卡片，文案在上，邮箱框 + 按钮纵向堆叠。

**订阅弹窗**：
- PC：居中模态卡片（420px 宽），含关闭按钮、图标、主标题、副文案、邮箱框、Subscribe 按钮、No thanks、隐私说明。
- Mobile：底部抽屉式（贴底弹出），内容同 PC。

#### A.4 页面元素

| 元素 | 内容 | 说明 |
|------|------|------|
| 主标题（页脚） | "Be first to shop new arrivals" | 抢先看新品钩子 |
| 主标题（弹窗） | "Don't miss the one that's yours" | 二手唯一性钩子 |
| 副文案（弹窗） | "Authenticated luxury, one piece each. When it's gone, it's gone — get first access to new drops." | 强调每件唯一、卖完即无 |
| 邮箱输入框 | placeholder "Enter your email" | 必填，邮箱格式校验 |
| 主按钮 | "Subscribe" | 提交订阅 |
| 次按钮（弹窗） | "No thanks" | 关闭弹窗，不订阅 |
| 隐私说明 | "By subscribing you agree to our Privacy Policy. Unsubscribe anytime." | 合规必备，含隐私政策链接 |

#### A.5 页面状态变体

| 状态 | 说明 | 设计稿 |
|------|------|------|
| 默认态 | 邮箱框 + Subscribe 按钮 | 页脚默认态 / 弹窗默认态（PC+Mobile） |
| 成功态 | 替换为成功反馈（页脚显示绿色"已订阅"徽章；弹窗显示"You're on the list!" + Start shopping） | 页脚成功态 / 弹窗成功态（PC ✅；Mobile 成功态与 PC 一致，仅布局适配，原型未单独出图） |
| 错误态 | 邮箱格式非法时输入框下方红字提示 | 复用 Input/Error 组件 |

#### A.6 操作流程

主流程：
1. 用户在邮箱框输入邮箱 → 点 Subscribe。
2. 前端校验邮箱格式（非法则报错，不提交）。
3. 调订阅写入：传 `email` + `source`（页脚=`footer` / 弹窗=`popup`）+ 登录态下的 `user_id`（可空）+ **设备指纹 `device_id`**（前端生成，见 A.6.2）。
4. **后端先做频率限流判断**（见 A.11）：按 `ip + device_id` 计数，超限则直接返回 429 + 提示文案，**不写订阅、不落凭证、不发邮件**；未超限继续。
5. **后端确定 user_id**（关键，见 A.6.1）：
   - 请求已带 user_id（登录态发起）→ 直接采用。
   - 请求未带 user_id（未登录发起）→ **拿 email 实时反查用户中心**：已注册则落该账户 user_id；未注册则 user_id 留空。
6. 后端写入订阅：若该 email 无订阅记录 → 新建（status=subscribed）；若已存在 → 更新为 subscribed（幂等）。无论新建或更新，**落一条 subscribe 同意凭证**（含来源、IP、设备 UA、时间戳）。
7. 前端切换为成功态。

分支流程：
- 该 email 已是 subscribed → 仍返回成功态（幂等，不报"已订阅过"错误），但凭证按业务规则可不重复落（见 A.8）。
- 弹窗点 No thanks / 关闭 → 不提交，关闭弹窗。

#### A.6.1 user_id 的确定逻辑（重要）

订阅的主体是 **email**，user_id 是可空关联。一个常见误区是"未登录订阅 = 未注册用户"——**这是错的**：已注册用户完全可能不登录，直接在 footer / 弹窗用注册过的邮箱订阅。因此 user_id 不能仅凭"请求是否带 user_id"判断，须按下表确定：

| 订阅发起场景 | 请求带 user_id | 处理 | 落库 user_id |
|------|:---:|------|:---:|
| 登录用户订阅（偏好中心必然登录；footer/弹窗登录态） | 有 | 直接采用 | 账户 ID |
| 未登录、email 已注册 | 无 | **实时反查用户中心命中** | 账户 ID |
| 未登录、email 未注册 | 无 | 实时反查未命中 | null（未关联） |

> - **后台"未注册"标签的准确含义**：user_id 为 null = "尚未关联到账户"。经实时反查后，已注册邮箱即便未登录订阅也会带上 user_id，因此 user_id=null 基本等同于"邮箱确实未注册"。
> - **本期无存量**：系统尚未上线、无存量用户，不需要"登录时补全历史 user_id"机制。先订阅后注册的衔接由模块 D 的注册事件回填覆盖。

#### A.6.2 设备指纹 device_id（用于频率限流）

订阅频率限流（A.11）需要一个比 IP 更稳定、能区分同一 NAT 出口下不同设备的标识，因此提交订阅时由前端附带一个**设备指纹** `device_id`。

| 项 | 说明 |
|------|------|
| 生成方 | 前端（C 端）生成，随订阅请求一并上报后端 |
| 取值方式 | 基于浏览器指纹（如 UA、屏幕、时区、Canvas 等特征聚合）生成稳定 ID，或首次访问时下发并存于 localStorage 的匿名标识 |
| 用途 | **仅用于 A.11 接口限流计数**（`ip + device_id` 维度）；不写入订阅记录、不进同意凭证（凭证只存设备 UA 快照，见 E.3） |
| 缺失/取不到 | 用户开无痕/强隐私模式导致指纹缺失时，`device_id` 可空，限流退化为「仅按 IP」并放宽阈值（见 A.11 降级规则） |
| 隐私 | 匿名标识，不含 PII；用途限于反滥用，纳入隐私政策说明 |

> 设备指纹具体生成方案（自研特征聚合 vs 第三方 SDK）由前端与安全方确认，本期只约定"提交时附带 device_id、仅用于限流、可缺失"。

#### A.7 校验规则

| 字段 | 规则 | 校验时机 |
|------|------|------|
| email | 非空；符合邮箱格式（RFC 基本校验） | 提交前（前端）+ 写入前（后端） |
| source | 必传，枚举 footer/popup（由入口固定，非用户输入） | 后端写入时 |
| device_id | 选填，前端生成的设备指纹；缺失时限流退化为仅按 IP（A.11） | 后端限流计数时 |

#### A.8 交互说明

- Subscribe 提交中按钮显示 loading 态（复用 Button/Loading）。
- 弹窗触发策略（进站延时 / 离开意图 / 频控）**归 C 端，本模块只认 `popup` 来源**（见待确认问题）。
- 重复订阅幂等：同邮箱重复提交不报错，状态保持 subscribed。

#### A.9 异常处理

| 异常 | 处理 |
|------|------|
| 邮箱格式非法 | 输入框下红字 "Please enter a valid email"，不提交 |
| 网络/服务异常 | 按钮恢复，提示 "Something went wrong, please try again" |
| 重复订阅 | 幂等成功，不报错 |

#### A.11 防滥用：订阅频率限制（接口限流）

> 目的：防止脚本/恶意用户对订阅写入接口批量注入假邮箱或对他人邮箱发起订阅轰炸（list bombing）。本期做**最小有效**的接口限流；double opt-in、人机验证（Turnstile）等更完整的反滥用手段列入二期。

**限流维度与阈值**：

| 维度 | 计数 Key | 窗口 | 阈值 |
|------|------|------|:---:|
| 单 IP + 单设备 | `rl:sub:{ip}:{deviceId}` | 24 小时（固定窗口） | 5 次 |

- **为什么组合 IP + 设备指纹**：纯 IP 限流在 NAT 场景（家庭/公司共用公网出口）会误伤——同一 WiFi 下多台真机算一个 IP。叠加设备指纹后，每台设备独立计数、互不挤占，正常家庭/公司用户不会被连坐。
- **正常用户安全边界**：真实用户对单站点的订阅动作通常 1 次，改偏好/退订再订也就 2-3 次，24 小时 5 次留有充分冗余，基本零误拦。
- **设备指纹缺失时的降级**：用户开无痕/强隐私模式导致指纹取不到时，退化为「仅按 IP」计数，此时应**放宽**阈值（建议 10 次/24h），避免 NAT 误伤回潮，不可收紧。

**算法与存储**：

- 采用**固定窗口计数器**（实现最简，对「防批量」目标足够；不引入滑动窗口/令牌桶）。
- 存储用 Redis，原子 `INCR` + `EXPIRE` 自动过期清零：

```
key = "rl:sub:" + ip + ":" + deviceId
count = INCR key
if count == 1:           # 仅首次提交时设过期，保证"首次提交后算 24h"，而非每次续期
    EXPIRE key 86400
if count > 5:
    拦截（不写订阅、不发确认/凭证），返回错误文案
```

**触发后处理**：

| 项 | 规则 |
|------|------|
| 拦截时机 | 限流判断须在**写订阅记录、落同意凭证、发任何邮件之前**——否则攻击者每刷一次就触发一封邮件，限流失去意义 |
| HTTP 状态码 | `429 Too Many Requests`，附 `Retry-After` 头 |
| C 端提示文案 | "Sorry, too many attempts. Please try again later."（英文，对应「对不起，操作太频繁」） |
| 本次请求 | 不写入订阅记录、不落凭证、不发邮件 |

**工程要点**：

- **取真实 IP**：服务在 CDN/负载均衡后时，从 `X-Forwarded-For` 取客户端 IP，勿取网关/LB 出口 IP（否则全站算一个人）。
- **fail-open**：Redis 抖动或不可用时，限流逻辑应**放行**而非拦截，避免风控组件自身成为业务故障点。
- **留痕**：每次触发限流记一条日志（IP、设备指纹、命中维度、时间），供后续阈值校准与异常排查。

### 模块 C：邮件一键退订（免登录落地页）

> 类型：流程型。营销邮件底部链接 → 退订落地页。邮件模板归 EDM 模块，本模块提供退订能力与落地页。

#### C.1 功能描述

每封营销邮件底部含可见的退订链接（CAN-SPAM 强制）。用户点击后跳转到**免登录退订落地页**，凭链接内签名 token 识别目标邮箱，一步完成退订。注册用户与未注册访客均可退订。

#### C.2 前置条件

- 用户收到过营销邮件（邮件含带签名 token 的退订链接）。
- **无需登录**——仅凭 token 识别邮箱（BR-03.2）。

#### C.3 操作流程（含页面跳转）

主流程：
1. 用户点邮件底部 "Unsubscribe" 链接 → 浏览器打开退订落地页（URL 带签名 token）。
2. 落地页校验 token（合法且未过期）→ 解析出目标邮箱 → 显示**确认态**："Unsubscribe from marketing emails?" + 邮箱 + Unsubscribe 按钮。
3. 用户点 Unsubscribe → 调退订接口（传 token / 解析出的 email + `source=email_unsub`）。
4. 后端将该 email 的 status 置为 unsubscribed → 落 unsubscribe 凭证（即时生效，BR-05）。
5. 落地页切换为**成功态**："You've been unsubscribed" + 说明"仍会收到订单与账户邮件" + Back to Looply。

分支流程：
- token 非法 / 过期 → 显示错误态，引导用户登录后在偏好中心管理（或重新获取退订链接）。
- 该 email 已是 unsubscribed → 幂等，直接显示成功态。

#### C.4 校验规则

| 字段 | 规则 | 校验时机 |
|------|------|------|
| token | 签名有效、未过期、未被篡改 | 落地页加载时 + 退订提交时（后端二次校验） |
| email | 由 token 解析得出，不接受 URL 明文传入 | 后端 |

#### C.5 异常处理

| 异常 | 处理 |
|------|------|
| token 非法/篡改 | 错误页 "This link is invalid"，引导登录管理偏好 |
| token 过期 | 错误页 "This link has expired"，引导登录管理偏好 |
| 重复退订 | 幂等，显示成功态 |
| 退订接口失败 | 保留确认态 + 提示重试 |

#### C.6 技术说明

- 退订 token 须签名防伪造、防重放（具体签名方式、有效期待与安全方确认，见待确认问题）。
- 退订**不依赖账户**：未注册邮箱同样可退订，只认邮箱。
- 退订须即时生效（CAN-SPAM 允许 10 工作日，Looply 目标即时，最迟 24h）。

#### C.7 设计要点：不做空头承诺

- 退订页**不引导"管理偏好少收点"**——本期偏好中心只有营销总开关、无频次/分类控制，不承诺没有的功能。
- 成功态**不放 Resubscribe 按钮**——免登录下一键重订有他人代订的 opt-in 合规风险；想重订自行去页脚/弹窗。
- 成功态保留"仍会收到订单与账户邮件"说明（准确反映事务邮件不受影响）。

#### C.8 UI 关联

- PC：`PC Web 触点 > ④ 邮件退订落地页`（确认态 / 成功态）
- Mobile：`Mobile Web 触点 > ④ 退订页`（确认态；成功态同 PC，仅布局适配）

### 模块 D：注册关联认领（机制）

> 类型：机制型。无独立页面，由注册流程触发的后台机制。

#### D.1 功能描述

注册模块本身**无订阅功能**、不采集营销订阅。本订阅模块监听注册事件，当某邮箱注册账户时，把该邮箱**已有的订阅记录**关联到新账户（回填 user_id），实现"访客先订阅、后注册"的平滑衔接。

#### D.2 触发条件

- 用户用邮箱完成注册（注册成功事件）。

#### D.3 处理流程

| 场景 | 处理 |
|------|------|
| 注册邮箱**已有**订阅记录 | 将该订阅记录的 `user_id` 从 null 回填为新账户 ID（一次 UPDATE）；订阅状态原样保持（不降级，已订阅不被覆盖）；历史凭证的 user_id 同步回填。**不新增同意凭证**——关联认领不改变同意状态。 |
| 注册邮箱**无**订阅记录 | 什么都不做，**不创建"未订阅"行**。用户日后可在页脚/弹窗/偏好中心主动订阅。 |
| 换邮箱注册（新邮箱无订阅记录） | 视作"无记录"场景，不建行。旧邮箱的订阅记录保持 user_id=null 独立存活。 |

#### D.4 规则说明

- **不降级原则**：注册流程的任何默认值都不得把已订阅覆盖为未订阅（BR-03.1）。
- **关联认领不写凭证**：consent_record 只记同意的授予与撤销；回填 user_id 是数据归属变更，不是同意事件，因此 source 枚举中**没有** register/link_account。
- **注册不采集订阅**：注册页不提供营销订阅勾选项、不询问营销同意（BR-06 / UC-01）。
- **与 A.6.1 实时反查的分工**（两个机制各管一段，不重复）：
  - **订阅写入实时反查（A.6.1）** 管的是"订阅发生时，该邮箱**已经**注册了"——未登录订阅也能当场带上 user_id。
  - **注册事件回填（本模块）** 管的是"订阅发生时该邮箱**还没**注册、**之后**才注册"——注册成功事件触发，把先前留空的 user_id 补上。
  - 顺序示意：先订阅后注册 → 走 D 的事件回填；已注册再订阅 → 走 A.6.1 实时反查。

#### D.5 异常处理

| 异常 | 处理 |
|------|------|
| 同邮箱存在多条订阅记录（理论不应发生，email 为主键） | email 唯一主体约束从根本避免；如出现，以唯一约束拒绝重复写入 |
| 回填时账户已被删除 | 关联失败记日志，订阅记录保持原 user_id=null |

#### D.6 技术说明

- 本模块通过监听**注册成功事件**（或注册流程调用关联钩子）实现，注册模块不感知订阅逻辑细节。

### 模块 E：同意凭证记录与审计（机制）

> 类型：机制型。无独立页面，每次同意变更自动落库；调取展示见模块 F。

#### E.1 功能描述

每次订阅状态变更（订阅 / 退订）都生成一条**不可篡改**的同意凭证，记录完整的合规举证信息。这是法务底座，与订阅状态管理同期上线。

#### E.2 触发条件

- 任一入口的订阅写入（模块 A）。
- 偏好中心开关切换（模块 B）。
- 邮件一键退订（模块 C）。

#### E.3 凭证字段

| 字段 | 含义 | 来源 |
|------|------|------|
| id | 凭证唯一 ID | 系统生成 |
| email | 关联邮箱 | 动作主体 |
| user_id | 账户 ID（可空快照） | 动作发生时的登录态，未注册为空 |
| action | 动作类型（见枚举） | 业务动作 |
| from_status | 变更前状态 | 系统记录 |
| to_status | 变更后状态 | 系统记录 |
| source | 触发来源（见枚举） | 入口固定 |
| ip | 操作 IP | 请求解析 |
| device | 操作设备 UA 快照（如 "iPhone 15 · iOS 18 · Safari"） | 请求解析；**审计字段，非推送 token** |
| created_at | 动作时间（不可篡改） | 系统生成 |

#### E.4 枚举定义

**action（动作类型）**：

| 枚举值 | 含义 | 触发时机 |
|------|------|------|
| `subscribe` | 订阅（授予同意） | 入口订阅、偏好中心开 |
| `unsubscribe` | 退订（撤销同意） | 邮件退订、偏好中心关 |

> 关联认领（link_account）不进此表，故 action 仅两值。

**source（触发来源）** —— 比订阅记录的 source 多覆盖退订来源：

| 枚举值 | 含义 | 适用动作 | 本期 |
|------|------|------|:---:|
| `footer` | 页脚订阅框 | subscribe | ✅ |
| `popup` | 订阅弹窗 | subscribe | ✅ |
| `preference` | 偏好中心（开或关） | subscribe / unsubscribe | ✅ |
| `email_unsub` | 邮件底部退订链接 | unsubscribe | ✅ |
| `bounce` | 硬退信系统退订 | unsubscribe | ⏸️ 二期 |
| `complaint` | 垃圾投诉系统退订 | unsubscribe | ⏸️ 二期 |

> 二期 bounce/complaint：硬退信、垃圾投诉这类非用户主动的系统抑制，归 EDM 抑制列表能力，本期 source 不含此两值。

#### E.5 规则说明

- **不可篡改**（BR-04）：凭证只追加不修改不删除。
- **未注册也记**：未注册访客的订阅/退订同样落凭证（email 即可，user_id 空）。
- **可检索**：按 email 或 user_id 检索，供后台与合规调取。
- **留存期**：待法务确认（见待确认问题）；删除账户时凭证按合规留存要求处理（举证 vs 删除权平衡）。

#### E.6 异常处理

| 异常 | 处理 |
|------|------|
| 凭证落库失败但状态已变更 | 状态变更与凭证写入应在同一事务，失败整体回滚，保证"有变更必有凭证" |

|------|------|
| 订阅状态存储（email, status） | 营销邮件组装（含类型：降价/促销/EDM） |
| 同意凭证审计 | 发送前调用本模块查询 |
| 回答"能不能发"（订阅状态） | 决定"发什么、怎么发、发哪种类型" |
| 提供退订能力与落地页 | 邮件模板规范、实际发件 |

#### G.3 处理流程

1. EDM 准备发送营销邮件 → 调用本模块查询接口（按 email / user_id）。
2. 本模块返回该 email 的订阅状态。
3. 已订阅 → EDM 发送；已退订 → EDM 不发（事务邮件不经此判断，强制送达）。
4. 邮件含退订链接 → 用户退订回到本模块写入（模块 C）。

#### G.4 规则说明

- 事务类邮件不经过此判断，强制送达（BR-02）。
- 本模块只读暴露状态，不感知消息类型。
- 合规举证链路起点在本模块（同意凭证 + 退订凭证）。

#### G.5 风险约束

- 本模块无法强制下游严格遵守查询结果，需在接口契约与上线评审中约束 EDM"必须先查询后发送"，并辅以发送日志审计（见风险 R-09）。

### 3.1 上下游系统依赖

| 依赖项 | 说明 | 协同方 |
|------|------|------|

### 3.2 外部服务依赖

- **邮件服务商（ESP）**：营销邮件发件、退订链接承载。发件归 EDM 模块，本模块提供退订能力与状态。需确认 ESP 选型、退订 token 签名与回调方式。

### 3.3 风险与应对

| 编号 | 风险 | 影响 | 应对 |
|------|------|:---:|------|
| R-01 | 默认勾选营销同意触发合规风险 | 高 | 强制 opt-in，不预勾选（BR-06） |
| R-05 | 同意凭证缺失，合规无法举证 | 高 | 每次变更落不可篡改凭证，与状态变更同事务（BR-04） |
| R-06 | 跨端同意状态不一致 | 中 | 以 email 为唯一数据源，进入实时拉取（BR-03） |
| R-09 | EDM 发送前未调用查询，绕过订阅状态发营销 | 高 | 接口契约约束 + 上线评审 + 发送日志审计 |
| R-10 | Email 无类型细分，退订即全量退营销 | 中 | 已知约束 AC-01；EDM 上线后扩展渠道内类目，结构已预留 |
| R-11 | 同邮箱多次订阅/注册产生重复或合并冲突 | 中 | email 唯一主体 + 注册合并去重 + 状态不降级（BR-03.1） |
| R-12 | 未注册邮箱涌入但永不注册，列表/凭证膨胀 | 低 | email 可独立存活；运营监控未注册占比，必要时清理长期无活动邮箱 |
| R-13 | 退订 token 被伪造/重放 | 高 | 签名 token + 过期校验 + 防重放（待安全方确认方案） |
| R-14 | 脚本批量注入假邮箱 / 对他人邮箱订阅轰炸 | 中 | 订阅入口接口限流：单 IP+设备 24h 限 5 次，超限 429（A.11）；double opt-in、人机验证列二期 |

## 四、版本规划

### 4.1 当前版本（MVP / P0）范围

- C 端订阅入口：页脚订阅框 + 订阅弹窗（写入 + 来源枚举）
- 偏好中心：查看 / 开 / 关 Email 营销订阅（单总开关）
- 邮件一键退订：免登录落地页（签名 token）
- 注册关联认领：邮箱已有订阅记录则回填 user_id（注册不采集订阅）
- 同意凭证记录与审计（合规举证）
- 订阅管理后台：列表 + 统计 + 凭证调取（只读）
- 对外订阅状态查询（供 EDM 调用）
- 跨端订阅状态同步（email 为唯一源）

### 4.2 后续迭代方向（二期）

| 方向 | 说明 |
|------|------|
| Push 渠道 | 权限引导、OS 状态反映、App 内细分开关（push_subscription 表，主键 user_id+device_token） |
| SMS 渠道 | TCPA express written consent（sms_subscription 表，主键 phone） |
| 站内信 / 通知中心 | 站内通知聚合，按类目分组 |
| 系统自动退订 | 硬退信(bounce) / 垃圾投诉(complaint) 抑制列表（source 扩 2 值，归 EDM 协作写入） |

| 类目×渠道矩阵 | 精细化"留提醒、关促销"，Email 内类型细分 |
| 提醒频率管理 | 逐条订阅源的频率控制 |

> **二期数据结构已在 ER 图预留**：push/sms 各自独立主键、靠 user_id 关联，扩展加表不改既有表结构（BR-20）。

## 五、数据与埋点

### 5.1 关键埋点事件（建议）

| 事件 | 触发点 | 用途 |
|------|------|------|
| subscribe_submit | 任一入口提交订阅 | 各入口订阅转化（含 source 维度） |

### 5.2 成功度量指标

- 各入口订阅转化（footer/popup/preference 分布）
- 退订率（按来源归因 email_unsub vs preference）
- 退订生效时延（目标即时）、同意凭证完整率（应为 100%）

> 埋点字段中的 source 维度与 consent_record.source 口径一致，便于归因分析。
