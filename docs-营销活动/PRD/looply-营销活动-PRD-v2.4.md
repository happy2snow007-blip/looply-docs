# 一、概述

## 1.1 背景与目标

looply 作为面向美国+香港市场的二手奢侈品 B2C 平台(三方+自营商家入驻),V1 阶段需要具备基础促销能力驱动转化。本期参考 Shopify discount 模型,仅落地 **Amount off products(按商品/品类/品牌减价)** 一种促销类型,由平台运营配置、平台承担优惠成本。

目标:
1. 运营可配置自动折扣与优惠码两类触发的商品减价活动,多市场按币种独立控制力度
2. 买家在商详/购物车/checkout/订单详情看到一致、合规的促销价格与优惠明细
3. 资损三道防线落地:事前(配置试算拦截+封顶/限次)、事中(实付兜底+核销原子扣减+到手价监控)、事后(退款回滚+一键熔断)

## 1.2 不做什么(V1 明确边界)

| 不做项 | 说明 |

| 商家自建促销(商家出资、账单结算) | V2;V1 仅平台运营配置、平台出资(A1) |
| 预算池封顶(budget_total/spent) | 字段已预留,V1 不落逻辑 |

| 订单级"整单减一次"(真正意义的满减) | **V2**。V1 的满额/满件只是**门槛**,达标后仍按商品逐件减免;运营配置时须注意二者区别 |
| 部分退款的优惠重算/追回 | V1 部分退款不回滚不重算(D3);依赖订单改价能力,V2 精细化 |

| **(v2.2)Sale 专题落地页 / Collection 快筛位 / 商品卡 Sale 角标** | 不做。露出 = 搜索结果页筛选;Collection 抽屉筛是零配置动态生成、会自动带上,属架构结果不是需求项 |
| **(v2.2)全站三套「原价」口径收口** | **单独立项**,不并入本期(营销 / Collection / 商详 / 首页 Feed 各自的商品卡取价口径不一致) |

| **(v2.4)营销侧生成短链、二维码、点击统计** | **不做**。短链生成、UTM 配置、二维码、点击与独立访客统计**全部由短链服务承载**,运营在「短链管理」完成;营销侧只产出含 code 的链接(§2.2.6) |

## 1.3 用户角色

| 角色 | 端 | 职责 |
|---|---|---|
| 平台运营 | 运营后台 | 配置/发布/暂停/结束促销活动;处置到手价告警;查看核销记录 |
| 买家(Buyer) | C 端(APP/PC) | 浏览促销价、输优惠码、下单享受折扣、查看订单优惠明细 |

## 1.4 核心场景

1. **配置发布**:运营新建折扣(选触发方式/折扣值/圈选商品/投放市场/使用条件/生效时间)→ 保存前价格试算拦截确认 → 发布生效
2. **C 端曝光转化**:买家商详页看到到手价+划线原价+促销标签 → 加购(购物车行级优惠+汇总)→ checkout 输码 → 试算(门槛/限次/封顶)→ 支付
3. **核销与回滚**:支付成功订单事件驱动原子核销(计数+1);整单退款事件驱动核销回滚(计数-1、限次释放)
4. **监控处置**:系统扫描在售商品到手价,降幅超阈值落告警 → 菜单角标提示 + 飞书群聚合推送 → 运营在价格监控排查计算链路 → 一键暂停活动/标记处理/忽略
5. **(v2.2)降价商品可被筛出**:活动开始 / 商品上架即命中活动 / 运营下调挂牌价 → 系统判定 Sale 资格成立并驱动商品域打标 → 买家在搜索结果页筛「Sale」能找到它;活动结束或 N 天窗口到期 → 自动摘标
6. **(v2.2)按到手价排序**:买家在搜索结果页选 `Price: Low to High` → 搜推按索引中的到手价排序(营销负责保证索引里的值随价格变化更新)
7. **(v2.2)下游统一取价**:商详 / 商品卡片向营销取一次,即拿到 到手价 + 减免 + 划线价 + Save + 生效折扣的规则变量,无需再拼第二个来源
8. **(v2.4)链接触达转化**:运营为优惠码活动生成含 code 的链接 → 复制到「短链管理」生成投放短链 → 投放(EDM / 社媒 / 私域)→ 买家点击进入落地页,码自动跟随 → 浏览加购 → 进 checkout **自动生效、无需手输** → 支付成功后该码自动清除

## 1.5 全局页面流转

**运营端**(营销中心):
```
促销活动列表 → 新建折扣 → (价格试算确认弹窗) → 返回列表
促销活动列表 → 活动详情(基本信息 Tab / 核销记录 Tab) → 编辑折扣
促销活动列表 → [结束活动弹窗] [删除弹窗] [优惠码链接弹窗]
活动详情 → [优惠码链接弹窗] → (复制链接后转至「短链管理 → 创建运营短链」生成投放短链)
促销打标设置(营销中心二级菜单,与促销活动并列)→ 配置最小降幅门槛 / Sale 保持天数
价格监控(一级菜单,与「营销中心」分组平级)→ 告警列表 → 排查抽屉(Drawer) / 监控设置弹窗
促销活动列表 告警轻量入口 → 价格监控
```

**C 端**(仅标注营销触点,页面本体归各自模块):
```
优惠码链接(投放短链)→ 落地页(首页 / 该活动的 Collection),码自动跟随
  ↓
商详页(到手价 + 促销标签)
  → 购物车(行级折后价 + Subtotal/Discount 汇总)
  → checkout(优惠码输入与 chip + 订单摘要 Subtotal/Discount)
  → 支付
  → 下单成功页 Order Confirmed(优惠透传)
  → 订单详情(优惠快照;退款后按实退回冲)
```

## 1.6 术语说明

| 术语 | 定义 |
|---|---|
| 促销活动 / 折扣(discount) | V1 采用 1:1 简化:一个活动 = 一条折扣规则(promotion 与 promotion_rule 一一对应)。运营视角只感知"折扣活动"一个概念 |
| 自动折扣(auto) | 命中圈选商品即自动生效,无需输码 |
| 优惠码(code) | 买家在 checkout 输入优惠码触发;V1 一码通用 |
| 到手价 | C 端展示层的单品折后价 = 原价按**自动折扣**计算的结果;优惠码、用户级限次、订单门槛不计入,以提示形式表达 |
| 试算 | checkout/购物车的订单级优惠计算:带买家身份(登录账户或结算邮箱,§2.8.1),判定门槛/限次/封顶与同商品取优,输出可用优惠、减免额与**行级分摊明细** |
| 核销 | 支付成功后对一次优惠使用的计数记录(promotion_redemption),不记金额 |
| 回滚 | 整单退款后释放该次核销:status→reverted、已用次数-1、限次释放 |
| 不叠加(V1 硬性) | 同一商品行同时命中多条折扣时,**只取优惠最大的一条**生效;一单内不同商品各自享受各自命中的折扣(等同分开下单)。V1 不提供任何叠加配置项 |
| 最大优惠封顶 | percentage 折扣单件最大减免金额,按市场币种录值 |
| 挂牌价(listing_price) | 商品在本市场的平台标准售价,**未计任何折扣**;是划线价、到手价与降幅计算的共同基准 |
| 到手价 | 挂牌价扣除自动折扣减免后的价格;**任何在售商品都有到手价**,无折扣时 = 挂牌价(§2.8.2 规则一) |
| 划线价 | C 端展示的 line-through 价格;**有折扣时 = 挂牌价、无折扣时 = 对比价**(见 §2.4)。**取值必须真实、不得虚构参考价**(FTC reference pricing 要求);本期 C 端**不出现合规说明文案**(设计稿未含,D4) |
| Save | 划线价 − 现价;两种场景取值见 §2.4 口径表 |
| **促销优惠金额** | v2.2 新增。**单品对外输出项**:挂牌价 − 到手价,无折扣时 = 0(§2.8.2)。与 §2.12 成因判定、§2.8.3 规则二里说的「减免额」是同一个量——那两处描述的是计算过程,本词专指对外输出的那个字段 |
| **Sale 资格** | v2.2 新增。某个在售商品当前是否处于「降价中」。有资格 → 该商品被打上 Sale 系统标签;无资格 → 摘标(见 §2.11) |
| **折扣型** | Sale 资格的一种成因:到手价 < 挂牌价,即被自动折扣打下来了 |
| **挂牌价下调型** | Sale 资格的另一种成因:当前挂牌价低于上一次记录的挂牌价,且降幅达到门槛 |
| **价格状态基线** | v2.2 新增。系统为每个在售商品 × 市场持久保存的一组价格状态(上次/当前挂牌价与到手价、最近降价时间、当前 Sale 资格与成因),供环比判降、Sale 维护与对外供给共用(见 §2.11) |
| **最小降幅门槛** | 挂牌价下调型的判定门槛,低于该幅度的降价不算 Sale。全局系统配置项 |
| **Sale 保持天数(N)** | 挂牌价下调型 Sale 的有效期。全局系统配置项 |

## 1.7 多语言支持

本模块为混合模块:**运营后台部分(促销活动管理、价格监控)仅面向内部运营,本期仅中文,不接入多语言**;以下三段仅覆盖 C 端部分。

**A. 静态 UI 文案**:C 端营销相关静态文案(促销标签模板、优惠码输入区按钮与校验提示、订单摘要行标题、合规说明等类别)由前端语言包实现(语言包落地,运营可在多语言后台查看/修改)。

**B. 动态业务内容 — 翻译服务接入**

本模块**自身产生**、需多语言的业务字段只有「活动名称」一项。按多语言 v3.2 标准流程接入:**先建卡 → 再注册字段 → 保存时写入翻译服务触发 AI 翻译**。

**接入判定口径(D5)**:**本期及未来有可能在 C 端展示的自产文本,一律接入**,不以"当期是否已在页面上出现"作为接入与否的依据。理由:接入是一次性的建卡+注册字段成本,而漏接的代价是——未来某个版本决定展示时,存量数据没有译文、只能补跑批量翻译并人工校对。因此 `promotion_name` **本期虽不在 C 端任何位置展示**(D1 已定汇总与订单侧全程不透传活动名与码值,§2.4 促销标签也改由折扣配置拼接),**仍然接入**。

|---|---|---|
| 1 | 页面文案 | `page-promo` |
| 2 | 促销活动 | `promotion` |

- **优惠码 `code`**:优惠码是**标识符不是文案**,各语种原样展示——**不翻译、不建 resource_type、不进聚合组**(本版明确)

**v2.2 追加 · 本期新增输出的翻译判定**:本期(§2.11 / §2.10)新增的对外输出**不产生任何需要翻译的文本字段**——

- **Sale 标签的前台展示名**(`Sale` / `On Sale` 等)由 **Collection 侧「筛选维度管理」在建维度时配置并注册翻译**(类目管理 PRD §2.5),**不归营销域**,本模块不代列

# 二、需求详细描述

## 2.1 全局约定

1. **活动-市场 1:1(A6,硬性)**:一个折扣活动只属于一个市场,建活动第一步选定、创建后不可更改;活动的全部金额字段按所属市场币种显式录值,起止时间按所属市场本地时区判定。系统不做实时汇率换算,买家下单/结算/核销全程不用汇率(汇率模块仅可作运营录值时的等值参考)。
2. **时区口径(D5 / E4 本版明确)**:活动起止时间按**所属 Market 的「基准时区」**判定,营销侧不再单独配置(单市场化后原 timezone_mode 废弃)。

   **为什么要指名到字段**:market 模块有**三层**时区概念——Market 的**基准时区**、Market 的**业务日切时间**、Country 的**本地时区覆盖**。原文只写"按所属市场本地时区"会被理解成取国家级覆盖值(同一 Market 下多国家时会取到不同值,导致同一活动在不同国家生效时刻不一致)。本模块**统一取 Market 基准时区**,与国家无关。
   - 取值来源:market 模块的 Market 基准时区字段(具体字段名以 market 模块交付为准,**对接时需确认**)
   - 业务日切时间**不参与**活动生效判定(那是对账/报表口径)
   - 展示:运营端配置页在时间选择器旁标注当前市场的基准时区(如"美东时间 UTC-5"),避免运营按本地时间理解
3. **金额展示**:C 端所有促销金额按当前市场币种展示;运营端按市场行分币种录入与展示。
   **跨市场运营口径**:同一促销策略要在多个市场上线 = 在各市场分别建活动(列表"复制"操作支持以现有活动为模板复制后改所属市场与金额);活动名建议带市场标识。
4. **状态机(活动)**:

| 枚举值 | 含义 | 进入条件 | 退出条件 |
|---|---|---|---|
| draft 草稿 | 已保存未发布 | 新建时"存为草稿" | 发布→scheduled 或 active(按开始时间);删除→物理删除 |
| scheduled 未开始 | 已发布但未到开始时间,对 C 端不生效 | 发布时 now < start_at | 到达开始时间→active(定时任务);手动结束→ended |
| active 进行中 | 对 C 端生效 | 发布时 now ≥ start_at,或 scheduled 到达开始时间 | 暂停→paused;到达结束时间(定时任务)或手动结束→ended |
| paused 已暂停 | 临时停止生效(熔断) | 运营手动暂停 / 监控处置一键暂停 | 恢复→active;结束→ended |
| ended 已结束 | 终态,不可恢复 | 到期自动 / 运营手动结束 | **不可删除**——核销记录与规则配置需永久可追溯(§2.2.4) |

**scheduled 说明(本版新增)**:此前"已发布未到开始时间"的活动在列表显示为"进行中",与实际不生效相矛盾,运营易误判为已在打折。本版落为正式状态枚举:发布时按 `now` 与 `start_at` 比较落 scheduled 或 active;**活动需在到达开始/结束时间时自动流转状态**(scheduled→active、active→ended),流转实现方式由技术方案定。**流转延迟不影响 C 端价格正确性**——C 端候选集判定同时校验状态与时间,时间未到即使状态未流转也不会生效。scheduled 活动可编辑、可提前结束,**不可删除**(与 active/paused/ended 一致——**只要发布过就不可删除**,无论后续是什么状态)。
**"已暂停"歧义消除**:paused 是可逆态(可随时恢复为 active),ended 才是终态。运营端状态标签需带 Tooltip 说明:"可随时恢复为进行中;如需彻底停止请用「结束活动」(不可恢复)"。
**状态存储分层说明**:paused 物理上落在规则层(promotion_rule.status=paused,即监控"一键暂停"的写入点),活动容器层(promotion.status)保留 draft/scheduled/active/ended 生命周期;1:1 模型下运营看到的活动状态 = 容器状态与规则状态的合成展示。分层保留 V2 活动容器多规则时"暂停单条规则≠暂停活动"的演进空间。
5. **操作记录**:运营端编辑页/详情页默认含操作记录区(操作时间/操作人/操作类型/操作详情);操作类型枚举:创建、编辑、发布、暂停、恢复、结束、删除、监控处置(告警侧)。
6. **空值显示**:运营端表格空值统一"—";上限类字段留空 = 不限。
6.1 **引用类下拉的展示格式(A1,硬性)**:凡引用外部模块实体的下拉选项,一律按「**名称(ID)**」展示,不得只显示名称。覆盖:商品标签(如 `夏季新品(TAG10021)`)、Collection(如 `Summer Essentials(C10001)`)、用户标签(如 `新客(UT2001)`)、品类、品牌。**已选中项在回显、详情页、导出文件中同样带 ID。**
7. **删除约束(A5/A4)**:**仅 draft 草稿可删除**;已发布过的活动(scheduled/active/paused/ended)**一律不可删除**,需要停用请用「结束活动」(终态、不可恢复)。**结束/删除弹窗均展示影响信息(名称/ID/已核销次数)。**

### 2.2.2 新建 / 编辑折扣

**功能描述**:折扣活动的配置表单,7 分区;编辑页复用新建结构并追加操作记录区。
**前置条件**:新建无;**编辑仅 draft / scheduled / paused**——**进行中(active)的活动不可直接编辑**(A5,本版调整)。

**为什么进行中不让改**:改配置的瞬间 C 端仍在按旧规则成交,容易出现"运营以为改完了、买家还在用旧价下单"的窗口期,事后对账也说不清哪笔按哪版规则成交。改为强制走「**暂停 → 编辑 → 恢复上线**」三步,期间 C 端一律恢复原价,窗口期归零。
**各状态可编辑范围**:

| 状态 | 能否编辑 | 可改字段 | 说明 |
|---|---|---|---|
| draft 草稿 | ✅ | **全部字段** | 未发布,无任何约束 |
| scheduled 未开始 | ✅ | 见下方「已发布后可改清单」 | 已发布但未生效,改动不影响存量订单 |
| active 进行中 | ❌ **不可编辑** | — | **须先「暂停」转为 paused 再编辑**(A5) |
| paused 已暂停 | ✅ | 见下方「已发布后可改清单」 | 编辑完点「恢复上线」转回 active |
| ended 已结束 | ❌ | — | 终态 |

**已发布后可改清单**(scheduled / paused 适用):
- **锁定不可改**:所属市场(A6)、触发方式(自动/优惠码)、优惠码码值、折扣值类型(百分比/固定金额)
- **可改**:活动名称、适用商品圈选明细、适用用户、使用门槛、限次(总量**不得小于已核销次数**)、最大优惠封顶、生效起止时间
- 保存后触发保存前试算拦截(§2.2.3);恢复上线时触发监控增量扫描(§2.12)
**页面元素与字段**:

| 分区 | 字段 | 控件 | 必填 | 规则 |
|---|---|---|---|---|
| 基本信息 | 所属市场 market_id | 大卡片单选(美国/香港) | 是 | **第一字段**;决定全表单金额币种与生效时区;创建后锁定不可改(A6) |
| | 活动名称 promotion_name | 输入框 | 是 | 1-100 字符;作为**订单快照(rule_name)与运营后台识别**来源,**不直接用于 C 端展示**(C 端促销标签由折扣配置自动拼接,见 §2.4);建议带市场标识 |
| | 触发方式 trigger_type | 大卡片单选 | 是 | auto 自动折扣 / code 优惠码 |
| | 优惠码 code(trigger=code 时) | 输入框+随机生成按钮 | 是 | 手动输入或系统随机生成;防猜校验:长度 **8–32 位**、字母数字混合、禁纯连续序列(如 ABC12345 合法,12345678 拒绝);允许字符集 **A–Z / 0–9**(不含空格与特殊字符,避免 URL 拼接与人工转述出错);**全局唯一**——不同活动不可使用同一优惠码(含不同市场也不可重复);不区分大小写去重(统一转成大写后存储)。**买家侧匹配同样不区分大小写**——checkout 手输与 `/discount/{码}` 链接路径均**统一转大写后比对**,`autumn15` 与 `AUTUMN15` 等价;V1 不提供码级单独停用(码随活动暂停/结束即失效),promotion_code.status=disabled 为 V2 定向多码预留 |

**导入的解析与回显规则**:

4. 点「加入有效商品(M 件)」**只把有效的加进圈选**,无效的不静默丢弃也不阻塞整批

**指定买家为什么存邮箱、不存账号 ID(v2.4 新增)**

| 方案 | 取舍 |
|---|---|
| **存邮箱(本版采用)** | ✅ 运营手上本来就只有邮箱 ✅ **未注册的邮箱也能预先配置**——给潜在客户发专属券是这个功能的典型用法,存账号 ID 则这类活动根本配不出来 ✅ 与 checkout 未登录场景的邮箱识别口径统一(§2.13.5),不需要第二套识别机制<br>⚠️ **接受的代价**:买家换邮箱下单就享受不到,需运营重新配置 |
| 存账号 ID(否决) | 绑定更稳(买家改邮箱不影响),但**未注册邮箱配不了**,且依赖用户管理提供反查、买家未登录时还要先反查一次才能判 |

> 🔴 **已知敞口(v2.4 补,运营必须知悉)**:「指定买家」**只凭结算邮箱放行**——不登录、不验证码、不需要拥有那个邮箱。
> 也就是说**任何知道名单里某个邮箱的人,在 checkout 填上它就能享受**;若该活动同时是优惠码活动、链接被转发出去,扩散是无门槛的。
>
> **这是"存邮箱不存账号 ID"这一选型的必然代价**——本版接受,不做邮箱所有权验证(验证会把未注册邮箱排除在外,而"给潜在客户发专属券"正是本功能的主要用途)。
>
> **对运营的含义**:「指定买家」是一个**知道邮箱即可冒用的软名单,不是身份锁**。
> **大额专属活动务必同时配置总使用次数上限**,用总量封住资损上限。

**匹配口径**:邮箱**不区分大小写**(统一转小写后比对)。**不做** Gmail 的 `+后缀` 与点号归一化——那属于反薅规则,与本功能"指定给某个人"的语义无关,且会误伤真实使用别名收件的买家。

**买家邮箱的录入与解析规则(v2.4 补,比照本节「按商品 ID 导入」)**:此前只写了「一行一个、也支持逗号分隔」,运营从 Excel 粘一列进来,拼错域名的邮箱会被静默存下——那位买家永远享受不到,而详情页也看不出来。故补齐:

| 项 | 规则 |
|---|---|
| **分隔符** | 换行 / 英文逗号 / 中文逗号 / 分号 / 空格,混排均可 |
| **规范化** | 逐条 trim 首尾空白 → 统一转小写 |
| **去重** | 规范化后去重,重复项不报错、只提示已去重 N 个 |
| **格式校验** | 逐条校验;**不拦截整批**,分「有效 / 格式不正确」两组回显,不正确的逐条列出供运营排查 |
| **实时汇总** | 输入区下方显示「识别 N 个:有效 M 个,重复已去重 X 个,格式不正确 K 个」 |
| **数量上限** | **500 个**;超出提示「超出上限 500 个,请拆分活动」 |
| **编辑语义** | **全量覆盖**——编辑时输入框回显现有全部邮箱,保存即以当前内容为准,不做增量追加 |
| **保存口径** | **只保存有效邮箱**,格式不正确的不入库(与商品 ID 导入「只把有效的加进圈选」一致) |

> **格式校验的判定标准由技术方案定**,PRD 只要求至少能识别出「缺 @」「缺域名」「缺顶级域」这三类明显错误;
> 国际化域名(IDN)不作要求。

**门槛取值校验(A3,本版新增)**:满件数量**最小为 2**——填 1 等同于"无门槛",与 `min_type=none` 语义重复,运营配出来只会让人误以为有门槛;保存时校验拦截并提示"满件数量需 ≥2;若不设门槛请选「无门槛」"。

### 2.2.3 保存前价格试算(资损事前拦截,机制+弹窗)

**功能描述**:发布(含进行中编辑保存)前,系统对圈选商品逐市场试算到手价,弹窗展示抽样结果与风险,运营确认后才落库。
**触发条件**:点"保存并发布"/进行中活动"保存"。
**处理流程**:
1. 系统按当前配置计算圈选商品到手价(仅计本折扣;若该商品同时命中其他进行中折扣,按 §2.8.3 规则二的整单最优组合口径参与试算)。**带门槛的折扣按单件挂牌价判定门槛**(与 §2.8.2 规则一口径一致)——不达标的商品在试算结果中标注"需凑单达标",不计入其到手价
2. 弹窗展示:命中商品总数、抽样商品明细(现价/到手价/降幅)、降幅最大项
3. 存在降幅 > 全局监控阈值(§2.12)的商品 → 顶部警示,抽样必含该商品,降幅标红
4. 运营选择:返回修改 / 确认无误保存(弹窗操作记入操作记录)
**规则说明**:抽样规则=降幅 Top3(不足 3 件全量);试算仅为提示不强制阻断(V1 无审批流,确认权在运营)。
**异常处理**:试算服务超时 → 提示"试算暂不可用",允许"跳过试算继续保存"(记录操作日志"未试算发布")。
**UI 关联**:运营端原型 v24 · 价格试算确认弹窗(PriceCheckModal)。

### 2.2.6 优惠码链接(v2.4 新增)

**功能描述**:为优惠码活动生成一条**含优惠码的链接**,供运营对外投放。买家点击该链接后码自动跟随,进 checkout 时自动生效(机制见 §2.13)。

**前置条件**:活动 `trigger_type=code`,且状态 **≠ draft**。

**为什么草稿不给这个入口**:草稿尚未发布、码不生效,链接投出去必然失败,等于让运营发废链接。列表操作列与详情页头部在草稿态均不出现该入口。

**已暂停 / 已结束的活动保留入口,但弹窗内必须明示失效(v2.4 补)**:这两种状态的码同样不生效,链接投出去同样无效——但**入口保留**,因为运营有回溯需求(核对当时投的是哪条链接)。为避免运营顺手复制去投放,弹窗内需:
- 只读信息区展示**活动状态**
- 顶部出警示:「该活动当前不生效,链接点击后不会有优惠。」

**限定人群的活动同样需要警示(v2.4 补)**:`eligibility_type ≠ all` 时弹窗顶部提示「本活动限定适用人群,仅名单/标签内的买家可用,不建议公开投放」——否则运营容易把专属码当通用码投到社媒,所有点击者到 checkout 都是静默无优惠。

**入口**(与 §2.2.5 同一弹窗,两处复用):

| 位置 | 入口形态 |
|---|---|
| 促销活动列表 | 操作列「优惠码链接」 |
| 活动详情页 | 页头操作按钮「优惠码链接」;基本信息区同时展示该活动的优惠码链接(**不带落地页参数的基础形态**,行内可直接复制)。⚠️ **须标注「基础链接(不含落地页参数)」**——Collection 活动从弹窗复制到的链接是带 `?redirect=` 的,两者不同,不标注运营会复制错 |

**页面元素(弹窗)**:

| # | 元素 | 内容与口径 |
|---|---|---|
| 1 | 活动信息(只读) | 活动名称 / 优惠码 / **状态** / 所属市场 / 适用商品 / **适用用户** |
| 2 | 落地页 | 见下方「落地页取值范围」 |
| 3 | 优惠码链接 | **只读展示,不可手改**——由「活动 + 落地页」自动拼出;右侧「复制」 |
| 4 | 底部操作 | 关闭 / 复制链接 |

**落地页取值范围(本版定稿)**:

| 活动适用商品范围 | 可选落地页 | 默认值 | 能否修改 |
|---|---|---|---|
| **Collection 圈选(只圈了 1 个)** | 首页 / 该活动的 Collection | **该活动的 Collection** | ✅ 可改,两个选项均为合规选择 |
| **Collection 圈选(圈了多个)** | **仅首页** | 首页 | ❌ 锁定 |
| 全部商品 / 指定商品 / 品类 / 品牌 / 商品标签 | **仅首页** | 首页 | ❌ 锁定 |

> **(v2.4)为什么圈了多个 Collection 反而只能落首页**:§2.2.2 的 Collection 是**多选**(命中任一即适用)。
> 若活动同时圈了 A、B 两个集合,落地页落到其中任何一个,**另一个集合的商品对进来的买家就是不可见的**——
> 买家看到的页面与他能享受优惠的商品范围对不上。首页在这种情况下反而最中性。
> **禁用时的提示文案**:「本活动圈选了多个 Collection,落地页固定首页——落到其中任一个都会让另一些商品的买家看不到」。

- **为什么只有 Collection 能落到自己**:落地页与活动商品范围不一致时,买家进来选到的商品用不了这个码。Collection 有与活动范围**严格对应**的页面,其余范围没有(如按品牌活动落到搜索页,搜索结果集不等于活动圈定的商品集),故一律以**首页**兜底。
- **运营无需填写任何落地目标**:单 Collection 活动的落地目标取活动自身绑定的那个 Collection;多 Collection 与其余活动均落首页、无目标。因此**任何情况下运营都不需要手填 ID,也就不存在填错的可能**。
- 「指定商品」「搜索结果页」两种落地页**本版不做**(见 §1.2)。
- **落地页字段的必填标记**:仅「只圈了 1 个 Collection」的活动带必填星号(运营确有选择);其余活动该字段锁定、不带星号。
- **锁定时的提示文案**(非多选场景):「本期仅按单个 Collection 圈选的活动可改落地页,其余固定首页」。

**链接形态**:

```
https://{所属市场域名}/discount/{优惠码}[?redirect=/collection/{CollectionID}]
```

- 域名取活动所属市场的域名。**V1 各市场使用同一域名**(国家级独立域名是 market 模块 V1.1 的后续迭代,本版无多域名场景)
- ⚠️ **链接本身不携带市场标识**——因此买家点链接后所处的市场,**由站点既有的市场识别逻辑决定**,与链接无关。
  若识别出的市场 ≠ 活动所属市场,校验链第 2 项不通过 → 按 §2.13.3 的 T1 失败处理(属"不能自救"类,静默)。
  **这意味着跨市场投放会静默全失效**(如香港活动的链接被美国买家点开),且运营端看不到任何回流信号——已列入 §三 风险
- 落地页为首页时不带 `redirect` 参数

**操作流程**

| # | 步骤 | 说明 |
|---|---|---|
| 1 | 打开弹窗 | 列表操作列或详情页头部进入 |
| 2 | 确认/选择落地页 | 非 Collection 活动无需选择 |
| 3 | 复制链接 | 链接随落地页选择实时更新 |
| 4 | **到「短链管理」生成投放短链** | 见下方硬性说明 |

> 🔴 **第 4 步不可省略(硬性)**:营销侧产出的是**长链**,直接投放会**拿不到点击统计、独立访客、二维码与 App 唤起**。运营须将该链接复制到**短链管理 → 创建运营短链**,粘贴为「基础 URL」,在那里配置 UTM 参数并生成短链,**用短链对外投放**。
>
> **为什么营销侧不直接生成短链**:短链服务已具备完整的链接生成能力(基础 URL + 备注 + UTM + 生成),营销再造一遍是重复建设;且 UTM 取值规范与枚举由短链服务统一维护,营销侧不重复维护第二份、避免两处分叉。

**第 4 步的流程支撑(v2.4 补)**:该步骤被标为硬性,但**系统侧没有任何拦截或事后发现手段**——运营若直接投长链,归因、二维码、App 唤起全部拿不到,而埋点上报的"链接被点击"对长链同样会上报,运营看不出自己投错了。故弹窗内需:
- 用**提示条**(非 helper 小字)说明必须去短链管理包装,并说清不做的后果
- 底部提供**「去短链管理」**的跳转入口,把两步流程接上

**两个复制入口的分工(v2.4 明确)**:弹窗内有两处可复制,行为不同、不可混淆:

| 位置 | 行为 |
|---|---|
| 链接框右侧「复制」 | 复制,**弹窗不关闭**(便于运营改落地页再复制一次) |
| 底部「复制链接」(主按钮) | 复制并**关闭弹窗** |

**复制反馈(v2.4 补)**:复制是本弹窗唯一的产出动作,而剪贴板操作本身完全不可见——**成功须出 Toast「链接已复制」**;浏览器拒绝剪贴板权限时提示手动选中复制(链接展示块已支持整段选中)。

**异常处理**:

| 情况 | 处理 |
|---|---|
| 活动在弹窗打开期间被结束或暂停 | 已复制的链接在买家点击时按 §2.13 处理(码不生效),运营端不做额外拦截 |
| **运营改了活动圈选的 Collection**(v2.4 补) | **链接是复制走的静态字符串,平台不追踪已投放的链接**——已发出去的链接仍指向旧 Collection,买家进去看到的商品可能都用不了这个码。**编辑页改动 Collection 圈选时需提示**:「该活动已生成过投放链接,改动后已投链接的落地页将不再匹配」 |
| **落地的 Collection 被下线或删除**(v2.4 补) | 买家点击时**降级跳首页**,**码照常记录**——不因落地目标失效而丢掉优惠 |
| **`redirect` 参数被人为篡改**(v2.4 补) | 链接是公开投放的,任何人都能改这个参数。**仅接受站内 Collection 路径**,取值非法或指向站外一律**忽略该参数、降级跳首页**,码照常记录 |

**UI 关联**:运营端原型 v24 · 促销活动列表 / 活动详情页 · 优惠码链接弹窗。

## 2.3 运营端 · 价格监控(页面型)

> **v2.2 结构调整**:原 §2.3.4 扫描机制已移出为独立的 **§2.12**——它同时服务价格监控、促销打标(§2.11)与索引供给(§2.10.3),不只属于本节。本节只保留价格监控的三个页面级功能。

### 2.3.1 告警列表

**功能描述**:到手价降幅监控告警工作台(独立二级菜单),发现→排查→处置闭环。
**页面元素**:
- 头部:监控设置入口、导出
- KPI:今日新增告警 / 待处理 / 本周已处置 / 监控中活动数
- **成因列口径**:由 §2.12 扫描时判定并落 `cause_type`;它决定排查方向与可用处置动作,是本版新增的关键分流字段
- 筛选:状态、活动、市场、降幅区间、时间范围
- 列表列:告警时间、商品(名称+listing ID)、**成因**(折扣配置 / 挂牌价下调 / 两者叠加)、命中活动(可多条,**逐条标注「生效 / 未生效」**,B3;纯挂牌价成因时为空显示「—」)、市场、**价格对比(按类型区分基准:cumulative=原价→当前到手价;sudden_drop=上次到手价→本次到手价,辅注原价)**、**降幅**、状态、操作(排查;pending 另有忽略)
- **降幅列口径(本版调整)**:原独立的"类型"列已取消,比较基准直接写进降幅列——第一行是触发本次告警的那个降幅(含基准与阈值),第二行是另一维度的参考值:
  - cumulative:`较原价 -55% /阈值50%`(单行)
  - sudden_drop:`较上次 -25% /阈值20%` + 第二行 `较原价 -40%`(参考,未超阈值不显示阈值)
  取消独立类型列的原因:"类型"本身是抽象命名,运营看了仍需再查比较基准;把基准写进数据列后信息自解释,页面也少一列。类型名**仅保留在筛选器中**(排查抽屉内不展示类型,抽屉以"成因"与"价格对比"表达),措辞统一为大白话:`比原价降太多` / `比上次降太多`(枚举 key `cumulative` / `sudden_drop` 不变)
- 筛选增加:告警类型、**成因**
**状态机(告警)**:

| 枚举值 | 含义 | 进入条件 | 退出条件 |
|---|---|---|---|
| pending 待处理 | 新告警 | 扫描发现降幅超阈值且该商品+市场无未处置告警 | 处置→resolved/ignored |
| resolved 已处理 | 已处置 | 运营"标记已处理"(备注必填);记录处置动作/人/时间 | 终态 |
| ignored 已忽略 | 预期内降幅 | 运营"忽略"(列表行或抽屉内) | 终态 |

**告警类型(双阈值监控)**:

| 枚举值 | 含义 | 触发条件 | 记录内容 |
|---|---|---|---|
| cumulative **比原价降太多** | 深折监控 | 到手价相对**商品原价**的累计降幅 > 累计降幅阈值(默认 50%) | 原价/到手价/累计降幅/阈值快照/链路快照 |
| sudden_drop **比上次降太多** | 突变监控(捕捉折扣力度调整等配置变更导致的价格跳水) | 当前到手价相对**上一次扫描到手价**的单次降幅 > 环比降幅阈值(默认 20%),即使累计降幅未超阈值 | 上次到手价(prev_final_price)/当前到手价/环比降幅(change_pct)/阈值快照/链路快照 |

**告警生成与去重规则**:系统按 §2.12 的监控范围计算在售商品各市场的到手价,按上表双阈值分别判定并落告警(一次判定可同时触发两类)。**环比比较的基准 = 该商品该市场上一次计算得到的到手价**。同一商品+同一市场+**同一告警类型**已存在 pending 告警时不重复生成,更新该告警至最新;处置后再次超阈值则生成新告警。
**UI 关联**:运营端原型 v24 · 价格监控列表页(含 4 空态)。

### 2.3.2 告警排查(抽屉)

**功能描述**:单条告警的排查与处置,核心是价格计算链路拆解。
**页面元素**:商品/市场/告警时间/**成因**/**价格对比**(按类型区分基准,同列表列口径)/累计降幅(对比阈值)/突降幅度(比上次降太多类:上次到手价→当前到手价+单次降幅,对比环比降幅阈值)/状态与处置记录;**不展示"告警类型"**(类型只在列表筛选器出现);**价格计算链路表**(环节/命中规则/变动金额/小计,来自 calc_snapshot 快照,非实时重算;纯挂牌价成因时链路只有"挂牌价"一个环节);主因初判提示;处置区(仅 pending)。

**处置区按成因分流(本版新增)**:

| 成因 | 处置区展示 |
|---|---|
| `discount` / `both` | **只提供「实际生效那一条」活动的暂停入口**(B3 本版修正) + 处置备注 + 标记已处理 + 忽略本条;`both` 另加提示"本次降幅同时含挂牌价下调,暂停活动后仍需到商品后台核实商品价" |
| `listing_price` | **不出「暂停活动」按钮**(无活动可暂停或活动并非成因) → 改为「查看商品」(跳商品后台该 listing)+ 处置备注 + 标记已处理 + 忽略本条;并显式提示:**挂牌价异动需到商品后台核实,营销侧无法直接处理** |

> **B3 口径澄清(本版新增)**:V1 一律不叠加 ⇒ 一个商品**最终只生效一条**折扣,但它可以**命中多条**(只是取优惠最大的那条生效)。所以「命中活动」列可能有多条,需**逐条标注「生效 / 未生效」**;处置区**只对生效那一条**提供暂停入口——暂停未生效的活动对当前降幅毫无作用,反而会误伤其他商品的正常促销。

**处理流程**:
1. 一键暂停活动(仅 `discount`/`both`,且**只针对生效那一条**)→ 该活动 status→paused(即时对 C 端止损),告警记录 handle_action=pause_promotion;**告警不自动转已处理**——暂停后该商品可能落到原先"未生效"的次优折扣上、降幅仍可能超阈值,需运营确认后手动"标记已处理"
1.2 **三个处置动作(暂停 / 标记已处理 / 忽略)均需二次确认**(A6)
1.1 查看商品(仅 `listing_price`)→ 跳转商品后台;运营核实后回本页手动"标记已处理"或"忽略";若确认为误操作改价,由商品侧改回,下一轮扫描到手价回升即不再新增告警(已有 pending 告警仍需人工收口),handle_action=notify_product
2. 标记已处理 → 备注必填 → status→resolved,记录处置人/时间/动作
3. 忽略 → status→ignored(适用预期内深折,如清仓)
**异常处理**:暂停活动失败(已被他人结束等)提示并刷新;快照缺失时链路区显示"快照缺失,仅展示汇总"。
**UI 关联**:运营端原型 v24 · 告警排查抽屉(AlertDrawer)。

### 2.3.3 监控设置(弹窗)

**功能描述**:全局监控参数与告警通知渠道配置。
**字段**:

| 分组 | 字段 | 控件 | 必填 | 规则 |
|---|---|---|---|---|
| 阈值 | 累计降幅阈值 | 数字(%) | 是 | 默认 50,范围 1-95,全局唯一(按活动/品类覆盖 V2) |
| | 环比降幅阈值 | 数字(%) | 是 | 默认 20,范围 1-95,全局唯一(按活动/品类覆盖 V2) |
| 范围 | 监控范围 | 只读 | — | 固定"全部进行中活动命中的在售商品" |
| 通知 | 站内提醒 | 只读 | — | **常开不可关**:待处理告警数以红色角标展示在左侧「价格监控」一级菜单上 |
| | **飞书群通知** | 单选(开/关) | 是 | **V1 新增**。开启后每轮扫描若有新增告警,向指定飞书群推送一条汇总卡片 |
| | **Webhook 地址** | 输入框 + 发送测试 | 飞书通知开启时必填 | 取自飞书群「设置 → 群机器人 → 添加自定义机器人」;**页面仅展示脱敏值(仅尾部 4 位可见)**,存储方式由技术方案定;保存前可点「发送测试」向该群发一条测试卡片自验 |
| | 推送策略 | 只读 | — | 每轮扫描聚合推送一条,本轮无新增告警则不推送(见 §2.12) |

> **阈值命名与评审用语对照**:「累计降幅阈值」= 评审说的"**到手价与挂牌价**的降幅阈值";「环比降幅阈值」= 评审说的"**当前到手价与历史到手价**的降幅阈值"。两者本就是现有的两个阈值,本版只统一措辞、未新增阈值。
>
> **触发时双阈值留痕(B1)**:告警落库时**两个阈值都要快照**(`cumulative_threshold_pct` + `change_threshold_pct`),不能只存"触发类型对应的那一个"——事后复核要能还原当时的完整配置,否则改过阈值就说不清当时到底按什么判的。

**规则说明**:
1. 阈值修改即时生效于下一轮扫描;修改记录进操作日志。阈值与 Webhook 配置均为**全局系统配置项,不落 ER 业务表**。
2. **通知渠道选型依据**:采用飞书**群自定义机器人 webhook**(后端 HTTP POST 即可,无需申请应用权限、无需维护 token)。告警为广播型场景(发运营群),V1 不做定向 @ 责任人——那需要自建应用 `im/v1/messages` + 运营账号与飞书 user_id 映射,列入 V2。
3. **安全**:Webhook 地址属敏感配置——**页面只展示脱敏值(仅尾部 4 位可见)、不得在操作日志中留明文**;存储方式与飞书侧签名校验(secret)的启用由技术方案落实。
4. **失败处理(V1 简化)**:推送失败仅记系统日志,**不落业务表、不在告警记录上标推送状态**;运营通过「发送测试」自验配置是否可用。站内角标不依赖飞书通道,飞书不可用不影响告警本身。
**UI 关联**:运营端原型 v24 · 监控设置弹窗。**本版未改本弹窗**——促销打标的两个配置项归 §2.11.6 独立配置页,不并入本弹窗。

## 2.4 C 端 · 商详页与商品卡片营销展示(页面型)

**功能描述**:商详页与商品卡片的价格展示。**营销侧对任何在售商品都统一输出到手价**(无折扣时 = 挂牌价),商详据此决定展示促销价格组还是常规价格组。
**前置条件**:商品在售、当前市场在投放范围。**不再要求"必须命中折扣"**——未命中折扣同样要拿到到手价(§2.8.2 规则一)。

**页面元素**

**A. 商详页价格区**(以 PC 商详本期主帧 `looply PC 商详页 — 营销样式更新` 为版式依据)

价格区各元素**同一行横排**,自左至右**排列顺序固定**(D7-7):

| 序 | 元素 | 视觉形态 | 出现条件 |
|---|---|---|---|
| 1 | **现价(到手价)** | 行首、**大号加粗** | 恒有 |
| 2 | **划线原价** | 紧邻现价右侧、灰色 line-through | 按下方「划线价与 Save 口径」表有值才出 |
| 3 | **Save 徽章** | **浅紫底 pill**(圆角实底色块) | Save > 0 **且本行没有活动规则标签**才出(v2.2 改写,见下方互斥规则) |
| 4 | **活动规则标签** | **紫色描边票券形**(带**齿孔** + **虚线分隔**) | 命中折扣才出;文案按下方模板自动拼接,**不取活动标题** |

> **⚠️ v2.2 改写 · Save 徽章与活动规则标签互斥,同一行只出其一**:
> - **命中折扣(有活动规则标签)** → 出规则标签(`20% OFF`),**不出 Save 徽章**
> - **未命中折扣但有对比价** → 出 Save 徽章,不出规则标签(此时本就没有规则标签)
>
> **为什么互斥**:两者说的是同一件事——`20% OFF` 和 `Save $1` 都在回答"这件便宜了多少",同时出现是重复信息,还会让买家去核对两个数对不对得上。Badge 形态改造后规则标签已直接表达力度,Save 徽章在有折扣场景下不再必要。
>
> **两者仍是两种不同的视觉组件,不可用同一个组件实现**(D7-7)。Save 徽章 = **浅紫底 pill**、内容为金额差值(如 `Save $1`);活动规则标签 = **紫色描边票券形**(齿孔 + 虚线分隔)、内容为力度 Badge(如 `20% OFF`)。虽然改为互斥,但**两个组件都要保留**——各自服务不同场景。

**B. 价格区下方**:**税费说明行**——商详模块既有元素、非营销新增,但属**价格区版式的一部分**,营销改版后仍位于价格区正下方,**排版时不要漏排**(D7-7)。

> **本期不含以下元素**(D4 / D6):
> - **FTC 合规说明小字**(「划线价为本商品的标准列表价」)——PC 商详设计稿价格区下方只有税费说明行,无此文案位(D4)
> - **折扣率标签**(如 `-20%`)——设计稿只有**一个**票券形规则标签,折扣信息**只由活动规则标签一个元素承载**,不再是「折扣标签 + 活动规则标签」两个并列元素(D6)
> - **「用码另减」提示**(`Extra $X off with code XXX at checkout`)——PC 商详无此元素(D6)

**C. 商品卡片**(列表页 / 推荐位 / 搜索结果等):**现价 + 划线原价 + Save 徽章**,**无折扣标签**;样式**以各模块卡片设计稿为准**(D6)。

> 说明:本期商详改动稿中的推荐位卡片区域**位于画板高度之外、已被裁切,在画布上不可见**,是从基础版复制而来的残留结构,**不构成视觉规范**,不得作为卡片样式依据。

**活动规则标签的自动拼接(C3)**

C 端展示的促销标签**由折扣配置自动拼接生成**,不再直接取活动标题(`promotion_name`)。原因:活动标题是运营给自己看的管理名(如"夏季大促 · 箱包 8 折"、"618 返场"),既可能不含优惠信息、也可能与实际配置不符;买家需要的是"这个优惠到底是什么"。

**拼接模板**(按「使用门槛 × 折扣值类型」六种组合)。**下表英文即 C 端实际展示的源文案,开发按此实现**;其他语种由语言包基于这份英文产出:

| 使用门槛 | 百分比折扣 `percentage` | 固定金额折扣 `fixed` |
|---|---|---|
| 无门槛 `none` | `{P}% OFF` | `{Amount} OFF` |
| 满额 `amount` | `{P}% OFF {Threshold}+` | `{Amount} OFF {Threshold}+` |
| 满件 `quantity` | `{P}% OFF {N}+` | `{Amount} OFF {N}+` |

> **v2.2 改写(R3)**:由句子式(`Spend $300, get 20% off`)改为 **Badge 式**——`力度 + 门槛后缀`,`OFF` 全大写。原因见下方「为什么改 Badge」。

**变量取值**:`{P}` = `percentage_value`(**直接取值不换算**,该字段存的就是 off 比例)｜`{Amount}` = `fixed_amount`｜`{Threshold}` = `min_amount`｜`{N}` = `min_quantity`;金额按所属市场币种符号与语种数字格式渲染。

- **封顶不进标签(v2.2 改写)**:`max_discount_amount` **不再拼进规则标签**,有封顶与无封顶的标签完全相同(均为 `{P}% OFF`)。⚠️ **已知信息损失**:配了封顶 $100 的 20% 折扣,买家在标签上看到的仍是 `20% OFF`,单价高的商品实际减免会低于 20% 的预期。**该敞口已记入模块《待优化清单》**,后续若要表达封顶需另设承载(如商详价格区下方一行小字),不塞回 Badge——Badge 是窄组件,塞进去会截断
- **满件门槛 ≥2**(§2.2.2),故 `{N}+` 语义成立
- **门槛后缀只在有门槛时出现**,`min_type = none` 时标签只有力度部分

**六种组合渲染样例(验收基准)**:

| 组合 | 配置 | 英文(实际展示) |
|---|---|---|
| 无门槛 × 百分比 | P=20 | `20% OFF` |
| 无门槛 × 百分比 **+ 封顶** | P=20, Cap=$100 | `20% OFF` ← **与无封顶完全相同,封顶不体现** |
| 无门槛 × 固定 | $80 | `$80 OFF` |
| 满额 × 百分比 | 满 $300, P=20 | `20% OFF $300+` |
| 满额 × 固定 | 满 $300, $80 | `$80 OFF $300+` |
| 满件 × 百分比 | 满 2 件, P=20 | `20% OFF 2+` |
| 满件 × 固定 | 满 2 件, $80 | `$80 OFF 2+` |

> **为什么改 Badge**:句子式(`Spend $300, get 20% off`)在窄票券里必然截断,且与同行的 Save 徽章语义重叠——两个元素都在说"你能省多少"。Badge 式把标签压到 ≤13 字符,同时 §2.4 元素表已定「**有活动规则标签时不出 Save 徽章**」,两者不再打架。
>
> **溢出约定**:最长串 `$80 OFF $300+` 约 13 字符(原句子式最长 38 字符)。仍要求**单行不换行、超出按省略号截断**;具体最小宽度由设计定。
>
> **中文文案待定**:上表只给英文源文案(截图定稿)。Badge 形态的中文表达(`8折`?`8折 满$300`?)**尚未确定**,由设计 / 运营确认后补入,开发先按英文实现。⚠️ **不要沿用旧的折率换算规则自行拼中文** —— 旧规则是给句子式设计的(`满 $300 享 8 折`),Badge 形态下未验证。

**多语言口径(重要)**:规则标签是**「模板 + 变量」而非运营录入的文本**,因此:
- 模板本身走**前端语言包**(§1.7 A 段静态文案),各语种各写一套
- 变量(金额/百分比/件数)由前端按语种的数字与货币格式渲染
- **不进翻译服务**——它没有"原文"可翻,与 §1.7 B 段"折扣力度标签为计算值非录入文本、不接翻译"是同一口径


**下游取价改造要求(C1)**:商详 / 购物车 / checkout **不得再直接取商品挂牌价当展示价**,一律改为调用营销的到手价计算服务(§2.8)。

| 页面 | 改造前 | 改造后 |
|---|---|---|
| 商详 / 商品卡片 | 直接取 `listing_price` | 调 §2.8.2 规则一,取返回的**到手价**(无折扣时该值 = 挂牌价) |
| 购物车 | 行价直接取 `listing_price` | 调 §2.8.3 规则二(按勾选集合),取各行优惠与汇总 |
| checkout | 同上 + 码 | 调 §2.8.3 规则二(全量,含优惠码) |
| **搜索 / Collection 列表排序**(v2.2 新增) | 按挂牌价排序 | 按**到手价**排序。搜索 PRD §6.3 的「当前销售价」即到手价;取值来自 §2.10.3 索引供给 |
| **搜索 / Collection 价格筛选滑块**(v2.2 新增) | 按挂牌价区间筛 | 按**到手价**区间筛,与排序同口径 |

> **上面两行的实现归搜索 / Collection 模块**,营销侧只保证供给到手价(§2.10.3)。**两者必须同口径**,否则同页会出现两套价格:商品挂牌 $1,200 / 到手 $960,买家把滑块拉到 `$0–$1,000`——按到手价筛该出现、按挂牌价筛不出现,而他切到价格排序时又能在 $960 附近看到它。

> 营销侧已保证**任何在售商品都有到手价返回**(无折扣时 = 挂牌价、减免 = 0,见 §2.8.2 第 3 步),所以下游不需要写"有没有促销"的分支,统一取一个字段即可。

**划线价与 Save 口径**:⚠️ **v2.2 改写**——原表述为「价格展示逻辑归商详模块,营销侧只负责供给到手价」,自 v2.2 起改为:**数值由营销统一计算并输出**(到手价 / 减免 / 划线价 / Save,见 §2.8.2 与 §2.10),**展示版式仍归各页面**(这一屏摆不摆划线价、Save 徽章放哪、票券标签什么样式,由商详与各卡片模块按自己的设计稿决定)。**取值规则本身未变**,两种场景的取值:

| 场景 | 现价 | 划线价 | Save(**数值**) | Save 徽章(**展示**) |
|---|---|---|---|---|
| **有折扣**(促销优惠金额 > 0) | 到手价 | **挂牌价** `listing_price` | 挂牌价 − 到手价 | ❌ **不展示**——改由活动规则标签表达(v2.2) |
| **无折扣**(促销优惠金额 = 0) | 挂牌价 | 对比价 `compare_at_price`(有且 > 挂牌价时;否则不展示划线价) | 划线价 − 挂牌价 | ✅ 展示 |

> ⚠️ **「数值」与「展示」是两回事**:营销侧**始终输出** Save 数值(§2.8.2 / §2.10),供下游按需使用;**只是商详与商品卡在有折扣时不把它渲染成徽章**。别把"不展示"理解成"不输出"。

> **划线价口径已定案(2026-07-28)**:**有折扣时,划线价取 `listing_price`(挂牌价)**,不取 `max(listing_price, compare_at_price)`。
> **理由**:若按 max 取值,当对比价高于挂牌价时,`Save` 会把"零售参考价与平台售价的差"也算进促销优惠——那部分不是本次活动省下来的钱,属**虚增促销力度**,有 **FTC reference pricing 合规风险**。
> **举例**:原始零售价 $2,000 / 平台挂牌 $1,200 / 促销价 $1,000 —— 按本口径 `Save = $200`(本次活动真实省下的);按 max 口径 `Save = $1,000`(把"本来就比专柜便宜的 $800"也算成了促销力度)。
> 本模块 §2.4 与 §2.8.2 **均已按该口径写定,无待回改项**。

**展示规则**:
- 到手价口径 = §2.8.2 规则一(仅自动折扣、门槛按本商品挂牌价判定、取减免最大一条、不判用户与限次、封顶生效)
- **门槛类折扣(满额/满件)**:按 §2.8.2 规则一以**本商品挂牌价**判定门槛——**达标即计入到手价、改变价格位**(单买这一件就能享);**不达标**则不计入价格,仅以**活动规则标签**表达(如 `满 $100 减 $20`),引导买家凑单,此时价格区不出划线价与 Save 徽章
- **未命中任何自动折扣(减免 = 0)**:到手价 = 挂牌价,价格区走商详模块的常规价格组(现价 = 挂牌价、划线价 = 对比价、Save = 划线价 − 挂牌价),**不出活动规则标签**与促销价样式
- **商品列表页/推荐位等商品卡片**:同到手价口径展示**现价 + 划线原价**;Save 徽章按上方互斥规则(有折扣时不出)。样式**以各模块卡片设计稿为准**(D6)
- 适用用户限定(指定标签)的折扣:商详无登录用户上下文时按"可能可享"展示到手价,加购/结算按登录用户校验,不符合则该优惠不生效并提示(避免商详虚报);V1 商详不做用户级隐藏
- 活动暂停/结束/商品移出投放市场后,C 端即时恢复原价展示

**异常处理**:促销数据获取失败 → 降级展示原价(不阻塞商详),Save 徽章与活动规则标签一并不展示;到手价计算结果 ≥ 原价 → 不展示促销组(防错配反向展示)。
**UI 关联**:C 端 Figma 设计稿,本期帧见 **§七.1 帧索引**;本地 `UI/` 旧 html 仅历史参考,不作开发依据。

## 2.5 C 端 · 购物车营销展示(页面型)

**功能描述**:购物车行级与汇总层展示自动折扣优惠。**移动端与 PC 端版式不同**(D1 / D7-4),页面元素分端定义。

**页面元素**

**A. 商品行(两端一致)**

| 元素 | 说明 | 出现条件 |
|---|---|---|
| **现价** | 该行到手价(行级自动折扣**已含在行价内**) | 恒有 |
| **划线原价** | 灰色 line-through,口径同 §2.4 对照表 | Save > 0 才出 |
| **Save 徽章** | **浅紫底 pill**,与 §2.4 同一组件(D7-5) | Save > 0 才出 |

> 商品行**不出折扣标签**——设计稿两端购物车帧的商品行只有 Save 徽章(D6)。未命中折扣的商品行仅展示现价,无划线价与 Save 徽章。

**B. 优惠汇总:两端版式不同(D1 / D7-4)**

| 端 | 位置 | 构成 |
|---|---|---|
| **移动端** | **没有汇总区**,优惠体现在**吸底栏** | `Select All` 勾选框 + **合计金额** + **券图标徽章**(如 `-$40.00`)+ `Check Out` 按钮,横排一行 |
| **PC 端** | **Mini Cart 抽屉底部** | `Total` 行 + `Discount` 行(左侧标签,右侧**券图标 + 紫色负数金额**) |

**展示规则**:
- 购物车级试算 = 各行到手价汇总(§2.8.3 规则二,按勾选集合)
- 满额/满件门槛按**当前勾选进入结算的、可售的命中商品集合**合计判定(勾选/取消/数量变化/删行/商品转不可售即时重算),达门槛才计入 `Discount`(PC)/ 吸底栏券徽章(移动端)
- 不可售商品行**不计入**汇总金额、**不计入满额/满件门槛的合计判定**、不参与 `Select All`;但**其营销元素保留展示**(划线价与 Save 徽章随整行灰化,不隐藏)——不可售态的分组、灰化与移除交互归购物车模块
- 未达门槛的进度提示(如 `Add $X more to save $Y`)V1 以 UI 稿为准,未出则不做

**异常处理**:试算失败 → **PC** 隐藏 `Discount` 行、**移动端**隐藏吸底栏券图标徽章,行级降级为原价,不阻塞结算入口;进入 checkout 后以 checkout 试算为准。
**UI 关联**:C 端 Figma 设计稿,本期帧见 **§七.1 帧索引**(移动 `shopping cart-首屏`、PC `looply PC 商详页 — 购物车(含优惠券)`);本地 `UI/` 旧 html 仅历史参考,不作开发依据。
> ⚠️ PC 帧名里的「含优惠券」指的是底部新增的 **`Discount` 汇总行**,**不是输码入口**——购物车不提供输码入口,checkout 是优惠码的唯一输入位(§2.6)。

## 2.6 C 端 · checkout 营销功能(页面型)

**功能描述**:checkout 的商品行营销展示、优惠码输入与订单级优惠试算展示;**checkout 是优惠码唯一输入入口**(优惠码链接带来的码在本页**自动应用**,不改变"唯一输入入口"这一口径——买家仍只能在本页手动输码,见 §2.13)。
**前置条件**:当前市场与活动所属市场一致。**买家登录与否均可使用优惠码**——未登录时以结算页填写的邮箱作为买家身份依据(该邮箱为结算必填项,未注册者下单时静默建号),每人限次与适用用户标签在邮箱填写完成后判定,详见 §2.13.5。

> 🔴 **(v2.4)本条是规则变更,需要开发改造,不是文档层面的口径修正**
>
> **现状(2026-08-25 核实)**:未登录买家**可以输入优惠码**,但**配置了使用次数限制的码,系统会要求先登录才能核验**。
>
> **本版要求**:**登录不得作为在 checkout 使用优惠码的必要条件**。带限次的码同样要支持未登录使用,限次改为**按结算邮箱关联查询**(见 §2.13.5)。
>
> **为什么必须改**:强制登录卡在下单最后一步,是转化漏斗上最贵的一道门槛——买家已经填完地址、选好支付方式,却因为想用一个优惠码而被要求先去注册/登录,流失是直接的。而**登录并不能换来更强的限次保障**:平台本就允许未登录下单(下单时以结算邮箱静默建号),买家换个邮箱注册照样能再用一次,与未登录换邮箱的效果完全相同。**用确定的转化损失,换一个并不成立的风控收益。**

### 2.6.2 优惠码的不叠加规则(本版重写)

> **为什么不再是「单订单只能用 1 个码」**:优惠码的本质是「**需要输码才触发的折扣**」,它与自动折扣**同属候选折扣池**,受 §2.8.3 **同一套不叠加约束——每个商品行至多生效一条折扣**。约束的对象是「**商品行**」,不是「订单」。此前 v1.8 及以前写的「V1 单订单仅支持输入 1 个优惠码」,实际只描述了**单商品进入 checkout** 这一种场景,不能用来限制所有场景。**这不是放宽限制,而是把限制放回它本来的粒度上。**(D2)

**正确规则**:

| # | 规则 | 说明 |
|---|---|---|
| 1 | 码与自动折扣**同池竞争** | 二者一并参与 §2.8.3 最优组合求解,**每个商品行至多生效一条**(自动折扣或码,二选一取优) |
| 2 | **一单可以有多个码同时生效** | 前提是它们**作用于不同商品行**——与 §2.8.3「不同商品各享各的、等同于分开下单」是**同一条规则** |
| 3 | **单商品场景最多一个码生效** | 只有一个商品行 ⇒ 至多一条折扣 ⇒ 再输新码时,若新码更优则**自然替换**旧码。这是**最优组合求解的结果,不是为单商品写的特殊逻辑**,开发不需要单独实现「替换」分支 |

**每次 Apply 的处理顺序(硬性,按序执行)**:(D2)

| 步 | 动作 | 不通过时 |
|---|---|---|
| 1 | **校验该码自身**——按下方《优惠码校验链》**逐项按序**执行 | 命中第一条不通过项即返回对应文案(§2.6.4),**不继续校验、不加入已应用集合** |
| 2 | 通过后加入已应用集合 | — |
| 3 | **整单重新求最优组合**(§2.8.3,码与自动折扣同池参与) | — |
| 4 | 检查求解结果:该码是否**产生了实际减免** | 若被更优折扣挤掉、**不产生任何减免** → 按 §2.6.4 出**行内错误提示**(第 9 条 `You're already getting a better offer, so this code won't apply.`),**同样不加入集合**(避免 chip 显示一个无实际作用的码) |

#### 优惠码校验链(v2.4 新增 · 全模块唯一权威)

> **为什么要单列这一张表**:v2.3 及以前,校验项清单在 §2.6.2、§2.8.3、§2.13.3 **三处各写了一份**,项目集合与先后都不同。
> 而 §2.6.4 的九条文案是**互斥单条展示**的——先命中哪条就报哪条,三份清单会让同一个码报出不同的错。
> **本表是唯一权威,上述各处一律引用本表,不再自行罗列。**

| 序 | 校验项 | 依赖买家身份? | 不通过时的文案(§2.6.4) |
|---|---|---|---|
| 1 | 码存在、未停用、所属活动进行中 | 否 | 第 1 条 |
| 2 | 活动所属市场 = 买家当前市场 | 否 | 第 7 条 |
| 3 | 商品范围命中(订单内至少一个商品行) | 否 | 第 6 条 |
| 4 | 使用门槛达标(满额 / 满件) | 否 | 第 2a / 2b 条 |
| 5 | 总使用次数未用尽 | 否 | 第 3 条 |
| 6 | **每人限次未用尽** | **是** | 第 4 条 |
| 7 | **适用用户命中**(tag 标签命中 / email 在指定买家名单内) | **是** | 第 8 条 |

**执行口径(硬性)**:

- **按序执行,命中第一条不通过即返回**,不继续往下校验——这保证同一个码在任何入口报出的文案一致。
- **「依赖买家身份」的两项(6、7)在身份不可用时一律跳过、不判、不拒绝**,留待身份可用后补校(见下方两时点模型)。**不得因身份为空而拒绝应用或要求买家登录**(§2.6 前置条件)。
- **买家身份的取值口径**见 §2.8.1;其中 `eligibility_type=email` 一律以**结算邮箱**为准。

#### 两时点校验模型(v2.4 新增 · checkout 通用)

**适用范围:checkout 内的全部优惠码,不区分来路**——链接自动带入的码与买家手输的码走同一套。

| 时点 | 校验哪些 | 不通过时 |
|---|---|---|
| **T1 · 码进入订单时**(自动应用 或 买家点 Apply) | 校验链第 **1–5** 项(不依赖身份) | 按 §2.6.4 提示;链接码的呈现见 §2.13.3 |
| **T2 · 买家身份可用后**(结算邮箱通过格式校验**且失焦**,值发生变化时触发;值未变不重复触发) | 补校第 **6–7** 项 | **取消该码的 apply、整单重算、把码值回填输入框,并在输入框下方的既有错误提示位展示原因**(详见 §2.13.3) |

> **为什么拆两个时点**:第 6、7 项都需要知道"买家是谁",而买家进 checkout 时通常尚未填邮箱。
> 若等填完邮箱再算全部优惠,买家进页面先看到原价、会以为链接没生效就走了;
> 若把限次一路推到支付前,买家会在点支付那一刻才被告知优惠没了。**先算不依赖身份的、身份明确后再补校**,是三者中体验损失最小的。
> 代价是**金额可能在填完邮箱后变动一次**——这个变动必须有呈现(§2.13.3)。

> **买家中途改邮箱**:结算邮箱每次变化都重新触发 T2,并**对全部已输入/已带入的码整单重新求解**——
> 此前因身份不符被移除的码,若新邮箱符合条件则**重新生效**。

**chip 与集合的一致性口径**:**chip = 当前实际生效的码**(集合内的码)。单商品场景下新码挤掉旧码时,**旧 chip 消失、新 chip 出现**;多商品场景下,作用于不同商品行的多个码 chip **并存展示**。(D2)

### 2.6.3 操作流程(优惠码)

输入码 → `Apply` → 按 §2.6.2 四步处理 → **成功**:chip 出现、`Discount` 行金额与 `Total`、主 CTA 金额同步刷新;**失败**:按 §2.6.4 在**输入框下方出行内红字**,**输入框内保留买家已输入的码**(不清空)、chip 不出现、金额不变 → 点 chip 上 `✕` **Remove** → 从集合移除并**整单重新求最优组合**(可能导致其他码/自动折扣重新生效)。

### 2.6.4 校验失败枚举

> **展示形式(v2.1 改定,以 Figma 为准)**:所有优惠码校验失败**以行内错误提示呈现**,位置为**优惠码输入框正下方**、`Subtotal` 之上。**不使用 Toast、不使用弹窗。**
>
> **PC 与移动端形态不同(刻意,不是设计稿有误)**:
>
> | 端 | 输入框 | 错误文案 | 依据 |
> |---|---|---|---|
> | **PC** | **边框保持原样、不变红** | 框下方一行红色小字 | Figma 帧 `looply PC Checkout — 营销code输入报错`(`5778:1667`) |
> | **移动端** | **转为错误态(红框)** | 框下方一行红色小字 | 移动端设计系统既有表单报错组件(`1013:16791`),与地址、验证码等字段同范式;移动端不单独出稿 |
>
> 两端均**复用各端设计系统既有的表单报错组件**,营销侧不新增视觉规范。
>
> **通用行为**:出错时**输入框内保留买家已输入的码**(不清空,便于修改重试);**chip 不出现、汇总区金额不变**(§2.6.3)。
>
> **下表英文即 C 端实际展示的源文案,开发按此实现**;其他语种由语言包基于这份英文产出。中文列仅供运营理解,非交付物。
> ⚠️ **设计稿上的报错文案 `Incorrect discount code` 是示例数据,不是实现文案**——一律按下表九条取值。
>
> **成功态不出错误提示**——成功的反馈是 chip 出现 + `Discount` 与 `Total` 联动(§2.6.3),视觉已自洽。

| # | 失败原因 | **英文源文案(直接实现)** | 中文(仅供运营理解) |
|---|---|---|---|
| 1 | 码不存在 / 已停用 / 活动非进行中 | `This code isn't valid or has expired.` | 优惠码无效或已过期 |
| 2a | 未达**满额**门槛 | `Spend {Threshold} or more to use this code.` | 满 {门槛金额} 可用 |
| 2b | 未达**满件**门槛 | `Add {N} or more eligible items to use this code.` | 满 {件数} 件可用 |
| 3 | 总量已用尽 | `This code has been fully redeemed.` | 该优惠码已被领完 |
| 4 | 每人限次已用完 | `You've already used this code.` | 你已使用过该优惠码 |
| 5 | 与已享折扣互斥(V1 一律不叠加,该码作用的商品行已命中优惠更大的折扣) | `These items already have an offer applied.` | 所选商品已享其他优惠 |
| 6 | 商品范围不命中 | `This code doesn't apply to the items in your cart.` | 购物车内商品不适用 |
| 7 | 码所属活动市场 ≠ 买家当前市场 | `This code isn't available in your region.` | 不适用于当前地区 |
| 8 | 用户不符合适用用户(未命中任一指定用户标签,**或不在指定买家邮箱名单内**) | `This code isn't available with this email.` | 不适用于该邮箱 |
| 9 | **码的优惠力度不如当前已生效的自动折扣**(C4) | `You're already getting a better offer, so this code won't apply.` | 当前已享更大优惠,该码不生效 |

**变量**:`{Threshold}` = `min_amount`(带币种符号)｜`{N}` = `min_quantity`,与 §2.4 规则标签同名同源,前端可共用格式化函数。

**文案口径(新增条目时按此对齐)**:
- **不暴露内部术语**——全表无 rule / candidate / threshold / 候选集 / 门槛判定;「门槛」译为买家动作(Spend / Add)而非 threshold
- **语气克制**——陈述句 + 句号,不用感叹号、不用 Sorry / Oops
- **不指责买家**——第 4 条用 `You've already used this code.` 而非 `You've exceeded the usage limit.`
- **不预设买家有账户(v2.4 改)**——本版取消了「用码必须登录」(§2.6 前置条件),未登录买家没有 account,故第 8 条由 `...for your account.` 改为 `...with this email.`,与实际判定依据(结算邮箱)一致
- **第 5 / 9 条刻意区分**:5 = 「这些商品已有优惠」(买家不知情),9 = 「你已享更大优惠」(明确告知);`offer` 一词统一,不混用 discount / promotion
- **第 2 条必须拆 2a / 2b**——满额与满件的买家动作完全不同(花钱 vs 加件),一个模板串塞不下

> **多语言口径**:上表文案为**「模板 + 变量」的静态 UI 文案**,与 §2.4 规则标签模板同处理——**英文为源文案写在本 PRD**,其他语种由语言包产出,**不进翻译服务**;变量(门槛金额 / 件数)由前端按语种的数字与货币格式渲染。

> **第 5 条与第 9 条的分流条件(v2.4 明确)**:两者**判定同源**——均由 §2.6.2 第 4 步「求解后该码未产生任何减免」触发,
> 此前只写了"由前端按上下文选择",没给上下文的判定标准,同一个输入两条文案都能论证。本版定死:
>
> | 把该码挤掉的是什么 | 出哪一条 |
> |---|---|
> | **自动折扣** | 第 9 条 `You're already getting a better offer, so this code won't apply.` |
> | **另一个已应用的优惠码** | 第 5 条 `These items already have an offer applied.` |
>
> **保留两条不合并**:两者买家心智不同——前者是明确告知"你已享更大优惠",后者是"这些商品已有优惠"(买家可能不知道自己已用了别的码)。

> **(v2.4)补两种此前未覆盖的输入**:
>
> | 情况 | 处理 |
> |---|---|
> | **重复输入一个已生效的码** | 出「该码已应用」提示,**不走第 9 条**——第 9 条说的是"你已享更大优惠",与事实不符(其实是同一个码) |
> | **输入框为空点 Apply** | Apply 按钮**置灰不可点**,不进入校验、不出任何文案 |(D2)

### 2.6.5 规则说明

- **多码生效口径**见 §2.6.2——**不再限制「单订单 1 个码」**,约束粒度为**商品行**(D2)
- **码不做预占**——Apply 仅校验可用性,使用次数的**唯一占用时点 = 支付成功核销**(§2.9)
- **支付发起前**系统对码做总量/每人限次**二次校验**,失败则提示码已失效并重算(并发用尽场景)
- 订单摘要各优惠金额为**试算分摊结果**(§2.8.4),支付成功后固化为订单优惠快照
- **不透传活动名与优惠码码值到 C 端汇总区**——汇总只出金额(D1)

### 2.6.6 异常处理

试算服务异常 → **弹 Toast** 提示优惠暂不可用,买家可原价继续结算或稍后重试(商品行降级为挂牌价、`Discount` 行隐藏、主 CTA 金额取未优惠 Total);码并发用尽(Apply 成功后支付时总量耗尽)→ 支付前二次校验失败,提示码已失效并重算。

> **为什么这里用 Toast、而 §2.6.4 用行内**:§2.6.4 是**优惠码本身校验不通过**,错误归属于输入框,故行内呈现;本条是**服务不可用**,与买家输入无关、也不挂在任何输入框上,故用 Toast 全局提示。两者刻意不同,不要统一。

## 2.7 C 端 · 成交后营销展示(页面型)

**功能描述**:订单成交后两个页面的优惠展示——**下单成功页**(支付完成即时页)与**订单详情**(历史可回看页)。两者是**不同页面、不同版式**,不可互相套用;共用同一份**成交快照**数据(§2.8.4 落库的 `order_discount`),口径为成交时刻,不随活动后续变化。

**共用数据口径(两个子页面均适用)**:

| 项 | 口径 |
|---|---|
| 数据源 | **只读订单侧成交快照**(`order_discount` + 订单行金额),**不调试算接口**——支付成功后金额已固化,重算会与实收不一致 |
| 活动名 `rule_name` | **仅落库存档**,供运营对账与客服追溯;**不透传 C 端**(D1) |
| 优惠码码值 | **不透传 C 端**(D1) |
| 金额口径 | 按订单所属市场币种,全程不涉及汇率 |
| 活动变更 | 活动结束/改名/暂停/降价,**均不影响已成交订单的展示** |

### 2.7.1 订单详情营销展示

## 2.8 机制 · 优惠命中与试算 + 行级分摊(机制型)

**功能描述**:营销域对外供给的统一计算能力。**按场景拆成两条规则**——单品场景走「规则一」,订单场景走「规则二」;两条规则共用同一套基础口径(§2.8.1)。
**触发条件**:商详/列表到手价查询、价格监控扫描、购物车试算、checkout 试算。

### 2.8.1 场景与共用口径

**四个场景各走哪条规则**:

| 场景 | 输入 | 适用规则 | 输出 |
|---|---|---|---|
| 商详页 / 商品卡片 | 单个商品 + 市场(无用户上下文) | **规则一**(§2.8.2) | **v2.2 扩充**:到手价 + 减免 + 划线价 + Save + 生效折扣的规则变量(见 §2.8.2 第 3 步) |
| 价格监控扫描 | 单个商品 × 市场(无用户上下文) | **规则一**(§2.8.2) | 到手价,供 §2.12 降幅比对 |
| 购物车 | 已勾选的商品行 + **买家身份(有则用,未登录时可能为空)** | **规则二**(§2.8.3) | 各行优惠 + 汇总 |
| checkout | 全部商品行 + **买家身份** + 优惠码 | **规则二**(§2.8.3) | 各行优惠 + 汇总 + 实付 |

> **(v2.4)「买家身份」的取值口径**
>
> | 用途 | 取值 |
> |---|---|
> | **每人限次**(校验链第 6 项) | 已登录取当前账户;未登录取**结算邮箱**关联到的账户,邮箱未注册则视为新买家、无历史核销 |
> | **适用用户 = tag**(校验链第 7 项) | 取当前账户的标签;未登录取结算邮箱关联账户的标签 |
> | **适用用户 = email**(校验链第 7 项) | **一律以结算邮箱为准,不走账户身份** |
>
> **`=email` 为什么只认结算邮箱(硬性)**:名单是运营按邮箱配的,而买家可能用 A 账户登录、却把订单收件邮箱填成 B——
> 若两个来源都认,同一订单会出现"按账户不命中、按结算邮箱命中"的双重结论,开发无从取舍。
> 统一认结算邮箱,与未登录场景口径一致,也与「专属券送给某个邮箱的持有人」这一业务语义吻合。
>
> **身份为空时**:第 6、7 两项**跳过不判、其余照常计算**,不得因此拒绝计算或要求买家登录;留待 §2.6.2 两时点模型的 T2 补校。

**共用口径 A · 候选折扣怎么筛**:所属市场 = 买家当前市场、且处于进行中(状态 + 按该市场本地时区的时间,双判定)的折扣;再逐个商品判断是否被圈选命中——`product_scope` 取 all / 品类 / 品牌 / **商品标签** / **Collection** / 指定商品;其中商品标签与 Collection 均为**命中任一即算(OR)**;Collection 的命中以**判定时刻**的商品池为准(池由 Collection 模块动态维护,营销侧不缓存)。

**共用口径 B · 商品是否可享(A5)**:指定商品的圈选关系**不物理删除**;每次判定时读商品域的实时可售状态——售出/下架的商品当下不可享,退款回到可售后自动恢复。

**共用口径 C · 单件减免怎么算**:
- `percentage`:减免 = round(现价 × 比例),再按 `max_discount_amount` 封顶(该字段仅 percentage 可配)
- `fixed`:减免 = min(`fixed_amount`, 现价)
- 均按所属市场币种计算,**全程不涉及汇率**
- 注:`max_item_count`(每单作用件数)已于 v1.2 移除,故 fixed 类无件数上限,风险由 §2.2.3 试算拦截 + §2.3 双阈值监控 + §2.8.4 实付兜底承接

**共用口径 D · 优惠码是「需输码触发的折扣」(D2,本版口径修正)**

优惠码**不是**「在自动折扣之外额外加的一层」,而是**候选折扣的一种触发方式**:

| 折扣类型 | 进入候选池的条件 |
|---|---|
| 自动折扣(auto) | 命中圈选商品即进入候选 |
| 优惠码(code) | 命中圈选商品 **且** 买家已在 checkout 输入并 Apply 成功,才进入候选 |

两者进入候选池后**完全同池、不做区分**,受**同一条约束**——**每个商品行至多生效一条折扣**(§2.8.3 第 2 步约束 ①),由同一次最优组合求解统一裁决谁生效。

由此直接推出三条结论(**都是求解的自然结果,不是特殊逻辑,开发不必为它们单写分支**):

| # | 结论 | 说明 |
|---|---|---|
| 1 | **一单可以有多个优惠码同时生效** | 前提是它们**作用于不同商品行**;这与 §2.8.3「不同商品各享各的、等同分开下单」是同一条规则 |
| 2 | **单商品场景下最多一个码生效** | 只有一个商品行 ⇒ 至多一条折扣 ⇒ 再输新码时,若新码更优则**自然替换**旧码 |
| 3 | **码可能被自动折扣挤掉** | 求解结果中该码不产生任何减免 ⇒ 不加入已应用集合(见 §2.8.3 第 1 步「新码 Apply 的处理顺序」) |

> **原「V1 单订单仅支持输入 1 个优惠码」的写法作废**(D2)——它只描述了「单商品进入 checkout」这一个场景,不能用来约束所有场景。

### 2.8.2 规则一 · 商详 / 商品卡片到手价(单品场景)

> **一句话**:只看这一件商品自己——它能不能满足门槛、最多能减多少。

**三步**:
1. **筛候选**:按共用口径 A + B 取出命中本商品的折扣,**只取自动折扣**——优惠码须由买家在 checkout 输入才触发(共用口径 D),商详页无输码上下文,故**任何优惠码都不参与到手价计算**。
   > **D2 不改变这一条**:码与自动折扣同池竞争,只发生在**规则二的订单场景**;**规则一始终只看自动折扣**。商详展示的到手价因此是「不用码就能拿到的价格」,买家在 checkout 用码后只会更便宜、不会更贵。
2. **判门槛**(先判门槛、再算优惠):
   - 无门槛(`min_type=none`)→ 直接可用
   - 满额 → 用**该商品挂牌价(现价)** 与 `min_amount` 比,达标才可用
   - 满件 → 按 **1 件**与 `min_quantity` 比,达标才可用
   - 即:**只有"无需凑单、单买这一件就能享"的折扣才计入到手价**;需要凑单才够格的折扣不参与本页价格计算
3. **取最大并统一输出**:在可用折扣中取减免最大的一条(V1 不叠加),按共用口径 C 算减免 → **到手价 = 挂牌价 − 该减免**。
   **无论是否命中折扣,本规则一律输出「到手价」**——**没有任何可用折扣时,到手价 = 挂牌价、减免 = 0**,而不是不返回或返回空。是否处于促销态由「减免 > 0」判断。

   **v2.2 输出扩充 —— 本规则统一输出下列五项**(原仅输出到手价):

   | 输出项 | 取值规则 |
   |---|---|
   | **到手价** | 上述三步的计算结果。无折扣时 = 挂牌价 |
   | **促销优惠金额** | 挂牌价 − 到手价。无折扣时 = 0。**本项即对外输出的口径名**;§2.12 成因判定与 §2.8.3 规则二内部沿用「减免额」指同一个量,只是那两处描述的是计算过程、不是对外输出 |
   | **划线价** | 有折扣(减免 > 0)时 = **挂牌价**;无折扣时 = **对比价**(存在且高于挂牌价才有值,否则无划线价)。口径同 §2.4 对照表 |
   | **Save 金额** | 划线价 − 到手价。划线价无值时 Save 无值 |
   | **生效折扣的规则变量** | 供前端按 §2.4 六模板拼接活动规则标签:使用门槛类型 / 折扣值类型 / 百分比值 / 固定减免金额 / 满额门槛值 / 满件门槛值 / 封顶金额。未命中任何自动折扣时无值 |

   > **「生效折扣」有且只有一条**——即上述第 3 步**实际计入到手价的那一条**(已通过门槛判定、且减免最大)。
   >
   > ⚠️ **不输出未达门槛的折扣。** 到手价计算本就不包含它们(第 2 步先判门槛),对外供给保持同一口径。因此也**不存在「已达标与未达标折扣并存、该展示哪条」的问题**。
   >
   > ⚠️ **本条与 §2.4「不达标则以活动规则标签表达、引导买家凑单」这条现行规则冲突**——不输出未达门槛的折扣,那条凑单引导标签将失去数据源。**该冲突已挂待拍板(C4'),记于模块 `待优化清单.md`;在拍板前开发按本节口径实现。**

> 🔴 **(v2.4)人群限定折扣会把专属价展示给全站——本版接受,运营必须知悉**
>
> 规则一**不判适用用户**,因此一个「指定买家(3 个邮箱)」或「指定用户标签」的**自动折扣**,
> 其折后价会成为该商品对**所有买家**的到手价:商详与商品卡片展示这个价、§2.11 据此判定 Sale 资格并驱动打标、
> §2.10.3 把它推进搜索索引参与排序与价格筛选。**而实际只有名单/标签内的买家能享受**——
> 其他买家加购后到 checkout 价格会涨回去。
>
> **本版决定接受该场景**(2026-08-25 拍板),不对规则一做人群过滤。
>
> **对运营的含义(重要)**:
> - **人群限定的活动优先用「优惠码」触发**——码不进规则一,天然不会外泄到全站
> - 若确需用**自动折扣**做人群限定,要预期到「全站看到低价、加购后涨回」带来的买家困惑与客诉
> - **指定买家(email)型尤其注意**:人群可能只有几个人,把他们的专属价挂给全站看,落差最大

**本场景不做的判定**:不判适用用户、不判限次。因为商详无登录用户上下文,故适用用户(标签)限定的折扣在此按"全部可享"展示,登录后由规则二在购物车/结算再校验。

> **v1.4 修正留痕**:v1.3 及以前写的是"商详无门槛判定",会让需要凑单的折扣在商详被无条件计入到手价——买家单买一件时实际付不到那个价,属虚标。本版起商详同样先判门槛。

### 2.8.3 规则二 · 购物车 / checkout 最优组合(订单场景)

> **一句话**:在"每件商品最多用一条折扣、每条折扣的门槛必须由**真正用它的那些商品**凑满"的前提下,选一种分法,让**整单省得最多**。

**第 1 步 · 筛候选**:按共用口径 A + B 取出候选,再逐条剔除——
- **适用用户不符**:`eligibility_type=all` 全部通过;`=tag` 校验买家是否命中该规则关联的任一用户标签(标签含"新客"等,由用户管理模块打标);**`=email` 校验买家邮箱是否在该规则的指定买家名单内(不区分大小写)**;自动折扣与优惠码均执行
- **限次已用尽**(checkout):总量(有效核销 `used_count` < `total_usage_limit`)、每人((rule,user) 有效核销 < `per_user_limit`);码类另判码有效性
- **门槛必然不可能达标**(剪枝):若"该折扣**命中的全部商品行**合计"都还不满足门槛,则无论怎么分配都达不到 ⇒ 直接剔除。这是充分条件,不影响结果正确性
> **购物车场景(v2.4 明确)**:执行校验链第 1–5 项(不依赖身份),**不含优惠码**;
> 第 6、7 项按 §2.8.1「身份为空时跳过不判」处理——**未登录买家的购物车不因适用用户判定而剔除折扣**,
> 该判定推迟到 checkout 的 T2 时点。checkout 全部执行。
>
> **为什么购物车不判适用用户**:购物车没有邮箱输入,身份大概率为空;若在此剔除,未登录买家看到的购物车金额
> 会与登录后不一致,而他并没有做错任何事。宁可在购物车多显示、到 checkout 补校,也不要少显示。

**checkout 的候选池构成(D2)**:候选池 = 命中的自动折扣 **∪** 买家**已应用优惠码集合**中命中的码。已应用集合随买家 Apply / 移除而变化,每次变化都触发**整单重新求解**。

**新码 Apply 的处理顺序(D2,四步)**:

| 步 | 动作 | 不通过时 |
|---|---|---|
| 1 | **校验码自身**——按 §2.6.2《优惠码校验链》逐项按序执行(**本处不再另行罗列校验项**,避免与权威表分叉) | 命中第一条不通过项即返回对应文案(§2.6.4),**不加入集合** |
| 2 | **加入已应用集合**(临时) | — |
| 3 | **按本节第 2 步整单重新求最优** | — |
| 4 | **看结果中该码是否产生减免**:是 → 正式加入集合、chip 展示;否 → **回滚,不加入集合**并出行内错误提示(§2.6.4 第 9 条) | — |

> 第 4 步是 D2 的关键:码能否留下由**整单求解结果**决定,不是先到先得。移除某个码同样触发整单重算——别的码或自动折扣可能因此重新生效。

**第 2 步 · 求最优分配**:

- **目标**:使**整单减免总额最大**
- **约束**:
  - ① 每个商品行**至多**分配一条折扣(也可以不分配);**自动折扣与已应用的优惠码在此不做任何区分**,二者竞争同一个名额(D2)
  - ② 每条被分配到商品的折扣,其门槛必须由**实际分配给它的那些行**满足——满额按这些行当前售价(未计本折扣)的合计、满件按这些行的件数合计
  - ③ 各行减免按共用口径 C 计算
- **为什么不能逐行各自取最大**:门槛按"实际使用者"判定 ⇒ 谁用这条折扣,决定它是否达标;而它是否达标,又反过来决定谁能用它。两者互相依赖,必须一起求解,不能拆成两步
- **平局规则(硬性)**:存在多个减免总额相同的分法时,**结果必须唯一且可复现**——同样的购物车与同样的活动配置,任何时候算出来都应是同一个分法。优先级:先取**用到折扣条数更少**的;若仍并列,由技术方案定一个稳定的确定性规则(不得随机、不得依赖查询顺序)
- **求解要求**:**按候选折扣 20 条规模评估**(D4 本版上调,原写"不足 10 条"——按 20 条设计可覆盖大促期间多活动并行的场景)。在该规模下**必须返回真正的最优解**,不接受近似结果;若技术方案判断某些极端规模下无法保证最优,需**事先与产品确认降级口径**,并在试算响应中标记本次结果为非最优,供监控与事后排查。具体求解算法由技术方案定

**第 3 步 · 输出**:整单优惠 = 各行生效折扣的减免额之和;输出各行明细供购物车/结算渲染。

**"不同商品各享各的"仍然成立**:一单内可以同时有多条折扣各作用于不同商品——前提是每条折扣的门槛都由它**实际作用的那些行**满足。

**全场景枚举(D1 本版新增)**:购物车 / checkout 下的多商品优惠组合,按"命中几条折扣 × 门槛类型 × 有无优惠码"穷举如下,每一行都要能被计算引擎正确处理:

| # | 场景 | 输入示例 | 预期结果 |
|---|---|---|---|
| 1 | 单商品命中单折扣、无门槛 | A 商品命中「8 折」 | 直接减,到手价 = 挂牌价 × 0.8 |
| 2 | 单商品命中多折扣、无门槛 | A 同时命中「8 折」与「直减 $80」 | 取减免大的一条 |
| 3 | 单商品命中带门槛折扣、**自身达标** | A $600 命中「满 $500 打 8 折」 | 达标 → 减 |
| 4 | 单商品命中带门槛折扣、**自身不达标** | A $300 命中「满 $500 打 8 折」 | 不达标 → 该折扣不生效 |
| 5 | **多商品凑单达标** | A $300 + B $300 同命中「满 $500 打 8 折」 | 两件合计 $600 达标 → 两件都减 |
| 6 | **凑单达标但拆开更优** | 场景 5 基础上 B 另命中「直减 $200」 | 需比较:两件都用满减 vs B 单用直减(此时 A 独用满减不达标) → 取整单最大 |
| 7 | 不同商品各享不同折扣(均无门槛) | A 命中「8 折」、B 命中「直减 $50」 | 各享各的,互不影响 |
| 8 | 部分商品不命中任何折扣 | A 命中折扣、C 未命中 | C 按挂牌价,不参与分配 |
| 9 | 命中折扣但**用户不符 / 限次用尽** | A 命中仅限"新客"的折扣、当前用户非新客 | 该折扣在候选阶段即剔除 |
| 10 | **优惠码参与**(仅 checkout) | 自动折扣已生效,再输入优惠码 | 码与自动折扣**同池求解**,受「每行至多一条」约束;码更优则取代该行的自动折扣,否则该码不生效并提示(§2.6) |
| 11 | 优惠码带门槛、需凑单 | 码为「满 $500 减 $100」,购物车合计 $600 | 按同一门槛规则判定(实际使用它的行合计) |
| 12 | 勾选变化导致门槛失守(购物车) | 场景 5 中取消勾选 B | 重新试算 → A 单独不达标 → 满减失效 |
| 13 | **多码同时生效**(D2 本版新增) | A 商品应用码 X、B 商品应用码 Y,两码商品范围不重叠 | **两个码都生效**——分别作用于不同商品行,不违反「每行至多一条」;汇总仍为单行 `Discount` |
| 14 | **同一商品行上两个码竞争**(D2 本版新增) | 单商品 A 先应用码 X,再应用码 Y | 只取减免大的一条;若 Y 更优则 X 的 chip 消失、Y 生效;若 Y 不更优则 Y **不加入集合**并提示 |

> 场景 6、12、14 是最容易算错的三类,开发自测与验收用例请务必覆盖。

**举例**:折扣 A「满 $500 全场 8 折」+ 折扣 B「Gucci 直减 $80」,购物车 = Gucci 包 $300 + LV 包 $300

| 分法 | A 实际作用的行 | A 是否达标 | 整单减免 |
|---|---|---|---|
| 甲:两件都用 A | $300 + $300 = $600 | ✅ ≥ $500 | $60 + $60 = **$120** |
| 乙:Gucci 用 B、LV 用 A | 仅 LV 的 $300 | ❌ < $500,A 失效 | 仅 B 的 **$80** |

→ 取整单最大 ⇒ **选甲,减 $120**。
> 若按"逐行各自取最大"会得到 $140(Gucci 取 B 的 $80、LV 取 A 的 $60),但那依赖"Gucci 帮 A 凑够门槛、自己却用 B"——在本版严格口径下**不合法**。

### 2.8.4 分摊、汇总与实付(落库口径)

**1. 行级分摊**
本版所有折扣均为**商品级**,减免天然落在具体商品行上,**不需要按占比二次分摊**。仅当未来引入订单级折扣(V2)时,才按各行折后金额占比分摊、尾差计入金额最大的那一行。

**2. 汇总口径(D1,与 Figma 一致)**
C 端购物车 / checkout / 订单详情的金额汇总区,**统一按下表输出**:

| 汇总行 | 取值 | 说明 |
|---|---|---|
| `Subtotal` | **各商品行折后价合计** | 已含自动折扣;**不是原价合计** |
| `Discount` | **优惠码带来的减免合计** | **只有一行**,不按活动拆多行 |
| `Shipping` / `Tax` | 由物流 / 税费模块给出 | 不在本模块 |
| `Total` | Subtotal − Discount + Shipping + Tax | 见第 3 条兜底 |

三条硬性约束:
- **汇总区不透传活动名与码值**——不出现 `Item discounts`、`Promo code XXXX` 这类逐条明细行;码本身以 chip 形式展示在输入框下方(§2.6),不进汇总
- **`Discount` 恒为单行**,即使多个码同时生效(共用口径 D 结论 1)也合并为一个数
- 自动折扣的减免**已经体现在 `Subtotal` 里**,不再单列,避免同一笔钱被算两次

**3. 实付兜底(A2)**
最终实付 = 应付合计 − 优惠合计;**若算出来是负数,则按 0 收**。
这个"不能低于 0"的兜底**只由订单计算引擎来做,且整条链路只做一次**——营销侧只负责算出优惠金额,不做这个截断;两边都截一次会导致金额对不上、对账查不清。

**4. 落库**
行级减免与生效折扣随订单写入 `order_discount`(含 `rule_name` 快照);多码生效时按**码维度分别落一条**,便于核销统计与退款回冲。

### 2.8.5 通用说明

**规则说明**:规则一的计算口径与 §2.12 价格监控扫描完全一致;所有金额按市场币种计算,无汇率参与。
**异常处理**:任一环节数据获取失败,按各页面的降级规则处理;计算引擎必须保证**同样的输入永远得到同样的输出**(可重放、可复算),这是对账与客诉复核的前提。

## 2.9 机制 · 核销与退款回滚(机制型)

**功能描述**:优惠使用的计数与逆向释放,保证限次与对账一致。
**触发条件**:订单支付成功事件(核销);订单整单退款事件(回滚)。

**优惠资格锁定时点(前置口径,原 §2.1-9 迁入)**:买家的优惠资格与金额以**订单创建(提交)时刻**的试算结果锁定;活动此后暂停/结束/到期不影响已创建订单(含未支付)的已锁优惠;支付成功核销时不再校验活动状态,仅执行唯一约束与原子计数。码类在支付发起前做总量/每人限次二次校验(§2.6)。

**处理流程**:
1. **核销**:支付成功 → 订单事件 → 营销侧记一次核销(写 promotion_redemption,status=valid,含 rule/code/user/order/redeemed_at),已核销次数 +1。**硬性要求**:①**同一活动在同一订单上只能核销一次**,重复事件不得重复计数;②**并发下不得超发**——总量已达上限时必须拒绝(该情形支付前二次校验已拦截,此处为最终兜底)。实现方式由技术方案定。
2. **回滚(D3)**:整单退款 → 订单事件 → 该订单核销 status→reverted、记 reverted_at,used_count−1、每人限次释放;**部分退款不回滚不重算**,买家仍占用使用次数,不因退款后不再满足门槛而追回优惠(重算依赖订单改价能力,V2)
3. 限次判定、KPI、对账均只统计 status=valid 的核销
**异常处理**:核销事件消费失败会重试,**重试不会重复计数**(同一订单只算一次);回滚事件晚到或重复触发,已是 reverted 的保持不变、不再二次扣减;**核销兜底拒绝**(总量被并发击穿后的最终拒绝):该订单已锁定的优惠保留、不向买家追回(体验优先),核销记录不写入。

## 2.10 机制 · 对外数据供给(机制型,v2.2 新增)

**功能描述**:明确营销域**以什么形态、把什么数据供给谁**。§2.8 回答"怎么算",本节回答"算出来给谁、怎么给"。

### 2.10.1 三种供给形态

| 形态 | 服务谁 | 内容 | 规则出处 |
|---|---|---|---|
| **A · 单品实时查询** | 商详、商品卡片 | 到手价 + **促销优惠金额** + 划线价 + Save + 生效折扣的规则变量 | §2.8.2 规则一 |
| **B · 批量索引供给** | 搜索 / Collection 的排序、价格区间筛、Sale 筛选 | 每个在售商品的**当前到手价**;Sale 标记通过商品域的 Sale 系统标签体现 | 本节 §2.10.3 |
| **C · 订单级试算** | 购物车、checkout | 各行优惠 + 汇总 + 实付 | §2.8.3 规则二 |

> **A 与 B 不是两套数据,是同一份「当前到手价」的两种问法**——A 实时问一件、B 全量推给索引。数据源同为 §2.11.3 的价格状态基线。

### 2.10.2 形态 A · 单品实时查询

**出统一能力,各模块自行决定是否接入**——营销不为下游是否接入负责,也不再为不同下游给不同口径。输出内容与取值规则见 **§2.8.2 第 3 步**,本节不复述。

**规则说明**:
1. **不区分用户**:不判适用用户标签、不判限次(沿用 §2.8.2「本场景不做的判定」)。带用户上下文的计算走规则二
2. **恒有输出**:任何在售商品都有输出,无折扣时到手价 = 挂牌价、减免 = 0。下游不需要写"有没有促销"的分支
3. **展示逻辑仍归各页面**:营销供给数值,版式由商详与各卡片模块按自己的设计稿决定

**异常处理**:营销侧数据获取失败 → 下游按各自降级规则处理(商详:降级展示原价、不阻塞页面);计算结果 ≥ 挂牌价 → 不输出划线价与 Save,防止反向展示。

### 2.10.3 形态 B · 批量索引供给

**为什么不能沿用形态 A**:两者量级完全不同,必须分开定义——

| | 形态 A 单品查询 | 形态 B 索引供给 |
|---|---|---|
| 需要多少商品的价格 | 当前这一页(几十件) | **整个结果集**(可能数万件) |
| 能否实时问一件算一件 | 可以 | **不可以**,排序要对全量结果集做 |
| 营销要交付什么 | 一次查询拿全的输出 | **数据供给 + 变化时推送更新** |

**结果要求**:
1. **到手价变化必须能被索引侧感知到**。触发面与 §2.12 完全一致——到手价变化的场景已被该清单全覆盖,**本节不新增任何触发源**
2. 以何种方式同步、多久同步一次、同步失败如何补偿,**由技术方案确定**

**一致性口径**:索引是快照,允许滞后。**不一致时以商详的实时到手价为准**,列表侧不做二次校验(成本高、收益低)。买家可能遇到:列表筛出 Sale 但点进去已无折扣(活动刚结束),或有折扣但暂未被筛出(活动刚开始)——**本期接受这个敞口**。

**UI 关联**:无自有页面。

## 2.11 促销打标(Sale 标签)(运营端 + 机制,v2.2 新增)

> **为什么独立成节、不并入 §2.3 价格监控**:价格监控是「发现异常降价 → 告警给运营」,促销打标是「标记降价商品 → 供买家筛选」,**读者与目的完全不同**,只是恰好都以降幅为输入。并进价格监控会让运营误以为调的是告警阈值。两者共用 §2.12 的触发面,除此之外互不依赖。

### 2.11.1 判定口径

**功能描述**:判定每个在售商品当前是否处于「降价中」,并驱动商品域给它打上 / 摘掉 **Sale 系统标签**,供前台按"在打折"筛选消费。判定**复用 §2.12 既有的扫描与计算,不新造引擎**。

**判定口径 —— 两类成因,满足任一即成立**:

| 成因 | 判定条件 | 有效期 |
|---|---|---|
| **折扣型** | 到手价 < 挂牌价(按 §2.8.2 规则一计算) | 折扣持续生效期间 |
| **挂牌价下调型** | 当前挂牌价 < 上次记录的挂牌价,**且**降幅 ≥ 最小降幅门槛 | 自最近一次降价起 **N 天** |

- 两类同时成立时,**按折扣型的有效期走**(更强,不受 N 天窗口约束)
- 两类都不成立、且 N 天窗口已过 → Sale 资格解除

> **⚠️ 折扣型是「当期比较」,不需要历史基线——本条最易被实现错**
>
> 「降价」这个词字面上暗示「曾经贵过」,容易让人以为要先有一个历史价格作基准。折扣型不是这样:
>
> | 成因 | 拿什么比 | 需要历史基线吗 |
> |---|---|---|
> | 折扣型 | 当期的**到手价 vs 同一时刻的挂牌价** | **不需要**,同一轮计算内两个值都算得出来 |
> | 挂牌价下调型 | 当期挂牌价 vs **上次记录的**挂牌价 | 需要 |
>
> 由此直接得出两条必须成立的行为:
> - ✅ **商品上架时就命中了活动 → 折扣型成立 → 首次扫描即打 Sale 标签**。它从来没有「贵过」,但到手价确实低于挂牌价,买家看到的就是划线价 + Save 徽章,货对板
> - ✅ **新上架商品没有挂牌价基线,因此不会被判成「挂牌价下调型」**。这是正确的,新品本就不该算「降价」。首次计算把当期值写入价格状态基线,供后续环比

**边界(同一条口径的反面)**:到手价**只计自动折扣、不计优惠码**(§1.6 术语)。因此**只配了优惠码的活动,其命中商品不打 Sale 标签**——买家在商详看不到任何价格下降,打了标筛出来就是货不对板。

### 2.11.2 打标与摘标的触发面

见 §2.12《全量触发场景清单》**全集**(到手价的每一次变化都会引起 Sale 资格重算),其中「时间侧 · N 天窗口到期」一行为本能力新增;「商品下架 / 售出」的口径见同节 v2.2 补充说明。本节不复述该表。

### 2.11.3 价格状态基线(数据要求)

系统需为每个在售商品 × 市场持久保存以下状态,它同时服务三件事——环比判降、Sale 资格维护、对外供给:

| 状态项 | 用途 |
|---|---|
| 上次挂牌价 | 判定「挂牌价下调型」的比较基准 |
| 上次到手价 | 判定环比降幅(§2.12 既有需求) |
| **当前到手价** | 对外供给(§2.10)与索引排序的取值来源 |
| **当前挂牌价** | 划线价取值与降幅计算 |
| **最近一次降价时间** | N 天窗口的计时起点 |
| **当前 Sale 资格**(有 / 无) | 打标与摘标的判断依据 |
| **Sale 成因**(折扣型 / 挂牌价下调型 / 两者) | 排查与运营核对 |

> ✅ **本项顺带补齐一个既有缺口**:§2.12 处理流程末尾要求「更新到手价基线」,但 ER v2.3 中该基线**只存在于告警表**——没有触发过告警的商品,基线无处可存。本基线正是它的正主。
>
> **本次迭代不出 ER 图(2026-08-05 用户定)。具体表结构、字段名、类型与索引由技术方案确定。**

### 2.11.4 打标与摘标的执行


- Sale 资格发生**变化**时(无→有 / 有→无)调用商品域的系统标签打标 / 摘标能力;资格未变化时不重复调用
- 打标对象为**渠道商品(listing)级**。同一件实物商品在多个渠道上架时各渠道独立判定——挂牌价、所属市场、命中的折扣都按渠道独立
- Sale 标签由系统按规则自动维护。**本期不要求商品域为它做「运营只读 / 不可手工增删 / 不可停用」的管控**——本期只用商品域既有的打标能力
> ⚠️ **由此接受两个敞口(本期已知、不处理)**:①运营在商品后台手工解绑 Sale 标签后,系统下一轮会重新打上,双方互相覆盖 ②Sale 标签若被运营在标签库里停用,系统打标会持续失败且无人察觉。**管控能力的诉求已记入 `商品/待优化清单.md`,后续版本再评估**

### 2.11.5 逆向链路(动了它谁会受伤)


| 谁动了什么 | 影响 | 处理策略 |
|---|---|---|
| 运营手工解绑某商品的 Sale 标签 | 下一轮又打回来,双方互相覆盖 | ⚠️ **本期不拦截**,已知敞口(见 §2.11.4);管控诉求记入商品《待优化清单》 |
| 运营在标签库里停用 Sale 标签 | 系统打标持续失败且无人察觉 | ⚠️ **本期不拦截**,同上 |
| 运营修改最小降幅门槛 / Sale 保持天数 | 判定松紧变化 | **不追溯**:即时生效于下一轮判定(§2.11.6) |
| 商品下架 / 售出 | 退出扫描范围 | **保留**:标签与基线均不动,重新可售时重算 |
| 活动暂停 / 结束 / 到期、商品移出圈选范围或 Collection 池 | 折扣型失去成因 | **联动**:即时摘标 |

**异常处理**:打标 / 摘标未成功时,**该商品的 Sale 资格记录不得被更新为「已生效」**——必须保持可被下一轮重新判定的状态,避免出现「记录说已打标、实际没打上」且再也不会自愈的错位。失败信息不对外展示、不进运营可见的业务记录。

### 2.11.6 运营端 · 促销打标设置(页面型)

**功能描述**:配置促销打标的判定参数。**独立页面,不并入价格监控的监控设置弹窗**。

**菜单位置(v2.2 定案)**:左侧「**营销中心**」分组下、**与「促销活动」并列的二级菜单「促销打标设置」**。至此营销中心含两个二级菜单:促销活动 / 促销打标设置。

> **为什么单开菜单而不是挂在促销活动页里**:打标参数与具体某个活动无关(它管的是「挂牌价下调型」这一类 Sale,压根不由活动驱动),挂在活动列表页会让运营以为是活动级配置。

**页面元素**:

| 字段 | 控件 | 必填 | 规则 |
|---|---|---|---|
| **最小降幅门槛** | 数字(%) | 是 | 默认 5,范围 1-50。挂牌价降幅低于该值不判为「挂牌价下调型」Sale(§2.11.1) |
| **Sale 保持天数** | 数字(天) | 是 | 默认 30,范围 1-180。挂牌价下调型 Sale 的有效期 N(§2.11.1) |
| 生效范围 | 只读 | — | 固定「全部市场;按市场/品类分别配置 V2」 |
| 生效时点 | 只读 | — | 固定「保存后于下一轮判定生效,不追溯已打标商品」 |
| 操作记录 | 表格 | — | 操作时间 / 操作人 / 操作类型 / 操作详情,按全局约定(所有配置页默认含) |

> **本页只管挂牌价下调型的参数**。折扣型 Sale 的生效与失效完全跟随活动本身,无参数可配。

**校验规则**:两项均为正整数,分别限 1-50 与 1-180;为空或越界时提交拦截并定位标红。

**规则说明**:
1. 两项均为**全局系统配置项**,不区分市场与活动(按市场/品类覆盖列入 V2)
2. **修改即时生效于下一轮判定、不追溯**——已打标商品在下一轮按新配置重新判定
3. 修改记录进操作日志

**异常处理**:保存失败保留表单内容并提示;并发修改冲突提示「配置已变更,请刷新」。

**UI 关联**:运营端原型 v24 · 促销打标设置页(`looply-营销活动-antd-原型-v24.html`)。

---

**UI 关联(本节机制部分)**:无 C 端页面。运营在商品后台看到的 Sale 标签展示归商品域。

## 2.12 机制 · 到手价扫描与变更识别(机制型)

> **v2.2 从 §2.12 移出并升为独立章节**。原先它挂在「§2.3 运营端 · 价格监控」下,但**它已不只服务价格监控**——§2.11 促销打标、§2.10.3 索引供给都依赖同一套扫描与触发面。放在价格监控下会让人以为改扫描只影响告警。
>
> **本节是三个消费方的共同基础**:①§2.3 价格监控(降幅超阈值 → 告警)②§2.11 促销打标(资格变化 → 打标/摘标)③§2.10.3 索引供给(到手价变化 → 推索引)。**扫描只跑一遍,三方各取所需。**

### 2.12.1 监控范围

到手价的下跌**不只由折扣造成**——挂牌价被改低同样会让买家看到的价格跳水。因此监控范围为**全部在售商品**,**含未被任何折扣命中的商品**(补上"无折扣商品挂牌价异动"的盲区);**下架 / 售出商品不在监控范围**(已不对外展示)。

### 2.12.2 全量触发场景清单

任何会改变"到手价"的动作,系统**都必须能识别到**。到手价 = 挂牌价 − 生效折扣减免,故触发源分两类:

| 类别 | 场景 | 是否需识别 | 影响面 |
|---|---|---|---|
| **挂牌价侧** | 商品改价(含红布林同步价变动) | ✅ 需识别 | 该 listing |
| | 商品上架 / 重新可售(退款回可售) | ✅ 需识别 | 该 listing |
| | 商品下架 / 售出 | ❌ **不在监控范围**(已不对外展示) | — |
| **折扣侧** | 活动**发布生效**(draft→scheduled/active) | ✅ 需识别 | 该活动命中的全部商品 |
| | 活动**到达开始时间**(scheduled→active,自动流转) | ✅ 需识别 | 同上 |
| | 活动**编辑保存后恢复上线**(paused→active) | ✅ 需识别 | 同上 |
| | 活动**暂停 / 结束 / 到期**(→paused / ended) | ✅ 需识别 | 同上(到手价**回升**,用于消解既有告警的复现) |
| | 圈选范围变更(改品类/品牌/标签/Collection/指定商品) | ✅ 需识别 | 变更前后命中集合的**并集** |
| | **Collection 商品池变化**(池由 Collection 模块维护) | ✅ 需识别(视作商品命中关系变化) | 进出池的 listing |
| **时间侧**(v2.2 新增) | **挂牌价下调型 Sale 的 N 天窗口到期** | ✅ 需识别 | 该 listing 的 Sale 资格解除(§2.11) |

> **注意"回升"也要识别**:活动暂停/结束后到手价回升,若不重新计算,环比比较的基准会停在低位,下一轮正常价反而被算成"暴涨",或让后续真实下跌被掩盖。

> **本节只规定"必须能识别到哪些变化"这一结果要求**。以何种方式识别(周期性重算 / 事件驱动 / 两者结合)、频率、以及识别不到时的补偿手段,**均由技术方案确定**,本 PRD 不作约束。

> **v2.2 补充 · 上表新增的「时间侧」一行为什么必须单列**:表内其余场景**全部是动作驱动**的(谁改了什么),而 N 天窗口到期**不是任何人的动作、是时间到了**——沿用原有触发面识别不到它。结果要求为:**距最近一次降价满 N 天的商品,其挂牌价下调型 Sale 资格必须被解除**;实现方式同样由技术方案定。

> **v2.2 补充 · 本节与「促销打标」的关系**:价格监控解决的是「**发现异常降价并告警给运营**」,促销打标解决的是「**标记降价商品供买家筛选**」——**两件事,只是恰好都以降幅为输入**。打标的判定口径、配置与执行**独立成 §2.11**,不并入本节;本节仅在触发清单上为其增加了「时间侧 · N 天窗口到期」一行(两者共用同一套触发面)。

> **v2.2 补充 · 「商品下架 / 售出」不在监控范围,对 Sale 标签意味着什么**:该场景仍**不纳入扫描**(已不对外展示,扩范围成本换不来收益),因此**不触发摘标、Sale 标签保留在该商品上**;**重新可售时**由上表「商品上架 / 重新可售」一行触发重算,届时若已无折扣即摘标。已知敞口:商品后台标签「使用次数」统计会把已下架/已售出的计入,数字偏高——**本期接受**。


### 2.12.3 处理流程

对需监控的商品 × 市场 → 按 §2.8.2 规则一(单品到手价)计算 → 分别与商品原价(累计)、上一次的到手价(环比)比对 → 超对应阈值按去重规则落告警,**并判定告警成因(见下)** → 更新到手价基线 → **本轮结束后,若有新增告警且飞书通知已开启,聚合推送一条飞书卡片**。

### 2.12.4 告警成因判定(`cause_type`)

对比本次与上次扫描的两个输入量——挂牌价、生效折扣减免额:

| 成因 | 判定条件 | 排查方向 | 可用处置 |
|---|---|---|---|
| `discount` 折扣配置 | 挂牌价未变,减免额变大 | 折扣力度/圈选配置 | 暂停命中活动 + 标记已处理 / 忽略 |
| `listing_price` 挂牌价下调 | 减免额未变(含恒为 0),挂牌价变低 | 商品侧改价是否正确 | **无活动可暂停**;查看商品 + 标记已处理 / 忽略 |
| `both` 两者叠加 | 挂牌价变低**且**减免额变大 | 两边都要看 | 同 `discount`(可暂停活动),但需一并核实挂牌价 |

- **无折扣商品的告警只会是 `listing_price`**,此时「命中活动」列为空、价格计算链路快照只有"挂牌价"一个环节
- **累计降幅对无折扣商品恒为 0**(到手价 = 挂牌价),故这类商品实际由**环比降幅**捕获;累计阈值仍只对折扣力度有意义

### 2.12.5 飞书聚合推送规则

- **推送时机**:每轮扫描结束后推送一次;本轮**无新增**告警(含仅更新既有 pending 告警的情况)则**不推送**
- **卡片内容**:标题「价格监控:本轮新增 N 条告警」+ 按降幅倒序取 **TOP 5** 明细(商品名 / 市场 / 降幅与基准 / 阈值)+ 「共 N 条待处理」+ **「去处理」按钮**(跳转后台价格监控列表)
- **为什么聚合不逐条**:一次配置失误可命中数百件商品,逐条推送会刷屏并导致运营屏蔽机器人,反而漏掉真正重大的告警

**规则说明**:扫描口径与 C 端到手价一致(仅自动折扣,同商品取优惠最大一条);监控只针对在售商品,售出/下架商品不扫描。

## 2.13 机制 · 优惠码链接的挂码与自动兑现(机制型,v2.4 新增)

**功能描述**:买家点击优惠码链接后,系统记住这个码;买家继续浏览、加购,进入 checkout 时该码**自动生效**,无需手输。本节只定义「码怎么跟着买家走、什么时候自动用上、什么时候清掉」——**折扣本身的校验、试算、分摊、核销全部沿用 §2.6 / §2.8 / §2.9,一条未改**。

**触发条件**:买家访问 `/discount/{优惠码}` 路径(通常来自投放短链的跳转)。

### 2.13.1 点击链接时的处理

| 步 | 动作 |
|---|---|
| 1 | 识别路径中的优惠码 |
| 2 | **仅校验该码是否存在**;存在即记住,不存在则不记 |
| 3 | 跳转到落地页(带 `redirect` 参数则跳该页,否则跳首页) |

**为什么此刻只校验"码存不存在"**:门槛、商品范围、适用用户这些都依赖购物车内容与买家身份,而买家此刻可能购物车是空的、也尚未登录,**判不了,判了必然误报**。全部留到 checkout 统一判定。

**落地后不出任何提示(本版明确)**:买家点链接落地后,页面与平时完全一致——**不出优惠提示条、不出任何"优惠已记住"的告知**。码静默跟随,到 checkout 才可见(chip + `Discount` 行)。

> **落地到 checkout 之间没有反馈,是已知并接受的**:买家在这段路径上无从得知码已生效,可能因此流失。
> 本版仍不做,理由是它需要新增 C 端元素与设计排期,而本需求的 C 端改动范围要保持为零。
> 若后续投放数据显示这段流失明显,再单独评估。

**异常处理**:

| 情况 | 处理 |
|---|---|
| 码不存在或拼写错误 | **静默跳落地页**,不记码、不报错 |
| 码存在但活动已结束/暂停 | 照常记住,到 checkout 按 §2.6.4 统一判定(此处不提前拦截) |

> **码不存在为什么不给报错页**:会被用来批量试探有效码值。静默处理使试探者无法据此判断某个码是否真实存在。

### 2.13.2 码记在哪里、存多久

| 项 | 口径 |
|---|---|
| **载体** | 浏览器侧记录(会话级),**不落库、不写入购物车** |
| **容量** | **只有一个码位**。再点另一条链接,**新码覆盖旧码**——同一时刻浏览器里**不可能同时存在两个链接码** |
| **有效期** | **浏览器会话期间**;关闭浏览器即失效 |
| **跨设备** | **不跟随**。手机点链接、电脑下单则该码不生效——本版已知并接受 |

**码位的完整生命周期(v2.4 新增,硬性)**:此前只定义了"写入"与"支付成功后清除"两个出口,其余出口未定义,开发无从判断码会不会"复活"。全部出口如下:

| # | 事件 | 对码位的处理 | 说明 |
|---|---|---|---|
| 1 | 买家点击优惠码链接 | **写入**(覆盖原有值) | 见 §2.13.1 |
| 2 | 进入 checkout | **读取**,不清除 | 见 §2.13.3 |
| 3 | 买家在 checkout 点 chip 上的 ✕ 移除 | **清除** | 否则刷新页面后码会自动回来,**买家永远移不掉**;清除后如需恢复,重新点一次链接即可 |
| 4 | T2 补校不通过被系统移除(§2.6.2) | **保留** | 买家改成符合条件的邮箱后应能重新生效(§2.6.2 两时点模型),清掉就恢复不了 |
| 5 | 支付成功且该码被核销 | **清除** | 见 §2.13.4 |
| 6 | 支付成功但该码未被核销 | **保留** | 下次结算仍可参与 |
| 7 | 关闭浏览器 | **清除**(会话级天然失效) | — |

> 🔴 **"新码覆盖旧码"覆盖的是「链接带来的那个码位」,不是把整个 checkout 限死成单码(硬性,开发极易误读)**
> 买家在 checkout **手输的码仍走 §2.6.2 的多码规则**(一单可多码、作用于不同商品行)。
> 最终一个 checkout 里可能是:**1 个链接码 + N 个手输码**,一并参与 §2.8.3 的整单最优组合求解。
> 若理解成"整单只能 1 个码",等于改掉了 §2.6.2。

> **(v2.4)码位被覆盖时,checkout 已应用集合要同步处理**:买家点链接 A 进了 checkout(A 已在已应用集合、chip 已显示),
> 又返回商城点了链接 B——此时码位被 B 覆盖,**A 必须同时从已应用集合移除并整单重算**,
> 最终 chip 只剩 B。否则会出现"码位是 B、页面显示 A"的错位。

**为什么不挂在购物车上**:买家可能从商详页直接 **Buy Now**(跳过购物车,见订单支付模块口径)。码若挂在购物车上,这条链路完全读不到——而"点链接进来直接买某件商品"恰恰是投放链接最主要的用法。

### 2.13.3 进入 checkout 时的自动兑现

**处理顺序(硬性,按序执行)**:校验项一律走 §2.6.2《优惠码校验链》与两时点模型,**本节不再另行罗列校验项**。

| 步 | 时点 | 动作 | 不通过时 |
|---|---|---|---|
| 1 | 进入 checkout（**T1**） | 取出码位里的码,执行校验链第 **1–5** 项(不依赖身份) | 见下方「T1 失败的呈现」 |
| 2 | 通过后 | 加入已应用集合,整单重新求最优组合(§2.8.3) | — |
| 3 | 求解后 | **执行 §2.6.2 第 4 步的减免检查**:该码是否产生了实际减免 | 未产生任何减免 → **不加入集合**(避免 chip 显示一个无实际作用的码);呈现同 T1 失败 |
| 4 | 结算邮箱可用后（**T2**） | 补校校验链第 **6–7** 项:每人限次 + **适用用户(tag 标签命中 / email 在指定买家名单内)** | 见下方「T2 移除的呈现」 |
| 5 | 支付发起前 | 沿用 §2.6.5 的总量/限次二次校验 | 提示码已失效并重算 |

### T1 失败的呈现:按「买家能不能自救」分两类(v2.4 改定)

| 失败原因 | 呈现 | 为什么 |
|---|---|---|
| **能自救**——未达满额门槛(2a)、未达满件门槛(2b) | **出中性引导提示**,位置在订单摘要上方,正向表述(如 `Spend $40 more to unlock $80 off.`) | 买家差一点就能拿到优惠,告诉他是有价值的;而且**他没有别的补救入口**——本节不回填码值、C 端全程不透传码值(§2.6.5)、购物车也没有输码入口(§2.5),不提示他就只能回去翻邮件找码 |
| **不能自救**——码无效/过期(1)、总量用尽(3)、每人用尽(4)、已享更优(5/9)、商品不适用(6)、地区不符(7)、账户不适用(8) | **完全静默**,不出任何提示、不回填码值,页面表现与"没有这个码"完全一致 | 告诉买家也改变不了结果,只会让他困惑"我做错了什么"——他并没有任何输入动作 |

> **引导提示不是报错**:用中性/正向样式,**不用红色错误态**——买家没有做错任何事,他只是还没加够。
> 文案为「还差多少」的正向表述,不要写成「未达门槛」。

> **适用范围**:上述分类**仅限链接自动应用这一条路径**。买家**手输**优惠码时,失败态仍按 §2.6.4 九条文案在输入框下方出行内错误提示,**未作任何改动**。

### T2 移除的呈现:必须给提示(v2.4 补,此前是真空)

> 🔴 **T2 的移除不适用「静默」口径。**
> 静默的前提是"买家没有输入动作、报错没有归属"。而 T2 发生在**买家刚填完邮箱**——他有明确的输入动作,
> 更关键的是:这是**当着买家的面把已经显示的优惠拿走、并让 Total 上涨**。
> 若不给任何解释,买家看到的就是「进页面 `Discount −$30`、填个邮箱金额跳回原价」,这是最容易变成客诉的场景。

**处理动作(硬性,按序执行)**:

| 步 | 动作 |
|---|---|
| 1 | **取消该码的 apply**——从已应用集合移除,chip 消失,整单重新求最优组合 |
| 2 | **把码值回填到优惠码输入框**(链接码此前从未在输入框出现过,此刻回填) |
| 3 | **在优惠码输入框下方的既有错误提示位**展示不通过的原因 |

| 项 | 口径 |
|---|---|
| **是否提示** | **必须提示**,不适用静默 |
| **文案** | 复用 §2.6.4 对应条目:限次不通过 → 第 4 条;适用用户(tag / email)不通过 → 第 8 条 |
| **位置** | **优惠码输入框正下方**,即 §2.6.4 定义的行内错误提示位——PC 仅框下红字、移动端红框 + 红字,**复用既有表单报错组件,不新增视觉规范** |
| **码值回填** | **必须回填**。回填后输入框内有内容,错误提示挂在其下方就有了明确归属;买家也能看到是哪个码出了问题,可直接改码或清空 |
| **适用范围** | **链接码与手输码同样适用**。未登录买家手输了一个「指定买家」专属码、T1 时身份为空放行、T2 补校不通过被撤销,同样按本条呈现(手输码本就在输入框里,无需额外回填) |

> **为什么 T2 回填、而 T1 不回填**:两者的差别在**买家有没有输入动作**。
> T1 发生在买家进页面的瞬间,他没做任何事,回填一个他没输过的码只会让人困惑"这哪来的";
> T2 发生在**买家刚填完邮箱**,他有明确动作,且系统正要**把已经显示的优惠拿走**——
> 此时回填码值 + 就地报错,买家才能看懂"是我填的这个邮箱用不了这个码",而不是"金额怎么自己涨了"。

**成功时的呈现**:与手输码完全一致——优惠码 chip 出现、`Discount` 行与 `Total`、主 CTA 金额联动刷新(§2.6.1 / §2.6.3)。**不额外标注"该码来自链接"**。

### 2.13.4 支付成功后的清除

| 项 | 口径 |
|---|---|
| **清除时机** | 支付成功(订单转 paid) |
| **清除条件** | **该码被本单核销了 → 清除;未被核销 → 保留**(下次结算仍可参与) |
| **依据** | 本单核销了哪些码,以核销记录为准(见 §2.9) |

**为什么必须清**:不清则该码在同一浏览器会话内会被反复自动应用。而本模块允许运营配置**不限次**的码(总量与每人限次留空 = 不限,见 §2.2.2),不清就是实打实的资损口子。

> **(v2.4)本条与「单码位」模型的关系**:v2.3 曾用「买家先后点过 A、B 两条链接、本单只用上 A」来论证不整体清空——
> **该论证与 §2.13.2 的单码位模型矛盾**(点了 B 之后 A 已被覆盖,两者不可能同时存在),本版已删除。
> 单码位下的清除规则很简单:**码位里的那个码,本单核销了就清、没核销就留**。
> 完整的码位生命周期见 §2.13.2 的出口表。

### 2.13.5 未登录场景的说明

**本模块优惠码支持未登录使用**(与 §2.6 前置条件一致)。未登录买家的身份以**结算页填写的邮箱**为准——该邮箱本就是结算必填项,且未注册邮箱在下单时会静默创建账户,因此"每人限次"在未登录场景同样可判。

**限次判定口径(硬性)**:

| 买家状态 | 每人限次怎么查 | 结果 |
|---|---|---|
| 已登录 | 按当前账户查历史核销 | 沿用 §2.9 现有口径,不变 |
| **未登录 · 邮箱已注册** | **按结算邮箱关联到对应账户**,查该账户的历史核销 | 按 §2.9 每人限次口径判定 |
| **未登录 · 邮箱未注册** | 无关联账户 = 无历史核销 | 限次判定**通过**;下单时静默建号,核销记入新账户 |

> **(v2.4)「指定买家」与本节的关系**:适用用户 `=email` 的活动同样按结算邮箱判定——
> 未登录买家填入的邮箱若在指定名单内,**直接享受,不需要登录、也不需要该邮箱已注册**。
> 这正是 §2.2.2 选择「存邮箱而非账号 ID」的原因:两处用的是同一个识别依据,不存在第二套机制。

> 🔴 **不得以"未登录"为由拒绝校验或要求买家先登录(硬性)**
>
> **现状(2026-08-25 核实)**:配置了使用次数限制的码,现行系统会**要求买家先登录**才进行核验。本版**必须改掉**。
>
> **正确做法**:未登录时以结算邮箱关联查询使用次数,查得到就按查到的次数判,查不到就当新买家放行——**任何情况下都不弹登录、不拦截下单**。
>
> **登录换不来更强的限次保障**:平台允许未登录下单并以结算邮箱静默建号,买家换个邮箱注册同样能再用一次,与未登录换邮箱的绕过效果完全相同。强制登录只是把同一个敞口挪到注册环节,却实打实地损失转化。

> ⚠️ **已知敞口(本版接受,运营须知悉)**:未登录场景的"每人限次"以**买家填写的邮箱**为识别依据,**可以被绕过**——换一个邮箱、在 Gmail 地址中加 `+后缀` 或加点,系统都会视为不同的人,同一个人在同一台设备上可反复使用同一个码。
>
> 本版**不做**设备指纹、IP 等额外识别手段(行业通行做法亦是如此,平台侧无原生手段可彻底解决)。
>
> **对运营的含义**:「每人限次」在未登录场景是**软约束不是硬锁**。**大额优惠码务必同时配置总使用次数上限**,以总量封住资损上限;仅靠每人限次不足以防止批量薅取。

# 四、版本规划

**V1(本期)**:概览 v1.0 能力全景中标 ✅ 的全部项——Amount off products(auto+code)、多市场按币种、封顶/限次/门槛、试算+行级分摊供给、到手价/购物车/checkout/订单详情 C 端展示、核销+整单退回滚、价格监控工作台(全局阈值/排查/一键暂停/**飞书群告警推送**/**覆盖挂牌价异动的成因分流**)、配置试算拦截。
**v2.2 追加(本期 · 价格计算与促销打标)**:Sale 状态判定与打标(两类成因 / N 天窗口 / 触发面 / 价格状态基线)、对外数据供给三形态(单品实时查询扩为五项输出、批量索引供给)、搜索与 Collection 的排序与价格滑块口径统一为到手价、新增「促销打标设置」独立配置页。**开发评审 TODO E1「首页/商品列表页缺到手价查询接口与排序能力」的营销侧部分本期闭环**,下游接入由各模块自行排期。
**本期只出营销域逻辑**:前台 Sale 筛选器的注册与交互、单值维度显示逻辑、排序与滑块的前端实现、搜推索引改造、商品域系统标签能力、各页面改为接入统一供给——均由对应模块负责,不在本 PRD 范围。
**本期不做**:Sale 按折扣力度分档、Sale 专题落地页 / 快筛位 / 商品卡 Sale 角标、全站三套「原价」口径收口(单独立项)。
**v2.4 追加(本期 · 优惠码分享链接)**:运营端生成含 code 的优惠码链接(落地页支持首页与该活动圈选的 Collection)、点击链接后码自动跟随、进 checkout 自动兑现、支付成功后自动清除;**折扣规则一条未改**,短链生成与 UTM 配置由短链服务承载(§2.2.6 / §2.13)。
**v2.4 追加(本期 · 适用用户增加「指定买家」)**:适用用户由 all/tag 扩为 **all/tag/email 三选一**,支持运营**按邮箱指定专属买家**(未注册邮箱亦可预配);ER 相应升级 **v2.2 → v2.3**(`eligibility_type` 枚举 +1、`promotion_eligibility` 增 `buyer_email`)。
**v2.4 追加(本期 · 优惠码使用条件调整,影响面超出分享链接)**:🔴 **取消「带使用次数限制的优惠码必须登录才能核验」**——改为未登录时按结算邮箱关联查询使用次数。**该变更作用于全部优惠码,不限于链接带来的码**,属对现行实现的改造(§2.6 / §2.13.5)。
**v2.4 本期不做**:App 端唤起后自动挂码(下一版)、落地页支持「指定商品」「搜索结果页」、跨设备延续、链接→下单的转化归因。
**V2 方向**:更多促销类型(BXGY/订单折扣/免邮/闪购)、商家自建促销与账单、预算池、审批流、人群定向与定向码、叠加类别模型(combines_with,V1 已完全取消叠加)、部分退款重算、告警阈值分级、邮件通知、飞书定向 @ 责任人(需自建应用+账号映射)、效果报表、多规则活动容器。

# 五、数据与埋点

核心埋点(明细字段由数据侧技术方案定):C 端促销曝光(商详促销组曝光,含 promotion_id)、用码行为(Apply 成功/失败+失败原因)、优惠订单(下单含 promotion 标记);运营端告警处置动作(处置类型/时长)。本期不做效果报表,埋点为 V2 报表储备。

**(v2.4)优惠码链接相关埋点**:优惠码链接被点击(含优惠码与落地页类型)、码自动应用成功 / 失败、链接码最终成交(区别于手输码成交)。

**失败原因的上报取值**:按 §2.6.2《优惠码校验链》的**序号**上报(1–7),另加两个非校验链的结果:`no_discount`(求解后未产生减免,对应 §2.6.4 第 5/9 条)与 `removed_at_t2`(T2 补校被移除)。**T1 静默的失败同样必须上报**——买家看不到,但运营需要据此判断投放质量(例如大量 `4 门槛未达` 说明门槛配高了)。**链接的点击量与独立访客由短链服务统计,营销侧不重复采集**;「点击 → 下单」的完整归因链路由短链服务规划(本版未打通),营销侧仅上报上述事件。
