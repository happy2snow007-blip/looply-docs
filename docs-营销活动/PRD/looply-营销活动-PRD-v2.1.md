# 一、概述

## 1.1 背景与目标

looply 作为面向美国+香港市场的二手奢侈品 B2C 平台(三方+自营商家入驻),V1 阶段需要具备基础促销能力驱动转化。本期参考 Shopify discount 模型,仅落地 **Amount off products(按商品/品类/品牌减价)** 一种促销类型,由平台运营配置、平台承担优惠成本。

目标:
1. 运营可配置自动折扣与优惠码两类触发的商品减价活动,多市场按币种独立控制力度
2. 买家在商详/购物车/checkout/订单详情看到一致、合规的促销价格与优惠明细
3. 资损三道防线落地:事前(配置试算拦截+封顶/限次)、事中(实付兜底+核销原子扣减+到手价监控)、事后(退款回滚+一键熔断)

## 1.2 不做什么(V1 明确边界)

| 不做项 | 说明 |
|---|---|
| Buy X get Y / Amount off order(订单满减) / Free shipping / 限时闪购 | V2 促销类型扩展 |
| 商家自建促销(商家出资、账单结算) | V2;V1 仅平台运营配置、平台出资(A1) |
| 预算池封顶(budget_total/spent) | 字段已预留,V1 不落逻辑 |
| 上线审批流 | V1 运营直接发布;靠试算拦截+监控兜底 |
| 定向码(一人一码,max_uses)/营销侧自建用户标签 | V2;V1 一码通用(D7),用户标签仅引用用户管理模块现有(含新客) |
| 折扣叠加(任何形式) | **V1 一律不叠加**(本版决策,取代原 can_combine 开关);combines_with 类别模型 V2 |
| 订单级"整单减一次"(真正意义的满减) | **V2**。V1 的满额/满件只是**门槛**,达标后仍按商品逐件减免;运营配置时须注意二者区别 |
| 部分退款的优惠重算/追回 | V1 部分退款不回滚不重算(D3);依赖订单改价能力,V2 精细化 |
| 活动维度聚合统计/效果报表(转化、ROI) | V2;V1 仅核销计数与告警工作台 |
| 监控阈值按活动/品类覆盖、邮件通知、飞书定向 @ 责任人 | V2;**V1 = 全局单一阈值 + 站内角标 + 飞书群机器人聚合推送** |

## 1.3 用户角色

| 角色 | 端 | 职责 |
|---|---|---|
| 平台运营 | 运营后台 | 配置/发布/暂停/结束促销活动;处置到手价告警;查看核销记录 |
| 买家(Buyer) | C 端(APP/PC) | 浏览促销价、输优惠码、下单享受折扣、查看订单优惠明细 |
| 系统 | — | 命中试算/行级分摊/核销/退款回滚/到手价扫描告警 |

## 1.4 核心场景

1. **配置发布**:运营新建折扣(选触发方式/折扣值/圈选商品/投放市场/使用条件/生效时间)→ 保存前价格试算拦截确认 → 发布生效
2. **C 端曝光转化**:买家商详页看到到手价+划线原价+促销标签 → 加购(购物车行级优惠+汇总)→ checkout 输码 → 试算(门槛/限次/封顶)→ 支付
3. **核销与回滚**:支付成功订单事件驱动原子核销(计数+1);整单退款事件驱动核销回滚(计数-1、限次释放)
4. **监控处置**:系统扫描在售商品到手价,降幅超阈值落告警 → 菜单角标提示 + 飞书群聚合推送 → 运营在价格监控排查计算链路 → 一键暂停活动/标记处理/忽略

## 1.5 全局页面流转

**运营端**(营销中心):
```
促销活动列表 → 新建折扣 → (价格试算确认弹窗) → 返回列表
促销活动列表 → 活动详情(基本信息 Tab / 核销记录 Tab) → 编辑折扣
促销活动列表 → [结束活动弹窗] [删除弹窗]
价格监控(一级菜单,与「营销中心」分组平级)→ 告警列表 → 排查抽屉(Drawer) / 监控设置弹窗
促销活动列表 告警轻量入口 → 价格监控
```

**C 端**(仅标注营销触点,页面本体归各自模块):
```
商详页(到手价 + 促销标签)
  → 购物车(行级折后价 + Subtotal/Discount 汇总)
  → checkout(优惠码输入与 chip + 订单摘要 Subtotal/Discount)
  → 支付
  → 下单成功页 Order Confirmed(优惠透传)
  → 订单详情(优惠快照;退款后按实退回冲)
```

## 1.6 术语说明

| 术语 | 定义 |
|---|---|
| 促销活动 / 折扣(discount) | V1 采用 1:1 简化:一个活动 = 一条折扣规则(promotion 与 promotion_rule 一一对应)。运营视角只感知"折扣活动"一个概念 |
| 自动折扣(auto) | 命中圈选商品即自动生效,无需输码 |
| 优惠码(code) | 买家在 checkout 输入优惠码触发;V1 一码通用 |
| 到手价 | C 端展示层的单品折后价 = 原价按**自动折扣**计算的结果;优惠码、用户级限次、订单门槛不计入,以提示形式表达 |
| 试算 | checkout/购物车的订单级优惠计算:带用户上下文,判定门槛/限次/封顶与同商品取优,输出可用优惠、减免额与**行级分摊明细** |
| 核销 | 支付成功后对一次优惠使用的计数记录(promotion_redemption),不记金额 |
| 回滚 | 整单退款后释放该次核销:status→reverted、已用次数-1、限次释放 |
| 不叠加(V1 硬性) | 同一商品行同时命中多条折扣时,**只取优惠最大的一条**生效;一单内不同商品各自享受各自命中的折扣(等同分开下单)。V1 不提供任何叠加配置项 |
| 最大优惠封顶 | percentage 折扣单件最大减免金额,按市场币种录值 |
| 挂牌价(listing_price) | 商品在本市场的平台标准售价,**未计任何折扣**;是划线价、到手价与降幅计算的共同基准 |
| 到手价 | 挂牌价扣除自动折扣减免后的价格;**任何在售商品都有到手价**,无折扣时 = 挂牌价(§2.8.2 规则一) |
| 划线价 | C 端展示的 line-through 价格;**有折扣时 = 挂牌价、无折扣时 = 对比价**(见 §2.4)。**取值必须真实、不得虚构参考价**(FTC reference pricing 要求);本期 C 端**不出现合规说明文案**(设计稿未含,D4) |
| Save | 划线价 − 现价;两种场景取值见 §2.4 口径表 |

## 1.7 多语言支持

本模块为混合模块:**运营后台部分(促销活动管理、价格监控)仅面向内部运营,本期仅中文,不接入多语言**;以下三段仅覆盖 C 端部分。

**A. 静态 UI 文案**:C 端营销相关静态文案(促销标签模板、优惠码输入区按钮与校验提示、订单摘要行标题、合规说明等类别)由前端语言包实现(语言包落地,运营可在多语言后台查看/修改)。

**B. 动态业务内容 — 翻译服务接入**

本模块**自身产生**、需多语言的业务字段只有「活动名称」一项。按多语言 v3.2 标准流程接入:**先建卡 → 再注册字段 → 保存时写入翻译服务触发 AI 翻译**。

**接入判定口径(D5)**:**本期及未来有可能在 C 端展示的自产文本,一律接入**,不以"当期是否已在页面上出现"作为接入与否的依据。理由:接入是一次性的建卡+注册字段成本,而漏接的代价是——未来某个版本决定展示时,存量数据没有译文、只能补跑批量翻译并人工校对。因此 `promotion_name` **本期虽不在 C 端任何位置展示**(D1 已定汇总与订单侧全程不透传活动名与码值,§2.4 促销标签也改由折扣配置拼接),**仍然接入**。

**B-3 「营销活动」聚合组声明(resource_group)**

上述 2 张卡按 v3.2 声明为**一个聚合组**,避免零散扔在"前端页面"域里运营认不出同属营销:

- **group_code**:`promo` ｜ **group_name**:营销活动 ｜ **domain**:前端页面 ｜ **成员数**:2
- 数据层仍是 2 张独立卡片(各自建卡、各自注册字段);聚合只发生在导航展示层——多语言后台显示一张聚合卡 + 2 个分组子导航

>
> **与 resource_type 的层级区分**:`promo` 是**聚合组**(导航层),`promotion` 是**卡片**(数据层),两者不同层不冲突。

|---|---|---|
| 1 | 页面文案 | `page-promo` |
| 2 | 促销活动 | `promotion` |

- **优惠码 `code`**:优惠码是**标识符不是文案**,各语种原样展示——**不翻译、不建 resource_type、不进聚合组**(本版明确)

# 二、需求详细描述

## 2.1 全局约定

1. **活动-市场 1:1(A6,硬性)**:一个折扣活动只属于一个市场,建活动第一步选定、创建后不可更改;活动的全部金额字段按所属市场币种显式录值,起止时间按所属市场本地时区判定。系统不做实时汇率换算,买家下单/结算/核销全程不用汇率(汇率模块仅可作运营录值时的等值参考)。
2. **时区口径(D5 / E4 本版明确)**:活动起止时间按**所属 Market 的「基准时区」**判定,营销侧不再单独配置(单市场化后原 timezone_mode 废弃)。

   **为什么要指名到字段**:market 模块有**三层**时区概念——Market 的**基准时区**、Market 的**业务日切时间**、Country 的**本地时区覆盖**。原文只写"按所属市场本地时区"会被理解成取国家级覆盖值(同一 Market 下多国家时会取到不同值,导致同一活动在不同国家生效时刻不一致)。本模块**统一取 Market 基准时区**,与国家无关。
   - 取值来源:market 模块的 Market 基准时区字段(具体字段名以 market 模块交付为准,**对接时需确认**)
   - 业务日切时间**不参与**活动生效判定(那是对账/报表口径)
   - 展示:运营端配置页在时间选择器旁标注当前市场的基准时区(如"美东时间 UTC-5"),避免运营按本地时间理解
3. **金额展示**:C 端所有促销金额按当前市场币种展示;运营端按市场行分币种录入与展示。
   **跨市场运营口径**:同一促销策略要在多个市场上线 = 在各市场分别建活动(列表"复制"操作支持以现有活动为模板复制后改所属市场与金额);活动名建议带市场标识。
4. **状态机(活动)**:

| 枚举值 | 含义 | 进入条件 | 退出条件 |
|---|---|---|---|
| draft 草稿 | 已保存未发布 | 新建时"存为草稿" | 发布→scheduled 或 active(按开始时间);删除→物理删除 |
| scheduled 未开始 | 已发布但未到开始时间,对 C 端不生效 | 发布时 now < start_at | 到达开始时间→active(定时任务);手动结束→ended |
| active 进行中 | 对 C 端生效 | 发布时 now ≥ start_at,或 scheduled 到达开始时间 | 暂停→paused;到达结束时间(定时任务)或手动结束→ended |
| paused 已暂停 | 临时停止生效(熔断) | 运营手动暂停 / 监控处置一键暂停 | 恢复→active;结束→ended |
| ended 已结束 | 终态,不可恢复 | 到期自动 / 运营手动结束 | **不可删除**——核销记录与规则配置需永久可追溯(§2.2.4) |

**scheduled 说明(本版新增)**:此前"已发布未到开始时间"的活动在列表显示为"进行中",与实际不生效相矛盾,运营易误判为已在打折。本版落为正式状态枚举:发布时按 `now` 与 `start_at` 比较落 scheduled 或 active;**活动需在到达开始/结束时间时自动流转状态**(scheduled→active、active→ended),流转实现方式由技术方案定。**流转延迟不影响 C 端价格正确性**——C 端候选集判定同时校验状态与时间,时间未到即使状态未流转也不会生效。scheduled 活动可编辑、可提前结束,**不可删除**(与 active/paused/ended 一致——**只要发布过就不可删除**,无论后续是什么状态)。
**"已暂停"歧义消除**:paused 是可逆态(可随时恢复为 active),ended 才是终态。运营端状态标签需带 Tooltip 说明:"可随时恢复为进行中;如需彻底停止请用「结束活动」(不可恢复)"。
**状态存储分层说明**:paused 物理上落在规则层(promotion_rule.status=paused,即监控"一键暂停"的写入点),活动容器层(promotion.status)保留 draft/scheduled/active/ended 生命周期;1:1 模型下运营看到的活动状态 = 容器状态与规则状态的合成展示。分层保留 V2 活动容器多规则时"暂停单条规则≠暂停活动"的演进空间。
5. **操作记录**:运营端编辑页/详情页默认含操作记录区(操作时间/操作人/操作类型/操作详情);操作类型枚举:创建、编辑、发布、暂停、恢复、结束、删除、监控处置(告警侧)。
6. **空值显示**:运营端表格空值统一"—";上限类字段留空 = 不限。
6.1 **引用类下拉的展示格式(A1,硬性)**:凡引用外部模块实体的下拉选项,一律按「**名称(ID)**」展示,不得只显示名称。覆盖:商品标签(如 `夏季新品(TAG10021)`)、Collection(如 `Summer Essentials(C10001)`)、用户标签(如 `新客(UT2001)`)、品类、品牌。**已选中项在回显、详情页、导出文件中同样带 ID。**
7. **删除约束(A5/A4)**:**仅 draft 草稿可删除**;已发布过的活动(scheduled/active/paused/ended)**一律不可删除**,需要停用请用「结束活动」(终态、不可恢复)。**结束/删除弹窗均展示影响信息(名称/ID/已核销次数)。**

## 2.2 运营端 · 促销活动管理(页面型)

### 2.2.1 促销活动列表

**功能描述**:营销中心默认页,活动的查询、状态总览与操作入口。
**前置条件**:运营已登录后台(权限本期不分级)。
**页面元素**:
- KPI:进行中活动数 / 草稿数 / 本月累计核销次数 / 7 天内即将结束数
- 价格监控轻量入口:**左侧一级菜单「价格监控」的红色角标**(数字=待处理告警数,点击进入价格监控页);角标为 0 时不显示。**本版调整**:菜单由「优惠监控」更名为「价格监控」(该页监控的是商品到手价降幅,不是优惠本身),并由「营销中心」子项提升为一级菜单;「营销中心」分组保留,当前仅含「促销活动」。原列表页顶部告警 Alert 条已于 v1.1 移除——告警处置是价格监控页的职责,列表页常驻横幅挤占页面且与本页任务无关,改为全局菜单角标引导
- 筛选:关键词(活动名称/ID/优惠码)、状态(草稿/未开始/进行中/已暂停/已结束)、触发方式、起止日期、查询/重置
- 列表列:活动名称(+ID)、触发方式(自动折扣/优惠码+码值)、折扣内容(+封顶)、适用商品、市场(单值,A6)、状态(paused 带可恢复 Tooltip)、已核销(有效核销次数,整单退款回滚后自动核减)、生效时间、**创建信息(创建人 + 创建时间,两行)**、操作
- 默认排序:按创建时间倒序(全局约定 A.11)
- 头部操作:导出(当前筛选结果,含优惠码值列——兼作码投放的列表导出,D7)、新建折扣
- 操作(按状态驱动):详情、编辑(**draft / scheduled / paused**;进行中不可编辑,A5)、发布生效(draft)、暂停(active)、恢复上线(paused)、结束活动(scheduled/active/paused)、复制(可作模板复制后改所属市场,A6)、删除(**仅 draft**,红色)
  > **本版移除**:列表操作里的「操作日志」入口(A7)——操作记录已在详情页与编辑页作为区块常驻,列表再放一个入口属重复;列表操作应只放"改变活动状态"的动作。
- **操作列形态(规范 A.1.1)**:按该行自身的操作数**逐行判定**——操作数 ≤4 个全部平铺;>4 个则**前 3 个平铺、第 4 个起全部收进「更多」**下拉,可见元素恒为 4(3 按钮 + 更多)。排序优先级:详情 > 编辑 > 状态主操作(发布/暂停/恢复上线/结束)> 复制 > 删除。**各状态实际形态(本版按 A4/A5/A7 重算)**:

| 状态 | 操作数 | 平铺 | 更多下拉 |
|---|---|---|---|
| 草稿 | 5 | 详情 / 编辑 / 发布生效 | 复制 / 删除(红) |
| 未开始 | 4 | 详情 / 编辑 / 结束活动 / 复制 | —(全平铺) |
| 进行中 | 4 | 详情 / 暂停 / 结束活动 / 复制 | —(全平铺,**无编辑**) |
| 已暂停 | 5 | 详情 / 编辑 / 恢复上线 | 结束活动 / 复制 |
| 已结束 | 2 | 详情 / 复制 | —(全平铺,**无删除**) |
- **二次确认覆盖(A6,硬性)**:凡会改变活动状态或产生新数据的操作,**都要有二次确认弹窗**,不允许点了直接执行:

| 操作 | 确认弹窗要点 |
|---|---|
| 发布生效 | 发布后进入未开始/进行中(按开始时间判定);**发布后不可再删除**,只能结束 |
| 暂停 | 立即停止对新订单生效、C 端恢复原价;已产生的核销与订单优惠不受影响;后续可恢复上线 |
| 恢复上线 | 立即重新对新订单生效;提示确认配置已改完、且当前仍在有效期内 |
| 结束活动 | 立即停止且**不可恢复**;展示名称 / ID / 已核销次数(原有) |
| 复制 | 生成新草稿(名称加"副本"、核销归零、优惠码不复制);所属市场保存前可改选 |
| 删除 | 不可恢复;**仅草稿可删**(原有) |
| 告警处置(暂停 / 标记已处理 / 忽略) | 见 §2.3.2 |

- **复制规则**:复制生成 draft 新活动——名称加"副本"后缀;所属市场默认原值、保存前可改选(改市场时金额类字段清空,强制按新市场币种重录);圈选/条件/时间随模板复制;已核销计数归零;**优惠码不复制**(码类活动需重新生成或输入,避免优惠码全局唯一冲突)
**页面状态变体**:正常数据 / 零数据引导(新建折扣 CTA) / 筛选无匹配(清除筛选) / 网络异常(重试)。
**校验规则**:关键词模糊匹配活动名称、活动 ID、优惠码;日期范围与生效时间取交集。
**异常处理**:列表加载失败展示异常态;操作接口失败 Toast 提示并保持原状态;并发状态冲突(如他人已结束)提示"状态已变更,请刷新"。
**UI 关联**:运营端原型 v13 · 促销活动列表页(含 4 空态演示)。

### 2.2.2 新建 / 编辑折扣

**功能描述**:折扣活动的配置表单,7 分区;编辑页复用新建结构并追加操作记录区。
**前置条件**:新建无;**编辑仅 draft / scheduled / paused**——**进行中(active)的活动不可直接编辑**(A5,本版调整)。

**为什么进行中不让改**:改配置的瞬间 C 端仍在按旧规则成交,容易出现"运营以为改完了、买家还在用旧价下单"的窗口期,事后对账也说不清哪笔按哪版规则成交。改为强制走「**暂停 → 编辑 → 恢复上线**」三步,期间 C 端一律恢复原价,窗口期归零。
**各状态可编辑范围**:

| 状态 | 能否编辑 | 可改字段 | 说明 |
|---|---|---|---|
| draft 草稿 | ✅ | **全部字段** | 未发布,无任何约束 |
| scheduled 未开始 | ✅ | 见下方「已发布后可改清单」 | 已发布但未生效,改动不影响存量订单 |
| active 进行中 | ❌ **不可编辑** | — | **须先「暂停」转为 paused 再编辑**(A5) |
| paused 已暂停 | ✅ | 见下方「已发布后可改清单」 | 编辑完点「恢复上线」转回 active |
| ended 已结束 | ❌ | — | 终态 |

**已发布后可改清单**(scheduled / paused 适用):
- **锁定不可改**:所属市场(A6)、触发方式(自动/优惠码)、优惠码码值、折扣值类型(百分比/固定金额)
- **可改**:活动名称、适用商品圈选明细、适用用户、使用门槛、限次(总量**不得小于已核销次数**)、最大优惠封顶、生效起止时间
- 保存后触发保存前试算拦截(§2.2.3);恢复上线时触发监控增量扫描(§2.3.4)
**页面元素与字段**:

| 分区 | 字段 | 控件 | 必填 | 规则 |
|---|---|---|---|---|
| 基本信息 | 所属市场 market_id | 大卡片单选(美国/香港) | 是 | **第一字段**;决定全表单金额币种与生效时区;创建后锁定不可改(A6) |
| | 活动名称 promotion_name | 输入框 | 是 | 1-100 字符;作为**订单快照(rule_name)与运营后台识别**来源,**不直接用于 C 端展示**(C 端促销标签由折扣配置自动拼接,见 §2.4);建议带市场标识 |
| | 触发方式 trigger_type | 大卡片单选 | 是 | auto 自动折扣 / code 优惠码 |
| | 优惠码 code(trigger=code 时) | 输入框+随机生成按钮 | 是 | 手动输入或系统随机生成;防猜校验:长度≥8、字母数字混合、禁纯连续序列(如 ABC12345 合法,12345678 拒绝);**全局唯一**——不同活动不可使用同一优惠码(含不同市场也不可重复);不区分大小写去重(统一转成大写后存储);V1 不提供码级单独停用(码随活动暂停/结束即失效),promotion_code.status=disabled 为 V2 定向多码预留 |
| 折扣内容 | 折扣值类型 value_type | 单选 | 是 | percentage 百分比 / fixed 固定金额 |
| | 折扣百分比 percentage_value | 数字(1-100,% off) | percentage 时必填 | 全市场统一;整数 |
| | 固定减价金额 fixed_amount | 数字(带所属市场币种符号) | fixed 时必填 | >0;不得 ≥ 圈选商品该市场最低原价(保存时试算校验提示) |
| | 最大优惠封顶 max_discount_amount | 数字(带币种符号) | 否 | percentage 时可配;留空=不封顶;>0 |
| 适用商品 | 适用范围 product_scope | 单选 | 是 | all 全部 / category 品类 / brand 品牌 / **tag 商品标签** / **collection** / listing 指定商品(限所属市场在售) |
| | 商品标签(product_scope=tag) | 多选 | 是 | 引用**商品模块「标签管理」**的标签;可多选,**命中任一标签即适用(OR)**;标签定义与打标归商品模块,营销侧仅引用不定义 |
| | Collection(product_scope=collection) | 多选 | 是 | 仅可选**与活动同市场**且 status=active 的 Collection;可多选,**命中任一即适用(OR)**;商品池由 Collection 模块维护(手动选品+规则选品),池内商品变化时命中范围**实时跟随**,营销侧不定义选品规则 |
| | 圈选明细 promotion_target | 多选/商品选择器 | 非 all 必填 | 至少 1 项;指定商品按在售 listing 圈选,支持**按商品 ID 批量导入**(见下) |

**指定商品的两种加入方式(A2 本版新增)**:

| 方式 | 适用 | 说明 |
|---|---|---|
| 从商品库选择 | 少量、需要看图确认 | 原有能力 |
| **按商品 ID 导入** | 批量、运营手里已有 ID 清单 | 粘贴一批 listing ID,**一行一个,也支持逗号/空格分隔** |

**导入的解析与回显规则**:
1. 粘贴后点「解析」,系统按分隔符切分并去重
2. 逐个校验,分成两组回显:**有效**(存在 + 在售 + 属于本活动所属市场)、**无效**(逐条给原因:商品不存在 / 已下架 / 不属于本市场)
3. 顶部汇总「识别 N 个:有效 M 个、无效 K 个」;无效清单以表格展示并提供「复制无效 ID」按钮,供运营拿去排查
4. 点「加入有效商品(M 件)」**只把有效的加进圈选**,无效的不静默丢弃也不阻塞整批
5. **不做 Excel/CSV 文件上传**:V1 圈选量级有限,文件上传要额外处理编码、模板与格式校验,收益不匹配;后续确有大批量需求再评估
**页面元素与字段(续上表)**:

| 分区 | 字段 | 控件 | 必填 | 规则 |
|---|---|---|---|---|
| 使用条件 | 使用门槛 min_type | 单选 | 是 | none / amount 满额 / quantity 满件 |
| | 满额门槛 min_amount | 数字(带币种符号) | min_type=amount 时必填 | >0,按所属市场币种。**这是门槛不是减免方式**:达标后,命中的**每件**商品各按折扣值减免(V1 为商品级折扣)。如需"整单只减一次"请等 V2 订单级折扣 |
| | 满件数量 min_quantity | 数字(件) | quantity 时必填 | **≥2 整数**(A3 本版收紧),全市场统一。同上——门槛达标后**每件**各减,非整单减一次 |
| | 总使用次数 total_usage_limit | 数字 | 否 | ≥1;留空=不限;编辑时不得小于已核销次数 |
| | 每人使用次数 per_user_limit | 数字 | 否 | ≥1;留空=不限;默认建议 1 |
| 生效时间 | 起止时间 start_at/end_at | 时间范围 | 开始必填 | 结束留空=长期;结束>开始;按所属市场本地时区判定 |
| 适用用户 | 适用用户 eligibility_type | 单选 | 是 | all 全部(默认)/ tag 指定用户标签;自动折扣与优惠码均受约束 |
| | 用户标签 | 多选(tag 时) | tag 必填 | 引用用户管理模块已有标签(含"新客"等),可多选,命中任一即适用;**标签定义与打标规则归用户管理模块,营销侧仅引用不定义** |

**门槛取值校验(A3,本版新增)**:满件数量**最小为 2**——填 1 等同于"无门槛",与 `min_type=none` 语义重复,运营配出来只会让人误以为有门槛;保存时校验拦截并提示"满件数量需 ≥2;若不设门槛请选「无门槛」"。

**操作流程**

| # | 步骤 | 说明 |
|---|---|---|
| 1 | 填写表单 | 7 个分区(基本信息 / 折扣内容 / 适用商品 / 使用条件 / 生效时间 / 适用用户) |
| 2 | 提交 | 新建:「保存并发布」或「存为草稿」;编辑:「保存」 |
| 3 | 保存前价格试算 | 弹窗展示抽样到手价与风险(§2.2.3);**存为草稿跳过此步**(未发布无资损) |
| 4 | 确认落库 | 按状态生效(draft / scheduled / active),返回列表 |

**分支**:试算发现降幅超阈值 → 返回修改;字段校验失败 → 定位到对应分区并标红。

**校验时机**:字段失焦即时校验 → 提交时全量校验 → 金额字段按币种做区间合理性校验(>0,≤该市场最高原价)。

**交互说明**(按分区列):

| 分区 | 交互规则 |
|---|---|
| 基本信息 · 所属市场 | **下拉选择**,选项来自 market 模块的已开设市场;选中后行内实时提示「金额以 X 录入 · 按 XX 基准时区判定生效」;**编辑态禁用**(A6 活动-市场 1:1) |
| 基本信息 · 触发方式 | **普通单选**(自动折扣 / 优惠码),说明文案随选项联动 |
| 折扣内容 · 金额类字段 | 币种符号随所属市场联动展示 |
| 适用商品 · 指定商品标签 / 指定 Collection | 选中后展开对应多选;**Collection 下拉只列出与所属市场一致且已上线(active)的集合**,切换市场时清空已选 |
| 适用商品 · 所有引用类下拉 | 统一「名称(ID)」格式(§2.1-6.1) |
| 适用用户 | 选「指定用户标签」时展开标签多选 |
| 全局 | 已发布活动(scheduled/paused)保存时二次确认「保存后需点『恢复上线』才重新生效」 |

**异常处理**:保存接口失败保留表单内容并提示;优惠码重复提示「该码已存在」;商品圈选对象已下架时保存不拦截(下单时动态判定,见 §2.8)。

### 2.2.3 保存前价格试算(资损事前拦截,机制+弹窗)

**功能描述**:发布(含进行中编辑保存)前,系统对圈选商品逐市场试算到手价,弹窗展示抽样结果与风险,运营确认后才落库。
**触发条件**:点"保存并发布"/进行中活动"保存"。
**处理流程**:
1. 系统按当前配置计算圈选商品到手价(仅计本折扣;若该商品同时命中其他进行中折扣,按 §2.8.3 规则二的整单最优组合口径参与试算)。**带门槛的折扣按单件挂牌价判定门槛**(与 §2.8.2 规则一口径一致)——不达标的商品在试算结果中标注"需凑单达标",不计入其到手价
2. 弹窗展示:命中商品总数、抽样商品明细(现价/到手价/降幅)、降幅最大项
3. 存在降幅 > 全局监控阈值(§2.3.4)的商品 → 顶部警示,抽样必含该商品,降幅标红
4. 运营选择:返回修改 / 确认无误保存(弹窗操作记入操作记录)
**规则说明**:抽样规则=降幅 Top3(不足 3 件全量);试算仅为提示不强制阻断(V1 无审批流,确认权在运营)。
**异常处理**:试算服务超时 → 提示"试算暂不可用",允许"跳过试算继续保存"(记录操作日志"未试算发布")。
**UI 关联**:运营端原型 v13 · 价格试算确认弹窗(PriceCheckModal)。

### 2.2.4 活动详情

**功能描述**:活动信息只读展示 + 核销记录查询;操作入口与列表页一致(共享弹窗)。

**状态可见性(硬性,本版明确)**:活动详情对**全部状态均可访问**(draft / scheduled / active / paused / **ended**),两个 Tab **均不随状态隐藏或降级**。
- **已结束(ended)的活动同样可以查看核销记录与完整规则配置**——谁在什么时候用了这个折扣、当时的门槛/折扣值/封顶/适用范围是什么,都要能查到
- 这是**「已发布过的活动一律不可删除」(§2.1-7)的配套要求**:禁止删除是为了保住追溯能力,若 ended 活动查不到核销记录与规则,禁删就失去意义
- 追溯口径:核销记录展示成交时快照,**不随活动后续变更而改变**

**页面元素**:
- 基本信息 Tab:活动 ID/名称/触发方式(码值)/状态/折扣类型与内容/最大优惠封顶/适用商品/所属市场/每人限用/已核销次数/生效时间/创建信息 + 操作记录区
- 核销记录 Tab:KPI(累计有效核销/已回滚/累计优惠金额[数据来自订单 order_discount 汇总])、筛选(状态/时间)、列表(核销时间/用户/订单号/优惠金额/状态[有效|已回滚,回滚行金额划线,悬浮显示回滚时间 reverted_at])、导出(导出文件含回滚时间列)
**异常处理**:核销列表加载失败展示异常态;优惠金额汇总来自订单侧,加载失败单独显示"—"并提示。
**UI 关联**:运营端原型 v13 · 活动详情页(两 Tab)。

### 2.2.5 共享弹窗(列表页与详情页共用)

| 弹窗 | 触发 | 内容与按钮 |
|---|---|---|
| 结束活动 | active/paused 的"结束活动" | 警示(结束后立即停止对新订单生效且不可恢复;已产生核销与订单优惠不受影响)+ 活动名/ID/已核销次数;取消 / 确认结束(红) |
| 删除折扣 | **仅 draft** 的"删除" | 警示(不可恢复);展示影响信息(名称/ID/已核销次数);取消 / 确认删除(红) |

## 2.3 运营端 · 价格监控(页面型)

### 2.3.1 告警列表

**功能描述**:到手价降幅监控告警工作台(独立二级菜单),发现→排查→处置闭环。
**页面元素**:
- 头部:监控设置入口、导出
- KPI:今日新增告警 / 待处理 / 本周已处置 / 监控中活动数
- **成因列口径**:由 §2.3.4 扫描时判定并落 `cause_type`;它决定排查方向与可用处置动作,是本版新增的关键分流字段
- 筛选:状态、活动、市场、降幅区间、时间范围
- 列表列:告警时间、商品(名称+listing ID)、**成因**(折扣配置 / 挂牌价下调 / 两者叠加)、命中活动(可多条,**逐条标注「生效 / 未生效」**,B3;纯挂牌价成因时为空显示「—」)、市场、**价格对比(按类型区分基准:cumulative=原价→当前到手价;sudden_drop=上次到手价→本次到手价,辅注原价)**、**降幅**、状态、操作(排查;pending 另有忽略)
- **降幅列口径(本版调整)**:原独立的"类型"列已取消,比较基准直接写进降幅列——第一行是触发本次告警的那个降幅(含基准与阈值),第二行是另一维度的参考值:
  - cumulative:`较原价 -55% /阈值50%`(单行)
  - sudden_drop:`较上次 -25% /阈值20%` + 第二行 `较原价 -40%`(参考,未超阈值不显示阈值)
  取消独立类型列的原因:"类型"本身是抽象命名,运营看了仍需再查比较基准;把基准写进数据列后信息自解释,页面也少一列。类型名**仅保留在筛选器中**(排查抽屉内不展示类型,抽屉以"成因"与"价格对比"表达),措辞统一为大白话:`比原价降太多` / `比上次降太多`(枚举 key `cumulative` / `sudden_drop` 不变)
- 筛选增加:告警类型、**成因**
**状态机(告警)**:

| 枚举值 | 含义 | 进入条件 | 退出条件 |
|---|---|---|---|
| pending 待处理 | 新告警 | 扫描发现降幅超阈值且该商品+市场无未处置告警 | 处置→resolved/ignored |
| resolved 已处理 | 已处置 | 运营"标记已处理"(备注必填);记录处置动作/人/时间 | 终态 |
| ignored 已忽略 | 预期内降幅 | 运营"忽略"(列表行或抽屉内) | 终态 |

**告警类型(双阈值监控)**:

| 枚举值 | 含义 | 触发条件 | 记录内容 |
|---|---|---|---|
| cumulative **比原价降太多** | 深折监控 | 到手价相对**商品原价**的累计降幅 > 累计降幅阈值(默认 50%) | 原价/到手价/累计降幅/阈值快照/链路快照 |
| sudden_drop **比上次降太多** | 突变监控(捕捉折扣力度调整等配置变更导致的价格跳水) | 当前到手价相对**上一次扫描到手价**的单次降幅 > 环比降幅阈值(默认 20%),即使累计降幅未超阈值 | 上次到手价(prev_final_price)/当前到手价/环比降幅(change_pct)/阈值快照/链路快照 |

**告警生成与去重规则**:系统按 §2.3.4 的监控范围计算在售商品各市场的到手价,按上表双阈值分别判定并落告警(一次判定可同时触发两类)。**环比比较的基准 = 该商品该市场上一次计算得到的到手价**。同一商品+同一市场+**同一告警类型**已存在 pending 告警时不重复生成,更新该告警至最新;处置后再次超阈值则生成新告警。
**UI 关联**:运营端原型 v13 · 价格监控列表页(含 4 空态)。

### 2.3.2 告警排查(抽屉)

**功能描述**:单条告警的排查与处置,核心是价格计算链路拆解。
**页面元素**:商品/市场/告警时间/**成因**/**价格对比**(按类型区分基准,同列表列口径)/累计降幅(对比阈值)/突降幅度(比上次降太多类:上次到手价→当前到手价+单次降幅,对比环比降幅阈值)/状态与处置记录;**不展示"告警类型"**(类型只在列表筛选器出现);**价格计算链路表**(环节/命中规则/变动金额/小计,来自 calc_snapshot 快照,非实时重算;纯挂牌价成因时链路只有"挂牌价"一个环节);主因初判提示;处置区(仅 pending)。

**处置区按成因分流(本版新增)**:

| 成因 | 处置区展示 |
|---|---|
| `discount` / `both` | **只提供「实际生效那一条」活动的暂停入口**(B3 本版修正) + 处置备注 + 标记已处理 + 忽略本条;`both` 另加提示"本次降幅同时含挂牌价下调,暂停活动后仍需到商品后台核实商品价" |
| `listing_price` | **不出「暂停活动」按钮**(无活动可暂停或活动并非成因) → 改为「查看商品」(跳商品后台该 listing)+ 处置备注 + 标记已处理 + 忽略本条;并显式提示:**挂牌价异动需到商品后台核实,营销侧无法直接处理** |

> **B3 口径澄清(本版新增)**:V1 一律不叠加 ⇒ 一个商品**最终只生效一条**折扣,但它可以**命中多条**(只是取优惠最大的那条生效)。所以「命中活动」列可能有多条,需**逐条标注「生效 / 未生效」**;处置区**只对生效那一条**提供暂停入口——暂停未生效的活动对当前降幅毫无作用,反而会误伤其他商品的正常促销。

**处理流程**:
1. 一键暂停活动(仅 `discount`/`both`,且**只针对生效那一条**)→ 该活动 status→paused(即时对 C 端止损),告警记录 handle_action=pause_promotion;**告警不自动转已处理**——暂停后该商品可能落到原先"未生效"的次优折扣上、降幅仍可能超阈值,需运营确认后手动"标记已处理"
1.2 **三个处置动作(暂停 / 标记已处理 / 忽略)均需二次确认**(A6)
1.1 查看商品(仅 `listing_price`)→ 跳转商品后台;运营核实后回本页手动"标记已处理"或"忽略";若确认为误操作改价,由商品侧改回,下一轮扫描到手价回升即不再新增告警(已有 pending 告警仍需人工收口),handle_action=notify_product
2. 标记已处理 → 备注必填 → status→resolved,记录处置人/时间/动作
3. 忽略 → status→ignored(适用预期内深折,如清仓)
**异常处理**:暂停活动失败(已被他人结束等)提示并刷新;快照缺失时链路区显示"快照缺失,仅展示汇总"。
**UI 关联**:运营端原型 v13 · 告警排查抽屉(AlertDrawer)。

### 2.3.3 监控设置(弹窗)

**功能描述**:全局监控参数与告警通知渠道配置。
**字段**:

| 分组 | 字段 | 控件 | 必填 | 规则 |
|---|---|---|---|---|
| 阈值 | 累计降幅阈值 | 数字(%) | 是 | 默认 50,范围 1-95,全局唯一(按活动/品类覆盖 V2) |
| | 环比降幅阈值 | 数字(%) | 是 | 默认 20,范围 1-95,全局唯一(按活动/品类覆盖 V2) |
| 范围 | 监控范围 | 只读 | — | 固定"全部进行中活动命中的在售商品" |
| 通知 | 站内提醒 | 只读 | — | **常开不可关**:待处理告警数以红色角标展示在左侧「价格监控」一级菜单上 |
| | **飞书群通知** | 单选(开/关) | 是 | **V1 新增**。开启后每轮扫描若有新增告警,向指定飞书群推送一条汇总卡片 |
| | **Webhook 地址** | 输入框 + 发送测试 | 飞书通知开启时必填 | 取自飞书群「设置 → 群机器人 → 添加自定义机器人」;**页面仅展示脱敏值(仅尾部 4 位可见)**,存储方式由技术方案定;保存前可点「发送测试」向该群发一条测试卡片自验 |
| | 推送策略 | 只读 | — | 每轮扫描聚合推送一条,本轮无新增告警则不推送(见 §2.3.4) |

> **阈值命名与评审用语对照**:「累计降幅阈值」= 评审说的"**到手价与挂牌价**的降幅阈值";「环比降幅阈值」= 评审说的"**当前到手价与历史到手价**的降幅阈值"。两者本就是现有的两个阈值,本版只统一措辞、未新增阈值。
>
> **触发时双阈值留痕(B1)**:告警落库时**两个阈值都要快照**(`cumulative_threshold_pct` + `change_threshold_pct`),不能只存"触发类型对应的那一个"——事后复核要能还原当时的完整配置,否则改过阈值就说不清当时到底按什么判的。

**规则说明**:
1. 阈值修改即时生效于下一轮扫描;修改记录进操作日志。阈值与 Webhook 配置均为**全局系统配置项,不落 ER 业务表**。
2. **通知渠道选型依据**:采用飞书**群自定义机器人 webhook**(后端 HTTP POST 即可,无需申请应用权限、无需维护 token)。告警为广播型场景(发运营群),V1 不做定向 @ 责任人——那需要自建应用 `im/v1/messages` + 运营账号与飞书 user_id 映射,列入 V2。
3. **安全**:Webhook 地址属敏感配置——**页面只展示脱敏值(仅尾部 4 位可见)、不得在操作日志中留明文**;存储方式与飞书侧签名校验(secret)的启用由技术方案落实。
4. **失败处理(V1 简化)**:推送失败仅记系统日志,**不落业务表、不在告警记录上标推送状态**;运营通过「发送测试」自验配置是否可用。站内角标不依赖飞书通道,飞书不可用不影响告警本身。
**UI 关联**:运营端原型 v13 · 监控设置弹窗。

### 2.3.4 扫描机制(机制型)

**监控范围**:到手价的下跌**不只由折扣造成**——挂牌价被改低同样会让买家看到的价格跳水。因此监控范围为**全部在售商品**,**含未被任何折扣命中的商品**(补上"无折扣商品挂牌价异动"的盲区);**下架 / 售出商品不在监控范围**(已不对外展示)。

**全量触发场景清单**:任何会改变"到手价"的动作,系统**都必须能识别到**。到手价 = 挂牌价 − 生效折扣减免,故触发源分两类:

| 类别 | 场景 | 是否需识别 | 影响面 |
|---|---|---|---|
| **挂牌价侧** | 商品改价(含红布林同步价变动) | ✅ 需识别 | 该 listing |
| | 商品上架 / 重新可售(退款回可售) | ✅ 需识别 | 该 listing |
| | 商品下架 / 售出 | ❌ **不在监控范围**(已不对外展示) | — |
| **折扣侧** | 活动**发布生效**(draft→scheduled/active) | ✅ 需识别 | 该活动命中的全部商品 |
| | 活动**到达开始时间**(scheduled→active,自动流转) | ✅ 需识别 | 同上 |
| | 活动**编辑保存后恢复上线**(paused→active) | ✅ 需识别 | 同上 |
| | 活动**暂停 / 结束 / 到期**(→paused / ended) | ✅ 需识别 | 同上(到手价**回升**,用于消解既有告警的复现) |
| | 圈选范围变更(改品类/品牌/标签/Collection/指定商品) | ✅ 需识别 | 变更前后命中集合的**并集** |
| | **Collection 商品池变化**(池由 Collection 模块维护) | ✅ 需识别(视作商品命中关系变化) | 进出池的 listing |

> **注意"回升"也要识别**:活动暂停/结束后到手价回升,若不重新计算,环比比较的基准会停在低位,下一轮正常价反而被算成"暴涨",或让后续真实下跌被掩盖。

> **本节只规定"必须能识别到哪些变化"这一结果要求**。以何种方式识别(周期性重算 / 事件驱动 / 两者结合)、频率、以及识别不到时的补偿手段,**均由技术方案确定**,本 PRD 不作约束。


**处理流程**:对需监控的商品 × 市场 → 按 §2.8.2 规则一(单品到手价)计算 → 分别与商品原价(累计)、上一次的到手价(环比)比对 → 超对应阈值按去重规则落告警,**并判定告警成因(见下)** → 更新到手价基线 → **本轮结束后,若有新增告警且飞书通知已开启,聚合推送一条飞书卡片**。

**告警成因判定(本版新增 `cause_type`)**:对比本次与上次扫描的两个输入量——挂牌价、生效折扣减免额:

| 成因 | 判定条件 | 排查方向 | 可用处置 |
|---|---|---|---|
| `discount` 折扣配置 | 挂牌价未变,减免额变大 | 折扣力度/圈选配置 | 暂停命中活动 + 标记已处理 / 忽略 |
| `listing_price` 挂牌价下调 | 减免额未变(含恒为 0),挂牌价变低 | 商品侧改价是否正确 | **无活动可暂停**;查看商品 + 标记已处理 / 忽略 |
| `both` 两者叠加 | 挂牌价变低**且**减免额变大 | 两边都要看 | 同 `discount`(可暂停活动),但需一并核实挂牌价 |

- **无折扣商品的告警只会是 `listing_price`**,此时「命中活动」列为空、价格计算链路快照只有"挂牌价"一个环节
- **累计降幅对无折扣商品恒为 0**(到手价 = 挂牌价),故这类商品实际由**环比降幅**捕获;累计阈值仍只对折扣力度有意义

**飞书聚合推送规则(V1 新增)**:
- **推送时机**:每轮扫描结束后推送一次;本轮**无新增**告警(含仅更新既有 pending 告警的情况)则**不推送**
- **卡片内容**:标题「价格监控:本轮新增 N 条告警」+ 按降幅倒序取 **TOP 5** 明细(商品名 / 市场 / 降幅与基准 / 阈值)+ 「共 N 条待处理」+ **「去处理」按钮**(跳转后台价格监控列表)
- **为什么聚合不逐条**:一次配置失误可命中数百件商品,逐条推送会刷屏并导致运营屏蔽机器人,反而漏掉真正重大的告警

**规则说明**:扫描口径与 C 端到手价一致(仅自动折扣,同商品取优惠最大一条);监控只针对在售商品,售出/下架商品不扫描。

## 2.4 C 端 · 商详页与商品卡片营销展示(页面型)

**功能描述**:商详页与商品卡片的价格展示。**营销侧对任何在售商品都统一输出到手价**(无折扣时 = 挂牌价),商详据此决定展示促销价格组还是常规价格组。
**前置条件**:商品在售、当前市场在投放范围。**不再要求"必须命中折扣"**——未命中折扣同样要拿到到手价(§2.8.2 规则一)。

**页面元素**

**A. 商详页价格区**(以 PC 商详本期主帧 `looply PC 商详页 — 营销样式更新` 为版式依据)

价格区各元素**同一行横排**,自左至右**排列顺序固定**(D7-7):

| 序 | 元素 | 视觉形态 | 出现条件 |
|---|---|---|---|
| 1 | **现价(到手价)** | 行首、**大号加粗** | 恒有 |
| 2 | **划线原价** | 紧邻现价右侧、灰色 line-through | 按下方「划线价与 Save 口径」表有值才出 |
| 3 | **Save 徽章** | **浅紫底 pill**(圆角实底色块) | Save > 0 才出 |
| 4 | **活动规则标签** | **紫色描边票券形**(带**齿孔** + **虚线分隔**) | 命中折扣才出;文案按下方模板自动拼接,**不取活动标题** |

> **⚠️ Save 徽章与活动规则标签是两种不同的视觉组件,不可用同一个组件实现**(D7-7)。Save 徽章 = **浅紫底 pill**、内容为金额差值(如 `Save $1`);活动规则标签 = **紫色描边票券形**(齿孔 + 虚线分隔)、内容为规则文案(如 `20% off`)。两者可同时出现在同一行,开发易做成同一种样式,需特别注意。

**B. 价格区下方**:**税费说明行**——商详模块既有元素、非营销新增,但属**价格区版式的一部分**,营销改版后仍位于价格区正下方,**排版时不要漏排**(D7-7)。

> **本期不含以下元素**(D4 / D6):
> - **FTC 合规说明小字**(「划线价为本商品的标准列表价」)——PC 商详设计稿价格区下方只有税费说明行,无此文案位(D4)
> - **折扣率标签**(如 `-20%`)——设计稿只有**一个**票券形规则标签,折扣信息**只由活动规则标签一个元素承载**,不再是「折扣标签 + 活动规则标签」两个并列元素(D6)
> - **「用码另减」提示**(`Extra $X off with code XXX at checkout`)——PC 商详无此元素(D6)

**C. 商品卡片**(列表页 / 推荐位 / 搜索结果等):**现价 + 划线原价 + Save 徽章**,**无折扣标签**;样式**以各模块卡片设计稿为准**(D6)。

> 说明:本期商详改动稿中的推荐位卡片区域**位于画板高度之外、已被裁切,在画布上不可见**,是从基础版复制而来的残留结构,**不构成视觉规范**,不得作为卡片样式依据。

**活动规则标签的自动拼接(C3)**

C 端展示的促销标签**由折扣配置自动拼接生成**,不再直接取活动标题(`promotion_name`)。原因:活动标题是运营给自己看的管理名(如"夏季大促 · 箱包 8 折"、"618 返场"),既可能不含优惠信息、也可能与实际配置不符;买家需要的是"这个优惠到底是什么"。

**拼接模板**(按「使用门槛 × 折扣值类型」六种组合)。**下表英文即 C 端实际展示的源文案,开发按此实现**;其他语种由语言包基于这份英文产出:

| 使用门槛 | 百分比折扣 `percentage` | 固定金额折扣 `fixed` |
|---|---|---|
| 无门槛 `none` | `{P}% off` | `{Amount} off` |
| 满额 `amount` | `Spend {Threshold}, get {P}% off` | `Spend {Threshold}, get {Amount} off` |
| 满件 `quantity` | `Buy {N}+, get {P}% off` | `Buy {N}+, get {Amount} off` |

**变量取值**:`{P}` = `percentage_value`(**直接取值不换算**,该字段存的就是 off 比例)｜`{Amount}` = `fixed_amount`｜`{Threshold}` = `min_amount`｜`{N}` = `min_quantity`;金额按所属市场币种符号与语种数字格式渲染。

- **有封顶时追加**:`(up to {Cap})`,`{Cap}` = `max_discount_amount`。**只挂在百分比三格上**——封顶字段仅 percentage 可配(§2.2.2),固定金额模板永不带
- **满件门槛 ≥2**(§2.2.2),故 `Buy {N}+` 语义成立

**六种组合渲染样例(验收基准)**:

| 组合 | 配置 | 英文(实际展示) | 中文(仅供理解) |
|---|---|---|---|
| 无门槛 × 百分比 | P=20 | `20% off` | 8 折 |
| 无门槛 × 百分比 + 封顶 | P=20, Cap=$100 | `20% off (up to $100)` | 8 折，最高减 $100 |
| 无门槛 × 固定 | $80 | `$80 off` | 立减 $80 |
| 满额 × 百分比 | 满 $300, P=20 | `Spend $300, get 20% off` | 满 $300 享 8 折 |
| 满额 × 固定 | 满 $300, $80 | `Spend $300, get $80 off` | 满 $300 减 $80 |
| 满件 × 百分比 | 满 2 件, P=20 | `Buy 2+, get 20% off` | 满 2 件享 8 折 |
| 满件 × 固定 | 满 2 件, $80 | `Buy 2+, get $80 off` | 满 2 件减 $80 |

> **溢出约定**:最长串 `Spend $300, get 20% off (up to $100)` 约 38 字符,而票券标签是窄组件——**单行不换行,超出容器按省略号截断**;具体最小宽度由设计定。
>
> **百分比在不同语种是两套模板,不是同一串做替换**:`percentage_value` 存的是 **off 比例**(1-100)。英文直接取值渲染 `{P}% off`;中文按折率习惯渲染,换算 `折率 = (100 − percentage_value) ÷ 10`,非整十时保留一位小数(`20 → 8 折`、`15 → 8.5 折`、`33 → 6.7 折`)。**英文为源文案**,中文由语言包另写一套,开发不得用同一串做字符串替换。

**多语言口径(重要)**:规则标签是**「模板 + 变量」而非运营录入的文本**,因此:
- 模板本身走**前端语言包**(§1.7 A 段静态文案),各语种各写一套
- 变量(金额/百分比/件数)由前端按语种的数字与货币格式渲染
- **不进翻译服务**——它没有"原文"可翻,与 §1.7 B 段"折扣力度标签为计算值非录入文本、不接翻译"是同一口径


**下游取价改造要求(C1)**:商详 / 购物车 / checkout **不得再直接取商品挂牌价当展示价**,一律改为调用营销的到手价计算服务(§2.8)。

| 页面 | 改造前 | 改造后 |
|---|---|---|
| 商详 / 商品卡片 | 直接取 `listing_price` | 调 §2.8.2 规则一,取返回的**到手价**(无折扣时该值 = 挂牌价) |
| 购物车 | 行价直接取 `listing_price` | 调 §2.8.3 规则二(按勾选集合),取各行优惠与汇总 |
| checkout | 同上 + 码 | 调 §2.8.3 规则二(全量,含优惠码) |

> 营销侧已保证**任何在售商品都有到手价返回**(无折扣时 = 挂牌价、减免 = 0,见 §2.8.2 第 3 步),所以下游不需要写"有没有促销"的分支,统一取一个字段即可。

**划线价与 Save 口径(与商详模块对齐)**:价格展示逻辑归**商详模块**(商详 PRD v1.8 §2.7),营销侧只负责供给到手价。两种场景的取值:

| 场景 | 现价 | 划线价 | Save |
|---|---|---|---|
| **有折扣**(减免 > 0) | 到手价 | **挂牌价** `listing_price` | **挂牌价 − 到手价** |
| **无折扣**(减免 = 0) | 挂牌价 | 对比价 `compare_at_price`(有且 > 挂牌价时;否则不展示划线价) | 划线价 − 挂牌价 |

> **划线价口径已定案(2026-07-28)**:**有折扣时,划线价取 `listing_price`(挂牌价)**,不取 `max(listing_price, compare_at_price)`。
> **理由**:若按 max 取值,当对比价高于挂牌价时,`Save` 会把"零售参考价与平台售价的差"也算进促销优惠——那部分不是本次活动省下来的钱,属**虚增促销力度**,有 **FTC reference pricing 合规风险**。
> **举例**:原始零售价 $2,000 / 平台挂牌 $1,200 / 促销价 $1,000 —— 按本口径 `Save = $200`(本次活动真实省下的);按 max 口径 `Save = $1,000`(把"本来就比专柜便宜的 $800"也算成了促销力度)。
> 本模块 §2.4 与 §2.8.2 **均已按该口径写定,无待回改项**。

**展示规则**:
- 到手价口径 = §2.8.2 规则一(仅自动折扣、门槛按本商品挂牌价判定、取减免最大一条、不判用户与限次、封顶生效)
- **门槛类折扣(满额/满件)**:按 §2.8.2 规则一以**本商品挂牌价**判定门槛——**达标即计入到手价、改变价格位**(单买这一件就能享);**不达标**则不计入价格,仅以**活动规则标签**表达(如 `满 $100 减 $20`),引导买家凑单,此时价格区不出划线价与 Save 徽章
- **未命中任何自动折扣(减免 = 0)**:到手价 = 挂牌价,价格区走商详模块的常规价格组(现价 = 挂牌价、划线价 = 对比价、Save = 划线价 − 挂牌价),**不出活动规则标签**与促销价样式
- **商品列表页/推荐位等商品卡片**:同到手价口径展示**现价 + 划线原价 + Save 徽章**(单品维度);样式**以各模块卡片设计稿为准**(D6)
- 适用用户限定(指定标签)的折扣:商详无登录用户上下文时按"可能可享"展示到手价,加购/结算按登录用户校验,不符合则该优惠不生效并提示(避免商详虚报);V1 商详不做用户级隐藏
- 活动暂停/结束/商品移出投放市场后,C 端即时恢复原价展示

**异常处理**:促销数据获取失败 → 降级展示原价(不阻塞商详),Save 徽章与活动规则标签一并不展示;到手价计算结果 ≥ 原价 → 不展示促销组(防错配反向展示)。
**UI 关联**:C 端 Figma 设计稿,本期帧见 **§七.1 帧索引**;本地 `UI/` 旧 html 仅历史参考,不作开发依据。

### 2.6.2 优惠码的不叠加规则(本版重写)

> **为什么不再是「单订单只能用 1 个码」**:优惠码的本质是「**需要输码才触发的折扣**」,它与自动折扣**同属候选折扣池**,受 §2.8.3 **同一套不叠加约束——每个商品行至多生效一条折扣**。约束的对象是「**商品行**」,不是「订单」。此前 v1.8 及以前写的「V1 单订单仅支持输入 1 个优惠码」,实际只描述了**单商品进入 checkout** 这一种场景,不能用来限制所有场景。**这不是放宽限制,而是把限制放回它本来的粒度上。**(D2)

**正确规则**:

| # | 规则 | 说明 |
|---|---|---|
| 1 | 码与自动折扣**同池竞争** | 二者一并参与 §2.8.3 最优组合求解,**每个商品行至多生效一条**(自动折扣或码,二选一取优) |
| 2 | **一单可以有多个码同时生效** | 前提是它们**作用于不同商品行**——与 §2.8.3「不同商品各享各的、等同于分开下单」是**同一条规则** |
| 3 | **单商品场景最多一个码生效** | 只有一个商品行 ⇒ 至多一条折扣 ⇒ 再输新码时,若新码更优则**自然替换**旧码。这是**最优组合求解的结果,不是为单商品写的特殊逻辑**,开发不需要单独实现「替换」分支 |

**每次 Apply 的处理顺序(硬性,按序执行)**:(D2)

| 步 | 动作 | 不通过时 |
|---|---|---|
| 1 | **校验该码自身**:码存在且活动进行中 → 商品范围命中 → 门槛达标 → 适用用户命中 → 限次未用尽 → 市场匹配 | 任一不通过 → 按 §2.6.4 失败态提示,**不加入已应用集合** |
| 2 | 通过后加入已应用集合 | — |
| 3 | **整单重新求最优组合**(§2.8.3,码与自动折扣同池参与) | — |
| 4 | 检查求解结果:该码是否**产生了实际减免** | 若被更优折扣挤掉、**不产生任何减免** → 按 §2.6.4 出**行内错误提示**(第 9 条 `You're already getting a better offer, so this code won't apply.`),**同样不加入集合**(避免 chip 显示一个无实际作用的码) |

**chip 与集合的一致性口径**:**chip = 当前实际生效的码**(集合内的码)。单商品场景下新码挤掉旧码时,**旧 chip 消失、新 chip 出现**;多商品场景下,作用于不同商品行的多个码 chip **并存展示**。(D2)

### 2.6.3 操作流程(优惠码)

输入码 → `Apply` → 按 §2.6.2 四步处理 → **成功**:chip 出现、`Discount` 行金额与 `Total`、主 CTA 金额同步刷新;**失败**:按 §2.6.4 在**输入框下方出行内红字**,**输入框内保留买家已输入的码**(不清空)、chip 不出现、金额不变 → 点 chip 上 `✕` **Remove** → 从集合移除并**整单重新求最优组合**(可能导致其他码/自动折扣重新生效)。

### 2.6.4 校验失败枚举

> **展示形式(v2.1 改定,以 Figma 为准)**:所有优惠码校验失败**以行内错误提示呈现**,位置为**优惠码输入框正下方**、`Subtotal` 之上。**不使用 Toast、不使用弹窗。**
>
> **PC 与移动端形态不同(刻意,不是设计稿有误)**:
>
> | 端 | 输入框 | 错误文案 | 依据 |
> |---|---|---|---|
> | **PC** | **边框保持原样、不变红** | 框下方一行红色小字 | Figma 帧 `looply PC Checkout — 营销code输入报错`(`5778:1667`) |
> | **移动端** | **转为错误态(红框)** | 框下方一行红色小字 | 移动端设计系统既有表单报错组件(`1013:16791`),与地址、验证码等字段同范式;移动端不单独出稿 |
>
> 两端均**复用各端设计系统既有的表单报错组件**,营销侧不新增视觉规范。
>
> **通用行为**:出错时**输入框内保留买家已输入的码**(不清空,便于修改重试);**chip 不出现、汇总区金额不变**(§2.6.3)。

>
> **成功态不出错误提示**——成功的反馈是 chip 出现 + `Discount` 与 `Total` 联动(§2.6.3),视觉已自洽。

| # | 失败原因 | **英文源文案(直接实现)** | 中文(仅供运营理解) |
|---|---|---|---|
| 1 | 码不存在 / 已停用 / 活动非进行中 | `This code isn't valid or has expired.` | 优惠码无效或已过期 |
| 2a | 未达**满额**门槛 | `Spend {Threshold} or more to use this code.` | 满 {门槛金额} 可用 |
| 2b | 未达**满件**门槛 | `Add {N} or more eligible items to use this code.` | 满 {件数} 件可用 |
| 3 | 总量已用尽 | `This code has been fully redeemed.` | 该优惠码已被领完 |
| 4 | 每人限次已用完 | `You've already used this code.` | 你已使用过该优惠码 |
| 5 | 与已享折扣互斥(V1 一律不叠加,该码作用的商品行已命中优惠更大的折扣) | `These items already have an offer applied.` | 所选商品已享其他优惠 |
| 6 | 商品范围不命中 | `This code doesn't apply to the items in your cart.` | 购物车内商品不适用 |
| 7 | 码所属活动市场 ≠ 买家当前市场 | `This code isn't available in your region.` | 不适用于当前地区 |
| 8 | 用户不符合适用用户(未命中任一指定用户标签) | `This code isn't available for your account.` | 不适用于当前账户 |
| 9 | **码的优惠力度不如当前已生效的自动折扣**(C4) | `You're already getting a better offer, so this code won't apply.` | 当前已享更大优惠,该码不生效 |

**变量**:`{Threshold}` = `min_amount`(带币种符号)｜`{N}` = `min_quantity`,与 §2.4 规则标签同名同源,前端可共用格式化函数。

**文案口径(新增条目时按此对齐)**:
- **不暴露内部术语**——全表无 rule / candidate / threshold / 候选集 / 门槛判定;「门槛」译为买家动作(Spend / Add)而非 threshold
- **语气克制**——陈述句 + 句号,不用感叹号、不用 Sorry / Oops
- **不指责买家**——第 4 条用 `You've already used this code.` 而非 `You've exceeded the usage limit.`
- **第 5 / 9 条刻意区分**:5 = 「这些商品已有优惠」(买家不知情),9 = 「你已享更大优惠」(明确告知);`offer` 一词统一,不混用 discount / promotion
- **第 2 条必须拆 2a / 2b**——满额与满件的买家动作完全不同(花钱 vs 加件),一个模板串塞不下

> **多语言口径**:上表文案为**「模板 + 变量」的静态 UI 文案**,与 §2.4 规则标签模板同处理——**英文为源文案写在本 PRD**,其他语种由语言包产出,**不进翻译服务**;变量(门槛金额 / 件数)由前端按语种的数字与货币格式渲染。

> **实现提示**:上表第 5 条与第 9 条在新模型下**判定同源**——均由 §2.6.2 第 4 步「求解后该码未产生任何减免」触发,区别仅在文案侧重(互斥 vs 力度不足)。技术实现可共用一个判定出口,文案由前端按上下文选择。**保留两条不合并**:两者触发场景与买家心智不同——前者是买家不知道商品已有自动折扣,后者是明确告知"已享更大优惠",分开对客服与买家更友好。(D2)

### 2.6.5 规则说明

- **多码生效口径**见 §2.6.2——**不再限制「单订单 1 个码」**,约束粒度为**商品行**(D2)
- **码不做预占**——Apply 仅校验可用性,使用次数的**唯一占用时点 = 支付成功核销**(§2.9)
- **支付发起前**系统对码做总量/每人限次**二次校验**,失败则提示码已失效并重算(并发用尽场景)
- 订单摘要各优惠金额为**试算分摊结果**(§2.8.4),支付成功后固化为订单优惠快照
- **不透传活动名与优惠码码值到 C 端汇总区**——汇总只出金额(D1)

### 2.6.6 异常处理

试算服务异常 → **弹 Toast** 提示优惠暂不可用,买家可原价继续结算或稍后重试(商品行降级为挂牌价、`Discount` 行隐藏、主 CTA 金额取未优惠 Total);码并发用尽(Apply 成功后支付时总量耗尽)→ 支付前二次校验失败,提示码已失效并重算。

> **为什么这里用 Toast、而 §2.6.4 用行内**:§2.6.4 是**优惠码本身校验不通过**,错误归属于输入框,故行内呈现;本条是**服务不可用**,与买家输入无关、也不挂在任何输入框上,故用 Toast 全局提示。两者刻意不同,不要统一。

### 2.6.7 UI 关联

C 端 Figma 设计稿,本期帧见 **§七.1 帧索引**(移动:`checkout-discount code` / `checkout-discount code-输入code后` / `checkout多商品-discount code`;PC:`增加营销code输入` / **`营销code输入报错`(`5778:1667`,v2.1 补录)** / `营销code可修改删除` / `结算完成增加营销透传`);本地 `UI/` 旧 html 仅历史参考,不作开发依据。

## 2.7 C 端 · 成交后营销展示(页面型)

**功能描述**:订单成交后两个页面的优惠展示——**下单成功页**(支付完成即时页)与**订单详情**(历史可回看页)。两者是**不同页面、不同版式**,不可互相套用;共用同一份**成交快照**数据(§2.8.4 落库的 `order_discount`),口径为成交时刻,不随活动后续变化。

**共用数据口径(两个子页面均适用)**:

| 项 | 口径 |
|---|---|

### 2.7.1 订单详情营销展示

**功能描述**:订单维度优惠快照展示(成交时口径,不随活动后续变化)。

**页面元素**(按设计稿实况重写,原 3 条元素全部作废):

| # | 位置 | 元素 | 说明 | 来源 |
|---|---|---|---|---|
| 1 | 商品行 | **仅单一成交价** | **无划线原价、无折扣标签、无 Save 徽章、无活动名**——移动 1 帧 + PC 5 帧共 6 帧一致 | D6 |

| 3 | Order Summary | **`Discount`** | **单行**,左侧标签 + 右侧「**票券图标 + 紫色负数金额**」;**不拆** `Item discounts` / `Promo code XXX`,**不带活动名、不带码值** | D1 |
| 4 | Order Summary | `Shipping` | 归订单模块 | — |
| 5 | Order Summary | `Tax` | 归订单模块,**税额计算与是否展示以订单模块口径为准**,营销侧不定义 | D7(补) |

| 7 | 分隔线下方 | **`Refund (N item)`** | 紫色金额,**位于 Total 下方**;**仅在真实发生退款时出现**,无退款则整行不展示;金额与件数口径归订单模块,营销侧不参与计算 | D7-9 |

**汇总行层级关系(硬性,D7-9)**:

```
Subtotal (N items)
  Discount            ← 优惠行,在 Total 上方,参与 Total 计算
  Shipping
  Tax
Total  (加粗)
────────────────────  ← 分隔
Refund (N item)       ← 退款行,在 Total 下方,不参与 Total 计算
```

> **不得把 Refund 并入 Discount 行,也不得用 Refund 冲减 Total**。Total 恒为**成交时的实付金额**;退款是成交之后发生的独立事实,只在 Total 下方另起一行表达。

> **`Refund` 行的出现条件**:**仅在该订单真实发生退款时展示**;无退款的订单不出该行。

**订单状态与营销展示的关系(硬性)**:

| 订单状态帧 | 营销展示 |
|---|---|
| `confirmed` | Discount 行照常展示 |
| `单一物流` | 同上 |
| `cancelled` | **同上——已取消订单同样照常展示 Discount 行** |
| `on its way` | 同上 |
| `completed` | 同上 |

**部分退款态口径(D7-8,本版新增)**:

- PC 5 帧中有 4 帧为**部分退款场景**,其 `Discount` 行**原样保留、金额不变**
- 规则:**优惠行恒为成交快照值,不随退款状态改写、不按剩余商品重算**
- 与 §2.9「回滚(D3)」呼应——**整单退款**才回滚核销计数(但订单详情仍展示原优惠明细);**部分退款不回滚不重算**,买家仍占用使用次数,优惠金额不追回、不改写

| 退款情形 | Discount 行 | Refund 行 | 核销计数(§2.9) |
|---|---|---|---|
| 无退款 | 成交快照值 | 不展示 | 保持 valid |
| **部分退款** | **成交快照值,不变** | 展示 `Refund (N item)` | **不回滚**(D3) |
| **整单退款** | **成交快照值,不变** | 展示 `Refund (N item)` | **回滚**,status → reverted(D3) |

**展示规则**:
- 快照数据一次成型,活动结束/改名/下架不影响历史订单展示
- **减免为 0 的订单**:`Discount` 行**不展示**(不出 `-$0.00` 空行)
- 优惠码与自动折扣**合并为同一行 `Discount`**,即使一单内同时存在多条折扣与多个码,C 端也只见一行合计

**异常处理**:成交快照读取失败 → **隐藏 `Discount` 行**,Subtotal / Total 仍按订单侧已固化金额展示,**不阻塞订单详情**;**不得**降级为实时试算(会与实收金额不一致)。

## 2.8 机制 · 优惠命中与试算 + 行级分摊(机制型)

**功能描述**:营销域对外供给的统一计算能力。**按场景拆成两条规则**——单品场景走「规则一」,订单场景走「规则二」;两条规则共用同一套基础口径(§2.8.1)。
**触发条件**:商详/列表到手价查询、价格监控扫描、购物车试算、checkout 试算。

### 2.8.1 场景与共用口径

**四个场景各走哪条规则**:

| 场景 | 输入 | 适用规则 | 输出 |
|---|---|---|---|
| 商详页 / 商品卡片 | 单个商品 + 市场(无用户上下文) | **规则一**(§2.8.2) | 该商品到手价 |
| 价格监控扫描 | 单个商品 × 市场(无用户上下文) | **规则一**(§2.8.2) | 到手价,供 §2.3.4 降幅比对 |
| 购物车 | 已勾选的商品行 + 登录用户 | **规则二**(§2.8.3) | 各行优惠 + 汇总 |
| checkout | 全部商品行 + 登录用户 + 优惠码 | **规则二**(§2.8.3) | 各行优惠 + 汇总 + 实付 |

**共用口径 A · 候选折扣怎么筛**:所属市场 = 买家当前市场、且处于进行中(状态 + 按该市场本地时区的时间,双判定)的折扣;再逐个商品判断是否被圈选命中——`product_scope` 取 all / 品类 / 品牌 / **商品标签** / **Collection** / 指定商品;其中商品标签与 Collection 均为**命中任一即算(OR)**;Collection 的命中以**判定时刻**的商品池为准(池由 Collection 模块动态维护,营销侧不缓存)。

**共用口径 B · 商品是否可享(A5)**:指定商品的圈选关系**不物理删除**;每次判定时读商品域的实时可售状态——售出/下架的商品当下不可享,退款回到可售后自动恢复。

**共用口径 C · 单件减免怎么算**:
- `percentage`:减免 = round(现价 × 比例),再按 `max_discount_amount` 封顶(该字段仅 percentage 可配)
- `fixed`:减免 = min(`fixed_amount`, 现价)
- 均按所属市场币种计算,**全程不涉及汇率**
- 注:`max_item_count`(每单作用件数)已于 v1.2 移除,故 fixed 类无件数上限,风险由 §2.2.3 试算拦截 + §2.3 双阈值监控 + §2.8.4 实付兜底承接

**共用口径 D · 优惠码是「需输码触发的折扣」(D2,本版口径修正)**

优惠码**不是**「在自动折扣之外额外加的一层」,而是**候选折扣的一种触发方式**:

| 折扣类型 | 进入候选池的条件 |
|---|---|
| 自动折扣(auto) | 命中圈选商品即进入候选 |
| 优惠码(code) | 命中圈选商品 **且** 买家已在 checkout 输入并 Apply 成功,才进入候选 |

两者进入候选池后**完全同池、不做区分**,受**同一条约束**——**每个商品行至多生效一条折扣**(§2.8.3 第 2 步约束 ①),由同一次最优组合求解统一裁决谁生效。

由此直接推出三条结论(**都是求解的自然结果,不是特殊逻辑,开发不必为它们单写分支**):

| # | 结论 | 说明 |
|---|---|---|
| 1 | **一单可以有多个优惠码同时生效** | 前提是它们**作用于不同商品行**;这与 §2.8.3「不同商品各享各的、等同分开下单」是同一条规则 |
| 2 | **单商品场景下最多一个码生效** | 只有一个商品行 ⇒ 至多一条折扣 ⇒ 再输新码时,若新码更优则**自然替换**旧码 |
| 3 | **码可能被自动折扣挤掉** | 求解结果中该码不产生任何减免 ⇒ 不加入已应用集合(见 §2.8.3 第 1 步「新码 Apply 的处理顺序」) |

> **原「V1 单订单仅支持输入 1 个优惠码」的写法作废**(D2)——它只描述了「单商品进入 checkout」这一个场景,不能用来约束所有场景。

### 2.8.2 规则一 · 商详 / 商品卡片到手价(单品场景)

> **一句话**:只看这一件商品自己——它能不能满足门槛、最多能减多少。

**三步**:
1. **筛候选**:按共用口径 A + B 取出命中本商品的折扣,**只取自动折扣**——优惠码须由买家在 checkout 输入才触发(共用口径 D),商详页无输码上下文,故**任何优惠码都不参与到手价计算**。
   > **D2 不改变这一条**:码与自动折扣同池竞争,只发生在**规则二的订单场景**;**规则一始终只看自动折扣**。商详展示的到手价因此是「不用码就能拿到的价格」,买家在 checkout 用码后只会更便宜、不会更贵。
2. **判门槛**(先判门槛、再算优惠):
   - 无门槛(`min_type=none`)→ 直接可用
   - 满额 → 用**该商品挂牌价(现价)** 与 `min_amount` 比,达标才可用
   - 满件 → 按 **1 件**与 `min_quantity` 比,达标才可用
   - 即:**只有"无需凑单、单买这一件就能享"的折扣才计入到手价**;需要凑单才够格的折扣不参与本页价格计算
3. **取最大并统一输出**:在可用折扣中取减免最大的一条(V1 不叠加),按共用口径 C 算减免 → **到手价 = 挂牌价 − 该减免**。
   **无论是否命中折扣,本规则一律输出「到手价」**——**没有任何可用折扣时,到手价 = 挂牌价、减免 = 0**,而不是不返回或返回空。
   这样商详、商品卡片、监控扫描等下游只需读同一个字段,不必各自判断"有没有促销";是否处于促销态由「减免 > 0」判断。

**本场景不做的判定**:不判适用用户、不判限次。因为商详无登录用户上下文,故适用用户(标签)限定的折扣在此按"全部可享"展示,登录后由规则二在购物车/结算再校验。

> **v1.4 修正留痕**:v1.3 及以前写的是"商详无门槛判定",会让需要凑单的折扣在商详被无条件计入到手价——买家单买一件时实际付不到那个价,属虚标。本版起商详同样先判门槛。

### 2.8.3 规则二 · 购物车 / checkout 最优组合(订单场景)

> **一句话**:在"每件商品最多用一条折扣、每条折扣的门槛必须由**真正用它的那些商品**凑满"的前提下,选一种分法,让**整单省得最多**。

**第 1 步 · 筛候选**:按共用口径 A + B 取出候选,再逐条剔除——
- **适用用户不符**:`eligibility_type=all` 全部通过;`=tag` 则校验用户是否命中该规则关联的任一用户标签(标签含"新客"等,由用户管理模块打标);自动折扣与优惠码均执行
- **限次已用尽**(checkout):总量(有效核销 `used_count` < `total_usage_limit`)、每人((rule,user) 有效核销 < `per_user_limit`);码类另判码有效性
- **门槛必然不可能达标**(剪枝):若"该折扣**命中的全部商品行**合计"都还不满足门槛,则无论怎么分配都达不到 ⇒ 直接剔除。这是充分条件,不影响结果正确性
> 购物车场景执行前两项中的"适用用户",不判限次、不含优惠码;checkout 全部执行。

**checkout 的候选池构成(D2)**:候选池 = 命中的自动折扣 **∪** 买家**已应用优惠码集合**中命中的码。已应用集合随买家 Apply / 移除而变化,每次变化都触发**整单重新求解**。

**新码 Apply 的处理顺序(D2,四步)**:

| 步 | 动作 | 不通过时 |
|---|---|---|
| 1 | **校验码自身**:码存在且有效、在活动时间内、未超总量/每人限次、适用用户匹配、命中当前订单中至少一个商品 | 报对应错误(§2.6 失败态),**不加入集合** |
| 2 | **加入已应用集合**(临时) | — |
| 3 | **按本节第 2 步整单重新求最优** | — |
| 4 | **看结果中该码是否产生减免**:是 → 正式加入集合、chip 展示;否 → **回滚,不加入集合**并出行内错误提示(§2.6.4 第 9 条) | — |

> 第 4 步是 D2 的关键:码能否留下由**整单求解结果**决定,不是先到先得。移除某个码同样触发整单重算——别的码或自动折扣可能因此重新生效。

**第 2 步 · 求最优分配**:

- **目标**:使**整单减免总额最大**
- **约束**:
  - ① 每个商品行**至多**分配一条折扣(也可以不分配);**自动折扣与已应用的优惠码在此不做任何区分**,二者竞争同一个名额(D2)
  - ② 每条被分配到商品的折扣,其门槛必须由**实际分配给它的那些行**满足——满额按这些行当前售价(未计本折扣)的合计、满件按这些行的件数合计
  - ③ 各行减免按共用口径 C 计算
- **为什么不能逐行各自取最大**:门槛按"实际使用者"判定 ⇒ 谁用这条折扣,决定它是否达标;而它是否达标,又反过来决定谁能用它。两者互相依赖,必须一起求解,不能拆成两步
- **平局规则(硬性)**:存在多个减免总额相同的分法时,**结果必须唯一且可复现**——同样的购物车与同样的活动配置,任何时候算出来都应是同一个分法。优先级:先取**用到折扣条数更少**的;若仍并列,由技术方案定一个稳定的确定性规则(不得随机、不得依赖查询顺序)
- **求解要求**:**按候选折扣 20 条规模评估**(D4 本版上调,原写"不足 10 条"——按 20 条设计可覆盖大促期间多活动并行的场景)。在该规模下**必须返回真正的最优解**,不接受近似结果;若技术方案判断某些极端规模下无法保证最优,需**事先与产品确认降级口径**,并在试算响应中标记本次结果为非最优,供监控与事后排查。具体求解算法由技术方案定

**第 3 步 · 输出**:整单优惠 = 各行生效折扣的减免额之和;输出各行明细供购物车/结算渲染。

**"不同商品各享各的"仍然成立**:一单内可以同时有多条折扣各作用于不同商品——前提是每条折扣的门槛都由它**实际作用的那些行**满足。

**全场景枚举(D1 本版新增)**:购物车 / checkout 下的多商品优惠组合,按"命中几条折扣 × 门槛类型 × 有无优惠码"穷举如下,每一行都要能被计算引擎正确处理:

| # | 场景 | 输入示例 | 预期结果 |
|---|---|---|---|
| 1 | 单商品命中单折扣、无门槛 | A 商品命中「8 折」 | 直接减,到手价 = 挂牌价 × 0.8 |
| 2 | 单商品命中多折扣、无门槛 | A 同时命中「8 折」与「直减 $80」 | 取减免大的一条 |
| 3 | 单商品命中带门槛折扣、**自身达标** | A $600 命中「满 $500 打 8 折」 | 达标 → 减 |
| 4 | 单商品命中带门槛折扣、**自身不达标** | A $300 命中「满 $500 打 8 折」 | 不达标 → 该折扣不生效 |
| 5 | **多商品凑单达标** | A $300 + B $300 同命中「满 $500 打 8 折」 | 两件合计 $600 达标 → 两件都减 |
| 6 | **凑单达标但拆开更优** | 场景 5 基础上 B 另命中「直减 $200」 | 需比较:两件都用满减 vs B 单用直减(此时 A 独用满减不达标) → 取整单最大 |
| 7 | 不同商品各享不同折扣(均无门槛) | A 命中「8 折」、B 命中「直减 $50」 | 各享各的,互不影响 |
| 8 | 部分商品不命中任何折扣 | A 命中折扣、C 未命中 | C 按挂牌价,不参与分配 |
| 9 | 命中折扣但**用户不符 / 限次用尽** | A 命中仅限"新客"的折扣、当前用户非新客 | 该折扣在候选阶段即剔除 |
| 10 | **优惠码参与**(仅 checkout) | 自动折扣已生效,再输入优惠码 | 码与自动折扣**同池求解**,受「每行至多一条」约束;码更优则取代该行的自动折扣,否则该码不生效并提示(§2.6) |
| 11 | 优惠码带门槛、需凑单 | 码为「满 $500 减 $100」,购物车合计 $600 | 按同一门槛规则判定(实际使用它的行合计) |
| 12 | 勾选变化导致门槛失守(购物车) | 场景 5 中取消勾选 B | 重新试算 → A 单独不达标 → 满减失效 |
| 13 | **多码同时生效**(D2 本版新增) | A 商品应用码 X、B 商品应用码 Y,两码商品范围不重叠 | **两个码都生效**——分别作用于不同商品行,不违反「每行至多一条」;汇总仍为单行 `Discount` |
| 14 | **同一商品行上两个码竞争**(D2 本版新增) | 单商品 A 先应用码 X,再应用码 Y | 只取减免大的一条;若 Y 更优则 X 的 chip 消失、Y 生效;若 Y 不更优则 Y **不加入集合**并提示 |

> 场景 6、12、14 是最容易算错的三类,开发自测与验收用例请务必覆盖。

**举例**:折扣 A「满 $500 全场 8 折」+ 折扣 B「Gucci 直减 $80」,购物车 = Gucci 包 $300 + LV 包 $300

| 分法 | A 实际作用的行 | A 是否达标 | 整单减免 |
|---|---|---|---|
| 甲:两件都用 A | $300 + $300 = $600 | ✅ ≥ $500 | $60 + $60 = **$120** |
| 乙:Gucci 用 B、LV 用 A | 仅 LV 的 $300 | ❌ < $500,A 失效 | 仅 B 的 **$80** |

→ 取整单最大 ⇒ **选甲,减 $120**。
> 若按"逐行各自取最大"会得到 $140(Gucci 取 B 的 $80、LV 取 A 的 $60),但那依赖"Gucci 帮 A 凑够门槛、自己却用 B"——在本版严格口径下**不合法**。

### 2.8.4 分摊、汇总与实付(落库口径)

**1. 行级分摊**
本版所有折扣均为**商品级**,减免天然落在具体商品行上,**不需要按占比二次分摊**。仅当未来引入订单级折扣(V2)时,才按各行折后金额占比分摊、尾差计入金额最大的那一行。

**2. 汇总口径(D1,与 Figma 一致)**
C 端购物车 / checkout / 订单详情的金额汇总区,**统一按下表输出**:

| 汇总行 | 取值 | 说明 |
|---|---|---|
| `Subtotal` | **各商品行折后价合计** | 已含自动折扣;**不是原价合计** |
| `Discount` | **优惠码带来的减免合计** | **只有一行**,不按活动拆多行 |
| `Shipping` / `Tax` | 由物流 / 税费模块给出 | 不在本模块 |
| `Total` | Subtotal − Discount + Shipping + Tax | 见第 3 条兜底 |

三条硬性约束:
- **汇总区不透传活动名与码值**——不出现 `Item discounts`、`Promo code XXXX` 这类逐条明细行;码本身以 chip 形式展示在输入框下方(§2.6),不进汇总
- **`Discount` 恒为单行**,即使多个码同时生效(共用口径 D 结论 1)也合并为一个数
- 自动折扣的减免**已经体现在 `Subtotal` 里**,不再单列,避免同一笔钱被算两次

**3. 实付兜底(A2)**
最终实付 = 应付合计 − 优惠合计;**若算出来是负数,则按 0 收**。
这个"不能低于 0"的兜底**只由订单计算引擎来做,且整条链路只做一次**——营销侧只负责算出优惠金额,不做这个截断;两边都截一次会导致金额对不上、对账查不清。

**4. 落库**
行级减免与生效折扣随订单写入 `order_discount`(含 `rule_name` 快照);多码生效时按**码维度分别落一条**,便于核销统计与退款回冲。

### 2.8.5 通用说明

**规则说明**:规则一的计算口径与 §2.3.4 价格监控扫描完全一致;所有金额按市场币种计算,无汇率参与。
**异常处理**:任一环节数据获取失败,按各页面的降级规则处理;计算引擎必须保证**同样的输入永远得到同样的输出**(可重放、可复算),这是对账与客诉复核的前提。

## 2.9 机制 · 核销与退款回滚(机制型)

**功能描述**:优惠使用的计数与逆向释放,保证限次与对账一致。
**触发条件**:订单支付成功事件(核销);订单整单退款事件(回滚)。

**优惠资格锁定时点(前置口径,原 §2.1-9 迁入)**:买家的优惠资格与金额以**订单创建(提交)时刻**的试算结果锁定;活动此后暂停/结束/到期不影响已创建订单(含未支付)的已锁优惠;支付成功核销时不再校验活动状态,仅执行唯一约束与原子计数。码类在支付发起前做总量/每人限次二次校验(§2.6)。

**处理流程**:
1. **核销**:支付成功 → 订单事件 → 营销侧记一次核销(写 promotion_redemption,status=valid,含 rule/code/user/order/redeemed_at),已核销次数 +1。**硬性要求**:①**同一活动在同一订单上只能核销一次**,重复事件不得重复计数;②**并发下不得超发**——总量已达上限时必须拒绝(该情形支付前二次校验已拦截,此处为最终兜底)。实现方式由技术方案定。
2. **回滚(D3)**:整单退款 → 订单事件 → 该订单核销 status→reverted、记 reverted_at,used_count−1、每人限次释放;**部分退款不回滚不重算**,买家仍占用使用次数,不因退款后不再满足门槛而追回优惠(重算依赖订单改价能力,V2)
3. 限次判定、KPI、对账均只统计 status=valid 的核销
**异常处理**:核销事件消费失败会重试,**重试不会重复计数**(同一订单只算一次);回滚事件晚到或重复触发,已是 reverted 的保持不变、不再二次扣减;**核销兜底拒绝**(总量被并发击穿后的最终拒绝):该订单已锁定的优惠保留、不向买家追回(体验优先),核销记录不写入。

**设计稿与 PRD 的分工(硬性)**:

1. **设计稿是版式依据**——元素构成、位置、样式、层级以 Figma 为准

4. **设计稿中的金额数字一律视为示例,不要求自洽**——各帧汇总金额相加与 `Total` 对不上、前后帧数值未刷新等,**均属示例数据,不构成实现依据、也不作为设计返工要求**。金额算式一律以 PRD 为准(§2.7.1 / §2.8.4)
