## 一、本次迭代做什么

### 1.1 背景与目标

**背景**：运营配好优惠码之后，只能把码值本身发出去，让买家自己记住、再到 checkout 手动输入。这中间每多一步都在掉转化，而**新媒体推广强依赖投放链接**——投放素材里给的就是一条链接，链接不能自动带码，等于让买家自己去记码、手输。

同时还有一道更硬的门槛：**配置了使用次数限制的优惠码，当前要求买家先登录才能核验**。这卡在下单最后一步（买家已填完地址、选好支付方式），流失是直接的。

**目标**：

1. 运营能为优惠码活动**一键生成一条含 code 的链接**用于投放
2. 买家点链接进来，**码自动跟随**，到 checkout **自动生效、无需手输**
3. **取消优惠码的强制登录**——改为按结算邮箱识别买家
4. 支持**按邮箱指定专属买家**

> **折扣规则一条都不改。** 改的是「码怎么送到买家手上」与「怎么识别买家是谁」。

### 1.2 本次范围

**做**：

| # | 功能 | 本文档章节 |
|---|---|---|
| 1 | 运营端生成含 code 的链接（可选落地页） | §2.1 |
| 2 | 链接的挂码机制：点击 → 记码 → 支付后清除 | §2.2 |
| 3 | **checkout 优惠码校验通用规则**（校验链 + 两时点模型 + 身份口径 + 失败呈现） | **§2.3** |
| 4 | 适用用户新增「指定买家（按邮箱）」 | §2.4 |

> **§2.3 是本次改动面最大的一节**，它管的是 **checkout 内的全部优惠码**——不区分码从哪来（链接带入 / 买家手输）、不区分买家是否登录。「取消强制登录」就是这套规则的直接结果。

**不做**：

| 不做项 | 说明 |
|---|---|
| **App 端唤起后自动挂码** | 下一版。本版链接**不列入 App 深链声明路径**，保证在浏览器打开 |
| **营销侧生成短链、二维码、点击统计** | 全部由短链服务承载，营销只产出含 code 的链接 |
| 落地页支持「指定商品」「搜索结果页」 | 本版仅支持**首页**与**该活动圈选的单个 Collection** |
| 跨设备延续 / 链接→下单的转化归因 | 码记在浏览器会话中，换设备不跟随；归因链路由短链服务规划 |
| **落地后的优惠提示条** | 从落地页到 checkout 之间不出任何提示。C 端保持**零新增元素**、无设计排期 |
| 一人一码（定向码批量发放） | 本版单活动单码。如需一人一码，运营可按人建活动（工作量为 N 倍） |

### 1.3 涉及的角色

| 角色 | 本次要做什么 |
|---|---|
| 平台运营 | 为 code 活动生成链接 → 到「短链管理」包装成投放短链 → 投放 |
| 买家（C 端） | 点链接 → 浏览加购 → 进 checkout 优惠自动生效；**或**照常在 checkout 手输码 |
| 系统 | 认码 / 记码 / 自动兑现 / 身份补校 / 支付后清码 |

## 二、需求详细描述

### 2.1 运营端 · 优惠码链接

**入口**：促销活动列表操作列、活动详情页头部。两处**共用同一个弹窗**。
**可用条件**：`trigger_type=code` 且状态 **≠ 草稿**。

> **草稿为什么不给**：码尚未生效，链接投出去必然失败，等于让运营发废链接。
> **已暂停 / 已结束保留入口**（运营有回溯需求），但弹窗内必须出警示「该活动当前不生效，链接点击后不会有优惠」。

**弹窗元素**：

| 元素 | 说明 |
|---|---|
| 活动信息（只读） | 活动名称 / 优惠码 / **状态** / 所属市场 / 适用商品 / **适用用户** |
| 落地页 | 见下表 |
| 优惠码链接 | **只读展示，不可手改**——由「活动 + 落地页」自动拼出；右侧「复制」 |
| 底部操作 | 关闭 / 复制链接 |

> **适用用户 ≠ 全部时**，弹窗需额外提示「本活动限定适用人群，仅名单/标签内的买家可用，不建议公开投放」——否则运营容易把专属码当通用码投到社媒。

**落地页取值范围**：

| 活动适用商品范围 | 可选落地页 | 默认 | 能否改 |
|---|---|---|---|
| Collection 圈选（**只圈了 1 个**） | 首页 / 该活动的 Collection | 该活动的 Collection | ✅ |
| Collection 圈选（**圈了多个**） | 仅首页 | 首页 | ❌ 锁定 |
| 全部商品 / 指定商品 / 品类 / 品牌 / 商品标签 | 仅首页 | 首页 | ❌ 锁定 |

> **圈了多个 Collection 为什么反而只能落首页**：落到其中任何一个，**另一个集合的商品对进来的买家就是不可见的**——买家看到的页面与他能享优惠的商品范围对不上。首页在这种情况下最中性。
> **锁定时的提示文案**：多选场景「本活动圈选了多个 Collection，落地页固定首页——落到其中任一个都会让另一些商品的买家看不到」；其余场景「本期仅按单个 Collection 圈选的活动可改落地页，其余固定首页」。

> **运营不需要填任何落地目标**：单 Collection 活动取活动自身绑定的那个；多 Collection 与其余活动均落首页、无目标。**任何情况下都不用手填 ID，也就不存在填错。**

**链接形态**：

```
https://{所属市场域名}/discount/{优惠码}[?redirect=/collection/{CollectionID}]
```

- 域名取活动所属市场的域名。**V1 各市场使用同一域名**
- 落地页为首页时不带 `redirect` 参数
- ⚠️ **链接不携带市场标识**——买家点链接后所处市场由站点既有的市场识别逻辑决定

**🔴 复制之后必须去短链管理包装（硬性）**

营销侧产出的是**长链**，直接投放会**拿不到点击统计、独立访客、二维码与 App 唤起**。运营须把它复制到**短链管理 → 创建运营短链**，粘贴为「基础 URL」，在那里配 UTM 并生成短链，**用短链对外投放**。

- 弹窗内需用**提示条**（非小字 helper）说明这一步及不做的后果
- 底部提供**「去短链管理」**跳转入口，把两步流程接上
- **复制成功须出 Toast「链接已复制」**——剪贴板操作不可见，不给反馈运营不知道成没成

**两个复制入口的分工**：链接框右侧「复制」= 复制、弹窗不关（便于改落地页再复制）；底部「复制链接」= 复制并关闭。

**异常处理**：

| 情况 | 处理 |
|---|---|
| 活动在弹窗打开期间被结束或暂停 | 已复制的链接在买家点击时按 §2.2 处理（码不生效），运营端不额外拦截 |
| **运营改了活动圈选的 Collection** | **链接是复制走的静态字符串，平台不追踪已投放的链接**——已发出去的链接仍指向旧 Collection。**编辑页改动 Collection 圈选时需提示**「该活动已生成过投放链接，改动后已投链接的落地页将不再匹配」 |

### 2.2 机制 · 链接的挂码与清除

#### 2.2.1 点击链接时

| 步 | 动作 |
|---|---|
| 1 | 识别路径中的优惠码 |
| 2 | **仅校验该码是否存在**；存在即记住，不存在则不记 |
| 3 | 跳转落地页（带 `redirect` 则跳该页，否则跳首页） |

> **此刻为什么只校验"码存不存在"**：门槛、商品范围、适用用户都依赖购物车内容与买家身份，而买家此刻购物车可能是空的、也尚未登录，**判不了，判了必然误报**。全部留到 checkout 统一判定（§2.3）。

> **码不存在为什么不给报错页**：会被用来批量试探有效码值。静默处理使试探者无法据此判断某个码是否真实存在。

**落地相关的异常**：

| 情况 | 处理 |
|---|---|
| 码不存在或拼写错误 | **静默跳落地页**，不记码、不报错 |
| 码存在但活动已结束/暂停 | 照常记住，到 checkout 按 §2.3 统一判定，此处不提前拦截 |
| 落地的 Collection 被下线或删除 | **降级跳首页，码照常记录** |
| `redirect` 参数被人为篡改 | 链接是公开投放的，任何人都能改。**仅接受站内 Collection 路径**，取值非法或指向站外一律**忽略该参数、降级跳首页**，码照常记录 |

**落地后到 checkout 之间不出任何提示**：页面与平时完全一致，码静默跟随，到 checkout 才可见。

#### 2.2.2 码记在哪、存多久

| 项 | 口径 |
|---|---|
| 载体 | 浏览器侧记录（会话级），**不落库、不写入购物车** |
| 容量 | **只有一个码位**，新码覆盖旧码——同一时刻不可能存在两个链接码 |
| 有效期 | 浏览器会话期间，关闭浏览器即失效 |
| 跨设备 | **不跟随**（已知并接受） |

> 🔴 **「新码覆盖旧码」覆盖的是「链接带来的那个码位」，不是把 checkout 限死成单码。**
> 买家手输的码仍走多码规则（一单可多码、作用于不同商品行），最终可能是「**1 个链接码 + N 个手输码**」。

> **码位被覆盖时，checkout 已应用集合要同步处理**：买家点链接 A 进了 checkout（A 已应用、chip 已显示），又返回商城点了链接 B——此时码位被 B 覆盖，**A 必须同时从已应用集合移除并整单重算**，最终 chip 只剩 B。否则会出现"码位是 B、页面显示 A"的错位。

> **为什么不挂购物车**：买家可能从商详直接 **Buy Now**（跳过购物车）。挂购物车则这条链路完全读不到——而"点链接进来直接买某件商品"恰恰是投放链接最主要的用法。

**码位的完整生命周期（7 个出口，硬性）**：

| # | 事件 | 对码位的处理 | 说明 |
|---|---|---|---|
| 1 | 买家点击优惠码链接 | **写入**（覆盖原有值） | 见 §2.2.1 |
| 2 | 进入 checkout | **读取**，不清除 | 见 §2.3 |
| 3 | 买家在 checkout 点 chip 上的 ✕ 移除 | **清除** | 否则刷新页面后码会自动回来，**买家永远移不掉**；清除后如需恢复，重新点一次链接即可 |
| 4 | T2 补校不通过被系统移除（§2.3） | **保留** | 买家改成符合条件的邮箱后应能重新生效，清掉就恢复不了 |
| 5 | 支付成功且该码被核销 | **清除** | 见下 |
| 6 | 支付成功但该码未被核销 | **保留** | 下次结算仍可参与 |
| 7 | 关闭浏览器 | **清除**（会话级天然失效） | — |

#### 2.2.3 支付成功后的清除

| 项 | 口径 |
|---|---|
| 时机 | 支付成功（订单转 paid） |
| 条件 | **该码被本单核销了 → 清除；未被核销 → 保留**（下次结算仍可参与） |
| 依据 | 本单核销了哪些码，以核销记录为准 |

> **为什么必须清**：不清则该码在同一浏览器会话内会被反复自动应用。而本模块允许运营配置**不限次**的码（总量与每人限次留空 = 不限），不清就是实打实的资损口子。

### 2.3 🔴 checkout 优惠码校验通用规则（本次改动面最大的一节）

> **适用范围（硬性，先读这一段）**：本节规则适用于 **checkout 内的全部优惠码**——
> **不区分码从哪来**（链接带入 / 买家手输），**不区分买家是否登录**。
>
> 也就是说：**买家没走链接、直接在 checkout 手输码，且全程未登录**，同样按本节执行。
> 这是本次改动影响面最大的部分——**它改变的是所有优惠码的校验方式，不只是链接带来的码**。

#### 2.3.1 优惠码校验链（7 项，唯一权威）

任何优惠码进入订单时，一律按下表**逐项按序**执行：

| 序 | 校验项 | 依赖买家身份? | 不通过时的文案 |
|---|---|---|---|
| 1 | 码存在、未停用、所属活动进行中 | 否 | `This code isn't valid or has expired.` |
| 2 | 活动所属市场 = 买家当前市场 | 否 | `This code isn't available in your region.` |
| 3 | 商品范围命中（订单内至少一个商品行） | 否 | `This code doesn't apply to the items in your cart.` |
| 4 | 使用门槛达标（满额 / 满件） | 否 | 满额未达：`Spend {Threshold} or more to use this code.`<br>满件未达：`Add {N} or more eligible items to use this code.` |
| 5 | 总使用次数未用尽 | 否 | `This code has been fully redeemed.` |
| 6 | **每人限次未用尽** | **是** | `You've already used this code.` |
| 7 | **适用用户命中**（tag 标签命中 / email 在指定买家名单内） | **是** | `This code isn't available with this email.` |

**执行口径（硬性）**：

- **按序执行，命中第一条不通过即返回**，不继续往下校验——保证同一个码在任何入口报出的文案一致
- **「依赖买家身份」的第 6、7 项，在身份不可用时一律跳过、不判、不拒绝**，留待身份可用后补校（§2.3.2）
- **不得因身份为空而拒绝应用或要求买家登录**
- 校验通过后加入已应用集合、整单重新求最优组合；**若求解后该码未产生任何减免**，则**不加入集合**（避免 chip 显示一个无实际作用的码），呈现同 §2.3.4 的失败处理

> **第 7 项文案本次由 `...for your account.` 改为 `...with this email.`**——本版取消强制登录后，未登录买家没有 account，原文案不成立；且实际判定依据就是邮箱。

**两条与「已享更优」相关的文案**（求解后被挤掉时使用，按挤掉它的是什么分流）：

| 把该码挤掉的是什么 | 文案 |
|---|---|
| **自动折扣** | `You're already getting a better offer, so this code won't apply.` |
| **另一个已应用的优惠码** | `These items already have an offer applied.` |

**两种此前未覆盖的输入**：

| 情况 | 处理 |
|---|---|
| 重复输入一个已生效的码 | 出「该码已应用」提示，**不走"你已享更大优惠"**——与事实不符（其实是同一个码） |
| 输入框为空点 Apply | Apply 按钮**置灰不可点**，不进入校验、不出任何文案 |

#### 2.3.2 两时点校验模型

| 时点 | 触发 | 校验什么 | 不通过时 |
|---|---|---|---|
| **T1 · 码进入订单时** | 自动应用（链接带入）**或** 买家点 Apply（手输） | 校验链第 **1–5 项**（**均与买家身份无关**） | 见 §2.3.4 |
| **T2 · 买家身份可用后** | **买家填完结算邮箱、鼠标移出输入框时**（值发生变化才触发，值未变不重复触发） | 补校第 **6–7 项** | 见 §2.3.4 |
| **支付发起前** | 点击支付 | 总量 / 限次二次校验（并发兜底） | 提示码已失效并重算 |

**为什么拆两个时点**：第 6、7 项都需要知道"买家是谁"，而买家进 checkout 时通常尚未填邮箱。若等填完邮箱再算全部优惠，买家进页面先看到原价、会以为链接没生效就走了；若把限次一路推到支付前，买家会在点支付那一刻才被告知优惠没了。**先算不依赖身份的、身份明确后再补校**，是三者中体验损失最小的。

> **买家中途改邮箱**：结算邮箱每次变化都重新触发 T2，并**对全部已输入/已带入的码整单重新求解**——此前因身份不符被移除的码，若新邮箱符合条件则**重新生效**。

#### 2.3.3 买家身份的取值口径

| 用途 | 取值 |
|---|---|
| **每人限次**（第 6 项） | 已登录取当前账户；**未登录取结算邮箱关联到的账户**，**邮箱未注册则视为新买家、无历史核销** |
| **适用用户 = tag**（第 7 项） | 取当前账户的标签；未登录取结算邮箱关联账户的标签 |
| **适用用户 = email**（第 7 项） | **一律以结算邮箱为准，不走账户身份** |

> **`=email` 为什么只认结算邮箱**：名单是运营按邮箱配的，而买家可能用 A 账户登录、却把订单收件邮箱填成 B——若两个来源都认，同一订单会出现"按账户不命中、按结算邮箱命中"的双重结论，开发无从取舍。统一认结算邮箱，与未登录场景口径一致，也与「专属券送给某个邮箱的持有人」这一业务语义吻合。

**🔴 本次改造的核心：取消强制登录**

| 项 | 内容 |
|---|---|
| **现状** | 未登录买家**可以输入优惠码**，但配置了使用次数限制的码，系统**要求先登录才能核验** |
| **改为** | **登录不得作为在 checkout 使用优惠码的必要条件**。限次按上表口径判定 |
| **影响范围** | **全部优惠码**，不限于链接带来的码 |

> 🔴 **任何情况下不弹登录、不拦截下单。** 若实现成「邮箱查不到账户就拦」，等于换个方式强制登录，本次改造白做。

**为什么必须改**：强制登录卡在下单最后一步（买家已填完地址、选好支付方式），是转化漏斗上最贵的门槛；而它**换不来更强的风控**——平台本就允许未登录下单并以结算邮箱静默建号，买家换个邮箱注册照样能再用一次，与未登录换邮箱的绕过效果完全相同。**等于用确定的转化损失，换一个并不成立的风控收益。**

> **前置依赖**：用户管理模块的「邮箱 → 账户」反查。**若暂不具备，不得退回「要求登录」**——先按「查不到即放行」上线，再补反查。

#### 2.3.4 成功与失败的呈现

**成功**：优惠码 chip 出现、`Discount` 行与 `Total`、主 CTA 金额联动刷新。**链接带来的码不额外标注"该码来自链接"**，与手输码表现一致。

**T1 失败 · 链接带入的码**：按买家**能不能自救**分两类

| 失败原因 | 呈现 |
|---|---|
| **能自救**（第 4 项：未达满额 / 满件门槛） | 出**中性正向引导**（如 `Spend $40 more to unlock $80 off.`），位置在订单摘要上方，**不用红色错误态**——买家没做错什么，他只是还没加够 |
| **不能自救**（第 1/2/3/5 项及"已享更优"） | **完全静默**，不提示、**不回填码值**，页面表现与"没有这个码"完全一致 |

> **不能自救的为什么静默**：买家**没有任何输入动作**（他只是点了个链接进来），突然出现一行红字会让他困惑"我做错了什么"；而告诉他"码过期了"也改变不了结果。

**T1 失败 · 买家手输的码**：**一律在优惠码输入框下方出行内错误提示**，文案取校验链对应条目。**这条未作任何改动，沿用现有实现。**

**🔴 T2 不通过（链接码与手输码同样适用）**：

| 步 | 动作 |
|---|---|
| 1 | **取消该码的 apply**——从已应用集合移除，chip 消失，整单重新求最优组合 |
| 2 | **把码值回填到优惠码输入框**（链接码此前从未在输入框出现过，此刻回填） |
| 3 | **在优惠码输入框下方的既有错误提示位**展示不通过的原因 |

- **文案**：限次不通过 → 第 6 项文案；适用用户不通过 → 第 7 项文案
- **位置**：优惠码输入框正下方——PC 仅框下红字、移动端红框 + 红字，**复用既有表单报错组件，不新增视觉规范**
- **必须回填**：回填后输入框内有内容，错误提示挂在其下方就有了明确归属；买家也能看到是哪个码出了问题，可直接改码或清空

> **为什么 T2 回填、而 T1（链接码）不回填**：差别在**买家有没有输入动作**。
> T1 发生在买家进页面的瞬间，他没做任何事，回填一个他没输过的码只会让人困惑"这哪来的"；
> T2 发生在**买家刚填完邮箱**，他有明确动作，且系统正要**把已经显示的优惠拿走**——
> 此时回填码值 + 就地报错，买家才能看懂"是我填的这个邮箱用不了这个码"，而不是"金额怎么自己涨了"。

### 2.4 适用用户 · 指定买家（按邮箱）

`eligibility_type` 由 `all / tag` 扩为 **`all / tag / email` 三选一互斥**（不支持组合）。

**典型用法**：给某个大客户、某批潜在客户发**专属券**——这批人身上没有现成标签，运营手上只有他们的邮箱。

| 项 | 口径 |
|---|---|
| **存什么** | **存邮箱，不存账号 ID**——运营手上只有邮箱；且**未注册的邮箱也能预先配置**（存账号 ID 则"给潜在客户发专属券"这类活动根本配不出来） |
| **匹配依据** | **一律以结算邮箱为准**（见 §2.3.3） |
| **大小写** | **不区分**，统一转小写后比对 |
| **别名归一化** | **不做** Gmail `+后缀` 与点号归一化——那是反薅规则，与"指定给某个人"的语义无关，且会误伤真实用别名收件的买家 |

**录入规则**（运营端表单）：

| 项 | 规则 |
|---|---|
| 分隔符 | 换行 / 英文逗号 / 中文逗号 / 分号 / 空格，混排均可 |
| 规范化 | 逐条 trim → 统一转小写 |
| 去重 | 规范化后去重，重复项不报错、只提示已去重 N 个 |
| 格式校验 | 逐条校验，**不拦截整批**，分「有效 / 格式不正确」两组回显，不正确的逐条列出 |
| 实时汇总 | 「识别 N 个：有效 M 个，重复已去重 X 个，格式不正确 K 个」 |
| 数量上限 | **500 个**，超出提示「超出上限 500 个，请拆分活动」 |
| 编辑语义 | **全量覆盖**——编辑时回显现有全部邮箱，保存以当前内容为准，不做增量追加 |
| 保存口径 | **只保存有效邮箱**，格式不正确的不入库 |

> 格式校验的判定标准由技术方案定，至少能识别「缺 @」「缺域名」「缺顶级域」三类明显错误；国际化域名（IDN）不作要求。

**切换适用用户类型时**：三者互斥，tag 与 email 的明细不共存。**切换时清空另一类的已配明细**，并二次确认「切换后原有的{标签/邮箱}配置将被清空」。

**详情页展示**：`=email` 时展示「指定买家（N 个）」+ **逐个列出全部邮箱**，数量多时清单区域内部滚动。

> **为什么必须逐个列出**：运营打开详情就是为了核对「配的是不是这几个人」，只给数量等于没回答；而**进行中的活动不可直接编辑**，运营连回编辑页看一眼都做不到。

**运营端其他配套**：

- 活动详情页基本信息补 **「使用门槛」「总使用次数」** 两个字段（此前列表与详情都查不到门槛，而进行中活动不可编辑，客服转来"买家说满 $300 用不了"时运营无处可查）
- 列表页「适用商品」列下补一行小字标注适用用户（全部不标 / tag 标标签名 / email 标「指定买家 N 个」），**不新增列**

## 四、依赖与风险

### 4.1 需要其他模块配合的 4 件事

| # | 依赖方 | 需要对方做什么 | 阻塞级别 |
|---|---|---|---|
| 1 | **用户管理** | 提供「邮箱 → 账户」反查（§2.3.3 的实现前提） | 可降级（先按查不到即放行上线） |
| 2 | **短链服务（社媒分享）** | 确认「创建运营短链」的基础 URL 支持指向 `/discount/{码}` | 需确认（预计天然支持） |
| 3 | **短链服务 / App** | **优惠码链接不得列入 App 深链声明路径** | 🔴 **漏了就是真 bug** |
| 4 | **Collection 模块** | 提供 **C 端 Collection 落地页的 URL 规则** | 需确认 |

> **第 3 条为什么是真 bug**：App 被系统唤起时**服务端收不到请求**，而 App 尚不认识这个码 → **码会静默丢失**，买家和运营都察觉不到。「在浏览器中打开」通过「不列入深链声明」实现即可，不需要额外手段。

> **第 4 条为什么要确认**：本文档暂按 `/collection/{CollectionID}` 书写，**若 C 端实际用 slug/handle，则链接全是死链**，而这在营销侧测不出来。

### 4.2 已知敞口（已拍板接受，运营须知悉）

| # | 敞口 | 对运营的含义 |
|---|---|---|
| 1 | **未登录场景「每人限次」可被绕过** | 换邮箱 / Gmail 加 `+后缀` 或加点均可绕过，行业无原生手段可解。**大额优惠码务必同时配总使用次数上限** |
| 2 | **「指定买家」是软名单，不是身份锁** | 只凭结算邮箱放行，**任何知道名单里某个邮箱的人都能冒用**。这是「存邮箱不存账号 ID」的必然代价 |
| 3 | **人群限定的自动折扣会把专属价泄给全站** | 商详到手价、Sale 打标、搜索排序都会用这个价，而实际只有名单内的人能享。**人群限定的活动优先用「优惠码」触发**——码不进商详取价逻辑，天然不外泄 |
| 4 | **跨市场投放会静默全失效** | 链接不携带市场标识，市场不匹配时按「不能自救」类静默处理，运营端看不到回流信号 |
| 5 | **链接不跨设备** | 手机点链接、电脑下单则不生效 |
| 6 | **落地到 checkout 之间没有任何反馈** | 买家在这段路径上无从得知码已生效，可能因此流失。本版不做提示条（保持 C 端零新增元素） |

## 五、验收要点

### 5.1 三个最容易实现错的点

| # | 点 | 错误实现会怎样 |
|---|---|---|
| 1 | **§2.3 管的是全部优惠码，不只链接码** | 若只在链接场景实现两时点模型，**手输码 + 未登录**的买家仍会被要求登录，本次改造只做了一半 |
| 2 | **未登录 + 邮箱未注册 = 直接放行** | 若实现成「查不到就拦」，等于换个方式强制登录 |
| 3 | **T2 不通过要「取消 apply + 回填码值 + 就地报错」三步** | 若沿用静默，买家会看到 chip 无声消失、Total 上涨且无任何解释——**这是本次最可能变成客诉的场景** |

### 5.2 核心验收场景

**A · 链接场景**

| # | 场景 | 预期 |
|---|---|---|
| 1 | 点链接 → 加购符合范围且达门槛的商品 → 进 checkout | 码**自动生效**，chip 出现、`Discount` 行与 `Total` 联动 |
| 2 | 点链接 → 商品不在范围内 → 进 checkout | **完全静默**，页面与"没有这个码"一致 |
| 3 | 点链接 → 差 $40 未达满额门槛 → 进 checkout | 出**中性正向引导**「还差多少」，非红色报错 |
| 4 | 自动应用成功 → 点 chip 上的 ✕ → 刷新页面 | 码**不再自动回来**（会话码位已清） |
| 5 | 点链接 A → 进 checkout（A 生效）→ 返回商城点链接 B → 再进 checkout | chip **只剩 B**，A 已从已应用集合移除 |
| 6 | 支付成功（本单用了该码）→ 再次进入 checkout | 码**不再自动应用**（已清除） |

**B · 非链接场景（未登录手输码，本次改造重点）**

| # | 场景 | 预期 |
|---|---|---|
| 7 | **未登录**、未填邮箱 → 手输一个**带每人限次**的码 → Apply | **正常生效**（第 6 项身份不可用、跳过不判），**不弹登录、不拦截** |
| 8 | 承接场景 7 → 填入一个**已用过该码**的邮箱 → 鼠标移出输入框 | 优惠**取消**、码值**回填输入框**、框下出「You've already used this code.」 |
| 9 | **未登录** + **从未注册过**的邮箱 + 带限次的码 | **直接放行**，不弹登录、不拦截 |
| 10 | 未登录手输一个「指定买家」专属码 → 填**不在名单**的邮箱 → 移出 | 优惠取消、码回填、框下出「This code isn't available with this email.」 |
| 11 | 承接场景 10 → 把邮箱改成**名单内**的 → 移出 | 该码**重新生效** |
| 12 | **已登录**买家（账户邮箱不在名单）→ 结算邮箱填**名单内**的 → 移出 | **命中生效**（`=email` 只认结算邮箱，不看账户） |

**C · 运营端**

| # | 场景 | 预期 |
|---|---|---|
| 13 | 给圈了 2 个 Collection 的 code 活动生成链接 | 落地页**锁定首页**、下拉禁用，提示说明原因 |
| 14 | 给草稿态 code 活动 | 列表操作列与详情页**都没有**「优惠码链接」入口 |
| 15 | 给已结束的 code 活动生成链接 | 入口在，但弹窗顶部出「该活动当前不生效」警示 |
| 16 | 买家邮箱框粘贴含拼错域名、重复项、大小写混杂的清单 | 实时汇总「识别 N 个：有效 M 个，重复已去重 X 个，格式不正确 K 个」，错误项逐条列出 |
| 17 | 适用用户由「指定用户标签」切到「指定买家」 | 二次确认后**清空原标签配置** |
| 18 | 打开任一 code 活动详情页 | 能看到「使用门槛」「总使用次数」「适用用户」三项 |
