## 一、本次迭代做什么

### 1.1 背景与目标

**背景**：运营配好优惠码之后，只能把码值本身发出去，让买家自己记住、再到 checkout 手动输入。这中间每多一步都在掉转化，而**新媒体推广强依赖投放链接**——投放素材里给的就是一条链接，链接不能自动带码，等于让买家自己去记码、手输。

**目标**：

1. 运营能为优惠码活动**一键生成一条含 code 的链接**用于投放
2. 买家点链接进来，**码自动跟随**，到 checkout **自动生效、无需手输**
3. 顺带解决两件挡在转化前面的事：**取消优惠码的强制登录**、**支持按邮箱指定专属买家**

**一句话**：折扣规则一条都不改，改的是「**码怎么送到买家手上**」。

### 1.2 本次范围

**做**：

| # | 功能 | 完整 PRD |
|---|---|---|
| 1 | 运营端生成含 code 的链接（可选落地页） | §2.2.6 |
| 2 | 点链接 → 记码 → 进 checkout 自动兑现 → 支付后清码 | §2.13 |
| 3 | 适用用户新增「指定买家（按邮箱）」 | §2.2.2 / §2.2.4 / §2.8.3 |
| 4 | **取消「带限次的优惠码必须登录才能核验」**（改造项） | §2.6 前置条件 / §2.13.5 |

**不做**（本版明确边界，见完整 PRD §1.2）：

| 不做项 | 说明 |
|---|---|
| **App 端唤起后自动挂码** | 下一版。本版链接**不列入 App 深链声明路径**，保证在浏览器打开 |
| **营销侧生成短链、二维码、点击统计** | 全部由短链服务承载，营销只产出含 code 的链接 |
| 落地页支持「指定商品」「搜索结果页」 | 本版仅支持**首页**与**该活动圈选的单个 Collection** |
| 跨设备延续 / 链接→下单的转化归因 | 码记在浏览器会话中，换设备不跟随；归因链路由短链服务规划 |
| **落地后的优惠提示条** | 从落地页到 checkout 之间不出任何提示（2026-08-26 拍板）。C 端保持**零新增元素**、无设计排期 |

### 1.3 涉及的角色

| 角色 | 本次要做什么 |
|---|---|
| 平台运营 | 为 code 活动生成链接 → 到「短链管理」包装成投放短链 → 投放 |
| 买家（C 端） | 点链接 → 浏览加购 → 进 checkout，优惠自动生效 |
| 系统 | 认码 / 记码 / 自动兑现 / 身份补校 / 支付后清码 |

## 二、需求详细描述

### 2.1 运营端 · 优惠码链接（完整 PRD §2.2.6）

**入口**：促销活动列表操作列、活动详情页头部。两处**共用同一个弹窗**。
**可用条件**：`trigger_type=code` 且状态 **≠ 草稿**。

> **草稿为什么不给**：码尚未生效，链接投出去必然失败，等于让运营发废链接。
> **已暂停 / 已结束保留入口**（运营有回溯需求），但弹窗内必须出警示「该活动当前不生效，链接点击后不会有优惠」。

**弹窗内容**：

| 元素 | 说明 |
|---|---|
| 活动信息（只读） | 活动名称 / 优惠码 / **状态** / 所属市场 / 适用商品 / **适用用户** |
| 落地页 | 见下表 |
| 优惠码链接 | **只读展示，不可手改**——由「活动 + 落地页」自动拼出；右侧「复制」 |
| 底部操作 | 关闭 / 复制链接 |

**落地页取值范围**：

| 活动适用商品范围 | 可选落地页 | 默认 | 能否改 |
|---|---|---|---|
| Collection 圈选（**只圈了 1 个**） | 首页 / 该活动的 Collection | 该活动的 Collection | ✅ |
| Collection 圈选（**圈了多个**） | 仅首页 | 首页 | ❌ 锁定 |
| 全部商品 / 指定商品 / 品类 / 品牌 / 商品标签 | 仅首页 | 首页 | ❌ 锁定 |

> **圈了多个 Collection 为什么反而只能落首页**：落到其中任何一个，**另一个集合的商品对进来的买家就是不可见的**——买家看到的页面与他能享优惠的商品范围对不上。首页在这种情况下最中性。

> **运营不需要填任何落地目标**：单 Collection 活动取活动自身绑定的那个；其余落首页、无目标。**任何情况下都不用手填 ID，也就不存在填错。**

**链接形态**：

```
https://{所属市场域名}/discount/{优惠码}[?redirect=/collection/{CollectionID}]
```

**🔴 复制之后必须去短链管理包装（硬性）**

营销侧产出的是**长链**，直接投放会**拿不到点击统计、独立访客、二维码与 App 唤起**。运营须把它复制到**短链管理 → 创建运营短链**，粘贴为「基础 URL」，在那里配 UTM 并生成短链，**用短链对外投放**。

> **为什么营销不直接生成短链**：短链服务已具备完整的链接生成能力，营销再造一遍是重复建设；且 UTM 取值规范与枚举由短链服务统一维护，营销侧不维护第二份、避免两处分叉。

### 2.2 机制 · 挂码与自动兑现（完整 PRD §2.13）

#### 2.2.1 点击链接时

| 步 | 动作 |
|---|---|
| 1 | 识别路径中的优惠码 |
| 2 | **仅校验该码是否存在**；存在即记住，不存在则不记 |
| 3 | 跳转落地页（带 `redirect` 则跳该页，否则跳首页） |

> **此刻为什么只校验"码存不存在"**：门槛、商品范围、适用用户都依赖购物车内容与买家身份，而买家此刻购物车可能是空的、也尚未登录，**判不了，判了必然误报**。全部留到 checkout 统一判定。

> **码不存在为什么不给报错页**：会被用来批量试探有效码值。静默处理使试探者无法据此判断某个码是否真实存在。

#### 2.2.2 码记在哪、存多久

| 项 | 口径 |
|---|---|
| 载体 | 浏览器侧记录（会话级），**不落库、不写入购物车** |
| 容量 | **只有一个码位**，新码覆盖旧码——同一时刻不可能存在两个链接码 |
| 有效期 | 浏览器会话期间，关闭浏览器即失效 |
| 跨设备 | **不跟随**（已知并接受） |

> 🔴 **「新码覆盖旧码」覆盖的是「链接带来的那个码位」，不是把 checkout 限死成单码。**
> 买家手输的码仍走多码规则（一单可多码、作用于不同商品行），最终可能是「**1 个链接码 + N 个手输码**」。

> **为什么不挂购物车**：买家可能从商详直接 **Buy Now**（跳过购物车）。挂购物车则这条链路完全读不到——而"点链接进来直接买某件商品"恰恰是投放链接最主要的用法。

**码位的完整生命周期**共 **7 个出口**，见完整 PRD §2.13.2。其中最易漏的两个：

- **买家手动移除 chip → 清除**（否则刷新后码自动回来，买家永远移不掉）
- **T2 补校被移除 → 保留**（否则买家改成符合条件的邮箱后恢复不了）

#### 2.2.3 进入 checkout 的自动兑现（本次核心）

**两时点模型**（完整 PRD §2.6.2，**checkout 通用规则，链接码与手输码同走一套**）：

| 时点 | 触发 | 校验什么 | 不通过时 |
|---|---|---|---|
| **T1** | 码进入订单时（自动应用 / 买家点 Apply） | 校验链第 **1–5 项**——码有效、市场匹配、商品范围命中、门槛达标、总量未用尽（**均与买家身份无关**） | 见下方「T1 失败」 |
| **T2** | **买家填完结算邮箱、鼠标移出输入框时**（值发生变化才触发，值未变不重复触发） | 补校第 **6–7 项**——每人限次、适用用户（tag 标签命中 / email 在指定买家名单内） | 见下方「T2 不通过」 |

> **完整的《优惠码校验链》见完整 PRD §2.6.2**，7 项按序、每项标注是否依赖买家身份、**命中第一条不通过项即返回**，不继续校验。三处旧清单已删除改为引用本表。

**为什么拆两个时点**：第 6、7 项都需要知道"买家是谁"，而买家进 checkout 时通常尚未填邮箱。若等填完邮箱再算全部优惠，买家进页面先看到原价、会以为链接没生效就走了；若把限次一路推到支付前，买家会在点支付那一刻才被告知优惠没了。**先算不依赖身份的、身份明确后再补校**，是三者中体验损失最小的。

**T1 成功**：与手输码完全一致——chip 出现、`Discount` 行与 `Total`、主 CTA 金额联动刷新。**不额外标注"该码来自链接"**。

**T1 失败**：按买家**能不能自救**分两类

| 失败原因 | 呈现 |
|---|---|
| **能自救**（未达满额 / 满件门槛） | 出**中性正向引导**（如 `Spend $40 more to unlock $80 off.`），位置在订单摘要上方，**不用红色错误态**——买家没做错什么，他只是还没加够 |
| **不能自救**（码无效/过期/用尽/已享更优/商品不适用/地区不符/账户不适用） | **完全静默**，不提示、**不回填码值**，页面表现与"没有这个码"完全一致 |

> 该分类**仅限链接自动应用路径**。买家手输码时，失败态仍按九条文案在输入框下方出行内错误提示，**未作任何改动**。

**🔴 T2 不通过（本次重点，此前是规则真空）**

| 步 | 动作 |
|---|---|
| 1 | **取消该码的 apply**——从已应用集合移除，chip 消失，整单重新求最优组合 |
| 2 | **把码值回填到优惠码输入框** |
| 3 | **在优惠码输入框下方的既有错误提示位**展示不通过的原因 |

- **文案**：限次不通过 → 第 4 条 `You've already used this code.`；适用用户不通过 → 第 8 条 `This code isn't available with this email.`
- **位置**：优惠码输入框正下方（§2.6.4 定义的行内错误提示位）——PC 仅框下红字、移动端红框 + 红字，**复用既有表单报错组件，不新增视觉规范**
- **适用范围**：**链接码与手输码同样适用**（手输码本就在输入框里，无需额外回填）

> **为什么 T2 回填、而 T1 不回填**：差别在**买家有没有输入动作**。
> T1 发生在买家进页面的瞬间，他没做任何事，回填一个他没输过的码只会让人困惑"这哪来的"；
> T2 发生在**买家刚填完邮箱**，他有明确动作，且系统正要**把已经显示的优惠拿走**——
> 此时回填码值 + 就地报错，买家才能看懂"是我填的这个邮箱用不了这个码"，而不是"金额怎么自己涨了"。

> **买家改邮箱**：结算邮箱每次变化都重新触发 T2，并**对全部已输入/已带入的码整单重新求解**——此前因身份不符被移除的码，若新邮箱符合条件则**重新生效**。

#### 2.2.4 支付成功后

| 项 | 口径 |
|---|---|
| 时机 | 支付成功（订单转 paid） |
| 条件 | **该码被本单核销了 → 清除；未被核销 → 保留**（下次结算仍可参与） |

> **为什么必须清**：不清则该码在同一浏览器会话内会被反复自动应用。而本模块允许运营配置**不限次**的码，不清就是实打实的资损口子。

### 2.3 适用用户 · 指定买家（完整 PRD §2.2.2 / §2.2.4）

`eligibility_type` 由 `all / tag` 扩为 **`all / tag / email` 三选一互斥**（不支持组合）。

**典型用法**：给某个大客户、某批潜在客户发**专属券**——这批人身上没有现成标签，运营手上只有他们的邮箱。

| 项 | 口径 |
|---|---|
| **存什么** | **存邮箱，不存账号 ID**——运营手上只有邮箱；且**未注册的邮箱也能预先配置**（存账号 ID 则"给潜在客户发专属券"这类活动根本配不出来） |
| **匹配依据** | **一律以结算邮箱为准，不走账户身份**（买家可能用 A 账户登录、把收件邮箱填成 B；两个来源都认会产生双重结论） |
| **大小写** | **不区分**，统一转小写后比对 |
| **别名归一化** | **不做** Gmail `+后缀` 与点号归一化——那是反薅规则，与"指定给某个人"的语义无关，且会误伤真实用别名收件的买家 |

**录入规则**（比照既有的「按商品 ID 导入」）：

| 项 | 规则 |
|---|---|
| 分隔符 | 换行 / 英文逗号 / 中文逗号 / 分号 / 空格，混排均可 |
| 规范化 | 逐条 trim → 统一转小写 |
| 去重 | 规范化后去重，重复项不报错、只提示已去重 N 个 |
| 格式校验 | 逐条校验，**不拦截整批**，分「有效 / 格式不正确」两组回显 |
| 实时汇总 | 「识别 N 个：有效 M 个，重复已去重 X 个，格式不正确 K 个」 |
| 数量上限 | **500 个** |
| 编辑语义 | **全量覆盖**，不做增量追加 |
| 保存口径 | **只保存有效邮箱** |

**详情页展示**：`=email` 时展示「指定买家（N 个）」+ **逐个列出全部邮箱**，数量多时清单区域内部滚动。

> **为什么必须逐个列出**：运营打开详情就是为了核对「配的是不是这几个人」，只给数量等于没回答；而**进行中的活动不可直接编辑**，运营连回编辑页看一眼都做不到。

### 2.4 🔴 取消优惠码强制登录（改造项，影响面超出本需求）

| 项 | 内容 |
|---|---|
| **现状** | 未登录买家**可以输入优惠码**，但配置了使用次数限制的码，系统**要求先登录才能核验** |
| **改为** | **登录不得作为在 checkout 使用优惠码的必要条件** |
| **影响范围** | **全部优惠码，不限于链接带来的码**。这是对现行实现的**改造，不是新增能力** |

**限次判定口径**：

| 买家状态 | 怎么查 | 结果 |
|---|---|---|
| 已登录 | 按当前账户查历史核销 | 沿用现有口径，不变 |
| **未登录 · 邮箱已注册** | **按结算邮箱关联到对应账户**，查该账户历史核销 | 按每人限次口径判定 |
| **未登录 · 邮箱未注册** | 无关联账户 = 无历史核销 | **判定通过、直接放行**；下单时静默建号，核销记入新账户 |

> 🔴 **任何情况下不弹登录、不拦截下单。** 若实现成「查不到就拦」，等于换个方式强制登录，本次改造白做。

**为什么必须改**：强制登录卡在下单最后一步（买家已填完地址、选好支付方式），是转化漏斗上最贵的门槛；而它**换不来更强的风控**——平台本就允许未登录下单并以结算邮箱静默建号，买家换个邮箱注册照样能再用一次，与未登录换邮箱的绕过效果完全相同。**等于用确定的转化损失，换一个并不成立的风控收益。**

> **前置依赖**：用户管理模块的「邮箱 → 账户」反查。**若暂不具备，不得退回「要求登录」**——先按「查不到即放行」上线，再补反查。

## 三、数据模型变更（ER v2.2 → v2.3）

> **链接本身不落库**——它是「域名 + `/discount/` + `promotion_code.code`」的拼接结果，平台不追踪已投放的链接。

## 四、依赖与风险

### 4.1 需要其他模块配合的 4 件事

| # | 依赖方 | 需要对方做什么 | 阻塞级别 |
|---|---|---|---|
| 1 | **用户管理** | 提供「邮箱 → 账户」反查 | 可降级（先按查不到即放行上线） |
| 2 | **短链服务（社媒分享）** | 确认「创建运营短链」的基础 URL 支持指向 `/discount/{码}` | 需确认（预计天然支持） |
| 3 | **短链服务 / App** | **优惠码链接不得列入 App 深链声明路径** | 🔴 **漏了就是真 bug** |
| 4 | **Collection 模块** | 提供 **C 端 Collection 落地页的 URL 规则** | 需确认 |

> **第 3 条为什么是真 bug**：App 被系统唤起时**服务端收不到请求**，而 App 尚不认识这个码 → **码会静默丢失**，买家和运营都察觉不到。「在浏览器中打开」通过「不列入深链声明」实现即可，不需要额外手段。

> **第 4 条为什么要确认**：PRD 暂按 `/collection/{CollectionID}` 书写，**若 C 端实际用 slug/handle，则链接全是死链**，而这在营销侧测不出来。

### 4.2 已知敞口（已拍板接受，运营须知悉）

| # | 敞口 | 对运营的含义 |
|---|---|---|
| 1 | **未登录场景「每人限次」可被绕过** | 换邮箱 / Gmail 加 `+后缀` 或加点均可绕过，行业无原生手段可解。**大额优惠码务必同时配总使用次数上限** |
| 2 | **「指定买家」是软名单，不是身份锁** | 只凭结算邮箱放行，**任何知道名单里某个邮箱的人都能冒用**。这是「存邮箱不存账号 ID」的必然代价 |
| 3 | **人群限定的自动折扣会把专属价泄给全站** | 商详到手价、Sale 打标、搜索排序都会用这个价，而实际只有名单内的人能享。**人群限定的活动优先用「优惠码」触发**——码不进商详取价逻辑，天然不外泄 |
| 4 | **跨市场投放会静默全失效** | 链接不携带市场标识，市场不匹配时按 T1「不能自救」类静默处理，运营端看不到回流信号 |
| 5 | **链接不跨设备** | 手机点链接、电脑下单则不生效 |
| 6 | **落地到 checkout 之间没有任何反馈** | 买家在这段路径上无从得知码已生效，可能因此流失。本版不做提示条（保持 C 端零新增元素），若投放数据显示流失明显再单独评估 |

## 五、验收要点

### 5.1 三个最容易实现错的点

| # | 点 | 错误实现会怎样 |
|---|---|---|
| 1 | **「新码覆盖旧码」只覆盖链接码位** | 若理解成「整单只能 1 个码」，等于改掉了已交付的多码规则 |
| 2 | **未登录 + 邮箱未注册 = 直接放行** | 若实现成「查不到就拦」，等于换个方式强制登录 |
| 3 | **T2 不通过要取消 apply + 回填码值 + 就地报错** | 若沿用静默，买家会看到 chip 无声消失、Total 上涨且无任何解释——**这是本次最可能变成客诉的场景** |

### 5.2 核心验收场景

| # | 场景 | 预期 |
|---|---|---|
| 1 | 点链接 → 加购符合范围且达门槛的商品 → 进 checkout | 码**自动生效**，chip 出现、`Discount` 行与 `Total` 联动 |
| 2 | 点链接 → 商品不在范围内 → 进 checkout | **完全静默**，页面与"没有这个码"一致 |
| 3 | 点链接 → 差 $40 未达满额门槛 → 进 checkout | 出**中性正向引导**「还差多少」，非红色报错 |
| 4 | 上述场景 1 之后 → 填入**不在指定买家名单**的邮箱 → 鼠标移出输入框 | 优惠**取消**、码值**回填输入框**、输入框下方出第 8 条文案 |
| 5 | 承接场景 4 → 把邮箱改成**名单内**的 → 移出输入框 | 该码**重新生效** |
| 6 | 未登录 + 从未注册过的邮箱 + 带限次的码 | **直接放行**，不弹登录、不拦截 |
| 7 | 自动应用成功 → 点 chip 上的 ✕ → 刷新页面 | 码**不再自动回来**（会话码位已清） |
| 8 | 点链接 A → 进 checkout（A 生效）→ 返回商城点链接 B → 再进 checkout | chip **只剩 B**，A 已从已应用集合移除 |
| 9 | 支付成功（本单用了该码）→ 再次进入 checkout | 码**不再自动应用**（已清除） |
| 10 | 运营给圈了 2 个 Collection 的 code 活动生成链接 | 落地页**锁定首页**、下拉禁用，helper 说明原因 |
| 11 | 运营给草稿态 code 活动 | 列表操作列与详情页**都没有**「优惠码链接」入口 |
| 12 | 运营在买家邮箱框粘贴含拼错域名、重复项、大小写混杂的清单 | 实时汇总「识别 N 个：有效 M 个，重复已去重 X 个，格式不正确 K 个」，错误项逐条列出 |
