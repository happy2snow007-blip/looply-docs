## 3. 新增功能

### 3.1 优惠码分享链接（主需求）

运营为优惠码活动生成一条含 code 的链接对外投放；买家点击后码自动跟随，进 checkout 时**自动生效、无需手输**。

**折扣规则一条未改**——校验、试算、分摊、核销全部沿用既有条款，新增的只是「码怎么送到买家手上」这条链路。

| PRD 章节 | 内容 |
|---|---|
| **§2.2.6**（新增） | 运营端·优惠码链接：入口、弹窗元素、落地页取值范围、链接形态、操作流程 |
| **§2.13**（新增，含 5 个子节） | 机制·挂码与自动兑现：点击处理 / 码存哪存多久 / 进 checkout 兑现 / 支付后清除 / 未登录说明 |

**关键口径**（开发极易误读，已在 PRD 内加粗）：

- **链接是纯拼接的静态字符串**：`https://{域名}/discount/{优惠码}[?redirect=/collection/{ID}]`，**不落库、不调接口、平台不追踪已投放的链接**
- **营销侧不生成短链**：运营复制链接后到「短链管理 → 创建运营短链」粘贴为基础 URL，在那里配 UTM 并生成投放短链。二维码、点击统计、独立访客、App 唤起**全部由短链服务承载**
- **码存在浏览器会话里、只有一个码位**：新码覆盖旧码；**不写购物车**（Buy Now 跳过购物车，挂购物车则该链路读不到）
- **「新码覆盖旧码」覆盖的是「链接带来的那个码位」，不是把 checkout 限死成单码**——买家手输的码仍走 §2.6.2 多码规则，最终可能是「1 个链接码 + N 个手输码」

### 3.2 适用用户 · 指定买家（按邮箱）

`eligibility_type` 由 `all / tag` 扩为 **`all / tag / email` 三选一互斥**，运营可按邮箱指定专属买家。

- **存邮箱而非账号 ID**——**未注册的邮箱也能预先配置**（给潜在客户发专属券是典型用法，存账号 ID 则这类活动根本配不出来）
- 匹配**不区分大小写**；**不做** Gmail `+后缀`/点号归一化（那是反薅规则，与本功能语义无关，且会误伤真实用别名收件的买家）
- 录入规则比照既有的「按商品 ID 导入」：切分去重 → trim → 转小写 → 格式校验 → 有效/无效分组回显 → **只保存有效邮箱**；**上限 500 个**；编辑为**全量覆盖**

## 4. 既有功能调整

### 4.1 🔴 取消「带限次的优惠码必须登录才能核验」（影响面超出本次需求）

| 项 | 内容 |
|---|---|
| **现状** | 未登录买家**可以输入优惠码**，但配置了使用次数限制的码，系统**要求先登录才能核验** |
| **改为** | **登录不得作为在 checkout 使用优惠码的必要条件**。限次改为**按结算邮箱关联查询**：查得到按查到的次数判，**邮箱未注册 = 无历史核销 = 直接放行**。任何情况下**不弹登录、不拦截下单** |
| **影响范围** | **全部优惠码，不限于链接带来的码**。这是对现行实现的**改造项，不是新增能力** |

**为什么必须改**：强制登录卡在下单最后一步（买家已填完地址、选好支付方式），是转化漏斗上最贵的门槛；而它**换不来更强的风控**——平台本就允许未登录下单并以结算邮箱静默建号，买家换个邮箱注册照样能再用一次，与未登录换邮箱的绕过效果完全相同。

> **前置依赖**：用户管理模块的「邮箱 → 账户」反查能力。**若暂不具备，不得退回「要求登录」**——先按「查不到即放行」上线，再补反查。

### 4.2 新增两张全模块权威表（§2.6.2 下）

v2.3 及以前，优惠码的校验项清单在 **§2.6.2 / §2.8.3 / §2.13.3 三处各写了一份**，项目集合与先后都不同。而 §2.6.4 的九条文案是**互斥单条展示**的——三份清单会让同一个码报出不同的错。本版收敛：

| 表 | 作用 |
|---|---|
| **《优惠码校验链》** | **全模块唯一权威**。7 项按序、**每项标注是否依赖买家身份**、命中第一条即返回不继续校验。§2.8.3 与 §2.13.3 的重复清单已删除、改为引用本表 |
| **《两时点校验模型》** | **checkout 通用规则，链接码与手输码同走一套**。T1（码进入订单时）只校第 1–5 项；T2（结算邮箱可用后）补校第 6–7 项（每人限次 + 适用用户） |

> **T2 的触发时机**：结算邮箱通过格式校验且失焦、**且值发生变化**时触发一次；值未变不重复触发。买家中途改邮箱同样触发，并**对全部已输入/已带入的码整单重新求解**——此前因身份不符被移除的码，若新邮箱符合条件则**重新生效**。

## 5. 开发关注重点

### 5.1 必须先读的两张表

**《优惠码校验链》与《两时点校验模型》（§2.6.2 下）是本次实现的核心依据。** 三处旧清单已删除改为引用，请勿再按各章节自行罗列的校验项实现。

### 5.2 三个最容易实现错的点

| # | 点 | 错误实现会怎样 |
|---|---|---|
| 1 | **「新码覆盖旧码」只覆盖链接码位** | 若理解成「整单只能 1 个码」，等于改掉了已交付的 §2.6.2 多码规则 |
| 2 | **未登录 + 邮箱未注册 = 直接放行** | 若实现成「查不到就拦」，等于换个方式强制登录，本次改造白做 |
| 3 | **T2 不通过要「取消 apply + 回填码值 + 就地报错」三步** | 若沿用「静默」，买家会看到 chip 无声消失、Total 上涨且无任何解释——**这是本次最可能变成客诉的场景**；若只报错不回填，错误提示挂在空输入框下没有归属 |

### 5.3 T1 失败的呈现按「能否自救」分两类

| 失败原因 | 呈现 |
|---|---|
| **能自救**（未达满额/满件门槛） | 出**中性正向引导**（如 `Spend $40 more to unlock $80 off.`），位置在订单摘要上方，**不用红色错误态** |
| **不能自救**（码无效/过期/用尽/已享更优/商品不适用/地区不符/账户不适用） | **完全静默**，不提示、不回填码值 |

> 该分类**仅限链接自动应用路径**。买家手输码时，失败态仍按 §2.6.4 九条在输入框下方出行内错误提示，**未作任何改动**。

### 5.4 会话码位的完整生命周期（7 个出口）

§2.13.2 有完整出口表，其中两个最易漏：

- **买家手动移除 chip → 码位保留**，只移出本次页面的已应用集合（当前页面 chip 立即消失、不自动重加；**刷新后码会重新自动应用回来，属预期**）
- **T2 补校被移除 → 保留**（否则买家改成合规邮箱后恢复不了）

### 5.4b 交付后修订（2026-08-28，产品确认）

> ⚠️ **本批修订发生在 V1.3 交付包发出之后**，包内 PRD / 迭代 PRD / 原型均已按新口径更新，请以当前包为准。

| # | 修订项 | 原口径 | 新口径 | 影响 |
|---|---|---|---|---|
| 1 | 分享链接弹窗的人群限定提示 | 适用用户 ≠ 全部时，弹窗额外提示「不建议公开投放」 | **取消该提示** | 仅运营端 UI，不涉及逻辑。是否投放由运营自行判断 |
| 2 | 买家在 checkout 点 chip 上的 ✕ | 清除码位 | **保留码位**，只移出本次页面的已应用集合 | ⚠️ **涉及实现**：当前页面 chip 须立即消失且不自动重加；**刷新或重进 checkout 后该码重新自动应用，属预期行为、不得当缺陷处理** |

> 修订 2 的取舍：码是运营发出的权益，链接多投在社媒，买家误点 ✕ 后未必找得回原链接——清掉即等于永久失去。保留码位让「移除」只在当前页面生效，代价是刷新后会回来，**测试须按预期通过、不按 bug 提**。

## 7. 已知敞口（已拍板接受，运营须知悉）

| # | 敞口 | 说明 |
|---|---|---|
| 1 | **未登录场景「每人限次」可被绕过** | 以结算邮箱识别，换邮箱 / Gmail 加 `+后缀` 或加点均可绕过。行业无原生手段可解（Shopify 亦然）。**大额优惠码务必同时配置总使用次数上限** |
| 2 | **「指定买家」是软名单，不是身份锁** | 只凭结算邮箱放行，不登录、不验证、不需要拥有该邮箱——**任何知道名单里某个邮箱的人都能冒用**。这是「存邮箱不存账号 ID」这一选型的必然代价 |
| 3 | **人群限定的自动折扣会把专属价泄给全站** | 规则一不判适用用户，因此「指定买家/指定标签」的**自动折扣**其折后价会成为该商品对**所有买家**的到手价，还会被打 Sale 标推进搜索索引。**本版决定接受**。<br>**对运营的含义：人群限定的活动优先用「优惠码」触发**——码不进规则一，天然不外泄 |
| 4 | **跨市场投放会静默全失效** | 链接不携带市场标识，买家所处市场由站点既有识别逻辑决定；市场不匹配时按 T1「不能自救」类静默处理，运营端看不到回流信号 |
| 5 | **优惠码链接不跨设备** | 码记在浏览器会话中，手机点链接、电脑下单则不生效 |
