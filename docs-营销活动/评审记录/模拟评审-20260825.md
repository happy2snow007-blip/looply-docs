# P0（11 条，按根因归组）

## 组 A · 新增功能后没回头重算的旧条款（4 条）

> **共同根因**：v2.4 加了「优惠码链接」和「指定买家」两个功能，但只写了新章节，**没有回头检查这两个功能会让哪些既有条款失效**。

### A-1. §2.2.1 操作列形态表未纳入「优惠码链接」

**三方一致提出（开发 P0 / 测试 P0 / 设计 P0）**

- **位置**：PRD §2.2.1「各状态实际形态」表 vs §2.2.6 入口定义 vs 原型 `PromotionListPage` 操作列
- **问题**：v2.4 给 code 活动加了「优惠码链接」操作，但 §2.2.1 那张按操作数算好平铺/收纳的表**一个字没改**。逐状态对照（优惠码活动）：

| 状态 | PRD 表写的 | 原型实际 |
|---|---|---|
| 未开始 | 4 个全平铺 | **5 个** → 3 平铺 + 更多 |
| 进行中 | 4 个全平铺 | **5 个** → 3 平铺 + 更多 |
| 已暂停 | 5 个 | **6 个** |
| 已结束 | 2 个 | **3 个** |

  同一份 PRD 里 §2.2.6 说列表有这个入口、§2.2.1 的表里没有，**两节自相矛盾**。排序优先级串「详情 > 编辑 > 状态主操作 > 复制 > 删除」里也没有它的位置。
- **建议**：该表拆成「自动折扣 / 优惠码」两组重算，并把「优惠码链接」写进排序优先级串（原型放在「结束活动」之后、「复制」之前）。

### A-2. Collection 是多选，但落地页规则按单个写死

**三方一致提出（开发 P0 / 测试 P0 / 设计 P0）**

- **位置**：§2.2.2 适用商品（Collection **多选**，命中任一即适用）vs §2.2.6 落地页表（全程单数「该 Collection」）vs 原型 `ShareLinkModal` 单值 `scopeRef`
- **问题**：运营圈了 Autumn Picks + Winter Drop 两个 Collection 的 code 活动，打开链接弹窗时下拉里显示几个选项？默认哪个？还是退化锁首页？**三份制品一个都答不上来**。§2.2.6 还写了「不存在运营填错 ID 的情况」——这句在多选场景下不成立。
- **建议**：三选一定死 ①下拉列出全部已圈选 Collection + 首页 ②多选时锁定首页 ③把「可选 Collection 落地页」的前提收紧为「只圈了 1 个」。**另外两种情形也要写清楚**。

### A-3. 详情页承诺「门槛都能查到」，但字段清单里没有门槛

**两方提出（设计 P0 / 测试 P1）**

- **位置**：§2.2.4 状态可见性说明 vs §2.2.4 页面元素清单 vs 原型 `basicTab`
- **问题**：§2.2.4 硬性写着「已结束的活动同样可以查看**完整规则配置**——当时的**门槛**/折扣值/封顶/适用范围，都要能查到」。但紧接着的字段清单**没有「使用门槛」、没有「总使用次数」**，原型逐字段核对下来同样两项都没有。
  后果与 PRD 自己为「适用用户」写的论证一模一样：客服转来「买家说满 $300 用不了」，运营在后台**任何页面都查不到这个活动的门槛配的是多少**——列表没有门槛列、详情没有、而进行中活动不可编辑（§2.2.2 A5），只能先暂停活动再进编辑页看。
- **建议**：详情页基本信息补「使用门槛」与「总使用次数」两行，PRD 字段清单与原型同步。

### A-4. ER 两个枚举字段没跟上 PRD

**三方提出（开发 P0 / 测试 P2 / 设计 P2）**

- **位置**：`gen_营销活动_er_v2.3.py` `promotion_rule` 的两个字段
- **问题**：
  - `eligibility_type` 仍是 `all全部/tag指定用户标签(V1;新客为标签之一)`，**没有 email**。脚本头注释、`DESIGN_RULES`、`promotion_eligibility` 的 note 三处都写了 email，唯独渲染到图上的字段注释漏了——**数据区是唯一数据源**，开发照 ER 建表就会漏掉这个枚举值，`buyer_email` 永远写不进去。
  - `product_scope` 仍是 `all/category/brand/listing`，**缺 tag 与 collection**（PRD §2.2.2 是六值，`promotion_target.target_type` 也已含这两项）。这是 v2.0 引入时的历史遗留，但**本版 §2.2.6 的落地页判定正是以 `product_scope=collection` 为分支条件**——枚举存不下这个值，新功能的判定入口直接失效。
- **建议**：两处字段注释补齐，重跑生成脚本，核对 SVG 内嵌 metadata。

## 组 B · 买家身份判定口径散在多处且互相打架（4 条）

> **共同根因**：v2.4 把「未登录可用 + 邮箱识别」这条新口径写进了 §2.6 / §2.8.1 / §2.13.3 / §2.13.5 **四个地方**，但四处的措辞、校验项清单、依赖身份与否的划分**各不相同**。

### B-1. 「买家邮箱」到底指账户邮箱还是结算邮箱

**测试视角提出（P0）**

- **位置**：§2.8.1 vs §2.13.5 vs §2.8.3 第 1 步
- **问题**：名单含 `vip@x.com`，买家用账户 `other@y.com` 登录、把结算邮箱填成 `vip@x.com`——算不算命中？
  - §2.8.1：「已登录取当前账户」
  - §2.13.5：「`=email` 的活动同样按结算邮箱判定」
  - §2.8.3 第 1 步：只写「校验买家邮箱是否在名单内」，没说是哪个
  **反向用例同样卡住**：账户邮箱在名单内、结算邮箱填了别的。
  这条直接决定「指定买家」能不能被转送使用，是本版新功能的核心判定，**必须唯一**。
- **建议**：明确 `=email` 一律以**结算邮箱**为准（与未登录口径统一），并在 §2.8.1「买家身份」下补一句「email 型适用用户不走账户身份」。

### B-2. Apply 的校验项清单与顺序，三节写了三个版本

**测试 P0 / 设计 P1**

- **位置**：§2.6.2 步 1 / §2.8.3「新码 Apply 四步」步 1 / §2.13.3 步 1

```
§2.6.2   码存在→商品范围→门槛→适用用户→限次→市场
§2.8.3   码存在→活动时间→限次→适用用户→商品命中        （无门槛、无市场）
§2.13.3  码存在→商品范围→门槛→市场                      （无适用用户、无限次）
```

- **问题**：项目集合与先后都不同，而九条失败文案是**互斥单条展示**的，先命中哪条报哪条。测「一个码同时未达门槛 + 不在名单 + 市场不符」应该报 2a / 8 / 7 哪一条？三份清单给三个答案。
- **建议**：三处合并为**一份带序号的校验链**（唯一权威），另两处改为引用；并明确「命中第一条即返回、不继续校验」。

### B-3. 未登录且未填邮箱时 Apply，两节预期相反

**测试 P0 / 开发 P1（购物车版本）**

- **位置**：§2.6.2 步 1 vs §2.8.1「买家身份」
- **问题**：未登录、邮箱还没填，Apply 一个每人限次已用尽（或自己不在名单）的码：
  - §2.6.2 步 1 把「适用用户命中、限次未用尽」列为**必过项** → 预期是红字报错
  - §2.8.1 说「身份为空时这两项不判、其余照常计算，**不得因此拒绝**」 → 预期是 chip 出现、金额下降
  **同一场景两个相反的预期。** 开发视角还发现同一矛盾出现在购物车：§2.8.1 说身份为空不判，§2.8.3 第 1 步末尾说「购物车场景执行前两项中的『适用用户』」——未登录买家的购物车会出现两种金额。
- **建议**：在 §2.6.2 步 1 给每个校验项标注「是否依赖买家身份」，并把 §2.13.3 的两时点模型**提升为 checkout 通用规则**（链接码与手输码同样适用）。

### B-4. §2.13.3 第 3 步的补校项漏了「指定买家」

**测试视角提出（P1，但属 B 组根因）**

- **位置**：§2.13.3 步 3
- **问题**：步 3 写的是「补校**每人限次**与**适用用户标签**」——**字面上不含 `eligibility_type=email`**。照字面读会得出「名单从不校验、码一直生效」的荒谬结论，而 §2.6.4 第 8 条又明写包含「不在指定买家邮箱名单内」。
- **建议**：改为「补校每人限次与适用用户（tag 与 email 两类）」。

## 组 C · 会话码生命周期模型未定死（2 条）

### C-1. §2.13.2「单码位覆盖」与 §2.13.4「B 码保留」自相矛盾

**开发视角提出（P0）**

- **位置**：§2.13.2 表「一条链接携带 1 个码，再点另一条**新码覆盖旧码**」 vs §2.13.4「为什么不整体清空：买家可能先后点过 A、B 两条链接，本单只用上 A，把 B 一并清掉买家会发现优惠莫名消失」
- **问题**：按 §2.13.2，点了 B 之后 A 已被覆盖，浏览器里**不可能同时存在 A 和 B**——§2.13.4 用来论证「不整体清空」的那个场景**在本模型下根本不会发生**。
  开发看 §2.13.4 会实现成「会话存一个码列表」，看 §2.13.2 会实现成「存一个码位」，两种实现的清除行为完全不同：前者存在「本单核销了 A、B 还留着下次再用」的资损面，后者没有。
- **建议**：二选一定死——**单码位**（则 §2.13.4 清除规则简化为「本单核销了这个码就清」，删掉 A/B 那段理由）或**多码位**（则 §2.13.2 的「覆盖」要改写，并定义上限与淘汰顺序）。

### C-2. 买家手动移除 chip 后，码会不会"复活"

**测试 P0 / 开发 P1**

- **位置**：§2.13.2 / §2.13.4 / §2.6.3
- **问题**：买家点链接进来、码自动应用、chip 出现；买家不想用（想留着下次），点了 chip 上的 ✕。刷新页面或退回购物车再进 checkout——按 §2.13.3「进入 checkout 取出记住的码」，**码又自动应用回来了，买家移不掉**。
  §2.13.4 只定义了「支付成功后清本单核销的码」这**一个**清除时机，买家主动移除是否同时清会话记录，PRD 一个字没写。
- **建议**：把会话码位的**完整生命周期列成状态表**——写入（点链接）、读取（进 checkout）、清除（支付成功核销 / 买家手动移除 / 系统补校移除 / 关闭浏览器），每种出口明确「清 or 留」。

## 组 D · 补校失败的呈现真空（1 条）

### D-1. 填完邮箱后优惠被移除、金额上涨，页面上没有任何解释

**设计 P0 / 测试 P1 / 开发 P1（手输码版本）**

- **位置**：§2.13.3 步 3
- **问题**：买家进 checkout 看到 `Discount −$30`、CTA `Pay Now at $270`；填完邮箱按个 Tab，**chip 无声消失、CTA 跳回 $300**。PRD 对这一步只写了六个字：「移除该优惠并重算，金额随之更新」。
  **而这里有个逻辑真空**：§2.13.3 定的「完全静默」，适用范围明写「仅限链接自动应用这一条路径」的**失败**——步 3 是**先成功后移除**，既不在静默的适用范围内，也没有自己的呈现定义。
  这比步 1 的静默严重得多：步 1 买家从未看到过优惠；步 3 是**当着买家的面把已显示的优惠拿走并涨价**，还发生在他有明确输入动作的时点。**这是本版最可能变成客诉的场景。**
  同一真空也存在于手输码：未登录手输「指定买家」码 → 身份为空判不了 → Apply 成功、chip 出现 → 填邮箱后被撤销 → chip 消失还是保留？出不出提示？PRD 没有对应条款。
- **建议**：步 3 的移除**必须给提示**——这里买家有输入动作、报错有归属，完全适用 §2.6.4 既有文案（第 4 条 / 第 8 条）。呈现位置建议挂在 `Discount` 行或订单摘要顶部，**而不是优惠码输入框**（买家没在那里输过东西）。并明确手输码在步 3 被移除时走同一套呈现。

## 评审方法说明

**三方撞车的问题优先级更高**——三个 agent 独立评审、互不可见，同时提出的问题基本可以排除"过度解读"：

| 撞车项 | 开发 | 测试 | 设计 |
|---|---|---|---|
| 操作列形态表漏算 | P0 | P0 | P0 |
| 多选 Collection 落地页 | P0 | P0 | P0 |
| ER 枚举没跟上 | **P0** | P2 | P2 |
| 邮箱输入无校验 | P1 | P1 | P1 |
| 落地页文案不一致 | P3 | — | P2 |
| 原型注释过期 | P3 | — | P3 |

> **ER 枚举那条三方评级差异很大**（开发 P0、另两方 P2）——**开发的评级是对的**：ER 数据区是唯一数据源、SVG metadata 由它生成，开发照它建表就会漏掉枚举值，`buyer_email` 永远写不进去。另外开发独家发现的 `product_scope` 缺 tag/collection，**直接卡死本版落地页的判定入口**，另两方都没查到这一层。
