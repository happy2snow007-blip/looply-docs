## P0(规则缺失或制品矛盾,阻塞开发)

### 1. [开发] 监控链路快照含优惠码环节,与扫描口径"仅自动折扣"矛盾

- **位置**:PRD §2.3.4(扫描口径与 C 端到手价一致,仅自动折扣、含叠加)+ 原型 v5 告警样例 AL20260726003(链路第 4 步"优惠码 WELCOME10(固定减,封顶后)")
- **问题**:按 PRD 与 A3 拍板口径,到手价不计优惠码,监控扫描的价格链路中不可能出现优惠码环节;但原型排查抽屉的示例数据把优惠码作为到手价计算的一环并计入降幅 55%。开发照原型样例实现,会把码折扣纳入扫描降幅,监控范围与告警金额全部失真;照 PRD 实现,则该样例场景(码叠出超阈)根本不会产生告警,两份制品给出的是两套监控口径。
- **建议**:确认以 PRD 口径为准,替换原型该条样例数据(链路仅含自动折扣环节);若确有"码叠加后超阈"的监控诉求,应作为口径变更明确写入 §2.3.4 再同步 ER/原型。

## P1(规则不完整,影响质量)

### 2. [开发] active/paused 活动的可编辑字段范围未定义

- **位置**:PRD §2.2.2(前置条件:编辑仅 draft/active/paused)
- **问题**:PRD 只锁定了所属市场(创建后不可改)和 total_usage_limit(不得小于已核销),其余字段在进行中活动上是否可改全部未说。场景:进行中的码活动把 code 从 SUMMER20 改成 FALL30——已投放出去的旧码立刻失效、已 Apply 未支付的会话怎么算?触发方式 auto↔code、折扣值类型 percentage↔fixed 在已产生核销后切换,核销记录的 code_id 关联与订单快照如何自洽?
- **建议**:给出编辑字段矩阵(按状态 × 字段:可改/锁定),至少明确进行中活动锁定触发方式与优惠码字符串,只允许调力度/时间/限次类字段。

### 3. [开发] 结算中活动结束/暂停的时点口径缺失

- **位置**:PRD §2.2.5(结束后立即停止对"新订单"生效)+ §2.9(核销流程无规则状态校验)
- **问题**:"新订单"以哪个时点界定未定义。场景:活动 23:59 到期,买家 23:58 完成试算进入支付,00:01 支付成功——核销时活动已 ended,这单优惠是否有效?§2.9 核销步骤未写"校验规则状态",§2.6 支付前二次校验只针对码/限次,未提活动状态与时间。自动折扣场景同样存在(无占用机制)。
- **建议**:明确锁定时点(建议:支付发起时二次校验通过即锁定,支付成功照常核销,活动结束不影响已发起支付的订单),并把活动状态/时间纳入支付前二次校验项。

### 4. [开发] 核销兜底拒绝后该订单优惠的处理缺失

- **位置**:PRD §2.9 步骤 1(达 total_usage_limit 即拒绝,为最终兜底)
- **问题**:兜底拒绝发生时订单已支付成功、买家已按优惠价付款、订单侧已按试算落 order_discount——核销被拒后这单的优惠算不算数?不追款的话 used_count 与实际优惠单数永久差一笔,§2.10 三向对账每天都会报不平;追款/取消订单又超出 V1 能力。PRD 只写了"拒绝",没写拒绝之后怎么办。
- **建议**:明确兜底拒绝的后置动作(建议:仍写入核销但标记超发类型供对账区分,或明确该场景计入对账差异的处理口径),避免对账规则与兜底规则互相打架。

### 5. [开发/测试] 满额门槛计算基准未定义

- **位置**:PRD §2.8 步骤 3(满额按命中商品行合计)
- **问题**:门槛判定在步骤 5/6 折扣计算之前执行,但"命中商品行合计"是原价合计还是折后合计未写。场景:min_amount=$500,命中商品原价合计 $520、自动折扣后 $416——门槛达标与否两种口径结论相反;购物车与 checkout 若各自理解不同,还会出现购物车显示已享、checkout 又被剔除。测试无法写用例。
- **建议**:明确基准(建议对齐 Shopify:按折扣前商品小计判定),并说明多折扣叠加时统一用同一基准。

### 6. [开发] "码占用"的载体与判定口径缺失

- **位置**:PRD §2.6 规则说明(支付发起后码占用,支付失败/取消释放)
- **问题**:占用没有数据载体也没有判定口径。ER 中核销流水只在支付成功时写入,§2.8 限次判定只统计 status=valid 的核销——那么"占用"体现在哪?场景:总量剩 1 次,用户 A 支付发起(占用),用户 B 此时试算——B 看到的是可用(valid 核销未满)还是已抢完(占用计数)?A 迟迟不支付,占用多久释放(支付超时时长归订单,但释放联动未声明)?
- **建议**:明确占用是否参与总量/每人限次判定;若参与,补占用记录口径(可为核销流水加 pending 状态或声明由订单支付超时事件驱动释放);若不参与,删除"占用"表述,明确并发窗口靠支付前二次校验+核销兜底承接。

### 7. [开发] 复制操作规则缺失

- **位置**:PRD §2.2.1(更多下拉:复制,可作为模板复制后改所属市场)
- **问题**:只有一句操作名。场景:复制一条已核销 3,719 次的进行中码活动——新活动状态是什么(draft?)、used_count/核销记录是否清零、优惠码是否带过来(不改市场时同码必违反 (market,code) 唯一,保存必失败)、跨市场复制时金额字段(fixed_amount/封顶/满额门槛)是照搬数值还是清空强制按新币种重录(照搬 $ 数值到 HK$ 语义完全不同)?
- **建议**:定义复制规则:生成 draft、计数清零、码字段清空待重录(或重新随机生成)、改市场时金额字段清空强制重录并提示。

### 8. [开发] promotion_code.status=disabled 无产生路径

- **位置**:PRD §2.6 校验失败枚举("已停用")+ ER promotion_code.status(active/disabled)
- **问题**:C 端失败原因和 ER 枚举都承认"码已停用"这个状态,但运营端列表、详情、编辑页没有任何停用/启用码的操作入口,操作类型枚举里也没有对应动作。开发无法回答"disabled 从哪来":要不要做入口?还是 V1 该状态永远不会出现?
- **建议**:二选一并写明:V1 不提供停用码操作,ER 该枚举为 V2 预留、C 端"已停用"文案分支 V1 不会触发;或在活动操作中补"停用码"入口与操作记录。

### 9. [设计/开发] 列表/推荐位促销展示缺定义

- **位置**:C 端 UI 稿①(推荐位卡片促销样例)+ PRD §2.8 触发条件("商详/列表到手价查询")vs §2.4-2.7(仅商详/购物车/checkout/订单详情四个页面)
- **问题**:UI 稿在商详推荐位画了促销价卡片,机制层也预设了"列表到手价查询"输入,但 PRD 页面型章节没有任何列表卡片(首页推荐、分类列表、搜索结果、商详推荐位)的促销展示定义——覆盖哪些列表、卡片上出哪些元素(到手价/划线价/标签?)、获取失败降级——全部空白。开发按 §2.4-2.7 实现会漏掉推荐位,按 UI 稿实现又没有规则依据。
- **建议**:新增一节定义 V1 列表/卡片场景促销展示范围与元素(或明确 V1 仅商详推荐位、其余列表 V2,并同步 UI 稿口径)。

### 10. [开发/测试] 购物车勾选与门槛判定口径 + 购物车模块依赖未声明

- **位置**:PRD §2.5(门槛按当前购物车内命中商品合计判定)+ §三 依赖表(无购物车行);购物车模块已交付 V1.1(~/Desktop/海外业务/购物车/)
- **问题**:购物车支持勾选部分商品结算(UI 稿"勾选联动实时重算"),满额/满件门槛按"购物车内命中商品合计"还是"已勾选命中商品合计"判定未写。场景:满 2 件减 $20,车内命中 2 件但只勾选 1 件——优惠行出不出?若按全车判定,进 checkout(仅勾选行)后又不达门槛,两页金额跳变。同时购物车模块已有交付设计,PRD 依赖表未声明对它的依赖(汇总结构嵌入优惠行、勾选联动重算、结算入口不阻塞)。
- **建议**:明确门槛与优惠行均按"已勾选的命中商品"集合计算(与 checkout 一致);依赖表补购物车模块一行。

## P2(描述可更精确)

### 11. [开发] discount_type 的 V1 固定值口径未写

- **位置**:ER promotion_rule.discount_type(product/order)vs PRD §2.2.2 表单(无此字段)
- **问题**:ER 有该字段且含 order 枚举(V2 订单折扣),PRD 与原型均未提及;开发不知道该字段 V1 谁来赋值。
- **建议**:PRD 全局约定补一句:V1 固定 discount_type=product,系统默认写入,无表单入口;order 为 V2 预留。

### 12. [开发] promotion_code.used_count 维护未定义

- **位置**:ER promotion_code.used_count vs PRD §2.9(仅写 rule.used_count±1)
- **问题**:核销/回滚流程未提码级计数增减;码级计数不维护则 ER 字段无数据来源,维护则回滚时也要 −1,均未写。
- **建议**:§2.9 补充:码类核销同步 code.used_count+1、回滚 −1;或声明 V1(1:1 单码)不维护、字段 V2 启用。

### 13. [开发] pending 告警"更新至最新"的范围与留痕未定义

- **位置**:PRD §2.3.1 告警生成与去重规则
- **问题**:同商品+市场+类型 pending 时"更新该告警至最新"——更新哪些字段(命中活动、快照、降幅、告警时间全量覆盖?)。场景:告警原指向活动 A,A 被暂停后新活动 B 又触发同类型超阈,更新后 A 的错配证据链被覆盖,排查对象变成 B,处置留痕断档;暂停活动与新活动交替命中时告警会反复翻新,首次发现时间也丢失。
- **建议**:明确更新范围(建议保留首次告警时间,覆盖价格/降幅/命中活动/快照)并说明证据链以更新后快照为准。

### 14. [开发] 草稿发布时起止时间已过期的校验缺失

- **位置**:PRD §2.1.4 状态机 + §2.2.1(draft 的"发布生效")
- **问题**:陈年草稿 end_at 已过去,点发布 → 状态置 active 但按时间判定永不生效,列表显示"进行中"误导运营;start_at 已过则立即生效,是否符合预期也未提示。
- **建议**:发布时校验:end_at 已过拦截提示"结束时间已过期,请修改后发布";start_at 已过给二次确认"发布后立即生效"。

### 15. [开发] 品类圈选层级口径未定义

- **位置**:PRD §2.2.2(product_scope=category)+ §2.8 步骤 1
- **问题**:商品类目为多级树,圈选"箱包"父类是否命中其下子类商品未写,直接影响命中范围与试算总数。
- **建议**:明确"圈选品类含其全部子品类商品"(或仅叶子类目可选),并与商品域类目查询口径对齐。

### 16. [开发/测试] fixed 折扣叠加商品降价可致 $0 到手价

- **位置**:PRD §2.8 步骤 6(fixed:减免=min(fixed_amount,现价))+ §2.2.2(仅保存时校验 fixed_amount<最低原价)
- **问题**:保存后商品降价至 ≤ fixed_amount,减免=现价,到手价 $0,商品白送;当前仅靠监控事后告警(100% 降幅)发现,期间订单已可 0 元成交。商详"到手价≥原价不展示"只防反向,不防 0。
- **建议**:明确是否允许 $0 到手价;建议加计算层下限保护(如到手价 <$0.01 时该折扣对该件不生效并触发告警)。

### 17. [开发] 不可叠加折扣多条命中时商详价与成交价可能不一致

- **位置**:PRD §2.8 步骤 5(不可叠加取整单优惠金额最大)+ 展示口径差异
- **问题**:商详单品口径取该件减免最大的折扣,订单级取整单优惠最大的折扣,两者可能不是同一条(如折扣 A 对该件减更多,但折扣 B 覆盖购物车更多件整单更优)——买家看到的商详到手价与 checkout 成交价不一致且无解释。PRD 未承认/未定义此场景的展示策略。
- **建议**:在 §2.8 展示口径差异中显式声明该不一致可能存在,约定以 checkout 试算为准,并评估是否需要 C 端说明文案。

### 18. [测试] 优惠码防猜与随机码规格不可判定

- **位置**:PRD §2.2.2 优惠码规则
- **问题**:"禁纯连续序列"未定义:连续指数字递增/递减?字母序?键盘序?最短连续长度?A1234567、12345ABC、AAAA1111 是否合法无法判定;随机生成码的长度、字符集(是否排除 0/O/1/I)也未给,测试无法出用例。
- **建议**:给出可执行规则,如:长度 8-20;须同时含字母与数字;不允许整串为单一连续递增/递减序列;随机码固定 10 位大写字母+数字、排除易混淆字符。

### 19. [测试] 金额舍入精度未定义

- **位置**:PRD §2.8 步骤 6/7(round(现价×比例);分摊按占比,尾差进最大行)
- **问题**:round 的精度(到分?)与舍入方式(四舍五入/银行家)未写;行级分摊占比保留几位也未写。同一输入不同实现结果差 1 分,对账与幂等校验("同输入同输出")无法判定。
- **建议**:统一声明:金额计算精确到分、四舍五入(或明确其他方式),分摊比例中间计算精度与尾差归属一并写死。

### 20. [测试] 运营端 KPI 口径未说明

- **位置**:PRD §2.2.1 KPI
- **问题**:"本月累计核销次数"是否剔除已回滚(列表列"已核销"明确为有效口径,KPI 未说)、"本月"是自然月还是近 30 天、"7 天内即将结束"是否含 paused 活动——三个数字口径都留白,验收无法判定对错。
- **建议**:逐一注明:有效核销(status=valid)、自然月、active 且 end_at 在未来 7 天内。
