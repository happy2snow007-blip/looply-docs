# 营销活动 · 多商品下单优惠计算 验收用例

> 验收日期：2026-08-13
> 验收依据：`PRD/looply-营销活动-PRD-v2.3.md`（＝交付开发 V1.2-20260811 所用版本）
> 覆盖范围：§2.8.3 规则二「购物车 / checkout 最优组合」全场景枚举 14 条 + §2.8.4 汇总落库口径
> 币种：USD（US Market）。全程不涉及汇率（§2.8.5）

## 零、先读这段：三条最容易判错的规则

测之前先把这三条记住，否则会把「对的」判成 bug：

**① 目标是「整单减免最大」，不是「每行各自减最多」**（§2.8.3 第 2 步）

门槛必须由**实际使用这条折扣的那些行**凑满。所以会出现「A 商品明明能减更多，系统偏偏给它用了减得少的那条」——因为 A 要留在满减里帮忙凑门槛，整单才更省。

**② `Subtotal` 含自动折扣，`Discount` 只装优惠码**（§2.8.4）

所以 Apply 一个码把自动折扣挤掉之后，**Subtotal 会变大、Discount 会变大、Total 变小**。界面上看着像"小计涨了"，这是对的（见 Case 8）。

**③ fixed（固定减价）类折扣按行重复计算**（共用口径 C + v1.2 移除 `max_item_count`）

「满 $500 减 $100」作用在 2 个商品行上 = 减 $200，不是 $100。PRD 明确写了 fixed 类**无件数上限**，靠试算拦截和监控兜底。**测出 $200 是符合 PRD 的，不是 bug**（但业务上是否可接受，见文末待确认）。

## 二、P0 核心用例

### Case 1 · 多商品凑单达标（PRD 场景 5）

**启用**：P1
**购物车**：A $300 + B $300（全勾选）

| 检查项 | 预期 |
|---|---|
| P1 是否生效 | ✅ 生效——实际使用行合计 $600 ≥ $500 |
| A 行到手价 | $240（减 round(300×0.2)=$60） |
| B 行到手价 | $240 |
| 两行 Save 徽章 | 均展示，各 $60 |
| Subtotal | **$480** |
| Discount | 见 §四「口径冲突」——**本项暂不判定** |

---

### Case 2 · 取消勾选导致门槛失守（PRD 场景 12 ⚠️ 高危）

**启用**：P1
**操作**：在 Case 1 基础上，**取消勾选 B**

| 检查项 | 预期 |
|---|---|
| 重算触发 | 取消勾选后**立即重算**（§2.5：勾选/数量/删行/转不可售均即时重算） |
| P1 是否生效 | ❌ 失效——A 单独 $300 < $500 |
| A 行到手价 | **$300**（恢复原价） |
| A 行划线价 / Save 徽章 | **均消失**（Save = 0 才不出） |
| Subtotal | **$300** |

> 反向再勾上 B，应恢复 Case 1 的结果。

---

### Case 3 · 凑单达标但拆开更优（PRD 场景 6 ⚠️ 最高危）

**启用**：P1 + P2
**购物车**：A(Gucci) $300 + B(LV) $300

**四种分法的穷举：**

| 分法 | P1 实际作用行 | P1 达标? | 整单减免 |
|---|---|---|---|
| 甲：两件都用 P1 | $300+$300=$600 | ✅ | $60+$60 = **$120** |
| 乙：A 用 P2、B 用 P1 | 仅 B 的 $300 | ❌ 失效 | 仅 $80 |
| 丙：A 用 P2、B 不用 | — | — | $80 |
| 丁：A 用 P1、B 不用 | 仅 A 的 $300 | ❌ 失效 | $0 |

| 检查项 | 预期 |
|---|---|
| 整单减免 | **$120**（取分法甲） |
| **A 行生效的折扣** | **P1「8 折」，不是 P2「直减 $80」** ← 核心验证点 |
| A 行到手价 | $240 |
| B 行到手价 | $240 |
| Subtotal | **$480** |

> ❌ **若结果是 $140**（A 减 $80 + B 减 $60），说明实现成了"逐行各自取最大"，**这是 bug**。PRD §2.8.3 举的反例原文就是这个数。
> ❌ **若 A 行显示减 $80**，同上，即使总额碰巧对也是错的。

---

### Case 4 · 单行多折扣竞争 + 封顶（PRD 场景 2）

**启用**：P1 + P4
**购物车**：C(Chanel) $800（单件即达 $500 门槛）

| 折扣 | 减免算式 | 结果 |
|---|---|---|
| P1 | round(800 × 0.2) | $160 |
| P4 | min(round(800×0.1), 50) = min(80, 50) | $50 |

| 检查项 | 预期 |
|---|---|
| 生效折扣 | **P1**（每行至多一条，取大） |
| C 行到手价 | **$640** |
| P4 封顶是否起效 | 单独测：只启用 P4 时，C 行应减 **$50** 而非 $80 |

---

### Case 5 · 部分商品不命中（PRD 场景 8）

**启用**：P2
**购物车**：A(Gucci) $300 + D(Dior) $200

| 检查项 | 预期 |
|---|---|
| A 行 | 到手价 $220，有划线价 $300 + Save $80 |
| D 行 | 到手价 $200，**无划线价、无 Save 徽章** |
| Subtotal | **$420** |

## 三、P1 优惠码用例（仅 checkout）

### Case 6 · 多码同时生效（PRD 场景 13）

**启用**：X + Y（无自动折扣）
**购物车**：A(Gucci) $300 + B(LV) $300
**操作**：依次 Apply `CODEX` → `CODEY`

| 检查项 | 预期 |
|---|---|
| 两码是否都生效 | ✅ 都生效——作用于不同行，不违反「每行至多一条」 |
| chip 展示 | 输入框下方**两个 chip**：CODEX、CODEY |
| Subtotal | **$600**（码的减免不进 Subtotal） |
| **Discount** | **单行 $210** ← 核心验证点 |
| Total | $600 − $210 = **$390** + Shipping + Tax |

> ❌ **Discount 若拆成两行**（分别显示 CODEX -$120 / CODEY -$90）→ bug。§2.8.4 硬性约束：`Discount` 恒为单行。
> ❌ **汇总区若出现码值或活动名** → bug。同条约束：汇总区不透传活动名与码值。

---

### Case 7 · 同一行两码竞争（PRD 场景 14 ⚠️ 高危）

**启用**：X（$120）+ Z（$60）
**购物车**：仅 A(Gucci) $300

**7a · 先优后劣**

| 步骤 | 预期 |
|---|---|
| Apply `CODEX` | 生效，Discount $120，chip 显示 CODEX |
| 再 Apply `CODEZ` | 校验通过 → 临时加入 → 整单重算 → **CODEZ 无减免 → 回滚不加入集合** |
| 最终 chip | **只有 CODEX** |
| 最终 Discount | **$120** |
| 提示 | 出行内错误提示（§2.6.4 第 9 条） |

**7b · 先劣后优**

| 步骤 | 预期 |
|---|---|
| Apply `CODEZ` | 生效，Discount $60 |
| 再 Apply `CODEX` | CODEX 更优 → **CODEZ 的 chip 消失**，CODEX 生效 |
| 最终 Discount | **$120** |

> 关键：码能否留下由**整单求解结果**决定，**不是先到先得**。

---

### Case 8 · 码挤掉自动折扣（PRD 场景 10 ⚠️ 界面反直觉）

**启用**：P2（auto $80）+ X（code $120）
**购物车**：仅 A(Gucci) $300

| 阶段 | Subtotal | Discount | Total（不含运费税费） |
|---|---|---|---|
| 未输码 | **$220** | $0 | $220 |
| Apply `CODEX` 后 | **$300** | **$120** | **$180** |

| 检查项 | 预期 |
|---|---|
| 码是否取代自动折扣 | ✅ $120 > $80，码胜出 |
| **Subtotal 变化方向** | **从 $220 涨回 $300** ← 这是对的，不是 bug |
| Total 变化 | $220 → $180，确实更便宜 |

> 原理：自动折扣没生效了，所以不再体现在 Subtotal 里；这笔钱转由 Discount 行承担。
> 移除 CODEX 后应回到 Subtotal $220 / Discount $0。

---

### Case 9 · 码带门槛需凑单（PRD 场景 11 ⚠️ 结果反直觉）

**启用**：S（`SAVE100`，满 $500 减 $100）
**购物车**：A $300 + B $300 = $600
**操作**：Apply `SAVE100`

| 检查项 | 预期 |
|---|---|
| 门槛判定 | ✅ 实际使用行 A+B 合计 $600 ≥ $500 |
| **Discount** | **$200**（不是 $100） |
| 算式 | 每行 min($100, $300) = $100，两行合计 $200 |
| Total | $600 − $200 = **$400** |

> ⚠️ **减 $200 符合当前 PRD**，见开头第 ③ 条。共用口径 C 是单件口径，且 v1.2 移除了 `max_item_count`，PRD 原文承认 fixed 类无件数上限。
> **但请确认这是不是业务想要的**——「满 500 减 100」在买家看来应该是整单减 $100。见文末待确认①。

## 四、P2 边界用例

### Case 10 · 适用用户不符（PRD 场景 9）

**启用**：P5（新客专享 85 折）
**账号**：非新客（无「新客」标签）
**购物车**：A $300

| 检查项 | 预期 |
|---|---|
| P5 是否生效 | ❌ 候选阶段即剔除 |
| A 行到手价 | $300，无划线价无 Save |
| 商详页对比 | ⚠️ **商详页会显示 85 折到手价 $255**——§2.8.2「本场景不判适用用户」。这是设计如此，不是 bug |

---

### Case 11 · 购物车与 checkout 金额不一致（设计如此）

**启用**：P1，总量限次 = 1，且已核销 1 次
**购物车**：A $300 + B $300

| 页面 | 预期 | 依据 |
|---|---|---|
| 购物车 | **显示减 $120**，Subtotal $480 | §2.8.3 第 1 步注：购物车**不判限次** |
| 进入 checkout | **P1 被剔除**，恢复 $600 | checkout 全部执行 |

> ⚠️ 这是 PRD 明确的设计——购物车不判限次。买家会看到"进结算页价格变贵了"。
> **测的是"是否按 PRD 表现"，不是"体验好不好"。** 体验问题另记（文末待确认②）。

---

### Case 12 · 平局可复现（§2.8.3 平局规则·硬性）

**构造**：两条 Gucci 直减 $80 的活动同时启用（P2 + P2'）
**购物车**：A(Gucci) $300

| 检查项 | 预期 |
|---|---|
| 减免金额 | $80（只生效一条） |
| **可复现性** | **连续刷新 5 次，生效的活动始终是同一条** ← 核心验证点 |

> PRD 硬性要求：同样输入永远得到同样输出，**不得随机、不得依赖查询顺序**（§2.8.5 可重放可复算）。
> 具体哪条胜出由技术方案定，验收只判「是否稳定」。

## 五、⚠️ 一个口径冲突：购物车的 `Discount` 行本次不判定

PRD v2.3 里两处规则直接打架，**测出什么结果都能找到依据，无法判对错**：

| 出处 | 原文口径 |
|---|---|
| **§2.5 购物车** | 满额/满件门槛「…**达门槛才计入 `Discount`**(PC)/ 吸底栏券徽章(移动端)」→ Discount 装的是**自动折扣减免** |
| **§2.8.4 汇总口径** | `Discount` = 「**优惠码带来的减免合计**」，且「自动折扣的减免**已经体现在 Subtotal 里，不再单列**」 |

而 §2.5 末尾又明确「**购物车不提供输码入口**，checkout 是优惠码的唯一输入位」。

**两条一起推：购物车的 Discount 按 §2.8.4 应恒为 $0，按 §2.5 应等于自动折扣减免。**

> 这条冲突 2026-07-28 就记进了 `待优化清单.md`（第 11 行 · 冲突②），**v2.3 未修复**。
> **建议：Case 1 / 2 / 3 / 5 只验商品行价格与 Subtotal，购物车 Discount 行留空不判**，等拍板后补测。
> checkout 的 Discount 行口径清晰（Case 6/7/8/9），正常判定。

## 七、验收前需产品确认的两件事

**① Case 9 的 fixed 按件放大，是否可接受？**
「满 $500 减 $100」在 2 件商品上减 $200、3 件减 $300。当前 PRD 明确承认（v1.2 移除 `max_item_count`），靠 §2.2.3 试算拦截 + §2.3 双阈值监控 + §2.8.4 实付兜底三道兜底。
**但买家心智里「满 500 减 100」就是整单减 100**，实际减更多属于超发。要不要恢复件数上限，建议拍一下。

**② Case 11 的购物车 / checkout 金额跳变，要不要处理？**
购物车不判限次是为了性能（不用对每个购物车都查核销数），但代价是买家在结算页看到涨价。可考虑在购物车加一句"最终优惠以结算页为准"。
