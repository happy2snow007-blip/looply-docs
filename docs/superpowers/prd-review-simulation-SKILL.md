# PRD 评审模拟

PRD 写完后、正式评审之前，模拟开发/测试/设计三个角色提问，提前发现**业务逻辑层面**的问题。

核心原则：

1. 评审只关注"PRD 是否把业务规则讲清楚了"，不讨论技术怎么实现。
2. 对需求本身做**逻辑验证**：合理客观地分析业务规则是否存在漏洞、逻辑错误或规则缺失，并与原型实现进行对照。不凭主观臆断，每个问题都要能说清"哪条规则 + 什么场景 = 什么矛盾/缺失"。
3. 发现问题**必须问用户**，不自作主张决定处理方式或擅自修改。

## 触发时机

- PRD 写完想检查质量
- 用户说"帮我评审一下PRD"、"模拟评审"、"PRD review"

## 前置条件

PRD 必须先通过 prd-writing skill 的"第四步：自检"。本 skill 是模拟他人视角评审，不替代作者自检。

开始前确认：
1. 用户提供 PRD 文件路径
2. 确认 PRD 已通过自检

## 输出位置

`~/Desktop/海外业务/{模块名}/评审记录/模拟评审-{日期}.md`

## 执行流程

### Step 1：读取上下文

通过目录约定自动定位模块根目录 `~/Desktop/海外业务/{模块名}/`，读取以下制品：

| 制品 | 子目录 | 用途 |
|------|--------|------|
| PRD | `PRD/` | 评审主体 |
| 原型 | `原型/` | 与 PRD 功能描述交叉对照 |
| ER 图 | `实体关系图/` | 与 PRD 数据定义交叉对照 |
| 设计稿 | `UI/` | 与 PRD 文案/交互交叉对照 |
| 调研报告 | `调研/` | 确认 PRD 覆盖了调研结论 |

找不到某个制品不阻塞评审，但要在评审记录中注明"未读取 XX 制品"。

**跨模块依赖检查（硬性）**：读完 PRD 后，提取所有被引用但未在当前模块内定义的外部概念（如 Market、库存、质检等）。对每个概念：
1. 先 `ls ~/Desktop/海外业务/` 了解全部模块布局
2. 到对应模块目录确认设计状态（已交付/设计中/未开始）
3. 已有设计 → 检查 PRD"依赖与风险"是否声明了依赖，未声明则标为 P1（缺依赖声明），不标为 P0（概念未定义）
4. 未有设计 → 标为真正的 P0（概念未定义）

### Step 2：跨制品一致性检查

在逐条评审之前，先做一轮交叉比对，找出制品间的矛盾：

- **PRD vs ER 图**：字段定义是否一致（枚举值、状态数量、字段有无）
- **PRD vs 原型（字段级，硬性）**：必须打开原型文件，逐模块做字段级对照，不能只看"有没有这个模块"。具体执行方法：
  1. **逐模块提取**：对 PRD 每个页面型功能，提取其定义的字段清单（列表列、筛选项、表单字段、弹窗内容、枚举值）
  2. **原型实际读取**：用 grep 或 Read 读取原型对应模块的实际代码，提取 `columns`、`filters`、`FormRow`、`Select options`、`modalConfig` 等渲染内容
  3. **逐项对照产出差异表**：
     ```
     | 模块 | 页面 | 字段/列 | PRD | 原型 | 差异类型 |
     |------|------|---------|-----|------|----------|
     | 商品 | 列表 | 采购价列 | ✅ 有 | ❌ 无 | PRD有原型无 |
     | 商品 | 筛选 | 已停售选项 | ✅ 有 | ❌ 无 | PRD有原型无 |
     ```
  4. **枚举值逐值比对**：PRD 中每个枚举定义（状态、类型、等级等）的每个值，与原型下拉选项的 `options` 数组逐值对照。值不一致或数量不同均为差异
  5. **数据承载结构比对（硬性）**：同一业务概念在 PRD 和原型中的数据录入方式是否一致。检查维度：
     - 录入形式：PRD 描述的是「动态表格（每行一条记录）」还是「固定字段（若干文本框）」？原型实际用的是哪种？
     - 控件类型：PRD 写的是「下拉选择」，原型是否真的用了 Select？还是改成了 TextArea？
     - 字段名对应：PRD 的字段名列表与原型的 FormRow label 是否逐个匹配（不能只看"两边都有这个区域"就跳过）
     - 反例：PRD 描述质检明细为"按检查类型分组的内嵌表格（质检项×结果×备注）"，原型实际是 4 个固定 TextArea（成色描述/外观描述/补充描述/配件信息）——概念都叫"质检"，但数据模型完全不同，属于 P0 差异
  6. 差异直接作为评审问题输出（PRD 与原型矛盾通常是 P0 或 P1）
  7. **反例警示**：只检查"PRD 每个模块是否关联了原型页面"不算完成此步骤——这只是 UI 关联完整性检查（prd-writing 自检第 7 条），不是字段级对照
- **PRD vs 设计稿**：文案措辞是否一致
- **PRD vs 调研报告**：调研结论中的 MVP 必做项是否都在 PRD 中落地

矛盾直接作为评审问题输出，通常是 P0 或 P1。

### Step 3：三角色评审

分别从三个角色视角提问。每个问题必须用具体业务场景说明（"当用户做 XX 时，PRD 没有定义 YY 会怎样"），不能只说"描述不清"。

**开发视角** — 关注"能不能按 PRD 把功能做出来"：
- 业务规则完整性：操作的前置条件、后置影响、边界 case 是否都有定义
- 状态流转：每个状态变更的触发条件和影响范围是否明确
- 数据来源：页面上每个字段的数据从哪来、用户输入还是系统生成
- 关联影响：A 实体变更后对已关联的 B 实体有什么影响

**测试视角** — 关注"能不能写出明确的测试用例"：
- 验收标准：每个功能的"做完"标准是否可判定（不是"体验好"这种模糊描述）
- 异常流程：错误提示文案、重试逻辑、降级行为是否定义
- 数值规格：字段的取值范围、长度限制、格式要求、是否允许重复

**设计视角** — 关注"UI 和 PRD 是否对齐"：
- UI 关联完整性：每个功能模块是否都有 PC 端和 APP 端设计稿引用
- 交互完整性：页面流转、加载态、空态、错误态是否有描述
- 文案一致性：PRD 文案和设计稿/原型文案是否一致

#### 评审边界：什么不该提

PRD 定义"要什么效果"，技术定义"怎么实现"。以下属于技术选型，不在评审范围内：

| 越界问题示例 | 为什么不该提 |
|-------------|-------------|
| "建议用乐观锁/悲观锁" | 并发控制方案是技术选型 |
| "前端刷新用定时器还是本地计算" | 渲染策略是技术选型 |
| "数据同步频率建议每小时一次" | 同步调度是技术选型 |
| "300 条数据 DOM 更新有性能问题" | 性能优化是技术选型 |
| "初始数据是预置还是首次部署导入" | 部署策略是技术选型 |
| "搜索用前端过滤还是后端查询" | 查询实现是技术选型 |

**判断方法**：如果问题的答案是"用方案 A 还是方案 B 实现"，那就是技术选型，不提。如果问题是"用户做了 X 之后会发生什么，PRD 没说"，那就是业务规则缺失，要提。

### Step 4：严重程度分级

每个问题按以下标准分级：

| 等级 | 判断标准 | 典型场景 |
|------|---------|---------|
| **P0** | 规则缺失导致开发无法继续，或制品间存在矛盾 | 状态枚举不一致、关联影响未定义、PRD 与 ER 图矛盾 |
| **P1** | 规则不完整但可以猜测意图，或异常流程缺失 | 边界 case 未覆盖、操作前置校验缺失、多端行为未对齐 |
| **P2** | 描述可以更精确，当前不阻塞但容易产生歧义 | 字段取值范围未说明、数字列数标注有误、统计口径未明确 |
| **P3** | 锦上添花的建议 | 文案优化、展示形式建议 |

### Step 6：用户逐条回应

1. 用户逐条确认处理方式（✅ 改 / ⏭️ 不改 / 💬 待讨论）
2. 需要改的，协助修改 PRD 并同步其他制品
3. 更新处理汇总表
4. 更新 PRD 版本号

## 自检清单

评审完成后逐项检查：

1. 三个角色都有提问（如某个角色确实没发现问题，说明原因）
2. 每个问题都标注了 PRD 中的具体位置
3. 每个问题都用具体业务场景描述，不是空泛的"描述不清"
4. 每个问题都有建议的解决方向
5. 没有越界提技术实现方案（用"判断方法"自查一遍）
6. 跨制品一致性检查已完成（或注明缺失的制品）
7. 评审记录存放在正确目录

## 反模式

1. **跳过前置条件**：必须确认 PRD 已通过自检
2. **只挑小毛病**：重点关注 P0/P1 级别的结构性问题，P3 不要超过总数的 1/3
3. **不读上下文**：必须读取所有可用制品，不能只看 PRD 文本
4. **问题没有位置**：每个问题必须指向 PRD 的具体章节
5. **自作主张**：发现问题必须问用户，不能擅自决定处理方式
6. **越界提技术方案**：不提技术实现可行性/方案选型类问题，这些由开发自行决定
7. **凭空造问题**：如果某个等级确实没有问题，留空并说明原因，不要为了凑数硬找
