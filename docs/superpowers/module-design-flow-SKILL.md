# 模块设计流程编排（Module Design Flow）

把一个新模块从「决策拍板」推进到「交付上传文档中心」的标准门禁流程。这是**编排层**——每个阶段调用已有的专业 skill，本 skill 只管：关卡推进、决策留痕、全链路同步、方法论约束。

## 适用与不适用

- **适用**：模块的前期调研已完成（或用户明确跳过），现在要把它做成 ER / 原型 / PRD 并交付开发。
- **不适用**：竞品对标、合规扫描、技术选型等前期调研 → 用 `module-kickoff`。

## 五条工作方法（贯穿全程，硬性）

这些不是某一阶段的动作，是每一步都要遵守的原则：

1. **决策留痕**：每个关键决策编号入册（A1/A2… 业务决策，D1/D2… 数据/设计决策），同步到「概览决策表 + 主线计划 + PRD 修订记录 + 飞书」。任何口径变更都要能追溯到"哪条决策、哪天、为什么"。
2. **边界问、常规做**：触及已定范围/边界的变更（如把某能力从 V2 提前到 V1、改动已拍板的架构）→ 停下用 AskUserQuestion 让用户拍板，不自作主张扩范围。功能内增强、明确 bug、口径修正 → 直接做并说明。判断标准：*这个决定的答案是不是用户的、会不会改变已承诺的范围*。
3. **一处改动、全链路同步**：任何口径变更都不是只改一个文件。固定同步链路 **ER → 原型 → PRD → 概览/主线 → 修订记录 →（飞书，若用飞书协作）**，每步配一致性检查（grep 查残留旧版本引用、旧口径）。这是多轮迭代后制品仍自洽的基本盘。**跨模块依赖也在此链路内**：若本模块依赖上游模块（如售后依赖订单/支付/商品/物流），或本模块的口径变更会波及上游模块的接口/字段，则同步范围要延伸到被依赖模块——依赖项和需对方配合的改动登记成清单；凡需上游模块配合改动的，按方法 2 当作"边界变更"升级给用户拍板，不擅自替上游模块定接口。
4. **挖根因，不打补丁**：同一问题失败 2 次就停下换思路。表象修复后必问"为什么会发生、以后会不会再犯"，做到「症状 + 机制 + 防复发」三层。防复发常意味着回头改 skill / 脚本 / 模板。
5. **subagent 扇出核查 + 验证优先**：覆盖核查、模拟评审、跨制品比对派独立 subagent（并行省时 + 非作者视角避盲区），主上下文留给决策和实现。每次改动都跑验证（原型自检脚本、语法校验、结构平衡、grep 一致性），声称事实前先核实（如"某模块未注册"必先 grep 确认），不臆断。

## 目录约定

模块根目录 `~/Desktop/海外业务/{模块名}/`，子目录：`PRD/ 原型/ 实体关系图/ 产品架构图/ 系统流程图/ UI/ 调研/ 评审记录/`。

## 门禁流程

每个关卡「过了才进下一关」。进入每关先声明当前在哪一关，出关时明确"通过 / 有问题回炉"。

### G1 · 方案收口（自顶向下铺功能全景 + 决策拍板）

**目标**：从业务架构自顶向下把功能全景铺开、V1 边界在架构层面切清楚、关键决策全部拍板，产出《业务架构与功能概览》作为唯一载体。**过了这关才算"方案收口"，才能进建模。**

**核心方法（硬性，最易踩坑处）**：G1 **不能只收集之前零散聊出来的问题**（自底向上）。必须**自顶向下**：从业务域架构出发，重新梳理"这个系统到底需要哪些产品功能"，把能力全景铺开，再在架构层面切 V1/V2 边界。零散讨论出来的决策项往往只是**细节级**，自顶向下铺开才会暴露**架构级决策**（决定系统骨架，通常是零散聊天完全漏掉的）。经验：某次自底向上只收了 7 条细节决策，自顶向下重铺后又发现 5 条架构级决策，其中 3 条此前完全没意识到。

**执行步骤**：

0. **确认域边界输入就绪**：G1 自顶向下铺架构需要域边界作为输入（本域负责什么、与哪些上游模块耦合）。若前期调研/域边界不清（尤其强跨域模块，如售后耦合订单/支付/商品/物流），先临场与用户厘清边界，或回 `module-kickoff` 补；不要在边界悬空时硬铺架构。
1. **铺能力全景**：调用 **product-architecture-diagram** skill 走域边界/功能梳理规范流程。自顶向下列出：域负责什么/不负责什么、能力全景、用户层（谁用）、外围系统（运行时依赖）。**能力全景的分组维度按本模块自身业务重新归纳，不要套用其他模块的分组**（营销是"怎么减/谁能享/最多减多少/实际用多少/数据供给/触达"，售后则可能是"谁能退/退什么/退多少/退到哪/纠纷判定/与交易链路的回滚"——每个模块的机制分组不同）。
2. **切 V1/V2 边界**：每个能力标 ✅V1 / V2 / ⬦待拍板。边界在架构层面切清楚，不是功能清单堆砌。
3. **识别决策项**：铺开过程中把需要用户拍板的分成两级——**架构级 A1/A2…**（决定骨架，优先）+ **细节级 D1/D2…**（沿用/局部选择）。架构级优先于细节级。
4. **逐项拍板**：每项给推荐方案 + "为什么之前漏了/为什么这样选"，用 AskUserQuestion 让用户逐项拍板（方法 2）。
5. **落文档**：全部写入《{模块}业务架构与功能概览》——含四块：① 域边界定义 ② 能力全景（标 V1/V2）③ 决策清单全集（A 级 + D 级，标 ✅ 已拍板）④ 推进状态。同步主线计划的决策记录（方法 1）。
6. **产出架构图**：概览确认后，用 product-architecture-diagram 产出架构图 SVG。

**出关标准**：能力全景铺全且 V1 边界在架构层切清楚；所有 A 级 + D 级决策状态"已拍板"、无 pending；《业务架构与功能概览》四块齐全；架构图 SVG 已出。

产出：`{模块}业务架构与功能概览-v{版本}.md`（G1 唯一载体，版本号起点按项目惯例）、产品架构图 SVG、主线计划文件。

### G2 · 数据模型（ER）

**目标**：ER 图落地，字段级可开发。

1. 调用 **er-diagram-generation** skill 生成/修改 ER 图 SVG（含结构化 metadata）。
2. 如需产品架构图/域边界，调用 **product-architecture-diagram**；需系统流程图调用 **swimlane-diagram-generation**。
3. ER 与 G1 决策交叉核对（每条决策在 ER 有对应落点）。
4. **出关标准**：ER 通过 skill 自检；与概览决策一致。

### G3 · 原型与 UI（复测关）

**目标**：本模块所需的原型/UI 成型，用户点测通过。

**先判断本模块的原型形态，再决定调哪个 skill、以谁为主**（硬性，不要默认"运营端后台为主"）。形态由 G1 的能力全景和用户层决定，常见几类：
- **运营端主导**（如营销配活动）：主体是后台管理台 → **antd-admin-prototype**。
- **C 端流程主导**（如售后发起退货/退款申请）：主体是 C 端用户流程 → C 端 UI skill（frontend-design / ui-design-workflow），运营端只是处理台/工单台，作为辅。
- **双端并重**（如售后：C 端申请 + 运营端工单处理）：两端都要，按业务重心排主次，可能两个 skill 都调。
- **纯 API / 数据服务 / 看板**：可能没有传统原型，产出接口契约或看板原型，antd-admin 不一定适用。

步骤：
1. 依形态选 skill 产出主体原型/UI（调 antd-admin-prototype 的走其自检脚本，Pass 才算数）。
2. 产出次要端的原型/UI（若有）。
3. 交用户点测复测。用户反馈按方法 2 分流：边界变更先问，常规直接改。
4. 每次改动走方法 3 全链路同步 + 一致性 grep。
5. **出关标准**：用户明确"G3 通过"；涉及 antd 原型的自检全绿；版本号全链路对齐。

### G4 · PRD Review

**目标**：PRD 完整、自洽、可交付评审。

1. 调用 **prd-writing** 撰写/修订 PRD，先过其自检。
2. 调用 **prd-review-simulation** 派 subagent 做多角色模拟评审（角色设定由该 skill 决定，方法 5），产出分级问题。
3. P0/P1 阻塞项修复闭环（全链路同步）；P2/P3 非阻塞项记入待办清单/wiki，不阻塞出关。
4. 导入飞书供用户正式 review（评论或改正文双通道核对）。
5. **出关标准**：用户 review 通过；P0/P1 已闭环。

### P5 · 交付上传

**目标**：制品打包 + 上传文档中心 + 收档。

1. **一致性终检**：全模块 grep 残留旧版本引用（旧原型/ER 版本号）、各文件版本号统一到最新，发现即修（方法 3）。
2. 调用 **sync-docs** skill：新模块先注册（MODULES + **sidebar_group** + index.html section，注意 sync.py 的导航自动注册只对它自插入的 section 生效——见 sync-docs skill 说明），打交付包，同步 git push。
3. 需要交付 diff 摘要时调用 **req-versioning**。
4. 更新主线计划推进状态 + 记忆 Module Status。
5. 遇 git 冲突/工具报错按方法 4 处理：看清根因再动手，不盲目重试。
6. **出关标准**：文档中心页面可见该模块（导航 + 内容块都在）；git 工作区干净；交付包可下载。

## 关卡状态速览

进入 skill 时先判断用户当前在哪一关（看已有哪些制品、上一步做到哪），从那一关接续，不必每次从 G1 开始。可用一句话向用户确认："当前在 G3（原型复测），继续？"

## 反模式（对照五条方法）

1. **G1 只收集零散聊出来的决策项，不自顶向下从业务架构铺功能全景** → 会漏掉架构级决策（决定骨架的那几条），方案没真正收口就往下走，后面 ER/原型/PRD 全部返工。这是 G1 最致命的坑。
2. 口径变更只改一个文件不同步全链路 → 违反方法 3，多轮后制品必打架。
3. 表象修好就收工、不问为什么 → 违反方法 4，同类坑反复踩。
4. 触及边界的变更自己拍了 → 违反方法 2，可能擅自扩范围。
5. 声称"某模块未注册/某文件已改"不核实 → 违反方法 5，凭记忆出错。
6. G3 默认"运营端后台为主"、不先判断本模块原型形态 → C 端主导或纯服务型模块会做错主体。
7. 强跨域模块只在本模块内做同步、不延伸到被依赖的上游模块 → 依赖漏接、接口对不齐。
8. 把营销的能力分组/版本号/三角色等某个模块的具体设定当通用规则照抄 → 违反编排层通用性。
9. 把下游 skill 的内容抄进本 skill → 违反编排层定位，维护两处。
10. 门没过就往下走 → 违反门禁，问题带到下游放大。
