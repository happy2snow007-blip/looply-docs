## 一组 · 我的改动没做全（3 条）

这三条不是 PRD 写错，是**今晚多轮改动的收尾遗漏**，性质上等同"改一处漏一处"。

### A1【P0】判责后能否改金额 —— PRD 内部两条规则互相取消
- **位置**：§2.5.9 异常处理表第 2 行 + 流程图 V2.2 段②注 ↔ §2.7.1 / §2.7.2 / §2.7.12
- **问题**：删「修改判责」时漏扫了 §2.5.9 与流程图段②注，那里仍写着「协商改方案也走线下，**运营可调退款金额与退货扣减**，调整结果 C 端可见」。开发在流程图里读到这句就会做出"已判责单可编辑金额"，而 §2.7.1 明写钱在提交那一刻已经打出去——改金额只会造出「单据金额 ≠ 已打款金额」的对账死账。
- **建议**：两处改为「协商结果只能通过线下退补款处理，系统内不提供判责后的金额修改入口」，并反向引用 §2.7.1。

### A2【P0】流程图段⑩仍写「关闭原因说明（必填）」，与同一张图的段③打架
- **位置**：流程图 V2.2 段⑩节点与注 ↔ 同图段③注 ↔ PRD §2.9.3
- **问题**：改「关闭说明选填」时**只改了段③、漏了段⑩**。现在同一张图自相矛盾：段③说"没有需要运营选填的原因字段、别做成必填"，段⑩主线节点却写着必填。开发照主线做就会做出一个必填框，而该文本按 `close_note` 定义会**原样进关闭邮件发给买家**。
- **建议**：段⑩节点改为「填写关闭说明（选填）· 勾选是否邮件告知买家（默认勾选）后二次确认」；注中「关闭原因必填」改为「关闭原因由系统按来源自动落值，共 3 个取值」。

### A3【P0】「复制」按钮：PRD 自相矛盾 + 指向一个不存在的备案条目
- **位置**：§1.5 全局页面流转 ↔ §2.2.1 操作列行为；原型 `PolicyListPage`
- **问题**：三点连环 —— ① §1.5 把「预填源政策内容」写成需求，§2.2.1 又把「不预填」当既成事实记下来；② 所指的「交付说明产物矛盾第 3 条」**不存在**（拆分 §7.4 时未检查引用，该文件第 3 条是"逾期未交寄自动关单"，也没有名为"交付说明"的文件）；③ 于是这个差异**无任何承载**，既不是需求也不在待办里。运营点「复制」得到一张空表单。
- **建议**：拍板复制即预填（否则该按钮无存在价值）→ §2.2.1 去掉括号说明、原型改为带记录跳转；删掉伪引用。

## 二组 · 规则互斥，开发必须选一个（4 条）

### B1【P0】判责结论下拉取值范围，三处互斥、原型取了第四种
- **位置**：§2.1.3（3）表单项 ↔ §2.7.4 ↔ §2.7.6 分支 B；原型 `AdjudicateModal`
- **问题**：§2.1.3 写「7 个取值」不分状态；§2.7.4 写「到仓分支实际可选 6 条」；§2.7.6 写「退货在途固定为退回途中丢件」；**原型两个入口一律渲染全部 7 条、不做过滤**。后果两条：货已到仓时能选「退回途中丢件」（触发丢件邮件 + 默认平台责任）；货没到仓时能选「与申请一致」——**在没见到货的情况下出具验货结论并立即打款**。
- **建议**：在 §2.7.4 下补「入口状态 × 可选结论」矩阵（待判责 6 条 / 退货在途锁定 1 条），§2.1.3 与 §2.7.6 引用该表；§2.7.10 校验表补两条；原型按 `status` 过滤。

### B2【P0】退货扣减 / 最终退款金额：「必填」与「留空按 0 不阻断」四处互斥
- **位置**：§2.1.3（3）表单项「必填=是」+ §2.7.3「是（可填 0）」 ↔ §2.7.8 + §2.7.10 校验 6「未填按 0 计，只提示不阻断」；原型 `required` 只画星号、`blocked` 不含金额
- **问题**：测试写「留空点提交」这条用例判不了预期是**拦截**还是**按 0 退款**——这是金额用例，差别是"退 $0 还是退全额"。若开发按"必填"加拦截，平台责任要全额退（扣减本该留空/填 0）时提交不了，运营只能填 0 绕过，而 PRD 特意设计成"留空 = 按 0 + 橙色提示让运营确认扣减意图"。
- **建议**：统一为「非必填，留空按 0.00 计并出提示、不阻断」，改掉两处必填标注，星号只作视觉提示。

### B3【P0】超期特批建单：「不可选」与「可选中+报错」两种实现并存
- **位置**：§2.1.3（6）表单项「已有进行中或已完成售后单的商品行**不可选**」 ↔ 同节校验「**选中**任一被拦商品行时出错误提示条、提交置灰」 ↔ §2.4.12；原型走后者
- **问题**：同一节内两种互斥实现。运营体验完全不同：前者点不动、看不到为什么；后者能选进去、被红条告知原因。
- **建议**：定为「可选中 + 错误提示条 + 提交置灰」（信息更全，与 §2.4.12 一致），改 §2.1.3 表单项措辞。

### B4【P0】关闭说明的写值范围不一致 → **内部定性可能进入对买家可见字段**
- **位置**：§2.1.2 右栏出现条件「仅已关闭」 ↔ §2.9.1 表「买家撤销=否、拒退关单=否」+ ER `close_note`「仅运营关闭场景写值」；原型对三种来源**一律渲染**
- **问题**：`close_note` 的定义是**对买家可见、C 端进度页展示**。原型里拒退单的该字段内容是「验货结论『退回件与订单不符』，经线下人工核实后选择出口『不退并关闭』…」。开发照 §2.1.2 实现「已关闭即出关闭说明」，**买家在 C 端会直接读到这条内部定性指控**——而 §2.7.9 与第 5 封邮件反复强调拒退理由绝不外露。买家撤销单同理（原型填的是系统描述，不是运营手填的 close_note，两个概念被合成一个字段）。
- **建议**：§2.1.2 出现条件改为「仅已关闭 **且** 关闭来源 = 运营关闭」（与紧邻的「邮件告知买家」同口径）；原型把拒退单与撤销单的该字段拆成仅内部展示的系统描述，或置空。

## 三组 · 真空白，会出事故（5 条）

### C1【P0】支付域「受理失败」落哪个状态未定义，且与状态机进入条件矛盾
- **位置**：§2.4.1「退款中」行 ↔ §2.8.3 步骤 4 ↔ §2.7.12；退款执行状态枚举只有 4 值
- **问题**：两层。① 状态机写「退款中」的进入条件是"判责提交**并已成功调起**支付域退款"，而 §2.8.3 写"受理失败 → 单据停在退款中"——受理失败 = 没成功调起，两句不能同时成立；② 受理失败（还没产生退款单）取 4 个枚举里的哪一个没写。后果：若不算「退款失败」，重发入口不出现，而「退款中」又不开放关单 → **单据在系统内没有任何出口**，直接违背 §1.1 目标 2。且重发弹窗要展示「退款单〔号〕于〔时间〕回传失败」，受理失败时这两个值都不存在。
- **流程图口径**：V2.2 是**先置「退款中」再调接口**，与 §2.8.3 一致、与状态机相反。
- **建议**：「退款中」进入条件改为"判责提交成功"（与调用结果解耦）；明确受理失败与回调失败**同落「退款失败」**、共用同一个重发出口；补重发弹窗无退款单号时的展示降级。

### C2【P0】多张售后单共用一个退货运单号：登记 / 推进 / 触达 / 地址 四处口径全缺
- **位置**：§2.6.4 步骤 3 · §2.4.1 待寄回与退货在途的进入条件 · §2.10.1 第 3 封 · §三.1
- **问题**：这是 V1 主场景（一单一行 + C 端可一次勾多件）。PRD 只有一句"多件同包裹寄回时共用一个运单号"，四件事没定义：
  ① **怎么登记** —— 逐单各登记一次，还是一次登记批量落到 N 张单？（回填弹窗只面向单张，无批量入口）
  ② **一条「已送达」轨迹推进哪几张单** —— 全部关联单一起推，还是只推登记过的？若只有 2 张登记、第 3 张停在待寄回怎么办？
  ③ **邮件发几封** —— 按触发时机会发 N 封内容相同的，而该封正文恰恰写着 "put them in the same box and use this tracking number for all of them"
  ④ **地址冲突** —— 各单退货地址取各自政策快照，N 张单命中不同政策就会拿到不同地址，买家收到两个地址、一个箱子
- **建议**：在 §2.6 补一节「多单共用运单」，写死这四件事的业务结果。

### C3【P0】丢件的「必填认定依据」在原型里没有任何拦截 → 无据退款
- **位置**：§2.7.10 校验 5「结论=退回途中丢件时判责说明**必填、阻断提交**」 ↔ §2.1.3 与 §2.7.3 表却标「必填=否」、§2.1.3 校验表无此项；原型 `blocked` 不含判责说明、无红星
- **问题**：运营选「退回途中丢件」、说明留空，提交按钮照样可点，退款照打。丢件是唯一「货没到仓也退钱」的出口，认定依据（承运商查件案号、轨迹停滞天数）是事后索赔与对账的**唯一凭据**，缺了平台拿不出举证。
- **建议**：§2.1.3 判责说明必填列改为「否（**结论=退回途中丢件时必填**）」并在该弹窗校验表补一行；原型 `blocked` 补该判据 + 红星。

### C4【P0】流程图段①缺「该商品行已退成钱」这条建单拦截 → **同一商品可被退两次**
- **位置**：流程图段①（只有 已发货 / 无进行中单 / 已签收 / 在时效内 四个判据）↔ PRD §2.4.5 拦截②、§2.4.9 校验 3、ER
- **问题**：一件商品已完成退款（终态已完成），互斥规则不拦终态单。开发照流程图实现只做互斥校验，第二张单建出来、审核、判责、**再退一次钱**。PRD §2.4.5 专门写了「条件②不能靠条件①推导」，恰恰说明这是最容易漏的一条 —— 而唯一画流程的那张图上没有它。
- **建议**：段① 在「无进行中的售后单?」之后补 D 节点「该商品行未退成过钱?」，否分支「已退成钱 → 不可申请」。

### C5【P0】退款反复失败时单据没有终态出口 → 死单
- **位置**：§2.4.1「退款中」行 · §2.8.5 · §2.9.3 开放状态表 ↔ §1.1 目标 2
- **问题**：「退款中」不开放运营关闭，出口只有"回调成功"，运营唯一动作是原额重发。买家原支付账户已注销 / 渠道永久拒绝原路退回时，这张单**永远停在退款中** → 互斥占用永不释放 → 该商品行永远显示"售后中"、买家也无法重新申请。与 §1.1 目标 2「每个非终态都有出口」正面冲突。
- **建议**：给退款中补一个人工终结出口（如"线下已另行赔付 → 运营标记结案"），或明确接受该敞口并写进 §三风险 + 待优化清单。

## 五组 · 评审确认写得好的部分（不用改）

四个视角**共同点名**的：

1. **状态机 §2.4.1** —— 7 状态逐个填齐进入/退出/可做操作，无"写不出进入条件"的值；三条反向约束（驳回是回环 / 退款失败不换状态 / 拒退不新增状态）写死
2. **两份快照机制 §2.4.10 + §2.5.6** —— 政策不刷新、原因码按新选的刷新，判据与不冻结的后果都写了
3. **白名单分岔 §2.3 + §2.4.6** —— 4 条 code 写死、逐条不可删改停、禁止前缀与 LIKE 推断、只读本单快照不回查字典、"其他"为何不进白名单；并明确"原型 13 条是示例数据、不要硬编码"
4. **关闭三来源差异矩阵 §2.9.1** —— 六列全填；§2.9.3 的「关闭原因 vs 关闭说明」对照表把最容易做错的点堵死了
5. **建单拦截三条 §2.4.5** —— "条件②不能靠条件①推导"与"两个终态结论正好相反"两句消掉了最常见的实现错误
6. **互斥占用释放 §2.9.4** —— "实时聚合、不需显式反写、订单域没有这个字段别去找"
7. **对外输出安全边界成体系** —— 驳回原因 vs 审核意见、判责说明 vs 关闭说明、时间线剔除清单、邮件剔除清单，四处都写成"取数层切干净、不靠运营自律"
8. **并发的业务结果基本给全** —— 同商品行并发建单、审核与撤销撞车、重复发起退款、终态不可二次关闭，全是"只给结果、实现由技术方案定"的正确写法
9. **责任归属反向约束 §2.7.7 + 校验 3b** —— 把"责任=平台→自动置 0/只读"列为 ⛔ 不要实现，点名三个位置
10. **邮件 7 封 §2.10** —— 英文源文逐字、变量取数来源、变量为空时的行为、明确不发的 4 处及理由；**第 5 封专门声明"流程图上没画节点，开发不得因此跳过"，而流程图实测确实只画了 5 处固定邮件、注释却写 6 处——PRD 提前兜住了这个坑**

## 六组 · 评审同时发现的备案错误

《待确认与产物差异》§7.4 的「ER 侧两处待补」第 ② 条**已过时**：ER `责任判定时点` 末句已写「本期 liability_party 不驱动任何金额计算（退货扣减全手填），为纯留痕字段」。该条应划掉。
