## 一、概述

### 1.1 背景与目标

**背景。** looply 的逆向诉求此前统一挂在订单域：支付前取消、已付款未发货的退款，都由订单域的退款申请单处理。这套机制在"货还没出仓"这个前提下成立——平台随时可以撤单、原路退钱，两步结束。

**货一旦交给承运商，这个前提就不存在了。** 平台失去了对实物的控制，此后任何逆向诉求都不可能靠"取消 + 退款"解决，必然多出两个环节：

- **实物回流**——货要从买家手上寄回平台，中间有面单、运单、轨迹、丢件；
- **验货判定**——货回来之后要先看是什么货、什么状态，才能决定退多少钱。

而 looply 是**二手一物一件**，这两个环节的分量比新品平台重得多：退回来的**不一定还是发出去的那件**（调包），也**不一定还是发出去时的成色**（磨损、缺配件、途中破损）。新品平台可以"同款同价、验完入库、原封退款"，二手不行——每一单的退款金额都要在看到实物之后才定得下来。这是售后必须独立成域、而不是在订单域加一个退款类型的根本原因。

**目标。** 建成一条从买家提出、平台受理审核、货物回流、验货判定，到退款执行的完整闭环链路，覆盖**订单发货之后**的全部逆向诉求，并满足三件事：

1. **金额可解释**——每一笔退款的基准、扣减、最终金额都有留痕，扣款被买家质疑时能拿出举证；
2. **流程不卡死**——每个非终态都有出口，买家不响应时运营有手段把单据推进到终态并释放占用；
3. **口径可跨市场复用**——售后时效、退货服务费、退货地址按 market 独立配置，V1 同时支撑美国站与香港站。

**V1 范围一句话**：平台自行履约的全部商品（含红布林代发件出关后，本期主要货源）· 退货退款 · 一单一行 · 线下预付面单 + 接物流信息服务查轨迹 · 售后只记客观验货结果 · 美国站 + 香港站。

### 1.2 不做什么（明确边界）

| # | 不做的事 | 归属 / 理由 |
|---|---|---|
| 1 | 退款资金的实际执行 | 归**支付域**。售后域把金额定死后创建退款单，原路退回，本域只关心退款结果 |
| 2 | 商品处置决策与重新上架、商品描述/价格修改 | 归**商品域**。售后只提供客观验货结果，**不下发处置结论**——能否再售、是否降级、是否报废由商品域判断 |
| 3 | 库存数量增减 | 归**库存域**。本期退货只放在仓内、不做入库处理，故 V1 不触发任何库存事件 |
| 4 | 物流轨迹的采集与承运商对接 | 归**物流信息服务**。售后只注册退货运单、接收轨迹与异常通知 |
| 5 | 面单生成与打印 | **本期不做**。物流信息服务已明确面单生成不在其本期范围，售后同样不做 → V1 走线下预约 |
| 6 | 仓库现场作业（收货、拆包、拍照、验瑕疵） | **在线下当地仓完成**，结果回传在线表格。looply 系统不承接仓库作业流程，**不设仓库端账号**；系统边界从"运营核对表格后录入"开始 |
| 7 | 正向物流 | 归**订单域**。逆向包裹不动订单域的包裹数据，也不改发货状态——即使未来有维修，正向发货状态仍保持"已签收"不变 |
| 8 | 发货前的逆向（支付前取消、已付款未发货退款） | 归**订单域**，已交付 |
| 9 | **审核 SLA** | **本期不做**：不设时限配置、不做超时标记与筛选、不自动通过。运营靠工单列表自行盯办 |
| 10 | **交寄时限与超时关单** | **本期不做**：不算交寄截止时点、不发关单前提醒、不做揽收超时扫描。买家长期不寄货由**运营手动关单**代替 |
| 11 | 真伪复核（防调包） | **本期不做**：系统内无"真伪存疑"结论值、无挂起态。线下验货仍会看真伪，发现可疑只写内部判责说明，流程照常推进 |
| 12 | 信用卡拒付 / PayPal 争议接入 | **本期不做**：不做举证归集、不做拒付结果回写 |
| 13 | 税费退回 | **本期税费恒为 0**：订单侧税额字段值恒为 0，退税金额字段预留、不参与退款计算；已退税费累计校验的逻辑保留，待订单侧真正产生税额后启用 |
| 14 | **C 端页面** | **归 `售后列表详情` 独立需求**。本 PRD 不写 C 端页面的元素构成、布局、按钮文案、状态屏映射与取值规则 |

> ⚠️ **上表第 14 条有一个不能一刀切掉的例外：字段对买家的可见性仍由本 PRD 定义。** 它不是"页面显示什么"，而是"这个字段能不能出现在买家侧"——属安全边界。审核意见 / 判责说明即使 C 端不显示，被带进邮件或接口返回就已经泄露。本模块专门把「驳回原因」与「审核意见」拆成两个字段，就是为了解决这件事，PRD 必须写死。

### 1.3 用户角色

| 角色 | 在本模块里做什么 | 是否进系统 |
|---|---|---|
| **运营人员** | 售后工单台全流程：审核、登记退货运单、判责（验货结论 + 责任归属 + 退款金额一次提交）、异常出口决策、超期特批建单、手动关单；以及售后政策与售后原因码的配置 | ✅ 本模块运营后台 |
| **买家** | 在 C 端提交售后申请、上传举证、查看进度与退货运单号、待审核阶段撤销申请、被驳回后修改重提 | ✅ 进系统，但**页面与设计稿归 `售后列表详情` 独立需求**，本 PRD 只定义规则与字段可见性 |
| **线下仓验货人员** | 收货、拆包、拍照、验瑕疵，结果回传在线表格 | ❌ **不进系统**，不设账号。验货结论由**运营**核对表格后录入售后单 |

> 本期系统内只有**买家**与**运营**两类使用者，无仓库端角色。运营端**不做角色差异化权限**（见 §六）。

### 1.4 核心场景

| # | 场景 | 一句话说清 |
|---|---|---|
| 1 | **需寄回的正常退货** | 买家收到货后在时效内申请，选了一条不在未收到货码表里的原因码 → 系统按"商品→品类→市场"匹配政策并冻结政策与原因码快照、建单进待审核 → 运营审核通过 → 运营线下预约面单、把退货运单号与承运商登记到单上并注册轨迹订阅 → 邮件与 C 端双渠道告知买家 → 买家持号交寄，揽收轨迹到达即推进"退货在途" → 物流"已送达"自动推进"待判责" → 运营核对线下验货表格，一次提交验货结论 + 责任归属 + 退款金额 → 单据进"退款中"并调起支付域退款 → 退款成功回调后落"已完成" |
| 2 | **未收到货分支（不寄回、不验货）** | 买家申请时选中的原因码落在系统侧的**未收到货码表**（显示已送达但未收到 / 运输中丢件 / 包裹为空 / 投递失败退回）→ 审核通过后**跳过待寄回与退货在途**直接进"待判责"，不注册退货运单、不产生验货记录 → 运营在判责表单只录责任归属与退货扣减（预填为空）→ 提交即调起退款 → 已完成 |
| 3 | **验货异常拒退关单** | 到仓判责时验货结论为"退回件与订单不符"或"空包或无实物" → 单据停在待判责、不调用退款 → 运营线下人工核实（联系买家、核对包裹称重与监控、承运商核查）→ 三个出口二选一走退款（全额 / 部分），或选"不退并关闭" → 落"已关闭 · 拒退关单"，**不产生退款单、不经过退款中**，货走线下回寄，同时释放该商品行的互斥占用 |
| 4 | **退回途中丢件** | 物流信息服务推来追踪异常 → 运营线下向承运商核实并确认包裹丢失/灭失 → 在"退货在途"状态**不等到仓直接判责**（判责结论固定为"退回途中丢件"、必填认定依据、责任归属默认平台责任可改、退货扣减预填为空）→ 提交即调起退款 → 已完成 |
| 5 | **审核驳回与买家重新提交** | 运营驳回时填写「驳回原因」（对买家可见、原样进邮件）+「审核意见」（仅内部）→ 单据**状态仍为待审核、不落终态** → 固定发一封驳回邮件 → 买家改原因码 / 补举证 / 改说明后在**原单上**重提（单号不变、政策快照不刷新、原因码快照按新选中的刷新）→ 回到审核环节，可反复多轮 |
| 6 | **运营手动关单** | 买家中途放弃、长期不交寄、或被驳回后既不改也不撤销 → 运营在**待审核 / 待寄回 / 退货在途**三个状态手动关单，**填写关闭说明（选填，一律对买家可见）**、勾选是否邮件告知（默认勾选）、二次确认 → 落"已关闭 · 运营关闭"，全程留痕并释放互斥占用，买家仍在时效内可重新申请 |

### 1.6 术语说明

| 术语 | 定义 |
|---|---|
| **售后单** | 售后域的业务单据与聚合根，承载一次逆向诉求从提出到终结的全过程；不复用订单域的退款申请单，直接对接支付域退款单 |
| **一单一行** | 售后单的申请粒度：一个订单商品行一张售后单；一次退多件 = 多张售后单，各自独立走完整流程 |
| **退货服务费** | 售后政策里按 market 配置的一笔固定金额（美国站现行 $15），代表平台承担的退货成本；正逆向均不向买家单独收运费，系统内不存在"退货运费"这个独立概念 |
| **退货扣减** | 一张售后单**实际扣掉**的总额，是本域**唯一扣款科目**，由运营在判责时手填一个数——它已包含退货服务费与验货发现的成色下降/缺配件扣款，系统不单列验货扣减项。**与"退货服务费"不是同一个东西**：后者是政策里配的起填值，前者是这一单实扣的总额 |
| **判责** | 一个动作（不是一个阶段）：运营在同一张表单里一次提交验货结论 + 责任归属 + 退款金额，提交即定案并调起退款 |
| **验货结论** | 判责表单里的单选结论，描述退回件的客观状态；只记客观结果，不含处置决策 |
| **责任归属** | 这一单由谁承担，二分类：平台责任 / 买家责任。统一在判责环节判定，本期为纯留痕结论、不驱动任何金额计算 |
| **政策快照** | 建单时对**命中的整条售后政策**留的一份存档，锁定当时的时效、服务费、退货地址等口径；驳回后重新提交**不刷新** |
| **原因码快照** | 建单时对**买家选中的整条原因码**留的一份存档，流程分岔一律读这份快照而非字典当前值；驳回后重新提交**按买家新选中的那条刷新** |
| **未收到货码表** | 系统侧维护的一份固定原因码白名单（本期 4 条），是"走不走寄回"的唯一判据：命中 → 不寄回、不验货；其余一律走寄回 |
| **拒退关单** | 判责异常人工核实后的第三个出口：不退款并直接关单，落"已关闭"并以关闭原因加以区分，**不产生退款单、不经过退款中** |
| **售后中** | 订单侧的展示口径：该商品行存在**非终态**售后单即为"售后中"。按商品行实时聚合本域数据得出，订单表不为售后新增任何状态字段 |

### 1.7 多语言支持

本模块是**混合模块**：既有仅面向内部运营的后台，又有面向买家的售后节点邮件。**C 端页面已拆为 `售后列表详情` 独立需求，其页面文案的多语言接入由该需求负责，不在本节展开。**

#### A. 静态 UI 文案

- **运营后台界面不接入多语言**：售后工单台与售后规则配置页仅面向内部运营，本期仅中文。
- **售后节点邮件模板接入多语言**：邮件模板的固定部分由**语言包**实现（语言包落地，运营可在多语言后台查看/修改），**以英文模板为源文**——英文串就是最终展示文案，开发直接实现，语言包只负责译成其他语种。**各封邮件的英文原文（主题 + 正文）逐字写在 §二 的邮件章节**，本节不重复。

> **上游内容归属**：商品标题、品牌名、成色等级名由**商品模块**负责接入；物流轨迹状态由**物流信息服务**定义与维护；订单相关展示由**订单域**负责。本模块只读取，不代为登记。
>
> **为什么"驳回原因/关闭说明"必须列进来而不是省略**：它们是**会原样进入买家邮件**的文本，不留痕的话后续复核分不清是"确认过不译"还是"当时漏了"。留痕的同时把处理方式写死（运营用英文填），开发才不会去给它们挂翻译。

**`group_code` 取 `aftersale` 的理由**：已有惯例是短缩写（商详 `pdp`、营销活动 `promo`），但售后可用的短缩写都有问题——`as` 太短且在技术语境里到处都是、`ret`/`return` 与"退货/退款"两个不同概念糊在一起、`rma` 是行业黑话而 looply 全线文档都不用这个词，运营在翻译中心导航里认不出。`aftersale` 是一个完整词、与既有的 `pdp` / `promo` / `market` / `order` 字形字音都不撞，扫一眼就知道是哪个模块。**可读性优先于再省两个字母。**

### 2.1 售后工单管理

#### 模块概述

售后工单是运营处理买家逆向申请的主界面，覆盖从审核受理到退款完成/关单的全过程。菜单位置：售后处理 → 售后工单。

本模块包含三类页面/组件：工单列表（§2.1.1）、工单详情（§2.1.2）、各操作弹窗（§2.1.3）。列表页与详情页对同一操作使用同一个弹窗，不各写一份。

**UI 关联**：本模块无 C 端 Figma 设计稿，运营端界面以**运营端原型 v16-antd 对应页面**为准（运营后台为单端，无 PC/APP 版式差异）。

---

#### 本模块公共枚举定义

以下枚举被列表、详情、弹窗多处引用，集中定义一次，各处引用不重复。

**（1）售后单状态（7 个取值，终态 2 个）**

| 枚举值 | 含义 | 触发时机 | 适用场景 |
|---|---|---|---|
| 待审核 | 买家已提交申请，等运营给审核结论 | 买家在 C 端提交申请后；审核驳回后单据回到本状态 | 运营待办。可审核、可关闭售后单；买家可自行撤销 |
| 待寄回 | 审核已通过，等买家把商品寄出 | 需寄回的单审核通过后 | 运营回填退货运单号；等买家交寄。可关闭售后单 |
| 退货在途 | 承运商已产生揽收轨迹，商品在寄回途中 | 退货运单产生揽收轨迹后自动推进 | 可提前判责（如判退回途中丢件）。可关闭售后单 |
| 待判责 | 商品已到仓（或本单无需寄回），等运营判责 | 退货运单物流状态为「已送达」时自动推进；不需寄回的单审核通过后直接进入 | 运营待办。可判责。**不开放**关闭售后单 |
| 退款中 | 判责已提交并已向支付域发起退款，等退款结果 | 判责提交（拒退出口除外）后 | 系统等待态，不是人工待办；退款执行失败的单停留在本状态可重试。**不开放**关闭售后单 |
| 已完成 | 退款成功，本单结束 | 收到退款成功结果后 | 终态。释放该商品行的互斥占用；该商品行不可再建单 |
| 已关闭 | 本单未产生实际退款即结束 | 买家撤销 / 运营关闭 / 判责选「不退并关闭」 | 终态。释放互斥占用；仍在售后时效内的买家可对该商品行重新申请 |

> 两条流程分支同属「退货」这一个售后类型，分岔依据是**售后原因码**（详见 §2.3）而不是类型字段：
> ① **需寄回分支**：待审核 →（审核通过）待寄回 →（揽收轨迹）退货在途 →（已送达）待判责 →（判责）退款中 →（退款成功）已完成
> ② **不需寄回分支**：待审核 →（审核通过）待判责 →（判责）退款中 →（退款成功）已完成，跳过待寄回与退货在途，也不做到仓验货
> ③ **驳回**：待审核 →（驳回）待审核，不落终态、不设「已驳回」状态
> ④ **关闭**：待审核 →（买家撤销）已关闭；待审核 / 待寄回 / 退货在途 →（运营关闭）已关闭；待判责 →（判责选拒退）已关闭

**（2）关闭来源（3 种）**

| 枚举值 | 含义 | 触发时机 | 适用场景 |
|---|---|---|---|
| 买家撤销 | 买家在 C 端自行撤销申请 | 待审核阶段买家主动撤销 | 不发关闭通知邮件 |
| 运营关闭 | 运营手动关单 | 待审核 / 待寄回 / 退货在途三个状态，运营在关闭弹窗提交 | 必须留痕；是否发邮件由运营勾选 |
| 拒退关单 | 判责验货结论异常，经线下人工核实后选「不退并关闭」 | 判责弹窗选择处理出口「不退并关闭」并提交 | **不产生退款单**、不经过退款中；商品线下回寄买家；固定发一封「拒退结果」邮件 |

> 「已关闭」只有一个状态值，三种来源的差异全部由关闭来源承载，不为拒退单新增独立状态。
> **关闭说明（`close_note`）不随关闭来源分叉**：三种来源统一口径——选填、有值即对买家可见，**不做按来源判断的可见性开关**（详见 §2.9.1）。

**（3）验货结论（7 个取值）**

仅需寄回的单产生本项；不需寄回的单无实物可验，不录本项。

⚠ **7 条是字段全集，不是任一入口下的可选范围**：界面可选项按入口状态收敛（待判责 6 条 / 退货在途锁定「退回途中丢件」1 条），见 **§2.7.4「入口状态 × 可选结论」矩阵**。

| 枚举值 | 含义 | 触发时机 | 适用场景 |
|---|---|---|---|
| 与申请一致 | 退回件与买家申报情况相符 | 到仓验货后运营录入 | 正常退款；**仍照常扣除退货扣减**，不因结论一致而豁免 |
| 附件缺失 | 退回件缺少配件、附件 | 同上 | 正常退款；扣减金额由运营在同一步填写 |
| 成色下降 | 退回件成色低于订单成色快照 | 同上 | 正常退款；成色下降所需扣款并入退货扣减，不单列科目 |
| 退回件与订单不符 | 退回的不是订单上的那件商品 | 同上 | **异常结论**，须在同一步选择处理出口（三选一） |
| 空包或无实物 | 包裹为空或无商品 | 同上 | **异常结论**，须在同一步选择处理出口（三选一） |
| 退回途中破损 | 商品在寄回途中损坏 | 同上 | 正常退款；责任归属由运营判定 |
| 退回途中丢件 | 退回包裹在途丢失，货未到仓 | 退货在途状态下运营直接判定 | 无独立「标记丢件」动作，它是本枚举的一个取值；选中后责任归属默认置为平台责任、运营可改；须在判责说明中写明认定依据 |

**（4）异常结论处理出口（3 个取值）**

仅当验货结论为「退回件与订单不符」或「空包或无实物」时出现，必选。

| 枚举值 | 含义 | 触发时机 | 适用场景 |
|---|---|---|---|
| 全额退款 | 按退款基准全额退还买家，不做退货扣减 | 异常结论 + 线下人工核实后 | 退款方案区退货扣减置 0、最终退款金额锁定为退款基准，均不可编辑 |
| 部分退款 | 退多少由运营在退款方案里填写 | 同上 | 退款方案区可编辑 |
| 不退并关闭（拒退关单） | 不退款，售后单直接关闭；商品线下回寄买家 | 同上 | 不调退款、不产生退款单；落已关闭 + 关闭来源=拒退关单 |

**（5）责任归属（2 个取值）**

| 枚举值 | 含义 | 触发时机 | 适用场景 |
|---|---|---|---|
| 平台责任 | 本单责任由平台承担 | **统一在判责环节**由运营录入 | 平台责任可豁免退货扣减，但豁免与否由运营手填金额体现，系统不自动置 0 |
| 买家责任 | 本单责任由买家承担 | 同上 | 同上 |

> ⚠ **不设物流责任**：物流出问题属平台与物流商之间的事，对买家而言即平台责任。物流原因由售后原因码承载（原因码记「为什么」，责任归属记「谁承担」）。
> ⚠ **判定时点统一在判责环节**，两条流程分支都不在审核环节判，**审核弹窗不设责任归属控件**。不需寄回的单虽无验货结论可录，责任归属同样在判责环节首次录入。
> ⚠ 本期责任归属**不驱动任何金额计算**（退货扣减全部手填），为纯留痕字段。

**（6）退款执行状态（4 个取值）**

由支付域退款单结果回传，售后单主状态不为退款失败新增枚举值。

⚠ **「受理失败」（调支付域接口没调通）不在本枚举内，也不落任何业务状态**——它属技术层面，由技术方案保证最终调用成功；调用未成功时售后单根本不进入「退款中」（详见 §2.8.3 末「受理失败 vs 回调失败」）。

| 枚举值 | 含义 | 触发时机 | 适用场景 |
|---|---|---|---|
| 待发起 | 退款方案尚未提交给支付域 | 判责未提交前 | 列表与详情不展示（此时无退款单，整块留空） |
| 退款处理中 | 已向支付域发起并**受理成功**，等结果 | 判责提交、退款单创建受理成功后 | 售后单主状态为「退款中」 |
| 退款成功 | 支付域回传成功 | 支付域回调 | 售后单推进至「已完成」 |
| 退款失败 | 支付域回传失败 | 支付域回调 | 售后单**仍为「退款中」**，出现「重新发起退款」入口与「退款失败待重试」标记 |

**（7）售后类型（本期 1 个取值）**

| 枚举值 | 含义 | 触发时机 | 适用场景 |
|---|---|---|---|
| 退货 | 退回商品并退款 | 建单时唯一可选值 | 本期恒为该值 |

> 维度保留：运营端列表与详情**仍展示「售后类型」这一项**，不因取值单一而隐藏。「仅退款」不再是售后类型，已降级为流程分支（要不要走寄回），由原因码决定。

#### 2.1.1 工单列表

**功能描述**

运营处理售后的主入口。按状态分区展示全部售后单，支持按单号/邮箱搜索、按责任归属与市场筛选、按申请时间范围筛选，并在行上直接执行审核、回填运单、判责、重新退款、关闭等操作。

- 操作者具备售后工单查看权限
- 至少存在一张售后单（无数据时进入零数据态）

**页面布局**

自上而下五段：
1. 页头：标题「售后工单」+ 副标题「发货后的全部逆向申请」；右侧操作区「超期特批建单」「导出」
2. KPI 卡区：4 张，等宽一行
3. 筛选区：搜索框 + 3 个筛选控件 + 查询 + 重置
4. 状态 Tab 区：全部 + 7 个状态
5. 数据区：列表 + 分页

**页面元素**

**① KPI 卡（4 张）**

| # | 卡片名 | 取值口径 | 点击行为 |
|---|---|---|---|
| 1 | 待审核 | 状态=待审核的售后单数 | 切换到「待审核」Tab |
| 2 | 待判责 | 状态=待判责的售后单数 | 切换到「待判责」Tab |
| 3 | 退款中 | 状态=退款中的售后单数 | 切换到「退款中」Tab |
| 4 | 退款失败待重试 | 状态=退款中 **且** 退款执行状态=退款失败 的售后单数 | 切换到「退款中」Tab |

> 4 张卡挂的都是运营待办口径。**不设「售后中」聚合卡**——「售后中」是给订单侧用的聚合口径，运营按具体状态筛选。

**② 搜索与筛选**

| 元素 | 控件 | 取值 | 说明 |
|---|---|---|---|
| 关键词搜索 | 单个输入框，占位「售后单号 / 订单号 / 物流单号 / 买家邮箱」 | 自由文本，可清空 | 一个关键词命中**四个字段中任意一个**即算匹配；四类值的编码规则互不重叠，无需运营先分清输的是哪一种 |
| 责任归属 | 下拉单选 | 全部责任归属 / 平台责任 / 买家责任 | 默认「全部责任归属」 |
| Market | 下拉单选 | 全部 Market / 美国站（US） / 香港站（HK） | 默认「全部 Market」 |
| 申请时间 | 日期区间选择器 | 申请开始日期 ~ 申请结束日期 | 按申请时间过滤 |
| 查询 | 主按钮 | — | 按当前条件查询 |
| 重置 | 次按钮 | — | 清空关键词、状态 Tab（回「全部」）、责任归属、Market |

**关键词搜索的匹配口径（硬性）**

- **部分匹配**：四个字段一律用包含匹配，不要求整串输对。运营常只记得邮箱 @ 前面那截（如 `emma.whit`）或只记得域名（如 `@gmail.com`），要求全等等于这个搜索框对邮箱不可用
- **大小写不敏感**：关键词与被匹配值统一忽略大小写。邮箱本身不区分大小写，运营输入习惯不一，四个字段用同一套处理，不为邮箱单开分支
- **买家邮箱不存放在售后单上**：售后单只记录申请人，邮箱实时关联用户资料取；改了邮箱后续邮件就该发新的，做快照反而会让邮件发去废弃地址。按邮箱检索时实时关联查询，**实现方式由技术方案定**

> ⚠ **不设状态筛选下拉**：状态由 Tab 承载主视图。
> ⚠ **不设「退款失败」筛选器**：退款失败待重试的单由 KPI 卡与列表「退款金额 / 支付结果」列被看见。

**③ 状态 Tab（8 个）**

顺序：全部 → 待审核 → 待寄回 → 退货在途 → 待判责 → 退款中 → 已完成 → 已关闭。

Tab 标签的计数与角标规则：

| Tab | 标签形态 | 说明 |
|---|---|---|
| 待审核 / 待判责 | 文字 + 红色角标（角标值=该状态单数） | 这两个状态运营不动手就推不动，属运营待办，用角标提醒 |
| 退款中 | 文字（数量）+ 红色角标（角标值=**退款失败待重试数**，为 0 时不出角标） | 退款中整体在等支付域回调，不是待办；其中失败待重试的部分才是运营待办 |
| 其余（全部/待寄回/退货在途/已完成/已关闭） | 文字（数量） | 待寄回、退货在途在等买家与物流，不是运营待办，不挂角标 |

**④ 列表字段（11 列）**

| # | 列名 | 内容 | 说明 |

#### 2.1.2 工单详情

**功能描述**

单张售后单的全量视图与操作中心。展示这单**已经发生**的事实，并把所有推进状态的动作收在页头。

**前置条件**

- 从列表页点「详情」进入，或从其他模块按单号跳入
- 该售后单存在

**页面布局**

自上而下：页头（面包屑 + 单号与标记 + 副标题 + 操作按钮排）→ 基本信息 → 退货信息 → 判责信息 → 操作记录。

**展示口径（硬性）**

本页只展示**已经发生**的事实。尚未产生的数据一律留空，**不出试算值 / 预填值 / 默认值**——金额尤其：未判责前退款基准、退货扣减、最终退款金额一个数字都不出。判责弹窗按政策快照预填退货扣减是「运营填表」用的，与本页展示是两回事。

**页面元素 — 页头**

| 元素 | 内容 | 出现条件 |
|---|---|---|
| 面包屑 | 售后工单 / 售后单详情 | 恒出 |
| 售后单号 | 单号（系统标识符样式） | 恒出 |
| 状态标签 | 当前状态 | 恒出 |
| 驳回标记 | 「已驳回 N 次 · 等买家修改」或「已驳回 N 次 · 买家已重新提交，等运营审核」 | 状态=待审核 且 被驳回过（结论为驳回的审核记录 ≥ 1 条）。两种文案的判据见下 |
| 退款失败待重试标记 | 「退款失败待重试」 | 状态=退款中 且 退款执行状态=退款失败 |
| 副标题 | 售后类型 · 所属市场 · 订单号 · 申请于「申请时间」 | 恒出 |

驳回标记两种形态的判据：
- **等买家修改** = 最近一条审核记录结论为驳回，且买家最近一次重新提交时间为空或早于该条审核时间
- **买家已重新提交，等运营审核** = 最近一条审核记录结论为驳回，且买家最近一次重新提交时间晚于该条审核时间

> 「这单被驳回过」与「当前正等买家修改」是**两个口径**：前者只看驳回记录条数，后者还要看重新提交时间。驳回次数不在售后单上单独存一份，由审核记录条数推出。

**页面元素 — 页头操作按钮**

| 按钮 | 出现条件 | 行为 |
|---|---|---|
| 审核 | 状态=待审核 | 打开审核弹窗 |
| 回填运单 | 状态=待寄回 | 打开回填运单弹窗。⚠ 退货在途及之后**不再提供该入口** |
| 判责 | 状态=退货在途 或 待判责，**且该单尚未判过责** | 打开判责弹窗。按钮文案**恒为「判责」，只有一种形态**；**判责是一次性入口**，已判过责的单不再出该按钮（详见 §2.7.2） |
| 重新发起退款 | 状态=退款中 且 退款执行状态=退款失败 | 打开重新发起退款弹窗 |
| 关闭售后单 | 状态 ∈ {待审核, 待寄回, 退货在途} | 打开关闭售后单弹窗（危险按钮） |
| 买家时间线 | 恒出 | 打开买家时间线弹窗 |
| 建单快照 | 恒出 | 打开建单快照弹窗 |
| 返回列表 | 恒出 | 回列表页 |

> 推进状态的动作**全部收在页头**，正文模块里不再各放一份；模块内只保留作用于该模块自身内容的按钮（退货信息里的「刷新轨迹」、基本信息里的「运营补传」）。

| 买家可见 | 「可见」标签 / 「—」 |

操作类型枚举（11 类）：

| 枚举值 | 触发时机 | 买家可见 | 记录内容 |
|---|---|---|---|
| 创建 | 买家在 C 端提交申请 | 是 | 提交事实；需寄回的单附申请时告知的退货服务费参考金额，不需寄回的单不带金额 |
| 审核通过 | 运营审核结论为通过 | 可见条：是；内部条：否 | 可见条只写结果；填了审核意见时**另起一条内部条**承载审核意见原文 |
| 审核驳回 | 运营审核结论为驳回 | 可见条：是；内部条：否 | 可见条写**驳回原因原文** + 已发驳回通知邮件；填了审核意见时另起一条内部条。**绝不把审核意见拼进买家可见那条** |
| 重新提交 | 买家修改申请后重新提交 | 是 | 重新提交事实 |
| 回填运单 | 运营保存退货运单 | 是 | 登记的运单号与承运商、已注册追踪并告知退货地址 |
| 状态推进 | 物流已送达自动进待判责；退款成功自动进已完成 | 是 | 推进事实与依据 |
| 判责并退款 | 运营提交判责 | **否** | 验货结论 · 责任归属 · 处理出口 · 判责说明原文，全量内部承载 |
| 发起退款 | 判责提交调起退款 | 是 | 退款基准 − 退货扣减 = 实退金额、退款单号 |
| 退款失败回传 | 支付域回传失败 | 是 | 退款单号 + 失败原因；本单仍为退款中、需重新发起 |
| 拒退关单 | 判责选「不退并关闭」 | 可见条：是；内部条：否 | 可见条只写客观结果（不予退款、不产生退款单、商品线下回寄、仍在时效内可重新申请），**不拼验货结论、不拼处理出口名**；内部条承载判责说明原文 |
| 关单 | 买家撤销 / 运营关闭 | 是 | 关闭来源 + 关闭说明；运营关闭时另记「邮件告知买家：是/否」与「关闭后买家可以对该商品行重新申请售后」 |

> ⚠ **同一动作若「结果可对外、细节不可对外」，必须拆成两条记录**（可见条 + 内部条），不能靠一条记录里的部分内容不展示来实现。审核与拒退关单是本期的两处实例。

#### 2.1.3 各操作弹窗

列表页行操作与详情页页头是同一个操作的两个入口，**共用同一个弹窗**，不各写一份。全部弹窗禁用遮罩关闭与右上角关闭图标，只能通过底部按钮退出。

**（1）审核弹窗**

- **入口**：列表行「审核」按钮 / 详情页头「审核」按钮
- **可用状态**：待审核
- **只读核对区**：售后单号 · 售后类型 · 售后原因（取建单快照）· 买家说明 · 历次审核记录（仅被驳回过时出现）

  历次审核记录的内容：「已驳回 N 次」标签 + 一句形态说明（「最近一次驳回后买家尚未重新提交」/「买家已于〔时间〕重新提交，本次为再审」）+ 逐条列出每次审核的〔时间 · 结论 · 审核人〕，驳回条附「驳回原因（已发给买家）」原文，有审核意见的附「审核意见（仅内部）」原文。运营再审时要看得到前几次已经要求过买家补什么。

- **表单项**

| 字段 | 控件 | 必填 | 出现条件 | 说明 |
|---|---|---|---|---|
| 审核结论 | 单选：通过 / 驳回 | 是 | 恒出 | 默认「通过」 |
| 驳回原因 | 多行文本 | 是 | 仅结论=驳回 | **对买家可见**，原样作为驳回通知邮件正文发出、C 端展示。引导文案：写清要买家补什么、怎么改——本内容会原样发送给买家 |
| 审核意见 | 多行文本 | 否 | 恒出 | **仅内部**，不进邮件、不对 C 端展示，只进操作记录的内部条。通过与驳回均可写 |

- ⚠ **审核弹窗不设责任归属控件**。两条流程分支一律在判责环节才定责任方。
- ⚠ 驳回原因与审核意见是**两个字段、对外性相反**，不共用一个输入框、不可合并。驳回时两个框同时出现，驳回原因在上、审核意见在下。
- ⚠ **运营须用英文填写驳回原因**（该文本原样进邮件正文，翻译服务对自由文本无能为力）。
- **校验**：审核结论必选；结论为驳回时驳回原因必填且不可全空白。
- **提交后的状态流转**

| 结论 | 状态流转 | 邮件 | 其他 |
|---|---|---|---|
| 通过（需寄回） | 待审核 → 待寄回 | 固定发「审核通过通知」 | 写入一条审核记录 |
| 通过（不需寄回） | 待审核 → 待判责 | 固定发「审核通过通知」 | 写入一条审核记录 |
| 驳回 | 待审核 → 待审核（回环，不落终态） | **固定发「审核驳回通知」，不设开关**，正文取驳回原因原文 | 写入一条审核记录；驳回次数不设上限 |

> 驳回邮件**固定发送**，与关闭通知的手动勾选**刚好相反**：驳回的语义是「要求买家去改申请」，不通知他，C 端只显示审核中，买家不知道要动手，单据就断在这里。**不要照关闭通知的样子给驳回也做一个开关。**

**（2）回填退货运单弹窗**

- **入口**：列表行「运单」按钮 / 详情页头「回填运单」按钮
- **可用状态**：**仅待寄回**。退货在途及之后不再提供该入口——揽收轨迹一旦产生就说明买家已按告知的单号交寄，此后再改登记值只会让留痕与实际轨迹对不上
- **表单项**

| 字段 | 控件 | 必填 | 说明 |
|---|---|---|---|
| 退货运单号 | 单行文本 | 是 | 线下预约面单拿到的承运商运单号 |
| 承运商 | 下拉单选 | 是 | 落库存承运商编码，展示名由承运商字典映射；承运商改名或做多语言时不必回改历史数据 |
| 退货地址 | 多行文本，**只读** | — | 取建单时政策快照的退货地址，标注「不可在此修改」 |

- 弹窗内提示：保存后向买家发出「退货运单号」邮件。⚠ **多张售后单共用同一运单号时该邮件按运单号去重、只发一封**（§2.6.5（3））；本弹窗只登记当前这一张单，**无批量登记入口**。
- **承运商可选范围（硬性）**：**下拉选项一律取物流模块的承运商字典**，与物流模块保持对齐。**售后域不自建承运商字典、不在售后侧硬编码任何承运商清单**——物流模块增删承运商，售后侧下拉自动跟随，不需要售后侧改代码或改配置。原型 v16 当前列出的 5 个（UPS / USPS / FedEx / SF Express（顺丰）/ Hongkong Post）**是原型示例值，不构成需求定义**，实际可选范围以物流模块字典的实时内容为准。
- **校验**：运单号与承运商均必填；运单号去除前后空格后不可为空。
- **提交后**：售后单登记退货运单号与承运商编码，并注册物流追踪；固定发「退货运单号与退货地址」邮件。**状态仍为待寄回**，待承运商产生揽收轨迹后自动推进至退货在途。

**（3）判责弹窗**

判责是**一个动作**：录验货结论 + 判责任方 + 填退款金额一次提交，并由该动作直接调起支付域退款，无需再有独立的「发起退款」动作。

- **入口**：列表行「判责」按钮 / 详情页头「判责」按钮。**文案恒为「判责」，无第二种形态**；开放条件与一次性口径详见 §2.7.2
- **可用状态**：退货在途、待判责两个状态。退货在途开放是为了让货未到仓也能判（如退回途中丢件）
- **只读核对区**（两种形态）

| 需寄回的单 | 不需寄回的单 |
|---|---|
| 售后单号 · 订单号 / 商品行 · 商品名称 · 到仓日期（未送达时提示「尚未送达（退货在途，可直接判丢件）」）· 订单成色快照 · 当前状态 | 售后单号 · 订单号 / 商品行 · 商品名称 · 售后原因 · 最近审核结论 · 最近审核时间 |

- **表单项**

| 字段 | 控件 | 必填 | 出现条件 | 说明 |
|---|---|---|---|---|
| 判责结论 | 下拉单选，**可选范围按入口状态收敛，取值以 §2.7.4「入口状态 × 可选结论」矩阵为准**（待判责 6 条 / 退货在途锁定「退回途中丢件」1 条） | 是 | 仅需寄回的单 | 不需寄回的单无实物可验，无本项。⚠ **不得一律渲染全部 7 条** |
| 责任归属 | 单选：平台责任 / 买家责任 | 是 | **恒出**（两个分支都出） | 不预填、不由原因码带出。例外：判责结论选中「退回途中丢件」且责任归属尚未选择时，默认置为平台责任，运营仍可改判买家责任 |
| 判责说明 | 多行文本 | **否**（判责结论 = 退回途中丢件时**必填**） | 恒出 | **内部字段，绝不外露 C 端**。判丢件时须在此写明认定依据（承运商查件案号、轨迹停留天数等），见校验表 |
| 瑕疵照片 | 图片上传 | 否 | 需寄回 **且** 状态=待判责 | 退货在途时货还没到仓、拿不到照片，不出本项 |
| 处理出口 | 单选：全额退款 / 部分退款 / 不退并关闭（拒退关单） | 是 | 仅判责结论 ∈ {退回件与订单不符, 空包或无实物} | 出现时同步出提示条说明为何要选。未选时不可提交 |
| 退款基准 | 只读 | — | 未选「不退并关闭」时 | 取商品行实付金额 |
| 退货扣减 | 金额输入 | **否**（留空按 0.00 计，出提示不阻断） | 未选「不退并关闭」时 | 见下方「退款方案」 |
| 最终退款金额 | 金额输入 | **否**（留空按 0.00 计，出提示不阻断） | 未选「不退并关闭」时 | 见下方「退款方案」 |

- **退款方案（退款基准 / 退货扣减 / 最终退款金额三行）**

  - **退款基准** = 该商品行的实付金额，构成口径为**已扣优惠分摊、不含销售税、优惠不追回**（下单时享受的优惠已从实付中扣除，退款只退实付，不因退货把优惠算回来向买家收回）。系统取数，运营不可改
  - **退货扣减**是本域**唯一扣款科目**：装的不只是退货物流成本，验货发现的成色下降 / 缺配件所需扣款一并并入，由运营手填一个总额。系统不单列验货扣减科目、不自动计算、**不按责任自动豁免**（平台责任要豁免就把金额填 0，由人决定）
  - 退货扣减的**预填值**按分支区分，预填只是起填值：
    - 需寄回的单 → 预填**建单时政策快照里的退货服务费金额**；改动后出现「恢复默认值」按钮与「已改写，默认值为 X」提示
    - 不需寄回的单 → **预填为空**（不是 0），由运营手填，占位提示「请手动填写」
  - **退货扣减与最终退款金额双向联动**，两者之和恒等于退款基准：改其中一个，另一个随之重算
  - **未填即按 0 计**：退货扣减留空时不拦截，出橙色提示「退货扣减未填写：提交后按 0.00 计，请确认这是本单的扣减意图」，退款按全额基准照常执行
  - 处理出口选「全额退款」时，退货扣减锁定为 0、最终退款金额锁定为退款基准，两项均不可编辑
  - ⚠ **申请时告知买家的退货服务费与实扣值之间不设任何一致性约束**，偏离多少都不改变流程走向。本域不为该字段派生任何拦截或中断逻辑
  - ⚠ **退还税费本期恒为 0**，不参与该算式（字段预留、逻辑保留，待订单侧真正产生税额后启用）

- **两个概念不要混用**：政策里配的「**退货服务费**」是一笔纯服务费配置值；单据上实际扣的叫「**退货扣减**」，是这一单实扣总额（含服务费与验货扣款）。C 端与运营端两端界面**一律用「退货扣减 / Return deduction」**指代后者。
- **校验**

| 条件 | 结果 |
|---|---|
| 需寄回的单未选判责结论 | 不可提交 |
| 判责结论的可选范围 | 按入口状态过滤（§2.7.4 矩阵）：**待判责不得选「退回途中丢件」**；**退货在途只能是「退回途中丢件」**，不可改选 |
| 未选责任归属 | 不可提交 |
| 判责结论为异常但未选处理出口 | 不可提交，并出提示条「处理出口未选择，无法提交」 |
| **判责结论 = 退回途中丢件、判责说明留空** | **不可提交**（丢件是唯一「货没到仓也退钱」的出口，认定依据是事后索赔与对账的唯一凭据）。其余结论下判责说明选填 |
| 退货扣减 / 最终退款金额 | 取值区间 0 ~ 退款基准，保留两位小数；**两项均非必填，留空按 0.00 计并出提示，不阻断提交**（§2.7.8） |

- **提交后的状态流转**

| 提交形态 | 状态流转 | 是否产生退款单 | 其他 |
|---|---|---|---|
| 常规判责（含异常结论选全额/部分退款） | 退货在途或待判责 → **退款中** | 是，即时向支付域发起退款 | 写入验货记录（需寄回的单）与退款方案；反写订单商品行退款状态为退款中 |
| 处理出口 = 不退并关闭 | 退货在途或待判责 → **已关闭**（关闭来源=拒退关单） | **否**，不向支付域发起退款 | 提交按钮变为危险按钮、文案改为「判责并关闭售后单（拒退关单）」；商品线下回寄买家，不进系统；固定发「拒退结果」邮件 |
| 退款成功回调 | 退款中 → 已完成 | — | 固定发「退款完成（含验货结果与金额明细）」邮件 |
| 退款失败回调 | **仍为退款中** | — | 出现「重新发起退款」入口；不为退款失败新增状态枚举 |

- ⚠ **不设「判责异常·待人工处理」挂起态**：人工核实是线下动作，核实完再回系统录入即可。
- ⚠ **丢件不设独立动作**：它是判责结论的一个取值，选中后须写明认定依据；判定丢件时固定发「丢件处理进展」邮件。

**（4）重新发起退款弹窗**

- **入口**：列表行「重新退款」按钮 / 详情页头「重新发起退款」按钮
- **可用状态**：状态=退款中 **且** 退款执行状态=退款失败
- **内容**：顶部提示「退款单〔单号〕于〔失败时间〕回传失败」；下方四个**只读**数字：商品行实付 · 退款基准 · 退货扣减（以负号展示）· 实退金额（强调展示）
- **表单项**：无。金额沿用判责时的成交值，**一律不可修改**——金额在判责时已经定过了，本弹窗只服务退款执行失败的重发
- **校验**：无输入项，无字段校验
- **提交后**：重新向支付域发起退款；**状态仍为「退款中」**，等新的回调结果

**（5）关闭售后单弹窗**

- **入口**：列表行「关闭售后单」按钮（危险）/ 详情页头「关闭售后单」按钮（危险）
- **可用状态**：**待审核 / 待寄回 / 退货在途** 三个状态
  - 待审核纳入的原因：驳回是回环（回到待审核等买家修改），买家既不修改也不撤销时单据会永久停在待审核
  - **不开放待判责 / 退款中**：那两个阶段货已在平台手上、或钱已在退的途中，应走判责与重新发起退款，不从这里硬关单
- **只读核对区**：售后单号 · 当前状态（附说明「非终态，关闭后落终态『已关闭』」）· 订单 / 商品行（订单号 + 商品行标识 + 商品名称）
- **表单项**

| 字段 | 控件 | 必填 | 说明 |
|---|---|---|---|
| 关闭说明 | 多行文本 | 否 | **一律对买家可见**（不分关闭来源），买家在 C 端进度页会看到这段说明、关闭通知邮件也会带上。运营须用英文填写（自由文本原样发出，翻译服务无能为力）。**输入框提示须写明：本内容会原样发送给买家，请勿填写验货结论、责任判定、拒退理由等内部定性内容** |
| 关闭后通知 | 复选框「邮件告知买家本单已关闭」 | — | **默认勾选**。说明文案：取消勾选后，买家收不到关单通知邮件 |

- ⚠ 关闭说明与判责说明**性质正好相反**：关闭说明对买家可见，判责说明绝不外露。开发不要照判责说明的样子把关闭说明当内部备注处理。
- ⚠ **是否发邮件由运营决定**，系统既不固定发也不固定不发；两种取值都进操作记录留痕（用于解释「这单为什么没发邮件」）。这与驳回邮件的固定发送口径**刚好相反**。
- **校验**：关闭说明**选填**，不设必填校验。
  ⚠ **「关闭原因」与「关闭说明」是两个字段，不要糊成一个**：**关闭原因**是系统按来源自动落值的枚举（买家撤销 / 运营关闭 / 拒退关单），**运营端没有让运营选它的控件**；**关闭说明**才是运营手填的自由文本、选填、对买家可见。运营侧**没有任何需要填的「原因」字段**，⛔ 不要做成必填项。详见 §2.9.3。
- **提交后**
  - 状态 → 已关闭，关闭来源 = 运营关闭，记录关闭时间、关闭说明、是否邮件告知
  - 勾选时发「关闭通知」邮件，未勾选不发
  - **释放该商品行的互斥占用**——释放是「进入终态的必然结果」，两个终态、三种关闭来源一律如此。占用与否**按订单商品行实时聚合本域非终态单得出，不需要显式反写字段**（写明这句是为了避免开发去订单域找一个不存在的占用字段）
  - **已关闭是终态、不可恢复**：关错了只能让买家重新提交一张新单
  - 仍在售后时效内的买家，可对该商品行重新申请

**（6）超期特批建单弹窗**

- **入口**：工单列表页头「超期特批建单」按钮
- **可用状态**：与售后单状态无关，是运营端的独立建单入口
- **适用范围**：仅用于**已超出政策时效窗口**的订单
- **表单项**

| 字段 | 控件 | 必填 | 说明 |
|---|---|---|---|
| 订单号 | 单行文本 | 是 | 输入订单号后带出该订单的商品行 |
| 商品行 | 多选下拉 | 是 | 可多选。命中拦截条件①或②的商品行（已有进行中的售后单 / 已退成钱）在下拉里**置灰、不可选中**，**选项上直接标出被拦原因** |
| 售后类型 | 单选 | 是 | 本期只有「退货」一个取值 |
| 选择售后原因 | 下拉单选 | 是 | 取原因码字典中**启用**的条目，展示「中文备注 / 展示文案」 |
| 备注 | 多行文本 | 否 | 特批理由。示例：买家在时效内已联系客服，因客服漏单导致超期，经主管同意特批受理 |

- **特批的边界（硬性）**：特批**只豁免售后时效判定**这一条，其余建单拦截条件一律照常成立，特批不能绕过。命中下列任一即建单失败：

| # | 拦截条件 | 说明 |
|---|---|---|
| ① | 该商品行已有进行中（非终态）的售后单 | 即互斥约束 |
| ② | 该商品行**已退成钱**（存在一张已完成的售后单） | 判据是**钱有没有退出去**，与走哪条流程分支无关。已完成的单已进终态、互斥不拦，必须单独判定 |

> ⚠ 两个终态对「能不能再建单」的结论**正好相反**：已完成 = 钱已退出去 → 不能再建单；已关闭 = 没退成钱（三种来源都没产生实际退款）→ 仍可在售后时效内重新申请。

- **校验**：被拦商品行**置灰不可选中**，原因直接标在选项上——**因此不存在「已选中被拦行」这个状态，也就没有对应的错误提示条与提交置灰逻辑**（⛔ 不要做成「可选中 + 提交时报错」）；至少选一个商品行才可提交。
- **提交后**：为选中的每个商品行各建一张售后单（一单一行），单据落「是否超期人工特批 = 是」与特批原因随单留痕，进入待审核。

**（7）售后附件弹窗（附件查看与运营补传）**

- **入口**：详情页「买家举证附件」字段下方的「运营补传」按钮
- **可用状态**：全状态可访问
- **内容**：附件清单表（文件 · 来源 · 文件类型 · 上传时间），来源以标签区分「买家举证」与「判责取证」，两类合并展示；无附件时表格出「暂无附件」
- **操作**：下方「运营补传」上传区，支持点击或拖拽、可多选
- ⚠ **附件的数量 / 格式 / 大小限制本 PRD 不写**，归 C 端申请页需求（运营端原型 v16 的上传区提示为示例，不构成需求定义）
- **提交后**：附件挂到本售后单下，来源标记为运营补传；底部只有「关闭」按钮，无提交类按钮

**（8）建单快照弹窗**

- **入口**：详情页头「建单快照」按钮
- **可用状态**：全状态可访问
- **功能描述**：建单那一刻会对两样东西各留一份整条留档——命中的**售后政策**与买家选中的**售后原因码**。两者之后在配置页被改动都不回溯本单。合成一个弹窗而不是两个按钮，因为运营查它们的场景是同一件事：「这单建的时候，规则长什么样」

| 中文备注 | 同上 |
| 举证要求 | 必传 / 选传 标签；同上 |

| 字段 | 说明 |
|---|---|
| 快照来源政策 | 政策编号 |
| 快照时间 | 即建单时间 |

- **内容**：顶部一句说明「买家侧会展示最新的售后进度，当前时间线和买家看到的信息一致」；下方时间轴，从新到旧，每条两级（标题 + 说明 + 时间）
- ⚠ **本 PRD 不定义时间线的事件清单与文案**，归 C 端页面需求。运营端弹窗直接呈现买家侧那一份，不另做一套运营版
- ⚠ **必须不出现在时间线里的内部信息**（这是数据能不能对买家侧返回的安全边界，不是「页面显示什么」）：验货结论 · 处理出口 · 判责说明 · 责任归属 · 审核意见 · 「第 N 次驳回」这类计数 · 内部状态名与内部术语。**唯一的中文出口**是运营关闭时手填的关闭说明，那是运营自己写给买家的原文，照登
- **底部**：只有「关闭」按钮

**（10）大图查看弹窗**

- **入口**：详情页任意缩略图（买家举证附件、判责取证）
- **可用状态**：全状态可访问
- **内容**：大图展示区 + 文件名 + 上传时间 + 上一张 / 下一张 + 「第 i / N 张」计数
- ⚠ **不展示「来源」**：大图是从某一组缩略图点进来的，那一组自己就是来源，弹窗里再标一次是复述
- ⚠ **买家举证与判责取证是两组独立的图**，各自翻页，不混在一起
- 无图可看时展示「暂无可查看的图片」
- **底部**：只有「关闭」按钮

### 2.2 售后政策配置

#### 模块概述

售后政策定义「哪些商品能退、退多久、扣多少钱、寄到哪」，按 market 独立配置。菜单位置：售后规则 → 售后政策。

**政策匹配规则（硬性）**

- 按 **商品 → 品类 → 全市场** 固定层级顺序**依次校验**，**匹配即停**，不再往上找
- 该层级顺序由系统固定，**不由优先级数值决定**
- **同层优先级**只用于同一层级内多条同时命中时的定序，数值大的优先。例：一件商品同属「手袋」与「特价清仓」两个品类、两条品类级政策都命中时靠它定先后
- **三级均未命中时的兜底（硬性）**：商品级、品类级、全市场级**三级依次校验后仍无任何启用中的政策命中**，则**不落任何默认政策、也不直接判"不可申请"**，而是**提示买家联系客服**。这是**唯一的兜底出口**——该情形属运营配置遗漏（该 market 未配全市场级兜底政策），系统不自行替运营决断，改由人工介入处理
- 政策命中发生在**建单那一刻**，整条政策随即留档为政策快照，此后的政策改动不回溯在途单

**UI 关联**：以运营端原型 v16-antd「售后政策」列表页与「新增/编辑售后政策」表单页为准。

#### 2.2.1 政策列表

**功能描述**：查看与维护全部售后政策，支持新增、编辑、复制、启停。

**前置条件**：操作者具备售后规则配置权限。

**页面布局**：页头（标题「售后政策」+ 副标题「匹配顺序：商品 → 品类 → 全市场，命中即停」+ 右侧「新增政策」）→ 筛选区 → 列表 → 分页。

**页面元素 — 筛选区**

| 元素 | 控件 | 取值 |
|---|---|---|
| 关键词 | 输入框，占位「政策编号 / 范围值」 | 自由文本，可清空 |
| Market | 下拉单选 | 全部 Market / 美国站（US）/ 香港站（HK） |
| 范围类型 | 下拉单选 | 全部范围类型 / 全市场 / 品类 / 商品 |
| 状态 | 下拉单选 | 全部状态 / 启用 / 停用 |
| 查询 · 重置 | 按钮 | — |

**页面元素 — 列表字段（11 列）**

| # | 列名 | 内容 | 说明 |
|---|---|---|---|
| 1 | 政策编号 | 编号 | 系统标识符样式 |
| 2 | 适用市场 | 市场名称 | |
| 3 | 适用范围 | 范围类型标签 + 范围值；全市场时范围值展示「全部商品」 | |
| 4 | 同层优先级 | 数值 | 居中 |
| 5 | 是否支持退货 | 支持 / 不支持 标签 | |
| 6 | 售后时效 | 「签收后 N 天」；不支持退货时「—」 | |
| 7 | 退货服务费 | 金额 + 币种；不支持退货时「—」 | 右对齐 |
| 8 | 退货地址 | 地址全文；无地址时「—」 | |

**范围类型枚举**

| 枚举值 | 含义 | 触发时机 | 适用场景 |
|---|---|---|---|
| 全市场 | 覆盖该 market 下全部商品 | 新增政策时选择 | 兜底层，匹配顺序最后一级；无范围值 |
| 品类 | 覆盖指定品类 | 同上 | 需选具体品类；一件商品可能命中多条品类政策，靠同层优先级定序 |
| 商品 | 覆盖指定商品 | 同上 | 需填商品 ID，支持多个；匹配顺序第一级 |

**操作列行为**

| 操作 | 行为 |
|---|---|
| 编辑 | 进入编辑页，带入该条数据 |
| 复制 | 进入新增页，并**预填源政策的全部内容**——四个分区的表单项逐项带入（适用市场 · 范围类型 · 适用品类 / 适用商品 · 同层优先级 · 是否支持退货 · 售后时效 · 服务费金额 · 币种 · 退货地址 · 政策状态），**唯一不带入的是政策编号**（由系统在保存时新生成）。运营在预填值上改动后保存，生成一条**新政策**，源政策不受影响。⚠ 复制页不预填即等同于「新增」，该按钮就没有存在价值 |
| 停用 / 启用 | 打开政策启停弹窗二次确认 |

**政策启停弹窗**

- 入口：列表行「停用」/「启用」

- 停用时附警示：停用后新申请不再命中本条
- 提交后：政策状态切换。**已建单据不受影响**（其政策快照已冻结建单时的整条政策）

**页面状态变体**：与 §2.1.1 同一套四态（正常数据 / 零数据 / 无匹配 / 加载失败）。零数据态与无匹配态的行动按钮分别为「新增政策」与「清除筛选条件」。

**操作流程**：进入列表 → 筛选定位 → 新增 / 编辑 / 复制 / 启停 → 保存后回列表。

**校验规则**：列表页无字段录入，校验随表单页与启停弹窗。

**交互说明**：列表横向可滚动，操作列固定在右侧；分页同 §2.1.1。

**异常处理**：加载失败出加载失败态；启停时该条已被他人改动 → 提交拦截并提示刷新后重试。

#### 2.2.2 政策新增 / 编辑

**功能描述**：录入或修改一条售后政策。新增与编辑共用同一张表单，差异只在标题、原因码类只读项与操作记录区。

**前置条件**：操作者具备售后规则配置权限；编辑时该政策存在。

**页面布局**：页头（面包屑 + 标题 + 副标题）→ 四个表单分区 →（编辑时）操作记录 → 底部操作条（取消 / 保存）。

副标题：新增时为「保存后即对新申请生效」；编辑时为该条政策编号。

### 2.3 售后原因配置

#### 模块概述

售后原因码是 C 端申请页的原因下拉配置，同时**承担流程分岔的判定依据**。菜单位置：售后规则 → 售后原因。

**原因码分两类，维护权与可变范围完全不同（硬性，开发必看）**

| | 谁维护 | 删除 | 停用 | 改 `reason_code` | 改展示文案 / 排序 / 是否必传举证 |
|---|---|---|---|---|---|
| **普通原因码**（如「与描述不符」「成色不符」「尺寸不合适」「其他」等） | **运营在后台自由配置**，可随时增删改 | ✅ 可 | ✅ 可 | ⛔ 创建后不可改（全局唯一标识） | ✅ 可 |
| **未收到货白名单（4 条）** | **系统预置**，随初始化落库，运营不可增删 | ⛔ 不可 | ⛔ 不可 | ⛔ 不可 | ✅ 可（只有这三项可改） |

**白名单为什么必须是例外**：流程走不走寄回，判据就是「买家选中的原因码在不在这 4 个 `reason_code` 里」。运营一旦删掉或停用其中一条，**买家就再也选不到那条「没收到货」的原因**，只能改选一条会要求他寄回的原因——**而他手上根本没有货**，这单必然卡死在待寄回。

> ⚠️ **原型 v16 里那 13 条原因码是示例数据，不是需求定义**。开发**不要把这 13 条硬编码进代码**。本节真正构成需求的只有三样：**① 上述 4 条白名单（系统预置、内容与约束均写死）；② 原因码的字段结构（原因码 / 展示文案 / 中文备注 / 是否必传举证 / 排序 / 启用状态）；③ 运营可配置的范围（即上表「普通原因码」那一行）**。除 4 条白名单外，字典里有哪些原因码、各自叫什么、怎么排序，**全部由运营在后台配置决定**，初始数据也由运营录入，不由代码预置。

**流程分岔判定（硬性）**

- 系统侧维护一份固定的**未收到货码表（白名单）**，共 4 条
- 买家选中的原因码 **∈ 白名单** → 审核通过后直接进入待判责，**跳过寄回与到仓验货**
- **其余任何原因码** → 审核通过后进入待寄回，走寄回、退货在途、到仓验货
- **默认方向是走寄回**：只有命中白名单才不寄回。运营后来新增的原因码一律按已收到货处理，不需要也无处标注分组
- ⚠ **判定只能查白名单常量，禁止用前缀 / 通配符 / 字符串匹配推断**。原因码统一用中性前缀，前缀**不携带任何分组含义**；一旦用前缀推断，运营新建的任意同前缀原因码都会被静默归进某一组，而本域**没有**对新增原因码的分组拦截（该拦截已明确不做）
- ⚠ 白名单是**系统常量、不是配置项**。做成运营可编辑就等于又回到「运营能改流程走向」
- ⚠ 判定时读的是**本单原因码快照**，不实时回查字典；字典只在建单那一刻被读一次

**未收到货白名单（4 条，系统预置）**

| # | 原因码 | 展示文案 | 中文备注 |
|---|---|---|---|
| 1 | ASR_MARKED_DELIVERED_NOT_RECEIVED | Marked delivered but not received | 显示已送达但未收到 |
| 2 | ASR_LOST_IN_TRANSIT | Lost in transit | 运输中丢件 |
| 3 | ASR_EMPTY_PACKAGE | Empty package | 包裹为空 |
| 4 | ASR_DELIVERY_FAILED | Delivery failed and returned | 投递失败退回 |

**白名单条目的不可变约束（对每一条都成立，不是只锁其中某一条）**

| 约束 | 说明 |
|---|---|
| **不可删除** | 删了历史单靠快照仍能显示，但新单再也走不进该分支 |
| **不可修改原因码** | 原因码取值本身就是判据 |
| **不可停用** | 停掉任意一条，C 端申请页就少一个入口，买家只能改选一条会要求他寄回的原因，而他手上根本没有货 |
| 可改的只有三项 | 展示文案 / 排序 / 是否必传举证——这三项改了只影响 C 端怎么展示、要不要传图，**不影响流程走向** |

> 运营端配置页必须对这几行**逐行禁用停用入口**（不是提交时才报错）；新增原因码时也不允许再输入这几个原因码（原因码全局唯一，重复即拒）。

> ⚠ **「其他」不进白名单**：`ASR_OTHER`（Other / 其他）是一条普通原因码，走寄回。理由——买家选「其他」时很可能是货已收到、只是原因不在列表里；放进白名单，这类买家就永远走不到寄回分支，而他手上是有货的。
> 已知代价：买家「没收到货、但情形不在这 4 条里」时，只能选最接近的一条，或选「其他」而被要求寄回。已记模块待优化清单。

**UI 关联**：以运营端原型 v16-antd「售后原因」列表页与「新增/编辑原因码」表单页为准。

| 启用状态 | 下拉：启用 / 停用 | 是 | 启用 | **白名单 4 条只读**（与列表页停用按钮置灰同一口径）；其余可改 | |

> ⚠ **原「收货情况」配置项已删除**：字典上不再有标识收货与否的字段，走不走寄回由原因码本身决定，不需要运营在这里配。

**操作记录**（仅编辑态出现）：结构同 §2.1.2 模块④，操作类型枚举为 创建 / 编辑 / 启用 / 停用。

**页面状态变体**

| 变体 | 差异 |
|---|---|
| 新增 | 标题「新增原因码」；副标题「原因码全局唯一，创建后不可修改」；原因码可输入；无操作记录区；主按钮「保存并创建」 |
| 编辑（普通原因码） | 标题「编辑原因码」；副标题为原因码；原因码只读；有操作记录区；主按钮「保存」 |
| 编辑（系统预置原因码） | 在编辑态基础上，「启用状态」额外置为只读 |

**操作流程**：进入表单 → 填原因码与文案 → 设举证要求与排序 → 保存 → 回列表并提示保存成功。取消则直接回列表。

**校验规则**

| 字段 | 规则 | 校验时机 |
|---|---|---|
| 原因码 | 必填；全局唯一，重复即拒；**不允许新建白名单里已有的 4 个原因码**（唯一性校验天然覆盖）；创建后不可修改 | 提交时 |
| 展示文案 | 必填 | 提交时 |
| 中文备注 | 选填 | — |
| 是否必传举证 | 必选 | 提交时 |
| 排序 | 必填，整数 1~999 | 输入时 + 提交时 |
| 启用状态 | 必选；系统预置原因码不可改为停用 | 提交时 |
| 原因码命名 | **结果要求（硬性）：原因码不得引入任何带分组含义的前缀**（不要再造 RO_ / NR_ / SHIP_ 之类）——分组含义一旦进 code，就会和「未收到货白名单」这个唯一判据形成第二套隐含分组，日后必然打架。**是否在录入时做表单层格式校验拦截、还是仅作规范约定，属技术方案决定，本 PRD 不约束** | 提交时 |

**交互说明**

- 编辑态下原因码输入框置为只读，不做「点了才报错」
- 系统预置原因码的启用状态下拉整体禁用
- 底部操作条固定在表单末尾，右对齐

**异常处理**

| 场景 | 处理 |
|---|---|
| 原因码重复 | 提交拦截，提示该原因码已存在 |
| 保存失败 | 保留已填内容，提示失败原因 |
| 编辑时该原因码已被他人改动 | 提交拦截并提示刷新后重试 |
| 试图停用系统预置原因码 | 界面上已置灰不可触发；即使绕过界面提交，系统同样拒绝，**实现方式由技术方案定** |

### 2.4 售后申请与受理

> 对应系统流程图 V2.3 **段①「资格判定与申请提交」**，并承接段⑥「未收到货分支」的分岔判据定义。

#### 2.4.1 售后单状态机（§2.4~§2.9 六节共用基准）

售后单状态共 **7 个**：非终态 5 个（待审核 / 待寄回 / 退货在途 / 待判责 / 退款中）、终态 2 个（已完成 / 已关闭）。**没有「已驳回」「退款失败」「拒退」这三个状态**——驳回是待审核单上的一次审核结论（回环）、退款失败是一次调用的结果、拒退是关闭原因的一个取值。

| 状态 | 含义 | 进入条件 | 退出条件 | 可做的操作 |
|---|---|---|---|---|
| 待审核 | 买家已提交申请，等待运营给出审核结论 | ① 买家在 C 端提交申请且全部建单校验通过（§2.4.5）；② 运营超期特批建单成功；③ 已在本状态的单被驳回后**保持本状态不变**（不是一次进入） | ① 审核通过且本单需寄回 → 待寄回；② 审核通过且本单不需寄回 → 待判责；③ 买家撤销 → 已关闭；④ 运营关闭 → 已关闭 | 运营：审核（通过 / 驳回）、关闭售后单；买家：撤销申请、被驳回后修改并重新提交 |
| 待寄回 | 审核已通过、需买家把货寄回，等运营线下取得面单并登记退货运单号 | 审核通过 且 本单**原因码快照不落在未收到货白名单**内 | ① 物流信息服务回传该退货运单的**已揽收**轨迹 → 退货在途；② 运营关闭 → 已关闭 | 运营：回填退货运单号与承运商（本状态是唯一登记入口）、关闭售后单 |
| 退货在途 | 买家已交寄，包裹在寄回途中 | 物流信息服务回传**已揽收**轨迹 | ① 物流信息服务回传**已送达** → 待判责；② 运营提交判责（含「退回途中丢件」结论）→ 退款中；③ 运营关闭 → 已关闭 | 运营：判责（不等到仓，用于丢件 / 灭失）、关闭售后单、查看轨迹；退货运单登记值**此后只读** |
| 待判责 | 等运营给出验货结论 / 责任归属 / 退款金额 | ① 走寄回的单：物流信息服务回传**已送达**（无人工签收登记）；② 不寄回的单：审核通过 且 原因码快照**落在未收到货白名单**内 | ① 运营提交判责（正常出口 / 异常出口①全额退 / 异常出口②部分退）→ 退款中；② 运营提交判责且选择异常出口③「不退并关闭」→ 已关闭（关闭原因 = 拒退关单） | 运营：判责（异常结论须在同一次提交内选定处理出口）。**不开放**运营关闭 |
| 退款中 | **「已调起支付域退款、等待回调结果」的时间差状态**。钱已经在退的途中，**不是留给运营的操作窗口**，也不是等运营再点一次的人工待办 | 运营提交判责，退款金额定案**并已成功调起支付域退款**（含段⑦丢件判责、段⑤异常出口①②） | ① 回调为**成功** → 已完成；② 回调为**失败** → **仍停留在本状态**，标记为「退款失败待重试」（不新增状态，见 §2.8.5）。**支付域回调是本状态的唯一出口** | 运营：**仅「重新发起退款」**（只对退款执行失败的单开放，金额沿用成交值、不可改）。**无任何判责类操作**——判责已定案，不可修改、不可撤回、不可重判。**不开放**运营关闭 |
| 已完成（终态） | 退款已实际到账，本次售后结束 | 支付域退款结果回调为成功 | 无 | 只读查看。该商品行**不可再次申请售后**（已退成钱，见 §2.4.5 拦截条件②） |
| 已关闭（终态） | 本单终结且未产生实际退款 | 三种来源之一：① 买家撤销；② 运营关闭；③ 拒退关单（详见 §2.9.1） | 无。**已关闭不可恢复** | 只读查看。该商品行在售后时效内**可重新申请** |

**共用口径（六节均适用）**

- 「售后中」= 全部**非终态**售后单的实时聚合（5 个非终态）。订单域展示商品行「售后中」时按商品行实时查本域聚合，**订单表不为售后新增状态字段**。
- 互斥占用（同一商品行同时只允许一张非终态售后单）与上一条**同一口径**：占用与否由实时聚合得出，**不需要任何显式反写字段**；单据进入任一终态即自动释放，无例外。
- 「驳回」不产生状态变更：单据停留在待审核（详见 §2.5.4）。
- 「退款失败」不产生状态变更：单据停留在退款中（详见 §2.8.5）。

#### 2.4.2 功能描述

买家在订单详情对**已发货**的商品行发起售后申请。系统按政策判定申请资格、按买家选中的原因码判定本单走哪条流程分支，通过后**按商品行拆单**生成售后单并冻结两份快照，单据进入待审核。超出时效窗口的订单，运营可在后台**超期人工特批**建单。

本期售后类型只有「**退货**」一个取值，但**类型维度保留**（为后续换货 / 部分补偿留位），运营端列表与详情**仍展示该项**，不因取值单一而隐藏。买家有没有收到货**不映射成售后类型**，映射的是「走不走寄回」这条流程分支。

#### 2.4.3 前置条件

| # | 条件 | 说明 |
|---|---|---|
| 1 | 该商品行**已发货** | 未发货的走订单取消 / 发货前退款，不进入本流程 |
| 2 | 该商品行命中一条**启用中的售后政策** | 政策按「商品 → 品类 → 市场」固定层级顺序**依次校验**，**命中即停**、不再往上找；层级顺序为系统固定，不由优先级决定。同一层级多条同时命中时，按优先级数值大者优先。**三级均未命中 → 提示买家联系客服**（见 §2.2 政策匹配规则的兜底口径） |
| 3 | 该商品行**无进行中的售后单** | 见 §2.4.5 拦截条件① |
| 4 | 该商品行**未退成过钱** | 见 §2.4.5 拦截条件② |
| 5 | 仍在售后时效窗口内 | 见 §2.4.4；超期的只能走 §2.4.8 超期人工特批 |

#### 2.4.4 时效判定

- 售后时效天数为 **market 级运营配置项**（美国站与香港站独立配置），本 PRD 不写死数值。
- **未签收期间不启动计时**：买家随时可申请；**签收后才开始算 N 天**，起算点 = 签收时点。
- 签收时间取**订单域的包裹签收时间**（订单履约事实的权威源），不跨域调物流服务取。
- 时效**严格按窗口判断、与申请次数无关**：单据关闭后若仍在时效内，可正常再次申请，不需要人工特批。
- **发货后即可申请，不以签收为门槛。**

#### 2.4.5 建单拦截条件（三条，特批只能豁免其中一条）

| # | 拦截条件 | 判据 | 超期特批能否豁免 |
|---|---|---|---|
| ① | 该商品行已有**进行中（非终态）**的售后单 | 按商品行实时聚合本域非终态单，命中即拦 | **否**，照常成立 |
| ② | 该商品行**已退成钱** | 该商品行存在一张**已完成**的售后单（退款已实际到账） | **否**，照常成立 |
| ③ | 已超出售后时效窗口 | §2.4.4 | **是**，特批只豁免这一条 |

**开发注意（两条容易做错的地方）**

- 条件②**不能靠条件①推导**：互斥管的是「同时只允许一张非终态单」，而已完成的单已进终态、互斥不拦，必须单独判定。
- 两个终态对「能不能再建单」的结论**正好相反**，不可一视同仁：**已完成 = 钱已退出去 → 不能再建单**；**已关闭 = 没退成钱**（买家撤销 / 运营关闭 / 拒退关单三种来源都没产生实际退款）**→ 仍可在时效内重新申请**。
- 条件②的判据是「**有没有退成钱**」，与该单走哪条流程分支无关：两条分支走到已完成一律都算。

#### 2.4.6 流程分岔判定：未收到货原因码白名单

本期**不为「收货与否」新增任何字段**——售后单上没有，原因码字典上也没有。走不走寄回的判据是**买家选中的那条原因码本身**，判定方式为**白名单包含判断**：

- 选中的原因码 **∈ 未收到货白名单** → 审核通过后直接进「待判责」，跳过寄回与到仓验货；
- **其余任何原因码** → 审核通过后进「待寄回」，走寄回 → 退货在途 → 到仓验货。

**判定的默认方向是「走寄回」**：只有命中白名单才不寄回，运营后来新增的任何原因码一律按已收到货处理。

**未收到货白名单（本期 4 条，系统初始化预置，运营不可创建）**

| # | 原因码 | 展示文案（英文源文案） | 中文（仅供运营理解） |
|---|---|---|---|
| 1 | `ASR_MARKED_DELIVERED_NOT_RECEIVED` | Marked delivered but not received | 显示已送达但未收到 |
| 2 | `ASR_LOST_IN_TRANSIT` | Lost in transit | 运输中丢件 |
| 3 | `ASR_EMPTY_PACKAGE` | Empty package | 包裹为空 |
| 4 | `ASR_DELIVERY_FAILED` | Delivery failed and returned | 投递失败退回 |

**⚠ 判据只能查这份白名单常量，禁止用前缀 / 通配符 / 字符串匹配推断。** 原因码统一使用中性前缀 `ASR_`（After-Sale Reason），**前缀不携带任何分组含义**；不允许写 `startsWith("ASR_...")`、不允许写 SQL 的 `LIKE 'ASR_XXX%'`。一旦这么写，运营新建的任意同前缀原因码都会被静默归进某一组，而本域**没有**对新增原因码的分组拦截（该拦截已明确不做）。新增原因码时也不得再引入带分组含义的前缀。

**运营侧不可变约束（对白名单里的每一条都成立，不是只锁其中某一条）**

| 项 | 是否允许运营改 | 说明 |
|---|---|---|
| 删除该原因码 | **否** | 删了历史单靠快照仍能显示，但新单再也走不进该分支 |
| 修改原因码 code | **否** | code 就是分岔判据本身 |
| 停用该原因码 | **否** | 停掉一条 → C 端申请页少一个入口，买家只能改选一条要求他寄回的原因，而他手上根本没有货 |
| 展示文案 / 排序 / 是否必传举证 | **是** | 改这三项只影响 C 端怎么展示、要不要传图，不影响流程走向 |

**结果要求**：运营端原因码配置页对白名单这几行**逐行禁用停用与删除入口**（不是提交时才报错），新增原因码时也不允许再输入这几个 code。

**⚠「其他」（`ASR_OTHER`）不进白名单，走寄回。** 买家选「其他」时很可能是货已收到、只是原因不在列表里；放进白名单会让这类买家永远走不到寄回分支，而他手上是有货的。已知代价：买家「没收到货、但情形不在这 4 条里」时只能选最接近的一条，或选「其他」而被要求寄回。

**⚠ 本期不存在「已收到货 + 不寄回只退钱」这个组合**——那等于商品留给买家只退钱，属部分退款 / 补偿，本期明确不做；两端都不提供该组合的取值路径。

#### 2.4.7 两条流程分支对照（需寄回 vs 不需寄回）

| 对照项 | 分支 A：需寄回（已收到货） | 分支 B：不需寄回（未收到货） |
|---|---|---|
| 进入判据 | 原因码快照 **∉** 未收到货白名单（默认方向） | 原因码快照 **∈** 未收到货白名单（4 条） |
| 售后类型 | 退货（本期唯一取值） | 退货（本期唯一取值，两分支相同） |
| 状态链路 | 待审核 → 待寄回 → 退货在途 → 待判责 → 退款中 → 已完成 | 待审核 → **待判责** → 退款中 → 已完成 |
| 跳过的环节 | 无 | **跳过 §2.6 逆向物流全节**、跳过 §2.7 的到仓验货 |
| 是否产生退货运单 | 是（运营线下预约面单并登记） | **否**，不生成退货运单、不注册轨迹 |
| 是否产生验货记录 | 是 | **否**，无实物可验 |
| 判责表单构成 | 判责结论 + 责任归属 + 退货扣减 + 瑕疵照片（详见 §2.7.3） | **责任归属 + 退货扣减**两项，**无判责结论、无瑕疵照片** |
| 责任归属判定时点 | 判责环节 | 判责环节（**与分支 A 相同**，审核环节一律不判） |
| 退货扣减预填值 | 建单时冻结的**政策快照**里的退货服务费金额 | **预填为空**（不给默认值），由运营手填 |
| 申请时是否告知退货服务费 | 是 | **否**（服务费是为退货物流成本收的，货没到就没有这笔成本） |
| 「不可退货」政策约束 | 生效 | **不生效**（货未收到时该约束不适用；否则 Final Sale 商品一旦丢件，买家钱货两空） |
| 共用的旁支 | 驳回回环（§2.5.4）、买家撤销（§2.9.2）、运营关闭（§2.9.3） | 同左，且运营关闭在本分支只有「待审核」一个开放状态 |

**⚠ 分支 B 与 §2.7.6「退回途中丢件」是两件事，入口条件相反，不要混用**：分支 B 是**正向物流**出问题、买家从没拿到货，审核通过后直接进待判责，全程没有寄回动作；退回途中丢件是**逆向物流**出问题、买家已交寄、货在寄回平台的路上丢了，单据停在退货在途直接判责。

#### 2.4.8 操作流程

**主流程**

1. 买家在订单详情对某商品行点击申请售后。
2. 系统读取该商品行的发货签收状态与实付金额，并按「商品 → 品类 → 市场」匹配售后政策。
3. 系统按 §2.4.3 / §2.4.4 判定资格：未发货的不可申请；已签收的按时效窗口判定；未签收的绕过时效判定、随时可申请。
4. 买家勾选商品（可多件）、从原因码清单选**一条**原因码、按该原因码的举证要求上传举证、填写补充说明。
   - 原因码下拉是**一份平铺清单**，**没有「货已收到？」这道前置选择题**——分岔判据就是他选中的那条原因码本身。
5. 系统按 §2.4.6 判定本单走哪条分支：命中白名单 → 不寄回、**申请前不告知退货服务费**；未命中 → 走寄回、**申请前告知退货服务费**。
   - 告知的服务费 = 政策配置值，**不与原因码挂钩、不做豁免推算**；告知时须同时明确**最终金额以审核结果为准**（具体文案归 C 端需求）。
6. 买家提交申请。系统执行 §2.4.9 全部校验。
7. 校验通过后系统建单：
   - 售后类型 = 退货（本期唯一取值）；
   - **一单一行拆单**：一次勾选 N 件 → 拆成 N 张独立售后单，各自独立走完整流程；
   - 状态 = 待审核；
   - **同时冻结两份快照**（§2.4.10）。
8. C 端提交成功页告知「已提交成功」；**本环节不发任何邮件**（买家刚点完提交、人还在页面上，邮件是多余触达）。第一封邮件出现在审核环节（§2.5）。
9. 单据进入待审核，等待运营审核。

**分支 1：已签收 / 未签收**（两条独立判定列）

- 未签收 → 时效不计时、绕过时效窗口判定，随时可申请；
- 已签收 → 时效自签收时点起算，落入「仍在时效窗口内？」判定；超期的 C 端不可申请。
- 两条路在「C 端展示可申请清单与时效状态」处汇合。

**分支 2：超期人工特批建单（运营端，不走 C 端）**

1. 运营在售后工单列表点击「超期特批建单」，输入订单号。
2. 选择要发起售后的商品行（**可多选**）、选择售后类型与售后原因、填写特批原因备注。
3. **特批只豁免时效判定这一条**，其余建单拦截条件（§2.4.5 ①②）一律照常成立、特批不能绕过。命中的商品行在选择时即被标记为不可提交，并给出具体原因（如「已有进行中的售后单 AS…（退货在途）」「该商品行已退成钱 —— 售后单 AS… 已完成」）。
4. 建单成功后，**特批标记与特批原因随单留痕**。
5. 特批建成的单与 C 端提交的单**走同一条流程**，无差别。

#### 2.4.9 校验规则

| # | 校验项 | 规则 | 校验时机 | 不通过的处理 |
|---|---|---|---|---|
| 1 | 发货状态 | 该商品行必须已发货 | 进入申请入口时 | 不展示售后入口；引导至订单取消 / 发货前退款 |
| 2 | 互斥占用 | 该商品行不得存在非终态售后单 | 进入申请入口时 + 提交时 | 不可重复申请，提示已有在途单 |
| 3 | 已退成钱 | 该商品行不得存在已完成的售后单 | 进入申请入口时 + 提交时 | 不可申请（该商品行的钱已经退给买家） |
| 4 | 时效窗口 | 已签收的必须仍在时效窗口内；未签收的不判本项 | 进入申请入口时 | 超期 → C 端不可申请，仅可走运营超期特批 |
| 5 | 原因码有效性 | 必须选中一条**启用中**的原因码，且只能选一条 | 提交时 | 阻断提交 |
| 6 | 必传举证 | 选中原因码要求必传举证时，举证不得为空 | 提交时 | 阻断提交，退回补充举证 |
| 7 | 是否支持退货 | **需寄回的单**：该商品行命中的政策必须支持退货；**不需寄回的单不校验本项** | 提交时（在分支判定之后） | 阻断提交 |
| 8 | 政策命中 | 必须命中一条启用中的政策。按**商品 → 品类 → 全市场**三级**依次校验、命中即停** | 申请入口 + 提交时 | **三级均未命中 → 提示买家联系客服**：不建单，且**不落任何默认政策、不判"不可申请"**。提示语要求买家联系客服处理（英文源文案由 C 端《售后列表详情》需求定义）。该情形属运营未配全市场级兜底政策，出口是人工介入 |

#### 2.4.10 建单时冻结的两个快照

建单时对**命中的整条政策**与**买家选中的整条原因码**各留一份快照，**整条留档、不逐字段补**。两者是同一套机制、同一个时点（建单即冻结），**开发不要只做政策那一份**。

| 快照 | 锁的是什么 | 消费方 | 不冻结的后果 |
|---|---|---|---|
| 政策快照 | 建单当时命中的整条售后政策（含时效天数、退货服务费金额、退货地址、是否支持退货等） | 退货扣减的预填值取数源（唯一）、退货地址下发、金额口径 | 运营改政策会**追溯改掉在途单**：关单时点被改（关单不可恢复）、邮件已告知的退货地址与系统新值对不上 |
| 原因码快照 | 建单当时买家选中的整条原因码（含 code 与展示文案） | **流程分岔的判定依据**、运营端与 C 端的原因展示 | 一张已进到「待判责」的未收到货单，会因字典被改而变成「要寄回」，但它早已跳过待寄回、回不去，**状态机就此卡死** |

**取数约束（给开发）**

- 判断一单要不要走寄回，**只读本单原因码快照里的 code**，**不实时回查原因码字典**，也不看售后类型（类型本期恒为「退货」，区分不出分支）。字典只在建单那一刻被读一次。
- 运营端与 C 端展示的原因文案，同样取快照——字典改了措辞，历史单仍显示建单当时的那一份。
- 原因码字典的事后调整（改展示名 / 改排序 / 停用某条普通原因）**不影响在途单**，已建单据一律按建单时的判定走完。
- 顺带收益：原因码展示文案将来改写或做多语言，历史单据凭快照仍能还原当时给买家看的说法，不必回改历史数据。
- **驳回后买家重新提交时，两份快照的处理相反**，详见 §2.5.6。

#### 2.4.11 其他数据口径

- **买家邮箱不进售后表、不做快照**：售后单只记录申请人，邮箱在需要时实时关联用户账户取（买家改了邮箱，后续邮件就该发到新地址）。运营端按买家邮箱搜工单时同样实时关联取数。
- **币种不冗余在售后单上**：售后是同一笔交易的逆向，币种必然继承订单，仅在退款方案上保留一个用于与支付域对账。
- **所属市场（已定）**：订单域目前无 market 维度，**本期由买家信息判定售后单所属市场**——该判定方式已确认成立、可支撑本期开发，不阻塞。订单域补 market 维度的排期未定，补齐后售后侧可改为直接取订单上的 market，属后续优化（缺口已记入订单域待优化清单）。

#### 2.4.12 异常处理

| 场景 | 处理 |
|---|---|
| 提交时并发：两次提交打到同一商品行 | 结果要求：同一商品行在任一时刻**只允许存在一张非终态售后单**，并发下不得建出第二张。实现方式由技术方案定 |
| 举证上传失败 | 提交被阻断，允许重新上传后再提交 |
| 政策在买家填写过程中被运营改动 | 以**提交建单那一刻**读到的政策为准并冻结进快照；已建单据不受后续改动影响 |
| 原因码在买家填写过程中被停用 | 提交时按校验规则 5 阻断，买家需改选其他原因码 |
| 超期特批时商品行命中拦截条件①或② | 该商品行在多选下拉里**置灰、不可选中**，被拦原因直接标在选项上；**运营选不进去**，因此不再有「选中后报错 + 提交置灰」这一段（见 §2.1.3（6）） |

#### 2.4.13 UI 关联

- 运营端原型 v16-antd：**售后工单列表页**（超期特批建单入口、列表「原因」列取原因码快照）、**售后单详情页**（基本信息模块、建单快照弹窗）、**超期特批建单弹窗**、**售后原因码配置页**（白名单行禁用停用 / 删除入口）、**售后政策配置页**。
- C 端申请页的页面元素、举证张数 / 格式 / 大小、时效倒计时文案等**不在本 PRD 范围**，归《售后列表详情》C 端需求。

### 2.5 审核

> 对应系统流程图 V2.3 **段②「运营审核」** + **段⑧「审核驳回与买家重新提交」**。

#### 2.5.1 功能描述

运营在售后工单台对待审核单给出审核结论。审核只做三件事：**定结论（通过 / 驳回）、写意见或驳回原因、推进状态**。审核有两个出口——通过后按原因码快照分岔到待寄回或待判责；驳回后单据**回到（保持）待审核**等买家修改，是一条**回环**而不是终态。

**⚠ 审核环节不判定责任归属。** 不论买家有没有收到货，责任归属一律留到判责环节（§2.7.7）。运营端审核弹窗**不设责任归属控件**，两条分支都没有。理由：原因码只说「为什么」，审核时拿不到判责依据；未收到货的单同样要等线下向承运商核实的结果，审核当场也定不了。

#### 2.5.2 前置条件

- 售后单状态 = 待审核。
- 运营已查看原因码、买家举证、订单商品行，并**对照单据上的政策快照**核对政策口径（不看政策的当前值）。

#### 2.5.3 操作流程（主流程：审核通过）

1. 运营在工单列表或详情页打开审核弹窗。弹窗上半区为只读核对区（售后单号、售后类型、售后原因、买家说明、**历次审核记录**），下半区为填写区。
2. 材料不齐无法判定时，运营**线下联系买家补材料**（系统内不设「补材料」中间状态）。
3. 运营选择审核结论 = 通过，可填写「审核意见」（仅内部，选填）。
4. 提交后：
   - 系统写入**一条审核记录**（结论、审核意见、审核人、审核时间）；
   - **固定发出一封「审核通过」邮件**给买家；
   - 系统按 §2.4.6 判定分岔：原因码快照 ∉ 未收到货白名单 → 状态 = **待寄回**（转 §2.6）；∈ 白名单 → 状态 = **待判责**（转 §2.7.6 分支 C）。
5. 「审核通过」邮件与 §2.6 的「退货运单号与退货地址」邮件**不合并、各发一封**：两者之间隔着运营线下向承运商预约面单这个人工动作，间隔时间较长——买家要先知道「已通过」，再等「怎么寄」。合并会让买家在审核通过之后长时间收不到任何通知。

#### 2.5.4 分支流程：审核驳回与买家重新提交（回环）

1. 运营选择审核结论 = 驳回。此时**两个文本框同时出现**：「驳回原因」（必填）与「审核意见」（选填）。
2. 提交后：
   - 系统写入一条审核记录（结论 = 驳回、驳回原因、审核意见、审核人、审核时间）；
   - **售后单状态仍为待审核，不进入任何终态**；
   - **固定发出一封「审核驳回」邮件**：正文 = 告知被驳回 + **驳回原因原文** + 引导去 C 端修改后重新提交；
   - C 端**只展示驳回原因**，并开放修改入口。
3. 买家修改后重新提交，系统记录**买家最近一次重新提交时间**。
4. 单据回到审核环节重新审核，**可多次驳回、多次重新提交，本期不设次数上限**；反复无效提交由运营在审核环节继续驳回来拦，不靠系统硬性封禁。
5. 买家长期不修改也不撤销时的出口 = **运营手动关闭售后单**（§2.9.3）——这正是「待审核」被纳入运营关单开放状态的原因。

**驳回的几条硬口径**

| 口径 | 内容 |
|---|---|
| 驳回不是状态 | 状态枚举里**没有「已驳回」**。单据从提交到定案之间只有「待审核」这一个待人工处理的状态 |
| 驳回邮件**固定发送、不设开关** | 驳回的语义是「要求买家去改申请」；不通知他，C 端只显示「审核中」，买家不知道要动手，单据就断在这里。**开发不要照运营关单的勾选框给驳回也做一个开关**（两者口径刚好相反，见 §2.9.3） |
| 驳回不写责任归属 | 驳回 = 未受理，无责任可分 |
| 互斥占用不释放 | 单据仍是非终态，该商品行在驳回期间依然被占用，买家不能另开一张新单 |
| 驳回不重置时效 | 也不对重新提交设时效卡点；本期不做任何超时自动关单 |
| 历次记录互不覆盖 | 每轮审核（通过或驳回）各写一条审核记录，历次驳回原因完整可查。审核弹窗里直接列全，运营再审时要看得到前几次已经要求过买家补什么 |

#### 2.5.5 驳回原因与审核意见：两个字段，可见性相反，不可合并

| 字段 | 对买家可见性 | 进邮件 | 写值时机 | 用途 |
|---|---|---|---|---|
| **驳回原因** | **对买家可见** | **是**，原样作为驳回邮件正文 | **仅驳回时**写值，且**必填** | 写清要买家补什么、怎么改；运营要按「给买家看的话」写 |
| **审核意见** | **绝不外露** | **否** | 通过与驳回**均可写**，选填 | 记内部判断（如「该买家本月第 2 次以同一原因发起，举证疑似二次拍摄」） |

**⚠ 这是对外输出的安全边界，不是页面展示偏好。** 系统在拼装任何**买家可见内容**（驳回邮件正文 / C 端页面 / 买家可见时间线）时，**绝不能把审核意见带进去**——这是硬性输出约束，不能靠运营自律少写。审核意见与验货环节的「判责说明」属同一类约束（§2.7.9）。

**为什么必须拆成两个字段**：驳回原因原样进买家邮箱之后，运营就没地方写内部判断了，两个字段各担一头。

#### 2.5.6 重新提交时两份快照的处理（相反，不要一把刷新或一把不刷）

| 快照 | 重新提交时 | 判据与理由 |
|---|---|---|
| 政策快照 | **不刷新** | 重新提交不重新匹配政策，金额口径按建单时冻结的走。否则运营改了政策，就能靠「驳回 → 买家重提」把新政策绕进在途单，快照就失去意义 |
| 原因码快照 | **按买家新选中的那条刷新** | 买家修改申请时可以改售后原因（例如从「描述不符」改成「包裹为空」）；不刷新等于买家改了没生效，流程分支仍按老快照走、系统仍然让他寄货 |

**统一判据**：快照锁的是**运营侧的配置变动**（政策与原因码字典的事后调整），**不锁买家自己的选择**——买家改原因码是他的主动行为，理应生效。

**⚠ 原因码可改意味着流程分支可能翻转**（从需寄回翻到不需寄回，或反向）。以**最后一次审核通过时**的原因码快照所属分组为准。

#### 2.5.7 校验规则

| # | 校验项 | 规则 | 校验时机 | 不通过的处理 |
|---|---|---|---|---|
| 1 | 审核入口开放状态 | 仅「待审核」状态展示审核入口 | 进入时 | 其他状态不展示该操作 |
| 2 | 审核结论 | 必选，二选一（通过 / 驳回） | 提交时 | 阻断提交 |
| 3 | 驳回原因 | 结论 = 驳回时**必填** | 提交时 | 阻断提交 |
| 4 | 审核意见 | 选填；通过与驳回均可写 | — | — |
| 5 | 责任归属 | **审核弹窗不提供该控件**（不是选填，是没有） | — | — |
| 6 | 买家重新提交的可改范围 | 只允许改**原因码 / 举证附件 / 文字说明**三项；**商品行不可改**（要换商品行只能撤销后重新发起）；售后类型本期恒为「退货」，无可改之处 | 买家提交时 | 阻断提交 |
| 7 | 重新提交的必传举证 | 选中原因码要求必传举证时，举证不得为空 | 买家提交时 | 阻断提交（未补齐不可提交） |

#### 2.5.8 审核相关的派生口径（不冗余字段）

| 派生口径 | 定义 | 说明 |
|---|---|---|
| 「这单被驳回过」 | 该单审核记录中结论为驳回的**条数 ≥ 1** | 主表**不冗余驳回次数字段**——它能从审核记录推出来，冗余就会出现两份不一致的真相 |
| 「当前正等待买家修改」 | 状态 = 待审核 **且** 最近一条审核记录结论为驳回 **且** 买家最近一次重新提交时间为空或早于该条记录的审核时间 | 即「最近一次驳回之后买家还没再提交过」。买家重新提交后该条件随即不成立，C 端不再提示「请修改」、转为「审核中」，直到运营再审写入新记录——所以「驳回」不会一直提示下去 |
| 「最近审核时间」 | 最近一条审核记录的审核时间 | 主表不保留审核结论、审核意见、审核时间字段 |

**为什么由业务记录而非日志承载**：历次驳回原因是业务事实（拒付争议抗辩需证明平台明确告知过买家第几次该补什么材料）。

#### 2.5.9 异常处理

| 场景 | 处理 |
|---|---|
| 材料不齐无法判定 | 线下联系买家补材料，系统不设中间状态；也可直接驳回并在驳回原因里写明要补什么 |
| 买家对审核结论有异议 | 本期**无 C 端申诉交互**，走线下客服；**协商结果只能通过线下退补款处理，系统内不提供判责后的金额修改入口**——判责提交即打款、金额当场定案，事后改单只会造出「单据金额 ≠ 已打款金额」的对账死账（见 §2.7.1 / §2.7.12） |
| 审核提交时单据状态已被改变（如买家已撤销） | 结果要求：审核结论只能落在「待审核」的单上；状态已变更的须拒绝本次提交并提示当前状态。实现方式由技术方案定 |
| 驳回邮件发送失败 | 邮件发送结果需可查（见邮件通知章节的发送记录口径）；邮件失败不改变单据状态 |

#### 2.5.10 UI 关联

- 运营端原型 v16-antd：**审核弹窗**（列表页行操作「审核」与详情页页头「审核」按钮是同一个操作的两个入口，共用同一份实现）、**售后单详情页**（页头「已驳回 N 次 · 等买家修改 / 买家已重新提交，等运营审核」标记）、**售后工单列表页**（「待审核」Tab 与 KPI 卡）。
- C 端驳回后的修改页元素**不在本 PRD 范围**。

### 2.6 逆向物流

> 对应系统流程图 V2.3 **段③「面单与交寄」**。**本节只适用于需寄回分支**（§2.4.7 分支 A）；不需寄回的单整节跳过。

#### 2.6.1 功能描述

审核通过后，运营**线下向承运商预约取回面单**，取得退货运单号后回到系统登记，系统据此向物流信息服务注册该退货运单并订阅轨迹，同时把运单号与退货地址通过邮件与 C 端双渠道告知买家。买家持运单号到承运商网点交寄，揽收轨迹产生后单据自动推进到「退货在途」。

**⚠ 时序与常规相反**：本模块是**运营先取得并登记运单号、再由买家去交寄**（面单线下预约，物流信息服务明列「面单生成不在本期范围」，售后同样不做 → 线下是本期唯一可行路径），而不是常见的「买家自寄后回填单号」。

#### 2.6.2 前置条件

- 售后单状态 = 待寄回。
- 该单为需寄回分支。
- 已有建单时冻结的政策快照（退货地址取自快照）。

#### 2.6.3 退货地址

- 退货地址按 **market 独立配置**，随售后政策下发（美国站与香港站各自配置）。
- 售后单上的退货地址取**建单时冻结的政策快照**，运营在运单登记弹窗内**只读、不可修改**。
- 存的是**完整地址文本快照**而不是地址库引用——它是仓库地址、要直接发给买家看，且需随 market 配。
- **香港站退货仓的具体地址不影响开发**：地址是**运营在售后政策里配置的自由文本**，不是代码里的常量，**开发按"可配置的地址文本"实现即可，不需要等地址定下来**。方案级已定"香港站的退货退回香港"，具体地址待仓储侧给出后由运营在后台填入；运营端原型里的地址为示例值，不构成需求定义。

#### 2.6.4 操作流程（主流程）

1. 运营线下向承运商预约取回面单，承运商出具面单并给出退货运单号。
2. 运营在售后单上登记**退货运单号**与**承运商**（承运商从字典中选，**存编码不存展示名**；展示名由承运商字典映射得出，承运商改名或做多语言展示时不必回改历史数据）。
3. 系统向物流信息服务注册该退货运单并订阅轨迹，**注册时业务单号传订单号**，复用物流服务「1 订单号 = N 运单」模型；售后单与该退货运单建立关联，后续轨迹由物流服务推送。
   - **多件同包裹寄回时，多张售后单共用一个退货运单号**，不新造退货包裹实体。登记方式、轨迹推进范围、邮件封数与地址口径见 **§2.6.5**。
4. 系统**固定发出一封「退货运单号与退货地址」邮件**给买家；C 端同步展示运单号与退货地址（**双渠道并行，买家不必等邮件**）。
5. 买家持运单号到承运商网点交寄，网点揽收。
6. 物流服务上报揽收轨迹并推送「已揽收」通知。
7. 系统将售后单状态推进为**退货在途**；**退货运单登记值此后只读**。

#### 2.6.5 多张售后单共用一个退货运单号

**这是 V1 的主场景，不是边角情况**：一单一行 + C 端可一次勾选多件 → 一个订单常拆出 N 张售后单，买家把 N 件装同一个箱子、用**同一张面单**寄回。本节把四件事写死，开发不要各自发挥。

**（1）怎么登记：逐单登记，无批量入口**

- 运营在**每一张**售后单上**分别打开回填退货运单弹窗、各登记一次**同一个退货运单号与承运商。
- **本期不做批量登记入口**——不做「一次登记落到 N 张单」的批量操作，回填弹窗只面向单张售后单。
- 因此同一个运单号会出现在多张售后单的登记值上，这是**预期结果**，不是脏数据。

**（2）一条轨迹推进哪几张单：按实际登记该运单号的单，全部一起推进**

- 一条轨迹事件（已揽收 / 已送达 / 追踪异常）**推进全部登记了该运单号的售后单**，不是只推第一张、也不是只推某一张。
  - 已揽收 → 这些单**一起**从待寄回推进到退货在途；
  - 已送达 → 这些单**一起**推进到待判责；
  - 追踪异常 → 这些单**一起**被标记并推送到运营工单台。
- **判据是「这张单上登记了这个运单号」**，不是「这些单属于同一个订单」——同订单但没登记该运单号的单不受影响。
- **少登记一张的后果（必须让运营看得见）**：只登记了 2 张、第 3 张没登记时，第 3 张**不会跟着推进**，会停在待寄回。这是登记动作缺失，靠运营在工单台发现后补登记该运单号即可，系统不代为推断。

**（3）邮件发几封：按运单号去重，只发一封**

- 共用同一个退货运单号的多张售后单，**只发一封**「退货运单号与退货地址」邮件（第 3 封），**不按单发 N 封内容相同的邮件**。
- 该封正文本身就写着"把这几件装同一个箱子、用同一个运单号寄回"，逐单发等于把同一句话重复发 N 遍。
- 触发口径见 §2.10.1 第 3 封。

**（4）退货地址冲突：不会发生，由运营在线下保证**

- **不同退货地址的售后单不会共用同一个退货运单号**：退货地址随各单的政策快照下发，运营在**线下预约面单**时，地址不同就会**预约不同的面单**，不存在"两个地址共用一张面单"的情形。
- **由运营在线下作业时保证，系统不做校验**——本期不校验共用运单号的各单退货地址是否一致，也不做冲突拦截或提示。

#### 2.6.6 登记值与轨迹：两个来源，各司其职

| 项 | 来源 | 用途 | 是否实时 |
|---|---|---|---|
| 退货运单号、承运商（登记值） | 运营在待寄回阶段手动登记，**落在售后单上** | 售后单自身可读、展示、对账、线下追查；不依赖实时调用物流服务 | **否，是留痕值**——记录的是「当时登记了什么」 |
| 轨迹与实时物流状态（已揽收 / 已送达 / 追踪异常） | **只从物流信息服务取**，本域不冗余 | 状态推进、到仓判定、异常识别 | 是 |

**⚠ 脏数据口径（必须写给开发）**：运单号若在物流侧被修正、或中途改换承运商切了追踪平台，**本域登记值不自动同步**。**登记值与物流侧当前值不一致时，一律以物流侧为准**；运营端须能识别出这种不一致并给出提示，需要实时状态时看轨迹，**不要拿登记值当权威源**。

#### 2.6.7 到仓时点

**以物流信息服务的「已送达」作为到仓时点的唯一来源。** 系统据此自动把状态推进为「待判责」，**无人工签收登记，仓库不碰系统**。

#### 2.6.8 校验规则

| # | 校验项 | 规则 | 校验时机 | 不通过的处理 |
|---|---|---|---|---|
| 1 | 登记入口开放状态 | **只在「待寄回」阶段开放**。进入「退货在途」后运营端不再提供运单登记 / 修改入口 | 进入时 | 其他状态不展示该操作 |
| 2 | 退货运单号 | 必填 | 提交时 | 阻断提交 |
| 3 | 承运商 | 必填，从承运商字典中选择，落库为编码 | 提交时 | 阻断提交 |
| 4 | 退货地址 | 取政策快照，**本弹窗内只读** | — | — |
| 5 | 登记值修改 | 待寄回阶段可重新登记覆盖；**退货在途之后不可修改** | — | 在途阶段没有任何正向流程需要改运单，要改只能先关单重来 |

#### 2.6.9 本期不做（写明以免被当成漏项）

- **不做「交寄时限」与「超时关单」判定**：不算交寄截止时点、不发关单前提醒、不做揽收轨迹超时判定。交寄时限天数在数据模型中字段预留但**不参与流程**，本域既无写入方也无消费方。
- 买家中途放弃 / 一直不寄货的出口 = **运营手动关闭售后单**（§2.9.3），是人工动作、不是系统按时限自动判定。
- 后期若要开超时关单，需同时补：政策配置项 + 交寄截止时点计算 + 关单前提醒 + 到期关单机制，不是加一个字段就够。

#### 2.6.10 异常处理

| 场景 | 处理 |
|---|---|
| 运营登记的运单号有误（尚在待寄回） | 重新登记覆盖即可；覆盖后重新注册追踪并重新发出运单号邮件 |
| 运单号在物流侧被修正 / 中途换承运商 | 本域登记值不自动同步；轨迹与实时状态以物流侧为准，运营端提示两者不一致 |
| 注册轨迹订阅失败 | 结果要求：登记动作与轨迹订阅必须**同时成立**；订阅未成功时不得让单据表现为「已订阅」，运营须能看到并重试。实现方式由技术方案定 |
| 轨迹长时间无更新 / 承运商判定包裹丢失 | 转 §2.7.6 分支 B「退回途中丢件」 |
| 买家长期不交寄 | 运营手动关闭售后单（§2.9.3） |

#### 2.6.11 UI 关联

- 运营端原型 v16-antd：**回填退货运单弹窗**（列表页行操作「运单」与详情页页头「回填运单」共用同一份实现）、**售后单详情页**「物流信息」模块（登记值 + 轨迹 + 不一致提示）。
- C 端退货地址与运单号的展示元素**不在本 PRD 范围**。

### 2.7 验货与判责

> 对应系统流程图 V2.3 **段④「到仓 · 判责」** + **段⑤「判责异常处置」** + **段⑦「退回途中丢件」**，并含段⑥不需寄回分支的判责形态。

#### 2.7.1 功能描述

**判责是一个动作，不是两步。** 运营在同一张表单里一次性录入**验货结论 + 责任归属 + 退货扣减金额**（含瑕疵照片）并提交；提交即定案退款金额、直接进入退款执行（§2.8），单据状态推进为「退款中」。**判责与退款之间没有第二个人工环节，也没有「待退款」这个等运营再点一次的状态。**

> **⛔ 判责是终局动作：提交即定案金额并调支付域发起退款，系统不提供任何修改入口。运营必须在提交前核对清楚。**
>
> **理由**：提交的那一刻钱就已经发出去了，事后改判责结论**不会把钱追回来**——改了只会让单据上的结论与实际已打出的金额对不上，制造对账死账。所以这里没有「先保存、再确认」的两段式，也没有反悔窗口。
>
> **「退款中」不是给运营留的修改窗口**：它只是「接口已调用、到支付域回调成功之间有时间差」而产生的等待态（见 §2.4.1 状态机）。金额填错、结论选错，都只能走线下处理，系统内无补救动作。

拆成「先录验货结论 → 再单独发起退款方案」两步，会让同一个人把同一批信息填两遍、来回切页面——实际作业时运营就是一边看货一边定金额的。

**⚠ 验货作业在线下当地仓完成，系统不承接作业过程。** 线下仓收货 → 拆包 → 拍照 → 验瑕疵，结果回传在线表格；**系统边界从「运营核对表格后录入」开始**。本期不对接在线表格（人工看着填），但**录入表单需按表格字段设计，以便后续对接不重构**。

**⚠ 责任判定统一在本环节落定**，两条流程分支都不在审核环节判（§2.5.1）。**但责任归属本期是纯留痕结论、不驱动任何金额计算**——这一条与概览原意不同，**开发务必先读 §2.7.7 再实现判责表单与金额逻辑**。

#### 2.7.2 前置条件与入口开放状态

判责入口开放在**两个状态**：

| 入口状态 | 适用场景 | 表单差异 |
|---|---|---|
| **待判责** | 货已到仓（走寄回分支），或货压根不会到仓（不需寄回分支） | 走寄回的：全项录入（含瑕疵照片）；不需寄回的：无判责结论、无瑕疵照片 |
| **退货在途** | 货已不可能到仓（退回途中丢件 / 灭失），**不等到仓直接判责** | 有判责结论（固定为「退回途中丢件」），**无瑕疵照片**（货还没到、拿不到照片） |

**不开放**：待审核、待寄回、退款中、已完成、已关闭。

**⚠ 判责入口是「一次性入口」，不是「可反复进入的编辑入口」**：单据一旦提交过判责就已离开上述两个状态（进入退款中或已关闭），因此**判责入口自然不再出现**。**判责一经提交即为定案，系统不提供任何形式的更改、重判或撤回**——不在列表行操作提供、不在详情页页头提供、不在任何状态下提供。

#### 2.7.3 判责表单构成（三项 + 瑕疵照片，同一张表单一次提交）

| # | 表单项 | 控件 | 必填 | 说明 |
|---|---|---|---|---|
| ① | 判责结论（验货结论） | 单选，字段全集 7 个取值；**界面可选范围按入口状态收敛，以 §2.7.4「入口状态 × 可选结论」矩阵为准** | 是（**仅需寄回的单出该项**） | 不需寄回的单没有实物可验，**不出该项** |
| ② | 责任归属 | 单选：平台责任 / 买家责任（**二分类，无「物流责任」**） | 是 | 两条分支都出。判责环节判定、**只判一次**、**不联动任何金额**（详见 §2.7.7） |
| ③ | 退货扣减金额 | 金额输入 | **否**（留空按 0.00 计，出提示不阻断） | 运营手填的**一个总额**（退货服务费 + 验货扣款），详见 §2.7.8 |
| ④ | 判责说明 | 多行文本 | **否**（判责结论 = 退回途中丢件时**必填**，见 §2.7.10 校验 5） | **内部字段，绝不外露 C 端**；选「退回途中丢件」时必须写明认定依据 |
| ⑤ | 瑕疵照片 | 图片上传 | 否 | **仅「待判责 + 需寄回」这一种形态出该项**；随单上传留档 |
| ⑥ | 异常结论处理出口 | 单选，三选一 | 判责结论为异常结论时**必选** | 见 §2.7.6 分支 A |
| ⑦ | 退款方案（退款基准 / 退货扣减 / 最终退款金额） | 见 §2.8.2 | — | 与本表单同一次提交 |

**⚠ 没有独立的「验货扣减金额 / 扣减原因」字段**：表单上只有一个金额输入框。成色下降 / 缺配件照样扣钱，但**不单列一项**，并进「退货扣减」由运营一并填入。

**⚠ 举证必须跟单走且带审计**——扣款结论可能被买家质疑，照片不能只留在外部表格。

#### 2.7.4 判责结论（验货结论）枚举：共 7 个取值

**本枚举以运营端原型 v16 为准，共 7 条，一条都不能少。** ⚠ ER v2.0 只写到「验货结论（含『退回途中丢件』结论值）」、**没有落完整清单**，以本表为准。

| 枚举值 | 含义 | 触发时机 | 后续走向 |
|---|---|---|---|
| 与申请一致 | 退回件与买家申请描述一致 | 「待判责」入口（需寄回分支），运营核对线下验货结果后选择 | 直接进入退款执行；通常只扣退货服务费（即预填的政策快照值） |
| 附件缺失 | 缺少配件、附件不全 | 同上 | 直接进入退款执行；运营可在服务费之上加扣（加扣金额并进同一个「退货扣减」框） |
| 成色下降 | 成色低于订单成色快照 | 同上 | 直接进入退款执行；运营可在服务费之上加扣 |
| **退回件与订单不符** | 寄回的不是本单商品 | 同上 | **异常结论 → 转人工核实**（§2.7.6 分支 A，对应流程图**段⑤**）：单据停留在待判责、不发起退款，运营线下核实后在同一次提交内三选一出口 |
| **空包或无实物** | 包裹内无商品 | 同上 | **异常结论 → 转人工核实**（§2.7.6 分支 A，对应流程图**段⑤**）：同上，三个出口（全额退 / 部分退 / 不退并关闭） |
| 退回途中破损 | 商品在寄回途中损坏 | 同上 | 直接进入退款执行；运营可在服务费之上加扣 |
| **退回途中丢件** | 包裹在寄回途中丢失 / 灭失 | **「退货在途」入口**（不在到仓分支出现）：物流服务给出追踪异常通知、运营线下向承运商核实为丢失 / 灭失后选择 | 转 §2.7.6 分支 B（对应流程图**段⑦**）：**不经过「待判责」**，在退货在途状态直接判责后进退款中；选中时**必填丢件认定依据** |

**⚠ 第 7 个取值容易被漏**：货根本没到仓、无货可验，单据停在「退货在途」直接判责，因此它**不会在到仓分支的表单里出现**——但它在数据层就是本字段的一个取值，枚举定义必须含它。**到仓分支实际可选 6 条，字段全集是 7 条。**

**「入口状态 × 可选结论」矩阵（硬性，本表是判责结论下拉取值范围的唯一权威）**

字段全集 7 条 ≠ 任一入口下的可选项。**下拉必须按入口状态过滤，不得一律渲染 7 条**：

| 入口状态 | 货在哪 | 可选结论 | 条数 | 控件形态 |
|---|---|---|---|---|
| **待判责**（需寄回的单，货已到仓） | 货在平台仓内，可验 | 与申请一致 · 附件缺失 · 成色下降 · 退回件与订单不符 · 空包或无实物 · 退回途中破损 | **6 条** | 下拉单选，**排除「退回途中丢件」**——货已到仓，丢件在事实上不成立 |
| **退货在途**（货不可能到仓） | 货已丢失 / 灭失，无实物 | **退回途中丢件** | **1 条** | **锁定为该值、不可改选**（只读展示或单选项下拉），运营无从选其他结论 |
| **待判责**（不需寄回的单） | 无实物 | **不出本字段**（§2.7.6 分支 C） | 0 | 表单上没有判责结论项 |

**两条反向后果（说明为什么必须过滤，不是「渲染全量更省事」）**：

- 待判责若能选「退回途中丢件」→ 触发「丢件处理进展」邮件 + 责任归属默认带出平台责任，而货明明就在仓里；
- 退货在途若能选「与申请一致」等验货类结论 → **在根本没见到货的情况下出具验货结论并立即打款**。

**⚠ 数据层枚举仍为 7 条，收窄的是界面可选范围**，不要为了过滤去删枚举值。

**⚠ 不需寄回分支（§2.7.6 分支 C）没有本字段**：无实物可验，判责表单上不出现判责结论项。

**⚠ 加扣不是自动计算**：上述取值**没有一条驱动系统自动算钱**，扣多少一律由运营填在同一个金额框里（§2.7.8）。

#### 2.7.5 操作流程（主流程：到仓正常判责）

1. 包裹在途，物流服务轨迹推进至**已送达**，主动通知售后域。
2. 系统自动推进状态 = **待判责**（无人工签收登记）。
3. 线下仓收货 → 拆包 → 拍照 → 验瑕疵，结果回传在线表格（本期不对接）。
4. 运营核对在线表格后打开判责弹窗，**一次性录入并提交判责表单**（§2.7.3）。
5. 判责结论落在「与申请一致 / 附件缺失 / 成色下降 / 退回途中破损」四个取值之一时，继续主线：
   - 系统记录判责结论、责任归属与退款方案；
   - 进入 §2.8 退款执行，状态 = **退款中**。
6. 判责结论落在「退回件与订单不符 / 空包或无实物」时 → 转 §2.7.6 分支 A。

**⚠ 到仓不发「平台已收到退货」邮件**——买家在物流轨迹上已能看到签收，重复触达无价值。
**⚠ 验货结果不单独发邮件**——它与退款完成的间隔太短（判完即算钱即发起退款），两封邮件会连着到达；已**合并为一封**，在退款完成时发出，内容含验货结果与退款金额明细（§2.8.4）。

#### 2.7.6 分支流程

**分支 A：异常结论 → 人工核实 → 三个出口**（对应段⑤）

1. 判责结论为「退回件与订单不符」或「空包或无实物」时，表单上出现「处理出口」必选项。
2. 单据**停留在待判责**、不发起退款（判责尚未定案，状态语义仍然成立）；**不新增独立状态**，也**不设「待人工处理」挂起态**——人工核实是线下动作，核实完再回系统录入即可。
3. 运营线下人工核实：联系买家、核对包裹称重与监控、承运商核查。
4. 核实后在**同一次提交内**三选一：

| 出口 | 动作 | 金额处理 | 结果状态 |
|---|---|---|---|
| ① 全额退款 | 按退款基准全额退还买家 | **不做退货扣减**（扣减锁定为 0） | 退款中 → 已完成 |
| ② 部分退款 | 退多少由运营在退款方案里手填并留档 | 运营手填实退金额与原因 | 退款中 → 已完成 |
| ③ **不退并关闭（拒退关单）** | **不退款、不产生退款单、不经过退款中** | 无 | **已关闭 · 关闭原因 = 拒退关单**（终态） |

5. **三个出口都必须经人工核实之后才走，系统不自动判定**；原型上不得把出口做成由验货结论自动预选。
6. 出口③的后续：
   - **不为拒退单独加状态枚举值**——落到「已关闭」，靠关闭原因 = 拒退关单与其他关闭来源区分。终态只有 2 个。
   - **同样释放该商品行的互斥占用**（互斥约束的是非终态单，进已关闭即为终态，占用必然解除）；与买家撤销、运营关闭是同一条规则，不是本出口的特例。
   - **允许买家在售后时效内重新申请**，按时效严格判定、与申请次数无关。业务把关仍在运营侧：重新申请的单照样要过审核，同一商品行反复空包提交会在审核环节被驳回，**不靠「禁止重申」来拦**。
   - **触发一封「拒退结果」邮件**：只告知处理结果（不予退款并关单）与退回件的**线下回寄安排**，**不写具体判责结论、不写任何内部判责表述**。拒退是买家钱货两空的重大结果，必须告知，但不外泄内部结论。
   - 货走**线下回寄**给买家，不进系统：本期不建拒退运单、不做回寄轨迹跟踪，系统只记录拒退结论与理由。
   - ⚠ **已知空缺**：本期买家侧看不到拒退理由（只见「不予退款 + 商品回寄」这个结果），客服需人工答复。

**分支 B：退回途中丢件**（对应段⑦，入口状态 = 退货在途）

1. 包裹在途中出现追踪异常：轨迹长时间无更新，或承运商判定包裹丢失 / 灭失；**判定依据是物流信息服务的追踪异常通知，不是买家自述**。
2. 系统标记运单异常并推送到运营工单台。
3. 运营**线下向承运商核实**包裹状态：
   - 确认仍可送达 → 回主流程等到仓；
   - 确认已丢失 / 灭失 → 继续第 4 步。
4. 运营在「退货在途」状态**直接打开判责表单**（不等到仓、不建验货记录、不经过待判责——货已经不可能到仓，卡着等到仓等于把单子挂死）。
5. 表单构成（三项，一次提交）：
   - ① 判责结论 = **退回途中丢件**——本分支**锁定为该值、不可改选**（按 §2.7.4「入口状态 × 可选结论」矩阵，退货在途入口只有这 1 条可选，验货类结论一律不出现）· **必填丢件原因说明**（承运商回复、轨迹停滞时长、线下核实经过），不能只勾一个选项就提交；
   - ② 责任归属：**默认平台责任 · 允许运营修改（非只读）**；
   - ③ 退货扣减：**预填为空**，运营手填（本分支不走验货，无验货扣款可并入，也没有产生退货物流成本）。
6. 提交即进入 §2.8 退款执行，状态 = 退款中。
7. **触发一封「丢件处理进展」邮件**，口径与常规退款告知一致，**只讲进展与金额**。
   ⚠ 邮件**不写「途中丢件按平台责任处理」这类表述**——责任归属是内部结论，对买家披露没有意义还容易被当成承诺。

**为什么责任归属默认平台责任但可改**：物流出问题属平台与物流商之间的事，对买家而言即平台责任，平台先足额赔付买家、再线下向物流商索赔。但实际会有买家伪造丢件的情况，把责任写死就没了退路——**默认值只是省事，不是规则**。

**分支 C：不需寄回分支的判责**（对应段⑥，入口状态 = 待判责）

1. 审核通过且原因码快照命中未收到货白名单的单，**不生成退货运单、不建验货记录**，直接进入待判责。
2. 判责表单只有**两项**：责任归属 + 退货扣减（**预填为空**）。**没有判责结论、没有瑕疵照片**（无实物可验）。
3. 责任归属**同样在本环节判定**，与走寄回的单是同一个落点。
4. **责任归属不由系统写死**：不存在「未收到货恒为平台责任」这条规则，也不存在「退货扣减自动豁免」，本期无任何自动豁免。
5. 提交即进入 §2.8 退款执行，状态 = 退款中。
6. 本分支**申请前不向买家告知退货服务费**（服务费是为退货物流成本收的，货没到就没有这笔成本），**但运营侧仍可按实际情况填写非 0 值**——是否收由人决定，系统不预设。

#### 2.7.7 责任归属：本期是纯留痕结论，不驱动任何金额

> **⚠ 本节是最容易被照着《业务架构与功能概览》原意误实现的一处，请逐条按本节实现，不要按概览实现。**

**三件事必须同时成立，缺一条实现就是错的：**

**第一，取值是二分类：平台责任 / 买家责任。** **不是**概览 A7 / §3.3 写的三分类——**本期不设「物流责任」**。物流出问题属平台与物流商之间的事，对买家而言即平台责任，平台先足额赔付买家、再线下向物流商索赔。物流原因由**原因码**承载：原因码记「**为什么**」，责任归属记「**谁承担**」，两者分工明确，不要把物流场景做成第三个责任取值。

**第二，责任归属不参与任何金额计算。** 概览 A7 / §3.3 写的是责任归属「驱动退货服务费豁免与验货扣减」——**本期实现没有这么做**。本期的实际口径是：

- **退货扣减（含退货服务费、含验货扣款）全部由运营手填**，系统**不计算、不分摊、不豁免**；
- 判了「平台责任」**不会**让系统自动把退货服务费置 0，也**不会**让扣减金额变成只读；平台责任要豁免服务费时，是**运营自己把金额填成 0**；
- 判了「买家责任」同样不触发任何自动加扣；
- 因此本期**没有**「默认责任方」「是否豁免服务费」这类字段，本域也不产生任何由责任驱动的金额逻辑。

**⛔ 明确不要实现的一条**：**「责任 = 平台 → 退货扣减自动置 0 / 自动豁免服务费 / 金额框置只读」这类联动，一处都不要做**——不在判责弹窗做、不在提交时做、不在后端算金额时做。这是照概览原意实现时最可能被写出来的逻辑，写了就与本期口径冲突。

**第三，丢件时的「平台责任」是默认值，不是自动判定。** 判责结论选中「退回途中丢件」时，判责弹窗把责任归属**默认带出「平台责任」**，但该控件**保持可编辑、不是只读**，运营可以改判买家责任。理由：实际会有买家伪造丢件的情况，把责任写死就没了退路——**默认值只是省事，不是规则**。除此之外**没有任何**由原因码、验货结论或流程分支自动带出责任归属的情形（不需寄回分支同样不预填，不存在「未收到货恒为平台责任」这条规则）。

**结论：责任归属本期是一条纯留痕的业务结论**，供事后统计、对账、与物流商索赔时取证使用；它**不影响**买家实际拿到多少钱。

**口径速查表**

| 项 | 口径 |
|---|---|
| 取值 | **二分类：平台责任 / 买家责任**。**不设「物流责任」**——物流出问题属平台与物流商之间的事，对买家而言即平台责任 |
| 与原因码的分工 | 原因码记「**为什么**」，责任归属记「**谁承担**」。原因码字典**没有默认责任方字段** |
| 判定时点 | **统一在判责环节**，两条流程分支一律如此；审核环节不提供录入入口 |
| 判定次数 | **只判一次，不存在改判 / 终判环节** |
| 是否预填 | 不预填、不自动带值。唯一例外：判责结论选中「退回途中丢件」时默认置为平台责任，**运营仍可改**（是弹窗默认值，不是自动带值） |
| 是否驱动金额 | **本期不驱动任何金额计算**，是一条纯留痕结论。原型与实现上**不得出现「责任 = 平台 → 退货扣减自动置 0 / 只读」这类联动** |
| 未录入时的展示 | 单据仍在流程中（待审核 / 待寄回 / 退货在途 / 待判责）→ 展示「判责时判定」；单据已到终态却从未判责（买家撤销 / 运营关闭）→ 展示「—」，**不写「尚未录入」**（会让运营以为这单还有一步没做） |

#### 2.7.8 退货扣减：本域唯一扣款科目

| 项 | 口径 |
|---|---|
| 定义 | 这一单**实际扣的总额**，**含退货服务费 + 验货发现的成色下降 / 缺配件扣款**。本域**不单列验货扣减科目** |
| 与政策里「退货服务费」的区别 | 政策里配的是**纯服务费**（market 级配置项，美国站现行 $15）；本项是**这一单实扣的总额**。两者名称刻意不同，指的不是同一个东西。**两端界面统一以「退货扣减 / Return deduction」指代本项** |
| 谁来填 | **运营手填**。系统**不自动计算、不按责任自动豁免、不按包裹分摊** |
| 预填值（走寄回分支） | 取**建单时冻结的政策快照**里的退货服务费金额（**唯一取数源**）。运营可改，改后以运营填写的金额为准；界面提供「恢复默认值」并在已改写时标出默认值是多少 |
| 预填值（不寄回 / 丢件分支） | **预填为空、不给默认值**（无退货动作、不产生退货物流成本，也无实物验货） |
| 未填怎么算 | **未填即按 0 计**，退款按全额基准照常执行到底。界面**只提示不阻断**（提示「提交后按 0 计，请确认这是本单的扣减意图」）。本域**不为该字段派生任何拦截或中断逻辑** |
| 与申请时告知值的关系 | 申请时告知的服务费与最终实扣之间**不设任何一致性约束**：不做偏离阈值二次确认，偏离多少都不改变流程走向 |
| 平台责任是否豁免 | 平台责任**可豁免**（运营把金额填 0 即可），但**由人决定、系统不自动置 0** |
| 验货结论一致时 | **同样扣除**（通常即预填的政策快照值） |
| 取值范围 | 0 ≤ 退货扣减 ≤ 退款基准 |

#### 2.7.9 内部字段的外露边界

**「判责说明」是内部字段，绝不对 C 端展示。** 它是可疑情况（如疑似调包）的唯一承载，运营可以照实写内部存疑情况；本域**不对其文本格式与内容作任何约定**，拒退关单的成立也不依赖该字段有值。

**结果要求**：拒退关单必须产生**两条**留痕记录，**不得合成一条**——

| 记录 | 对买家可见 | 内容 |
|---|---|---|
| ① | **可见** | 只写客观结果：判责结论 + 出口「不退并关闭」+ 落终态已关闭（关闭原因 = 拒退关单）+ 可重新申请提示。**不含判责说明原文** |
| ② | **不可见** | 承载判责说明原文，仅内部可见 |

合成一条就会把内部备注推给买家，正是本条要防的外泄。

**⚠「判责说明」与「关闭说明」性质正好相反**：关闭说明**对买家可见**（§2.9.3），开发不要照判责说明的样子把它当内部备注处理。

#### 2.7.11 本期不做（写明以免被当成漏项）

- **不做「按责任自动豁免 / 自动计算金额」**：概览 A7 / §3.3 的「责任归属驱动退货服务费豁免与验货扣减」**本期不实现**，退货扣减全部由运营手填（详见 §2.7.7）。本期无任何自动豁免。
- **不设「物流责任」**：责任归属本期二分类（详见 §2.7.7），与概览的三分类是**已知差异、不是遗漏**。
- **真伪复核不做**：无「真伪存疑」结论值、无挂起态；发现可疑只写判责说明，流程照常推进。
- **库存回流与商品重新上架不做**：本期退货只放在仓内，不下发处置指令。**售后只记客观验货结果，处置决策（能否再售 / 降级 / 报废）与执行均归商品域**，本域无处置字段。
- **无 C 端申诉交互、无系统内争议工单**：买家不认可判责结论时线下协商。

#### 2.7.12 异常处理

| 场景 | 处理 |
|---|---|
| 判责提交时单据状态已变（如已被关闭） | 结果要求：判责只能落在开放的两个状态上；状态已变更须拒绝本次提交并提示当前状态。实现方式由技术方案定 |
| 判责提交成功但**调支付域退款接口没调通**（受理失败） | **属技术层面**：调用未成功则售后单**不进入「退款中」**，产品侧不为它定义业务状态，由技术方案保证最终调用成功（§2.8.3 末「受理失败 vs 回调失败」）。运营侧无对应待办 |
| 判责提交成功、退款已受理但**支付域回传退款失败**（回调失败） | 单据停留在退款中、标记「退款失败待重试」，运营可「重新发起退款」（§2.8.5） |
| 一个包裹寄回多件、实到件数少于售后单数 | 各张售后单**分别验、各录一条**；缺的那件录「空包或无实物」并走异常三出口 |
| 追踪异常但核实后包裹仍可送达 | 回主流程等到仓，不判丢件 |
| 已提交判责后发现结论 / 金额有误 | **系统内无补救动作**——判责提交即调支付域发起退款，是终局动作、无修改窗口（§2.7.1）。钱已发出，改结论也追不回来；只能走**线下处理**。这也是判责提交必须二次核对的原因 |

### 2.8 退款执行

> 对应系统流程图 V2.3 **段④ 尾段（退款执行与失败处理）**。本节承接 §2.7 的判责提交动作，两条流程分支、三种判责入口（到仓正常 / 异常出口①② / 丢件 / 不需寄回）**共用本节**。

#### 2.8.1 功能描述

判责提交即定案退款金额，并**由该动作直接向支付域发起退款单创建（原路退回）**，售后单随之进入「退款中」；收到支付域的退款成功结果后落「已完成」。**售后单不走订单域的退款申请单，直连支付域退款单**（订单域的退款申请单仅服务发货前退款）。

#### 2.8.2 退款金额的构成

| 项 | 谁产生 | 可否编辑 | 口径 |
|---|---|---|---|
| **退款基准** | 系统按订单商品行取数 | **只读** | = 该商品行的**实付金额**，构成口径为**已扣优惠分摊、不含销售税** |
| **退货扣减** | 运营在判责时录入 | 可编辑，有预填 | 见 §2.7.8。本域**唯一扣款科目** |
| **随退税费** | — | — | **本期恒为 0**，字段预留、不参与计算（订单税费字段金额恒为 0） |
| **最终退款金额** | 运营在判责时录入 | 可编辑，有预填 | 预填 = 退款基准 − 退货扣减 |

**恒等约束**：退款基准 = 退货扣减 + 最终退款金额，**始终成立**。

**⚠ 这是恒等约束，不是单向派生**：退货扣减与最终退款金额**两个都是运营的录入值**，**双向联动**——改动其中一个，另一个随之重算。所以本域唯一的算式表达的是这条恒等关系，而不是「谁被谁算出来」。

**⚠ 优惠不追回**：下单时享受的优惠按行分摊后已从实付中扣除，退款只退实付，**不因为退货把这部分优惠再算回来向买家收回**；剩余商品继续享受已分摊优惠。

#### 2.8.3 操作流程（主流程）

1. 运营提交判责（§2.7），退款金额定案。
2. 系统记录判责结论、责任归属与退款方案。
3. 系统向支付域发起**退款单创建（原路退回）**。**调用成功（支付域已受理）是进入「退款中」的前提**，与 §2.4.1 状态机的进入条件「判责提交，退款金额定案并已成功调起支付域退款」一致。
4. 受理成功后：
   - 售后单状态 = **退款中**；
   - 系统**反写订单商品行的退款状态 = 退款中**。
     ⚠ **只在此刻反写**，不在申请时或审核通过时反写：那时金额还没定死；且订单域「退款中」的现有定义是「退款审批通过，该商品不得发货」，提前置会语义错位。该写入时机需与订单域两侧对齐。
5. 支付域原路退回买家支付账户，并回传退款结果。**支付域回调是「退款中」的唯一出口。**
6. 回调为**成功**：
   - 系统记录退款流水与完成时间，状态 = **已完成**（终态）；
   - **反写订单商品行退款状态 = 已退款**；
   - **固定发出一封「退款完成」邮件**，内容含**判责结果 + 退款金额明细**（验货结果不单独发邮件，已合并进本封）。
7. 回调为**失败** → §2.8.5。

**⚠ 「受理失败」与「回调失败」是两件不同的事，不要合并处理（硬性，2026-08-02 定案）**

| | **受理失败** | **回调失败** |
|---|---|---|
| 是什么 | **接口没调通**——售后域向支付域发起退款单创建这一次调用本身失败（网络、超时、服务不可用等） | **业务流程的一步**——退款单已创建、支付域执行原路退回后回传「退款失败」（如原卡已注销、渠道拒绝） |
| 属于哪一层 | **技术层面** | **业务层面** |
| 产品侧怎么定义 | **不为它定义任何业务状态**——⛔ 既不落「退款中」，也不落「退款失败」。**由技术方案保证该调用最终成功**（重试、补偿等，机制由技术方案定） | 落**退款执行状态 = 退款失败**，售后单**停留在「退款中」**（不新增主状态，§2.8.5） |
| 运营侧看到什么 | **没有需要运营处理的单据形态**——调用未成功时售后单还没进入「退款中」 | 详情页退款区展示支付域失败结果与原因，页头出「重新发起退款」入口 |
| 运营能做什么 | 无动作（不是运营的问题） | **重新发起退款**（金额沿用成交值，只读） |

⛔ **不要写成"受理失败 → 单据停在退款中、运营可重试"**：受理失败意味着调用没成功，按状态机根本进不了「退款中」；写成那样会造出一个"没有退款单号却要展示『退款单〔号〕于〔时间〕回传失败』"的空壳单据。**「重新发起退款」弹窗只服务回调失败**，其可用条件（状态 = 退款中 且 退款执行状态 = 退款失败）本身就保证了退款单必然存在，不存在字段取空的展示降级问题。

#### 2.8.4 已退税费累计校验（本期无输入，逻辑保留）

**本期税费恒为 0**，订单虽有税费字段但金额恒为 0，因此本期该校验**无实际输入**。**待订单侧真正产生税额后必须启用**，以下为其**结果要求**：

- **同一订单下全部售后单已退还的税费总额，不得超过该订单实际收取的税额。** 一单一行下同一订单可能拆出多张售后单，无累计校验会**退超原税额**（支付域只校验金额总额、不拆税，兜不住这一层）。
- **该校验的排他性必须持续到退款单创建成功为止，仅覆盖校验动作不足够。** 否则「校验通过 → 释放 → 另一张单也校验通过 → 两张都创建成功」这个时间窗内，并发仍会退超。
- **实现方式（用什么机制保证排他、粒度如何取）由技术方案定。**

#### 2.8.5 退款失败的承载：不新增状态

**⚠ 本节只讲「回调失败」**（退款单已创建、支付域执行后回传失败）。**「受理失败」不落本节**——它是接口没调通、属技术层面，产品侧不为它定义业务状态（§2.8.3 末）。

| 口径 | 内容 |
|---|---|
| 失败不是状态 | **不为退款失败新增售后单主状态枚举**——它是支付域一次退款执行的结果，不是售后单的一种业务状态 |
| 失败的单停在哪 | **停留在「退款中」**，与刚到货的「待判责」单天然分开、不会混在一起 |
| 运营看到什么 | 售后单详情的退款区展示**支付域退款单的实时状态**（含失败态与失败原因）；失败原因原文落在操作记录里 |
| 运营能做什么 | **只有「重新发起退款」这一个动作**。它是**打款失败后的重试，不是重新判责**：判责结论与金额在判责提交时已定案，本弹窗**全部为只读、没有任何输入项**——运营核对「商品行实付 / 退款基准 / 退货扣减 / 实退金额」四个数字后点确认，按**原成交金额**再发起一次。**不产生新的判责结论、不改动任何金额、不回退状态** |
| 重试后状态 | 仍为「退款中」 |
| 失败处理本身 | 在支付域完成；售后侧只负责重新发起与展示 |
| 运营端如何被看见 | 列表的「退款金额 / 支付结果」列展示支付结果标记；工单台设「退款失败待重试」KPI 卡 |

| 1 | 退款基准 | 系统取数，**运营不可写入** | — | — |

#### 2.8.8 异常处理

| 场景 | 处理 |
|---|---|
| 支付域**受理失败**（接口没调通） | **属技术层面，产品侧不定义业务状态**：调用未成功则售后单**不进入「退款中」**，由技术方案保证最终调用成功（重试 / 补偿）。⛔ 不落「退款失败」、不出重发入口（见 §2.8.3 末「受理失败 vs 回调失败」） |
| 支付域**回调失败**（退款执行失败） | 停在退款中，展示支付域结果与失败原因，运营端可重试；**不新增状态** |
| 支付域回调迟迟不到 | 单据保持退款中；结果要求：退款结果必须能被售后域最终获知，获知方式由技术方案定 |
| 反写订单商品行退款状态失败 | 结果要求：售后单状态与订单商品行退款状态**最终必须一致**；不一致须可被发现。实现方式由技术方案定 |
| ⚠ 同一订单多张售后单并发退款（税费维度） | 见 §2.8.4；本期税费恒 0 故无实际风险，税额上线后必须启用 |

#### 2.8.9 UI 关联

- 运营端原型 v16-antd：**判责弹窗**内的退款方案字段组（退款基准只读 / 退货扣减 / 最终退款金额）、**重新发起退款弹窗**、**售后单详情页**「判责信息」模块的**算账列**（基准 − 扣减 = 最终）与**执行列**（退款单号 / 执行状态 / 到账时间）、**售后工单列表页**「退款金额 / 支付结果」列与「退款失败待重试」KPI 卡。
- C 端退款金额明细展示元素**不在本 PRD 范围**。

### 2.9 关单

> 对应系统流程图 V2.3 **段⑩「运营手动关闭售后单」** + **段⑨「待审核期买家撤销申请」**，并收口 **段⑤ 出口③「拒退关单」** 的关闭语义。

#### 2.9.1 三种关闭来源（本期共 3 种，靠关闭原因区分，不靠状态区分）

终态只有 2 个（已完成 / 已关闭）。**「已关闭」有三条边通向它**：

| # | 关闭来源 | 谁发起 | 开放状态 | 是否通知买家 | 是否写关闭说明 | 是否释放互斥占用 | 是否允许重新申请 |
|---|---|---|---|---|---|---|---|
| ① | **买家撤销** | 买家（C 端） | 仅**待审核** | **不发邮件** | **选填；有值即对买家可见** | 是 | 是（按时效严格判定） |
| ② | **运营关闭** | 运营（工单台） | 待审核 / 待寄回 / 退货在途 | **由运营勾选决定**（默认勾选） | **选填；有值即对买家可见** | 是 | 是（按时效严格判定） |
| ③ | **拒退关单** | 运营（判责异常出口③） | 待判责（判责动作的出口） | **固定发一封**「拒退结果」邮件 | **选填；有值即对买家可见** | 是 | 是（按时效严格判定） |

**⚠ 关闭说明（`close_note`）三种来源口径完全统一（硬性，2026-08-02 定案）**

- **一律选填、一律对买家可见**：只要该字段有值，C 端进度页就展示、关闭通知邮件就带上，**不按关闭来源做任何条件判断**。
- **⛔ 不要实现「来源 = 运营关闭才展示」这类可见性开关**：运营在填写时分不清自己填的这条会不会被买家看到，一旦规则按来源分叉，迟早会有人把内部内容填进去当"内部备注"用。**规则统一才是这条的目的。**
- **配套的运营写作要求（必须写进运营手册与后台输入框提示）**：关闭说明**一律对买家可见**，无论哪种关闭来源。运营填写时**不得写入内部定性内容**（验货结论、责任判定、拒退理由等）——它会**原样展示给买家**并进关闭通知邮件。需要记内部判断的，写在判责说明里（§2.7.9，那才是绝不外露的字段）。
- 界面上目前只有**关闭售后单弹窗**这一个填写入口（买家撤销由买家发起、拒退关单走判责弹窗出口），所以另外两种来源的取值通常为空——**这是"有没有填写入口"的事实，不是给该字段另立一套可见性规则**。为空时按 §2.10.3 第 7 封的规则整段不展示。

**共同口径**

- 三者都**释放该商品行的互斥占用**，且都**允许买家重新申请**，一律按时效严格判定、**与申请次数无关**。
- 差异只在**是否通知买家**这一列；关闭说明的口径三者完全一致。
- **「逾期未交寄」不是关闭来源之一**——本期不做超时关单，长期不寄货由运营手动关闭（来源②）。
- **已关闭是终态、不可恢复**：关错了只能让买家**重新提交一张新单**，不做「撤销关单」。

#### 2.9.2 买家撤销（来源①）

**操作流程**

1. 买家在 C 端售后详情点击「撤销申请」。
2. 二次确认后提交撤销。
3. 系统校验当前状态 = 待审核；非待审核的**不展示撤销入口**。
4. 系统置状态 = **已关闭**、关闭原因 = **买家撤销**，并释放该商品行的互斥占用。
5. **不发邮件**——撤销是买家自己发起、自己二次确认的动作，结果在 C 端当场可见，再发一封属无效触达。

**口径**

- **撤销只在「待审核」开放**：一旦运营已给出通过结论，撤销入口即关闭。
- **被驳回的单状态仍是待审核，撤销入口因此依然开着**——买家既可以改了重交，也可以直接撤销。
- **撤销是终态，不是暂停**：已关闭的单不可恢复，买家只能重新发起新申请。
- 加这个动作的原因：不给撤销，买家误提交后会被互斥锁死，只能干等运营驳回才能重新申请。
- 撤销后若仍未签收，时效尚未起算，买家随时可再申请。

#### 2.9.3 运营手动关闭（来源②）

**为什么有这个动作**：本期不做超时关单。买家过了审核再想放弃（或一直不寄货、或被驳回后既不修改也不撤销），会出现**货没退成、钱没退到、C 端撤销入口已关、互斥又挡着不能重新申请**——四条路同时堵死，单子永久停在非终态。这个动作是买家不响应时的**唯一出口**。它是**人工动作**，不算超时、不设时限阈值，完全由运营在线下确认情况后手动发起。

**开放状态：3 个**

| 状态 | 是否开放 | 理由 |
|---|---|---|
| 待审核 | **开放** | 驳回是回环不是终态，买家被驳回后既不修改也不撤销时需要一个出口把单子关掉；不给的话单据永久停在待审核、互斥占用不释放 |
| 待寄回 | **开放** | 线下已确认买家放弃退货，或长期不交寄 |
| 退货在途 | **开放** | 同上 |
| 待判责 | **不开放（刻意）** | 货已经在平台手上，必须给出判责结论与责任归属，走判责流程；确实不该退的从 §2.7.6 出口③（拒退关单）出，同样落到已关闭 |
| 退款中 | **不开放（刻意）** | 退款已发起、钱正在退，只能等支付域结果；失败就在退款中重试 |

**⚠ 待判责 / 退款中不开放是刻意的，不是漏了。** 硬关这两个状态会留下「货在平台、钱没退清、单已终态」的死账，所以关闭入口**不展示**。

**操作流程**

1. 运营在工单列表行操作或详情页页头点击「关闭售后单」（**同一操作的两个入口，共用同一份实现**）。
2. 弹窗展示只读核对区：售后单号、当前状态（并标明「非终态，关闭后落终态『已关闭』」）、订单 / 商品行。
3. 运营填写**关闭说明（选填）**。
   - ⚠ **弹窗里没有让运营选「关闭原因」的控件**，也不存在需要运营填的「原因」必填项——详见下方「关闭原因 vs 关闭说明」。
4. 运营勾选**是否邮件告知买家**（**默认勾选**；需要不发时手动取消勾选）。
5. 二次确认后提交。
6. 系统：
   - 置状态 = **已关闭**、关闭原因 = **运营关闭**；
   - 记录**操作人 / 操作时间 / 关闭说明 / 是否已邮件告知**（全程留痕，用于事后解释「这单为什么没发邮件」）；
   - **释放该商品行的互斥占用**；
   - 勾选了通知 → 发出一封「关闭通知」邮件（含关闭说明）；未勾选 → 不发，以 C 端单据状态与时间线告知。

**⚠「关闭原因」与「关闭说明」是两个不同的东西，不要糊成一个**

这两个词长得像，实际一个是系统自动落的枚举、一个是运营手填的文本，**运营端只填后者**：

| 项 | 关闭原因 | 关闭说明 |
|---|---|---|
| 形态 | **枚举**，三个取值：买家撤销 / 运营关闭 / 拒退关单（§2.9.1） | **自由文本** |
| 谁写值 | **系统按关闭来源自动落值**——运营关闭场景恒为「运营关闭」 | **运营手填** |
| 运营端有没有这个控件 | **没有**。关闭弹窗里**不提供选择关闭原因的控件**，运营无从选、也不需要选 | 有，关闭弹窗里的文本框 |
| 是否必填 | 不适用（运营不填） | **选填** |
| 对买家可见性 | 决定 C 端看到的是哪一类关闭 | **一律对买家可见**：只要有值，C 端进度页就把这段原文展示给买家、关闭通知邮件也带上，**不按关闭来源加任何条件判断**（§2.9.1） |
| 写值范围 | 三种关闭来源都写 | **三种关闭来源统一口径：选填、有值即对买家可见**。⛔ 不做「仅运营关闭场景写值 / 仅运营关闭才展示」这类分叉——运营填写时区分不清，规则必须统一。界面上目前只有关闭弹窗一个填写入口，另两种来源取值通常为空（为空时相关展示段整段不出） |
| 表达的内容 | 只说「**哪一类**关闭」 | 说「**这一单具体怎么回事**」——枚举装不下这段内容 |

**⛔ 开发注意两条**：① **不要把「关闭原因」做成运营的必填选择项**——它没有可选来源，运营关闭这条路径上它恒为「运营关闭」；② **不要把「关闭说明」做成必填**，它是选填的。

**关闭说明与判责说明性质正好相反**：判责说明是内部字段、绝不外露（§2.7.9），关闭说明**对买家可见**。开发不要照判责说明的样子把它当内部备注处理。

**⚠ 为什么这里给选择、买家撤销却一律不发**：撤销是买家自己点的、结果当场可见；运营关闭时买家不是发起方，多数情况该通知，但也存在「线下已经沟通过了」的场景，所以做成运营按场景决定，而不是系统一刀切。
**⚠ 与驳回邮件的口径刚好相反**：驳回是**行动请求**，没有「不发」这个选项（§2.5.4）。**开发不要照关闭的勾选框给驳回也做一个开关。**

#### 2.9.4 互斥占用的释放：实时聚合，不需要显式反写字段

**这是本节最容易被开发漏掉的一步，也是最容易做错的一步。**

- 互斥占用（同一商品行同时只允许一张非终态售后单）**按商品行实时聚合本域非终态单**得出，与订单侧「售后中」标识**同一口径**。
- 因此**释放是「进入终态」的必然结果**：两个终态、三种关闭来源一律释放，**无任何例外**。
- **不需要显式反写任何占用字段**——**订单域没有这样一个字段，开发不要去找**。
- **不释放的后果**：该商品行仍被在途单占着，买家依旧无法重新申请，「运营手动关闭」这条决策就白做了。

#### 2.9.5 关闭后的重新申请

| 项 | 口径 |
|---|---|
| 是否允许 | **三种关闭来源都允许** |
| 判定依据 | **按售后时效严格判定、与申请次数无关**；仍在时效内可正常再次申请，不需要人工特批 |
| 未签收的情形 | 时效尚未起算，买家随时可再申请 |
| 反复无效申请怎么拦 | 由运营在**审核环节继续驳回**来拦，**不靠「禁止重申」** |
| 与「已完成」的区别 | 已完成 = **钱已退出去 → 不能再建单**；已关闭 = **没退成钱 → 可重新申请**。两个终态结论**正好相反**（§2.4.5） |

#### 2.9.6 校验规则

| # | 校验项 | 规则 | 校验时机 | 不通过的处理 |
|---|---|---|---|---|
| 1 | 买家撤销开放状态 | 仅「待审核」 | 进入时 + 提交时 | 非待审核不展示撤销入口 |
| 2 | 运营关闭开放状态 | 仅「待审核 / 待寄回 / 退货在途」三个状态 | 进入时 + 提交时 | 待判责 / 退款中不展示关闭入口 |
| 3 | 关闭说明 | **选填**（填了会原样展示给买家） | 提交时 | 不阻断 |
| 3b | 关闭原因 | **系统按关闭来源自动落值**，运营关闭场景恒为「运营关闭」。⛔ **不提供运营选择控件、不做成必填项** | 提交时 | — |
| 4 | 邮件告知勾选 | 默认勾选；两种取值都要留痕 | 提交时 | — |
| 5 | 二次确认 | 关闭为危险操作，必须二次确认 | 提交前 | — |
| 6 | 终态不可恢复 | 已关闭的单不提供任何恢复 / 撤销关单入口 | — | — |
| 7 | 并发关闭 | 结果要求：单据进入终态后不得被二次关闭或改写终态。实现方式由技术方案定 | 提交时 | 拒绝并提示当前状态 |

#### 2.9.7 异常处理

| 场景 | 处理 |
|---|---|
| 关闭提交时单据状态已变（如买家已撤销、或已推进到待判责） | 拒绝本次提交并提示当前状态；待判责 / 退款中不再展示关闭入口 |
| 关闭成功但通知邮件发送失败 | 不影响关单结果；邮件发送结果需可查（见邮件通知章节） |
| 运营关错单 | **无法恢复**，只能让买家重新提交一张新单；这是「关闭必须二次确认 + 全程留痕」的原因 |
| 买家撤销与运营审核并发 | 结果要求：同一张单只能落一个终结结论，先到者生效，后到者被拒绝并提示。实现方式由技术方案定 |

#### 2.9.8 UI 关联

- 运营端原型 v16-antd：**关闭售后单弹窗**（列表页行操作与详情页页头共用同一份实现）、**售后单详情页**（关闭原因标签 + 关闭说明 + 「邮件告知买家：是 / 否」留痕 + 「关闭后买家可以对该商品行重新申请售后」提示）、**操作记录**区（关单 / 拒退关单事件）。
- C 端「撤销申请」入口与二次确认、已关闭态的进度页展示元素**不在本 PRD 范围**。

### 2.10 邮件通知

**模块概述**

售后域对买家的主动触达只有一条渠道：邮件。本节定义本域**发哪几封、什么时候发、发给谁、正文写什么**，以及哪些节点**刻意不发**。

三条贯穿全节的口径，先记住：

1. **收件人恒为买家本人**，取买家账号当前的注册邮箱。售后单只记申请人，**邮箱不进售后表、不做快照**——买家改了邮箱，后续售后邮件就该发到新邮箱（与政策快照 / 原因码快照的判据不同：那两个锁的是运营侧配置变动，邮箱是买家自己的资料）。
2. **本域不设邮件总开关**。发或不发由节点本身固定，7 封里只有第 7 封「关闭通知」由运营在关单弹窗逐单勾选，其余 6 封固定发送。
3. **邮件绝不外露内部信息**。验货结论、判责说明、责任归属、审核意见一律不进任何邮件（剔除清单见 §2.10.3 开头）。

#### 2.10.1 邮件节点全表

| # | 邮件 | 触发时机 | 收件人 | 是否可关 | 对应流程段 |
|---|---|---|---|---|---|
| 1 | 审核通过通知 | 运营提交审核结论 = 通过 | 买家 | 固定发，无开关 | 段② |
| 2 | 审核驳回通知 | 运营提交审核结论 = 驳回 | 买家 | **固定发，不设开关**（与第 7 封刚好相反） | 段⑧ |
| 3 | 退货运单号与退货地址 | 运营在「待寄回」登记退货运单号与承运商并保存成功后。**按退货运单号去重：一个运单号只发一封**——多张售后单共用同一运单号时不逐单发（§2.6.5（3）） | 买家 | 固定发，无开关 | 段③ |
| 4 | 退款完成 | 支付域退款结果回调 = 成功、售后单落「已完成」后 | 买家 | 固定发，无开关 | 段④ |
| 5 | 拒退结果 | 判责异常人工核实后选择出口③（不退并关闭），售后单落「已关闭 · 拒退关单」 | 买家 | 固定发，无开关 | 段⑤（**主线未画节点，仅段注声明**，本节将其显式定为正式需求） |
| 6 | 丢件处理进展 | 「退货在途」状态下运营提交判责、结论 = 退回途中丢件，售后单进入「退款中」 | 买家 | 固定发，无开关 | 段⑦ |
| 7 | 关闭通知 | 运营手动关闭售后单（待审核 / 待寄回 / 退货在途）**且勾选了「邮件告知买家」** | 买家 | **运营逐单勾选，默认勾选** | 段⑩ |

**关于第 5 封（重点）**：拒退关单是买家**钱货两空**的重大结果，必须告知。它在实体关系图上没有对应规则、在系统流程图主线上没有画节点（主线已走进终态框）、在运营端原型上也没有发送提示，此前只靠段⑤的一段注释托底。**本节将其定为与其余 6 封同等的正式需求**，开发不得因为"图上没有"而不做。

**关于第 1 封的两种正文**：审核通过邮件在流程上发生在分支判定之前，但买家下一步该做什么，两条分支完全相反——走寄回的要等运单号、不寄回的什么都不用做。因此第 1 封**同一封邮件、同一个主题，正文分 A/B 两个版本**，按该单原因码快照是否命中「未收到货码表」选择（判据见 §2.2 流程分岔）。两个版本的正文见 §2.10.3。

**关于第 4 封与第 6 封的先后**：退回途中丢件的单会先收到第 6 封（进展 + 金额），退款成功后再收到第 4 封（退款去向）。两封内容不重复：第 6 封说"这笔钱已经定了、正在退"，第 4 封说"钱已经退出去了、退到哪"。

#### 2.10.2 明确不发的 4 处

以下 4 个节点**刻意不发邮件**，不是遗漏。开发与测试按本表验收，评审时不再逐个追问。

| 不发的节点 | 理由 |
|---|---|
| **提交受理**（买家提交售后申请） | 买家刚点完提交、人还在页面上，邮件是多余触达。改由**提交成功页当场告知「已提交成功」**（成功页文案归 C 端需求）。本期不设审核时限，成功页与邮件都**不承诺处理时长** |
| **到仓收货**（退货包裹送达仓库） | 买家在物流轨迹上已经能看到签收，再发一封重复触达无价值。到仓时点由物流服务的「已送达」自动识别，没有人工签收动作，也没有对应的告知需求 |
| **验货结果单独发** | 验货与退款的间隔太短（判责提交即定案金额、即调用支付域退款接口），单独发会和退款完成那封连着到达。**已合并进第 4 封「退款完成」**——合并后的口径是只报金额与去向，不解释扣款的定性原因（见 §2.10.3 开头的剔除清单） |
| **买家撤销** | 撤销是买家自己发起、自己二次确认的动作，结果在 C 端当场可见，再发一封属无效触达。C 端单据状态与时间线即为告知渠道 |

> 「已关闭」的三个来源在是否通知买家上**各不相同**，这是刻意设计，不要拉平：**买家撤销**不发 · **运营关闭**由运营勾选决定 · **拒退关单**固定发一封只告知结果的邮件。

#### 2.10.3 邮件模板（英文原文）

**为什么英文原文写进 PRD**：邮件没有设计稿，这些英文串就是**最终展示给买家的文案**，源语种文案的定义权在产品。开发按本节实现即可；不给语言包 key（属开发侧实现细节），也不存在"最终以语言包为准"这种层级——语言包只负责把这里的英文源文翻成其他语种。

**写作与实现的通用约束**（7 封全部适用）：

- 变量位用 `{{变量名}}` 标出，**开发不得把变量的示例值写死**。金额、单号、时间、地址一律取实时值。
- 金额按买家所属 market 的币种与格式规则展示（格式化规则不翻译）。
- **凡涉及支付账户，仅展示卡组织 + 尾 4 位**，不得出现完整卡号。
- 每封结尾统一附**售后单号 + 订单号**与**回信入口**；正文提到"去改申请 / 看详情"的，附 C 端售后详情页链接。链接的生成方式属技术方案。
- **本期不做审核 SLA**，任何一封邮件都**不得出现"预计 N 个工作日内处理完""X 天内给结果"**这类**平台自己的服务承诺**——本期没有任何时限配置项支撑这种承诺。
  > **例外（性质不同，不要一起禁掉）**：**支付渠道的退款到账时长是客观事实，不是平台承诺**，可以写。第 4 封按 C 端已确认文案写明到账区间。

**「不外露内部信息」——本节从邮件里剔除的字段（硬性）**：

| 剔除的内容 | 为什么不能进邮件 |
|---|---|
| **验货结论**（与申请一致 / 附件缺失 / 成色下降 / 退回件与订单不符 / 空包或无实物 / 退回途中破损 / 退回途中丢件） | 它是内部定性结论，一旦写进邮件就成了平台对买家的定性指控，且改口径就要改历史触达。第 4 封只报**金额**，不报**结论枚举**，也不解释"为什么扣了这笔钱" |
| **验货备注** | 内部字段，可疑情况的唯一承载，绝不外露 |
| **责任归属**（平台责任 / 买家责任） | 内部留痕结论，本期不驱动任何金额。对买家披露没有意义，还容易被当成赔付承诺（第 6 封尤其不得写「途中丢件按平台责任处理」） |
| **审核意见** | 内部字段。第 2 封的正文**只取驳回原因**，同一条审核记录里的审核意见绝不带出——这条要在取数层就切干净，不能靠运营自律少写 |
| **拒退的具体理由与判责表述** | 第 5 封只告知结果与回寄安排，不写因为什么被拒 |

|---|---|---|
| `{{RejectionReason}}` 驳回原因 | 运营手写的自由文本 | **原样插入邮件正文**，不接翻译服务、不做任何加工 |
| `{{CloseNote}}` 关闭说明 | 运营手写的自由文本 | 同上 |
| 单号 / 金额 / 时间 / 地址 | 非文本内容 | 不翻译，按格式化规则处理 |

> **配套操作要求（必须写进运营手册与后台提示）**：这两个字段**运营须用英文填写**。原因是翻译服务对运营手写的自由文本无能为力，而它们会**原样进入买家邮箱**——运营填中文，买家收到的就是中文。运营端原型已在两个输入框的提示语中说明"本内容会原样发送给买家""买家在 C 端进度页会看到这段说明"，本条要求在此基础上增加"**请用英文填写**"的明确提示。

**Market 覆盖**：V1 覆盖**美国站 + 香港站**两个 market。邮件语种以**买家所属 market 的语言策略**为准——每个 market 支持哪些语言、默认语言是什么，由 market 模块统一配置，**售后域不自建语言配置、不在本 PRD 写死语种清单**。

**Fallback**：沿用平台统一策略（多语言 PRD §4.6）——有译文返回译文 → 有过期译文返回旧译文 → 无记录返回英文源文。产品不自定义。

**一个 market 支持多语言时取哪一种（已定）**：**沿用多语言模块的既有语种选择策略，售后域不自定义、不另立一套规则。** 具体取值顺序（买家账号语言偏好优先、还是 market 默认语言优先）由多语言模块统一定义，售后邮件按其结论执行；该策略日后调整，售后侧自动跟随，不需要回改本 PRD。**售后域在本节只声明"跟随"这一件事**，不复述多语言模块的判定细则，避免两处口径各自演化后打架。

#### 2.10.5 发送机制的边界

**能力边界**：消息通知模块**仅提供邮件通道**。**发送节点、触发时机、收件人、正文内容全部由售后域定义与维护**——包括本节这 7 封的清单、模板与两个 market 的语言覆盖。消息通知模块不感知售后业务语义，不代为决定发不发、发什么。

**不属于本 PRD 的部分**：邮件的发送队列、失败重试、模板存储位置、发信域名与 SMTP / 服务商配置，均属技术方案范畴，本节不约束。

**发送留痕**：

- **产品侧本期不提供邮件发送记录的运营查询入口**——运营端不做"邮件发送记录"页面、不做按售后单查"这封发出去没有"的入口。买家反馈"没收到邮件"时，本期由运营走线下向技术侧核查。
- **是否落一张发送记录表属技术方案范畴，本 PRD 不约束**（PRD 只约束结果：上述查询入口本期不做）。
- **已知风险**：买家称未收到退货运单号邮件时，运营在工单台无法自证邮件是否发出，只能找技术查日志。退货运单号完全依赖邮件传递，此处响应效率会受影响。已记入模块待优化清单，**V2 补运营端查询入口**。

> **两处产物措辞相反，已按下述口径统一（已拍板）**：
> - 实体关系图设计规则 `本图范围_不画不等于不建` 第 ② 条原文：「售后节点邮件记录（消息通知模块仅提供通道，节点与内容由本域定义，需覆盖两个 market 的语言）」，且前置句为「**都是 ✅V1 能力、建表时必须补**」。
> - 模块待优化清单第 10 条原文：「**本期不建**通知记录表」「产品侧本期不做运营查询入口」。
>
> **统一口径：邮件发送记录建不建表属技术侧决定，本 PRD 不表态；产品侧本期不做运营端的查询入口。** 这样两处产物都成立，且符合 PRD 只约束结果、不约束落表的边界——ER 那句说的是"技术上可以建"，待优化清单那句说的是"产品上不做入口"，二者本就不在同一层，不构成真冲突。


## 三、依赖与风险

### 3.1 上下游依赖

> 每条只写**业务能力与归属**，以及本模块对它的**关键要求**；对接形态属技术方案范畴，不在此定义。

| 依赖方 | 本模块依赖的能力 | **我对它的关键要求** |
|---|---|---|
| **订单支付（订单域）** | 订单、订单商品行、包裹数据 | ① 需能按商品行提供**发货与签收状态**（发货后才可申请，售后时效以**签收时间**起算，未签收不计时）、**商品行实付金额**（已扣优惠分摊、不含销售税，作为退款基准）、**成色等级快照**（验货比对基准）；② 商品行退款状态由**售后域反写**（判责调起退款时置"退款中"、到账置"已退款"），**写入时机需两侧对齐**——订单域现有"退款中"的语义是"退款审批通过、该商品不得发货"，提前置会语义错位；③ 订单域预留的"退货退款"退款申请单类型**本模块不使用**，需回订单域同步说明避免开发误接；④ 订单详情页展示"售后中"须**实时查售后域聚合**，订单表不为售后新增状态字段。**已知上游缺口（已定处置）**：订单域目前**无 market 维度**，**V1 由买家信息判定所属 market**——该方式已确认成立，本期不阻塞开发；订单域补齐 market 后再改为直取，缺口已记订单侧待优化 |
| **物流信息服务** | 退货运单注册、轨迹查询、状态与追踪异常的主动通知、**承运商字典** | ① 需支持**逆向运单**的注册与轨迹订阅，且需支持"**同一个业务单号对应多张运单**"（一单一行下多张售后单可共用一个退货运单号）。**注册时业务单号具体传什么值属技术方案决定，本 PRD 不约束**——PRD 只约束结果：多张售后单共用一个退货运单号的模型必须成立；② 其"**已送达**"节点是本模块**到仓时点的唯一来源**——售后不设人工签收登记，该通知不到就推不进待判责，可靠性直接决定链路是否卡住；③ 需能主动推送**追踪异常**（长时间无更新、承运商判定丢失/灭失），它是丢件分支的唯一发现手段；④ **不提供面单生成能力**（其本期范围已明列），故本期面单走线下预约；⑤ 需提供**承运商字典**供售后端回填运单弹窗的承运商下拉取值（见 §2.1.3）——**售后域不自建承运商字典**，字典的增删改由物流模块维护，售后侧只读取并跟随 |
| **库存** | — | **本期无需改动**。退货回仓后只放在仓内、不做入库处理，**售后 V1 不触发任何库存事件**；关键要求是库存侧**不得因售后单据自行触发回流**，双方本期都不动 |
| **商品** | 商品快照、成色等级、质检信息 | ① 需提供**成色等级快照**供验货比对（随订单商品行落存）；② **处置决策与执行归商品域**——售后只提供客观验货结论，**不下发处置指令**；商品域**不得把售后的验货结论当成"可上架"的授权**，是否允许再售由商品域自行判断；③ 本期退回件不重新上架，双方均不处理 |
| **支付** | 创建退款单、退款结果回调 | ① 需支持**按售后单创建退款单原路退回**，并把**终态结果**回传售后域——"退款中"的唯一出口就是这次结果回传，回传不到单据会永久停在退款中；② 需支持**同一订单多次、部分金额退款**（不限制退款粒度），售后的扣减后部分退款才成立；超额防护（已退 + 本次 ≤ 原支付金额）由支付域承担；③ 退款失败需**可重试且可查失败原因**——本模块不为失败新增状态，失败单停在"退款中"，运营在详情页看支付域的实时结果并重新发起 |
| **消息通知** | **仅提供邮件通道** | ① 发送节点与模板内容**由售后域定义与维护**，通知侧不定义业务节点；② 需支持**按语种下发**同一节点的不同语种模板（V1 覆盖美国站与香港站）；③ 需能反馈**发送是否成功**。⚠️ **本期产品侧不做运营端的邮件发送记录查询入口**（邮件发送记录是否落表属技术侧决定）——代价是买家说"没收到邮件"时运营无法自证，只能找技术查，已记模块待优化清单 |
| **销售市场 Market** | market 主数据 | 只读主数据，无需改动。售后**时效天数、退货服务费金额、退货地址**三项均按 market 独立配置，V1 需覆盖**美国站 + 香港站**；各 market 的退货在本 market 内闭环，不做跨境退回 |
| **多语言 / 翻译中心** | 卡片建卡、字段注册、译文读取 | 需支持本域 3 张卡片的建卡与字段注册（见 §1.7 B-2）；**字段注册完成是本模块上线的前置里程碑**。上游模块（商品）若未完成接入，其内容在对应语种下按 Fallback 回退英文源文 |
| **用户（登录注册域）** | 买家账号信息 | 需提供**按买家查邮箱**与**按邮箱检索**的能力。买家邮箱**不进售后表、不做快照**——它是买家自己的资料，改了之后后续售后邮件就该发到新邮箱，快照反而会让邮件发去废弃地址；按邮箱搜工单实时关联查 |

### 3.2 风险与已接受的代价

| # | 风险 | 影响 | 本期处置 |
|---|---|---|---|
| 1 | **"其他"原因码不在未收到货码表里，走寄回** | 买家"确实没收到货、但情形不在码表 4 条内"时无准确选项，只能选最接近的一条，或选"其他"而**被要求寄回——他寄不出来，这单会卡在待寄回** | **已接受，不做缓解**。取"默认走寄回"这一侧是因为反向判错代价大得多（选"其他"的买家很可能是货已收到、只是原因不在列表里，放进码表等于商品留给他还退了钱）。兜底手段是运营在工单台发现后**手动关单**（见 §1.4 场景 6）。**不补运营侧改判入口、不补兜底码** |
| 2 | 未收到货码表中的"投递失败退回"与另外 3 条性质不同 | 该情形下**平台侧手上已有实物**、理论上可以验货，但当前归在码表里 → 跳过寄回**也跳过到仓验货** | **本期维持现状**。上线前 review 售后原因码时一并确认（见 §七.3 待确认） |
| 3 | **不做审核 SLA** | 运营看不出哪些单积压超时，只能自己翻工单列表逐条看 | 本期不做。有运营反馈积压问题时再评估 |
| 4 | **不做真伪复核** | 调包在验货后、退款前**无系统拦截点**；发现可疑只能写内部判责说明，退款流程照常推进 | 已接受的敞口，记入待优化清单 |
| 5 | **不做交寄时限与超时关单** | 买家长期不交寄时系统不会自动收口，全靠运营主动发现 | 由运营手动关单代替（开放待审核 / 待寄回 / 退货在途三个状态） |
| 6 | **"退款失败"不进主状态机** | 失败单与正常排队的单在主状态上无法区分，**列表筛不出来**，主动发现依赖运营逐单点开看 | 缓解：详情页退款区展示支付域的实时状态与失败原因，可在此重新发起 |
| 7 | **拒退关单的具体理由不对买家展示** | 买家只看到"不予退款 + 商品回寄"这个结果，理由需客服人工答复 | 明知的取舍：内部判责说明是内部字段、绝不外露；买家侧只给客观结果 |
| 8 | **退货扣减全部由运营手填**，与申请时告知买家的金额之间无系统约束 | 实扣与告知值可以任意偏离，系统不拦截、不二次确认 | 本期不设偏离阈值校验；靠操作留痕与事后抽查约束 |
| 9 | **举证附件无防篡改凭证** | 举证是扣款纠纷时的凭证，缺少完整性校验就无法证明"现在库里这张就是买家当初传的那张" | 记入待优化清单，V1.x 补 |
| 10 | 逆向运单注册时**业务单号具体传什么值**属技术方案决定 | 本 PRD 只约束结果：物流侧必须支持"同一业务单号对应多张运单"，以承载多张售后单共用一个退货运单号的模型。传订单号还是传别的标识由技术方案与物流服务侧对齐 | **已定：PRD 不约束传值，由技术方案决定**（见 §三.1 物流信息服务行 ①） |
| 11 | **退款反复失败时「退款中」没有人工终结出口** | 买家原支付账户已注销、或渠道永久拒绝原路退回时，运营唯一动作是原额重发、必然再次失败 → 该单**永远停在「退款中」**（退款中不开放运营关闭，出口只有回调成功）。连带三条：**互斥占用永不释放** → 该商品行在订单侧**持续显示"售后中"** → **买家永远无法对该商品行重新申请**。与 §1.1 目标 2「每个非终态都有出口」正面冲突 | **2026-08-02 用户明确接受该敞口，本期不做人工终结出口**——不加"线下已另行赔付 → 运营标记结案"这类动作，也不给「退款中」开放运营关闭。发生时只能由技术侧介入处理数据。已记入待优化清单 |

| **税费** | 税费随退款退还 + 已退税费累计校验启用 | 逻辑已保留，待订单侧真正产生税额后启用 |
