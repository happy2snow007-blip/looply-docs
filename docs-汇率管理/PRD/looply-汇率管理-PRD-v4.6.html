一、概述

1.1 背景与目标

Looply 是面向美国市场的跨境二手电商平台，从二手奢侈品（包袋、首饰、配饰）切入。平台支持多地区本地币种定价，不同地区按本地货币定价。汇率管理模块负责管理所有有向币种对的平台汇率，数据源采集 USD 基准汇率，系统通过派生计算生成所有方向的原始汇率，每个方向独立配置点差并发布。

汇率管理模块是平台的用户价格换算基础设施，核心目标：

  1. 从外部数据源定时采集原始汇率
  2. 通过点差规则加工生成平台汇率
  3. 每日定时发布，保证用户端价格稳定
  4. 支持运营监控、手动干预与异常兜底
  5. 提供完整的操作记录与审计追溯

1.2 不做什么

明确不做原因
金额换算计算调用方自行计算：目标金额 = 源金额 × 平台汇率。汇率模块提供所有有向币种对的平台汇率（含派生方向），调用方不自行推导
金额格式化与展示符号、千分位、小数点由前端/格式化服务负责
报价锁定属于结算/支付模块职责
心理价修正属于商品定价/营销模块职责
支付结算与财务对账属于支付/财务模块职责
多汇率源智能比价MVP 后续迭代
自动汇率对冲策略MVP 后续迭代

1.3 用户角色

角色说明
运营人员通过后台管理汇率：配置点差、查看平台汇率、处理异常告警、设置汇率模式
系统（定时任务）每小时采集原始汇率、每日 UTC 00:00 自动发布平台汇率、触发异常告警

本模块为纯后台管理模块，无 APP 端，无终端用户直接交互。

1.4 核心场景

  1. 日常运营：系统每日自动采集并发布汇率，运营通过"平台汇率"页面监控当前状态
  2. 点差调整：运营根据业务需要调整全局或单方向点差，下次发布时自动生效
  3. 异常处理：采集汇率波动超过阈值时，系统暂停自动发布并告警，运营审核后决定发布或忽略
  4. 手动干预：市场剧烈波动时，运营可将币种切换为固定模式手动设定汇率
  5. 问题排查：通过各页面底部的操作记录回溯历史操作，支持订单核对与审计

1.6 术语说明

术语说明
基准货币汇率换算的基准，Looply 统一使用 USD
目标货币需要换算到的货币（如 EUR、GBP、JPY）
原始汇率未应用点差的汇率值，含直接采集的原始值与系统派生计算值
点差平台在原始汇率基础上叠加的调整比例
平台汇率应用点差后实际对外提供的汇率
自动模式币种跟随市场汇率 + 点差，每日定时自动发布
固定模式运营手动设定汇率值，定时发布跳过该币种
采集系统从第三方数据源获取原始汇率的动作
发布将加工后的平台汇率推送给业务系统使用的动作
汇率版本每次发布的唯一标识，格式：SNAP-YYYYMMDD-序号。定时发布一批所有币种对共享同一个序号；手动发布（单币种）独立占一个序号；序号按同日累计递增（如 SNAP-20260508-0001、SNAP-20260508-0002）

派生(derived)标记该汇率是否为系统计算得出（true=计算派生，false=直接发布）
最近成功率数据源最近 24 小时内成功采集次数 / 总采集次数 × 100%

1.7 多语言 / 多国家策略

本模块为内部运营后台，仅支持中文界面，不涉及多语言。汇率数据本身以 ISO 4217 币种代码标识，天然支持国际化。

精度口径：汇率服务自身定义汇率的小数位数（存储 NUMERIC(18,8)，展示默认 4 位四舍五入）；币种主数据的 decimal_precision 字段不在本服务使用，主要用于商品定价计算。

2.3.3 主备自动切换（机制型）

功能描述

当主数据源采集失败时，系统自动切换到备用数据源继续采集，保证汇率数据不中断。

触发条件

  • 主数据源连续 3 次采集失败

处理流程

  1. 主数据源采集失败，记录失败日志
  2. 连续 3 次失败后，系统自动切换到优先级次高的备用数据源
  3. 备用数据源采集成功后，后续采集任务使用备用源
  4. 同时触发"数据源失败告警"通知运营
  5. 运营修复主数据源后手动切回（见下方"主备切换规则"）

主备切换规则（手动 / 自动两条路径）

  • 自动切换（故障触发）：主数据源连续 3 次采集失败时，系统按优先级依次尝试下一个可采集成功的数据源升为主，原主降备；无需人工选择
  • 手动切换（运营操作）：将当前主数据源切为备时，弹窗强制选择另一个数据源升为主，选定后事务化提交（原主降备 + 新主升主同一事务），保证恒有且仅一个主；系统中仅一个数据源时不可切换主备（入口禁用，提示"至少需两个数据源方可切换主备"）
  • 切换判断基于连续失败次数，单次失败不触发切换
  • 所有数据源均失败时，系统保留最近一次成功采集的数据，不发布新汇率
  • 切换事件（手动/自动）记录到 operation_log（entity_type=数据源，operation_type=主备切换）；failure_count 运行时维护

异常处理

2.4.2 定时采集任务（机制型）

功能描述

触发条件

  1. 读取所有已启用数据源的配置
  2. 按优先级顺序调用数据源 API
  3. 获取所有已启用币种的 USD → 目标币种汇率
  4. 写入原始汇率记录表
  5. 触发派生计算：基于最新采集的 USD→X 数据，计算所有逆向（X→USD）和交叉（X→Y）方向的派生原始汇率，一并写入原始汇率表；派生记录的"采集时间"= 源 USD 采集时间

  • 每次采集记录成功/失败状态和响应时间

异常处理

  • 单次采集超时（30 秒）：标记为失败，等待下次重试
  • 数据源返回异常数据（如汇率为 0 或负数）：丢弃该条数据，标记为失败
  • 连续失败触发主备切换（见 2.3.3）

2.5.3 异常告警触发机制（机制型）

功能描述

系统在每日 UTC 0:00 发布时，自动对比最新原始汇率（含派生原始汇率）与当前生效汇率，超过阈值时生成告警并暂停该币种的本次发布。各币种对（含派生方向）独立判定，互不影响。

触发条件

  • 每日 UTC 0:00 定时发布时执行告警判定（非采集时）

处理流程

  1. 发布任务启动，获取每个有向币种对的最新采集值/派生原始汇率
  2. 对所有有向币种对（含直接采集和派生方向），计算与当前生效汇率的差异百分比：|(新值 - 旧值) / 旧值| × 100%
  3. 差异超过告警阈值时：
  • 自动模式币种：生成"待处理"告警，暂停该币种的本次发布
  • 固定模式币种：生成"固定模式提示"告警，仅提示不影响当前生效值
  1. 差异未超过阈值：不生成告警，正常发布

规则说明

  • 告警阈值默认 ±5%，运营可在告警页面修改
  • 各币种对独立判定，互不影响（无级联暂停机制）
  • 自动模式币种触发告警后，该币种的发布被暂停，直到运营处理（确认发布或忽略）
  • 运营处理告警时，系统取当时最新采集值再次判定：未超阈值直接发布；仍超阈值则提示"当前仍超阈值，确认发布？"，运营确认后发布
  • 忽略后，下次发布时如果差异仍超阈值，会再次生成新告警
  • 同一有向币种对已存在"待处理"告警时，新一轮发布判定又触发告警，则上一条自动置为"已忽略"，仅保留最新一条待处理（badge 每对只计最新一条）
  • 不做告警未处理超时升级（无 SLA 自动动作），未处理则保持当前生效汇率不动
  • 固定模式币种的告警仅为提示性质，不影响当前生效汇率

异常处理

  • 告警判定失败不影响其他币种的正常发布流程

2.7 定时发布机制（机制型）

功能描述

系统每日 UTC 00:00 自动执行汇率发布，将最新原始汇率应用点差规则后生成新的平台汇率。

触发条件

  • 每日 UTC 00:00 定时触发

处理流程

  1. 读取所有已启用且为自动模式的有向币种对
  2. 获取每个方向的原始汇率（直接采集的 USD→X 或派生计算的逆向/交叉）
  3. 对每个方向执行告警判定：最新原始汇率 vs 当前生效汇率，超阈值则暂停该方向并生成告警
  4. 未触发告警的方向：查询当前生效的点差规则（方向点差优先，无则用全局默认）
  5. 计算平台汇率：原始汇率 × (1 + 点差比例)
  6. 写入新的平台汇率
  7. 固定模式的方向：跳过，不发布
  8. 生成发布批次号，写入变动日志
  9. 旧的生效汇率标记为过期

规则说明

  • 发布频率：每日 1 次（UTC 00:00）
  • 固定模式币种不参与定时发布
  • 告警判定在发布流程中执行，超阈值的币种暂停本次发布，其余正常发布（各币种对独立判定，互不影响）
  • 发布后所有业务系统查询到的汇率立即更新
  • 同一批次发布的所有币种共享同一个批次号，在变动日志中可聚合查看
  • 版本号生成规则：格式 SNAP-YYYYMMDD-序号，序号按同日累计递增。定时发布一批共享一个序号（如 SNAP-20260508-0001），手动发布单独占一个序号（如 SNAP-20260508-0002）

异常处理

  • 定时任务执行失败：记录错误日志，触发系统告警，等待下次手动触发
  • 部分币种发布失败：成功的币种正常生效，失败的币种保留旧值并告警

技术说明

  • 发布为原子操作，同一批次内的币种要么全部成功要么全部回滚（按币种粒度）
  • 发布完成后清除 Redis 缓存，业务系统下次查询获取最新值
  • 后台管理页面直查 DB，前端不缓存，不提供刷新按钮；无"手动发布全部"按钮

2.9 派生原始汇率与有向币种对发布（机制型）

功能描述

系统仅从外部数据源采集 USD 基准汇率（USD→EUR、USD→GBP、USD→JPY）。系统通过派生计算（倒数/交叉）自动生成所有有向币种对的原始汇率，每个方向独立配置点差后发布为平台汇率。

设计原则

  • 采集层不变：数据源仍只采集 USD→X 方向的原始汇率
  • 派生原始汇率：系统自动计算所有方向的原始汇率（X→USD、X→Y），作为点差计算的基础
  • 方向独立：每个有向币种对独立配置点差、独立发布平台汇率
  • 一致性保证：同一时刻所有调用方获取到的同一币种对汇率完全一致
  • 不要求互反：平台不提供货币往返兑换，故不要求平台汇率互反（A→B 与 B→A 乘积不必为 1）；原始汇率层互反，平台汇率因各方向独立加点而不互反，属预期行为
  • 版本号归属：定时自动发布的派生方向 snapshot_id 继承源 USD 发布批次；手动发布的任一单方向（含派生方向，如手动设固定）用独立手动序号，不继承（手动优先级高于继承）。派生概念仅存在于原始汇率层，平台汇率层无派生概念

派生原始汇率计算逻辑

方向类型公式示例
直接采集数据源返回 USD→XUSD→EUR = 0.9235
逆向派生1 / (USD→X)EUR→USD = 1 / 0.9235 = 1.0828
交叉派生(USD→TO) / (USD→FROM)EUR→GBP = 0.7921 / 0.9235 = 0.8578

平台汇率发布流程

每个有向币种对独立执行：

  1. 获取该方向的原始汇率（直接采集或派生计算）
  2. 查询该方向的点差规则（方向点差 > 全局默认）
  3. 计算平台汇率 = 原始汇率 × (1 + 点差比例)
  4. 发布为该方向的平台汇率

查询接口统一返回格式

{
  "from": "EUR",
  "to": "GBP",
  "rate": 0.8647,
  "snapshot_id": "SNAP-20260508-0001",
  "source_type": "cross_derived"
}
字段说明
from源币种 ISO 4217 代码
to目标币种 ISO 4217 代码
rate平台汇率值（已应用点差）
snapshot_id汇率版本号（继承自源 USD 汇率发布批次）
source_type原始汇率来源类型：direct（直接采集）、reverse_derived（逆向派生）、cross_derived（交叉派生）

对外查询接口契约（供商品/运费/购物车结算/支付路由/营销等下游调用）

  • 查询方式：支持单个币种对查询与批量查询；每次返回各币种对的最新生效平台汇率
  • 限流：内部系统调用，不限流
  • 鉴权：内部服务间鉴权，具体方式由开发定义
  • 未命中语义：
  • 币种对不存在（如币种未启用）：返回提示 "xxx-yyy 币种对不存在"
  • "尚未发布"态：新币种在 market 模块开启时即自动触发一次发布，故理论上不存在"已启用未发布"状态
  • 已停用：返回提示 "xxx、yyy 币种已停用，不支持查询"
  • 缓存与降级：发布后清 Redis；电商汇率时效性要求不高，数据源异常降级时可接受一段时间使用旧汇率（具体 TTL 与最大可接受陈旧度由开发在 NFR 中定义）
  • NFR：读接口 QPS/延迟 SLA、可用性目标、采集与日志的保留/归档策略由开发定义

原始汇率来源展示规则

页面上原始汇率来源字段按以下规则展示：

  • 直接采集：显示数据源名称，如"直接采集（Open Exchange Rates）"
  • 逆向派生：显示"逆向派生（来自 USD→X）"，如"逆向派生（来自 USD→EUR）"
  • 交叉派生：显示"交叉派生（来自 USD→FROM 和 USD→TO）"，如"交叉派生（来自 USD→EUR 和 USD→GBP）"

规则说明

  • 调用方通过统一接口查询任意币种对，无需关心底层原始汇率是直接采集还是派生计算
  • 每个方向独立应用点差（不再是"交叉汇率不应用点差"）
  • 派生方向可独立设为固定模式：派生方向（如 EUR→USD、EUR→GBP）可独立设为固定模式，与其源 USD→X 方向的模式互不影响。平台汇率中派生币种的原始汇率通过基础币种派生计算得出，而平台汇率的模式（自动/固定）为每个方向独立配置
  • 派生恒基于最新原始市场值，与源腿（USD→X）的发布模式（自动/固定）无关；交叉方向 fetched_at 取两条源腿中较晚的时间
  • 同一批次内任一源腿采集缺失，则该派生方向本批不计算、不发布（不混用上一批时间戳的源值）
  • 某币种停用时，涉及该币种的所有方向平台汇率同步停用
  • 源 USD 汇率缺失（某币种未发布）时，相关派生方向无法发布（固定模式的派生方向不受影响，因其不依赖原始汇率）
  • 计算精度：内部存储 NUMERIC(18,8)，对外展示默认按 4 位小数四舍五入；币种主数据的 decimal_precision 不在本服务使用（仅用于商品定价计算）
  • 启用币种以币种管理（market）模块为准、动态获取，非写死。设非 USD 币种数为 N，有向币种对总数 = N×(N−1)（直接 N + 逆向 N + 交叉 N×(N−2)）。下方公式示例中的 EUR/GBP/JPY 仅为示例数据

五、数据与埋点

本模块为内部运营后台，暂无前端埋点需求。关键操作通过变动日志记录，满足审计追溯。

后续如需运营行为分析，可在以下节点增加埋点：

  • 手动发布操作频次
  • 告警处理响应时间
  • 固定模式使用频率

本模块不涉及终端用户行为埋点，故本章节省略详细埋点表。

六、权限与角色矩阵

本模块 MVP 阶段操作权限由「权限管理」模块统一定义，暂不做审批流（maker-checker）。"确认发布""设置固定汇率"等直接影响对客价格的资金敏感操作，作为风险显式记录，预留高危操作审批扩展位。

后续如需引入多角色（如只读查看者、审批者）与审批流，再扩展权限矩阵。
