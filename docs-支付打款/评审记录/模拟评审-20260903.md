## P0（规则缺失或制品矛盾，阻塞开发）

### 1. [开发] 摩根回调失败但钱实际已打出去，重发会重复打款

- **位置**：PRD §2.8.1 失败原因「摩根侧超时无回调」/「摩根侧临时故障」；§2.8.2 分支一「可原单重发」
- **问题**：PRD 目前的处置是「无需改单，直接重发」。但**「我方收到失败/没收到回调」不等于「摩根没把钱打出去」**——超时、回调丢失、摩根内部已受理但响应异常，这三种情况下钱都可能已经到了卖家账户。运营按 PRD 直接重发，就会**打第二笔**。
  而 Zelle / RTP 是终局清算，两笔都追不回。
  更麻烦的是**对账也发现不了**：两次发起各产生一条本方流水，摩根侧也各有一条对应记录，逐笔匹配全部「已对账」——差异只存在于业务层（这个卖家本该只收一笔），系统里看不出来。
- **场景**：卖家 Sarah 应收 $1,850 → 第一次发起超时无回调 → 运营重发 → 两笔都成功 → Sarah 收到 $3,700，looply 多付 $1,850 且无法追回，对账页显示两笔全部正常。
- **建议方向**（需拍板）：
  - **A · 重发前必须先查证**：新增「向摩根查询该笔状态」的前置动作，确认前一笔确实未出款才允许重发。依赖摩根提供单笔状态查询能力（→ 并入 W3 一起问摩根）
  - **B · 只在系统内加提示**：重发弹窗强制显示「上一次发起于 X 时间，状态为『超时无回调』。请先在摩根后台确认该笔是否已出款」+ 必须勾选「已确认未出款」。不依赖摩根接口，靠人挡
  - **C · 按失败原因区分**：「摩根侧临时故障」「余额不足」是明确没打出去的，可直接重发；**只有「超时无回调」需要走查证**
  - 推荐 **C + B**：先按原因收窄到真正有风险的那一类，再对这一类加人工确认。A 依赖摩根能力、本期不确定

### 2. [测试] 渠道单边账没有打款日期，按日期筛选时它永远出不来

- **位置**：PRD §2.9.1 列表字段「打款日期 —— 渠道单边账时我方无此笔，显示 `—`」；§2.9 筛选
- **问题**：打款日期取的是**我方创建打款单的日期**，渠道单边账（摩根有、我方无）自然没有这个值。而对账页如果按日期范围筛选，**无日期的记录会被全部排除**——偏偏渠道单边账是最需要被人看到的一类差异（意味着摩根那边多出一笔我方不知道的出款）。
- **场景**：运营每天筛「昨天」的对账记录来核对，一条渠道单边账躺在列表里但因为没有日期而从不出现在筛选结果中，直到月底财务对总账才发现少了一笔。
- **建议方向**（需拍板）：
  - **A · 筛选改用摩根结算日期**：对账页的日期筛选走摩根侧账期日期（每条结算记录都有），打款日期只作展示列。⚠️ 但摩根日期口径待 W3 确认
  - **B · 无日期记录不参与日期筛选、恒定置顶**：任何日期条件下渠道单边账都显示在列表最前
  - **C · KPI 上「有差异」数字可点击**，点了直接跳到不带日期条件的差异清单
  - 推荐 **A 为主 + C 兜底**：A 是根治（筛的本来就该是「摩根这一天出了哪些账」），C 让运营有一个不依赖筛选条件的入口

## P1（规则不完整，影响质量）

### 3. [开发] 「打款中」等多久才判定为失败，PRD 没定

- **位置**：PRD §2.1.1 状态机「打款中 → 打款成功 / 打款失败」；§2.8.1 失败原因「摩根侧超时无回调 —— 超过约定时长未收到结果回调」
- **问题**：「约定时长」是多久，PRD 没写。这不是纯技术参数——它直接决定**运营在现场要等多久才能采取行动**：卖家还站在门口，等 30 秒和等 10 分钟是完全不同的体验；等太短又会把还在处理中的单据误判为失败，诱发第 1 条的重复打款。
- **建议方向**：产品定一个业务时长（建议 **5 分钟**：三条通道都是秒级到账，5 分钟未回调基本可判定异常），并明确超时后单据自动置「打款失败」还是保持「打款中」等人工介入。

### 4. [开发] 没有任何防重复录入机制

- **位置**：PRD §2.3 新建打款单（全节）
- **问题**：本期无回收单、无业务单号（A6/A9），系统里**没有任何东西能判断两张打款单是不是同一笔业务**。运营手滑提交两次、或两个运营对同一个卖家各录一次，系统照单全打，且不可撤销。
- **场景**：现场网络卡顿，运营以为没提交成功又点了一次 → 卖家收到两笔。
- **建议方向**（需拍板）：
  - **A · 软提示**：提交时若存在「相同收款人 + 相同金额 + N 分钟内」的单据，二次确认弹窗上方红色提示「X 分钟前已向该收款人打过 $Y，确认这是另一笔业务？」，不拦截、只提醒
  - **B · 不做**：靠二次确认与限额兜底，记入待优化清单
  - 推荐 **A**：成本低，且正好挡住最高频的「重复提交」形态

### 5. [测试] 限额「单日」的时区与起止点没定义

- **位置**：PRD §2.10 限额类型「单日累计上限」「单操作人单日上限」
- **问题**：PRD 说「当日已发起打款金额」，但本模块**明确不标时区**（§3.4 已接受的代价）。那「当日」是按美东、UTC 还是服务器时区？是自然日 00:00–24:00 还是滚动 24 小时？测试无法判定用例是否通过，运营也无法预期什么时候额度会重置。
- **建议方向**：明确为「**按美东时间自然日**」（业务发生地在美国，运营按当地作息理解「今天」最自然），并在限额配置页标注时区。

### 6. [测试] 限额统计的是「已发起」还是「成功」，重发算几次

- **位置**：PRD §2.10「全平台当日已发起打款金额 + 本单金额」
- **问题**：三个口径未定，且相互影响：① 打款**失败**的单算不算进当日累计？② 一张单**重发三次**算一次还是三次？③ 「待补收款信息」挂起的单算不算？
  若按「已发起」计且重发累计，一张 $5 万的单重发两次就吃掉 $15 万额度，运营会莫名其妙被限额拦住。
- **建议方向**：建议按「**当日实际出账金额**」统计——即只计入打款成功的流水，失败与重发不重复占用额度。理由：限额的目的是控制**资金实际流出**的风险敞口，没打出去的钱不构成敞口。

### 7. [开发] 「打款失败」态想换收款方式，没有入口

- **位置**：PRD §2.6 操作列「打款失败 → 详情、重发」；§2.8.2 分支划分
- **问题**：PRD 把失败分成两类——「可原单重发」只给重发、「需更换收款方式」只给更新收款信息。但现实中会出现交叉：一张因「摩根侧临时故障」失败的单，运营联系卖家时卖家说「我 Zelle 那个邮箱不用了，改打我 PayPal 吧」。此时单据处于「打款失败」态，**页面上只有「重发」，没有「更新收款信息」**，运营做不了。
- **建议方向**：「打款失败」与「待补收款信息」两个状态**都提供这两个操作**，由运营按实际情况选；处置方式表改为「**建议**处置方式」，不作为操作入口的硬性开关。

## P2（描述可更精确）

### 8. [开发] 业务备注非必填，但 PRD 称它是「唯一追溯依据」

- **位置**：PRD §2.3 字段表「业务备注 —— 非必填 —— 这是本单唯一的业务追溯依据（A9）」
- **问题**：两句话并列读起来自相矛盾。非必填意味着可以为空，为空的单据就完全没有追溯信息——而 §3.4 又把「仅自由文本备注」列为已接受的代价。开发会困惑：到底该不该拦。
- **建议**：保留非必填（这是已拍板的），但把话说完整：「非必填。**填了它就是本单唯一的业务追溯依据**；不填则该单在事后审计时只能对到金额、对不到事由（A9 已接受的代价）」。

### 9. [设计] 移动端提交后是独立成功页还是提示，两处表述不一致

- **位置**：PRD §1.5 页面流转写「移动端二次确认 → **提交成功页**」；§2.4 操作流程写「确认打款 → **成功提示**」
- **问题**：一个是页面、一个像 toast，开发不知道该做哪个。现场场景下这一屏很重要——卖家往往要看一眼「打出去了」。
- **建议**：统一为**独立成功页**，展示收款人、金额、打款方式与提交时间，并提供「再打一笔」「返回」两个出口。理由：toast 会自动消失，现场来不及给卖家看。

### 10. [设计] 对账页没有定义空状态

- **位置**：PRD §2.9（对比 §2.6 打款单列表写了三种空态）
- **问题**：对账页在「今天还没拉取数据」「拉取失败」「筛选无结果」三种情况下显示什么，PRD 没写。第一种尤其常见（每天早上运营打开时可能还没到拉取时点）。
- **建议**：补三种空态，其中「尚未拉取」态直接提供「拉取结算数据」按钮作为主行动。
