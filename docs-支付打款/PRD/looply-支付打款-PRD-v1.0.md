## 一、概述

### 1.1 背景与目标

looply 在美国开展**上门回收**业务：回收人员上门验货、与卖家谈定价格、当场把钱打给卖家。**当场拿到钱是这项业务的核心卖点**——卖家交出一只包，几分钟内手机上就能看到到账。

要支撑这件事，系统必须解决三个问题：

1. **钱得在池子里**——looply 预先在摩根开立资金账户并线下充值，系统要能看到余额、在快见底时喊人补钱
2. **钱得打得出去**——回收人员在现场用手机（或运营在 PC 后台）录一笔打款，通过实时通道把钱送到卖家账户
3. **每一笔都得对得上**——出款流水逐笔留痕，每天与摩根侧数据比对，差异能被发现

**本期目标**：打通「录入 → 校验 → 出款 → 对账」这条主链路，让上门回收业务能真实跑起来。

### 1.2 不做什么（明确边界）

| 不做的事 | 为什么 | 依据 |
|---|---|---|
| 回收业务本身（预约、上门、验货、鉴定、估价） | 本期全部线下人工完成，本模块只接收「打给谁、打多少」这个结果 | A0-1 |
| 回收单 | 无上游系统，打款单由运营手工录入 | A6 |
| 买家侧收款与订单退款 | 属订单支付域，资金方向相反、走原路返回 | A0-2 |
| 卖家账号体系与收款人档案 | 卖家来自线下、未必有 looply 账号；每次打款单独录入 | A8 |
| 税务信息采集（W-9 / TIN） | 上门回收属平台买断实物商品，IRS 明列「支付货款」为 1099-MISC 例外 | A4 |
| 人工审核环节 | 优先保障现场秒到账体验，改用「限额 + 全量留痕」做内控 | A2 |
| 充值的系统化管理（充值单、余额台账、充值流水） | 本期充值完全线下，系统只做余额监控与告警 | A13 |
| 系统内的对账差错处理闭环 | 差异线下核实，系统只负责发现和标记 | 用户 2026-09-03 定 |
| OFAC 制裁名单系统筛查 | 本模块只有收款人姓名一个可比对字段，必然大量模糊命中；改由收货环节人工核验证件时执行 | A16 |
| 对卖家的打款结果通知 | 依靠通道自带通知（银行入账提示 / PayPal·Venmo App 推送） | A10 |
| ACH 与 Push to Card 通道 | ACH 非实时与业务卖点冲突；Push to Card 涉及卡号数据安全成本 | A1 |

### 1.3 用户角色

| 角色 | 终端 | 界面语言 | 在本模块做什么 |
|---|---|---|---|
| 运营 · 资金专员 | looply 运营后台（PC） | **中文** | 查看余额与配置告警、录入打款单、处理打款失败、日终对账、配置限额 |
| 运营 · 上门人员 | **移动端页面**（同域名、同一套登录鉴权、同一个权限点） | **英文** | **仅发起打款**：录入 + 二次确认 |

> **C 端卖家不直接使用本系统**。卖家在线下口头或纸面提供收款方式，由运营代为录入。
> 两个角色**共用同一个权限点**，不做权限拆分——移动端只是同一套权限在小屏上的另一种渲染（A18）。

### 1.4 核心场景

**场景一 · 现场打款（主场景）**
回收人员上门验货谈定 $1,850 → 手机打开运营后台 → 菜单点「发起打款」→ 录入卖家姓名、选 Zelle、填卖家邮箱、填金额 → 提交前弹确认页（完整账号 + 大字号金额）→ 把手机转给卖家核对 → 勾选「已核对」→ 确认打款 → 卖家几分钟内收到入账提示。

**场景二 · 余额见底**
定时任务发现可用余额低于预警线 → 推送飞书群并 @ 业务/财务 → 财务线下向摩根账户补充资金 → 下次同步后余额恢复。

**场景三 · 打款失败**
摩根异步回调失败 → 打款单置「打款失败」→ 运营在列表看到 → 判断失败原因属于「可原单重发」（如摩根侧故障）还是「需更换收款方式」（如收款别名未注册）→ 前者直接重发，后者线下联系卖家改报收款方式后更新信息重新发起。

**场景四 · 日终对账**
每日定时拉取摩根前一日结算数据 → 按渠道交易号与本方流水逐笔匹配 → 金额与手续费双侧比对 → 标记「已对账 / 有差异」→ 运营查看差异清单线下核实。

### 1.6 术语说明

| 术语 | 含义 |
|---|---|
| **打款单** | 一次「打给谁、打多少」的业务凭证，由运营录入产生，是本模块的核心单据 |
| **打款流水** | 一次向摩根发起打款的执行记录。**一张打款单可对应多条流水**——失败重发会新增流水，打款单号不变 |
| **收款别名** | Zelle / PayPal / Venmo 用来标识收款人的邮箱或手机号（不是银行账号） |
| **RTP** | Real-Time Payments，美国实时清算网络，需要路由号 + 银行账号，7×24 秒级到账 |
| **可达性校验** | 录入 RTP 收款信息时，查 TCH 参与机构目录确认卖家开户行是否接入 RTP |
| **打款日期** | **创建打款单的日期**（我方口径），不是摩根的账期日期 |
| **对账状态** | 一笔流水与摩根侧数据的比对结果：未对账 / 已对账 / 有差异 |
| **渠道单边账** | 摩根侧有这笔记录、我方无对应流水。（不使用「孤儿打款」这类非行业表述） |
| **终局清算** | 钱到账即不可撤销，付款方无法追回。Zelle 与 RTP 均属此类 |

> ⚠️ **本模块没有「结算状态」**。收款场景里「结算」指渠道 T+N 把钱结算给商户，是真实的资金动作；
> 出款是从自有账户直接出去，不存在这一步。照搬订单支付的结算状态会与对账状态恒等冗余。

### 1.7 界面语言

**本模块为纯运营后台模块，不接入多语言**——但两端的固定语言不同（A19）：

| 终端 | 语言 | 为什么 |
|---|---|---|
| PC 后台 | **中文** | 使用者是国内运营团队（资金专员） |
| 移动端「发起打款」 | **英文** | 使用者是**美国本地上门人员**；更关键的是**二次确认页要直接转给美国卖家核对收款账号与金额**（见 2.5），中文界面卖家看不懂，二次确认就失去意义 |

**实现方式**：两端各自**固定单语言、硬编码文案**，不走语言包、不建多语言卡片、不做语言切换。使用者语言由终端决定，不由用户选择。

**共享组件按端渲染**：疑似重复打款提示（2.5.1）等 PC 与移动端共用的组件，判定逻辑只有一份，**文案按所在终端的语言渲染**。

本模块产生的数据（打款单、流水、对账记录）**不在 C 端展示**——卖家不使用本系统，也不接收系统发出的打款通知（A10）。因此本模块无动态内容翻译需求，无 B 段接入清单。

## 二、需求详细描述

### 2.1 全局约定

以下五项是跨页面共用的规则，各功能章节直接引用，不重复定义。

#### 2.1.1 打款单状态机

| 状态 | 什么情况下出现 | 可做什么 | 下一步去哪 |
|---|---|---|---|
| **待打款** | 极短暂的中间态：打款单已创建、尚未向摩根提交指令；以及「更新收款信息」后等待重新发起时 | 详情 | → 打款中 |
| **打款中** | 已向摩根提交打款指令，等待异步回调 | 详情 | → 打款成功 / 打款失败；**超过 5 分钟仍无回调则自动置「打款失败」**（失败原因记为「摩根侧超时无回调」）|
| **打款成功** | 摩根回调确认出款成功 | 详情 | **终态**（Zelle/RTP 终局清算，PayPal/Venmo 到账后亦不可由付款方追回） |
| **打款失败** | 摩根回调失败，且失败原因属于「可原单重发」类 | 详情、**重发** | → 打款中（重发后） |
| **待补收款信息** | 摩根回调失败，且失败原因属于「需更换收款方式」类（收款别名未注册 / 银行账户不存在）；以及卖家三条通道都不可用时的挂起态 | 详情、**更新收款信息** | → 待打款 → 打款中 |

> **「待补收款信息」不是失败终态**：款项客观上仍然欠着卖家，单据挂起等待卖家改报收款方式，不置失败（A1 已接受的代价）。

#### 2.1.2 收款信息的加密、脱敏与明文查看

| 环节 | 规则 |
|---|---|
| 存储 | 收款别名、路由号、银行账号**加密落库**，同时派生一个脱敏值单独存储 |
| 界面展示 | 列表、详情、导出**一律只用脱敏值**。邮箱示例：`s***@gmail.com`；银行账号示例：`****3092` |
| 明文查看 | 详情页提供「查看明文」入口，**每次查看都写审计日志**（谁、什么时候、看了哪一单） |
| 提交前确认 | **例外：二次确认弹窗显示完整明文**——脱敏了运营就没法核对，而核对正是这一步的全部目的（见 2.5） |

#### 2.1.3 三道校验：顺序与拦截时机

打款单提交时按**成本从低到高**依次校验，**三道全部在落库之前**——任一不通过都**不创建打款单**（A14）。

| 顺序 | 校验 | 校验什么 | 不通过怎么办 |
|---|---|---|---|
| ① | **收款信息校验** | 格式合法性；打款方式为 RTP 时，另查 TCH 参与机构目录确认开户行已接入 RTP | 表单内当场提示，提交按钮置灰 |
| ② | **限额校验** | 逐条比对所有启用中的限额规则（单笔上限、单日累计上限、单操作人单日上限） | 拦截并提示超出哪条限额 |
| ③ | **余额校验** | 向摩根查询**实时可用余额**，与本单金额比对 | 拦截提交，提示「超出可用余额，补充资金后再录入」 |

> **为什么余额校验放最后**：它要调摩根接口，是三者中最贵的一道。前两道在本地就能判完。
>
> **为什么不落单**：将来有回收单之后，「欠卖家这笔钱」的凭证是回收单，打款单只是执行凭证。本期回收全线下、欠款记在线下协议台账，按目标态设计可免二次改造（A14）。
>
> **本地余额只用于展示**：录入页显示的「资金池可用余额」来自定时同步的本地值，仅供运营心里有数；**放行与否以提交时的实时查询为准**。

#### 2.1.4 打款单的不可变更约束

打款单**不提供编辑，也不提供删除**——一笔钱打出去了就是打出去了，凭证不能被改写或抹掉。

| 状态 | 能做的唯一动作 | 录错了怎么办 |
|---|---|---|
| 待打款 / 打款中 | **只能等** | 已向摩根提交指令，系统内无法撤回；等回调结果 |
| 打款成功 | 无 | **只能线下向卖家追讨**。Zelle / RTP 终局清算，PayPal / Venmo 到账后付款方亦无法追回 |
| 打款失败 | 重发 | 重发前可先确认信息，但**金额不可改**——金额错了应当作废这单（挂着不动）另录一单 |
| 待补收款信息 | 更新收款信息 | 可改收款方式与收款信息，**金额不可改** |

> **为什么连金额都不让改**：改金额等于把「这单打了多少」这个事实改掉，审计时无法还原当初发生了什么。
> **金额录错的正确处置**：多打了 → 线下追讨；还没打出去（失败态）→ 该单不再重发，另录一张正确的单。

**限额与告警配置的变更影响**：限额规则的编辑、停用**只影响之后提交的打款单**，不影响已创建的单据（打款单提交即发起，不存在"在途待审"的单）。告警配置变更即时生效。

#### 2.1.5 资金操作审计日志

不设人工审核（A2）之后，**审计日志是唯一的内控手段**，因此记录要求是硬性的。

| 项 | 要求 |
|---|---|
| 记什么动作 | 录入打款单、提交并发起打款、重发、更新收款信息、查看收款信息明文、修改限额配置、启用/停用限额规则、修改告警配置 |
| 每条记录哪些内容 | 操作时间、操作人、操作类型、操作内容（含关键业务值，如金额、打款方式、流水号） |
| 操作人展示 | **姓名拼音，不含职务**（如 `Zhang Wei`） |
| 能不能改 | **只增不改不删** |
| 保留期 | **建议 7 年**（对齐美国金融记录保留惯例）。⚠️ 待法务确认，见 §三 W6 |
| 在哪看 | 打款单详情页底部「操作记录」区，支持按操作类型、操作人、时间范围筛选 |

> 本表记录**业务约束**，日志表本身的结构设计交技术侧（产品 ER 不画日志表）。

### 2.2 资金账户与余额监控

**功能描述**：让运营随时看到摩根资金账户还剩多少钱，并在快见底时自动喊人补。这是 A13（充值完全线下）之后，系统对充值环节的**全部参与**。

**前置条件**：资金账户已在摩根开立，账户标识已配置进系统。

**页面元素**

| 区块 | 内容 |
|---|---|
| 余额概览 | **当前可用余额**（大字号）· 余额同步时间 · 今日打款笔数 |
| 告警配置 | 预警阈值 · 通知渠道 · 接收群 · 告警频率 · 知会范围；右上「修改告警配置」按钮 |
| 账户信息 | 账户编号 · 账户名称 · 所属渠道 · 币种 · 账户状态 |

**规则说明**

| 项 | 规则 |
|---|---|
| 余额来源 | 定时同步摩根侧余额并回写本地，页面展示本地值 + 同步时间 |
| 本地值的定位 | **仅供展示与预警，不作为放行依据**。打款放行以提交时的实时查询为准（见 2.1.3） |
| 账户数量 | 本期**单账户**，页面不提供新增账户入口 |

**异常处理**：同步失败时页面保留上一次成功同步的余额并显示同步时间，运营据此判断数据新鲜度。

**UI 关联**：原型 v17「资金账户」页；无 PC/移动端差异（本页移动端不提供）。

#### 2.2.1 告警配置（弹窗）

| 字段 | 控件 | 必填 | 说明 |
|---|---|---|---|
| 预警阈值 | 金额输入 | ✅ | 可用余额低于该值时触发告警 |
| 通知渠道 | 下拉 | ✅ | 本期仅「飞书群机器人」一个选项 |
| 群 Webhook | 文本 | ✅ | 飞书群机器人地址 |
| 告警频率 | 下拉 | ✅ | 每次触发都推送 / 每 30 分钟最多一次 / 每 2 小时最多一次 |
| 知会范围 | 文本 | — | 在飞书消息中 @ 的角色 |

弹窗底部提供「发送测试消息」按钮，用于验证 Webhook 是否配置正确。

#### 2.2.2 余额不足告警（机制型）

**触发条件**：定时任务同步余额后，发现可用余额 < 预警阈值。

**处理流程**：同步余额 → 与阈值比对 → 低于阈值则按「告警频率」判断本轮是否推送 → 推送到飞书群并 @ 知会范围内的角色 → 业务/财务线下向摩根账户补充资金。

**规则说明**

- **告警频率的作用**：同一次余额不足在设定周期内只推送一次，避免刷屏。余额恢复到阈值以上后重新计次。
- **告警只推送、不落库**（本期不建告警发送记录表）。
- 未低于阈值时本轮不做任何动作。

**异常处理**：飞书推送失败时不阻塞其他流程；⚠️ 由于告警不落库，**推送失败在系统内不留痕迹**——这是本期已接受的敞口（见 §三风险表）。

### 2.3 新建打款单（PC）

**功能描述**：运营录入线下回收协议约定的应付金额与卖家收款信息，提交后直接向摩根发起打款。**本模块无上游系统对接，打款单在此产生**（A6）。

**前置条件**：登录运营后台且具备打款权限。

**页面顶部提示**（固定展示，不可关闭）

> ⚠️ **提交即向摩根发起打款，无人工审核环节**
> Zelle 与 RTP 为终局清算、不可撤销，PayPal / Venmo 到账后亦不可由付款方追回。请核对收款账号与金额后再提交。

**页面元素**

**分区一 · 收款人信息**

| 字段 | 控件 | 必填 | 说明 / 占位示例 |
|---|---|---|---|
| 收款人姓名 | 单行文本 | ✅ | 与收款账户实名一致，如 `Sarah Chen` |
| 打款方式 | 单选按钮组 | ✅ | Zelle / PayPal / Venmo / RTP 银行账户 |
| 收款别名 | 单行文本 | ✅ | **仅 Zelle/PayPal/Venmo 时出现**。邮箱或手机号，如 `sarah@gmail.com` |
| 路由号 | 单行文本（限 9 位数字） | ✅ | **仅 RTP 时出现**。支票底部左起 9 位；注意区分 ACH 与电汇路由号 |
| 银行账号 | 单行文本 | ✅ | **仅 RTP 时出现**。8 至 17 位数字 |

**分区二 · 打款信息**

| 字段 | 控件 | 必填 | 说明 |
|---|---|---|---|
| 打款金额 | 金额输入（$，两位小数，最小 0.01） | ✅ | 右侧同行展示「资金池可用余额 $X」 |
| 出款账户 | 只读 | — | 本期单账户，自动带出、不可改 |
| 业务备注 | 多行文本 | — | 回收物品、线下协议号等。**填了它就是本单唯一的业务追溯依据**；不填则该单事后审计时只能对到金额、对不到事由（A9 已接受的代价）|

#### 2.3.1 操作流程

1. 运营填写收款人信息 → 选打款方式（表单按方式切换字段）
2. 选 RTP 时，路由号填满 9 位**立即触发可达性校验**：
   - 已接入 → 字段下方绿色回显开户行名称（如 `JPMorgan Chase Bank, N.A. · 已接入 RTP`）
   - 未接入 → 红色提示「该开户行未接入 RTP，请让卖家改用 Zelle / PayPal / Venmo」，**提交按钮置灰**
3. 填金额，超出可用余额时字段下方红色提示「超出可用余额，补充资金后再录入」，**提交按钮置灰**
4. 点「提交并发起打款」→ 弹**二次确认**（见 2.5）；若命中疑似重复判定，确认弹窗上会多一条红色提醒（见 2.5.1）
5. 确认后创建打款单并向摩根发起，回到列表页

#### 2.3.2 校验规则与异常处理

| 字段 | 规则 | 校验时机 |
|---|---|---|
| 收款人姓名 | 必填 | 提交时 |
| 收款别名 | 必填；邮箱或手机号格式 | 失焦 + 提交时 |
| 路由号 | 必填；9 位纯数字；**开户行须已接入 RTP** | 输入满 9 位即时校验 |
| 银行账号 | 必填；8–17 位纯数字 | 失焦 + 提交时 |
| 打款金额 | 必填；> 0；两位小数；**≤ 实时可用余额**；**满足所有启用中的限额规则** | 输入时校验金额本身，余额与限额在提交时校验 |

**异常处理**

| 场景 | 处理 |
|---|---|
| 可达性校验服务不可用 | 提示「暂时无法确认开户行是否支持 RTP，请稍后重试或改用其他打款方式」，不放行 RTP 提交 |
| 提交时余额查询失败 | 拦截提交并提示重试，**不创建打款单**（宁可不打，不可错打） |
| 提交时限额已被其他打款占满 | 拦截并提示超出哪条限额 |
| 网络中断 | 表单已填内容保留在页面上，不清空 |

**UI 关联**：原型 v17「新建打款单」页（PC）；移动端见 2.4。

### 2.4 移动端发起打款

**功能描述**：上门回收人员在现场用手机录入并发起打款。**这是本模块的主场景**——上门回收的卖点是当场拿钱。

**前置条件**：与 PC 端**完全相同**——同一套登录鉴权、同一个权限点。运营后台菜单中「发起打款」入口在 PC 与移动端都存在，**按终端识别渲染不同页面**（A18）。

**与 PC 端的关系**

| 维度 | 说明 |
|---|---|
| 承载链路 | **只有「录入 + 二次确认」一条**。列表、详情、对账、限额、资金账户在手机上无使用场景，移动端不提供 |
| 字段构成 | **与 PC 端完全一致**（见 2.3），不增不减 |
| 校验规则 | 与 PC 端完全一致 |
| 版式 | 单列纵向排布、控件全宽、按钮加大；侧边菜单改为**可收起展开**的抽屉式导航 |
| 安全增强 | **全部不加**——不加验证码二次验证、不加更短登录态、不加独立权限开关（A18）。⚠️ 代价见 §三风险表 |
| **界面语言** | **全英文**（A19）。PC 端保持中文，两端不要求语言一致——使用者不同、且移动端确认页要给美国卖家看 |

> **跨端布局不要求一致**：移动端版式独立设计，与 PC 端的差异属刻意端差异，不是待拉平项。要求一致的只有**信息架构**（字段顺序、分区划分）与**业务规则**。

**操作流程**：菜单点「发起打款」→ 录入页（分区与字段同 PC）→ 提交 → 移动端二次确认页 → **把手机转给卖家核对** → 勾选「已核对」→ 确认打款 → **成功提示条**（几秒后自动消失，回到录入页，便于连续录入下一笔）。

**交互说明**：移动端二次确认页承担一个 PC 端没有的作用——**它是给卖家看的**。因此完整账号与大字号金额在小屏上同样是硬性要求（见 2.5）。

**UI 关联**：原型 v17 移动端录入页 + 移动端确认页；截图见 `原型/looply-支付打款-手机端-菜单展开-v14.png`、`菜单收起-v14.png`（截于 v14，截图为中文版；**移动端已于 v17 改为全英文**，版式未变）。

### 2.5 提交前二次确认（公共组件）

**功能描述**：在 PC 端与移动端提交打款前弹出，回显本单关键信息由运营（或卖家）核对。**这是取消人工审核后的关键防线**。

> **与 A2「不设人工审核」不冲突**：A2 取消的是**第二个人**的复核，本组件是**同一个人**提交前的自查。

**页面元素**（PC 与移动端共用同一套信息，版式各自适配）

| 元素 | 硬性要求 | 为什么 |
|---|---|---|
| 顶部警示 | 红色：「确认后立即向摩根发起，到账不可撤销」 | 让人停一秒 |
| 收款人 | 加大字号 | — |
| 打款方式 | — | — |
| 收款账号 | **完整明文，不脱敏** | 脱敏了就没法核对，而核对正是这一步的全部目的 |
| 开户行 | 仅 RTP 且可达性校验通过时展示 | — |
| 打款金额 | **大字号突出**（28px 级） | 防「多打一位」——这是三类误打风险中最容易发生的一类 |
| 确认勾选 | **必须勾选「我已与卖家核对收款账号与金额」，否则确认按钮置灰** | 把"看过了"变成一个显式动作 |
| **疑似重复提示** | 命中判定条件时，在顶部警示**下方**追加一条红色提示（见下） | 见 2.5.1 |

**操作流程**：勾选 → 「确认打款」（危险色）→ 创建打款单并发起。或点「返回修改」回到表单，已填内容保留。

**规则说明**：本弹窗**不做拦截性校验**——三道校验已在提交时完成（见 2.1.3），此处只做人工核对与重复提醒。

#### 2.5.1 疑似重复打款提示

**为什么需要**：本期无回收单、无业务单号（A6/A9），系统里**没有任何东西能判断两张打款单是不是同一笔业务**。运营手滑提交两次、或现场网络卡顿以为没提交成功又点一次，系统就会照单打两笔，且不可撤销。

| 项 | 规则 |
|---|---|
| 判定条件 | 存在**相同收款人姓名 + 相同打款金额 + 创建时间在 30 分钟内**的打款单（不限状态） |
| 命中后的行为 | **只提醒，不拦截**——在二次确认弹窗顶部警示下方追加红色提示，运营仍可正常勾选并确认 |
| 提示文案 | 「**X 分钟前已向 {收款人} 打过 {金额}**，确认这是另一笔业务？」（X 与金额取最近一张匹配单据的实际值） |
| 为什么不拦截 | 「同一个卖家当天卖两件同价位物品」是真实存在的正常场景。拦死会让运营在现场做不了业务，而现场是不能等的 |

> ⚠️ **这条挡的是「录了两张单」，挡不住「同一张单重发导致打两次」**——后者由 §2.8.3 的重发前查证负责。两个机制针对不同场景，缺一不可。
>
> **回收单上线后本条可退役**：届时打款单引用回收单，一笔回收业务对应一张打款单是天然约束，不再需要靠「收款人+金额+时间」这种近似判定。

**UI 关联**：原型 v17 `PayoutConfirmModal`（PC）/ `PayoutMobileConfirm`（移动端）；截图 `原型/looply-支付打款-二次确认弹窗-v12.png`。

### 2.8 打款失败处理（流程型）

**功能描述**：摩根回调失败后，运营判断失败原因、决定重发还是换收款方式。

**前置条件**：打款单状态为「打款失败」或「待补收款信息」。

#### 2.8.1 失败原因（完整枚举）

| 失败原因 | 什么情况下出现 | **建议**处置方式 | 打款单落到哪个状态 |
|---|---|---|---|
| 摩根返回余额不足（并发占用） | 提交时余额校验通过，但**校验到实际发起之间**余额被其他打款占用 | 可原单重发 | 打款失败 |
| 摩根侧超时无回调 | 指令已提交，**超过 5 分钟**未收到结果回调 | 可原单重发（须先查证，见 2.8.3） | 打款失败 |
| 摩根侧临时故障 | 摩根返回系统性错误 | 可原单重发 | 打款失败 |
| 收款别名未注册 | 卖家提供的邮箱/手机号未在 Zelle / PayPal / Venmo 注册 | 需更换收款方式 | 待补收款信息 |
| 银行账户不存在 | RTP 路由号+账号无法定位到有效账户 | 需更换收款方式 | 待补收款信息 |

> ⚠️ **「开户行不支持 RTP」不在本表**——它已在录入时被可达性校验拦掉、根本不会落单（A15）。
>
> ⚠️ **「余额不足」的语义已收窄**：提交时余额不足的单据**根本不会被创建**（A14）。本表这一条只覆盖并发场景。

#### 2.8.2 处置流程

**分支一 · 可原单重发**（摩根返回余额不足 / 超时 / 临时故障）
1. 运营在列表或详情点「重发」
2. 弹窗回显：打款单号 · 收款人 · 收款账号（脱敏）· 打款金额 · **上次失败原因**；余额不足时额外显示「当前资金池余额 / 本单金额」
3. **必填「重发原因」**（如：已线下补充资金 / 摩根侧故障已恢复）
4. 点「确认重发」→ **系统先向摩根查证上一笔的真实状态**（见 2.8.3）
5. 查证确认未出款 → **打款单号不变**，新增一条打款流水，单据回到「打款中」

#### 2.8.3 重发前的出款查证（防重复打款）

**为什么必须查**：「我方收到失败」或「我方没收到回调」**都不等于「摩根没把钱打出去」**。超时、回调丢失、摩根内部已受理但响应异常，这三种情况下钱都可能已经到了卖家账户。此时重发就是**打第二笔**，而 Zelle / RTP 是终局清算、两笔都追不回。

**更麻烦的是对账发现不了**：两次发起各产生一条本方流水，摩根侧也各有一条对应记录，逐笔匹配全部「已对账」——差异只存在于业务层（这个卖家本该只收一笔），系统里看不出来。

**规则**

| 项 | 规则 |
|---|---|
| 触发时机 | 运营点「确认重发」之后、真正发起之前 |
| 查什么 | 向摩根查询**上一条打款流水的真实出款状态** |
| 查证结果为「未出款」 | 正常重发，新增一条流水 |
| 查证结果为「已出款」 | **阻断重发**，提示「上一笔实际已出款成功」，并把该流水与打款单更新为成功状态 |
| 查证结果为「仍处理中」 | **阻断重发**，提示「上一笔仍在处理中，请稍后再试」 |
| **查证接口调用失败** | **阻断重发**，提示「暂时无法确认上一笔是否已出款，请稍后重试或到摩根后台核实」。⚠️ **宁可不打，不可错打** |

> ⚠️ **本节依赖摩根提供「按笔查询打款状态」的能力，该能力尚未确认**（§三 W8）。若摩根不提供，本节规则无法按上述形态落地，需回头重新拍板处置方式。

**分支二 · 需更换收款方式**（收款别名未注册 / 银行账户不存在）
1. 线下联系卖家，问清可用的其他收款方式
2. 运营在列表或详情点「更新收款信息」
3. 弹窗内重选打款方式并填写新的收款信息（字段与校验同 2.3；选 RTP 同样触发可达性校验）
4. 「保存并重新发起」→ 单据回到「待打款」→ 随即发起 → 「打款中」

**规则说明**

- **重发不产生新打款单**：打款单号不变，只新增一条流水。这样「一次业务应付」始终对应一张单
- **无自动重试**：所有重发均由运营手工发起。系统不做自动轮换通道、不做自动重试（A5）
- **三条通道都不可用时**：单据挂在「待补收款信息」等待，**不置失败**——款项客观仍然欠付（A1 已接受的代价）

**异常处理**：重发时若余额仍不足，按 2.1.3 的余额校验拦截，不产生新流水。

**UI 关联**：原型 v17 `ResendModal` / `RepayeeModal`（列表页与详情页共用同一实现）。

### 2.9 打款对账

**功能描述**：每日拉取摩根结算数据，与本方打款流水逐笔比对金额与手续费，把对不上的挑出来给运营线下核实。

**前置条件**：摩根已提供前一日结算数据。⚠️ 数据提供方式与字段待确认（§三 W3）。

#### 2.9.1 列表字段与筛选

| 列 | 说明 |
|---|---|
| 打款日期 | **创建打款单的日期**（我方口径），**仅作展示、不参与筛选**。渠道单边账时我方无此笔，显示 `—` |
| 打款单号 | 可点击进打款单详情；渠道单边账时显示 `—` |
| 渠道 | 本期恒为 J.P. Morgan，**枚举可扩展** |
| 打款流水号 | 本方流水号；渠道单边账时显示 `—` |
| 渠道交易号 | 摩根侧交易号，**与打款流水号 1:1**，是对账的匹配键 |
| 出款对比 | 双列子表头：**系统** / **渠道**，金额不一致时高亮 |
| 手续费对比 | 双列子表头：**系统** / **渠道**，不一致时高亮 |
| 对账时间 | 完成比对的时间 |
| 对账状态 | 未对账 / 已对账 / 有差异（固定在右侧） |

> **为什么渠道交易号放主表、不做展开行**：它与打款流水号是 1:1 关系（就是流水上的一个字段），没有明细可展开。

**筛选项**：**摩根账期日期**（范围）· 对账状态 · 渠道 · 打款单号/渠道交易号（关键词）· 「只看渠道单边账」快捷开关。

> ⚠️ **日期筛选用的是摩根账期日期，不是打款日期**。这一条是硬性的：渠道单边账（摩根有、我方无）**没有打款日期**——我方压根没建过这张单。若按打款日期筛，这类记录在任何日期条件下都出不来，而它恰恰是最需要被发现的差异（意味着摩根那边多出一笔我方不知道的出款）。
> 对账页的日期筛选本来就该回答「**摩根这一天出了哪些账**」，用摩根侧日期才是正解。
> ⚠️ 摩根账期日期的具体字段与口径待 W3 确认。

**KPI**：结算记录总数 · 未对账 · 已对账 · 有差异（红色，**数字可点击**，点击后跳转到不带日期条件的差异清单）。

**头部操作**：导出 · 拉取结算数据。

#### 2.9.2 拉取结算数据（弹窗）

| 字段 | 说明 |
|---|---|
| 渠道 | 只读，J.P. Morgan Global Payments |
| **摩根结算日期** | 日期范围，必填。系统每日自动拉取前一日数据，此处用于**补拉历史或重试失败** |

> ⚠️ **这里的「摩根结算日期」与列表的「打款日期」是两个概念**：前者是摩根侧的账期日期（决定拉哪一批数据），后者是我方创建打款单的日期（用于业务检索）。

#### 2.9.3 对账规则

| 项 | 规则 |
|---|---|
| 执行时点 | 每日定时自动拉取前一日数据。**建议 UTC 次日 06:00 之后**（留出摩根出账缓冲），⚠️ 具体时点待 W3 确认摩根数据可用时间后定 |
| 匹配键 | **渠道交易号**（与订单支付同一字段，A12 三处同构） |
| 入账记录处理 | **仅保留出款方向记录，入账记录直接丢弃**。充值不入系统（A13），入账记录在本方必然无对应流水，若参与比对会每充值一次就产生一条固定噪音差异 |
| 落库范围 | 拉回的结算记录**全量落库**，用对账状态与「是否渠道单边账」标记结果——不是只存差异，否则审计不出「摩根说这一天有几笔」 |
| 判定「已对账」 | 按渠道交易号匹配到本方流水，**且金额一致、手续费一致** |
| 判定「有差异」 | 匹配到了但金额或手续费不一致；或**渠道单边账**（摩根有此笔、我方无对应流水） |
| 差异处置 | **系统不做处理闭环**，运营查看差异清单后线下核实。系统只负责发现和标记 |

**空状态**

| 状态 | 什么时候出现 | 页面显示 |
|---|---|---|
| 尚未拉取 | 当日定时任务还没到执行时点，或从未拉取过 | 提示「今日结算数据尚未拉取」+ 主行动按钮「拉取结算数据」 |
| 无匹配 | 筛选条件下无结果 | 提示 + 「清除筛选」 |
| 异常 | 拉取或加载失败 | 提示 + 「重试」 |

**异常处理**：拉取失败时列表保持上一次数据，运营可通过「拉取结算数据」手工补拉。

**UI 关联**：原型 v17「打款对账」页；截图 `原型/looply-支付打款-对账页截图-v11.png`。

### 2.10 限额配置

**功能描述**：配置打款的金额上限。**不设人工审核之后，限额是唯一的事前内控手段**（A2）。

**列表字段**：限额类型 · 限额金额 · 状态（启用/停用）· 最后修改人 · 最后修改时间 · 操作（编辑 / 启用·停用）。

**限额类型枚举（完整定义）**

| 限额类型 | 校验什么 |
|---|---|
| 单笔上限 | 本次打款金额不得超过该值 |
| 单日累计上限 | 全平台当日**实际打款成功**金额 + 本单金额不得超过该值 |
| 单操作人单日上限 | 当前操作人当日**实际打款成功**金额 + 本单金额不得超过该值 |

**规则说明**

| 项 | 规则 |
|---|---|
| 校验方式 | 打款单提交时**逐条校验所有启用中的规则，任一不通过即拦截** |
| 停用的影响 | 停用后该规则不再参与提交校验；停用时弹确认框说明这一后果 |
| 适用范围 | **V1 恒为「全局」**，界面不提供「按打款方式」配置。⚠️ 数据模型已预留该维度——Push to Wallet 上限 $6 万与 RTP 上限 $1000 万差两个数量级，按方式配限额是可预期的近期需求 |
| **统计口径** | 只计入**打款成功**的金额。打款失败的不占额度，同一张单重发多次也只按最终成功的那一笔计一次。<br>**为什么**：限额是为了控制**资金实际流出**的风险敞口，没打出去的钱不构成敞口。反例：一张 $5 万的单重发两次才成功，若按「已发起」计会吃掉 $15 万额度，运营会莫名其妙被拦住 |
| **「单日」怎么算** | **按美东时间自然日**（00:00–24:00）。业务发生地在美国，运营按当地作息理解「今天」最自然。限额配置页需标注时区 |
| 取值 | ⚠️ 具体数值待摩根确认实际限额与费率后定（§三 W5） |

**新建 / 编辑（弹窗）**：限额类型（下拉，必填）· 限额金额（必填，> 0）· 状态（必填，默认启用）。

**异常处理**：同一限额类型重复创建时提示已存在，引导去编辑。

**UI 关联**：原型 v17「限额配置」页。

## 三、依赖与风险

### 3.1 外部依赖

| 依赖 | 依赖什么能力 | 关键要求（不满足会怎样） |
|---|---|---|
| **摩根 Global Payments** | 资金账户余额查询、打款指令发起、打款结果异步回调、日终结算数据 | ① **余额查询必须是实时的**——本地缓存值不能作为放行依据，否则并发下会超发；② **回调必须能关联到具体一笔打款**，否则打款状态永远停在「打款中」（如何关联由技术方案定）；③ 摩根挂了则**无法打款**，本模块核心功能全不可用 |
| **飞书开放平台** | 群机器人消息推送 | 挂了则余额见底无人知晓——A13 之后，系统对充值环节的全部参与就是这个告警 |
| **The Clearing House RTP 参与机构目录** | 按路由号判断开户行是否接入 RTP | 挂了则可达性校验失效，RTP 退化为「发起后才知道不可达」 |
| **looply 运营后台** | 承载本模块页面（PC 与移动端）、运营身份与登录鉴权、权限点 | 挂了运营进不来，无法录入打款单 |

**本期不依赖**：回收业务系统（不存在，线下作业）· 用户账号系统（不建收款人档案）· 邮件/短信服务（不做对卖家的打款通知）· 汇率服务（仅 USD）· 摩根 Account Validation（在 Fraud Solutions 产品线下需另签约，本期不接）。

### 3.2 与订单支付模块的关系

本模块与订单支付**保持独立**，但有三处**强制同构**（A12）：

| 同构项 | 具体要求 |
|---|---|
| 数据模型 | 打款单 / 打款流水的字段命名与结构对齐订单支付的支付单 / 支付流水 |
| 渠道抽象 | 摩根作为**现有 Payment Service 里的一个新 channel 接入**，不另起服务 |
| 对账模型 | 匹配键、对账状态语义与订单支付对齐（**唯一例外：出款没有「结算状态」**，见 §1.6） |

> **为什么现在不合并**：打款服务 C1 回收采购、订单支付服务 C2 交易，业务线与资金方向均不同；打款单与订单表零外键关联，并入会在订单 ER 里形成孤岛表；订单支付 V1.3 于 2026-08-31 刚交付，此刻重构将导致开发返工。
> **已立项后续工作**：把订单支付里的支付部分拆出来，与本模块合并为统一支付域。同构之后合并是「同构表合并」而非「异构系统打通」，成本差一个数量级。

### 3.4 已知风险（均为已拍板接受，记录在案）

| 风险 | 已接受的代价 | 来源 |
|---|---|---|
| **不设人工审核** | 单个运营可独立完成「填账号 → 填金额 → 打款」全过程，且 Zelle / RTP 不可撤销。三类风险只能事后发现：金额填错、账号填错（钱进陌生人账户且追不回）、内部人主动作案。**限额只能封顶单次损失，不能阻止发生** | A2 |
| **移动端不加安全增强** | 手机丢失且登录态未过期时，捡到的人可直接发起不可撤销的打款，**限额是唯一封顶手段** | A18 |
| **OFAC 不做系统筛查** | 摩根拦截**不免除 looply 责任**；本模块无法验证收货环节是否真的执行了人工筛查，也留不下凭证 | A16 |
| **仅自由文本备注** | 对账只能对到「打了多少钱」，对不到「为什么打」。争议或内部审计时无结构化业务依据 | A9 |
| **充值不入系统** | 查不到充值历史、无余额台账；只能翻银行流水 | A13 |
| **不建收款人档案** | 回头客每次重新录入；打款失败要换通道时手上没有该卖家的其他收款方式 | A8 |
| **不接 ACH** | 「Zelle 未注册 + 钱包未注册 + 开户行不支持 RTP」的卖家在 V1 无可用通道（RTP 覆盖约 71–75% 美国活期账户，缺口真实存在），单据挂起等待 | A1 |
| **打款日期用我方口径且不标时区** | 摩根按 ET 或 UTC 划账期，本地 23:50 成功的打款可能落在摩根次日账单，按日筛选时产生**假差异**。W3 确认后需重新评估 | A14/A13 |
| **告警不落库** | 推送失败在系统内不留痕迹 | 本期范围 |
| **防重复只提醒不拦截** | §2.5.1 的判定基于「收款人 + 金额 + 30 分钟」这种近似特征，不是真正的业务唯一性。两个运营在不同时段对同一卖家各录一次（超过 30 分钟）仍不会被提醒；且提醒不拦截，运营点过去就打出去了。**回收单上线后才能根治** | 用户 2026-09-03 拍板：只提醒不拦截 |
| **支付域暂不统一** | 财务要一次性取全量资金进出，本期需分别从两个模块取数再合并 | A11 |

| 重发 / 更新收款信息 | ✅ | ✗ |
| 打款对账 | ✅ | ✗ |
| 限额配置 | ✅ | ✗ |

> **✗ 不是权限限制，是页面不提供**——两个角色持有同一个权限点，差异仅在于移动端只渲染「发起打款」一条链路。
> ⚠️ 这意味着**任何持有该权限点的人在手机上都能发起不可撤销的打款**，且不加任何额外验证（A18 已接受的代价）。
