> **本 PRD 只写买家侧页面。** 售后域的业务规则、状态机、运营端页面、邮件模板由 **`售后` 模块 PRD v1.0** 承载，本文件引用不复述。

## 一、概述

### 1.1 背景与目标

售后域的运营端与业务链路已于 2026-08-02 交付开发 V1.0，但那一版**刻意不写买家侧页面**——买家能不能自己发起、发起后看到什么、看到的每一句话怎么取值，全部留给本需求。结果是：链路在系统内跑得通，买家在 App 和网页上却无处可看。

本需求补齐这一段，目标三件事：

1. **买家自己能发起**——在订单详情页看得到入口，不能申请时当场知道为什么，不用找客服；
2. **买家自己能查进度**——每一个售后状态都有一句买家看得懂的话，且与他能采取的动作对应；
3. **不外泄内部结论**——验货结论、责任归属、判责说明、审核意见一个字都不出现在买家侧（售后 PRD §2.1.3(9) 的安全边界，本 PRD 逐页落实）。

**V1 范围一句话**：订单详情页的售后入口与进度楼层 · 申请链路 4 屏 · Returns 列表 · Return details 详情 10 形态 · 两端（PC + 移动端）。

### 1.3 用户角色

| 角色 | 在本需求里做什么 |
|---|---|
| **买家** | 唯一使用者：发起售后、查看进度、修改被驳回的申请、待审核阶段撤销 |
| 运营 | 不使用本需求的页面。但运营在工单台的「买家时间线」弹窗里看到的，**就是本 PRD §2.1.2 定义的这一份**（售后 PRD §2.1.3(9)：运营端直接呈现买家侧那一份，不另做一套） |

### 1.4 核心场景

| # | 场景 | 一句话说清 |
|---|---|---|
| 1 | **多件订单发起售后** | 订单详情底部点 `Request a return` → 出选择商品半层 → 勾选可申请的商品行 → `Continue` 进填写页 → 选原因、填说明、传图 → 提交 → 成功提示告知拆成了几张单 |
| 2 | **单件订单发起售后** | 同上，但**可申请商品行只有 1 个时跳过选择半层**，直接进填写页 |
| 3 | **不能申请时当场知道原因** | 点 `Request a return` 后，整单无一件可申请 → 出说明层（6 种形态，命中单一原因给具体日期与规则数值，多原因给通用文案）；部分可申请 → 正常进选择半层，不可申请的行**在半层里置灰并标出原因** |
| 4 | **查进度** | 订单详情页 Returns 楼层 → 1 张单直接进详情、多张进按订单过滤的列表；或从个人中心 Returns 进全量列表 → `View Details` 进详情 |
| 5 | **被驳回后改了重交** | 详情页出琥珀提示条与驳回原因原文 → `Update My Request` 进修改页 → 只能改原因 / 说明 / 图，商品行不可改 → 重新提交 |
| 6 | **待审核阶段反悔** | 详情页 `Cancel Request` → 二次确认 → 落已关闭；仍在时效内可重新发起 |

### 1.5 全局页面流转

```
【发起】
  订单详情页 ──「Request a return」──▶ 无法申请说明层（整单无一件可申请）──「I Got It」──▶ 订单详情页
                                  └─▶ 选择商品层（可申请 ≥2 件）──「Continue」──▶ 售后申请填写页
                                  └─▶ 售后申请填写页（可申请 =1 件，跳过选择层）
  售后申请填写页 ──「Submit return request」──▶ 提交成功层 ──▶ 订单详情页 / Returns 列表

【查看】
  订单详情页 · Returns 楼层 ──（N=1）──▶ 售后详情页
                            └（N≥2）──▶ Returns 列表（按订单过滤）
  个人中心 ──「Returns」──▶ Returns 列表（全部）──「View Details」──▶ 售后详情页

【详情页内】
  售后详情页 ──「Update My Request」──▶ 售后申请修改页 ──提交──▶ 提交成功层 ──▶ 订单详情页
            ──「Cancel Request」──▶ 取消二次确认层 ──确认──▶ 售后详情页（已关闭态）
            ──「Start a new request」──▶ 售后申请填写页（带入本单商品行）
                                      └─（该商品行已不可申请）──▶ 无法申请说明层
            ──「怎么寄回 ?」──▶ 说明浮层
            ──「Return deduction ?」──▶ 说明浮层
            ──物流卡「›」──▶ 物流追踪弹窗（订单模块既有）
```

**新增页面共 3 个**：售后申请填写页（新建 / 修改两形态共用一页）· Returns 列表页 · 售后详情页 —— 另有**订单详情页的两处增量**（不是新页面）。

**以下均为浮层，不构成页面跳转**（两端形态不同，见各节）：无法申请说明 · 选择商品 · 原因选择器 · 提交成功 · 取消二次确认 · 怎么寄回说明 · Return deduction 说明。

### 1.6 术语说明

| 术语 | 定义 |
|---|---|
| **售后单** | 售后域的业务单据，一个订单商品行一张。买家侧标识为 `Return number`（形如 `RMA-20260730-0011`） |
| **半层 / 模态** | 同一个组件的两端形态：移动端为**底部半层**（Bottom Sheet），PC 为**页面居中模态**。两端形态刻意不同，不拉平 |
| **Returns 楼层** | 订单详情页上通向该订单售后单的入口块，本需求新增（§2.2.1） |
| **买家时间线** | 售后单进展的买家可见投影，是详情页顶部状态描述与 Returns 楼层副行的**唯一取值源**（§2.1.2） |
| **可申请商品行** | 该订单中同时满足售后 PRD §2.4.3 全部 5 条前置条件的商品行 |
| **Return deduction** | 售后 PRD 的「退货扣减」在买家侧的名称。**两端界面一律用这个词**，不出现「退货服务费」 |
| **未收到货白名单** | 售后 PRD §2.4.6 的 4 条系统预置原因码。**本需求在 C 端不展示这 4 条**（§2.3.2） |

### 1.7 多语言支持

本模块是**纯 C 端模块**，全部内容面向买家。

#### A. 静态 UI 文案

本模块的页面固定文案（标题、按钮、字段标签、说明段、状态标签、空态、校验提示、**买家时间线的事件标题与说明**）由**前端语言包**实现（语言包落地，运营可在多语言后台查看/修改）。

**英文即源文案**：looply 的源语种是英文，**本 PRD 各节写出的英文串就是最终展示文案**，开发直接实现；语言包只负责把它翻成其他语种。不给语言包 key（属开发侧实现细节），也不存在「最终以语言包为准」这种层级。

#### B. 动态业务内容 — 翻译服务接入

**B-1 字段接入清单**

本模块**自身不产生**任何需要接翻译服务的业务字段——页面上的动态值全部来自上游：

| 域名 | 卡片名 | 卡片编码（resource_type） | 字段 | 中文显示名 | 数据类型 | 展示面 | 备注 |
|---|---|---|---|---|---|---|---|
| 前端页面 | 售后 C 端页面文案 | `aftersale_page` | 页面静态文案 | 页面静态文案 | text | 本需求全部页面与浮层 | **本需求新增的唯一一张卡**。值由系统固定，运营不可增删 → 落语言包 |

**上游内容归属**（只声明归属，不代为列清单）：

- **售后原因展示文案** → 由 **售后域** 的 `aftersale_reason` 卡接入（售后 PRD §1.7 B-1 已登记）；C 端取的是**本单原因码快照**里的展示文案。
- **售后单状态展示名 / 关闭原因展示名** → 由售后域 `aftersale_enum` 卡接入（同上）。⚠️ 本模块的**状态标签文案不取该卡**——状态标签是买家侧独立的一套措辞（§2.1.1），属本模块静态文案。
- **驳回原因 / 关闭说明** → **不接入翻译服务**：运营手写的自由文本，系统原样展示（售后 PRD §1.7 已定，运营须用英文填写）。
- **买家补充说明（You Notes）** → **UGC，不翻译**，按买家原文展示。
- **商品标题、品牌名、成色等级名** → 由**商品模块**负责接入。
- **物流轨迹状态与描述** → 由**物流信息服务**定义与维护，前端按返回字段直接展示。

**B-2 建卡信息声明**

#### C. Fallback 规则

## 二、需求详细描述

> **两端形态的总口径（全文适用）**：**PC 与移动端不要求样式一致**。同一功能在两端可以是不同版式（半层 vs 模态、面包屑 vs 返回箭头、堆叠 vs 键值两列），这是刻意的端差异，**不得以「两端应一致」为由拉平，也不得因两端不一致判设计有误**。本 PRD 各节写的是**元素构成与展示口径**；位置、间距、字号、颜色一律**以 Figma 设计稿为准**。
>
> **设计稿金额与日期一律视为示例**：各帧数值相加对不上、前后帧未刷新，均不构成实现依据。

**时间展示口径（全文适用，硬性，2026-08-05 拍板 D3）**

本模块页面上出现的**全部时间**（提交时间、完成时间、关闭时间、退款完成时间、时效剩余天数的基准日、物流轨迹除外）统一按下表处理：

| 项 | 口径 |
|---|---|
| 存储 | 后端统一存 **UTC** |
| 展示时区 | **按该售后单所属 market 的「基准时区」渲染**，**不按买家浏览器本地时区**。基准时区是 market 模块的配置项（IANA 时区标识，如 `America/New_York`），**具体取值随配置走，本 PRD 不写死是哪个时区** |
| 展示粒度 | **只到日期**，形如 `Jul 29, 2026`。本模块**不展示时分**（设计稿两端全部帧均无时分） |
| 时区后缀 | **不标**（如 `PT` / `HKT`）。仅到日期粒度时标时区没有意义，且设计稿未画 |
| 物流轨迹时间 | **例外，不适用本口径**：由物流信息服务返回什么就展示什么，本 PRD 不定义（与订单 PRD v1.5 §1.4 的处置一致） |

**为什么按 market 时区而不按浏览器时区**：买家、客服、运营三方看到的必须是**同一个日期**。按浏览器时区渲染时，一个出差到欧洲的美国站买家看到的日期会和客服后台差一天，对单时说不清是哪一天提交的。

**⚠️ 一个 market 可能横跨多个时区，所以只能取「基准时区」这一个值（硬性）**

`market 主数据 PRD v1.0` 明确写着「**一个国家可对应多个时区（如美国有 4 个时区）**」，并为此设计了三层：

| 层级 | 字段 | 本模块用不用 |
|---|---|---|
| Market 级 | **基准时区**（Market 的默认时区） | ✅ **只用这一个** |
| 国家级 | 本地时区覆盖（国家可选覆盖） | ❌ 不用 |
| 时区表 | IANA 标识 + 时区名称 | 仅作为基准时区的取值来源 |

⛔ **开发不要按下列任何一种去算时区**：买家收货地址所在时区 · 买家账号国家的本地时区 · 订单发货地时区 · 服务器时区。
**只读 market 的基准时区一个值。** 否则同一个 market 里不同州的买家会看到不同日期，客服照样对不上。

> ⚠️ **已知的跨模块口径分歧（必须让开发知道）**：`订单列表详情 PRD v1.5` §1.4 现行口径是「按**买家浏览器本地时区**渲染并标注时区」。**本模块与之不一致**——同一个买家在订单详情页与售后详情页看到的日期**可能差一天**。该分歧需与订单模块对齐，已记 §三 风险与待优化清单。**在对齐之前，本模块按本表实现，不要自行改成跟订单一致。**

### 2.1 公共组件

以下四项被多个页面引用，集中定义一次，各页引用不重复。

#### 2.1.1 售后状态在买家侧的映射（状态标签）

售后单状态共 7 个（售后 PRD §2.4.1）。买家侧**不直接展示这 7 个内部状态名**，而是映射为 8 个状态标签——「待审核」按是否正等买家修改拆成两个，这是买家唯一需要动手的区分。

| # | 售后单状态（内部） | 派生条件 | C 端状态标签文案（英文源文案） | 买家要不要动手 |
|---|---|---|---|---|
| 1 | 待审核 | 未被驳回过，或已重新提交、等再审 | `Pending review` | 否 |
| 2 | 待审核 | **当前正等买家修改**（判据见下） | `Action needed` | **是** |
| 3 | 待寄回 | — | `Awaiting your shipment` | **是** |
| 4 | 退货在途 | — | `On its way to us` | 否 |
| 5 | 待判责 | — | `Being checked` | 否 |
| 6 | 退款中 | — | `Refund on the way` | 否 |
| 7 | 已完成 | — | `Completed` | 否 |
| 8 | 已关闭 | 三种关闭来源**共用一个状态标签** | `Closed` | 否 |

**「当前正等买家修改」的判据**（引用售后 PRD §2.5.8，不另立口径）：状态 = 待审核 **且** 最近一条审核记录结论为驳回 **且** 买家最近一次重新提交时间为空或早于该条审核时间。买家一旦重新提交，状态标签即回到 `Pending review`。

> ⚠️ **状态标签不区分关闭来源**：买家撤销、运营关闭、拒退关单三种来源在列表上都是 `Closed`，差异由详情页的状态描述承载（§2.5.2）。
> ⚠️ **不出「退款失败」状态标签**：退款执行失败时售后单仍为「退款中」（售后 PRD §2.8.5），买家侧照常显示 `Refund on the way`（§三 风险 4）。
> ⚠️ 设计稿列表帧（`745:9228` / `745:10530`）只示例了其中 6 个状态标签，**未出现 `On its way to us` 与 `Being checked`**——那是示例数据只画了 6 张卡，不是这两个状态不展示。两者复用同一套标签样式，无需另行出稿。

#### 2.1.2 买家时间线（事件全集）

**为什么必须在这里定义**：售后 PRD §2.1.3(9) 把时间线的事件清单与文案明确划给 C 端需求，而运营端「买家时间线」弹窗**直接呈现这一份**、不另做一套。本节因此同时服务三个消费方：

| 消费方 | 用它的哪一部分 |
|---|---|
| 售后详情页顶部状态区 | **当前生效事件**的「状态描述」+「补充说明」两行（§2.5.1 A 区） |
| 订单详情页 Returns 楼层（N=1） | **最新一条事件**的「楼层摘要」+ 发生日期（§2.2.1） |
| 运营端「买家时间线」弹窗 | 全部事件，从新到旧 |

**事件全集（13 条）**

**本期时间线不承载的两件事**

| 不出的事件 | 理由 |
|---|---|
| **退款执行失败** | 售后 PRD 的操作记录把「退款失败回传」标为买家可见，但买家侧**没有任何可采取的动作**，且失败原因（如原卡已注销）属支付渠道信息。本期时间线**不出该事件**，买家侧维持事件 9 的展示，直到重发成功落事件 10。该口径与售后 PRD 操作记录的可见性标记存在差异，已记 §三 风险 4 |
| **历次驳回** | 只展示**最近一次**驳回原因，历史驳回不在买家侧留痕（与售后 PRD §2.5.4「C 端只展示驳回原因」一致） |

**本浮层的内容边界（硬性）**

| 不写 | 为什么 |
|---|---|
| **退货运费的归属**（「不是运费 / 运费我们出」） | 本浮层只在**退款中 / 已完成**出现——货早已寄回、运费问题在此时已无意义。买家在这一屏关心的是「这笔钱为什么被扣」，不是「运费谁出」 |

- 📌 **文案待产品最终确认**：上述两段为本轮定稿版本，产品已说明后续可能再调整措辞。**调整只动文案、不动上表的内容边界**——边界是规则，措辞不是。

#### 2.2.1 Returns 进度楼层

**功能描述**

订单详情页上通向该订单售后单的唯一入口块。整块可点。

**前置条件**

该订单下存在**至少 1 张应计入的售后单**（计数口径见下）。

**页面布局**

位置：**订单标识信息之后、第一个商品分组之前**，与商品分组平级、不嵌在任何卡片内。两端位置一致（`745:3072` / `745:11803`）。

**页面元素**

| 元素 | 内容 | 出现条件 |
|---|---|---|
| 图标 | 售后图标（圆形底） | 恒出 |
| 标题 | `Returns` | 恒出 |
| 副行 | 见下方「副行取值」 | 恒出 |
| 右侧箭头 | `›` | 恒出 |

**副行取值（两种形态）**

| 形态 | 副行内容 | 说明 |
|---|---|---|
| **N = 1** | **该售后单当前生效事件的「楼层摘要」+ `·` + 事件发生日期** | 取值源为 §2.1.2 事件全集的「楼层摘要」列。例：`Return label ready — drop it off at FedEx · Jul 30` |
| **N ≥ 2** | `{N} return requests on this order` | 只给条数，**不展示任何单据的状态与进展**——多张单进展各异，楼层放不下也不该替买家挑一张 |

**N 的计数口径（硬性）**

- **N = 该订单下「非已关闭」的售后单数** = 5 个非终态（待审核 / 待寄回 / 退货在途 / 待判责 / 退款中）+ 已完成。
- **已关闭一律不计**，三种关闭来源（买家撤销 / 运营关闭 / 拒退关单）都不计。
- **N = 0 时整个楼层不渲染**——不是置灰、不是显示「0 条」。
- **已完成必须计入**：删掉商品行级售后表达后，楼层是订单页通向售后历史的唯一路径，买家事后回查「我当时退了多少钱」必须有入口。

> **已知代价（已接受）**：订单若只申请过一次且被关闭，订单详情页回到完全没有售后痕迹的状态，买家只能从个人中心 Returns 列表找回。

**操作流程**

| N | 点击后 |
|---|---|
| 1 | 直接进入**该售后单的详情页**（§2.5） |
| ≥ 2 | 进入 **Returns 列表页的「按订单过滤」形态**（§2.4） |

> 与底部申请入口「只有 1 件可申请就跳过选择层」是同一套逻辑：**能唯一确定目标时就不让买家再选一次**。

**异常处理**

| 场景 | 处理 |
|---|---|
| 售后数据加载失败 | 楼层不渲染，不阻断订单详情页其余部分 |
| 楼层展示后单据状态已变（如唯一一张单刚被关闭） | 点击后按**跳转时**的实际数据决定落点；若已无应计入的单，进入 Returns 列表的按订单过滤形态并展示该订单的历史单据 |

**UI 关联**：移动端 `745:3072`（N=1）/ `745:6493`（N≥2）；PC 端 `745:12338`（N=1）/ `745:11803`（N≥2）。

#### 2.2.2 申请售后入口（Request a return）

**功能描述**

订单详情页底部操作区的售后发起入口。

**前置条件（硬性）**

**按订单状态判定，`order_status ∈ {shipped, completed}` 时展示，其余状态不展示。**

| order_status | 列表页标签 | 是否出 `Request a return` | 说明 |
|---|---|---|---|
| `pending_payment` | Placed | ❌ | 还没付钱 |
| `paid` | Confirmed | ❌ | 未发货，走订单取消 / 发货前退款（订单域） |
| **`shipped`** | **On its way** | ✅ | — |
| **`completed`** | **Completed** | ✅ | — |
| `cancelled` | Cancelled | ❌ | 订单已取消 |

- **为什么用订单状态而不是「有没有已发货商品行」**：两者等价——只要订单内有**任意一件**商品发货，订单即流转为 `shipped`（订单 PRD v1.5 §6.3：该状态下可同时存在已发货组 + 待发货组 + 退款组）。用订单状态表述与订单模块口径一致，也免得开发再去逐行聚合一遍。
- **一个订单只有一个入口**，不按商品行分别给入口。哪些商品行能退，由点击后的分流与选择层回答。
- **不以签收为门槛判断入口是否展示**——入口照常出，是否可申请由点击后的资格判定回答（§2.2.3）。

**页面元素**

| 端 | 位置与构成 |
|---|---|
| PC | 底部操作区，`Request a return`（次按钮，左）+ `Continue Shopping`（主按钮，右） |
| 移动端 | 底部操作区，`Continue Shopping`（主按钮，上）+ `Request a return`（次按钮，下） |

> 两端按钮的排列顺序刻意不同，属端差异，不拉平。`Continue Shopping` 是订单 PRD v1.5 §3.8 的既有按钮，本需求只在其旁**新增** `Request a return`。

**操作流程（点击后的分流，硬性）**

系统按售后 PRD §2.4.3 的 5 条前置条件逐个商品行判定资格，然后**两级判断**：

**第一级 —— 看整单可申请商品行数**

| 可申请商品行数 | 走向 |
|---|---|
| **0** | 出**无法申请说明层**（§2.2.3），不进入申请链路 |
| **> 0** | 进入第二级判断 |

**第二级 —— 看订单内商品行总数（不是可申请数）**

| 订单内商品行总数 | 走向 |
|---|---|
| **1** | **跳过选择商品层，直接进入售后申请填写页**（§2.3.1），该商品行为本次申请对象 |
| **> 1** | 出**选择商品层**（§2.2.4） |

> ⚠️ **第二级的判据是「订单内一共有几件」，不是「有几件能退」**（硬性）。
> 一个 3 件的订单里 2 件已退过、只剩 1 件可申请时，**照样要进选择层**——因为买家需要在那一屏看到另外两件为什么是灰的（`Already refunded on…`）。直接跳进填写页，买家会以为这个订单本来就只有一件商品，另外两件凭空消失了。
> 只有**订单本身就只有一件商品**时才跳过选择层——那时没有"其他商品"需要解释。

**分流一览（两级合起来看）**

| 订单内商品数 | 可申请数 | 走向 |
|---|---|---|
| 1 | 0 | 无法申请说明层 |
| 1 | 1 | 直接进填写页 |
| ≥2 | 0 | 无法申请说明层 |
| ≥2 | 1 | **选择层**（其余置灰并标原因） |
| ≥2 | ≥2 | 选择层 |

**异常处理**

| 场景 | 处理 |
|---|---|
| 资格判定失败 | 提示 `Something went wrong. Please try again.`，不进入任何后续层 |
| 点击时资格已变（如另一端刚提交过） | 以点击时重新判定的结果为准；提交时再判一次（售后 PRD §2.4.9 校验 2/3 的「进入申请入口时 + 提交时」两道） |

**UI 关联**：移动端 `745:3072` / `745:6493` 底部；PC 端 `745:12338` / `745:11803` 底部。

| 说明 | 见下表 |

**六种形态的英文源文案**

| 1 | Final Sale | 命中的政策「是否支持退货」= 不支持（售后 PRD §2.2.2） | `This item was a Final Sale` | `Final sale items can't be sent back once they've reached you. If the package never arrived, or the item was missing from it, you can still contact us by email and ask for a refund and tell us what happened.` |
| 2 | 超时效 | 已超出售后时效窗口（售后 PRD §2.4.5 拦截③） | `The return window for this item has closed` | `Returns need to be requested within {WindowDays} days of delivery. This item was delivered on {DeliveredOn}, so the window closed on {WindowClosedOn}.` |
| 3 | 已有进行中单 | 该商品行已有非终态售后单（拦截①） | `There's already an open return for this item` | `You can only have one return open per item at a time. Follow the one you've already started.` |
| 4 | 已退成过钱 | 该商品行存在已完成的售后单（拦截②） | `You've already been refunded for this item` | `We refunded this item on {RefundedOn}. Each item can only be returned once, so this one can't be sent back again.` |
| 5 | **整单未签收** | **该订单内不存在任何已签收的商品行**（判据见下） | `This order hasn't been delivered yet` | `We can't start a return online until your package is delivered. If it's lost, or the tracking says delivered but nothing arrived, contact us — our team can start the return for you.` |
| 6 | 多原因通用 | 一单内存在 ≥2 种不同的不可申请原因 | `None of the items in this order can be returned right now` | `Something about this order means it can't be returned online right now. If you think that's not right, our team can take a look.` |

**变量取值**

| 变量 | 取值来源 |
|---|---|
| `{WindowDays}` | 本单命中政策的**售后时效天数**（market 级配置，不写死） |
| `{DeliveredOn}` | 订单域的包裹签收时间 |
| `{WindowClosedOn}` | `{DeliveredOn} + {WindowDays}` |
| `{RefundedOn}` | 该商品行已完成售后单的退款完成时间 |

> 🔒 **形态 3 的说明只写到「跟进已有的那一张」为止（防拆注记）**：不得再补「等它结束了就能重新申请」这类话。
> 那张在途单的**两个终点结论正好相反**——走到「已完成」= 钱已退出去 → 该商品行**永久不可再申请**（售后 PRD §2.4.5 拦截②）；只有走到「已关闭」才能在时效内重申。
> 一句「once it's finished」把两种相反的结果说成了同一种，会给买家错误预期。

**形态 5「未签收」的判据（硬性）**

- **触发判据**：**该订单内不存在任何已签收的商品行**。
  - 只要有**任意一件**已签收，就不走本形态——那件可以申请，走正常分流（可申请数 > 0）。
  - 部分商品行未签收时，那些行在**选择层里置为禁用**并标 `Not delivered yet — contact us if it's lost`（§2.2.4 禁用原因 1）。
- **签收状态取订单域的包裹签收时间**（售后 PRD §2.4.4：签收时间取订单域的包裹签收时间，不跨域调物流服务取）。

**形态 5 是本需求对 C 端自助入口的收窄（硬性说明）**

- **C 端**：未签收的商品行**不允许买家自助发起售后**。
- **业务能力不变**：包裹丢件、显示已送达但未收到确实存在，**仍允许走售后，由运营代操作建单**。
- **与售后 PRD 的关系**：售后 PRD §2.4.3 前置条件第 1 条是「该商品行**已发货**」、售后 PRD §2.4.4 写明「发货后即可申请，**不以签收为门槛**」。本条**只收窄 C 端自助入口，不改售后域能力**。

**⚠️ 由此存在的运营侧缺口（已知敞口，本需求不解决）**

核实结论（`售后 PRD v1.0` 全文）：运营端**只有一个建单入口**「超期特批建单」（§2.1.3(6)），适用范围写死「仅用于**已超出政策时效窗口**的订单」；而未签收的单**时效根本没起算**（售后 PRD §2.4.4「未签收期间不启动计时」）→ 不命中拦截条件③ → **够不着这个入口**。

**结果：C 端关了、运营端也进不去，整单未签收的买家在系统内无法自助发起售后**，只能靠客服线下推动。

| 项 | 口径 |
|---|---|
| 本需求怎么处理 | **不解决、不承载**。本 PRD 只把 C 端的收窄规则写清楚（形态 5），**不定义运营端建单入口** |
| 归谁 | **售后模块**。缺口、候选方案与影响范围已记 `售后/待优化清单.md` **第 38 条**，由产品**单独处理** |
| 开发要知道的 | 本需求上线后，**整单未签收的售后诉求在系统内没有自助入口**，需走线下客服。这是**已知且已接受的敞口**，不是漏做 |

**异常处理**

| 场景 | 处理 |
|---|---|
| 三级政策均未命中（售后 PRD §2.4.9 校验 8） | **不落任何默认政策、也不判「不可申请」**，出通用形态但说明改为：`We can't start this return online right now. Please contact us and our team will take a look.` |

**UI 关联**：移动端 `745:6747` / `745:7935` / `745:8192` / `745:8451` / `745:8710` / `745:8969`；PC 端 `745:12873` / `745:16647` / `745:13400` / `745:15591` / `745:15063` / `745:16119`（顺序对应形态 1→6）。

**功能描述**

**「Reason」必填与举证必填的联动（硬性）**

- `Add photos` 是否必传，取**买家选中的那条原因码的「是否必传举证」配置**（售后 PRD §2.3.2）：必传 → 标题带 `*` 且提交时校验非空；选传 → 无 `*`、可不传。
- **未选原因码时**，`Add photos` 按**必传**展示（带 `*`），避免买家先传后发现不用传。

**扣减告知条（英文源文案）**

> `A return deduction of about {ServiceFee} applies to each refund.`
> `The exact amount is confirmed after we check the item.`

- `{ServiceFee}` 取**命中政策的退货服务费金额**（market 级配置）。
- **恒出**：本期 C 端不展示未收到货原因（§2.3.2），所有从 C 端发起的申请都走寄回分支，因此不存在「不告知服务费」的情形。
- ⚠️ **告知值与最终实扣之间不设任何一致性约束**（售后 PRD §2.7.8）：实扣由运营在判责时手填，偏离多少都不改变流程走向。本条文案已含「确切金额验货后确认」的表述，不再另加提示。

**多商品形态的口径（硬性）**

- 选中 N 件时，本页**只填一份**原因 / 说明 / 举证，**提交后 N 张单共用这一份内容**。
- **不支持逐件填写不同原因**——一次退多件通常是同一批问题；要分别说明只能分次申请。

**校验规则**

| 字段 | 规则 | 校验时机 | 不通过 |
|---|---|---|---|
| Reason | 必选一条**启用中**的原因码，且只能选一条 | 提交时 | 阻断，定位到该项 |
| Anything else | 上限 300 字符；前后空格自动去除 | 输入时 | 超出不可继续输入 |
| Add photos | 选中原因码要求必传时不得为空 | 提交时 | 阻断 |
| Add photos | 最多 6 张；单张 ≤ 10 MB；格式 JPG / PNG | 选择文件时 | 提示 `Some files couldn't be added. Use JPG or PNG under 10 MB.` |
| 资格复检 | 按售后 PRD §2.4.9 全部 8 条重新校验 | 提交时 | 阻断，提示对应原因 |

**操作流程**

1. 选原因 → 填说明（可选）→ 传图。
2. 点 `Submit return request`。
3. 系统按售后 PRD §2.4.8 建单：按商品行拆成 N 张、状态 = 待审核、冻结政策快照与原因码快照。
4. 出**提交成功层**（§2.3.4）。**本环节不发任何邮件**（售后 PRD §2.10.2）。

**异常处理**

| 场景 | 处理 |
|---|---|
| 上传失败 | 该张不进列表，提示 `Upload failed. Please try again.`，不影响已传的其他图 |
| 提交时某商品行资格已失效 | 阻断并提示 `One of the items you selected can no longer be returned. Please go back and select again.` |
| 提交超时 / 网络异常 | 保留已填内容，提示 `Something went wrong. Please try again.`；**不得重复建单** |

#### 2.3.2 原因选择器（Reason）

**功能描述**

从原因码字典里选一条售后原因。

**两端形态**：移动端底部半层 / PC 居中模态。

**页面元素**

| 元素 | 内容 |
|---|---|
| 标题 | `Reason` |
| 关闭 | `×` |
| 选项列表 | 一条一行，展示**原因码的展示文案**；当前已选项高亮 |

- **平铺单层清单，没有分组、没有前置选择题**——分岔判据是买家选中的那条原因码本身（售后 PRD §2.4.6），不再问「货收到没有」。
- 选中即回填到填写页的 `Reason` 行并关闭本层。

**选项取值范围（硬性，本需求的关键收窄）**

C 端展示的原因码 = **原因码字典中「启用」的条目，减去「未收到货白名单」的 4 条**。

| 判据 | 说明 |
|---|---|
| 过滤依据 | **以售后 PRD §2.4.6 的未收到货白名单为唯一判据**（那 4 条原因码），命中即不展示。**不新增「C 端是否展示」配置字段** |
| 禁止的实现方式 | ⛔ **不得用前缀 / 通配符 / 字符串匹配推断**（`ASR_` 是中性前缀，不携带分组含义）——与售后 PRD §2.4.6 同一条硬性约束 |
| 排序 | 按原因码字典的「排序」值升序（数值越小越靠前） |
| 展示文案 | 取原因码字典的「展示文案」；建单后本单一律取**原因码快照**里的那一份 |

**为什么 C 端不展示这 4 条**

买家在 C 端**未签收就不允许自助发起售后**（§2.2.3 形态 5 / §2.2.4 禁用原因 1）。既然未签收的单进不来，「显示已送达但未收到 / 运输中丢件 / 包裹为空 / 投递失败退回」这 4 条在 C 端就没有可成立的使用场景——留着只会让已签收的买家误选，导致系统判定他不用寄货、而货其实在他手上。

**连带后果（必须让开发知道）**

| 后果 | 说明 |
|---|---|
| **「不需寄回分支」在 V1 的 C 端永远走不到** | 售后 PRD §2.4.7 分支 B（跳过待寄回与退货在途、直接进待判责）**只能由运营代建单进入**。分支本身照常实现，入口收窄 |
| **白名单的不可停用约束依然成立** | 售后 PRD §2.3 要求这 4 条不可删除 / 不可改码 / 不可停用——**该约束不因 C 端不展示而放宽**：运营代建单时仍要选得到，且历史单靠快照回显 |
| **「其他」（`ASR_OTHER`）照常展示** | 它是普通原因码、走寄回（售后 PRD §2.4.6），不受本条过滤影响 |

> ⚠️ **设计稿 `745:6320` / `745:18297` 的选项清单为示例数据**（12 条，含 4 条未收到货原因），**不构成需求定义**。C 端实际展示的条目由运营在后台配置 + 本节的过滤规则共同决定，开发**不得把设计稿上的清单硬编码进代码**。

**为什么不做成「C 端是否展示」配置字段（决策留痕，2026-08-05 拍板 D2）**

评估过的另一方案：在原因码字典上加一个「C 端是否展示」开关，由运营配置。**已否决，维持白名单判据。**

| | 白名单判据（**采用**） | 新增配置字段（否决） |
|---|---|---|
| 改动面 | 零新增，**不动已交付的售后运营端 V1.0** | 需改售后运营端原因码配置页与字典结构，影响已交付范围 |
| 误配风险 | 白名单是**系统常量**，运营改不动 | 运营可能把 4 条白名单误配成"展示"，买家又能选到"没收到货"→ 系统判他不用寄货、而货在他手上 → 需额外把这 4 行锁死，等于又加一层特例 |
| 灵活性 | **低**：「走不走寄回」与「前台给不给看」绑死 | 高：两件事解耦，将来想单独藏某条普通原因码可直接配 |
| 规则可见性 | **低**：规则只存在于 PRD 与代码里，运营在后台看不到"这 4 条为什么 C 端没有" | 高，运营能在配置页看见 |

**接受的代价（两条，须写进运营手册）**：
1. 将来若要「允许 C 端选丢件、但仍不寄回」，或想在 C 端藏掉某条普通原因码，**都要改代码**，不能靠配置解决。
2. 运营在原因码配置页**看不出**这 4 条在 C 端是隐藏的 → **要求在售后运营端原因码列表的这 4 行加一句只读说明**（如「系统预置 · C 端不展示」）。该说明属售后运营端改动，已记待优化清单。

| 场景 | 处理 |

| 原因码字典加载失败 | 层内展示 `Couldn't load reasons. Please try again.` + 重试入口 |
| 已选原因码在填写过程中被运营停用 | 提交时按售后 PRD §2.4.9 校验 5 阻断，提示 `That reason is no longer available. Please choose another one.` |

| 为什么不回订单详情页 | 说明 |
|---|---|
| **会绕成一个圈** | 已关闭的单不计入 Returns 楼层的 N（§2.2.1 计数口径排除已关闭）。买家从楼层点进这张单、再点重新申请、又被送回订单页——而那个订单页上这张单根本不显示，他只能再点一次底部入口重走一遍。**多绕两步，且中途看不到自己刚才那张单** |
| **目标商品行本来就是确定的** | 重新申请的对象就是这张单退的那件商品，系统已经知道是哪一件，没有需要买家再选一次的信息 |

**点击时必须先判资格**（不能直接把不可申请的商品行塞进表单）：

| 该商品行当前资格 | 走向 |
|---|---|
| **可申请** | 直接进填写页，商品行已带入 |
| **不可申请** | 出**无法申请说明层**（§2.2.3）的对应形态，说明为什么现在不能重申（最常见：`The return window for this item has closed`——单是关了，但时效也过了） |

> ⚠️ 判资格发生在**点击的那一刻**，不是渲染按钮的时候：按钮**恒出**（不因不可申请而隐藏或置灰）。理由——买家需要知道"为什么不能"，而不是面对一个消失的按钮；这与 §2.2.2 底部入口「入口照常出、点了才告诉你为什么」是同一套口径。

| 元素 | 内容 |
|---|---|
| 标题 | `What we need you to change` |
| 正文 | **驳回原因原文**（`{RejectionReason}`），原样展示、不加工、不翻译 |
| 时效行 | `Your return window is open for another {DaysLeft} days.`；`{DaysLeft} ≤ 0` 时整行不展示 |

> ⚠️ **只展示最近一次驳回原因**，历次驳回不在买家侧留痕。
> ⚠️ **绝不带出「审核意见」**——它与驳回原因是两个字段、对外性相反（售后 PRD §2.5.5），取数层就要切干净。

**B 区 · 寄回指引卡（d3）**

| 卡头标题 | `How to ship it back` | 恒出 |

- ⚠️ **本页不展示退货地址**：本期走线下预约预付面单，买家到承运商网点出示运单号、由网点贴单，**不需要地址**。退货地址仍随「退货运单号与退货地址」邮件发出（售后 PRD §2.10.3 第 3 封），两个渠道**不要求内容一致**。

## 三、依赖与风险

### 3.1 上下游依赖

> 每条只写**业务能力与归属**，以及本需求对它的**关键要求**；对接形态属技术方案范畴。

| 依赖方 | 本需求依赖的能力 | 我对它的关键要求 |
|---|---|---|
| **售后域**（售后 PRD v1.0） | 售后单数据、状态机、政策快照与原因码快照、判责与退款结果、关闭说明与驳回原因 | ① 需能**按订单**与**按买家**两个维度查售后单，并返回本 PRD 各页所需字段；② **买家可见字段与内部字段必须在取数层就切开**——验货结论、判责说明、责任归属、审核意见绝不能出现在返回给 C 端的数据里，不能靠前端不渲染；③ 需提供**剩余时效天数**的计算依据（政策快照时效天数 + 订单签收时间）。**本需求不要求售后域新增任何能力**——运营侧代建单入口的缺口归售后模块自行处理（§三 风险 3） |
| **订单域**（订单列表详情 PRD v1.5） | 订单详情页、商品行发货与签收状态、商品行实付金额、订单快照的商品图与标题 | ① 订单详情页需为本需求**预留两处落点**：Returns 楼层（订单标识信息之后、第一个商品分组之前）与底部 `Request a return` 按钮；② 需能按商品行提供**发货状态与签收时间**，它是入口展示与未签收判定的唯一依据；③ **物流追踪弹窗**需支持传入退货运单号打开（d4 形态复用该弹窗） |
| **物流信息服务** | 退货运单的轨迹与状态 | 轨迹的**状态名与描述由该服务定义与维护**，本需求按返回字段直接展示、不自建枚举、不做翻译 |
| **个人中心模块** | 账户菜单 | 需在账户菜单新增 `Returns` 项指向本需求的列表页（§2.6）。**这是本需求上线的前置条件**——不加菜单项，买家从个人中心找不到售后 |
| **多语言 / 翻译中心** | 卡片建卡与字段注册 | 需为本需求新建 `aftersale_page` 卡并把聚合组 `aftersale` 成员数由 3 改为 4（§1.7 B-2/B-3）。**字段注册完成是本需求上线的前置里程碑** |
| **商品域** | 商品标题、品牌名的多语言 | 由商品模块负责接入，本需求只读取；未接入的语种按 Fallback 回退英文源文 |
| **销售市场 Market** | market 主数据的**基准时区** | 本模块**全部时间按售后单所属 market 的基准时区渲染**（§二 开头「时间展示口径」）。关键要求：① 需能**按 market 取到基准时区**（IANA 标识）；② **一个 market 只取这一个值**——market 自身已声明「一个国家可对应多个时区（如美国有 4 个）」，本模块**不下钻到国家级的本地时区覆盖**。⚠️ market PRD 原文说基准时区「影响后台时间展示和报表统计」，**本需求把它的用途扩到了 C 端展示**，需与 market 模块知会一声 |

### 3.2 风险与已接受的代价

| # | 风险 | 影响 | 本期处置 |
|---|---|---|---|
| 1 | **「按订单过滤」形态与「全部」形态外观完全一致** | 买家从 Returns 楼层进来后，分不清在看这个订单还是全部，也没有一键回全部的出口 | **已接受**（2026-08-05 产品拍板不补稿）。结果要求：两种形态除数据范围外**表现完全一致**，后续补标识时同步生效。已记待优化清单 |
| 2 | **「怎么寄回」浮层缺多件合寄说明** | 一单拆多张、共用一个运单号时，只看 C 端的买家可能分别寄 N 个包裹，产生多余运费与到仓混乱 | **已接受**（同上）。缓解：邮件第 3 封含该说明。已记待优化清单 |
| 3 | **未签收不允许 C 端自助申请，运营侧也进不去** | C 端关了、运营端「超期特批建单」限定「已超时效」也够不着 → **整单未签收的买家在系统内无自助入口**，只能靠客服线下推动 | **本需求不解决**（2026-08-05 拍板）。缺口与候选方案已记 `售后/待优化清单.md` 第 38 条，**由产品单独处理**。⚠️ 开发按现状实现，不要自行在运营端加建单入口 |
| 4 | **退款失败对买家不可见** | 售后单停在「退款中」、买家侧持续显示 `Refund on the way`，实际钱一直没到。若反复失败（原卡注销等），买家会长期看到一个不会变的进度 | **已接受**。理由：买家侧无任何可采取的动作，披露失败原因也不解决问题。缓解靠运营在工单台的「退款失败待重试」KPI 卡主动处理。⚠️ 该口径与售后 PRD 操作记录把「退款失败回传」标为**买家可见**存在差异，以本 PRD 为准，已记待优化清单 |
| 5 | **C 端不展示未收到货 4 条原因码** | 「不需寄回分支」在 V1 的 C 端永远走不到，只能由运营代建单进入。买家「确实没收到货」时只能走客服 | **刻意设计**（与风险 3 是同一个决策的两面）。已在 §2.3.2 写明连带后果 |
| 6 | **拒退关单的理由不对买家展示** | 买家只看到「不予退款 + 商品回寄」，理由需客服人工答复 | 沿用售后 PRD §3.2 风险 7 的既定取舍，内部判责说明绝不外露 |
| 7 | **退货地址不在 C 端展示** | 买家若把邮件删了，C 端查不到退货地址 | **已接受**：本期走线下预付面单，买家到网点出示运单号即可，不需要地址。⚠️ 售后 PRD §2.6.4 写的是「C 端同步展示运单号与**退货地址**」，本 PRD 收窄为只展示运单号，**售后 PRD 该句需同步修订**，已记待优化清单 |
| 8 | **一次多件只填一份原因** | 买家想为不同商品填不同原因时只能分次申请 | 已接受，V1 不做逐件填写 |
| 9 | **时区口径与订单模块不一致** | 本模块按 **market 基准时区**渲染（D3），订单模块 §1.4 按**买家浏览器本地时区**并标时区。同一买家在订单详情页与售后详情页看到的日期**可能差一天**（例：一个美国站买家人在欧洲出差，订单页按他当地时区可能显示 Jul 30、售后页按 market 基准时区仍是 Jul 29） | **已确认处置（2026-08-05）**：**订单模块计划把 §1.4 改为 market 时区口径**，本模块的口径即为**对齐后的目标态**，按本 PRD 实现即可、不必等。⚠️ 在订单 PRD 改完之前，两页日期可能短暂不一致，属**已知的过渡态**，不是缺陷、不要报 bug |
| 10 | **C 端不展示未收到货 4 条，规则只存在于 PRD 与代码** | 运营在售后后台的原因码配置页**看不出**这 4 条在 C 端是隐藏的，可能误以为买家能选到 | **已接受**（D2，见 §2.3.2 方案对比）。缓解：要求售后运营端在这 4 行加只读说明「系统预置 · C 端不展示」，已记待优化清单 |

| **逐件填写不同原因** | 多件申请时分别填原因与举证 | 有实际诉求时 |

## 五、数据与埋点

**本期不定义，故省略。**

理由：本需求是**已交付售后链路的买家侧补齐**，V1 的首要目标是把链路跑通并让买家看得见，尚无待验证的转化假设。售后数据看板列在售后 PRD §4.2 的 V2，届时再一并定义 C 端埋点事件与指标口径，避免现在先埋一批没人看的点。

## 六、权限与角色矩阵

**本模块不涉及，故省略。**

理由：本需求的使用者只有**买家**一类，且只能访问自己的售后单——这属**数据归属**（§2.6 已写明越权访问一律按「不存在」处理），不是权限矩阵。运营端权限归售后 PRD §六。
