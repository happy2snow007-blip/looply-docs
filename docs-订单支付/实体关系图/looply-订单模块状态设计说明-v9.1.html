1. 设计概览

订单模块采用分层状态模型：订单级只管生命周期（order_status），发货和退款维度下沉到商品级（order_item），订单级需要展示时实时聚合，不落库、不同步、零不一致风险。

退款维度：这件商品退了没
为什么发货/退款不存在订单表？
v5.x 的设计在订单和商品两层都存 fulfillment_status + refund_status，需要同步链路保证一致性。v6.0 砍掉订单层的这两个字段，商品级是唯一事实源。订单列表需要「部分发货」筛选时，用 GROUP BY order_id + HAVING 从 order_item 实时聚合。0-1 阶段订单量小，聚合代价几乎为零；后续量大时可加物化视图或缓存字段，不改数据模型。
待付款在父订单层 · 支付后拆单（v9.1 变更）
为支持卡支付命中渠道风控审核（pending review）等异步到账场景，下单即创建整体订单 parent_order，起始 parent_status = pending_payment。待付款期间只有父订单、不拆子订单——买家一次下单在列表里只显示一条、只需完成一次支付。支付到账后 parent_order 转 paid，此时才按商家拆出子订单 order（起始即 paid）。
v9.1 变更原因：若下单即拆单，未支付时买家回到订单列表会看到多条待付款订单、需付多次款，体验割裂。改为支付后拆单后，待付款态归属父订单，子订单 order 不再有 pending_payment。一物一件商品在提交支付时锁定，未提交付款超时（30 分钟）自动关单释放；已提交付款进入渠道审核（payment_order = processing）的不受此超时影响，等渠道回调决定结果。
上下游交互链路：渠道 → 支付单 → 订单
订单不直接与三方渠道交互。渠道回调只落到支付单（payment_order），由支付单联动订单状态变化。订单侧只感知支付单状态，不感知渠道。

为什么用两个独立字段？
发货和退款是两个独立维度，各自流转互不耦合。如果用单字段，「已发货但正在退款」无法表达（只能取一个值）。拆成两个字段后，fulfillment_status = shipped + refund_status = refunding 可以自然组合。同时，order_item 是发货/退款维度的唯一事实源，订单级不再冗余存储，彻底消除同步不一致问题。

商品级双维度状态分别跟踪发货进度和退款进度。退款审批通过后 refund_status 变为 refunding，发货时校验 refund_status = none 才允许发货，防止退款中的商品被误发。

5. 优惠层

v8.0 新增：订单优惠结果快照
订单只记录优惠的应用结果（哪条优惠、折扣多少、分摊到哪些商品），不存促销规则。
• order_discount 挂 parent_order（支持跨店优惠：跨店满减的商品可能分属不同商家的 order）
• order_discount_item 记录每件商品分摊了多少折扣，支持精确退款计算
• order_item / order / parent_order 各有 discount_amount 冗余汇总字段，退款和结算直接读本地字段

order_discount.discount_type 3 个值 v8.0 新增

枚举值中文说明
threshold满减满 $X 减 $Y，按商品金额比例分摊折扣
coupon优惠券固定金额或百分比折扣，按适用商品比例分摊
buy_gift买赠买 A 赠 B，B 作为正常 order_item（unit_price=原价, discount_amount=原价, item_total=0）
后续扩展：flash_sale（限时折扣）、member（会员折扣）等

order_discount_item.role 2 个值 v8.0 新增

枚举值中文说明
qualify触发商品该商品触发了此优惠（买赠场景：A 触发赠品）
benefit受益商品该商品享受了折扣（满减/优惠券：所有适用商品；买赠：B 全额免单）
退款与优惠的关系：退单件商品时，退款金额基于 order_item.item_total（已扣优惠后的实付金额），不是 unit_price × quantity。买赠场景退主商品（qualify）时，通过 order_discount_item 找到关联赠品（benefit），决定是否一起收回。

为什么挂 parent_order 而非 order？
促销的参与范围是一次下单（parent_order），不是单个商家（order）。跨店满减中，商家 A 的商品 $120 + 商家 B 的商品 $80 共同凑 $200 才触发优惠。如果优惠记录挂 order，就拆成了两条孤立记录，丢失了「同一次促销」的关联。

退款和结算不受影响：order_item.discount_amount / order.discount_amount 是冗余汇总字段，高频读取不需要回溯 parent_order。

6. 退款申请层（业务域）

v7.0 变更：业务决策与资金操作分离
v6.0 的 refund 表同时承担「要不要退」和「怎么退钱」两个职责。v7.0 拆分为：
• refund_request（业务域）：管审批决策、退款原因、操作人
• refund_order（支付域）：管资金退回，与 payment_order 对称
两者通过单号松耦合：refund_request.refund_ref_no = refund_order.refund_no，与收款方向的 payment_ref_no = payment_no 模式对称。

9. 设计规则与约束

状态流转规则

规则说明
父订单起始状态下单即创建 parent_order，起始 parent_status = pending_payment（此时不拆子订单）；支付到账后转 paid
支付后拆单 + 子订单起始parent_order 转 paid 时才按商家拆出子订单 order，子订单起始 order_status = paid；所有 order_item 初始 fulfillment_status = pending，refund_status = none
待付款超时/失败payment_deadline = 下单 + 30 分钟。超时规则按支付单状态区分：① pending（未提交付款）超过 30 分钟 → 支付单转 closed → parent_order 转 cancelled，释放库存；② processing（已提交付款、渠道审核中）不受 30 分钟超时影响，等渠道回调决定 succeeded/failed，回调失败 → 支付单转 failed → parent_order 转 cancelled，释放库存（此时无子订单，无退款）
processing 72h 兜底processing 超过 72h 无回调 → 系统主动查询渠道：① 成功 → 正常到账流程；② 失败 → 支付单转 failed，同正常回调失败（取消订单、释放库存、发取消邮件）；③ 仍处理中或查询异常 → 支付单保持 processing + remark 写入"渠道处理超72小时未成功"，订单和库存不变，运营通过后台筛选发现并人工介入。系统不再自动轮询
库存锁定提交支付即锁定一物一件商品（锁在父订单），pending_payment 期间不可被他人购买，转 cancelled 时释放
shipped 触发条件首个 order_item.fulfillment_status 变为 shipped 时，order_status 从 paid 变为 shipped
completed 触发条件所有 order_item.fulfillment_status 变为 received 时，order_status 变为 completed
cancelled 约束父订单 pending_payment 可因支付失败/超时取消；子订单 paid 且所有 order_item.fulfillment_status = pending 时可发货前取消（退款成功后才置 cancelled）。已发货不可取消
退款不改生命周期order_item.refund_status 变化不影响 order_status。completed 订单的所有商品 refunded 表示「完成后全退」
退款阻断发货refund_request 审批通过(approved)后，order_item.refund_status 变为 refunding，该商品不得发货（发货时校验 refund_status = none）

聚合关系

v6.0 起，发货/退款维度不再存储在 order 表，以下聚合仅影响 order_status：

商品级状态变化触发的 order_status 变化
首个 order_item.fulfillment_status → shippedorder_status → shipped
所有 order_item.fulfillment_status → receivedorder_status → completed
发货/退款维度无需聚合写入：订单列表页需要「部分发货」「有退款」等筛选时，直接查询 order_item 聚合。不再有「子层变化 → 写入订单层」的同步链路。

优惠与金额规则

规则说明
金额公式order 实收 = subtotal_amount + shipping_fee - discount_amount + tax_amount。order_item.item_total = unit_price × quantity - discount_amount
冗余汇总链order_item.discount_amount（各 order_discount_item 之和）→ order.discount_amount（本单各 item 之和）→ parent_order.discount_amount（各子 order 之和）
退款按实付金额退单件商品退 item_total（已扣优惠），不退 unit_price × quantity（优惠前原价）
买赠赠品表示赠品作为正常 order_item：unit_price=原价, discount_amount=原价, item_total=0。退主商品时通过 role=qualify/benefit 找关联赠品
优惠快照原则订单只存结果（promotion_name + 金额 + 分摊），不存规则。promotion_ref_id 引用促销模块供追溯，规则变更不影响历史订单

命名约定

字段所属域说明
order_item.refund_status订单域（商品级）这件商品退没退：none / refunding / refunded
refund_request.approval_status订单域（退款申请）审批决策：pending / approved / rejected
refund_order.status支付域（退款单）资金操作：pending / succeeded / failed

v7.0 起退款相关状态分布在三个实体、两个域：order_item 跟踪商品是否退款，refund_request 跟踪审批决策，refund_order 跟踪资金到账。三者各司其职，不互相同步。
