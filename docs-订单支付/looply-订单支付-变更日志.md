**2026-07-17｜异步邮件触发规则落地（5 分钟阈值）**
- 背景：技术反馈指出「命中风控=异步」仅是业务场景描述，无可执行的系统判定规则（渠道不一定回传明确的「审核中」信号）。PM 决策：以「提交付款后满 5 分钟支付单仍未变 succeeded」作为异步判定的系统规则。
- 决策边界（关键）：5 分钟阈值**仅作为「订单已接收」邮件(#4)的发送判定**，不影响支付单状态流转、C 端页面跳转、库存锁定、超时等任何其它逻辑（PM 明确「5 分钟只作为异步邮件触发阈值，不影响其他逻辑」）。
- 改动内容（仅 PRD v1.2）：
  - §5.2 发送策略：「异步场景下单时先发」改为「提交付款后 5 分钟内 succeeded → 仅发 #1；满 5 分钟仍 processing → 发 #4 再发 #1」，并声明阈值仅用于邮件、不影响其它逻辑
  - §5.2b 触发时机：「进入风控审核时触发」改为「提交付款满 5 分钟仍 processing 时触发，由延迟 5 分钟的定时检查读取支付单状态判定」
  - §3.2 支付到账处理：新增第 6 项「#4 邮件触发」，点明阈值独立于 C 端跳转判定
  - §3.3 静默注册：设置密码链接挂载改为「挂用户收到的首封含订单信息邮件」——同步挂 #1，异步挂 #4，同一 Token 只挂首封避免重复引导
  - §附录变更记录 v1.2 行：追加交付后修订四项标注
- 实现口径：一个延迟 5 分钟的定时/延时任务，到点读支付单状态——仍 processing 发 #4，已 succeeded 不发。
- 影响范围：PRD 已更新（v1.2 原地修订）；ER 图 / 流程图 / 后台原型无影响（无字段/状态变更，纯邮件触发规则 + C 端文案挂载调整）；C 端页面跳转逻辑按 PM 决策不动（异步跳转判定沿用现状，与邮件阈值是两套，PRD 已注明）

## V1.3（设计中 · 2026-08-31）

**2026-08-31｜弃单数据补齐与导出**

- 需求来源：产品提出「弃单模块收集的数据信息比较少，需补齐优惠码填写情况和收货地址填写情况，同时支持弃单数据导出」。同批次的「订单管理菜单导出字段扩充」经产品确认**本次不含**，另行处理。
- 核实结论（动手前盘点 PRD v1.2 / ER v9.1 / 原型 v7 / 营销活动迭代 PRD V1.3）：
  - **优惠码在系统里完全没有落点**。营销 V1.3 明确「链接不落库、会话里的码位记在浏览器侧不落库」，只有下单成功才产生核销记录；弃单是没下单的，后台查不到任何优惠码痕迹。
  - **收货地址只有一个 `address_id` 指针**，游客边填的地址无落点；且 ER 里**账单地址连字段都不存在**，而 PRD §4.2.2 已经画了账单地址区块 —— 属产物间打架。
  - **结算会话没有买家邮箱字段**，但 PRD §4.2.1 列表有「买家 = 结算时填写的邮箱」这一列；静默注册在支付成功后才发生，弃单买家大多无用户记录，该列取不到值 —— 同属产物间打架。
  - **PRD §1.2 与 §7 的「结算页不展示优惠码输入框」口径已过期**，被营销活动模块 V1.3（2026-08-25 交付）推翻。
- 数据依据：模块目录下 Shopify 弃单导出 `checkouts_export_1 (4).csv`（711 个结算会话）—— 36% 填了优惠码、63% 填了收货地址、**65% 填了账单地址（比收货地址还多）**、38% 走到支付环节。优惠码码值分布中 `67`(80次) / `777`(32) / `45` / `sarah` / `123` 等**过半是买家瞎猜的码**，构成「记每一次尝试而非只记生效码」的直接依据。
- 产品决策（2026-08-31 拍板，四项全按推荐）：
  - 优惠码 → **记每一次尝试**（码值 / 来源 / 通过与否 / 未通过原因 / 减免金额 / 被移除时间）
  - 地址 → **存完整快照，账单地址本期一起做**
  - **加结算进度**（六值、只进不退），用于定位流失环节
  - 导出 → **一行一个弃单会话**，商品合并成一列
- 改动内容：

**2026-08-31｜交付后修订 3：补两类被漏掉的场景 + 修文档中心时间戳失效（原型 v10 → v11）**

- **① 时间戳失效的根因与修复**：迭代 PRD 那张卡片是**手工写进 index.html 的**，而 sync.py 的「更新于」只对它自己管理的 artifacts 条目（changed_items）刷新，手工卡片永远不动 → 被冻在写入时的值。
  - **没有采用全局按 mtime 刷新**：实测全库 143 个带「更新于」的条目中 68 个与文件 mtime 不符，但其中大量是 clone / 批量复制造成的假 mtime（多个不同模块的文件 mtime 都是 `2026-07-08 11:34`、`2026-08-10 20:40`），全局刷新会把更多条目改成**更错的时间**。
  - **修法**：sync.py 的 `static_docs` 增加可选 `index_href`，新增 `refresh_static_doc_stamps()`——**只刷新显式声明了 index_href 的手工卡片**，按仓库内该文件 mtime，其余一概不动。已验证生效（`[更新] index.html 手工卡片时间戳 x1`，线上 16:07 → 19:18）。

- **② 链接自动带入的码（易漏，已补进两份 PRD）**：营销 §2.3.4 规定链接码校验失败对买家**完全静默**（不提示、不回填、页面与「没有这个码」一致）。若订单侧照搬「静默」理解成不记录，**运营排查「投放链接带的码为什么没人用成」时一条都查不到**——而这正是本需求要解决的核心场景之一。已明确三条：自动应用成功 / 买家侧静默失败 / 未达门槛的中性引导，**三种都记**。总原则写成：**一次校验 = 一条记录，判断依据是「有没有发生过一次校验」，不是「买家看没看见」。**
