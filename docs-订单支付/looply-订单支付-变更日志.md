**2026-07-17｜技术反馈处理：弃单转化口径统一 + 72h 人工核账边界**
- 来源：技术团队在《v1.2-变更说明-大白话版》飞书文档评论 + 文末「需 PM 确认清单」提出的问题。
- 根因（弃单口径打架）：V1.2「待付款态上移」改造时，把 §2.2.1 结算会话层的转化口径改成了「提交支付即转化」（口径 A），但 §4.2 后台弃单管理章节沿用 V1.1 旧文案「已完成支付才转化」（口径 B）未同步。V1.1 是「先收钱后建单」，转化本就等于付款成功，故 §4.2 在旧语境正确；改造漏改导致同一 converted 枚举两处定义冲突。
- 决策：转化口径统一为 **B（支付成功才转化）**。
- 改动内容（仅 PRD v1.2）：
  - §2.2.1 checkout_status：converted 触发点「提交支付」→「支付成功（parent_order 转 paid）」；pending 含「已提交支付但付款未成功」；新增「转化时点说明」+「数据结构与召回策略解耦」声明
  - §3.2 下单处理步骤3：提交支付时会话保持 pending（原为置「已转化」）
  - §3.2 到账成功步骤2：支付成功那步补「结算会话置 converted」
  - §2.2.6 交互链路：去支付时会话 pending，回调成功才 converted，取消时保持 pending
  - §4.2 弃单枚举：文案对齐（口径 B 下语义本正确，补全触发场景描述）
  - §5.5 弃单恢复邮件：新增「发送范围排除」——召回仅面向「从未提交支付」的会话，已提交支付（审核中/失败/取消）不发；明确弃单率统计（含失败/超时取消，真实流失）与召回发送对象是两层
- 设计原则修正：召回排除条件落在邮件触发策略层（§5.5），不因「发不发邮件」反向改数据结构枚举（保留用户两态设想）
- #4 72h 人工核账边界（技术清单 #4）：开发结论「本期只读、不做手动置状态」。§2.2.6 改「手动操作支付单状态」为「线下跟进」+ 补「本期只读」边界声明；§4.3 支付单管理原本即无手动置状态入口（仅详情/关闭），符合结论未改
- 待优化清单（§后续迭代新增 2 项）：① 支付单人工核账受控操作（下期）；② §4.2「发送恢复链接」按钮显示条件收口，与 §5.5 召回范围对齐（下期）
- 技术清单其余项落位：#2 付款失败可重试（PRD 已按「可重试」实现，确认理解无误，本次无改动）；#3 #5 邮件模板（上一条修订已补 §5.4b）；#6 Order Placed 页（开发确认按 PRD 文案实现，附录「待补」标注保留）；#7 14天异步关单任务（倾向下线，eCheck 本期不做，待确认）

**2026-07-17｜异步邮件触发规则落地（5 分钟阈值）**
- 背景：技术反馈指出「命中风控=异步」仅是业务场景描述，无可执行的系统判定规则（渠道不一定回传明确的「审核中」信号）。PM 决策：以「提交付款后满 5 分钟支付单仍未变 succeeded」作为异步判定的系统规则。
- 决策边界（关键）：5 分钟阈值**仅作为「订单已接收」邮件(#4)的发送判定**，不影响支付单状态流转、C 端页面跳转、库存锁定、超时等任何其它逻辑（PM 明确「5 分钟只作为异步邮件触发阈值，不影响其他逻辑」）。
- 改动内容（仅 PRD v1.2）：
  - §5.2 发送策略：「异步场景下单时先发」改为「提交付款后 5 分钟内 succeeded → 仅发 #1；满 5 分钟仍 processing → 发 #4 再发 #1」，并声明阈值仅用于邮件、不影响其它逻辑
  - §5.2b 触发时机：「进入风控审核时触发」改为「提交付款满 5 分钟仍 processing 时触发，由延迟 5 分钟的定时检查读取支付单状态判定」
  - §3.2 支付到账处理：新增第 6 项「#4 邮件触发」，点明阈值独立于 C 端跳转判定
  - §3.3 静默注册：设置密码链接挂载改为「挂用户收到的首封含订单信息邮件」——同步挂 #1，异步挂 #4，同一 Token 只挂首封避免重复引导
  - §附录变更记录 v1.2 行：追加交付后修订四项标注
- 实现口径：一个延迟 5 分钟的定时/延时任务，到点读支付单状态——仍 processing 发 #4，已 succeeded 不发。
- 影响范围：PRD 已更新（v1.2 原地修订）；ER 图 / 流程图 / 后台原型无影响（无字段/状态变更，纯邮件触发规则 + C 端文案挂载调整）；C 端页面跳转逻辑按 PM 决策不动（异步跳转判定沿用现状，与邮件阈值是两套，PRD 已注明）
