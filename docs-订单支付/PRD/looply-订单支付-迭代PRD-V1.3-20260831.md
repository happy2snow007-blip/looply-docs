# looply 订单支付 · 迭代 PRD V1.3 — 弃单数据补齐与导出

> **迭代主题**：弃单补记「优惠码尝试 / 地址快照 / 结算进度」三类数据，并支持弃单数据导出
> **文档定位**：本文自包含，开发按本文即可 coding，无需回读完整 PRD。完整 PRD v1.3 为归档沉淀版本，规则以本文与完整 PRD 一致为准。
> **基线版本**：订单支付 PRD v1.2（交付开发 V1.2-20260714）· ER v9.1 · 后台原型 v7
> **改动范围**：运营后台「弃单管理」+ 结算会话数据采集。**不涉及 C 端页面新增元素、不涉及订单管理菜单**。

---

## 一、背景与目标

### 1.1 为什么做

弃单管理页现在只有六列（会话编号 / 买家 / 商品数 / 预估金额 / 状态 / 创建时间），运营回答不了三个问题：买家**卡在哪一步**走的、**填过什么优惠码、为什么没用上**、**寄到哪个国家**（做定向召回要按地域分批）。

这三类数据在当前在用的 Shopify 弃单导出里都有（`Discount Code` / `Discount Amount` / 完整收货与账单地址），**新系统一旦切换，运营现有的弃单分析动作会直接断掉**。同一份导出的 711 个结算会话中，**36% 填过优惠码、63% 填过收货地址、65% 填过账单地址、38% 走到了支付环节**——这些都是当前系统完全不落库的信息。

**记录颗粒度取「每一次尝试都记」**：只记最终生效的那个码，就看不到「填了码但没用上」的那批会话，而这批恰恰是要排查的——码没生效的原因（未达门槛 / 地区不支持 / 每人限次已用尽）直接指向规则配置是否合理。

### 1.2 本次做什么

| # | 事项 | 章节 |
|---|---|---|
| 1 | 结算会话补记**买家邮箱**（游客也有） | §2.1.1 |
| 2 | 结算会话补记**收货地址 + 账单地址完整快照**，并给出「填写完整度」判定 | §2.1.2 |
| 3 | 新增**优惠码尝试记录**：每输入一次记一条（码值 / 来源 / 通过与否 / 未通过原因 / 减免金额） | §2.1.3 |
| 4 | 新增**结算进度**：买家最远走到结算页哪一步 | §2.1.4 |
| 5 | 弃单**列表页**加导出按钮（**筛选项与列均不变**）| §2.2 |
| 6 | 弃单**详情页**地址区块改为始终展示；优惠码尝试**并入事件时间线**，不单独成模块 | §2.3 |
| 7 | 弃单**数据导出**（一行一会话） | §2.4 |
| 8 | 订正三处已过期 / 打架的口径 | §2.5 |

### 1.3 本次不做什么

| 不做的事 | 说明 |
|---|---|
| **订单管理菜单的导出字段扩充** | 属另一条需求，本期不含。本文任何内容都不改动订单管理页 |
| **改动营销模块的优惠码机制** | 校验链、码位跟随、失败文案全部沿用营销 V1.3，本次**只做记录，不改判定**。边界见 §1.5 |
| **弃单优惠码的补发 / 定向发码** | 「给填了码但没达门槛的买家补一张券」属营销域的召回玩法，本期不做 |
| **按优惠码维度的聚合报表** | 后台不做图表统计，运营导出后线下透视 |
| **C 端页面新增任何元素** | 结算页视觉与交互完全不变，买家侧无感知 |
| **历史数据回填** | 上线前已存在的结算会话没有这些字段，展示为空。见 §三 依赖与风险 |

### 1.4 顺带修掉的三处产物打架

核对 PRD v1.2 / ER v9.1 / 原型 v7 时发现：① 列表「买家」列取的是结算邮箱，但结算会话**没有邮箱字段**（静默注册在支付成功后才发生，弃单买家大多无用户记录）；② 详情页画了收货与账单地址两个区块，但**账单地址在数据结构里不存在**；③ §1.2 的「结算页不展示优惠码输入框」已被营销 V1.3 推翻。三处本次一并修。

### 1.5 与营销模块的边界（**开发必读**）

营销 V1.3 明确写了两件"不落库"：

> 「**链接本身不落库**——它是「域名 + `/discount/` + 优惠码」的拼接结果，平台不追踪已投放的链接。**会话里的码位也不落库**——记在浏览器侧。」

**本次不推翻这条。** 两者记的是不同的东西：

| | 营销侧的「码位」 | 本次新增的「优惠码尝试记录」 |
|---|---|---|
| 记的是什么 | 买家点了链接后**跟随他浏览的那个待用码** | 买家**在结算页实际提交校验的每一次输入** |
| 存在哪 | 浏览器侧，会话级，不落库 | 结算会话下，落库 |
| 谁在用 | C 端自动带码逻辑 | 运营后台弃单分析 |
| 本次是否改动 | **否，完全不动** | 新增 |

**一句话给开发**：优惠码怎么带、怎么判、失败提示什么文案，**全部沿用营销 V1.3 §2.3 不变**；本次只是在校验有结果的那一刻，**额外把结果记一条**。校验逻辑本身零改动。

### 1.6 多语言

本次改动全部在**运营后台**（弃单管理列表 / 详情 / 导出），界面仅面向内部运营，本期仅中文，不接入多语言。

优惠码校验的 C 端失败文案由**营销模块**定义和维护（营销 V1.3 §2.3 校验链），本次记录的「未通过原因」是**后台侧的中文枚举**，与 C 端展示文案是两套，不互相引用。

## 二、需求详细描述

### 2.1 结算会话数据记录（新增采集）

**功能类型**：机制型

#### 功能描述

买家在结算页填写的信息，随填随存到结算会话，使其在未完成支付（即弃单）时仍可被后台完整查看。

#### 触发条件

买家进入结算页创建结算会话后，在页面上填写 / 修改任一信息时。

#### 记录时机与更新规则（**通用规则，下列各项均适用**）

| 规则 | 说明 |
|---|---|
| **随填随存** | 买家在结算页填写的信息需在填写过程中保存到结算会话，不能等到点击下单才存——**弃单买家永远不会点下单** |
| **覆盖更新** | 同一会话内买家反复修改地址，以**最后一次填写的内容**为准，不保留修改历史（优惠码除外，见 §2.1.3） |
| **只进不退** | 结算进度只记录**最远到达**的环节，买家回退修改不会把进度降回去 |
| **转化后保留** | 会话转化为订单后，这些数据**照常保留在结算会话上**，不因转化而清空——「已转化」的弃单记录同样要能查看当时填了什么 |
| 保存的具体时机与频率 | 由技术方案定，PRD 只要求「买家离开页面时，他已填写的内容必须已被记录」 |

---

#### 2.1.1 买家邮箱与身份

| 记录项 | 说明 |
|---|---|
| **买家邮箱** | 结算页 Contact 区块的邮箱。**游客、未登录、已登录三种情况都要记**：已登录取账户邮箱（系统自动带出），未登录取买家手填的邮箱 |
| **是否注册用户** | 该会话创建时买家是否已有账户。用于运营区分「老客流失」与「新客流失」 |
> **来源只体现在事件时间线里，不落会话字段、不进导出**：已登录买家的邮箱与收货地址大多是系统自动带出的，时间线用「自动带入」与「填写 / 修改」两类事件区分（见 §2.3）。
> **不新增「来源」字段**——结算进度已按「自动带出算已填」统一口径（§2.1.4），导出的地址填写情况同样不区分来源。要判断买家有没有真的动手，看详情页时间线。

> **为什么必须补**：弃单召回邮件发给谁、后台列表「买家」这一列显示什么，全靠这个字段。现有数据结构里它不存在（见 §1.4 第 1 条），弃单买家大多是游客，取不到用户记录。

---

#### 2.1.2 收货地址与账单地址快照

**记录内容**：买家填了多少就存多少，**不要求填完整才存**。

| 地址类型 | 记录字段 |
|---|---|
| **收货地址** | 收件人名、收件人姓、收件人全名、收件人电话（含区号）、地址行 1、地址行 2、城市、州/省、邮编、国家 |
| **账单地址** | 同上一套字段（收件人字段对应为账单联系人姓名 / 电话） |
| **账单地址是否同收货地址** | 买家勾选「账单地址与收货地址相同」时记为「是」，此时账单地址各字段不再重复存值 |

> **字段口径与订单表完全一致**（同名同义），这样会话转化为订单后，运营可以直接比对「结算时填的」和「最终下单用的」是否一致。

**填写完整度判定**（收货地址与账单地址各自独立判定）：

| 状态 | 判定条件 |
|---|---|
| **未填写** | 该地址的所有字段均为空 |
| **部分填写** | 有任一字段有值，但必填项未齐 |
| **已填完整** | 必填项全部有值 |

**必填项定义**：收件人姓名、电话、地址行 1、城市、州/省、邮编、国家。地址行 2 为选填，不参与判定。

> 账单地址勾选了「同收货地址」时，账单地址的完整度**跟随收货地址的判定结果**。

> **为什么账单地址必须做**：实测 Shopify 数据里填了账单地址的会话（463）**比填了收货地址的还多**（449）——买家在支付环节填卡时会连带填账单地址。只做收货地址会漏掉这批已经走到很后面的高价值流失。

#### 2.1.3 优惠码尝试记录

**核心规则：买家每提交一次优惠码校验，就记一条记录，不管通过与否。** 一个会话可以有多条。

**每条记录包含**：

| 记录项 | 说明 |
|---|---|
| **优惠码码值** | 买家实际提交的字符串，**统一转成大写后存储**（与营销侧存储口径一致）。**不校验、不判定码的真伪，买家提交什么就记什么** |
| **码来源** | 「链接带入」（买家点投放链接进来，码自动应用）/「买家手输」（在优惠码输入框手动输入） |
| **校验结果** | 「已应用」/「未通过」 |
| **未通过原因** | 校验结果为「未通过」时必填，取值见下方枚举表 |
| **本次减免金额** | 校验结果为「已应用」时记录该码实际减免的金额 + 币种；未通过时为 0 |
| **尝试时间** | 该次校验发生的时间 |
| **被移除时间** | 该次「已应用」的码后来被买家点 chip 上的 ✕ 移除的时间。未被移除则为空 |

**未通过原因枚举**（与营销 V1.3 §2.3 校验链逐条对应，**不新增判定逻辑，只是把营销已有的判定结论记下来**）：

| 枚举值 | 含义 | 对应营销校验链 |
|---|---|---|
| 码无效或已失效 | 码不存在、已停用、或所属活动非进行中 | 第 1 项 |
| 地区不支持 | 活动所属市场与买家当前市场不符 | 第 2 项 |
| 商品范围未命中 | 订单内没有任何商品在该码的适用范围内 | 第 3 项 |
| 未达使用门槛 | 满额或满件门槛未达标 | 第 4 项 |
| 总次数已用尽 | 该码的总使用次数已用完 | 第 5 项 |
| 该买家已用过 | 每人限次已用尽 | 第 6 项 |
| 该买家不在适用范围 | 标签未命中 / 邮箱不在指定买家名单内 | 第 7 项 |
| 已有更优惠的折扣 | 商品上已有自动折扣且更优，该码不叠加 | 营销 §2.3 自动折扣互斥 |
| 未产生实际减免 | 校验全部通过，但整单求最优组合后该码不产生任何减免，故未加入已应用集合 | 营销 §2.3 求解后为零 |

> **枚举随营销校验链演进**：营销后续增删校验项时，本枚举需同步。两侧口径必须保持一一对应，**不允许订单侧另立一套判定标准**——本次记录的是营销给出的判定结论，不是重新判一次。

**几个边界情况的处理口径**：

**总原则：一次校验 = 一条记录。判断依据是「有没有发生过一次校验」，不是「买家看没看见」。**
买家手输和链接自动带入一视同仁；**买家侧静默的失败同样要记**（见下表第 1、2 行）。

| 场景 | 怎么记 |
|---|---|
| **链接带入的码自动应用成功** | 记 **1 条「已应用」**，码来源 = 链接带入。买家没有任何输入动作，但这是一次真实校验 |
| **链接带入的码校验不通过，买家侧完全静默**（营销 §2.3.4：不提示、不回填、页面与「没有这个码」完全一致）| **照记 1 条「未通过」**。买家看不到 ≠ 没发生——运营排查「投放链接带的码为什么没人用成」查的正是这批，漏记等于这个需求的核心场景之一失效 |
| **链接带入的码未达门槛，买家侧只出中性引导**（非红色报错）| 同样记 **1 条「未通过」**，原因 = 未达使用门槛。呈现是中性的，判定结果仍是不通过 |
| 买家连续输错 3 次再输对 1 次 | 记 **4 条**：3 条「未通过」+ 1 条「已应用」 |
| 买家应用成功后又点 ✕ 移除 | 仍是 **1 条「已应用」**，在该条上补记「被移除时间」，**不新增记录** |
| 移除后刷新页面，链接码自动重新应用 | **新增 1 条「已应用」**（这是一次新的应用行为，营销 V1.3 明确这是预期行为） |
| 链接带入的码 A 被链接 B 覆盖，A 从已应用集合移除 | A 那条记录补记「被移除时间」；B 新增一条记录 |
| 同一个码在同一会话被反复应用 / 移除 | 每次应用各记一条，不去重——运营需要看到买家的犹豫过程 |
| 买家在**买家身份明确前后**得到不同校验结果（营销的 T1/T2 两时点） | 各记一条。T1 通过、T2 因限次被拒的，会是「已应用」+「未通过（该买家已用过）」两条；**原「已应用」那条同时补记被撤销时间** |

> **T2 撤销与买家主动移除共用「被移除时间」一个字段，不新增字段区分**（2026-08-31 产品拍板）。
> 需要分辨时，看该码后面**有没有紧跟一条「未通过」记录**：有 → 系统按 T2 判定撤销的；没有 → 买家自己点 ✕ 移除的。

**会话级冗余（供导出与后续统计直接取值，避免每次聚合明细）**：

| 记录项 | 取值规则 |
|---|---|
| **当前生效优惠码** | 当前处于「已应用且未被移除」状态的码。无则为空 |
| **当前优惠减免金额** | 当前生效码的减免金额合计。无则为 0 |
| **优惠码使用情况** | 「未填写」（无任何尝试记录）/「填写未通过」（有尝试记录但当前无生效码）/「已应用」（当前有生效码） |

#### 2.1.4 结算进度（流失环节）

**记录买家在这个会话里最远走到了哪一步**，用于回答「他是卡在哪儿走的」。

| 进度值 | 含义 | 判定时机 |
|---|---|---|
| 进入结算页 | 创建了会话，但没填任何信息 | 会话创建即为此值 |
| 已填邮箱 | Contact 区块的邮箱已填写 | 邮箱字段首次有值 |
| 已填收货地址 | 收货地址达到「已填完整」 | 收货地址完整度首次判定为「已填完整」 |
| 已选配送方式 | Shipping 区块已选定配送方式 | 配送方式首次有值 |
| 已填支付信息 | Payment 区块已选支付方式并开始填写支付信息 | 买家在支付区块选定支付方式 |
| 已提交支付 | 点击了下单按钮，已创建支付单，但付款未成功（含渠道审核中、失败、超时取消） | 支付单创建时 |

**规则**：

- **只进不退**：买家填完地址又回头改邮箱，进度仍是「已填收货地址」，不回落
- **自动带出算「已填」**（2026-08-31 产品拍板）：已登录买家进页面时邮箱与地址自动带出，进度**直接按带出的内容推进**，与买家手填一视同仁
- **可跳跃**：中间值不必逐个经过——已登录买家进页面邮箱与地址都带出，进度直接从「进入结算页」跳到「已填收货地址」
- **与状态的关系**：结算进度描述**流失位置**，弃单状态（待转化 / 已转化）描述**转化结果**，两者独立。已转化的会话进度停在「已提交支付」

> ⚠️ **看这个指标时要配合时间线**：自动带出算已填，意味着**已登录买家一进页面进度通常就是「已填收货地址」**，哪怕他什么都没动。所以「进度 = 已填收货地址」不等于「买家填过地址」。要判断买家究竟有没有动手，看时间线里是「自动带入」还是「填写 / 修改」——**时间线是唯一能分辨这件事的地方。**

> **为什么这一项值得做**：地址填没填只能二分，而「已提交支付但没付成」和「进页面就走了」是两种完全不同的流失——前者是支付环节出了问题（该找支付渠道排查），后者是流量质量问题。这两类混在一起看，弃单率这个数就没有可行动性。数据来源与地址快照是同一套随填随存机制，一起做的增量成本很低。

#### 事件时间线（**优惠码尝试记录并入本区块，不单独成模块**）

优惠码的每一次尝试都在时间线里出一条事件，**不再另起一张表**。买家在结算页的动作本来就是一条时间序列——填邮箱、填地址、试码、选配送、付款失败、离开——把试码单独抽成表格，运营要在两个地方来回对时间才能还原发生了什么。

在 PRD v1.2 已定义的事件类型基础上补充 4 类：

| 新增事件 | 事件详情格式 | 颜色 | 触发 |
|---|---|---|---|
| **自动带入联系方式** | `{邮箱} · 取自登录账户` | 普通-灰色 | 已登录买家进入结算页，邮箱自动带出 |
| **自动带入收货地址** | `{地址摘要} · 取自账户默认地址` | 普通-灰色 | 已登录买家进入结算页，默认地址自动带出 |
| 填写邮箱 | 买家填写的邮箱 | 普通-灰色 | 买家手动填写 |
| 填写收货地址 | 买家填写的地址摘要 | 普通-灰色 | 买家手动填写 |
| **修改收货地址** | `由 {原城市/州} 改为 {新城市/州}` | 普通-灰色 | 买家改动了自动带出或此前填过的地址 |
| 应用优惠码 | `{码值}（{码来源}）· 已应用，减免 {金额}` | 普通-灰色 | 校验通过 |
| 优惠码校验失败 | `{码值}（{码来源}）· 未通过：{未通过原因}` | 警告-橙色 | 校验不通过（**含买家侧静默的情况**）|
| 移除优惠码 | `{码值} · 买家主动移除，本单不再享受该优惠` | 警告-橙色 | 买家点 ✕ 移除 |

> 🔴 **自动带出与买家填写必须是两条不同的事件**，不能都记成「填写邮箱 / 填写地址」。已登录买家的信息大多是系统带的，混在一起记会让运营把「系统填的」看成「买家填的」，从而误判这单的流失位置。**一眼要能看出：这单里哪些是买家自己动的手。**

**码来源**取「链接带入」/「买家手输」。三类优惠码事件由 §2.1.3 的尝试记录逐条派生：**一条尝试记录 = 一条时间线事件**；被移除的那条额外派生一条「移除优惠码」事件。

> **自动填写的码与手输的码在时间线里一视同仁。** 链接带入的码即使在买家侧是静默失败的（营销 §2.3.4，买家页面上什么都看不到），后台时间线**照样出「优惠码校验失败」事件**——两侧口径不同是刻意的：买家不需要为一个自己没输过的码困惑，而运营必须看得到投放链接带来的码在这一单上发生了什么。

> **数据照记不变**：§2.1.3 的尝试记录该存的字段一个不少（含码来源、未通过原因、减免金额、被移除时间），本条改的只是**后台怎么展示**——从独立表格改为时间线事件。导出仍按 §2.4 输出全部优惠码字段。

#### 其余区块

结算商品列表、恢复邮件记录、页头操作按钮**本次不改动**。

### 2.4 弃单数据导出

**功能类型**：流程型

#### 功能描述

运营在弃单列表页导出弃单数据，用于线下做召回分析、地域分布分析、优惠码失效排查。

#### 导出粒度

**一行 = 一个弃单会话**。商品信息合并到一列，不按商品展开。

> **为什么不按商品展开**：Shopify 现有导出是按商品行展开的（711 个会话产生 869 行），导致**会话被重复计数**——运营用它算弃单率、算平均金额时必须先去重，实测极易算错。弃单分析的单位是「会话」不是「商品」，一行一会话可以直接透视。
> 代价：无法直接分析「哪些商品最常被放弃」。该诉求本期由「商品名称」列的文本内容承载，若后续成为高频需求，再增加按商品展开的导出维度。

#### 操作流程

1. 运营在弃单列表页设置好筛选条件
2. 点击右上角「导出」按钮 → 弹出导出配置弹窗
3. 确认导出范围与文件格式 → 点击「开始导出」
4. 导出完成后弹窗切换为成功状态，展示文件名与「完成」按钮

| 字段 | 控件 | 说明 |
|---|---|---|
| 导出范围 | 单选 | 当前筛选结果（N 条）/ 全部数据（N 条）。默认选中「当前筛选结果」 |
| 状态 | 下拉选择 | 全部 / 待转化 / 已转化。默认带入列表当前筛选值 |

| 文件格式 | 单选 | Excel (.xlsx) / CSV (.csv)。默认 Excel |

> 弹窗形态与交互**复用本模块「对账管理」已有的导出弹窗**（PRD v1.2 §4.6），不新造样式。

顶部提示文案：「导出当前筛选条件下的弃单数据，包含买家联系方式、地址、优惠码使用情况等信息，用于线下召回分析」。

| **IP 与设备信息不导出** | 详情页展示的 IP（脱敏）与设备信息**不进入导出文件**——它们对召回分析无用，却会扩大个人数据的外流面 |

| 导出过程失败 | 弹窗展示失败状态与失败原因，提供「重试」按钮 |

| 1 | 游客进结算页填邮箱后直接关页面 | 弃单列表能看到该会话，买家列显示邮箱，流失环节为「已填邮箱」，收货地址为「未填写」 |

## 五、本次拍板的三条口径（2026-08-31）

| # | 问题 | 拍板 | 随之接受的代价 |
|---|---|---|---|
| 1 | T2 撤销与买家主动移除要不要用字段区分？ | **不区分**，共用「被移除时间」 | 分辨时需看该码后面有没有紧跟一条「未通过」记录，不够直观 |
| 2 | 自动带出的邮箱与地址算不算「已填」？ | **算已填**，与买家手填一视同仁 | 已登录买家一进页面进度通常就是「已填收货地址」，**「进度 = 已填收货地址」不等于「买家填过地址」**；判断买家有没有动手要看时间线 |
| 3 | 联系方式 / 收货地址「来源」要不要落库？ | **不落库**，只体现在时间线事件里 | 导出的「收货地址填写情况」不区分自动带出与买家填写，按该列做召回分析时无法筛掉「系统带出、买家没动过」的那批 |

> 三条都指向同一个取舍：**不为区分来源而扩数据结构，代价由时间线兜底。** ER v9.2 因此无需再改。
