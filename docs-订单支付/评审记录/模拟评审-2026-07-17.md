## P0（规则缺失或制品矛盾，阻塞开发）

### 1. [开发] §4.3 支付单列表和详情弹窗缺少 remark 字段 — PRD 内部矛盾

- **位置**：PRD §2.2.6（line 330）vs PRD §4.3 列表字段（line 1398-1412）+ 详情弹窗（line 1418-1427）
- **问题**：§2.2.6 明确写了 "后台支付单列表和详情页展示"，但 §4.3 支付单管理的列表字段表和详情弹窗布局中均未包含 remark。原型 v7 已实现（列表有 remark 列 + 详情有红底备注区块），PRD 与原型存在矛盾。开发按 §4.3 做会漏字段，按原型做又没有 PRD 依据。
- **建议**：§4.3 列表字段表增加"备注"行（说明：有值红色展示/无值显示"—"）；详情弹窗基本信息区块下方增加"备注"行（有值时红底色块展示）。与原型对齐。

## P1（规则不完整，影响质量）

### 2. [开发] §4.3 支付单状态枚举 failed 触发时机未覆盖 72h 兜底

- **位置**：PRD §4.3 支付单状态枚举（line 1445）
- **问题**：failed 的触发时机写的是"收到渠道支付失败 Webhook（余额不足、风控拒绝等）"，但 72h 兜底场景也会触发 failed（系统主动查询渠道后非成功）。开发如果按枚举表做状态变更入口，可能遗漏 72h 兜底的触发路径。
- **建议**：触发时机补充"或 processing 超 72h 系统查询渠道非成功"。

### 3. [测试] 72h 兜底触发取消后，C 端买家是否收到邮件？文案是什么？

- **位置**：PRD §3.2 支付到账处理（line 785-786）+ §5.5 订单取消通知邮件
- **问题**：正常支付失败和 30 分钟超时都明确写了"发送取消通知"。但 72h 兜底触发 parent_order cancelled 时是否也发 #5 取消通知邮件，PRD 没有说。场景特殊性：用户 72 小时前提交了付款，现在突然被告知取消，和"30 分钟没提交被关单"体验完全不同。是用同一封取消邮件模板，还是需要区别文案（如"We were unable to process your payment"）？
- **建议**：明确72h兜底取消是否发送买家邮件，以及是否复用 #5 模板或新增模板/变体。

### 4. [开发] "通知运营"的渠道和方式未定义

- **位置**：PRD §2.2.6（line 328）、§2.4 规则表（line 400）
- **问题**：两处都写了"通知运营"，但没有定义通知方式。是发邮件给指定运营邮箱？推送飞书/Slack 消息？后台弹窗/待办？开发无法实现一个未定义渠道的通知。
- **建议**：明确运营通知渠道。建议 0-1 阶段最简方案：发邮件到指定运营邮箱（与邮件通知体系复用），或在后台支付单列表通过筛选"失败+有备注"自行发现。

### 5. [开发] §3.2 支付到账处理章节未覆盖 72h 兜底流程

- **位置**：PRD §3.2 支付到账处理（line 780-787）
- **问题**：该章节列举了支付处理的所有分支（成功、失败、超时、同步/异步），但缺少 72h 兜底分支。72h 兜底规则只在 §2.2.6 和 §2.4 的状态定义章节出现，在功能描述章节（§3.2）没有落地。开发读功能描述写逻辑时可能遗漏。
- **建议**：在 line 787 后增加第 6 条："processing 72h 兜底：支付单 processing 超过 72 小时未收到回调 → 系统主动查询渠道 → 查询成功按正常到账流程处理；查询非成功 → 支付单转 failed + remark → parent_order 转 cancelled → 释放库存 → 通知运营"。

### 6. [开发] 版本记录未包含 72h 兜底和 remark 变更

- **位置**：PRD §九 版本记录（line 2120）
- **问题**：v1.2 的变更说明覆盖了支付后拆单、取消时序、30 分钟超时，但没有提到 72h 兜底机制和 remark 字段新增。这两项是本次调整的重要组成部分。
- **建议**：v1.2 变更说明追加："**processing 72h 兜底**：processing 超 72h 无渠道回调，系统主动查询渠道，非成功则 failed + remark 记录原因、通知运营。新增 payment_order.remark 字段。"
