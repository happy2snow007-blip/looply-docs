## 二、三件事

### 1. 订单导出扩充（§三）

线上原有 **9 列** → 目标态 **40 列 = 保留 9 + 新增 31**。

| 要点 | 内容 |
|---|---|
| **粒度改了** | 从一行一订单改为 **一行一商品**。订单域里发货 / 退款 / 红布林建单 / 找货全部按件，一行一订单表达不了「两件里退了一件」 |
| **金额输出规则** | 商品级金额每行真值；**订单级金额（订单优惠合计、订单金额）只在该订单第 1 行输出，其余行留空**——这样两类都能直接求和 |
| 列名 | 现有 9 列列名一律沿用，**只改一个**：「商品数」→「订单商品总数」（一行一商品后原名会被读成"这一行几件"） |
| 时区 | 一律 **美东（US/Eastern）**，含夏令时、按美东自然日切分，表头注明 |
| 枚举 | **导中文展示值**，不导 `paid` / `cancelled` 这类英文枚举名 |
| 金额格式 | 按币种标准小数位，**USD 保留 2 位**（现有导出是 4 位 `605.0000`） |
| 留痕 | 每次导出记一条操作日志：操作人 / 时间 / 筛选条件 / 订单数与行数 |

**🔴 退款取数是最容易做错的一处（§3.4）**：退款有两个来源（订单发起、售后单发起），**只查一处会漏**——2026-09-03 实测 100 个子单，只查订单侧漏掉 2 笔售后退款，含一笔 $333。且**商品退款状态 = 已退款却取不到金额时，必须输出「记录缺失」，不得静默留空**；留空会被运营读成「没退款」，对账直接对不上。「记录缺失」是本期**预期会出现**的一类值（实测 100 单中 9 单命中），不是异常兜底。

### 2. 订单详情页三处（§四）

| 位置 | 改动 |
|---|---|
| 优惠信息表 | 新增**优惠码**列（大写等宽，如 `SAVE30`；自动折扣显示 `—`；一单多码按码分行） |
| 商品明细 | 商品名称改为**两行**：品牌（全大写、次级文本）+ 商品名。**不拼成一个字符串** |
| 收货 / 账单地址 | 加**复制地址**按钮，按美国面单规范拼多行、空行不输出；国家输出全称 `United States`（不是 `US`，快递系统识别全称） |

### 3. 订单列表页（§五）

| 改动 | 内容 |
|---|---|
| 新增 5 个查询维度 | 渠道商品ID / HBLitemID / 红布林订单号 / 物流单号（精确）+ 收件人·地址（模糊） |
| 筛选区 | 6 个精确匹配 ID 维度并成**一个统一搜索框**（不让运营先选类型）；买家邮箱 / 收件人·地址 / 卖家ID / 子单类型 / 取消原因 / 日期保持独立控件，共两行 |
| 查看详情 | 「订单号」列与「查看详情」按钮改为**新标签页打开**，须满足四条浏览器原生行为（直接点 / Cmd·Ctrl+点 / 中键 / 右键菜单）。详情页已有独立地址，不涉及地址改造 |

**🔴 统一搜索框不要按格式猜类型，六个维度全查、命中即返回。** 这些号的形态是重叠的：订单号 20 位纯数字 vs USPS 物流单号 20~22 位纯数字；HBLitemID 9~10 位 vs DHL 物流单号 10 位。先猜类型再查一个，必然出现「明明有这张单却搜不到」，且**只在特定长度的号上翻车，极难复现**。

## 三、⏳ 一处待产品拍板（实现前请确认）

**退款金额要不要落到具体商品行**（见迭代 PRD §3.4 末尾）。

实测发现：退款申请侧记的「退款商品」标识与订单商品行的标识**不是同一套编码**，当前拿不到「这笔退款退的是哪一件」。

- **作为硬性要求** → 研发先对齐两侧标识，一单多件的退款金额才落在对的那一行
- **本期不做** → 退款金额只在订单第 1 行输出订单级合计，「退款数据来源」列标 `订单级合计`。**代价**：一单两件退了其中一件时金额恒落在第 1 行，退的正好是第 1 件才对、退第 2 件就错，而运营从表上看不出这一行是真值还是合计

**产品拍板前请勿按任一方向实现。**
