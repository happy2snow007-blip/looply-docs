## 2. 一句话概括本次改动

本次是一次**订单数据模型层面的改造**，核心是两件事：

1. **支付后拆单**：下单时只创建整体订单 `parent_order`（待付款态），支付到账后才按商家拆出子订单 `order`。待付款态从子订单上移到父订单层。
2. **取消时序修复**：已付款订单取消，改为「退款成功后才置已取消」，退款失败则挂人工、订单保持已付款。

外加待付款超时、同步/异步支付（风控）、库存锁定时机前移等配套变更。

## 4. 新增功能 / 新增内容

### 4.1 待付款态（pending_payment）与支付后拆单

- 下单点击 Buy Now → 只创建 `parent_order`（起始 `parent_status = pending_payment`），**不创建子订单**。
- 支付到账 Webhook → `parent_order` 转 `paid`，**此时才**按商家拆出 N 个 `order`（起始 `order_status = paid`）并生成 `order_item`。
- C 端订单列表：待付款只显示一条整体订单、只需付一次款；支付后按商家展示多条子订单。
- 后台订单列表：新增「待付款」Tab（查 parent_status = pending_payment 的父订单）。

### 4.2 待付款超时机制

- 新增 `payment_deadline` = 下单 + **30 分钟**。
- 超时规则按支付单状态区分：
  - **pending（未提交付款）**：超过 30 分钟 → 支付单转 closed → parent_order 转 cancelled + 释放锁定库存。此时无子订单、无退款。
  - **processing（已提交付款、渠道审核中）**：不受 30 分钟超时影响，等渠道回调决定 succeeded/failed。回调失败 → 支付单转 failed → parent_order 转 cancelled + 释放库存。
- **processing 72h 兜底**：processing 超过 72h 仍无回调 → 系统主动查询渠道支付结果：① 成功 → 正常到账流程；② 失败 → 支付单转 failed（同正常回调失败，取消订单、释放库存、发取消邮件，无 remark）；③ 仍处理中或查询异常 → 支付单保持 processing + `remark` 写入"渠道处理超72小时未成功"，订单和库存不变，通知运营人工介入。系统不再自动轮询。
- **需要定时/延时任务**扫描超时父订单（仅关闭 payment_order.status = pending 的支付单），以及 72h 兜底任务扫描长时间处于 processing 的支付单。

### 4.3 同步 / 异步支付（卡风控审核）

- 同步渠道（卡未命中风控）：数百毫秒到账，C 端等结果跳订单成功页（Order Confirmed）。
- 异步（卡命中风控审核）：支付单停 `processing`、parent_order 停 pending_payment，C 端跳「订单已提交」页（Order Placed / Payment Processing 变体）。
- 需支付回调二次驱动状态流转。

### 4.4 新增页面 / 变体

- **C 端订单成功页待付款变体**（parent_order = pending_payment）：标题 Order Placed，文案 "We're processing your payment. We'll notify you as soon as it's verified."，不显示 "Thank you for your purchase"，CTA View Order。

### 4.5 邮件通知（PRD §五章，共 6 类；PRD §5.x 均已有模板定义）

| 邮件 | 触发时机 | 本次是否新增 | PRD 章节 |
|------|---------|------------|---------|
| 支付成功确认 | 支付到账 → order 转 paid | 既有（发送时点后移） | §5.2 |
| 发货通知 | 运营确认发货 | 既有 | §5.3 |
| 退款成功通知 | 退款成功 Webhook | 既有 | §5.4 |
| **订单已接收（仅异步场景）** | 下单创建 parent_order(pending_payment) 且进入风控审核 | **新增** | §5.2b |
| **订单取消通知（待付款失败/超时）** | 待付款订单转 cancelled | **新增** | §5.4b |
| 弃单恢复 | 结算未提交支付、满足弃单判定 | 既有 | §5.5 |

- 同步/异步判定分两套（2026-07-17 明确）：
  - **C 端页面跳转**：按卡是否命中风控——未命中=同步跳 Order Confirmed，命中=异步跳 Order Placed（沿用现状，本次未改）。
  - **异步邮件(#4)触发**：按「提交付款后满 5 分钟支付单仍为 processing」判定（可观测的系统规则）。5 分钟内 succeeded → 不发 #4；满 5 分钟仍 processing → 发 #4。**该阈值仅用于邮件触发，不影响支付流转/页面跳转/库存/超时。**
- 发送策略（防打扰）：秒到账（5 分钟内 succeeded）仅发「支付成功确认」1 封；异步（提交付款满 5 分钟仍 processing）先发「订单已接收」，到账再发「支付成功确认」，共 2 封。
- 实现：需一个延迟 5 分钟的定时/延时任务，到点读支付单状态决定是否发 #4。
- 静默注册「设置密码」链接：挂用户收到的**首封含订单信息邮件**——同步（秒到账）挂「支付成功确认」，异步（满 5 分钟）挂「订单已接收」。同一 Token 只挂首封，异步场景后续到账的「支付成功确认」不再重复嵌入。
- **订单取消通知模板**：2026-07-17 修订已在 PRD §5.4b 补齐（Subject/正文/取消原因文案表/变量/发送边界），此前 PRD 第五章缺该模板的问题已闭环。

## 5. 数据模型变化（ER v8.0 → v9.1）

### 5.1 parent_order（父订单）新增 4 字段

| 字段 | 类型/说明 |
|------|----------|
| `parent_status` | 父订单状态：pending_payment / paid / cancelled |
| `payment_deadline` | 待付款超时时间（下单 + 30 分钟，仅对 pending 状态生效） |
| `paid_at` | 付款到账时间 |
| `cancelled_at` | 取消时间（待付款取消） |

> parent_order 从 9 字段变为 13 字段，**需要 DDL 变更 + 迁移脚本**。

### 5.2 payment_order（支付单）新增 1 字段

| 字段 | 类型/说明 |
|------|----------|
| `remark` | 备注（72h兜底等异常说明）。processing 超72h且渠道查询非成功时写入"渠道处理超72小时未成功"。后台支付单列表和详情页展示 |

### 5.3 order（子订单）无字段增删，语义变化

- `paid_at` 说明改为「付款到账时间（继承父订单）」。
- 表语义：支付到账后才按商家拆分（起始 paid）。
- **注意**：order 表两版都没有 `payment_deadline`，不存在「从 order 迁移」——超时字段是本次**新增**到 parent_order。

### 5.4 枚举变化

| 枚举 | 变化 |
|------|------|
| `parent_order.parent_status`（全新维度） | pending_payment / paid / cancelled |
| `order.order_status` | paid / shipped / completed / cancelled（**起始即 paid，不再含 pending_payment**） |
| `checkout_session.checkout_status` | 转化口径与 V1.0 基线一致（**支付成功才转化**）。v1.2 仅细化：pending 语义扩展为「结算流程中 or 已提交支付但付款未成功」（因新增待付款态，pending 覆盖面变宽）；新增「数据结构与召回策略解耦」说明。**注**：过程中曾一度改为「提交支付即转化」，2026-07-17 修订已改回「支付成功才转化」，与基线口径统一，故本项非实质差异 |
| `payment_order.status` | pending / processing / succeeded / failed / closed（processing 在原型 v5 已存在，非本次新增；以 PRD/ER 为权威） |

> 其余表（order_item / order_package / refund_request / refund_order / payment_transaction / order_discount 等）字段与关系两版一致。

## 6. 流程变化（系统流程图 v1.0 → v2.0）

### 6.1 段落结构

| v1.0 | v2.0 |
|------|------|
| ① 结算与**支付** | ① 结算与**下单** |
| ④ 订单取消 + ⑤ 退款处理（两段） | ④ 订单取消**与退款**（合并为一段） |

### 6.2 拆单时机（核心变更）

- v1.0：① 段点 Place Order → ② 段支付成功后「创建父订单 + 按商家拆子订单」（父子订单同时创建）。
- v2.0：① 段「创建 parent_order(待付款)、挂父订单快照、暂不拆单」→ ② 段到账后「parent_order 转已支付 + 按商家拆子订单(起始 paid) + 生成子订单明细」。

### 6.3 库存锁定时机 + 术语（双变）

- v1.0：**支付成功时**预占库存；术语「预占」。
- v2.0：**下单即锁**库存（锁在 parent_order）；术语统一为「锁定」；发货时「锁定转实扣」。
- 需处理：下单锁定后支付失败/超时的释放逻辑。

### 6.4 取消时序（核心变更）

- v1.0：取消 → 立即「订单状态→已取消」→ 再退款。
- v2.0：
  - **未付款分支（新增）**：parent_order→已取消 + 关支付单 closed + 释放库存，**结束不退款**。
  - **已付款分支**：创建退款申请 → 商品退款中（**订单暂不改状态**）→ 通道退款 → Webhook →「**退款成功后才置订单已取消**」；退款失败→「挂人工，订单不置取消」。

### 6.5 弃单边界（2026-07-17 口径最终确认）

- 转化口径：**支付成功才转化**（converted 在 parent_order 转 paid 时置），与 V1.0 基线一致。
- 弃单判定：`checkout_status = pending` 且超时即弃单。「提交支付但最终失败/超时取消」的会话仍为 pending，**算入弃单率**（结算漏斗真实流失）。
- 数据结构与召回策略解耦：召回邮件不面向已提交支付（审核中/失败/取消）的会话——此为 §5.5 邮件发送策略，不影响 checkout_status 枚举与弃单统计口径。
- 后台「发送恢复链接」按钮显示条件与召回范围对齐，列为后续迭代（见 PRD §后续迭代）。

## 7. 开发关注重点（按优先级）

1. **【最高】订单创建时机改造**：parent_order 从「支付成功创建」改为「下单创建（待付款）」；子订单拆分 + order_item 生成从下单挪到支付到账回调里。落库时机、事务边界、幂等键都要改。所有依赖「下单即有子订单」的逻辑需按新时序重排。

2. **【高】parent_order DDL 变更**：新增 parent_status / payment_deadline / paid_at / cancelled_at 四字段 + 迁移脚本。待付款态生命周期只在 parent_order 维护，子订单不含待付款态。

3. **【高】取消置位时序**：已付款取消必须等退款成功回调后才置 order 为 cancelled；退款失败要挂人工、订单保持 paid，**不能提前置 cancelled**。任何「取消即完结/即释放库存」的旧实现要改。

4. **【高】待付款超时任务**：基于 payment_deadline（下单+30分钟）的定时/延时任务。超时时**仅关闭 pending 状态的支付单**→走未付款取消（释放库存、不退款）。processing 状态（已提交付款、渠道审核中）的支付单**不关闭**，等渠道回调。

5. **【中】库存锁定时机前移**：从「支付成功」提前到「下单点 Place Order」，锁定主体是 parent_order；处理下单后支付失败/超时的释放。术语由「预占」统一为「锁定」。

6. **【中】同步/异步支付分岔**：命中风控 → 支付单 processing、parent_order 停待付款、前端跳「订单已提交」页；需支付回调二次驱动状态。

7. **【中】前端页面**：新增「订单已提交」页（异步）；C 端订单列表待付款展示一条父订单；订单成功页两套变体（Order Confirmed / Order Placed）。

8. **【中】邮件 + 5 分钟异步判定任务**：异步场景多发一封 #4「订单已接收」，触发点为「提交付款满 5 分钟仍 processing」（**非下单时**），需延迟 5 分钟的定时任务读支付单状态决定是否发；到账再发 #1；秒到账（5 分钟内 succeeded）只发 #1。设置密码链接挂用户首封含订单信息邮件（同步挂 #1、异步挂 #4）。该 5 分钟阈值仅用于邮件触发，不影响支付流转/页面跳转/库存/超时。

9. **【低】checkout_session 转化时机（口径与基线一致，无需改代码）**：converted 仍在**支付成功**时置（parent_order 转 paid），与 V1.0 一致。v1.2 仅扩展 pending 语义（含已提交支付但未成功），弃单判定口径不变（checkout_status=pending 且超时）。「提交支付但失败/超时取消」算入弃单率。召回邮件排除已提交支付会话属发送策略（见邮件方案），不影响本字段逻辑。
