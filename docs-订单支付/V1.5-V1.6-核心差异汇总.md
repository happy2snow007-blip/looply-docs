# 订单支付 V1.5 → V1.6 核心差异汇总

## 1. 本次交付范围

| 类型 | V1.5 基线 | V1.6 交付 |
|---|---|---|
| 开发 PRD | 多国家开站支持迭代 PRD V1.5 | 发货前验货退款迭代 PRD V1.6 |
| 后台原型 | v25 | v34 |
| ER 图 | v9.2（另含多国家增量 ER v1.0） | v9.6 |
| 系统流程图 | v2.0（另含多国家增量流程 v1.0） | v3.0 |
| 邮件模板 | 沿用既有退款邮件 | 退款成功与订单取消结果邮件模板 v2 |

完整 PRD v1.6 用于归档和全量规则查询，不作为本开发包的主实现文档。研发以迭代 PRD V1.6、原型 v34、ER v9.6、流程图 v3.0 为本期实施基线。

## 2. 新增能力

- 运营可在订单列表和订单详情发起退款，一次选择多件商品并逐件填写商品退款金额。
- 同一申请只生成一张退款申请、一张退款单和一笔渠道退款，避免多件商品产生多笔到账记录。
- 单独填写“本次退款总额”。总额允许大于商品退款明细合计，差额作为订单级退款，用于承载运费、税费等未分摊金额。
- 同一商品在前一笔退款终态后，可再次发起部分退款；未结束申请会占用订单可申请退款额度。
- 后台退款记录分别展示申请状态和资金状态，覆盖提交、审批、渠道退款与失败处理阶段。

## 3. 业务规则调整

- 系统不区分“退款”和“补偿”，不增加退款类型。
- 不在商品维度选择“继续发货”或“不再发货”。
- 普通部分退款申请、审批和退款处理中均允许操作发货，不要求等待退款到账。
- 当“订单累计成功退款”达到“订单实付”时，必须先触发订单取消；订单取消后再释放该订单仍处于预占状态的库存。
- 预计累计退款达到订单实付时，从申请提交起阻断新的发货操作，避免取消与发货产生冲突。
- 已发货或已签收商品的履约事实保留；订单取消只释放尚未发货且仍被订单预占的库存。
- 普通部分退款成功且订单继续履约时不发送退款成功邮件；仅在已付款订单取消成功后，按订单发送一封退款成功与订单取消结果邮件。

## 4. 金额口径

- 订单实付包含商品金额、运费、税费并扣减优惠，是订单累计退款和取消判定的唯一上限。
- 商品累计已退只累加该商品明细中的成功退款金额。
- 订单累计成功退款累加每笔退款申请总额，包括商品退款与订单级退款。
- 订单可申请退款 = 订单实付 − 订单累计成功退款 − 同订单其他未结束申请占用金额。
- 本次退款总额不得小于商品退款明细合计，也不得超过订单可申请退款。

## 5. 数据与状态变化

- 删除退款申请的 `refund_type` 分流。
- 删除商品单一 `refund_status`；商品仅保留累计成功退款金额 `refunded_amount`。
- 退款申请总额与商品退款明细解耦；差额不分摊到任一商品。
- 累计退款达到订单实付后，订单可从已付款、已发货或交易完成进入取消处理并最终变为已取消。
- 重复提交、重复审批和重复渠道回调只生效一次，不重复建单、累计金额、取消订单、释放库存或发送邮件。

## 6. 页面变化

- 发起退款弹窗增加多商品选择、逐件退款金额、本次退款总额和订单级退款金额。
- 金额摘要收敛为“本次可退、商品合计、订单级退款”。
- 发起退款和发货弹窗删除规则解释说明条。
- 发货校验改为按订单预计累计退款判断是否阻断。
- C 端本期无新增页面、状态、商品分组或交互；继续只展示订单级累计 Refund，并回归 Confirmed、On its way、Completed 和 Cancelled 的现有展示。

## 7. 开发关注重点

1. 退款申请总额、商品退款明细合计、订单累计成功退款是三个不同金额，禁止相互替代。
2. 多商品退款只能创建一笔渠道退款，商品明细用于额度与累计拆分。
3. 普通部分退款不阻断发货；预计累计达到实付时必须阻断新发货。
4. 全额结果由多次成功退款累计触发，不能只判断单笔退款金额。
5. 库存释放必须由订单取消触发，退款成功不能直接释放库存。
6. 退款结果邮件必须等订单取消成功后发送，普通部分退款不发送。
7. C 端不读取商品级退款明细，本期仅验证订单级 Refund 的既有展示。

## 8. 跨模块依赖

- 售后退款额度需扣除商品全部历史成功退款金额。
- 库存模块继续按订单取消事件释放订单预占，不解除人工质量锁定。
- 支付渠道需支持一张退款单对应一笔退款，并以幂等结果更新成功累计。
