## 3. 新增功能

### 3.1 结算会话补记三类数据（§4.2.0，新增章节）

买家在结算页填的东西**随填随存**到结算会话，让弃单后台能看到"他填了什么、卡在哪"。

| 类别 | 记什么 |
|---|---|
| **买家邮箱与身份** | 结算时的邮箱（**游客也记**）+ 是否注册用户 + **联系方式来源 / 收货地址来源**（自动带出 / 买家填写 / 自动带出后被修改）|
| **地址快照** | 收货地址 10 项 + 账单地址 9 项，**买家填多少存多少**，各自带填写状态（未填写 / 部分填写 / 已填完整）|
| **优惠码尝试记录** | **每提交一次校验记一条**，含码值 / 来源（链接带入·买家手输）/ 结果 / 未通过原因（九类）/ 减免金额 / 被移除时间 |
| **结算进度** | 六值枚举，记录**最远到达**的环节，只进不退 |

**为什么记每一次尝试而不是只记生效码**（本次最关键的设计决定）：取自当前 Shopify 后台的 711 条真实弃单会话，**36% 填过优惠码**。只记「最终生效的那个码」，就看不到「填了码但没用上」的那批会话——而码没生效的原因（未达门槛 / 地区不支持 / 每人限次已用尽）直接指向规则配置是否合理，正是运营要排查的。

> **平台不判定买家输入的码是真是假**，提交什么就记什么，不做真伪或有效性的预判。

### 3.2 弃单列表增强（§4.2.1）

**唯一改动：右上角多一个「导出」按钮。** 筛选项（3 项）与列表列（7 列）**均保持原样**。优惠码、地址填写情况、结算进度都是排查用的细节，落点在详情页与导出文件，不进列表。

### 3.2b 已登录买家的自动带出（**易漏，开发必读**）

已登录买家进结算页时，**邮箱与收货地址大多是系统自动带出的**，他本人一个字没填。两条口径：

1. **时间线要用不同事件区分**：「自动带入联系方式 / 自动带入收货地址」与「填写邮箱 / 填写收货地址」是**两类事件**，不能混记。混了运营会把系统填的看成买家填的，误判流失位置。买家改动带出的地址，再出一条「修改收货地址」。
2. **自动带出算「已填」**（产品拍板）：进度按带出的内容照常推进，与买家手填一视同仁。
   ⚠️ 随之而来的读法要求：**「进度 = 已填收货地址」不等于「买家填过地址」**——已登录买家一进页面通常就是这个进度。要判断买家有没有真动手，**看时间线里是「自动带入」还是「填写 / 修改」**。

### 3.3 弃单详情增强（§4.2.2）

- 基本信息新增**结算进度**、最后活动时间、转化订单号
- 地址区块改为**始终显示 + 空态**（见 §4 第 1 条）
- 事件时间线新增 4 类事件：填写邮箱 / 应用优惠码 / 优惠码校验失败 / 移除优惠码。**优惠码尝试记录并入时间线呈现，不单独成模块**——买家在结算页的动作本就是一条时间序列，抽成独立表格会让运营在两处对时间才能还原经过。事件详情格式：`{码值}（{码来源}）· 已应用，减免 {金额}` / `{码值}（{码来源}）· 未通过：{原因}` / `{码值} · 买家主动移除，本单不再享受该优惠`

### 3.4 弃单数据导出（§4.2.3，新增章节）

**一行 = 一个弃单会话**（商品合并成一列），**43 列**。弹窗形态复用对账管理那套。

两条硬性约束：
- **导出必须留痕**（操作人 / 时间 / 筛选条件 / 条数）——数据含邮箱、电话、完整地址，这是隐私合规要求
- **IP 与设备信息不进导出文件**——对召回分析无用，只会扩大个人数据外流面

## 7. 与营销活动模块的边界（**开发必读**）

营销 V1.3 明确写了「链接不落库、会话里的码位记在浏览器侧不落库」，**本次不推翻这条**。

| | 营销侧的「码位」 | 本次新增的「优惠码尝试记录」 |
|---|---|---|
| 记什么 | 买家点链接后**跟随他浏览的待用码** | 买家**在结算页实际提交校验的每一次输入** |
| 存哪 | 浏览器侧，会话级，不落库 | 结算会话下，落库 |
| 本次是否改动 | **否，完全不动** | 新增 |

**一句话**：优惠码怎么带、怎么判、失败提示什么文案，**全部沿用营销 V1.3 §2.3 不变**；本次只是在校验有结果的那一刻额外把结果记一条，**校验逻辑零改动**。

营销返回本文未覆盖的未通过原因时，记为「其他」并保留营销侧原始标识，**不丢弃记录**。

## 8. 需要注意的实现约束

| # | 约束 |
|---|---|
| 1 | **随填随存**：不能等买家点下单才存——弃单买家永远不会点下单。具体保存时机与频率由技术方案定，业务要求是「买家离开页面时，他已填的内容必须已被记录」 |
| 2 | **转化后保留**：会话转为订单后这些数据照常保留，不因转化而清空 |
| 3 | **历史数据不回填**：上线前已存在的会话没有新增字段，列表与导出对应列为空 |
| 4 | **单次导出上限 5 万条**，超出不执行并提示缩小筛选范围；是否走异步生成由技术方案定 |
| 5 | 未采集到的字段**导出为空**，不填「无」「未知」等占位文本——空值在 Excel 里能直接筛选和计数，占位文本不行 |

**第五轮 · 时间线区分「地址填写完成」**（同日）：

原「填写收货地址」一条事件，答不了最要紧的问题——**买家是填了一半走的，还是填完了才走的**。拆成两条：

| 事件 | 触发 |
|---|---|
| **开始填写收货地址** | 收货地址首次有任一字段有值（详情写「已填 N/7 项」）|
| **收货地址填写完成** | 收货地址首次达到「已填完整」（必填项齐全）|

- 配套原型 v12 → **v13**（emma 单拆为两条事件；lisa 单只有「开始填写」，正是卡在填地址的样例）。
