## P0（规则缺失或制品矛盾，阻塞开发）

### 1. [开发] §3.3 source_language_code 描述与 §1.5/§3.8 矛盾

- **位置**：PRD §3.3 写入参数表（第 180 行）vs §1.5（第 60 行）vs §3.8（第 231 行）
- **问题**：§3.3 写入参数表中 source_language_code 的说明为"源语言代码（**取自商家 default_content_language 或用户当前选择**）"。但 §1.5 明确"本期硬编码为 `en`（英语），不依赖商家模块"，§3.8 也写"本期硬编码为 `en`"。开发看 §3.3 会去找 merchant 表的 default_content_language 字段（该字段不存在），与 §1.5/§3.8 直接冲突。
- **建议**：将 §3.3 第 180 行改为"源语言代码（本期硬编码 `en`，后续方案见 §3.8）"，与 §1.5/§3.8 对齐。

## P1（规则不完整，影响质量）

### 2. [开发] §4.7 "AI翻译中" UI 提示的检测机制未定义

- **位置**：PRD §4.7 后的 **UI 提示**段（第 321 行）+ §2.3 翻译状态定义（第 97-106 行）
- **问题**：第 321 行写"当字段处于'AI 翻译中'状态时，译文输入框仍可编辑，但显示提示：'AI 翻译进行中，手动保存后将以您的输入为准'"。但 §2.3 只定义了两个 DB 状态（translated / outdated），"AI翻译中"不是持久化状态。开发会问：前端如何知道某字段正在被 AI 翻译？是 translation 表有一个 translating 中间态？是一个单独的队列接口？还是前端根据"刚触发过但还没回调"本地推断？PRD 没给答案。原型中也没有实现这个状态（grep 未匹配）。
- **建议**：两种处理方向：
  - A）在 §2.3 补充瞬态状态"AI翻译中"（如 translation 表增加 `translating` 临时状态，AI完成后变为 translated），并在 §6.2 翻译详情页补充该状态的 UI 展示
  - B）删除该 UI 提示，改为在 §4.7 中说明"AI 结果到达后若检测到 updated_at 更新则静默丢弃，前端无需感知 AI 进行中状态"

### 3. [设计] §6.3 resource_type 映射表与原型下拉 + §6.1 资源列表三方不一致

- **位置**：PRD §6.3 resource_type 映射表（第 595-608 行）+ §6.1 资源类型列表（第 389-406 行）+ 原型 RegisterKeyModal（第 1142 行）
- **问题**：三处定义不一致：

  | 页面 | §6.1 资源列表 | §6.3 映射表 | 原型下拉 |
  |------|:---:|:---:|:---:|
  | 登录注册 page-auth | ✅ | ❌ | ✅ |
  | 集合页 page-collection | ✅ | ❌ | ✅（"Collection"） |
  | 订单列表 page-orders | ✅ | ❌ | ✅（"订单中心"） |
  | 搜索页 page-search | ✅ | ❌ | ✅（"搜索"） |
  | 导航栏 page-nav | ✅ | ❌ | ✅（"导航栏"） |
  | 支付成功页 page-order-success | ✅ | ✅ | ❌ |
  | 服务条款 legal-tos | ✅ | ✅ | ❌ |
  | 隐私政策 legal-privacy | ✅ | ✅ | ❌ |
  | 退货政策 legal-return | ✅ | ❌ | ❌ |
  | Cookie政策 legal-cookie | ✅ | ❌ | ❌ |

  §6.3 映射表只覆盖了 §6.1 资源列表中 26 个前端页面/法律文档类型里的 9 个，遗漏 17 个。开发无法确定遗漏的页面对应什么 resource_type。原型下拉选项与映射表也有出入。

- **建议**：§6.3 映射表必须覆盖 §6.1 中所有 `page-*` 和 `legal-*` 资源类型，一一映射。原型下拉也同步更新。同时统一命名（如 §6.1 叫"集合页"，原型叫"Collection"，应统一）。

### 4. [测试] §6.4 术语导入弹窗缺少详细定义

- **位置**：PRD §6.4（第 641 行）+ 原型 ImportTermModal（第 1119-1129 行）
- **问题**：PRD §6.4 只有一行"导入术语按钮 | 打开导入弹窗"，没有任何弹窗内容定义（支持什么格式、模板包含哪些字段、导入后展示什么结果）。测试无法写导入功能的用例。对比 §6.3 的 Key 批量导入有完整描述（"支持 xlsx/CSV/JSON 格式导入，模板包含所有必填字段，导入后显示成功数/失败数/失败明细"），术语导入的定义明显缺失。原型实现支持 .xlsx 和 .csv（不含 JSON），也无法从 PRD 得到验证。
- **建议**：在 §6.4 "导入术语按钮"后补充导入弹窗定义，至少包含：支持格式、模板字段（source_term / source_language_code / rule_type / context / 各语言翻译列）、导入结果展示、校验规则（如重复术语处理）。

## P2（描述可更精确）

### 5. [设计] §6.3 注册Key弹窗 PRD 遗漏"备注"字段

- **位置**：PRD §6.3 页面文案表单（第 586-593 行）+ 原型 RegisterKeyModal（第 1153 行）
- **问题**：原型注册Key弹窗包含一个"备注"选填字段（`<FormRow label="备注"><Input placeholder="选填" /></FormRow>`），但 PRD §6.3 表单字段表中没有列出"备注"。编辑Key弹窗（EditKeyModal 第 1192 行）也有"备注"字段，Key列表表格原本也没有备注列。轻微不一致，不阻塞但会造成 PRD 与原型差异。
- **建议**：在 §6.3 表单字段表中补充"备注 | 否 | 选填，说明该 Key 的用途或注意事项"。

### 6. [开发] §5.3 多源语言处理缺本期说明

- **位置**：PRD §5.3（第 349-352 行）
- **问题**：§5.3 开头写"不同商家的商品可能有不同源语言（如日本商家源语言为 ja，美国商家源语言为 en）"，读起来像是当前就支持的功能。但 §1.5 和 §3.8 明确本期硬编码 en。开发可能误以为需要实现多源语言的读取逻辑。
- **建议**：在 §5.3 开头加一句"本期所有资源 source_language_code 统一为 en，以下描述的是系统架构如何支持未来多源语言场景"，与 §1.5/§3.8 呼应。

### 7. [设计] §4.3 分流规则的 outdated 记录在翻译详情页无 UI 区分

- **位置**：PRD §4.3（第 276-278 行）+ §6.2 翻译详情页（第 456-465 行）
- **问题**：§4.3 定义了按 translation_source 分流：ai 记录自动重译，manual 记录仅标记 outdated 等运营手动确认。但 §6.2 翻译详情页中，所有 outdated 记录统一显示"待更新"橙色标签，运营无法区分：哪些是"AI 正在自动重译、稍等即可"的记录，哪些是"需要我手动处理"的记录。在翻译量大时，运营可能白费时间逐条检查已在自动重译中的字段。
- **建议**：在 §6.2 状态标签说明中补充区分规则，如：待更新（AI重译中）显示"重译中"标签 / 待更新（需手动）显示"待更新"标签。或至少在 §6.2 的字段翻译行中增加 translation_source 的标记（如小图标区分 AI/人工来源），让运营能快速识别需要关注的记录。
