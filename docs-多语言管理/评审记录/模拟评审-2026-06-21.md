## P0（规则缺失或制品矛盾，阻塞开发）

### 1. [开发] static_content 源文本编辑路径缺失

- **位置**：PRD 第 2.2 节 vs 第 5.2 节
- **问题**：PRD 2.2 明确声明 static_content 规则为"运营在翻译后台直接编辑源语言内容"，且 3.2.2 描述了"运营编辑源语言内容并保存"会触发内部生成 translation_request。但 5.2 翻译详情页将源文本定义为"只读显示源语言内容"，没有任何编辑入口。原型也同样将源文本展示为只读 div。

  具体场景：运营需要修改首页 Banner 标语（static_content），当前 PRD 和原型都没有描述在哪里、怎么编辑源文本。编辑源文本是触发目标语言重新翻译的核心路径，不定义清楚无法开发。

- **建议**：在 5.2 翻译详情页中，对 static_content 类型的字段，源文本区域改为可编辑状态（TextArea），并补充以下规则：
  - 当查看的语言 = 源语言时（如运营选择编辑英文原文），字段显示为编辑模式
  - 或者增加一个"编辑源文本"的操作按钮，点击后切换为编辑态
  - 保存后触发内部 translation_request 生成

### 2. [开发] 翻译设置页 PRD 有定义但原型无实现

- **位置**：PRD 第 5.5 节 vs 原型菜单结构
- **问题**：PRD 5.5 定义了"翻译设置"页面（目标语言列表、AI翻译模型选择、翻译提示词模板、术语表自动应用开关），原型的左侧菜单只有 3 个入口（翻译内容 / Key管理 / 术语表），没有"翻译设置"页面。

  具体场景：开发按原型做菜单不包含设置页，按 PRD 做则多出一个页面，产品意图不明确。

- **建议**：二选一——
  A. 原型补充翻译设置页面（菜单加第 4 项）  
  B. PRD 5.5 标记为"本期不做"并从功能模块中移除（如果认为 AI 参数和提示词当前可以写死代码里）

### 3. [开发] Key 注册弹窗字段严重不一致

- **位置**：PRD 第 5.3 节"添加 Key（弹窗）" vs 原型 RegisterKeyModal（line 1083）
- **问题**：PRD 定义注册 Key 弹窗有 8 个表单字段（resource_type, resource_label, field_name, field_label, field_type, key_type, source_system, sort_order），是统一的表单结构。

  原型实现完全不同：按 key_type 分两种表单——
  - "业务字段"模式：来源模块 + 实体类型 + 字段名 + Key名称（自动拼接）= 4 个字段
  - "页面文案"模式：归属页面 + Key名称 + 源文本(英文) = 3 个字段

  缺失字段对比：
  | PRD 字段 | 原型(业务字段模式) | 原型(页面文案模式) |
  |---------|-------------------|-------------------|
  | resource_type | ✅ 有(实体类型) | ❌ 无(归属页面不等于 resource_type) |
  | resource_label | ❌ 无 | ❌ 无 |
  | field_name | ✅ 有 | ❌ 无(Key名称≠field_name) |
  | field_label | ❌ 无 | ❌ 无 |
  | field_type | ❌ 无 | ❌ 无 |
  | key_type | ✅ 有 | ✅ 有 |
  | source_system | ✅ 有(来源模块) | ❌ 无 |
  | sort_order | ❌ 无 | ❌ 无 |

  开发以哪个为准完全无法判断。

- **建议**：确定产品意图后统一。如果原型的分模式设计更符合运营使用习惯，则 PRD 应改为描述这种分模式表单；如果 PRD 的统一表单更合理，则更新原型。关键是 field_type（text/image/rich_text）和 field_label 在任何模式下都不能缺，否则翻译详情页无法正确渲染字段卡片。

### 4. [测试] resource_type 格式约束与资源类型列表自相矛盾

- **位置**：PRD 第 5.3 节校验规则 vs 第 5.1 节资源类型列表
- **问题**：5.3 定义校验规则为"resource_type 格式 | 小写字母、数字、连字符，最大 50 字符"（即只允许 a-z0-9-）。但 5.1 资源类型列表中包含 `attribute_option`（下划线）。ER 图 resource_type_open_field 设计规则也列出了 `pdp_template`、`email_template` 等下划线格式。

  具体场景：开发按 5.3 做输入校验 → 注册 "attribute_option" 时校验不通过 → 无法注册商品域属性选项的翻译字段。

- **建议**：格式约束改为"小写字母、数字、连字符、下划线"（即允许 a-z0-9_-），与实际使用的 resource_type 一致。

## P1（规则不完整，影响质量）

### 5. [开发] 术语规则类型原型缺少 recommended

- **位置**：PRD 第 5.4 节 vs 原型 AddTermModal（line 1053-1054）、GlossaryListPage 筛选（line 989-990）
- **问题**：PRD 和 ER 定义 3 种规则类型（do_not_translate/mandatory/recommended），原型只实现了 2 种（禁译词/强制术语），缺少"推荐术语"选项。

  具体场景：运营想添加一个推荐但不强制的术语翻译（如行业通用但允许灵活表达的词），在原型中找不到该选项。

- **建议**：原型 AddTermModal 和 GlossaryListPage 筛选中补充"推荐术语"选项。

### 6. [开发] Key 管理表格缺少 field_type 列

- **位置**：PRD 第 5.3 节表格列定义 vs 原型 KeyManagementPage columns（line 939-946）
- **问题**：PRD 定义了"字段类型 | field_type | text / image / rich_text"列，原型表格没有这一列。field_type 对运营有实际意义（区分文本翻译和图片翻译的字段）。

- **建议**：原型 Key 管理表格补充 field_type 列。

### 7. [开发] Key 管理缺少导出按钮

- **位置**：PRD 第 5.3 节页面元素 vs 原型 KeyManagementPage headActions（line 954-958）
- **问题**：PRD 明确列出"导出按钮 | 导出当前列表为 CSV"，原型只有"注册Key"和"批量导入"两个按钮。

- **建议**：原型补充导出按钮，或 PRD 明确标注本期不做导出功能。

### 8. [开发] 添加术语弹窗缺少 source_language_code 字段

- **位置**：PRD 第 5.4 节"添加术语（弹窗）" vs 原型 AddTermModal（line 1045-1067）
- **问题**：PRD 将 source_language_code 列为必填字段，原型没有这个字段（默认所有术语源语言为英文，但未给运营选择入口）。

  具体场景：looply 支持多源语言（日语商家的术语源语言可能是日文），如果添加术语时不能选择源语言，日语术语无法正确注册。

- **建议**：原型 AddTermModal 补充"源语言"下拉字段。如果当前阶段确定术语只从英文出发，则 PRD 将该字段改为"否（选填）"并说明默认值。

### 9. [开发] PRD 未定义 key_type 中文显示名映射

- **位置**：PRD 第 5.3 节 vs 原型 KeyManagementPage
- **问题**：PRD 表格列定义 key_type 显示值为"entity_field / static_content"（技术值），但原型展示的是"业务字段 / 页面文案"（中文名）。PRD 没有定义 key_type 枚举值到中文显示名的映射关系。

  具体场景：开发做 UI 时不知道显示技术值还是中文名，以及筛选器 option 用什么文字。

- **建议**：在 PRD 1.4 术语说明或 5.3 节补充映射表：entity_field → 业务字段、static_content → 页面文案（或确定用什么中文名）。

### 10. [开发] 字段注册后未翻译的 request 如何重新消费未定义

- **位置**：PRD 第 3.4 节"翻译请求消费规则"
- **问题**：3.4 定义"未注册的请求 | 忽略，status 保持 pending（等待字段注册后再处理）"。但没有定义这些 pending 的 request 在字段注册后如何被重新消费。

  具体场景：商品模块先推送了 translation_request（field_name=material），此时翻译模块还没注册这个字段，request 保持 pending。后来运营在 Key 管理注册了这个字段，那些挂起的 pending request 怎么办？定时轮询？注册时触发回扫？

- **建议**：补充规则——字段注册（status 变为 active）时，系统自动查询并消费所有 resource_type + field_name 匹配的 pending request。

## P2（描述可更精确）

### 11. [开发] 原型 STATUS_MAP 使用 stale 而非 outdated

- **位置**：原型 line 468 vs ER 图 translation.status 定义
- **问题**：ER 图定义状态值为 `translated` / `outdated`，原型代码中 STATUS_MAP 的 key 使用 `stale`（`STATUS_MAP = { translated:{...}, stale:{...}, untranslated:{...} }`），RD 数据中字段状态也用 `st:'stale'`。虽然只是前端展示变量命名，但容易在对接 API 时产生混淆。

- **建议**：原型 STATUS_MAP 的 key 统一改为 `outdated`，与后端 ER 定义一致（前端也用同一个术语）。

### 12. [测试] 翻译详情页"保存"行为定义模糊

- **位置**：PRD 第 5.2 节"手动编辑译文"操作流程第 2 步
- **问题**：描述为"点击保存（或失焦自动保存）"——开发需要实现哪种？两种的 UX 和技术复杂度差异大（自动保存需防抖、乐观更新、冲突处理）。

- **建议**：明确选择一种。从原型看有显式"保存"按钮，建议统一为"点击保存按钮提交"，移除"失焦自动保存"描述。

### 13. [测试] translated_value 字段长度限制未定义

- **位置**：PRD 第 5.2 节 + ER 图 translation.translated_value
- **问题**：PRD 对译文输入框没有定义最大长度限制。考虑到 rich_text 和法律文档翻译可能很长，开发需要知道数据库字段类型设计（VARCHAR(n) vs TEXT）。

- **建议**：补充说明——text 类型建议 TEXT（无固定长度上限）；或明确：短文本 ≤500 字符、长文本用 TEXT 类型。
