# looply 多语言模块 PRD

> 版本：V3.2  
> 日期：2026-07-23  
> 状态：评审版  
> 说明：本文档为完整自包含 PRD，独立可读，涵盖多语言模块的全部功能与数据设计。

**本版（V3.2）变更要点**：在 V3.1 基础上整合三项能力，解决"商详接多语言"暴露的单层模型缺口——

1. **翻译资源目录（建卡 + 域元数据）**：把原来散落的 `resource_type` 开放字段升级为显式建卡对象 `translation_resource`，并新增域元数据 `translation_domain` 驱动导航分 Tab。业务模块须"先建卡再注册字段"。
2. **页面聚合（`resource_group`）**：把一个 C 端页面下的多个资源卡片聚合成一个导航单元，解决"动态套动态"（如商详 CMS）导致的卡片零散。
3. **静态文案后台管理（`storage_mode`）**：新增 `storage_mode` 区分"翻译中心 / 语言包"两种落地方式，静态文案以语言包落地并支持后台查看/修改。

数据模型表数量由 5 张扩展为 8 张，`translatable_field_config` 完成改造。数据模型基准为 ER v2.4，配套后台原型为 v13、接入规范（产品版）为 v3.2。

## 一、概述

### 1.1 背景与目标

looply 作为面向全球市场的二手电商平台，需要将商品信息、页面文案、通知模板、法律文档等内容翻译为多种目标语言，以支撑多国销售。

多语言模块是 looply 的基础能力模块，为所有业务模块提供统一的多语言内容存储与翻译服务。

**核心目标**：

1. 统一多语言管理后台，运营可集中管理所有业务内容的源文本和翻译
2. AI 自动翻译为主，人工修正为辅，无审核环节，追求翻译效率
3. 注册表模式接入，各业务模块按需建卡并注册可翻译字段，翻译模块不感知业务细节
4. 术语表保证品牌名、专业术语在所有语言中的翻译一致性
5. Localized Content 分离架构：所有多语言文本（含源语言）统一存储在翻译模块，业务表只保留结构化数据
6. 翻译中心以"域 → [页面分组] → 卡片 → 实例 → 字段"的层级组织内容，卡片可聚合、可按域导航

### 1.2 本期不做

| 不做的事 | 理由 |
|---------|------|
| 审核/审批流程 | 本期 AI 直译 + 人工可修正，无审核节点 |
| 翻译任务/批量作业管理 | 本期全部自动触发，不做手动创建批量任务 |
| 翻译历史版本 | 只保留当前有效版本，变更通过审计日志追溯 |
| 商家端翻译界面 | 本期只做运营后台 |
| 多渠道差异化翻译 | 所有渠道使用同一份翻译 |
| 语言列表管理 | 语言归属 Market 模块，翻译模块只引用 |
| 翻译设置页面 | AI 翻译模型、提示词模板等参数本期写死代码，不做后台配置界面 |
| Key 导出功能 | 本期只做导入，不做 CSV 导出 |
| APP 端后台 | 多语言管理为运营后台功能，仅提供 PC 端，不做 APP 端 |
| 运营自助建卡 / 分组 / 域管理界面 | 本期建卡、分组归属、域元数据均走 migration / config 由开发落地，不做运营自助增改删排序界面（见 §九 后续迭代方向） |
| Key 管理页手动注册 / 编辑 | 本期 Key 管理页只读，字段由业务模块通过 API 注册（见 §5.3） |

### 1.3 用户角色

| 角色 | 说明 | 主要操作 |
|------|------|---------|
| 翻译运营 | 负责多语言内容管理和质量修正 | 编辑源文本、查看翻译进度、修正译文、管理术语表 |
| 系统管理员 | 负责翻译模块配置 | 在 Key 管理页只读查看已注册可翻译字段；术语表管理 |

> 本期建卡、页面分组、域元数据的维护由开发在业务模块联调阶段通过 migration / config 完成，不作为运营/管理员的后台操作。

### 1.4 术语说明

| 术语 | 说明 |
|------|------|
| 域（domain） | 翻译内容的一级分类（商品域 / 前端页面 / 通知模板），对应 translation_domain 一条记录，驱动导航页分 Tab |
| 页面分组（resource_group） | 把同一 C 端页面下的多个卡片聚合成的导航单元，对应 resource_group 一条记录，如"商详页" |
| 卡片 / 翻译资源（translation_resource） | 翻译中心一级对象，一张卡 = 一个 resource_type（一个业务实体类型，或一类页面文案） |
| Key | 可翻译字段的注册标识，对应 translatable_field_config 中一条记录，归属某张卡片 |
| resource_type | 资源类型编码，由 translation_resource 建卡统一登记（本版由开放字段升为建卡主键），如 product、page-home、pdp_template |
| key_type | 卡片的 UI 分类标签：entity_field（业务实体字段）/ static_content（页面文案/法律文档等）。仅用于后台分类展示，不决定数据落地方式（见 §2.2） |
| storage_mode | 卡片内容的落地方式：translation_table（翻译中心 translation 表）/ language_pack（前端语言包）。决定内容实际存储位置与后台保存行为（见 §2.2） |
| integration_status | 卡片对接状态：connected（已对接）/ pending（待对接）/ placeholder（占位） |
| source_hash | 源文本的哈希值，用于检测源内容是否变更 |
| 术语概念 | glossary_concept 中的一条记录，一个源词条目对应多个目标语言译法 |
| 源语言记录 | translation 表中 source_language_code = language_code 的记录，表示原始录入内容而非翻译产物 |

### 1.5 多语言策略

- **语言标识**：使用 ISO 639-1 语言代码（如 en、fr、de、es、ja）
- **源语言（本期）**：所有资源的 source_language_code 硬编码为 `en`（英语）。本期不依赖商家模块，统一以英语作为源语言
- **源语言（后续）**：需结合商家模块和平台多 Market 运营视角重新设计，不仅是读取商家默认语言，还需考虑多 Market 场景下源语言的确定策略。具体方案待商家模块设计时统一规划
- **目标语言**：取 status = active 或 planning 的 Market 下已开通语言（market_language.status = active），去重后作为目标语言列表。suspended 状态的 Market 语言不参与新翻译触发（已有翻译记录保留不删，Market 恢复时自动可用）
- **统一读取**：前端通过 resource_type + resource_id + field_name + language_code 查询翻译服务即可获取任何语言的内容，无需区分源语言还是目标语言
- **RTL 支持**：language 表标记是否从右到左（rtl），前端渲染时据此调整布局方向

## 二、数据架构

### 2.1 Localized Content 分离原则

平台中的数据分为两类，按类型决定存储位置：

| 类别 | 特征 | 存储位置 | 示例 |
|------|------|---------|------|
| 结构化数据 | 值不随语言/地区变化 | 业务表原字段 | 价格、库存、重量、尺寸、brand_id、成色等级、SKU编码 |
| 本地化内容 | 值随语言/地区变化 | 翻译模块（translation 表或语言包，见 §2.2） | 标题、描述、SEO 文案、Banner 图、法律文档、通知模板、页面静态文案 |

**判断标准**：该字段的值是否随语言/地区变化？是 → 本地化内容，存翻译模块；否 → 结构化数据，存业务表。

**关键设计**：业务表不存任何文本字段。例如 product 表不存 title、description，这些内容全部存在翻译模块中（包括英文源版本）。

### 2.2 key_type 语义与 storage_mode

**key_type（卡片级分类标签）**

key_type 是卡片（translation_resource）上的一个 UI 分类标签，用于后台界面分组展示。本版起 key_type 由字段级上移至卡片级——同一张卡片的所有字段共享卡片的 key_type：

| key_type | 含义 | 示例 |
|----------|------|------|
| entity_field | 来自业务实体的字段 | product.title、category.name、brand.description |
| static_content | 页面文案/法律文档/通知模板 | page-home.hero_title、legal-tos.content、notif-email.subject |

**核心语义**：key_type 只用于后台分类展示，**不决定数据落地方式和触发链路**。内容实际存哪里、后台保存后如何处理，由 `storage_mode` 决定。

**storage_mode（内容落地方式）**

`translation_resource.storage_mode` 区分卡片内容的落地存储：

| storage_mode | 含义 | 落地存储 | 后台保存行为 |
|--------------|------|---------|-------------|
| translation_table | 翻译中心（动态业务内容） | translation 表 | 保存写入翻译服务，触发 AI 翻译（见 §四） |
| language_pack | 语言包（页面静态文案） | 前端语言包 | 多语言后台提供查看/修改面，保存后同步回语言包（同步机制由技术方案定） |

**静态文案的落地与后台管理**：页面静态 UI 文案（按钮、提示语、表单标签等）技术上仍以前端语言包落地（能力已实现）。在此基础上，多语言后台提供查看/修改面——运营可在翻译详情页动态管理静态文案的多语言值，保存后同步回语言包。两种 storage_mode 的内容在翻译详情页使用同一套界面，通过标注"翻译中心 / 语言包"区分。

> 静态文案的后台查看/修改入口在 **翻译详情页**（作为聚合卡下的"页面文案"分组或独立卡），不在 Key 管理页；且页面静态语言包字段不进入 Key 管理列表（见 §5.3）。

### 2.3 状态与枚举定义

**translation.status（翻译状态）**

| 状态值 | 中文显示 | 含义 |
|--------|---------|------|
| translated | 已翻译 | AI 或人工翻译完成，当前有效 |
| outdated | 待更新 | 源内容已变更，当前译文可能不准确 |

**"未翻译"不是数据库状态**：未翻译 = translation 表中无对应记录。前端根据"注册字段总数 × 已开通语言数 - 已有翻译记录数"计算未翻译数量。

**translatable_field_config.status（字段状态）**

| 状态值 | 中文显示 | 含义 | 触发时机 |
|--------|---------|------|---------|
| active | 启用 | 翻译模块接受该字段的源内容写入和翻译触发 | 业务模块通过 API 注册字段时默认状态 |
| inactive | 停用 | 翻译模块拒绝该字段的新写入，不触发新翻译，已有翻译记录保留可查 | 字段停用（本期通过 config 处理） |

状态转换：active ↔ inactive（可双向切换）。

**translation_resource.storage_mode（内容落地方式）**

| 枚举值 | 含义 | 落地存储 |
|--------|------|---------|
| translation_table | 翻译中心（动态业务内容） | translation 表 |
| language_pack | 语言包（页面静态文案） | 前端语言包 |

**translation_resource.integration_status（卡片对接状态）**

| 枚举值 | 中文显示 | 含义 | 导航页表现 |
|--------|---------|------|-----------|
| connected | 已对接 | 业务模块已完成翻译服务对接 | 实线卡片，可点击进入翻译详情页，显示翻译进度 |
| pending | 待对接 | 业务模块已设计但尚未完成翻译服务对接 | 实线卡片（灰色），不可点击，完成对接后切为 connected |
| placeholder | 占位 | 资源类型已规划但业务模块尚未设计 | 虚线卡片，不可点击，无翻译进度，业务模块对接后切为实线 |

**translation_resource.key_type（卡片分类）** / **glossary_concept.rule_type（术语规则）** 枚举定义分别见 §2.2 与 §6。

### 2.4 数据模型概览

本 PRD 数据模型依据多语言模块实体关系图 v2.4，包含 8 张表：

| 实体 | 说明 | 归属 |
|------|------|------|
| language | 语言 | 外部引用（Market 模块） |
| translation_domain | 翻译域（域元数据） | 多语言模块规则表（本版新增） |
| resource_group | 资源分组（页面聚合） | 多语言模块规则表（本版新增） |
| translation_resource | 翻译资源（卡片 / 建卡） | 多语言模块规则表（本版新增） |
| translation | 翻译内容 | 多语言模块核心表 |
| glossary_concept | 术语概念 | 多语言模块规则表 |
| glossary_translation | 术语翻译 | 多语言模块规则表 |
| translatable_field_config | 可翻译字段配置 | 多语言模块规则表（本版改造） |

**本版数据模型三点变化**：

1. **新增建卡与聚合三张表**：`translation_domain`（域元数据：domain / domain_name / sort_order / status）、`resource_group`（页面聚合：group_code / group_name / domain(FK) / sort_order / status）、`translation_resource`（建卡：resource_type(PK) / display_name / domain(FK) / group_code(FK,可空) / key_type / storage_mode / source_system / integration_status / sort_order）。
2. **translatable_field_config 改造**：`resource_type` 由开放字段升为 **FK → translation_resource**；卡片级属性（display_name / key_type / source_system）上移至 translation_resource；字段配置表只保留字段级属性（config_id / resource_type(FK) / field_name / field_label / field_type / sort_order / status）。
3. **translation 表不变**：resource_type 仍为 EAV 字段，逻辑引用 translation_resource.resource_type；language / glossary_concept / glossary_translation 沿用原设计。

> 三张新表均预留 `sort_order`，为后续"卡片 / 分组 / 域 运营编辑 + 排序管理"（见 §九）铺好数据基础，届时无需再改 ER。

详细字段定义见：`~/Desktop/海外业务/多语言/实体关系图/looply-多语言模块实体关系图-v2.4.svg`

## 三、业务模块集成规范

本节定义 Localized Content 分离架构对各业务模块的设计要求。所有需要多语言支持的业务模块必须遵守。

### 3.1 核心原则：业务表不存文本

每个业务模块在设计数据模型时，必须将字段分为两类分别存储：

| 字段类型 | 判断标准 | 存储位置 | 示例 |
|---------|---------|---------|------|
| 结构化数据 | 值不随语言变化 | 业务表 | price、stock、weight、brand_id、condition_grade |
| 本地化内容 | 值随语言变化 | 翻译模块 translation 表 | title、description、seo_title、banner_image |

**硬性规则**：业务表中不允许存在任何"会随语言变化"的文本/图片字段。这些内容全部由翻译模块管理。

**典型示例**：

```
product 表（只存结构化数据）:
  id, brand_id, category_id, condition_grade,
  weight, length, width, height,
  source_language_code,  ← 标记该商品原始录入语言
  created_at, updated_at

  ❌ 不存: title, description, condition_summary 等文本字段
```

### 3.2 受影响的业务表清单

以下业务表的文本字段需从业务表剥离，改由翻译模块存储：

| 业务表 | 需剥离的本地化内容字段 |
|--------|---------------------|
| product | title, description, condition_summary, appearance_desc, accessories_info, supplement_notes |
| listing | listing_title, listing_description, seo_title, meta_description |
| category | category_name |
| brand | brand_name, introduction, description |
| series | series_name, alias, description |
| spu | spu_name, description |
| sku | sku_name |
| attribute_def | attribute_name |
| attribute_option | option_value |
| condition_grade | grade_name, grade_description |

**后续需要多语言支持的内容**：以下内容也需要翻译能力，具体实现方式（业务模块 API 对接、前端静态页面、语言包等）待各自设计时确定：

| 内容类型 | 涉及内容 | 当前状态 |
|---------|---------|---------|
| 法律协议 | 服务条款、隐私政策、退货政策、Cookie 政策等法律文档正文 | 未设计，可能作为前端静态页面或独立模块 |
| Banner / 运营配置 | 首页 Banner、活动文案等运营动态配置内容 | 模块未设计 |
| 通知模板 | 邮件模板、站内消息模板 | 模块未设计 |

### 3.3 业务后台写入规范

业务后台（如商品管理后台）在用户录入文本内容时，底层必须写入翻译服务而非业务表：

**前置条件（本版强化）**：

1. **先建卡**：业务模块上线前须先在 `translation_resource` 中建卡（写入 resource_type + display_name + domain + [group_code] + key_type + storage_mode + source_system + integration_status），登记该资源类型。
2. **再注册字段**：在 `translatable_field_config` 中注册该卡片下的每个可翻译字段（resource_type 为 FK 指向建卡，status=active）。
3. **未建卡 / 未注册字段则源文写入被拒**：翻译服务对未建卡的 resource_type 或未注册的字段拒绝源文写入，防止产生游离译文。
4. 本期建卡与字段注册通过 migration / config 在业务模块联调阶段落地，resource_type 由建卡登记（见 §3.6）。

**写入参数**：

| 参数 | 必填 | 说明 |
|------|------|------|
| resource_type | 是 | 资源类型标识，须已在 translation_resource 建卡 |
| resource_id | 是 | 资源实例 ID |
| field_name | 是 | 字段标识，如 title，须已在 translatable_field_config 注册 |
| source_language_code | 是 | 源语言代码（本期硬编码 `en`，后续方案见 §3.8） |
| translated_value | 是 | 文本内容或图片 CDN URL |

**写入时机**：

| 业务场景 | 写入行为 |
|---------|---------|
| 创建资源（如新建商品） | 逐字段写入源语言记录，触发首次翻译 |
| 编辑资源（如修改商品标题） | 更新源语言记录的 translated_value，触发过期检测和重译 |
| 批量导入 | 通过批量写入接口一次提交多条源语言记录 |

### 3.4 业务后台读取规范

业务后台在展示文本内容时（如商品编辑页回显标题），同样从翻译服务读取：

- 调用翻译服务查询接口获取对应语言的文本内容
- language_code 传源语言代码即可获取源文本
- 不需要从业务表读取文本字段（业务表中没有）

### 3.5 资源删除处理

| 场景 | 处理方式 |
|------|---------|
| 业务资源删除（如商品下架删除） | 业务模块调用翻译服务删除接口，清除 resource_type + resource_id 下的所有翻译记录（全部语言全部字段） |
| 业务资源软删除 | 翻译记录保留，不做处理 |

### 3.6 建卡与字段注册要求

各业务模块上线前，必须按"先建卡再注册字段"完成以下登记：

1. **建卡**：梳理本模块需接入多语言的资源类型，在 `translation_resource` 建卡登记 resource_type、展示名、归属域、[页面分组]、key_type、storage_mode、来源系统、对接状态。
2. **注册字段**：梳理每张卡片下的本地化内容字段清单，在 `translatable_field_config` 中注册每个可翻译字段（FK 指向建卡）。
3. 注册后字段状态为 active，翻译模块开始接受该字段的源内容写入。

**落地方式（本期）**：建卡与字段注册均通过 migration / config 由开发在业务模块开发联调阶段完成，作为上线前置条件；不做运营自助建卡界面（见 §九）。

**"动态套动态"结构接入**：对商详 CMS 这类"模板 × 类目容器 × 容器内字段"的动态套动态结构，按配置粒度拆成多个独立 resource_type 分别建卡（各自单层平铺），再声明一个 resource_group 把它们聚合成一张页面导航卡（见 §5.1 / §5.2）。

### 3.7 容错设计

| 异常场景 | 业务模块处理方式 |
|---------|----------------|
| 翻译服务暂时不可用 | 源内容写入应重试（异步队列），不阻塞业务操作主流程。录入成功后用户可正常操作结构化数据 |
| 翻译服务返回空（无翻译记录） | 前端展示兜底文案（如"内容暂无翻译"）或降级显示源语言 |
| 源语言记录写入失败 | 提示用户"保存失败，请重试"，该条文本内容不可用 |

### 3.8 source_language_code 维护

每个业务资源需在业务表中保留 `source_language_code` 字段：

- 记录该资源的原始录入语言
- **本期**：硬编码为 `en`（英语），所有资源统一以英语作为源语言
- **后续**：源语言确定策略需结合商家模块和多 Market 运营视角重新设计，具体方案待商家模块设计时统一规划
- 该字段属于结构化数据（不随语言变化），存业务表

## 四、翻译流程

### 4.1 统一触发路径

所有翻译的触发路径完全统一，不区分 key_type：

```
源语言记录编辑保存
  → 更新 translation 表源语言记录的 translated_value
  → 重新计算 source_hash
  → 检测 hash 变更
  → 将同一 resource_type + resource_id + field_name 下所有目标语言的 status 标记为 outdated
  → 系统自动触发重新翻译（调用 AI 翻译服务）
  → 翻译完成后更新目标语言记录：status = translated
```

**关键设计**：
- 无中间审核环节，AI 翻译完成后直接标记为 translated
- 运营可事后在翻译详情页手动修正
- 源语言记录的编辑是触发其他语言重译的唯一入口

> 上述流程适用于 storage_mode = translation_table 的动态业务内容。storage_mode = language_pack 的静态文案同样支持源文/译文编辑与翻译，保存后同步回语言包（见 §2.2）。

### 4.2 源内容写入来源

源语言记录（source_language_code = language_code）的写入有两个来源：

| 来源 | 说明 | 场景 |
|------|------|------|
| 业务后台 | 商品后台录入标题/描述时，底层写入翻译服务 | 商品创建、商品编辑 |
| 翻译后台 | 运营在多语言管理后台直接编辑源文本 | 页面文案维护、源文本修正 |

两种来源写入后的行为完全一致：更新 source_hash → 标记目标语言 outdated → 触发自动重译。

### 4.3 过期检测（outdated）

当源内容变更时，系统自动检测并处理：

1. 源语言记录被编辑保存（来自业务后台或翻译后台）
2. 系统计算新的 source_hash
3. 新 hash ≠ 旧 hash → 将同一 resource_type + resource_id + field_name 下所有**目标语言**记录的 status 更新为 outdated
4. **按 translation_source 分流处理**：
   - translation_source = **ai** → 自动触发 AI 重新翻译，完成后覆盖写入（status=translated，translation_source=ai）
   - translation_source = **manual** → **不自动覆盖**，仅标记 outdated，保留运营手动精修的译文，等待运营在翻译详情页手动确认更新
5. AI 重译完成后 source_hash 更新为当前源的 hash

**hash 相同**：源内容未实际变更（如编辑后又改回原文），不触发任何操作。

**设计考量**：人工精修的译文成本高于 AI 翻译，自动覆盖会导致运营反复精修。按来源区分后，运营可以基于旧译文微调适配新源内容，而非从零翻译。

### 4.4 首次翻译触发

当新资源创建（如新商品上架），源语言记录写入后：

1. 系统检测该 resource_type + resource_id + field_name 的目标语言是否已有翻译记录
2. 无记录 → 系统自动为所有已开通目标语言调用 AI 翻译
3. 翻译完成后写入 translation 表：status = translated，translation_source = ai

### 4.5 字段注册触发回扫

当 translatable_field_config 新注册字段（status 变为 active）时：

1. 系统查询 translation 表中该 resource_type + field_name 已有的源语言记录
2. 对每条源语言记录，检查是否缺少目标语言翻译
3. 缺少的 → 系统自动触发 AI 翻译并写入结果

### 4.6 前端读取时的 Fallback 策略

当前端请求某语言的翻译时，按以下优先级返回：

1. translation 表中有对应语言记录且 status=translated → 返回译文
2. translation 表中有对应语言记录且 status=outdated → 返回旧译文（带标记，提示可能过期）
3. 无翻译记录 → 返回源语言版本（从 translation 表取源语言记录）

### 4.7 人工与 AI 翻译冲突处理

当运营在翻译详情页手动编辑译文时，可能存在 AI 翻译正在进行中的情况。冲突处理规则：

**人工优先原则**：运营手动保存的译文优先级高于 AI 自动翻译结果。

处理流程：
1. 运营手动保存译文 → 立即写入 translation 表（translation_source=manual，status=translated），记录 updated_at
2. 若此前已触发的 AI 翻译结果随后返回 → 系统检查该记录的 updated_at 是否晚于 AI 任务触发时间
3. updated_at > AI 触发时间 → 说明运营已手动更新，**丢弃 AI 结果**，不覆盖
4. updated_at ≤ AI 触发时间 → 正常写入 AI 结果

**前端无感知**：AI 翻译进行中状态由后端管理，前端不感知也不展示。冲突判定完全在后端通过 updated_at 时间戳静默处理。

## 五、功能模块

### 5.1 Translation 导航

**功能类型**：页面型

**功能描述**

以卡片网格形式展示所有可翻译资源，按业务域分组，运营可快速定位到具体资源进行翻译管理。同一页面下的多个资源卡片合并为一张聚合卡呈现。

**页面元素**

| 元素 | 说明 |
|------|------|
| 域分组标签（Tab） | 由 translation_domain 域元数据驱动（商品域 / 前端页面 / 通知模板），后端元数据决定 Tab，不再前端硬编码 |
| 语言选择器 | 选择当前查看的目标语言 |
| 搜索框 | 按资源名称搜索 |
| 资源卡片网格 | 聚合卡 + 独立卡混排，每卡显示：卡名、翻译进度（已翻译/总字段数）、待更新数、对接状态 |

**页面聚合（聚合卡）**

| 元素 | 说明 |
|------|------|
| 聚合卡 | 同一 `group_code` 的成员卡片，在导航页合并为**一张聚合卡**（卡名 = group_name，如"商详页"），不再各自出卡 |
| 聚合进度 | 聚合卡进度 = 各成员卡进度合计 |
| 聚合对接状态 | 由成员卡的 integration_status 汇总（有 placeholder / pending 成员时整体标注对应状态） |
| 独立卡 | `group_code` 为空的资源仍作**独立卡**展示（向后兼容，v3.1 既有全部卡片行为不变） |

> **数据层 vs 展示层**：数据层仍是 N 个独立 resource_type（各自建卡、各自注册字段、各自单层字段模型）；聚合只发生在导航展示层——把同 group_code 的卡片合并为一张聚合卡，不破坏单层字段模型。聚合是可选的组织层，不强制。

**卡片对接状态**

每个资源类型的卡片有三种对接状态，由 translation_resource.integration_status 决定（枚举定义见 §2.3）：

- **已对接（connected）**：实线卡片，可点击进入翻译详情页，显示翻译进度
- **待对接（pending）**：实线卡片（灰色），不可点击，完成对接后切换为已对接
- **占位（placeholder）**：虚线卡片，不可点击，无翻译进度，业务模块完成对接后自动切换为实线

**资源类型示例**

| 域 | resource_type | 显示名称 | 说明 |
|----|--------------|---------|------|
| 商品域 | listing / product / spu / sku / category / brand / series / attribute / attribute_option / enum | 渠道商品 / 实物商品 / 标品SPU / 标品SKU / 类目 / 品牌 / 系列 / 属性 / 属性选项 / 成色等级 | entity_field，各自独立卡 |
| 前端页面 | page-pdp（商详页） | 商详页聚合卡 | 聚合 group_code = pdp 的成员：页面文案 + 鉴定认证（pdp_template）+ 成色等级 + 成色展示名 + 属性展示名 |
| 前端页面 | page-home / page-cart / page-checkout / legal-tos / legal-privacy 等 | 首页 / 购物车 / 结账页 / 服务条款 / 隐私政策 等 | static_content 或占位 |
| 通知模板 | notif-email / notif-message | 邮件模板 / 站内消息 | 占位 |

> 具体卡片清单、聚合归属与对接状态以 translation_resource / resource_group 元数据为准（本期由 config 落地）。

> **前端页面包含两类多语言内容**：
> - **静态文案**（key_type = static_content，storage_mode = language_pack）：按钮文字、提示语、表单标签等固定 UI 文本，语言包落地，运营可在翻译详情页查看/修改（见 §2.2）
> - **业务动态内容**（key_type = entity_field，storage_mode = translation_table）：协议正文、Banner、运营活动文案等，需各自业务模块单独对接翻译服务（见 §3.2）

**操作流程**

1. 运营进入 Translation 页，默认显示"商品域"Tab
2. 选择目标语言（如 fr 法语）
3. 卡片显示每个资源（含聚合卡）在该语言下的翻译进度
4. 点击某资源卡片 → 进入翻译详情页（聚合卡进入后可在成员间切换，见 §5.2）

**页面状态变体**

| 状态 | 表现 |
|------|------|
| 默认态 | 按域分组展示卡片（聚合卡 + 独立卡），显示翻译进度 |
| 空状态（某域无注册字段） | 该 Tab 内显示提示"暂无已注册的可翻译资源" |
| 加载态 | 卡片区域显示骨架屏 |

**交互说明**
- 卡片进度使用进度条 + 数字（如 12/15）
- 有"待更新"内容的卡片显示橙色角标
- 域分组 Tab 后显示该域的资源数量
- 视觉细节（颜色、间距、标签样式等）以后台原型 v13 为准

**UI 关联**
- PC 端：`looply-多语言管理后台原型-v13-antd.html` → Translation 导航页

### 5.2 翻译详情页（Master-Detail）

**功能类型**：页面型

**功能描述**

左侧展示某资源类型下的所有资源实例列表（Master），右侧展示选中资源的逐字段翻译对照（Detail），支持源文本编辑、译文编辑和图片翻译。从聚合卡进入时，页面顶部提供子导航在各成员资源类型间切换。

**聚合卡子导航**

从聚合卡进入翻译详情页时：

- 页面顶部用**子导航（分组切换）**在各成员 resource_type 间切换（如商详页聚合卡下的：页面文案 / 鉴定认证 / 成色等级 / 成色展示名 / 属性展示名）
- 每个成员内部仍是标准的 Master（实例）- Detail（平铺字段）结构
- 子导航同时标注该成员的 resource_type、配置粒度、以及 **storage_mode 标注（翻译中心 / 语言包）**
- 从独立卡进入时无子导航，直接展示该资源的 Master-Detail

> **"页面文案"分组**：聚合卡下 storage_mode = language_pack 的"页面文案"成员，承载该页面的静态文案后台查看/修改；保存后同步回语言包（见 §2.2）。

**页面布局**

| 区域 | 内容 |
|------|------|
| 顶部子导航 | （聚合卡进入时）成员切换 + 各成员 storage_mode 标注 |
| 左侧面板（Master） | 资源实例列表，显示：资源名称、resource_id、翻译进度条 |
| 右侧面板（Detail） | 选中资源的逐字段翻译，每字段一行：源文本（可编辑）+ 译文输入框 + 操作按钮 |

**左侧面板元素**

| 元素 | 说明 |
|------|------|
| 搜索框 | 按资源名称/ID 搜索 |
| 状态筛选 | 全部 / 已翻译 / 待更新 / 未翻译 |
| 资源列表 | 每行显示：资源名称、翻译进度（如 3/5）、状态色标 |

**右侧面板元素**

| 元素 | 说明 |
|------|------|
| 资源信息栏 | 资源名称、resource_type、resource_id、storage_mode 标注 |
| 一键AI翻译按钮 | 对所有未翻译 + 待更新字段执行 AI 翻译 |
| 字段翻译行 | 每个注册字段一行 |

**字段翻译行结构（文本字段）**

| 元素 | 说明 |
|------|------|
| 字段标签 | field_label（如"商品标题"） |
| 源文本 | TextArea 可编辑，显示源语言内容 |
| 译文输入框 | TextArea，可编辑 |
| AI翻译按钮 | 对该字段执行 AI 翻译 |
| 状态标签 | 已翻译（绿）/ 待更新（橙）/ 未翻译（灰） |

**字段翻译行结构（图片字段）**

| 元素 | 说明 |
|------|------|
| 字段标签 | field_label（如"首页 Banner"） |
| 源图片预览 | 显示源语言图片缩略图，可点击"替换"重新上传 |
| 译图预览 | 显示目标语言图片缩略图（无则显示占位） |
| 上传按钮 | 上传目标语言图片，获取 CDN URL 写入 translated_value |
| 状态标签 | 同文本字段 |

**字段翻译行结构（富文本字段）**

当 field_type = rich_text 时，翻译行使用富文本编辑器代替普通 TextArea：

| 元素 | 说明 |
|------|------|
| 字段标签 | field_label + "富文本"标签 |
| 源文本编辑器 | 富文本编辑器，带工具栏（加粗/斜体/下划线/标题/列表），渲染 HTML 格式内容 |
| 译文编辑器 | 同源文本编辑器，支持格式化编辑。无译文时显示占位提示 |
| AI翻译按钮 | 同文本字段，AI 翻译保留 HTML 格式标签 |
| 状态标签 | 同文本字段 |

典型使用场景：商品描述（product.description）、服务条款正文（legal-tos.content）、隐私政策正文（legal-privacy.content）等包含格式化内容的长文本字段。

**页面状态变体**

| 状态 | 表现 |
|------|------|
| 默认态 | 左侧显示资源列表，右侧显示选中资源的字段翻译 |
| 左侧空状态（该资源类型无实例） | 左侧列表显示"暂无资源数据"，右侧为空 |
| 右侧空状态（选中资源无注册字段） | 右侧显示"该资源暂无已注册的可翻译字段" |
| AI 翻译进行中 | 对应字段的 AI 翻译按钮显示加载动画，译文输入框置灰不可编辑 |

**源文本编辑规则**

所有字段（不区分 key_type）的源文本区域均为可编辑状态：
- 文本字段：源文本显示为 TextArea，运营可直接修改
- 图片字段：源图片区域有"替换"按钮，可重新上传
- 保存时（storage_mode=translation_table）：更新 translation 表源语言记录的 translated_value，重新计算 source_hash，自动为所有目标语言标记 outdated 并触发重新翻译
- 保存时（storage_mode=language_pack）：更新语言包内容并同步回语言包（同步机制由技术方案定）

**操作流程**

手动编辑译文：
1. 运营在译文输入框中输入/修改内容
2. 点击保存按钮
3. 系统写入 translation 表：translated_value = 输入内容，translation_source = manual，status = translated（language_pack 卡片则同步回语言包）

编辑源文本：
1. 运营在源文本 TextArea 中修改内容（或替换源图片）
2. 点击保存按钮
3. 系统更新源语言记录的 translated_value + source_hash
4. 系统自动将所有目标语言记录标记为 outdated
5. 系统触发自动重新翻译

单字段 AI 翻译：
1. 运营点击某字段的"AI翻译"按钮
2. 系统调用 AI 翻译服务，传入源文本 + 术语表约束
3. 翻译结果填入译文输入框
4. 系统写入 translation 表：translation_source = ai，status = translated

一键 AI 翻译：
1. 运营点击"一键AI翻译"按钮
2. 系统对所有 status 为"未翻译"或"待更新"的字段批量调用 AI 翻译
3. 结果逐字段写入 translation 表

上传翻译图片：
1. 运营点击图片字段的"上传"按钮
2. 选择本地图片文件
3. 系统上传至 CDN，获取 URL
4. 写入 translation 表：translated_value = CDN URL，translation_source = manual，status = translated

**异常处理**

| 异常场景 | 处理方式 |
|---------|---------|
| AI 翻译服务不可用 | 提示"AI翻译服务暂时不可用，请手动编辑" |
| 保存失败 | 提示"保存失败，请重试"，保留输入内容 |
| 图片上传失败 | 提示"上传失败"，保留原图 |
| 语言包同步失败 | 提示"同步失败，请重试"，保留后台编辑内容 |

**字段状态变更规则（后台机制，供理解）**

| 操作 | 状态变化 | 对已有翻译记录的影响 | 对外查询的影响 |
|------|---------|-------------------|--------------|
| 停用字段 | active → inactive | 翻译记录保留不删除，不再触发新翻译 | 已有翻译内容仍可正常查询返回 |
| 重新激活 | inactive → active | 系统回扫该字段已有资源，补齐缺失的目标语言翻译 | 恢复正常 |
| 业务模块新增字段写入 | 字段未注册 | 写入被拒绝 | - |

**设计考量**：停用不删除翻译数据，避免前端页面因字段配置变更而出现内容丢失。业务侧如需彻底清除，通过资源删除接口处理（见 §3.5）。

## 六、术语管理

### 6.1 术语在翻译中的应用

AI 翻译时，系统自动将术语表规则注入翻译请求：

1. 查询 glossary_concept 表中 status=active 的所有术语
2. 按 rule_type 组织约束指令：
   - do_not_translate → 告知 AI 保留原文
   - mandatory → 告知 AI 必须使用指定译法
3. 将约束指令附加到翻译提示词中

### 6.2 术语覆盖率

术语的翻译覆盖率 = 该概念已有 active 译法的目标语言数 / 系统已开通目标语言总数

- 禁译词：显示"自动锁定"（无需人工翻译）
- 强制术语：显示覆盖率（如 3/5），提醒运营补齐缺失语言

### 6.3 术语状态管理

| 操作 | 效果 |
|------|------|
| 删除术语 | 等同于废弃：glossary_concept.status = deprecated，AI 翻译不再应用该规则。数据保留，可恢复 |
| 废弃单条译法 | glossary_translation.status = deprecated，该语言不再约束 |
| 恢复术语 | status 改回 active，规则重新生效 |

**删除 = 废弃的快捷方式**：列表页"删除"按钮的底层行为是将 status 设为 deprecated（非物理删除），运营可在后续恢复。避免误删导致术语规则丢失。

## 七、系统边界

### 7.1 系统定位

多语言模块是 looply 的多语言基础设施层，定位为"所有本地化内容的唯一存储源和翻译管理中心"。

### 7.2 边界判断原则

- 归本模块：与多语言内容的存储、编辑、翻译、查询直接相关的能力
- 不归本模块：语言本身的管理、业务结构化数据的管理、前端渲染逻辑

### 7.3 归属判定

| 能力项 | 归属 | 说明 |
|--------|------|------|
| 所有本地化内容存储（含源语言） | ✅ 多语言模块 | 核心职责，单一数据源 |
| 翻译资源建卡、页面聚合、域元数据 | ✅ 多语言模块 | 翻译中心组织结构（本期由 config 落地） |
| 源文本编辑 | ✅ 多语言模块 | 运营后台编辑入口 |
| AI 翻译执行 | ✅ 多语言模块 | 调用 AI 服务翻译文本 |
| 翻译过期检测与重译触发 | ✅ 多语言模块 | 通过 source_hash 对比 |
| 术语表管理 | ✅ 多语言模块 | 翻译质量保障 |
| 可翻译字段注册 | ✅ 多语言模块 | 注册表模式核心 |
| 对外内容查询接口 | ✅ 多语言模块 | 对外提供内容服务 |
| 语言列表管理 | ❌ Market 模块 | 多语言模块只引用 |
| 国家/地区管理 | ❌ Market 模块 | - |
| 商品结构化数据管理 | ❌ 商品模块 | 多语言模块不感知业务实体的结构化字段 |
| 商品后台源文本录入 UI | ❌ 商品模块 | 商品后台负责录入界面，底层调用翻译服务 API 写入 |
| 前端多语言渲染 | ❌ 前端 | 多语言模块只提供数据 |
| 语言包同步机制 | ❌ 技术方案 | 多语言模块声明"保存后同步语言包"诉求，具体机制由技术方案定 |
| CDN 图片存储 | ❌ 基础设施 | 多语言模块只存 CDN URL |

### 7.4 对外接口

| 接口方向 | 对接方 | 交互方式 |
|---------|--------|---------|
| 入（写入） | 各业务模块 | 业务模块先建卡再注册字段，通过翻译服务 API 写入源语言记录（如商品后台录入标题时调用） |
| 出（查询） | 前端 / 各业务模块 | 按资源类型+语言查询翻译内容 |
| 引用 | Market 模块 | 读取 language 表获取已开通语言列表 |

## 八、依赖与风险

### 8.1 上下游系统依赖

| 依赖方 | 依赖内容 | 关键要求 |
|--------|---------|---------|
| Market 模块 | language 表（已开通语言列表） | 多语言模块启动前 Market 模块须已上线，至少有一个 active 语言记录 |
| 各业务模块（商品、协议、Banner 等） | 先建卡（translation_resource）+ 注册可翻译字段（translatable_field_config）+ 写入源语言记录 | 业务模块需按 §3 集成规范完成对接，建卡与字段注册是上线前置条件；未建卡则源文写入被拒 |
| 建卡 / 聚合 / 域元数据落地（migration / config） | translation_resource / resource_group / translation_domain 的数据落地 | 本期无运营自助界面，靠开发在联调阶段通过 migration / config 落地；建卡能力未上线则业务模块无法建卡、无法注册字段 |
| CDN / 对象存储 | 图片资产上传和托管 | 需支持多地域访问，返回可直接引用的 URL |
| 前端语言包同步机制 | storage_mode = language_pack 静态文案的后台保存回写 | 需提供后台保存后同步回语言包的能力，具体机制由技术方案定 |

### 8.2 外部服务依赖

| 服务 | 用途 | 关键要求 | 风险 |
|------|------|---------|------|
| AI 翻译服务 | 自动翻译文本内容 | 由技术团队评估确定 | 服务不可用时翻译功能降级为纯人工，已有内容不受影响 |

**本期处理**：AI 翻译模型和提示词模板写死代码（见 §1.2），服务商选型由技术团队决定。

### 8.3 风险项

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| AI 翻译服务不可用 | 无法自动翻译，运营需全量手动处理 | §3.7 容错设计已定义降级策略；AI 不可用不影响已有翻译内容的读取 |
| 建卡 / 域元数据能力（migration + config）未上线 | 业务模块无法建卡、无法注册字段 | 列为业务接入硬前置，先于业务模块对接落地 |
| 聚合成员归属 / 排序靠 config，配置错漏 | 聚合卡成员缺失或顺序乱 | 上线前核对各 group 成员清单 + sort_order |
| 静态文案语言包同步机制未定 | 后台改了不同步 / 延迟 | 同步机制由技术方案定，产品声明"保存后同步语言包"诉求 |
| 向后兼容回归 | v3.1 既有卡片行为改变 | 未归组资源保持独立卡，聚合为可选组织层；上线前回归验证既有卡片行为不变 |
| 业务模块对接进度延迟 | Translation 导航页卡片长期处于"待对接/占位"状态 | 翻译模块可独立部署运行，不依赖业务模块全部对接完成 |
| 术语表不完整 | AI 翻译结果中品牌名/专业术语不一致 | 上线前梳理核心术语清单，优先录入高频术语 |
