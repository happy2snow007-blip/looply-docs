## 一、概述

### 1.1 背景与目标

Looply 是面向美国市场的跨境二手奢侈品电商平台。地址库管理是平台的**轻基础服务**，核心职责：

- 为美国用户提供流畅的地址填写体验（Google Autocomplete）
- 存储结构化地址数据，供订单和物流消费
- 基础格式校验，降低无效地址率

地址模块在业务链路中的角色：
- 不是核心竞争力，但是下单闭环的必要环节
- 地址错误直接导致退件（行业退件率 5-8%）
- 复杂地址表单导致弃单（行业弃单率 15-25%）

**设计原则**：

| 原则 | 说明 |
|------|------|
| 先跑通再优化 | MVP 只做美国，验证闭环后再扩展 |
| 依赖成熟服务 | 重度依赖 Google Places，不自建 |
| 最小字段集 | 只收集下单必要字段，不过度收集 |
| 预留钩子不预建系统 | 存 place_id、verified 等为后续预留，但不提前建去重/风控系统 |
| 国家数据统一管理 | 国家可用性引用 market 模块，地址库不独立维护国家列表 |

### 1.2 不做什么

| 明确不做 | 原因 |
|----------|------|
| ES 搜索 | PostgreSQL 足够，用户地址簿不超过 10 条 |
| 地址相似度检测 | 后期优化项，MVP 用户量小 |
| Address Validation API | 成本高、复杂、ROI 不确定（verified 字段已预留） |
| 后台校验规则引擎（运营配置 UI） | MVP 不做运营配置界面；校验规则由初始化脚本预置到 address_field_validation_rules 表，后端读表校验，美国地址格式固定 |
| GDPR 导出 / 审计日志平台 | 数据量小、美国优先、CCPA 只需支持删除 |
| 风控联动 | 还没到风控阶段 |
| 启用非美国国家配置 | 数据模型已支持多国，但 MVP 只启用美国 |
| 地址数据多语言存储 | 美国地址不需要多语言存储（前端 i18n 界面多语言 MVP 会做） |
| 地址标准化建议 | V1.1 再做 |
| 后台用户地址列表 | 地址模块后台定位为配置中心，不管理用户数据 |

### 1.3 用户角色

| 角色 | MVP 场景 |
|------|----------|
| C端买家 | 填写收货地址、管理地址簿、设置默认地址 |
| 物流系统 | 消费地址数据生成面单 |
| 运营人员 | 通过后台配置国家地址字段规则、管理行政区划数据、配置配送限制、维护邮编数据 |

### 1.4 核心场景

1. **地址填写**：用户在下单流程中填写收货地址，通过 Autocomplete 快速补全
2. **地址管理**：用户在个人中心管理地址簿，增删改查、设置默认地址
3. **下单快照**：订单创建时冻结地址数据，后续修改不影响已有订单
4. **后台配置**：运营配置美国地址字段的展示名称、必填规则、显示顺序
5. **区划维护**：运营通过批量导入维护美国州级行政区划数据
6. **配送限制配置**：运营配置不可配送地址规则（PO Box、军事地址、自定义限制区域）
7. **邮编数据维护**：运营通过批量导入维护邮编→城市/州映射数据

### 1.5 全局页面流转

**C端**：

```
行政区划管理 ──「启用/停用」──→ 切换状态

配送限制管理 ──「编辑」──→ 配送限制编辑页（基本信息 + 识别规则配置 + 操作记录）

```

### 1.6 术语说明

| 术语 | 说明 |
|------|------|
| 超集字段 | 数据库包含所有国家可能用到的字段，通过国家配置控制展示 |
| 前端展示字段 | field_config（数组，含 enabled/level/order）+ field_i18n_keys 的统一配置 |
| place_id | Google Places 返回的地点唯一标识，预留用于去重和标准化 |
| Address Snapshot | 订单创建时冻结的地址副本，由订单模块管理 |
| name_format | 姓名拼接顺序配置（first_last / last_first） |
| market 模块 | 平台国家/市场管理模块，地址库引用其国家启用状态 |

### 1.7 多语言 / 多国家策略

| 维度 | MVP 策略 | 后续扩展方向 |
|------|----------|-------------|
| 界面语言 | 前端 i18n 支持 en-US 和 es-US | 随市场扩展增加语种 |
| 地址数据存储 | 仅存英文原文，不做多语言存储 | V2 扩展欧洲/中东时按需增加本地语言字段 |
| 国家支持 | 数据模型支持多国，MVP 只启用美国 | V2 启用英国、加拿大、日本等 |
| 字段差异 | 通过 country_address_config 控制各国字段展示 | 新增国家时配置对应字段规则即可 |
| 校验规则 | address_field_validation_rules 按国家存储正则 | 新增国家时录入对应校验规则 |
| 姓名顺序 | 美国为 first_last | 日本等亚洲国家为 last_first |
| 电话格式 | 美国固定 +1 前缀 | 各国按 country_code 动态展示区号 |

## 二、需求详细描述

### 2.1 C端地址模块

#### 模块概述

为美国用户提供完整的地址填写和管理能力，集成 Google Places Autocomplete 提升填写效率，支持 shipping 和 billing 两种地址类型。

#### 2.1.1 地址表单（页面型）

**功能描述**：用户填写或编辑收货/账单地址的核心页面，集成 Google Places 自动补全能力。

**前置条件**：
- 用户已登录
- 国家地址配置已启用（country_address_config.enabled = true）
- Google Places API 可用（不可用时降级为手动输入）

**页面入口**：
- 地址列表页点击「新增地址」
- 下单流程中点击「新增收货地址」
- 地址列表页点击「编辑」（回填模式）

**页面布局**（美国，PC 端）：

```
┌─────────────────────────────────────────────┐
│  First Name                                  │
│  [____________________________________]      │
│                                              │
│  Last Name                                   │
│  [____________________________________]      │
│                                              │
│  Phone Number                                │
│  [+1] [____________________________________] │
│                                              │
│  Address Line 1 (Street address)             │
│  [____________________________________] ← Autocomplete
│                                              │
│  Address Line 2 (Apt, Suite, Unit, etc.)     │
│  [____________________________________]      │
│                                              │
│  City              State ▼      ZIP Code     │
│  [____________]    [__]         [_________]  │
│                                              │
│  ☐ Set as default address                    │
│                                              │
│  [Cancel]                    [Save Address]  │
└─────────────────────────────────────────────┘
```

**APP 端差异**：
- 单列布局，City / State / ZIP Code 各占一行
- 键盘类型适配：Phone 弹数字键盘，ZIP Code 弹数字键盘
- Autocomplete 候选列表以底部半屏弹窗展示

**页面元素**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| first_name | text | 是 | 收件人名，1-50 字符 |
| last_name | text | 是 | 收件人姓，1-50 字符 |
| phone | tel | 是 | 美国手机号，10 位数字，前缀 +1 固定 |
| address_line1 | text | 是 | 街道地址，1-100 字符，触发 Autocomplete |
| address_line2 | text | 否 | 公寓/套房号，0-100 字符 |
| city | text | 是 | 城市，1-50 字符 |
| state | select | 是 | 美国 50 州 + DC 下拉选择 |
| postal_code | text | 是 | ZIP Code，5 位或 5+4 位格式 |
| is_default | checkbox | 否 | 是否设为默认地址 |

**页面状态变体**：

| 状态 | 说明 |
|------|------|
| 默认态（新增） | 所有字段为空，+1 前缀预填 |
| 默认态（编辑） | 回填已有数据，address_line1 不自动触发 Autocomplete |
| 加载态 | Autocomplete 候选列表加载中，显示 loading 指示器 |
| 错误态 | 校验失败字段标红，下方显示错误提示文案 |
| 提交中 | Save Address 按钮置灰 + loading，防止重复提交 |
| 降级态 | Google API 不可用时，隐藏 Autocomplete 提示，纯手动输入 |

**操作流程**：

主流程：
1. 用户进入地址表单页
2. 填写 First Name、Last Name、Phone
3. 在 Address Line 1 输入 3+ 字符，触发 Autocomplete
4. 从候选列表选择地址，系统自动填充 City、State、ZIP Code
5. 用户补充 Address Line 2（如有）
6. 勾选是否设为默认地址
7. 点击 Save Address
8. 系统校验通过，保存成功，返回地址列表

分支流程：
- Autocomplete 无匹配结果 → 用户手动填写所有字段
- 用户选择 Autocomplete 结果后修改了自动填充的字段 → 允许修改，以用户最终输入为准
- 编辑模式下用户清空 address_line1 重新输入 → 重新触发 Autocomplete

**校验规则**：

| 字段 | 规则 | 校验时机 | 错误提示 |
|------|------|----------|----------|
| first_name | 1-50 字符，仅允许英文字母、扩展拉丁字符、空格、连字符、撇号 | 失焦 | First name contains invalid characters |
| last_name | 同 first_name | 失焦 | Last name contains invalid characters |
| phone | 美国手机号格式，区号不能以 0 或 1 开头 | 失焦 | Invalid US phone format |
| address_line1 | 1-100 字符，允许字母、数字、常用地址标点 | 提交 | Address contains invalid characters |
| address_line2 | 0-100 字符，允许字母、数字、常用地址标点 | 提交 | Address contains invalid characters |
| city | 1-50 字符，仅允许字母、空格、连字符、撇号 | 提交 | City name contains invalid characters |
| state | 必须为有效的美国州代码（2 位大写字母） | 提交 | Invalid state code |
| postal_code | 5 位数字或 5+4 格式（如 94102 或 94102-1234） | 失焦 | Invalid ZIP Code format |
| state ↔ postal_code（交叉硬校验） | 所填 ZIP 必须落在所选 State 内，数据源为邮编映射表（postal_code_mapping）；**Autocomplete 选中填充的地址豁免此校验**，仅纯手动输入（未走 Autocomplete 或降级态）时触发 | 提交 | This ZIP Code does not match the selected state |

> State↔ZIP 硬校验说明：仅对用户手动输入的地址生效。用户从 Google Autocomplete 候选中选择的地址视为可信，不做此交叉校验；若用户选择后又手动修改了 State 或 ZIP，则按手动输入处理，重新触发校验。邮编映射表导入期间（预计 3-5 秒）降级为不校验、允许通过。

**交互说明**：
- 字段顺序和展示名称由后台 country_address_config 配置驱动
- State 字段为下拉选择，数据来源于行政区划表
- 表单提交时前后端双重校验（前端即时反馈，后端安全兜底）
- 编辑模式下回填已有数据，address_line1 不再触发 Autocomplete（除非用户清空重新输入）
- 每用户最多 20 条地址，达到上限时新增入口置灰并提示

**异常处理**：

| 异常场景 | 处理方式 |
|----------|----------|
| 网络异常 | 提交失败时显示 toast "Network error, please try again"，不清空表单 |
| 校验失败 | 对应字段标红 + 错误提示，焦点定位到第一个错误字段 |
| Google API 不可用 | 静默降级为手动输入，不阻断流程 |
| 地址数量达上限 | 新增入口置灰，提示 "You can save up to 20 addresses" |
| 并发冲突（编辑时地址已被删除） | 提交时返回 404，提示 "This address no longer exists" 并返回列表 |
| 服务端错误 | 显示通用错误提示 "Something went wrong, please try again later" |

**UI 关联**：
- PC 端：个人中心-交互稿-v1.pen（Page 4~11）
- APP 端：移动端-交互稿-v1.pen

#### 2.1.3 地址 CRUD（机制型）

**功能描述**：地址数据的增删改查底层机制，定义业务规则和数据处理逻辑。

**触发条件**：
- 新增：用户在地址表单页点击 Save Address
- 编辑：用户修改已有地址后点击 Save Address
- 删除：用户在地址列表点击 Delete 并确认
- 设为默认：用户点击 Set as Default

**处理流程**：

| 操作 | 处理方式 | 业务规则 |
|------|----------|----------|
| 新增 | 校验通过后写入数据库，自动拼接 recipient_name | 每用户上限 20 条；首条地址自动设为默认 |
| 编辑 | 校验通过后更新数据库，重新拼接 recipient_name | 已被订单快照引用的地址可正常修改（快照独立） |
| 删除 | 软删除（标记 deleted_at） | 默认地址不可删除；已被快照引用不受影响 |
| 设为默认 | 同用户同类型旧默认取消，新地址设为默认 | shipping 和 billing 各一个默认 |

**规则说明**：
- recipient_name 拼接规则：根据 country_address_config.name_format 决定顺序
  - first_last → "John Smith"
  - last_first → "Smith John"
- 地址显示拼接规则：根据 country_address_config.display_format 决定各字段的组合展示格式
  - 美国格式：`{address_line1}, {address_line2}, {city}, {state} {postal_code}`
  - 示例：123 Main St, Apt 4B, New York, NY 10001
  - address_line2 为空时自动跳过：123 Main St, New York, NY 10001
  - MVP 阶段前端硬编码美国格式，数据库 display_format 字段已预留供后续扩展
- 软删除数据保留 90 天后物理清理（CCPA 要求可提前彻底删除）
- place_id 存储：如果地址来自 Autocomplete 选择，保存对应的 place_id

**异常处理**：

| 异常场景 | 处理方式 |
|----------|----------|
| 超过 20 条上限 | 拒绝新增，返回错误提示 |
| 删除默认地址 | 拒绝操作，提示需先更换默认地址 |
| 并发设置默认 | 数据库事务保证同类型只有一个默认 |

#### 2.1.4 基础格式校验（机制型）

**功能描述**：前后端双重校验机制，前端提供即时反馈优化体验，后端作为安全防线防止恶意数据注入。

**触发条件**：
- 前端校验：用户输入时（失焦或提交）
- 后端校验：表单提交到服务端时

**处理流程**：

1. 用户填写表单字段
2. 前端在失焦/提交时执行格式校验，不通过则标红提示
3. 前端校验通过后提交到后端
4. 后端读取 country_address_config.field_config 判断字段是否启用（enabled），未启用字段跳过校验
5. 启用字段根据 address_field_validation_rules 表加载校验规则，先判必填性（requirement_type=required 且为空 → 返回"XX is required"）
6. 非空字段再按 priority 执行格式/长度规则
7. 按 priority 顺序逐条执行格式/长度校验，命中首个失败即返回对应 error_message
8. 全部通过 → 保存数据

**校验架构说明**：

字段展示与校验职责分离：
- **是否展示**（enabled）：由 `country_address_config.field_config` 管理，控制字段在前端表单中是否出现
- **必填性**（required/optional）：由 `address_field_validation_rules.requirement_type` 管理
- **格式/长度校验**：同样由 `address_field_validation_rules` 管理，rule_type 枚举为 pattern（正则格式）、length（长度范围）、custom（自定义正则），按 priority 顺序执行

**规则说明**：

为什么后端必须再次校验：
- 前端可以被绕过（浏览器开发者工具、直接调用 API、多渠道输入）
- 后端是数据安全的最后防线，防止恶意字符注入

后端校验执行顺序：
1. 读取 `country_address_config.field_config`，跳过 enabled=false 的字段（不展示则不校验）
2. 对启用字段读取 `address_field_validation_rules`，按 priority 顺序执行
3. requirement_type=required 的字段判空，为空则返回 "{field} is required"
4. 非空字段按 `address_field_validation_rules` 的 priority 顺序执行格式/长度规则
5. 命中首个失败规则即返回对应 error_message，不继续后续规则

字段校验规则（美国）：

| 字段 | 必填 | 长度 | 允许字符 | 前端时机 | 后端时机 |
|------|------|------|----------|----------|----------|
| first_name | 是 | 1-50 | 英文字母、扩展拉丁字符、空格、连字符、撇号 | 失焦 | 提交 |
| last_name | 是 | 1-50 | 同 first_name | 失焦 | 提交 |
| phone | 是 | 10-20 | 数字、+、空格、括号、连字符 | 失焦 | 提交 |
| address_line1 | 是 | 1-100 | 字母、数字、扩展拉丁字符、常用地址标点 | 提交 | 提交 |
| address_line2 | 否 | 0-100 | 同 address_line1 | 提交 | 提交 |
| city | 是 | 1-50 | 英文字母、扩展拉丁字符、空格、连字符、撇号 | 提交 | 提交 |
| state_province | 是 | 2 | 大写英文字母 | 提交 | 提交 |
| postal_code | 是 | 5-10 | 数字、连字符 | 失焦 | 提交 |

> 单字段格式校验全部通过后，追加一步 **State↔ZIP 交叉硬校验**：以 postal_code 反查邮编映射表（postal_code_mapping），确认其对应的 state_code 与用户所选 state_province 一致，不一致则返回 "This ZIP Code does not match the selected state"。该校验仅对手动输入地址生效，Autocomplete 选中填充的地址豁免；邮编映射表导入期间降级为不校验、允许通过。前后端均执行（前端失焦/提交时即时反馈，后端提交时兜底）。

安全性考虑：
- 字符集白名单限制，不允许 HTML 标签字符（防 XSS）
- 不允许 SQL 特殊字符组合（防注入）
- 不允许路径遍历模式（防目录穿越）

校验规则按国家动态配置，存储在 address_field_validation_rules 表中（必填性 requirement_type + 格式/长度规则），应用启动时加载到内存缓存，按国家代码索引。字段启用/层级/顺序配置存储在 country_address_config.field_config 中，同样缓存。

**异常处理**：

| 异常场景 | 处理方式 |
|----------|----------|
| 前端校验失败 | 字段标红 + 错误提示，阻止提交 |
| 后端校验失败 | 返回 400 + 错误字段列表，前端展示对应错误 |
| 校验规则缓存失效 | 从数据库重新加载，期间使用默认规则兜底 |

#### 2.1.5 Google Places Autocomplete（机制型）

**功能描述**：集成 Google Places API，在用户输入街道地址时提供自动补全候选列表，选择后自动填充结构化地址字段。

**触发条件**：
- 用户在 address_line1 输入框键入 3 个及以上字符
- 防抖 300ms 后触发

**处理流程**：

1. 用户在 address_line1 输入 3+ 字符
2. 防抖 300ms 后调用 Google Places Autocomplete API（限定美国地址）
3. 展示候选地址列表（最多 5 条）
4. 用户点击选择某条候选
5. 调用 Place Details API 获取结构化地址
6. 自动填充 address_line1、city、state、postal_code
7. address_line2 留空让用户补充 Apt/Suite
8. 用户确认/修改后保存

**规则说明**：

字段映射：

| Google 返回字段 | 映射到 | 说明 |
|----------------|--------|------|
| street_number + route | address_line1 | 拼接为完整街道地址 |
| subpremise | address_line2 | 如有则预填 |
| locality | city | 城市 |
| administrative_area_level_1 (short_name) | state | 州缩写 |
| postal_code | postal_code | 邮编 |

关键实现要点：
- Session Token：将多次 Autocomplete + 1 次 Details 合并为一个计费会话
- 国家限制：仅返回美国地址结果
- 防抖策略：300ms，减少无效请求

**异常处理**：

| 异常场景 | 处理方式 |
|----------|----------|
| Google API 不可用 | 静默降级为纯手动输入，不显示错误，不阻断下单 |
| API 限流 | 同上，降级为手动输入 |
| 返回结果为空 | 隐藏候选列表，用户手动填写 |
| 网络超时 | 3 秒超时后隐藏 loading，用户可继续手动输入 |

#### 2.1.6 Address Snapshot（机制型）

**功能描述**：订单创建时冻结地址数据为快照，确保后续地址修改不影响已有订单的物流信息。

**触发条件**：
- 订单创建时，订单模块调用地址库读取地址数据

**处理流程**：
1. 用户下单，选择收货地址
2. 订单模块调用地址库读取该地址的完整数据
3. 订单模块在自己的数据库中创建地址快照
4. 快照与订单绑定，后续地址修改/删除不影响快照
5. 物流系统读取快照数据生成面单

**规则说明**：
- 职责边界：地址库只提供数据读取能力，快照的创建和管理由订单模块负责
- 快照独立性：用户修改或删除原地址，不影响已有订单的快照数据
- 物流消费：物流系统读取快照数据，不读取实时地址

**异常处理**：

| 异常场景 | 处理方式 |
|----------|----------|
| 读取地址时地址已被删除 | 订单模块提示用户重新选择地址 |
| 地址库服务不可用 | 订单创建失败，提示用户稍后重试 |

#### 2.1.7 结算页配送限制校验（机制型）

**功能描述**：用户在结算页选择/确认收货地址后，系统即时校验该地址对购物车中所有商品的配送可达性。如果命中配送限制规则，阻止用户提交订单并给出明确提示。

**触发条件**：
- 用户在结算页选择或确认收货地址后
- 购物车中有商品

**处理流程**：
1. 用户在结算页选择/确认地址
2. 前端异步调用配送限制校验接口，传入地址数据 + 购物车商品列表（含 merchant_id）
3. 后端按每个商品的 merchant_id 查询对应商家已启用的配送限制规则
4. 逐条规则校验地址字段（address_line1/address_line2/city/state）
5. 返回校验结果：通过 / 不通过（附带受限商品列表和命中规则）

**校验逻辑**：
- 固定规则（PO Box / 军事地址）：按商家维度独立判断，商家启用了才校验
- 自定义规则：按商家维度匹配，关键词/正则/州多选逐条校验
- 同一商品命中多条规则时，只返回第一条命中的规则提示

**前端交互**：

场景 1 — 全部商品不支持配送：
- 地址卡片下方显示警告 banner："This address is not available for delivery."
- 提供「Change Address」按钮
- 提交订单按钮置灰不可点击

场景 2 — 部分商品不支持配送：
- 地址卡片下方显示概要 banner："X items can't be delivered to this address." + 可展开详情
- 展开后列出受限商品名称 + 命中原因（如"PO Box address not supported"）
- 提供「Change Address」和「Remove These Items」两个操作入口
- 商品列表中受限商品行标红 + 原因提示
- 提交订单按钮置灰不可点击

**规则说明**：
- 前端不硬编码 PO Box/军事地址正则，通过接口动态读取商家已启用的配送限制规则
- 地址保存时不做配送限制校验（仅做字段格式校验），因为保存时不知道要买哪个商家的商品
- 校验结果缓存：同一地址 + 同一购物车组合，5 分钟内不重复请求（地址或购物车变更时清除缓存）

**异常处理**：

| 异常场景 | 处理方式 |
|----------|----------|
| 校验接口超时（3s） | 降级放行，允许提交订单，后端下单时二次校验兜底 |
| 校验接口不可用 | 同上，降级放行 |
| 用户更换地址后 | 清除旧校验结果，重新触发校验 |
| 用户移除受限商品后 | 重新触发校验，如果剩余商品全部通过则恢复提交按钮 |

**UI 关联**：
- PC 端：结算页-交互稿-v1.pen（待补充配送限制校验页面）
- APP 端：移动端-交互稿-v1.pen（待补充）

1. **基本信息区**：规则名称、国家（默认 US）
2. **识别规则配置区**：匹配字段选择 + 匹配方式选择 + 匹配内容输入
3. **操作记录**（仅编辑页）：操作时间、操作人、操作类型、操作内容

**交互说明**：
- 固定规则不可编辑识别逻辑，仅可 Toggle 启用/禁用
- 自定义规则统一使用 i18n key `delivery_restriction.general`，买家端提示文案固定为"该地址不支持配送"
- 匹配字段选择"州"时，匹配方式自动切换为州多选控件，无需填写正则或关键词
- 配送限制默认全品类生效，无需品类维度配置
- 多商家隔离：自营平台也是一条独立 merchant 记录（merchant_id 永不为 NULL），与其他商家平级；每个商家（含自营平台运营）登录后，列表按当前登录主体的 merchant_id 做权限过滤，只能看到和管理自己的规则。本后台原型即为单一登录主体视角，故列表无需商家维度列/筛选

**异常处理**：

| 异常场景 | 处理方式 |
|----------|----------|
| 正则表达式语法错误 | 保存时校验，提示"正则表达式格式不正确，请检查" |
| 规则名称重复 | 提示"规则名称已存在" |
| 停用已启用规则 | 二次确认弹窗"停用后将立即停止拦截，确认停用？"，确认后规则状态变为"已停用" |
| 网络异常 | toast 提示"操作失败，请重试" |

**UI 关联**：
- PC 端：后台原型 v5 - 配送限制管理页

#### 2.2.5 国家邮编管理（页面型）

**功能描述**：管理邮编→城市/州的映射数据，**仅用于 C 端 State↔ZIP 硬校验的数据源**（校验所填 ZIP 是否落在所选 State 内）。数据通过批量导入维护，列表只读不支持单条编辑。

**前置条件**：
- 运营人员已登录后台
- 拥有地址配置管理权限

**页面入口**：后台侧边栏 → 地址配置 → 国家邮编管理

**页面布局**（PC 端）：
- KPI 统计卡片：邮编总数、州/地区数、城市数、覆盖国家
- 筛选工具栏：国家筛选 + 州筛选 + 搜索邮编/城市 + 查询按钮 + 导入邮编数据按钮
- 数据表格

**页面元素**：

| 列名 | 说明 |
|------|------|
| 国家 | 国家代码（如 US） |
| 州/省(L1) | 州代码和名称（如 NY - New York） |
| 城市(L2) | 城市名称 |
| 邮编 | 邮政编码 |

**页面状态变体**：

| 状态 | 说明 |
|------|------|
| 有数据态 | 正常展示表格 |
| 空态 | 无数据时显示空状态 + "导入邮编数据"引导 |
| 导入中 | 上传文件后显示导入进度 |
| 导入结果 | 成功/失败条数汇总 |

**操作流程**：

主流程（查看）：
1. 运营进入国家邮编管理页面
2. 查看 KPI 统计卡片了解数据概况
3. 通过筛选条件查看特定国家/州的邮编数据

主流程（导入）：
1. 点击「导入邮编数据」
2. 选择文件（CSV/Excel）
3. 系统解析文件，显示预览（条数、国家、覆盖州数）
4. 确认导入
5. 系统执行导入，显示结果（成功/失败/跳过条数）

**交互说明**：
- 数据为只读列表，不支持单条编辑（通过批量导入维护）
- 导入逻辑：按国家全量覆盖该国邮编数据，在数据库事务中执行（先删后插），保证原子性——要么全部成功，要么全部回滚
- 导入期间（预计 3-5 秒）如有前端请求邮编校验，降级为不校验（允许通过），不阻断用户操作
- 导入文件必须包含列：country_code、postal_code、state_code、city
- 分页展示，默认每页 20 条

**异常处理**：

| 异常场景 | 处理方式 |
|----------|----------|
| 文件格式错误 | 提示"请上传 CSV 或 Excel 格式文件" |
| 文件缺少必要列 | 提示"文件缺少必要列：{列名}，请检查后重新上传" |
| 邮编格式校验失败 | 显示错误行号和原因，允许修正后重新上传 |
| 导入部分失败 | 显示成功/失败条数明细，失败数据可下载 |

### 7.2 数据模型设计说明

详细数据模型参见实体关系图：`实体关系图/looply-地址库管理实体关系图-v2.3.svg`

核心设计思路：
- **超集字段设计**：数据库包含所有国家可能用到的字段（如 district、building_name），通过 country_address_config 控制各国展示哪些字段。避免后续扩展时改表结构
- **姓名拆分存储**：recipient_first_name + recipient_last_name 拆分存储，支持支付网关 AVS 校验和物流 API；recipient_name 冗余存储拼接结果
- **配置预留字段**：country_address_config 中 name_format、display_format 字段已预留，MVP 不在界面暴露，但美国初始化数据需写入（name_format=first_last，display_format=`{address_line1}, {address_line2}, {city}, {state} {postal_code}`）；字段顺序由 field_config 数组内 order 承载，不再单设 field_order
- **字段展示与校验分离**：country_address_config.field_config 管"展示哪些字段、怎么展示"（enabled 启用 / level 行政区划层级 / order 顺序）；address_field_validation_rules 管"填什么内容、怎么校验"（requirement_type 必填性 + pattern/length/custom 格式校验），按 priority 顺序执行
- **多规则校验模型**：同一字段可配置多条校验规则（如 postal_code 同时有 pattern 和 length 规则），按 priority 顺序执行，命中首个失败即返回对应 error_message
- **行政区划自引用**：administrative_division 通过 parent_id 实现树形层级（州→市→区），支持各国不同层级深度
- **配送限制多商家隔离**：自营平台也是一条独立 merchant 记录（merchant_id 永不为 NULL），与其他商家平级；每个商家的固定规则与自定义规则均挂在各自 merchant_id 下，校验时按商品所属 merchant_id 查询该商家全部已启用规则，不存在跨商家叠加
- **邮编映射**：postal_code_mapping 存储邮编→城市/州的映射关系，MVP 仅作为 C 端 State↔ZIP 硬校验的数据源（不做 ZIP→城市/州自动填充）
- **i18n key 命名规范**：地址字段国际化文案 key 统一采用 `address.field.{field_name}` 格式（如 `address.field.first_name`），存储于 country_address_config.field_i18n_keys，实际多语言文案由翻译中心维护；配送限制规则 key 由系统按规则类型自动写入（`delivery_restriction.po_box` / `delivery_restriction.military` / `delivery_restriction.general`），后台不暴露
- **phone 逻辑字段映射**：phone / alternate_phone 在 field_config 中作为单个逻辑字段配置（统一启用/顺序），前端渲染为「区号 + 号码」组合控件（区号按用户所在国家默认显示、可改）；存储层映射为 address 表的 phone_country + phone_number / alternate_phone_country + alternate_phone_number 两列
