## 一、模块概述

### 1.1 模块定位

地址库管理是 Looply 平台的基础服务模块，为前端用户地址填写提供结构化支持，包括：

- 多国地址字段适配与校验
- 地址自动填充（Autocomplete）
- 地址格式校验（邮编、电话、邮箱）
- 地址合理性建议（邮编推荐、城市-州匹配）
- 为后续物流模块提供标准化地址数据

### 1.2 业务背景

Looply 面向美国市场，后续扩展至欧洲（EU）、英国（UK）、日本（JP）。跨境电商场景下，地址准确性直接影响：

- 物流配送成功率（错误地址导致退件率 5-8%）
- 用户下单转化率（复杂地址表单导致弃单率 15-25%）
- 关税合规（海关申报需要标准化地址）
- 反欺诈风控（地址异常是欺诈信号之一）

### 1.3 目标用户

| 角色 | 场景 |
|------|------|
| C端买家 | 填写收货地址、管理地址簿 |
| C端卖家 | 填写退货地址、发货地址 |
| 运营后台 | 查看/编辑用户地址、配置校验规则 |
| 物流系统 | 消费标准化地址数据生成面单 |

## 二、国际地址字段设计

### 2.1 服务端统一数据模型

采用「超集字段 + 国家配置」模式，服务端存储所有可能字段，前端根据国家配置动态渲染。

```
address {
  id              UUID        主键
  user_id         UUID        关联用户
  label           String      地址标签（Home/Office/自定义）
  country_code    String(2)   ISO 3166-1 alpha-2 国家代码
  recipient_name  String      收件人姓名
  phone_country   String(5)   电话国家区号（+1, +44, +81）
  phone_number    String(20)  电话号码
  address_line1   String(200) 地址行1（街道/门牌）
  address_line2   String(200) 地址行2（公寓/套房/楼层）
  city            String(100) 城市
  state_province  String(100) 州/省/县
  postal_code     String(20)  邮政编码
  district        String(100) 区/町（日本等亚洲地址）
  building_name   String(100) 建筑名称（日本地址常用）
  is_default      Boolean     是否默认地址
  address_type    Enum        地址类型（shipping/billing/return）
  verified        Boolean     是否经过三方验证
  verified_at     Timestamp   验证时间
  latitude        Decimal     纬度（自动填充获取）
  longitude       Decimal     经度（自动填充获取）
  place_id        String      Google Place ID（用于去重和更新）
  raw_input       JSON        用户原始输入（用于审计）
  created_at      Timestamp
  updated_at      Timestamp
}
```

### 2.2 各国地址字段配置

| 字段 | 美国(US) | 英国(UK) | 欧盟(DE/FR) | 日本(JP) |
|------|----------|----------|-------------|----------|
| address_line1 | 必填 | 必填 | 必填 | 必填 |

## 三、地址自动填充（Autocomplete）

### 3.1 三方服务对比

| 维度 | Google Places API | Loqate (GBG) | SmartyStreets | HERE Autocomplete |
|------|-------------------|---------------|---------------|-------------------|
| 覆盖范围 | 全球 200+ 国家 | 全球 245 国家 | 美国为主，国际有限 | 全球 200+ 国家 |
| 准确度 | 极高（持续更新） | 高 | 美国极高 | 高 |
| 价格 | $2.83/1000次(Autocomplete) + $5/1000次(Details) | $0.04-0.08/次 | $0.01/次(美国) | $0.50/1000次 |
| 日文地址 | 支持 | 支持 | 不支持 | 支持 |
| 延迟 | 50-150ms | 100-200ms | 50-100ms(美国) | 100-200ms |
| 地址验证 | 有(Address Validation API) | 有(内置) | 有(核心功能) | 有限 |
| SDK/集成 | JS SDK + REST | JS Widget + REST | REST | JS SDK + REST |

### 3.2 推荐方案

**主方案：Google Maps Platform（Places API + Address Validation API）**

理由：
1. Looply 目标市场覆盖美国→欧洲→日本，Google 全球覆盖最完整
2. 用户对 Google 地址补全交互最熟悉，降低学习成本
3. Places API 返回结构化地址组件，可直接映射到服务端字段
4. Address Validation API 提供 USPS/Royal Mail 级别的地址验证
5. 与 Google Maps 生态打通，后续物流追踪可复用

**备选方案：Loqate**

适用场景：如果 Google API 在某些地区受限或成本超预算时切换。

### 3.3 自动填充交互流程

```
用户输入 → 防抖(300ms) → 调用 Places Autocomplete
                              ↓
                    返回候选列表(最多5条)
                              ↓
              用户选择候选项 → 调用 Place Details
                              ↓
                    解析 address_components
                              ↓
              自动填充各字段 → 用户可修改 → 提交
```

### 3.4 关键实现细节

- **防抖策略**：用户停止输入 300ms 后触发请求，减少 API 调用量
- **Session Token**：使用 Google Session Token 将多次 Autocomplete + 1次 Details 合并计费
- **国家限制**：根据用户选择的国家，限定 Autocomplete 搜索范围（`componentRestrictions`）
- **语言适配**：根据用户语言偏好设置 API 的 `language` 参数
- **降级策略**：API 不可用时，退化为纯手动输入模式，不阻断下单流程

## 四、地址格式校验

### 4.1 邮政编码校验

| 国家 | 格式 | 正则 | 示例 |
|------|------|------|------|
| US | 5位 或 5+4位 | `^\d{5}(-\d{4})?$` | 10001, 90210-1234 |
| UK | 复杂格式 | `^[A-Z]{1,2}\d[A-Z\d]?\s?\d[A-Z]{2}$` | SW1A 1AA, EC2R 8AH |
| DE | 5位数字 | `^\d{5}$` | 10115, 80331 |
| FR | 5位数字 | `^\d{5}$` | 75001, 69001 |
| JP | 3+4位 | `^\d{3}-?\d{4}$` | 100-0001, 5300001 |

### 4.2 电话号码校验

| 国家 | 区号 | 格式规则 | 示例 |
|------|------|----------|------|
| US/CA | +1 | 10位数字(NPA-NXX-XXXX) | +1 212-555-0123 |
| UK | +44 | 10-11位，首位去0 | +44 20 7946 0958 |
| DE | +49 | 10-11位 | +49 30 12345678 |
| FR | +33 | 9位，首位去0 | +33 1 23 45 67 89 |
| JP | +81 | 10-11位，首位去0 | +81 3-1234-5678 |

**校验策略**：
- 前端：实时格式校验 + 位数校验（输入时）
- 后端：libphonenumber 库做严格校验（提交时）
- 存储：统一存储为 E.164 格式（如 +12125550123）

### 4.3 邮箱校验

- 前端：RFC 5322 基础正则 + 常见域名拼写建议（如 gmial.com → gmail.com）
- 后端：格式校验 + MX 记录验证（异步）
- 不做邮箱验证发送（属于用户账户模块职责）

### 4.4 校验时机

| 时机 | 校验内容 | 反馈方式 |
|------|----------|----------|
| 输入中(onChange) | 格式提示（如邮编位数） | 输入框下方灰色提示 |
| 失焦(onBlur) | 完整格式校验 | 红色错误提示 |
| 提交前(onSubmit) | 全字段必填+格式+合理性 | 阻断提交+定位错误字段 |
| 后端(API) | 最终校验+地址验证 | 返回错误码 |

## 五、地址合理性建议

### 5.1 邮编-城市-州匹配

当用户填写邮编后，系统自动：
1. 根据邮编反查对应的城市和州（US）/ 城市（UK/DE/FR）/ 都道府県+市区町村（JP）
2. 如果用户已填城市/州与邮编不匹配，弹出建议提示
3. 如果邮编对应多个城市，展示下拉选择

**数据来源**：
- US：USPS ZIP Code 数据库（免费，月更新）
- UK：Royal Mail PAF（付费）或 ONS Postcode Directory（免费）
- JP：日本邮便局邮编数据（免费 CSV，月更新）
- 通用：Google Geocoding API 反查

### 5.2 地址标准化建议

| 场景 | 建议内容 | 示例 |
|------|----------|------|
| 缩写标准化 | 街道类型缩写 | "Street" → "St", "Avenue" → "Ave" |
| 方向标准化 | 方向缩写 | "North" → "N", "Southwest" → "SW" |
| 单元号格式 | 补充 Apt/Suite | "123 Main St 4B" → "123 Main St, Apt 4B" |
| 邮编补全 | ZIP+4 补全 | "10001" → "10001-7305" |

### 5.3 重复地址检测

- 用户新增地址时，与已有地址簿做相似度比对
- 相似度 > 85% 时提示"您已有类似地址，是否使用已有地址？"
- 比对算法：标准化后的字符串 Levenshtein 距离 + place_id 匹配

## 七、与物流模块的关系

### 7.1 地址库为物流模块提供的服务

| 服务 | 说明 |
|------|------|
| 标准化地址数据 | 提供已验证的结构化地址字段（address_line1/2, city, state, postal_code 等） |
| 地理坐标信息 | 提供经纬度（latitude/longitude）用于距离计算和地图展示 |
| Google Place ID | 提供 place_id 用于地址去重和第三方服务集成 |
| 收件人信息 | 提供收件人姓名、电话，用于面单打印和配送通知 |
| 地址变更通知 | 订单创建后地址修改，通知物流系统更新（通过事件机制） |

**职责边界说明**：
- 地址库负责：地址数据的存储、格式校验、标准化
- 物流模块负责：配送可行性评估（PO Box 检测、偏远地区判断、Zone 映射、运费计算）

### 7.2 接口设计预留

```
// 地址库提供给物流模块的接口
GET  /api/v1/addresses/{id}                   → 获取完整地址对象
GET  /api/v1/users/{user_id}/addresses        → 获取用户所有地址
POST /api/v1/addresses                        → 创建新地址
PUT  /api/v1/addresses/{id}                   → 更新地址
```

```
// 物流模块自己提供的接口（消费地址数据）
POST /api/v1/logistics/evaluate-deliverability
Body: { address_id, carrier, product_type }
Response: { 
  deliverable: true,
  is_po_box: false,
  is_military: false,
  is_remote_area: false,
  zone: "Zone 3",
  restrictions: [],
  estimated_days: 3-5
}
```

### 7.3 数据流向

```
用户填写地址 → 地址库（校验&标准化&存储）
                        ↓
                  返回 address_id
                        ↓
订单创建（引用 address_id） → 物流模块获取地址数据
                        ↓
              物流模块评估可达性（PO Box/Zone/运费）
                        ↓
              生成面单 → 调用物流商API（UPS/FedEx/DHL）
```

## 八、技术方案

### 8.1 架构设计

```
┌─────────────────────────────────────────────────┐
│                   前端层                          │
│  地址表单组件 ← 国家配置 ← Autocomplete SDK      │
└──────────────────────┬──────────────────────────┘
                       │ REST API
┌──────────────────────▼──────────────────────────┐
│                 地址服务(Address Service)          │
│  ┌──────────┐ ┌──────────┐ ┌──────────────────┐ │
│  │ 校验引擎  │ │ 标准化   │ │ 合理性建议引擎   │ │
│  └──────────┘ └──────────┘ └──────────────────┘ │
└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│              三方服务适配层(Adapter)               │
│  Google Places │ Address Validation │ 邮编数据库  │
└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│                   数据层                          │
│  PostgreSQL(地址数据) │ Redis(邮编缓存) │ ES(搜索) │
└─────────────────────────────────────────────────┘
```

### 8.2 性能要求

| 指标 | 目标 |
|------|------|
| Autocomplete 响应 | < 200ms（含网络） |
| 地址校验 | < 100ms |
| 地址提交 | < 300ms |
| 邮编反查 | < 50ms（缓存命中） |

### 8.3 缓存策略

- 邮编-城市映射：Redis 缓存，TTL 7天（数据月更新）
- Autocomplete 结果：不缓存（实时性要求高）
- 国家字段配置：本地缓存，应用启动时加载
- 地址验证结果：Redis 缓存，TTL 30天（地址不常变）

## 九、安全与合规

### 9.1 数据安全

- 地址数据属于 PII（个人可识别信息），需加密存储
- 传输层：全链路 HTTPS/TLS 1.3
- 存储层：敏感字段 AES-256 加密（phone_number, recipient_name）
- 访问控制：地址数据仅本人和授权客服可查看
- 日志脱敏：日志中地址信息做掩码处理

### 9.2 合规要求

| 法规 | 要求 | 应对 |
|------|------|------|
| CCPA（加州） | 用户可请求删除个人数据 | 支持地址数据彻底删除 |
| GDPR（欧盟） | 数据最小化、用户同意 | 仅收集必要字段，明确告知用途 |
| APPI（日本） | 个人信息保护 | 日本用户数据存储合规 |

### 9.3 与风控模块的协作

地址模块不负责欺诈检测和风险评估，但需要为风控模块提供数据支持：

**地址模块提供的数据：**
- 标准化的地址信息（供风控模块分析地址模式）
- 地理坐标（用于 IP 地理位置一致性校验）
- 地址修改历史（用于异常行为检测）
- 地址使用频率（多个账户使用同一地址的检测）

**风控模块的职责：**
- 地址黑名单管理（已知欺诈地址库）
- 地址与 IP 地理位置一致性校验
- 异常行为检测（短时间内添加大量不同地址）
- 地址-用户关联分析（多账户共用地址）
- 综合风险评分和决策（放行/人工审核/拒绝）

**接口协作：**
```
// 风控模块调用地址模块获取数据
GET /api/v1/addresses/{id} → 获取完整地址信息
GET /api/v1/users/{user_id}/addresses → 获取用户所有地址
GET /api/v1/addresses/{id}/usage-history → 获取地址使用历史
```
