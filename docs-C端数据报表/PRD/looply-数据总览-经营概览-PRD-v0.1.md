# Looply 数据总览 / 经营概览 PRD v0.1

**文档状态**：产品评审稿  
**版本日期**：2026-08-03  
**适用端**：Looply 内部数据报表（PC）  
**原型基线**：`outputs/looply-数据总览-售后影响评审版-antd-原型-v1.html`

## 一、概述【必写】

### 1.1 背景与目标

数据总览是管理层经营驾驶舱，用最少的全站指标回答三个问题：整体经营是否健康、变化发生在哪个环节、需要下钻到哪个业务模块。

V1 围绕“流量获取 → 浏览 / 找货 → 购买意向 → 交易转化”呈现整体规模、成交结果、年度订单目标、关键行为覆盖、趋势和售后影响。GA4、订单系统和 Shopify 是数据实现来源，不改变本报表的业务结构。

### 1.2 V1 边界

V1 包含：

- 全局筛选与上一等长周期对比；
- 7 个核心经营指标；
- 售后影响摘要；
- 年底 100 单 / 天目标及订单趋势；
- 关键行为覆盖；
- 访问访客与购买转化率趋势；
- 业务模块下钻入口。

以下能力由业务主表或下钻页面承接：

- 严格按事件顺序计算的用户漏斗；
- 独立 Checkout / 订单流程漏斗；
- 渠道规模、渠道质量和分渠道漏斗；
- 购买前行为路径构成；
- 售后订单、商品、原因和责任归属明细。

### 1.3 用户角色

| 角色 | 使用目标 | 核心关注 |
|---|---|---|
| 老板 / 管理层 | 快速判断经营健康度与目标差距 | 订单目标、成交结果、异常变化 |
| 产品负责人 | 判断变化发生在哪个业务环节 | 关键行为覆盖、转化率趋势、下钻方向 |
| 业务部门 | 作为每日经营同步和专项复盘背景 | 访问规模、购买效率、退款影响 |

### 1.4 核心场景

1. 每日查看所选周期结束日的 GA4 Purchase 数，判断与年底 100 单 / 天目标的差距。
2. 查看周期经营结果，判断访客规模、购买效率和成交金额是否发生变化。
3. 查看关键行为覆盖，判断问题更接近浏览、购买意向还是交易转化。
4. 查看退款订单和退款金额摘要，判断是否需要进入售后明细复盘。

### 1.5 全局页面流转

数据总览 → 获客与渠道表现  
数据总览 → 浏览与找货  
数据总览 → 购买意向与交易转化  
数据总览 → 访客 / 注册用户 / 商品分析  
数据总览 → 售后明细

### 1.6 术语说明

| 术语 | 定义 |
|---|---|
| 访客 | GA4 在所选口径下识别的访问主体，包含未登录访客和已登录用户 |
| 注册用户 | 已完成账号注册的用户，仅在账号身份分析中使用，不替代“访客” |
| 访问访客 | 周期内至少触发一次 `page_view` 的去重访客 |
| 首次访问访客 | 周期内触发 `first_visit` 的去重访客，不等于新注册用户 |
| 购买访客 | 周期内至少触发一次 `purchase` 的去重访客 |
| GA4 Purchase 数 | GA4 指标 `ecommercePurchases`，待与订单系统支付成功订单对账 |
| 成交收入 | GA4 `grossPurchaseRevenue`，表示退款前购买收入，不直接命名为财务 GMV |
| 购买意向访客 | 周期内发生收藏或加购行为的访客并集，按同一访客标识联合去重 |
| 周期结束日 | 用户所选统计周期的结束日期，订单目标卡和近 14 日趋势以该日为锚点 |

### 1.7 多语言 / 多国家策略

V1 为内部中文报表，固定 UI 文案归入后台静态 message package；指标名称、筛选项和状态文案不进入 C 端翻译中心。金额默认显示 USD。国家 / 地区筛选只改变数据范围，不改变页面结构。

## 二、需求详细描述【必写】

### 2.1 数据总览页面

#### 2.1.1 页面布局

页面按以下顺序展示：

1. 页面标题、数据状态和导出入口；
2. 全局筛选；
3. 7 个核心经营指标；
4. 售后影响；
5. 订单目标与趋势；
6. 关键行为覆盖；
7. 访问与购买转化趋势；
8. 关注与下钻。

UI 关联：PC 为“数据总览 / 经营概览·方案评审版”；APP 端不涉及。

左侧导航在 V1 仅展示当前可用的“数据总览”。访客与用户分析、流量分析、商品分析和交易转化尚未提供可切换页面时，不在左侧导航展示；已定义的业务下钻通过页面内入口承接。

#### 2.1.2 全局筛选

| 筛选项 | 默认值 | 规则 |
|---|---|---|
| 统计周期 | 过去 28 个完整自然日 | 用户可选择日期范围；所有模块使用同一周期 |
| 对比 | 上一等长周期 | 对比周期与当前周期天数相同；未取得对比数据时选项置灰并注明未载入 |
| 国家 / 地区 | 全部 | 使用 GA4 可用国家 / 地区维度筛选 |
| 端类型 | 全部端 | 枚举为全部端、App、Mobile Web、PC Web |
| App 平台 | 全部 App | 仅端类型为 App 时出现；枚举为全部 App、iOS、Android |

点击“查询”后，页面用同一组已提交筛选条件刷新全部模块。点击“重置”恢复默认筛选。订单目标、近 7 日均值和近 14 日趋势均以所选周期结束日为锚点。

查询中的重复请求按提交顺序管理，较早请求的返回结果不得覆盖较新的筛选结果。

#### 2.1.3 7 个核心经营指标

访客指标与交易指标分组展示。

| 分组 | 指标 | 计算口径 | 退款影响 |
|---|---|---|---|
| 访客规模 | 访问访客数 | `page_view` 周期去重访客 | 不影响 |
| 访客规模 | 首次访问访客数 | `first_visit` 周期去重访客 | 不影响 |
| 访客规模 | 购买访客数 | `purchase` 周期去重访客 | 退款后保留购买访客身份 |
| 访客规模 | 购买转化率 | 购买访客数 ÷ 访问访客数 | 退款后不回退 |
| 交易结果 | GA4 Purchase 数 | `ecommercePurchases` | 退款不冲减 |
| 交易结果 | GA4 成交客单价 | `grossPurchaseRevenue ÷ ecommercePurchases` | 使用退款前成交金额 |
| 交易结果 | GA4 成交收入 | `grossPurchaseRevenue` | 使用退款前成交金额 |

当前周期与上一等长周期的变化只在 KPI 区统一呈现。无对比数据时显示“对比数据未载入”。金额格式为 `$` 加千分位，客单价保留两位小数。

#### 2.1.4 售后影响

模块回答“本期发生了多少退款、金额影响多大”，位于核心 KPI 下方。

| 指标 | 口径 | 缺失处理 |
|---|---|---|
| 退款订单数 | 按退款完成日归属，对 `order_id` 或 `transaction_id` 去重；同一订单多次或部分退款计 1 个退款订单 | 缺少可去重交易标识时显示“— / 暂未接入” |
| 退款金额 | 按退款完成日汇总实际退款金额 | 查询成功且结果为 0 时显示 `$0`；查询失败或字段未接入时显示“—” |

两张指标卡下方展示普通统计口径文字：本期退款可能对应历史成交订单，不回改上方 7 个核心指标。V1 不展示简单的本期退款率；未来退款率按同一批原支付订单 Cohort 计算。

“查看售后明细”进入售后下钻。明细数据未接入时，入口进入对应空状态，不生成模拟订单。

#### 2.1.5 订单目标与趋势

模块回答“所选周期结束日的订单表现如何，距离年底 100 单 / 天目标还有多远”。

展示内容：

- 周期结束日 GA4 Purchase 数 / 100；
- 目标完成度和距离目标的订单差额；
- 较前一自然日的绝对变化和百分比变化；
- 截至周期结束日的近 7 日日均 GA4 Purchase 数及目标完成度；
- 截至周期结束日的近 14 个自然日 GA4 Purchase 趋势，并叠加 `y = 100` 目标线。

所选周期不足 7 日或 14 日时，可读取周期开始日前的历史数据补足观察窗口；页面必须标明趋势实际起止日期。自然日边界与 GA4 Property 报告时区一致，并在页面展示该时区。

#### 2.1.6 关键行为覆盖

模块回答“访问、看商品、产生购买意向、开始 Checkout、购买分别覆盖多少访客”。经营分析链路为：

`访问访客 → 商详访客 → 购买意向（收藏访客｜加购访客）→ Checkout 访客 → 购买访客`

每个指标按所选周期独立去重。箭头仅表示经营分析方向，不表示同一批访客严格依序完成全部行为。

| 指标 | 事件 / 计算 | 展示规则 |
|---|---|---|
| 访问访客 | `page_view` 去重访客 | 展示人数，占访问访客 100% |
| 商详访客 | `view_item` 去重访客 | 展示人数和占访问访客比例 |
| 收藏访客 | `add_to_wishlist` 或已确认的自定义收藏事件去重访客 | 展示人数和占访问访客比例 |
| 加购访客 | `add_to_cart` 去重访客 | 展示人数和占访问访客比例 |
| 购买意向访客 | 对收藏事件或加购事件筛选后联合去重 | 展示人数和购买意向覆盖率 |
| Checkout 访客 | `begin_checkout` 去重访客 | 展示人数和占访问访客比例 |
| 购买访客 | `purchase` 去重访客 | 展示人数和占访问访客比例 |

购买意向覆盖率 = 购买意向访客 ÷ 访问访客。收藏与加购可能覆盖同一访客，两项人数不能直接相加。购买访客是交易结果，不加入购买意向访客集合。

Looply 列表页商品卡片可直接收藏，因此收藏访客不是商详访客子集。页面不计算“商详 → 收藏”的转化率或流失率。

收藏事件未接入时：收藏访客、购买意向访客和购买意向覆盖率显示“—”，并分别标注“收藏事件待接入”和“数据不完整”；加购访客继续展示真实值。

#### 2.1.7 访问与购买转化趋势

模块回答“流量规模发生了什么变化，购买转化效率是否同步改善”，使用两张并列单坐标轴图：

| 图表 | 数据 | 业务问题 |
|---|---|---|
| 每日访问访客趋势 | 每日 `page_view` 去重访客 | 流量规模如何变化 |
| 每日购买转化率趋势 | 当日 `purchase` 去重访客 ÷ 当日 `page_view` 去重访客 | 购买效率如何变化 |

每日访客数用于日趋势，不跨日相加生成周期访客。周期购买转化率使用周期去重购买访客 ÷ 周期去重访问访客，不使用每日转化率的算术平均值。

购买访客总数在顶部 KPI 展示，趋势模块不重复展示每日购买访客折线。两张图各自使用单一纵轴，Tooltip 展示日期和当前图表的真实值。

#### 2.1.8 关注与下钻

总览只提供少量业务入口，不自动生成无法解释的异常结论。

| 入口 | 下钻回答的问题 |
|---|---|
| 获客与渠道表现 | 用户首次从哪里来，渠道规模和质量如何 |
| 浏览与找货 | 推荐、搜索、类目和商详到达是否有效 |
| 购买意向与交易 | 收藏 / 加购、Checkout、订单创建和支付失败发生在哪里 |
| 访客、注册用户与商品分析 | 留存、复购、身份分层及品牌 / 品类 / 商品表现如何 |
| 售后明细 | 哪些订单、商品和原因造成退款 |

### 2.2 页面状态与异常处理

| 状态 | 页面行为 |
|---|---|
| 首次加载 / 查询中 | 保留页面结构，数据区域显示加载状态；查询按钮防止重复提交 |
| 查询成功 | 一次性更新与当前筛选条件匹配的全部成功模块 |
| 单模块无数据 | 对应模块显示“暂无数据”，其他模块继续展示 |
| 指标未接入 | 指标值显示“—”，同时展示具体缺失原因 |
| 单模块查询失败 | 对应模块显示失败状态和“重试”；其他成功模块继续展示 |
| 全页查询失败 | 页面显示失败状态和“重试”，保留已提交的筛选条件 |
| 无访问访客 | 购买转化率显示“—”，不执行除零计算 |
| 无权限 | 页面提示当前账号无报表访问权限，不展示经营数据 |

本页面为只读报表，不涉及数据写入、编辑和删除，因此不存在业务数据写入冲突。导出时使用当前已成功查询的筛选条件和结果。

### 2.3 验收标准

1. 全局筛选提交后，所有模块使用同一日期、国家 / 地区和端类型条件。
2. 7 个核心指标均使用成交发生时口径，退款后数值不回改。
3. 退款订单数与 refund 事件数严格区分；无法按订单去重时显示“—”。
4. 收藏事件缺失时，收藏和购买意向相关指标显示缺失状态，加购真实值仍展示。
5. 关键行为覆盖中的收藏、加购并列，箭头不展示相邻转化或流失。
6. 趋势模块只有访问访客和购买转化率两张单轴图，没有双坐标轴和每日购买访客折线。
7. 周期购买转化率不使用每日转化率平均值。
8. 任一模块失败时，其他已成功模块继续展示。

## 三、依赖与风险【必写】

### 3.1 兼容性与约束

- GA4 适合行为分析；支付成功订单、财务 GMV 和订单级退款最终以订单系统 / Shopify / 财务数据为准。
- 游客可以使用多项功能并下单，所有“访客”指标必须覆盖未登录和已登录身份。
- 跨设备、匿名转登录合并取决于 GA4 Reporting identity、User-ID 和 Looply 统一访客身份的实际实施情况。
- `add_to_wishlist` 尚未在当前线上事件清单中观察到；收藏事件接入前不生成购买意向并集。
- GA4 当前可查询 `refundAmount` 和 refund 事件数，但 refund 事件数不能替代去重退款订单数。

### 3.2 依赖与关键要求

| 依赖 | 提供内容 | 关键要求 |
|---|---|---|
| GA4 Data API | 访客、行为、Purchase、收入、退款金额和按日趋势 | 同一查询必须使用一致的日期、过滤条件、报告身份和 Property 时区 |
| C 端埋点 | 收藏、加购、Checkout 和 Purchase 事件 | 事件在业务成功后触发；收藏需覆盖列表页和商详页入口 |
| 订单系统 / Shopify | 支付成功订单、订单金额、退款订单和退款金额 | `transaction_id` 与订单标识可对账；退款记录可按退款完成时间和原订单关联 |
| 统一访客身份 | 游客、登录用户和购买订单的身份关联 | 使用非 PII 稳定标识，明确匿名转登录和跨端合并规则 |
| 经营目标配置 | 年底目标 100 单 / 天 | 目标适用市场、自然日时区和生效日期需与报表一致 |

### 3.3 主要风险

| 风险 | 影响 | 处理 |
|---|---|---|
| Purchase 重复或漏报 | Purchase 数、收入和客单价失真 | 使用 `transaction_id` 与订单系统逐单对账 |
| 首次访问事件异常偏高 | 首次访问访客解释错误 | 排查 Cookie 生命周期、跨域和重复初始化 |
| 收藏事件缺失 | 购买意向总数和覆盖率无法计算 | 显示缺失状态，完成埋点后再开放 |
| 退款缺少订单标识 | 退款订单数无法去重 | 仅展示真实退款金额，订单数显示未接入 |
| 时区不一致 | 日目标和按日趋势错位 | GA4、订单系统和经营目标统一自然日边界 |

## 四、版本规划【必写】

### 4.1 当前版本 v0.1

完成数据总览页面结构、指标口径、缺失状态和下钻边界；使用当前可取得的 GA4 数据展示，订单与退款订单级数据按接入状态呈现。

### 4.2 后续迭代方向

- 接入订单系统 / Shopify，完成支付成功订单、GMV 和退款订单对账；
- 接入收藏事件，开放购买意向访客联合去重指标；
- 在交易转化下钻建设购买前行为路径构成；
- 根据管理需要增加按订单 Cohort 计算的退款率；
- 接入统一访客身份，提升游客、登录用户和跨端身份合并质量。

## 五、数据与埋点【按需】

### 5.1 关键事件

| 事件 | 业务触发 | 总览用途 |
|---|---|---|
| `page_view` | 页面访问被记录 | 访问访客、访问趋势和转化率分母 |
| `first_visit` | GA4 识别为首次访问 | 首次访问访客 |
| `view_item` | 商品详情核心内容可见 | 商详访客 |
| `add_to_wishlist` | 收藏事务成功 | 收藏访客和购买意向访客 |
| `add_to_cart` | 加购事务成功 | 加购访客和购买意向访客 |
| `begin_checkout` | Checkout 已成功开始 | Checkout 访客 |
| `purchase` | 订单后端确认支付成功 | 购买访客、Purchase 数和成交收入 |
| `refund` | 退款完成并上报 | 退款金额和 refund 事件辅助核验 |

### 5.2 数据计算约束

- 周期访客指标必须对完整日期范围重新去重，不将每日访客数相加。
- 购买意向访客通过收藏事件或加购事件筛选后联合去重，不将两项人数相加。
- Purchase 数优先使用 `ecommercePurchases`；成交收入使用 `grossPurchaseRevenue`。
- 退款金额使用 `refundAmount`；退款订单数需要订单标识去重。
- 缺失字段显示“—”，查询成功且真实值为 0 时显示 0。
